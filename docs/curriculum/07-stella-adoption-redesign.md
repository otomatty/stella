# 新カリキュラムをstellaに載せる再設計案

作成日 2026年10月5日  
版 0.1  
状態 提案  
[全体設計へ戻る](00-overall-design.md)

00〜06の新カリキュラム(版2.2)を、stellaの教材形式・実行・評価・スキルツリーへ載せるための再設計案である。2026年10月5日時点のstella(`main`)を調べ、オーナーが決めた方針(§1)に沿って提案する。「教材の単位」と「学習画面の置き場所」は未決のため、判断材料と選択肢を示すにとどめる。

本書の「講座」はstellaの`packages/content/courses/<slug>/`(D1の`stages`、画面の「ステージ」)を指す。新カリキュラムの「教材パック」は講座1つに対応させ、新カリキュラムの「コース」(卒業までの全体)はプログラムと呼んで区別する。

## 2 設計の原則

1. **エディタはIDEにだけ置く。** LMS(Web)は、読む・知識問題に答える・進み具合と評価結果を見る・レビューする場所にする。コードを書く・実行する・提出する操作はIDEで完結させる。
2. **「手元で確かめる」と「正式に評価する」を分ける**(04 §7)。手元のテスト成功は練習の証拠であり、自力確認の合格ではない。
3. **人の時間は、人にしか判断できないところに使う。** 機械で判定できる受入条件は機械に任せ、講師・メンターは説明・設計判断・つまずきの解消・励ましに使う。
4. **配信は常に最新にし、記録の側に「どの内容で何をしたか」を残す。** 版を固定しない代わりに、提出や証拠に教材の内容ハッシュを残す。
5. **残す講座(C・D群)は今の仕組みのまま動かす。** 新形式は旧形式と並走させ、旧講座を新形式へ移すことは前提にしない。

### 3.2 旧講座の退役

講座のディレクトリを消しても、D1のステージは消えない。seedは載っている講座をupsertするだけで、載っていない講座のステージは`published`のまま残る(`packages/shared/scripts/export-seed-sql.ts`)。唯一の削除の仕組み`RETIRED_DEMO_STAGES`は、受講登録・進捗・提出・修了証まで削除するため使わない。

提案は、seedに「アーカイブする講座」の一覧を足し、`status='archived'`にするだけで行は残す方式である。アーカイブしたステージは、スキルツリー・ステージ一覧・検索・SRSから外れる(`apps/api/src/lib/skill-map-data.ts`ほか)。修了証と提出履歴は残る。

CMSの`PATCH /api/cms/stages/:id/status`でもアーカイブできる。ただし、公開中の講座がそのslugを前提にしている間は拒否される。前提を付け替えたseedを流してからアーカイブする。

### 3.3 it-basicsの削除

it-basicsはスキルツリーの唯一の根であり、4つの島の表示条件でもある。次を同じ変更で行わないと、検査やseedが落ちるか、島が誰にも見えなくなる。

| 対象 | 変更 | 変えない場合 |
| --- | --- | --- |
| html-css-basics, sql-basics の`course.json` | 退役する講座なので、講座ごとアーカイブへ回す | — |
| fe-kamoku-a, aws-clf-c02-basics, ai-fluency-basics の`course.json` | `prerequisites: ["it-basics"]` → `[M01のslug]` | `assertPrerequisiteGraph`が「存在しない講座」で落ちる。CI・seedも止まる |
| `packages/shared/src/skill-map/islands.ts` | AWS資格・情報処理資格・AI駆動開発・Salesforce案件の`requires`を、M01のslugにする | 未知のslugは「決して満たされない」扱いになり、4島が全員から黙って消える |
| `packages/content/scripts/build_thumbnails.py` | `SPECS["it-basics"]`を消し、M01の項目を足す | 引数なしの実行が「course.jsonがありません」で止まる |
| テスト | `manifest.test.ts`、`export-seed-sql.test.ts`、`islands.test.ts`がit-basicsを前提にしている | テストが落ちる |
| 文書 | `AGENTS.md`、`packages/content/CLAUDE.md`(唯一の前提なし講座・動画PoCの説明)、`helpContent.ts`の受講者向けヘルプ | 説明が古くなる |
| D1の旧ステージ | seedの後にアーカイブする | 根が2つになり、中心の星が描かれない。配置ウィザードにも旧講座が出続ける |

動画のPoCは、it-basicsだけが全トピックの台本(`narration.json`)を持っている。PoCを続けるなら、M01の解説トピックに移す。

**既存受講者の後退に注意する。** it-basicsをクリアしてM01をクリアしていない受講者は、4島が見えなくなる。旧講座(html-css-basicsなど)の続きも、M01からやり直しになる。提案は次の2つである。

- M01の開始診断(06の確認A相当)を、既存受講者が短時間で受けられるようにする。合格すればM01をクリア扱いにする。
- 移行期間だけ、島の表示条件で「M01またはit-basicsのクリア」を認める。いまの`requires`はANDだけなので、ORを書けるようにする。

## 4 教材の単位とファイル形式(再提案)

### 4.1 単位の対応(2案)

新設計は、プログラム ＞ パック ＞ 単元(3〜10時間) ＞ 課題セット ＞ 課題で、1コマは60〜90分である(03 §3)。stellaは、講座 ＞ モジュール ＞ レッスン(LMSの1回分) ＞ トピック(2〜3分の動画1本)である。

| | 案1 単元=モジュール(推奨寄り) | 案2 単元=レッスン |
| --- | --- | --- |
| パック | 講座(ステージ) | 講座(ステージ) |
| 単元 | モジュール(D1のsection) | レッスン |
| 1コマ | レッスン | なし(単元の中の区切り) |
| 解説 | トピック(1 Takeaway、語彙台帳) | トピック |
| 課題 | 単元に属するタスク | レッスンに属するタスク |
| 利点 | 今の3層と語彙台帳・PDF・動画の仕組みをそのまま使える。1コマ単位で進捗を出せる | 階層が浅く、短い単元を作りやすい |
| 欠点 | モジュールの意味が「大テーマ」から「単元」に変わる | 3〜10時間・課題20問前後の単元が1レッスンになり、進捗と画面が粗くなる |

本書の以降の説明は案1で書く。案2でも、タスクの置き場所が単元直下からレッスン直下へ移るだけで、ほかの設計は変わらない。

### 4.2 何をどこで使うか

| 要素 | 正本 | 受講者が使う場所 |
| --- | --- | --- |
| 解説(スライド・動画・まとめ) | トピックの`slides.md`、レッスンの`doc.md` | 学習画面(§12で決める) |
| 知識問題 | レッスンの`knowledge.md` | アプリ。SRSの対象 |
| 演習課題(基礎Q・接続C・自力S・修正R・統合T) | 単元の`tasks/<id>/` | IDE(拡張の課題パネル) |
| 確認A・B | `tasks/<id>/`と、配らない予備の類題 | IDE。正式評価はサーバー側 |
| 参照元 | 共通の台帳と単元の`references.json` | 解説・課題の近くと、単元の末尾 |
| ヒント・解答・解説 | `tasks/<id>/hints.md`、`private/` | 解放条件を満たしたあとにIDEとアプリで |
| 進み具合・評価結果・レビュー | D1 | アプリ |

LMSはタスクの一覧と状態(未着手・手元で合格・提出済み・評価済み)だけを表示する。「VS Codeで開く」から課題を開き、Web上にエディタは置かない。今のWeb提出欄(`AssignmentSubmitPanel`の単一テキスト欄)は新形式では使わない。

### 4.3 ディレクトリ案

既存の`modules/<m>/<l>/<t>/`を単元・コマ・解説としてそのまま使い、単元の直下に`unit.json`・`references.json`・`tasks/`を足す。旧形式の講座と同じ読み込み処理(`packages/content/src/manifest.ts`)を拡張して扱える。

```text
packages/content/
  sources/registry.json          # 参照元の台帳(全講座で共有)
  environments/<id>.json         # 実行環境の定義(Node・ライブラリ・OS・ブラウザの版)
  skills.json                    # スキルIDの台帳
  patterns.json                  # 実装パターンの台帳(類題の単位)
  courses/<pack-slug>/
    course.json                  # format: 2、packId、plannedHours、environment ほか
    CURRICULUM.md
    modules/<unit>/              # 単元
      unit.json                  # 予定時間、使うスキル、評価するスキル、再利用する成果物
      references.json            # 本文・課題と参照元の対応
      <lesson>/                  # 1コマ
        <topic>/slides.md        # 解説。1 Takeaway・語彙台帳・4〜6枚は今の規則のまま
        doc.md                   # まとめ。OS別ブロックを書ける(§11)
        knowledge.md             # 知識問題
      tasks/<task-id>/
        task.json                # 種別、パターン、runner、提出ファイル、評価、支援
        README.md                # 課題文(IDEの課題パネルに出す)
        starter/                 # 配布するファイル
        tests/                   # 手元で走る公開テスト
        hints.md                 # 段階的なヒント
        private/                 # 受講者へ配らない
          solution/              # 解答例
          explanation.md         # 解説
          tests/                 # 正式評価だけで使う非公開テスト
          variants/              # 確認A・B・復習用の予備の類題
```

`task.json`の主な項目は次のとおりとする。

| 項目 | 内容 |
| --- | --- |
| `id` | パック・単元・課題を含む一意のID。短い`Q01`だけで結果を保存しない(04 §3) |
| `kind` | `basic` / `connection` / `independent` / `debug` / `integration` / `assessment-a` / `assessment-b` |
| `pattern` | 実装パターンのID。類題と復習の単位(§7) |
| `skills` | `uses`(使うスキル)と`assesses`(評価するスキル)を分ける(04 §1) |
| `runner` / `environment` | 実行定義のIDと実行環境の版(§5) |
| `submit` | 提出するファイルのglob、説明欄の要否、修正演習の記録欄の要否 |
| `evaluation` | 手元の公開テスト、正式評価の有無、課題ごとのルーブリック(03 §8) |
| `support` | ヒントの段数、解答を解放する条件(§8) |
| `sources` | 参照元ID(§9) |
| `estimatedMinutes` | 予定時間。ペースの計算に使う(§10) |

### 4.4 受講者の作業フォルダー

今の拡張は、課題ごとに`~/.stella/exercises/<課題ID>/`を作り、ワークスペースフォルダーとして追加している。その結果、ウィンドウが無題のマルチルートになる。新設計では、前のパックで作ったもの(M04の検証関数など)を後のパックで使い直すため、課題ごとにばらばらのフォルダーは合わない。

提案は、プログラム全体で1つの学習フォルダー(06 §3 の`web-training`)を使う方式である。拡張はその中の`<pack>/<unit>/<task>/`へ配布ファイルを置く。

- 学習者のファイルは上書きしない。衝突したら、準備先と衝突を表示する(04 §6)。
- M01 U05から、このフォルダーをGitで管理する。前の成果物を使う課題は、学習者自身のファイルを参照する。
- 前の実装が壊れていて進めない場合は「固定した開始点」を配る。使ったことを記録する(01 §4)。

### 4.5 既存の仕組みとの関係

- `course.json`に`format: 2`を足し、新形式の講座だけ`tasks/`・`unit.json`・`knowledge.md`を読む。C・D群の講座は今のまま動く。
- 課題は`packages/shared/src/problems/`のTypeScriptファイルではなく、教材リポジトリの`tasks/`を正本にする。D1にはタスク用の表を新しく作り、今の`assignments`表(QuickJS用)は旧形式の講座に残す。
- `practice.md`の「解答例と解説」と確認クイズは、新形式では`private/`・`knowledge.md`へ分ける。受講者向けPDFの解答編は、新形式では作らない(§8)。
- 検査を足す。`task.json`のスキーマ、公開テストが解答例で通ること、`private/`が配信物や公開APIに混ざらないこと、参照元(§9)、OS別ブロック(§11)を確認する。語彙台帳とスライド4〜6枚の検査は、解説トピックにそのまま使う。

## 5 演習の実行・採点基盤(再設計の要件)

基盤はオーナーが再設計する。ここでは、新カリキュラムとstellaの現状から決まる要件をまとめる。

### 5.1 現状

- 採点は拡張内のWebView(QuickJSとsql.js)だけで行う。DOM・`fetch`・タイマー・モジュール・Node APIがなく、1回3秒・32MBで止まる(`packages/code-runner/src/quickjs-runner.ts`)。
- 拡張は外部プロセスを起動しない(`child_process`・ターミナル・Tasks APIのどれも使っていない)。Workspace Trustも確認していない。
- 採点結果はサーバーへ送られない。合格すると拡張が`POST /api/lesson-progress`でレッスン完了を送るだけで、サーバーはその値を信頼する。
- 課題の公開API(`GET /api/cms/assignments/:id`)は、テストの式・期待値・SQLの初期データを受講者にも返す。

### 5.2 runnerの一覧(案)

| runnerId | 使うパック | 手元での実行 | 正式評価 |
| --- | --- | --- | --- |

### 5.3 拡張に求めること

- 実行は、拡張に同梱した実行定義(runnerIdごとの固定の引数)だけで行う。WebView・LMS・課題ファイルから受け取った文字列をコマンドとして実行しない(04 §6)。
- `capabilities.untrustedWorkspaces`を宣言し、信頼していないフォルダーでは実行しない。
- `stella.serverUrl`がワークスペース設定(`.vscode/settings.json`)で上書きできる。このままだと、学習用プロジェクトの設定一つでJWTが別のサーバーへ送られる。外部のプロジェクトを開く前提にする前に、ユーザー設定に限定する。
- 手元の結果(runner、テスト名、成否、所要時間、内容ハッシュ)をAPIへ送る。完了の自己申告だけで記録しない。
- 提出・採点で読むのは`submit`で宣言したファイルだけにする。今は作業フォルダーの全ファイルを再帰的に読むため、`node_modules`があると全部を読んでしまう。
- Node導入前(M01 U00〜U03)は`static-preview`と手動確認だけで進められるようにする。

### 5.4 正式評価の場所(要検証)

Cloudflare WorkersではNodeのツールチェーンやブラウザを動かせない。候補は次のとおり。

| 候補 | 利点 | 懸念 |
| --- | --- | --- |
| コンテナ実行(Cloudflare Containers等) | 今の構成に近い。非公開テストを受講者に渡さない | 費用と起動時間 |
| 受講者ごとの非公開リポジトリとGitHub Actions | M16のCIと地続き。ログが残る | 序盤からGitHubアカウントが要る(06は後続教材で導入する方針) |
| 講師・メンターの手元で実行 | 追加の基盤が要らない | 負担が増え、原則3に反する |

確認A・B・統合Tだけを正式評価の対象にすれば、実行回数は課題全体のごく一部で済む。

## 6 提出・評価・レビュー

### 6.1 2系統の評価

- **知識:** アプリで回答する。今の小テスト(単一選択・複数選択・正誤。サーバー側で採点)を使う。教材から投入できるのは今は単一選択だけなので、`knowledge.md`から複数選択・正誤も書けるようにする。
- **実装:** IDEからファイルを提出し、評価する。提出は「宣言したファイル + 手元の結果 + 説明 + 支援の記録 + 課題の内容ハッシュ」を1組にする。

### 6.2 課題の種別ごとの経路

| 種別 | 手元 | 提出 | 機械の評価 | 人 |
| --- | --- | --- | --- | --- |
| 基礎Q・接続C | 公開テスト | 手元で合格した時点で自動送信(証拠として保存) | なし | 見ない。つまずいたときだけ |
| 自力S | 公開テスト | 短い説明つきで提出 | AIの所見を受講者へ直接返す(AIによる所見と明示) | 抜き取りで確認 |
| 修正R | 再現手順 | 再現・原因・修正・回帰確認の記録つき(03 §6) | AIが記録と差分の整合を確認 | 抜き取りで確認 |
| 統合T | 公開テスト | 説明つき | 非公開テスト + AI下書き | 確定する |
| 確認A・B | 公開テストの一部 | 説明つき。ヒント・解答は使えない | 非公開テスト + AI下書き | 確定し、スキルを「自力で確認」「時間を空けて確認」にする |

### 6.3 レビューの負担を減らす

今のレビューは、テナントの全提出を新しい順に並べるだけである。並べ替え・絞り込みは「今後対応」で、AI下書きは講師が画面を開いてから作る。下書きは課題文・テスト・解答例を知らない。

1. **人が見る提出を絞る。** 人が見るのは、統合T・確認A/B・引継ぎと、抜き取りだけにする。基礎・接続の課題は機械の証拠で完結させる。
2. **AI下書きを提出時に作る。** 入力に、課題文・課題ごとのルーブリック・解答例・よくある誤り・非公開テストの結果を渡す。講師が開いた時点で下書きがそろっている。
3. **課題ごとのルーブリック。** 今はAIと固定の4項目である。`task.json`に03 §8 の評価対象(デザイン、部品の契約、操作、画面連携、失敗と境界、変更と説明)を書く。
4. **コメント集。** パターンごとによくある誤りと定型コメントを持ち、選んで直して送れるようにする。
5. **まとめて見る。** 同じ課題の提出を並べ、共通のつまずきは全体への補足やつまずき教材(Discovery)へ回す。
6. **キュー。** 優先度・待ち時間・担当者で並べる。管理者もレビューできるようにする(今はAPIでは可能でも、画面に入口がない)。
7. **提出前のセルフチェック。** 提出画面に受入条件のチェックリストを出し、差し戻しを減らす。
8. **ワンクリック確定。** 機械の評価が全合格で、AIの重大な指摘がなければ、人は所見を確認して確定するだけにする。

### 6.4 一人ひとりを育てる

- **担当メンター。** 今は講師と受講者を結ぶ担当の仕組みがない。受講者にメンターを割り当て、キューとダッシュボードを担当分に絞れるようにする。
- **週次の育成メモ。** 予定と実績の差(§10)、スキルの状態、つまずき、支援の量、レビュー結果から、AIが1人1枚の要約を作る。メンターは5分で読み、一言の声掛けか、ペースの調整をする。
- **つまずきの検知。** 同じ課題で手元の失敗が続く、ヒントを最後まで開く、数日進まない、確認Bに落ちる、を検知してメンターに知らせる。
- **支援の記録。** ヒント・解答の表示、引継ぎ、講師の介入、AIチャットの利用を課題ごとに記録し、習得の水準(03 §7 の未確認・支援付き・自力・時間を空けて確認)に反映する。受講者自身にも見せる。
- **ピアレビュー(選択肢)。** M15のレビュー単元から、受講者同士で自力S・統合Tの提出をレビューする。レビューそのものを学習の証拠にし、メンターはレビューの質を見る。

### 6.5 データの変更

- `submissions`を、1つの`code`列からファイル単位の保存(R2)へ変える。課題ID・内容ハッシュ・種別・手元と正式評価の結果・説明・支援の記録を持たせる。上書きせず、試行ごとの履歴を残す。
- AIの指摘を、行番号だけでなくファイルと行範囲に付ける。
- スキルと証拠の表を足す(スキルID、水準、根拠になった提出、支援の有無、日時)。
- 講座のクリア条件に、課題の正式な評価結果を使う。今はVS Codeの課題(`code`レッスン)が課題合格の条件に入らず、完了は自己申告である。講師が合格にしてもレッスンは完了にならない。
- 未判定のAI所見が受講者に見えている(`ReviewResultView.tsx`)。判定済みだけを見せる。

## 7 復習

### 7.1 知識はSRS

今のSRS(`review_cards`、SM-2、1日20枚)をそのまま使う。カードの元を`knowledge.md`の知識問題に限り、スキルと結び付ける。

### 7.2 コードはパターン単位の類題

SRSは同じ設問を解き直させる。コードでは、同じ実装パターンの別の問題(類題)を時間を空けて出す。

- **パターンの台帳。** 単元の基礎課題は「値・条件・境界・組合せ・利用場面」を変えた同じパターンの問題群である(03 §2)。その単位を`pattern`として登録する。
- **類題の在庫。** パターンごとに、練習用の課題(公開)と、確認A・B・復習用の予備(`private/variants/`)を持つ。予備は受講者ごとに出題済みを記録し、見た問題を「未見」として出し直さない(03 §7)。
- **出す時期。** 自力で合格したパターンは、約3日後・約1週間後(=確認B)・約3週間後に類題を出す。支援付きでしか解けなかったパターンは間隔を短くし、補習の小問題3問と翌日以降の未見問題へつなぐ(03 §7)。
- **作り方。** データや条件を差し替えられる課題は、テンプレートとパラメータから類題とテストを作る。AIで類題の下書きを作ってもよいが、解答例が全テストに通り、典型的な誤答(ミュータント)が落ちることを機械で確かめ、人が承認してから在庫に入れる(今のDiscoveryと同じく承認制)。
- **毎日の復習画面。** 知識のカードと「今日の類題」1問を並べる。類題は「VS Codeで開く」から解く。

## 8 解答と非公開素材のUX

解答を「隠す」より、「出す順番」を設計する。練習で行き詰まらせないことと、自力確認の結果を正しく残すことを両立させる。

| 種別 | 取り組み中 | 合格後 | 備考 |
| --- | --- | --- | --- |
| 基礎Q・接続C | ヒントを段階的に開ける(方針 → 手がかりのコード → 解答例) | 解答例と解説を自動で開く。自分のコードと並べて見られる | ヒントや解答を開くと「支援付き」になる。罰ではなく記録 |
| 自力S・修正R | ヒントは開ける。解答例は一定回数の挑戦後か合格後 | 解答例・別解と、選び方の理由 | 支援の段数を証拠に残す |
| 統合T | 仕様・状態見本・API契約へのリンクだけ | レビューの所見と解答例 | — |
| 確認A・B | 公式ドキュメントと文法の参照だけ(03 §7) | 評価の所見。Aの解答例は確定後に開く | 予備の類題は出題前も後も見せない |

- ヒントと解答はIDEの課題パネルに出す。今のパネルは課題文と採点結果しか出さない。
- `private/`はseedでD1・R2の非公開の場所へ入れ、公開APIは解放条件を満たした受講者にだけ返す。非公開テストは正式評価の環境にだけ渡し、受講者の端末へは送らない。
- 配布・印刷用のPDFは、新形式では課題文・参照元・解説だけにし、解答編を作らない。
- **公開前に確かめること。** 今の公開APIは課題のテストを受講者へ返す。Webの`AIChatBot.tsx`は`@stella/shared/assignments`を読み込んでおり、課題の解答がWebのJSに含まれている可能性がある(未検証)。
- **正本の置き場所。** 教材リポジトリを受講者が読める運用なら、`private/`は別の非公開リポジトリか非公開の保管場所へ移す。

## 9 参照元(新設計05を採用)

- `packages/content/CLAUDE.md`の絶対ルール3「クレジット表記を教材本体に入れない」を、05に沿って書き換える。`STYLE_GUIDE.md`と`THEME_TO_COURSE.md`の外部素材の節も合わせる。
- 台帳は`packages/content/sources/registry.json`(05 §8 の`source-registry.json`)、使用箇所は単元の`references.json`に置く。トピック・まとめ・課題の冒頭(front-matter・`task.json`)には、参照元IDを書く。
- 表示は3か所にする。解説・課題の近く、単元の末尾の一覧、配布PDFである。IDEの課題パネルにも出す。
- 版は常に最新を配信するため(§13)、公開の関門はCIに置く。`content:check`は次の場合に失敗させ、`main`へ入れない。
  - 未登録のsourceRefがある。
  - 技術のトップページだけを根拠にしている。
  - レビュー状態が`approved`でない。
  - 環境の定義がない。
- リンク切れは週1回の定期ジョブで確認する。タイムアウトやアクセス制限は削除と分け、手動確認として記録する(05 §9)。
- 残す講座(C・D群)への適用範囲は決める必要がある。提案は、新規作成と改訂のときから必須にし、それまでは警告だけにする方式である。

## 10 ペースの自動設定

今は、学習計画のデータがない。`stages.duration_hours`は教材から入らず、全講座で空である。ステージ一覧は空のとき「約20時間」と固定値を出している。受講登録の期日は、自分で開始した講座では入らない。

- **入力:** パック・単元・課題の予定時間(`course.json`の`plannedHours`、`unit.json`、`task.json`)、プログラムの標準(週35時間)、受講者の週あたりの時間と開始日。
- **既定:** 受講者がM01を始めた日を開始日にし、週35時間で計算する。週30時間なら約42週、週40時間なら約32週になる(00 §5)。受講者・メンターが週の時間を変えると、残りを計算し直す。
- **出すもの:** 今週の目安(単元とコマ)、各パックの目標日、予定との差(進んだ予定時間で測る。費やした時間では測らない)。確認Bは確認Aの合格から7日後に自動で予定する。
- **遅れたとき:** 罰を与えず、残りの予定を引き直す。差が1週間を超えたらメンターに知らせる(§6.4)。補習の2〜4週間は別枠として、予定の計算に含めない。
- **開始診断:** 確認できたスキルの練習時間を予定から差し引く。確認A・Bは差し引かない(00 §5)。
- **データ:** 受講者の設定(週の時間・開始日)をプロフィールへ足し、`/api/me`で編集できるようにする。予定日は保存せず、その都度計算する。`duration_hours`は`plannedHours`から入れ、固定値の「約20時間」はなくす。

## 11 OS別の手順

可能である。ただし、今の描画は4系統(Webの`react-markdown`、VS CodeのWebView、PDF・動画、pptx)に分かれている。WebとVS Codeは生のHTMLを文字として出し、VS CodeのWebViewは画像も出せない。そこで範囲を絞る。

- **書ける場所を限る。** OS別のブロックは、まとめ(`doc.md`)と課題文(`README.md`)だけに書く。スライドと動画はOSに依存しない説明にし、pptxと動画の生成は変えない。
- **書き方:**

  ```markdown
  :::os windows
  PowerShellで次を実行します。
  :::
  :::os macos
  ターミナルで次を実行します。
  :::
  ```

- **見せ方:** OSのタブにし、既定は受講者のOSにする。拡張は`process.platform`で正確に分かる。Webは利用者のOS情報から推定し、プロフィールの設定で上書きできるようにする。「あなたのOS: Windows(変更)」と表示する。
- **画像:** `name.windows.png` / `name.macos.png`のように、OSごとに用意する。
- **PDF:** M01のようにOS差が大きい講座は、OS別にPDFを作る。それ以外は、両方を見出し付きで並べる。
- **検査:** OS別のブロックは、WindowsとmacOSの両方がそろっていること、画像がOSごとにあることを確かめる。
- **環境診断:** 拡張がOSに応じて確認コマンドを変える(例:Windows PowerShellの`npm.cmd`、06 §3)。

## 12 学習画面の置き場所(判断材料)

未決のため、どちらの案にも寄せない。ただし、次はどちらに決めても変わらない。

- IDEに課題パネルが要る(課題文・ヒント・実行・提出・結果・参照元)。
- 環境診断と実行は拡張の仕事である。
- VS Code導入前のM01 U00〜U01は、ログインなしでブラウザで読める必要がある。今のWebは、未ログインではログイン画面しか出さない。
- 管理・レビュー・知識問題・SRSはアプリに置く。

| 観点 | VS Code(WebView)に置く | Webに置く |
| --- | --- | --- |
| 解説と演習の行き来 | 同じ画面で横に並べられる | ウィンドウを切り替える |
| VS Code導入前の閲覧 | できない(別途Webが要る) | できる |
| 環境の確認 | 拡張が端末の状態を読める | 読めない |
| 動画・図解 | 今のWebViewは画像すら出せず、作り直しが要る。動画の再生方式は要検証 | 今の仕組み(動画・スライド・図解)をそのまま使える |
| スマートフォンでの知識問題・SRS | できない | できる |
| 開発の手間 | 解説の描画をWebViewにも作る。2系統の保守 | 今の画面を使える |
| 印刷・PDF | 影響なし | 影響なし |
| 学習の中断と再開 | VS Codeを開けば続きから | ブラウザとVS Codeの両方を開く |

決めるための試行は、00 §6 の最初の試行(M01の導入案内からVS Code内での学習開始・翌日の再開まで)に組み込むのがよい。観察する値は次のとおり。

- 画面を切り替えた回数
- 最初にHTMLの変更を表示できるまでの時間
- 途中で止まった場所
- 支援の量
- 翌日の再開にかかった時間

## 13 版の運用(常に最新)

- 提出・証拠・正式評価に、課題の内容ハッシュを残す。レビューでは、受講者が見ていた課題文を出す。
- 合格済みの課題のテストを後から厳しくしても、過去の合格は取り消さない。
