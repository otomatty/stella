作成日 2026年10月5日  
版 0.7\
状態 提案

00〜06の新カリキュラム(版2.2)を、stellaの教材形式・実行・評価・スキルツリーへ載せるための再設計案である。2026年10月5日時点のstella(`main`)を調べ、オーナーが決めた方針(§1)に沿って実装方法を提案する。学習画面の採用先は、`dev-env-basics`の試行後に決める。

[Issue #26](https://github.com/otomatty/stella/issues/26)の着手前の方針を2026年10月5日に決定し、§1と各節に反映した。後続の作業は§15.1にまとめる。学習画面については、比較手順を確定し、採用先を§15の未決事項に残す。

本書の「講座」はstellaの`packages/content/courses/<slug>/`(D1の`stages`、画面の「ステージ」)を指す。新カリキュラムの「教材パック」は講座1つに対応させ、講座はslugの名前で呼ぶ。00〜06はM01〜M18の番号で書かれているため、番号との対応は§3.1の表で引く。新カリキュラムの「コース」(卒業までの全体)は、本書ではプログラムと呼ぶ。

## 2 設計の原則

1. **エディタはIDEにだけ置く。** LMS(Web)は、読む・知識問題に答える・進み具合と評価結果を見る・レビューする場所にする。コードを書く・実行する・提出する操作はIDEで完結させる。
2. **動作は受講者が確かめ、レビューは規則を見る。** 動くかどうかは、手元の実行結果で受講者が確かめて直す。AIと人のレビューは、テストやlintでは判定できないコーディング規則などを見る。サーバーではコードを実行しない。
3. **人の時間は、人にしか判断できないところに使う。** 人が必ず見るのは、人に回す条件(§6.3)に当たった提出だけにする。AIが合格にした提出は、人が好きなときに確認できる。講師は、残りの時間をつまずきの解消と励ましに使う。
4. **配信は常に最新にし、記録の側に「どの内容で何をしたか」を残す。** 版を固定しない代わりに、提出に教材の内容ハッシュを残す。
5. **残す講座は今の仕組みのまま動かす。** 新形式は旧形式と並走させ、残す講座を新形式へ移すことは前提にしない。

### 3.2 旧講座の削除

講座のディレクトリを消しても、D1のステージは消えない。seedは載っている講座をupsertするだけで、載っていない講座のステージは`published`のまま残る(`packages/shared/scripts/export-seed-sql.ts`)。

進捗を削除してよいため、既存の削除の仕組み`RETIRED_DEMO_STAGES`を使う。名前を「退役させる講座」の一覧に改め、次の19講座を載せる。これで、ステージと、その受講登録・進捗・提出・修了証が削除される。

it-basics, modern-css-basics, page-composition-basics, typescript-basics, typescript-node-basics, node-basics, db-design-basics, cli-basics, git-basics, fetch-api-basics, npm-build-basics, web-a11y-basics, frontend-testing-basics, rest-api-basics, web-security-basics, docker-basics, cicd-basics, linux-ops-basics, observability-basics

- **引き継ぐ6つのslugは一覧に載せない。** 載せると、新しい講座がupsertの直後に削除される。git-basicsで同じことが起き、一覧から外した経緯がある。
- 引き継ぐslugの講座は、ステージのUUIDが変わらず中身だけ入れ替わる。消えたレッスンと、その進捗はseedのpruneで削除される。
- typescript-basicsが参照していたTypeScriptの課題66問(`packages/shared/src/problems/`)は、どの講座からも参照されなくなる。今回はソースとD1の`assignments`を保持する。新形式のタスクには転用せず、整理はカリキュラムの切り替えと別に扱う。

### 3.3 it-basicsの削除

it-basicsはスキルツリーの唯一の根であり、4つの島の表示条件でもある。次を同じ変更で行わないと、検査やseedが落ちるか、島が誰にも見えなくなる。

| 対象 | 変更 | 変えない場合 |
| --- | --- | --- |
| fe-kamoku-a, aws-clf-c02-basics, ai-fluency-basics の`course.json` | `prerequisites: ["it-basics"]` → `["dev-env-basics"]` | `assertPrerequisiteGraph`が「存在しない講座」で落ちる。CIもseedも止まる |
| `packages/shared/src/skill-map/islands.ts` | AWS資格・情報処理資格・AI駆動開発・Salesforce案件の`requires`を`dev-env-basics`にする | 未知のslugは「決して満たされない」扱いになり、4島が全員から黙って消える |
| `packages/content/scripts/build_thumbnails.py` | `SPECS["it-basics"]`を消し、新しい講座の項目を足す | 引数なしの実行が「course.jsonがありません」で止まる |
| テスト | `manifest.test.ts`、`export-seed-sql.test.ts`、`islands.test.ts`がit-basicsを前提にしている | テストが落ちる |
| 文書 | `AGENTS.md`、`packages/content/CLAUDE.md`(唯一の前提なし講座・動画PoCの説明)、`helpContent.ts`の受講者向けヘルプ | 説明が古くなる |

動画のPoCは、it-basicsだけが全トピックの台本(`narration.json`)を持っている。PoCを続けるなら、`dev-env-basics`の解説トピックに移す。

### 3.5 Gitの共同作業の置き場所

Gitだけの講座は作らず、必要になる講座の単元に分けて置く。新設計は、道具をそれを必要とする教材で導入し(06 §3)、設計・品質・テストも各教材へ分散させる方針である。Gitも同じ扱いにする。

課題の提出はVS Code拡張から行うため、提出のためにGitHubやPRを早く覚える必要はない。そこで、共同作業の入口は、受講者が初めて「既存のアプリを壊さずに変える」`ui-integration-basics`に置く。

| 講座 | Gitで扱うこと | ここに置く理由 |
| --- | --- | --- |
| `dev-env-basics` | init、add・commit、diff、log(ローカルだけ) | 06 U05 のとおり。変更を記録して説明する |
| `html-css-basics`〜`react-ui-basics` | 単元ごとにcommitする習慣。修正演習で、壊した変更をrestoreで戻す | 新しい操作は足さず、反復で定着させる |
| `ui-integration-basics` | clone、branch、merge、コンフリクトの解消、GitHubアカウント、push、自分のリポジトリでのPR | 提供された既存アプリへ部品を組み込む最初の講座。変更をブランチに分け、既存機能を壊していないことを確かめてから取り込む流れが、そのまま単元の目的になる |
| `design-quality-basics` | PRのレビューとレビューへの対応、commitの単位、ピアレビュー(§6.5) | 新設計のこの講座に「レビュー」の単元がある |
| `deploy-ops-basics` | PRで動くCI、ブランチの保護、tag、revertによる切戻し | CIと切戻しの単元がある |
| `code-reading-basics` | fork・clone、履歴の調査(log・blame・bisect)、最小の変更をPRで出す | 未知のプロジェクトへの変更と回帰テストを扱う |
| `fullstack-capstone` | 一人でもブランチとPRで進め、PRとCIの記録を制作の証拠にする | 卒業判定の証拠(03 §9)になる |

`ui-integration-basics`で増える時間は、Gitの単元1つ(4〜6時間)を見込む。講座の70時間の中で調整し、プログラム全体の時間(1,260時間)は変えない。

Gitだけの講座(例:35時間)を`ui-integration-basics`の後に挟む案もある。ただし、全体が1,295時間になり、道具だけを切り出して教える形になるため勧めない。

## 4 教材の単位とファイル形式

### 4.1 単位の対応(決定)

新設計は、プログラム ＞ パック ＞ 単元(3〜10時間) ＞ 課題セット ＞ 課題で、1コマは60〜90分である(03 §3)。stellaは、講座 ＞ モジュール ＞ レッスン(LMSの1回分) ＞ トピック(2〜3分の動画1本)である。

| 新カリキュラム | stellaでの対応 |
| --- | --- |
| パック | 講座(ステージ) |
| 単元 | モジュール(D1のsection) |
| 1コマ | レッスン |
| 解説 | トピック(1 Takeaway、語彙台帳) |
| 課題 | 単元に属するタスク。`modules/<unit>/tasks/<task>/`に置く |

単元=モジュールの案を採用する。単元の3〜10時間を60〜90分のレッスンに分け、途中まで進めたことを記録できるためである。解説の語彙台帳・PDF・動画の仕組みも使える。新形式では、モジュールの意味を「大テーマ」から「単元」に変える。

### 4.2 何をどこで使うか

| 要素 | 正本 | 受講者が使う場所 |
| --- | --- | --- |
| 解説(スライド・動画・まとめ) | トピックの`slides.md`、レッスンの`doc.md` | 学習画面(§12で決める) |
| 知識問題 | レッスンの`knowledge.md` | アプリ。SRSの対象 |
| 演習課題(基礎・接続・自力・修正・統合) | 単元の`tasks/<id>/` | IDE(拡張の課題パネル)で解き、拡張から提出 |
| 確認A・B | `tasks/<id>/`と、配らない予備の類題 | 出題された時点でIDEに配る |
| 参照元 | 共通の台帳と単元の`references.json` | 解説・課題の近くと、単元の末尾 |
| ヒント・解答・解説 | `tasks/<id>/hints.md`、`private/` | 解放条件を満たしたあとに、IDEとアプリで |
| 進み具合・AIと人のレビュー結果 | D1 | アプリ |

LMSはタスクの一覧と状態だけを表示する。状態は、未着手・手元で合格・提出済み・AIで合格・講師の確認待ち・再提出・合格の7つとする。課題は「VS Codeで開く」から始め、Web上にエディタは置かない。今のWeb提出欄(`AssignmentSubmitPanel`の単一テキスト欄)は新形式では使わない。

### 4.3 ディレクトリ案

既存の`modules/<m>/<l>/<t>/`を単元・コマ・解説としてそのまま使い、単元の直下に`unit.json`・`references.json`・`tasks/`を足す。旧形式の講座と同じ読み込み処理(`packages/content/src/manifest.ts`)を拡張して扱える。

```text

  environments/<id>.json         # 実行環境の定義(Node・ライブラリ・OS・ブラウザの版)

```

`task.json`の主な項目は次のとおりとする。

### 4.4 受講者の作業フォルダー

今の拡張は、課題ごとに`~/.stella/exercises/<課題ID>/`を作り、ワークスペースフォルダーとして追加している。その結果、ウィンドウが無題のマルチルートになる。新設計では、前の講座で作ったもの(`javascript-data-basics`の検証関数など)を後の講座で使い直すため、課題ごとにばらばらのフォルダーは合わない。

- 学習者のファイルは上書きしない。衝突したら、準備先と衝突を表示する(04 §6)。

- 前の実装が壊れていて進めない場合は「固定した開始点」を配る。使ったことを記録する(01 §4)。

## 6 提出・評価・レビュー

### 6.1 2系統の評価

- **知識:** アプリで回答する。今の小テスト(単一選択・複数選択・正誤。サーバー側で採点)を使う。教材から投入できるのは今は単一選択だけなので、`knowledge.md`から複数選択・正誤も書けるようにする。
- **実装:** VS Code拡張から提出し、AIが一次レビューする。提出は次の6つを1組にする。
  - 宣言したファイル
  - 手元の実行結果
  - 配布したテストのハッシュ
  - 説明
  - 支援の記録
  - 課題の内容ハッシュ

### 6.2 提出から合否までの流れ

```text
手元で実行(拡張の「確認」。テスト・lint・整形)
  → 受講者が結果を見て直す。全部通ると「提出」が押せる
  → 提出(ファイル・結果・説明・支援の記録)
  → 機械の照合(テスト・設定のハッシュ、結果と提出ファイルの対応)
  → AIの一次レビュー(提出直後に自動。コーディング規則など)
      ├ 人に回す条件(§6.3)に当たらない → 合格で確定。所見を受講者へ返す
      │      人はいつでもこの提出を確認できる(§6.4)
      └ 人に回す条件に当たる → 人の最終レビュー(AIの下書き付き) → 合格 / 再提出
             受講者には「講師の確認待ち」だけを見せる
```

動作の判定と規則の判定を分ける。

- **動作:** 受講者が手元のテストで確かめて直す。提出できる時点で、テストは通っている。
- **機械で判定できる規則:** 整形・未使用の変数・禁止した構文などは、lintとASTの検査に入れて手元の実行に含める。
- **AIと人が見る規則:** 機械で判定しにくい規則を見る。たとえば、名前が意味を表しているか、関数の分け方と責務、重複や不要な複雑さ、単元で教えた書き方を使っているか、既存コードの書き方に合わせているか、説明とコードが一致しているか。

すべての課題が同じ流れを通る。課題の種別で変わるのは、提出に必要なものと、AIが重く見る規則である。

| 種別 | 提出に必要なもの | AIが重く見る規則 | 合格で残る証拠 |
| --- | --- | --- | --- |
| 基礎・接続 | ファイルと手元の結果 | 単元で教えた書き方、命名、既習の規則 | 練習(支援の有無を記録) |
| 自力 | 上記 + 短い説明 | 構成と責務の分け方、説明とコードの一致 | 練習。支援なしなら自力の傾向として記録 |
| 修正 | 上記 + 再現・原因・修正・回帰確認の記録(03 §6) | 記録と差分の整合、変更が必要な範囲に収まっているか | 練習 |
| 統合 | 上記 + 説明 | 既存コードの書き方と部品の契約に合わせているか、責務の置き場所 | 統合の証拠 |
| 確認A | 上記 + 説明。ヒントと解答は使えない | 上記に加え、説明が自分の設計判断を述べているか | スキルを「自力で確認」 |
| 確認B | 確認Aと同じ | 確認Aと同じ | スキルを「時間を空けて確認」 |

### 6.3 人に回す条件と確信度のしきい値

**ルーブリックは確かめられる文で書く。** 「読みやすさを1〜5で採点」のような尺度にはしない。「関数名が戻り値の意味を表している」「同じ処理を2か所以上に書いていない」のように、コードを見て当否を決められる文にする。AIは各項目について「満たす」「満たさない」「判断できない」のどれかと、根拠になるファイルと行を返す。

**確信度は数値ではなく3段階にする。** AIが自分で付けた0〜1の数値は、実際の正しさと対応しない。そこで、根拠を示せたかどうかで次の3段階を定義させる。

| 確信度 | 定義 |
| --- | --- |
| 高 | すべての必須項目に、コードの該当箇所を根拠として示せる |
| 中 | 根拠は示せるが、規則の解釈に幅がある項目がある |
| 低 | 根拠を示せない項目がある。または、提出が課題と対応していないように見える |

**しきい値(初期値。おすすめの値で決定):**

| 課題の種別 | AIで確定する | 人に回す |
| --- | --- | --- |
| 基礎・接続・自力・修正(練習) | 確信度が高・中で、必須項目をすべて満たす | 確信度が低、または必須項目に「満たさない」「判断できない」がある |
| 統合・確認A・確認B(証拠になる課題) | 確信度が高で、必須項目をすべて満たす | 確信度が中・低、または必須項目に「満たさない」「判断できない」がある |

練習は件数が多く、誤って合格にしても後の類題や確認で拾える。そのため中まではAIで確定する。統合と確認A・Bはスキルの証拠になるため、中から人に回す。

ほかに、次の場合はAIの判定によらず人に回す。

- 機械の照合で、テスト・設定のハッシュが一致しない、または結果と提出ファイルが食い違う。
- 確認A・Bで、許されていない支援(ヒント・解答の表示)の記録がある。
- AIが判定できなかった(拒否・タイムアウト・形式の誤り)。AIが止まっても、提出は人のキューで必ず受け止める。
- 受講者が講師への相談を求めた。

**しきい値の見直し:** 人がAI合格の提出を確認した記録(§6.4)と、人の最終レビューの結果を使い、月に1回見直す。

- 練習の「中」でAIが合格にした提出のうち、人が覆した割合が1割を超えたら、その講座の練習も中から人に回す。
- 人に回した提出のうち、人がそのまま合格にした割合が8割を超える種別は、条件が厳しすぎる。項目の書き方かしきい値を緩める。
- 課題ごとの「人に回した割合」が3割を超えたら、AIより先に課題文とルーブリックを疑う。

**受講者への見せ方:** 人に回した提出は、受講者には「講師の確認待ち」とだけ表示し、AIの所見は見せない。人が確定した後に、人が確定した所見だけを返す。確認待ちの間も、受講者は次の課題へ進める。同じ課題を出し直した場合は新しい提出で置き換え、AIが改めてレビューする。

### 6.4 人のレビューの負担を減らす

今のレビューは、テナントの全提出を新しい順に並べるだけである。並べ替え・絞り込みは「今後対応」で、AI下書きは講師が画面を開いてから作る。下書きは課題文・テスト・解答例を知らない。

1. **AIの下書きを提出時に作る。** 入力は、プログラム共通と講座の追加分のコーディング規則、課題文、課題ごとのルーブリック、解答例、よくある違反、手元の結果である。人が開いた時点で、判定案・所見・受講者への返信案がそろっている。
2. **人に回した理由でキューを分ける。** 規則の違反、確信度、AIの判定不能、ハッシュの不一致、相談を見分けられるようにする。理由、待ち時間、担当者で並べる。管理者もレビューできるようにする(今はAPIでは可能でも、画面に入口がない)。
3. **確定は1回の操作で。** 人はAIの判定案を承認するか、所見を直して再提出にする。
4. **コメント集。** パターンごとによくある違反と定型コメントを持ち、選んで直して送れるようにする。
5. **まとめて見る。** 同じ課題の提出を並べ、共通のつまずきは全体への補足やつまずき教材(Discovery)へ回す。
6. **AIが合格にした提出を、いつでも確認できる。** 期間は限定しない。
   - 一覧は講座・課題・受講者・確信度・日付で絞り込め、既定では確信度が中のものを先に並べる。
   - 人ができることは3つある。確認済みにする。判定を変えずにコメントを足す(受講者へ通知する)。再提出に覆す(合格とスキルの証拠を取り消し、理由を受講者へ通知する)。
   - 覆した記録は、しきい値の見直し(§6.3)とAIへの指示の改善に使う。
7. **AIの判定を校正する。** 人の最終レビューでAIの判定を覆した記録も残し、ルーブリックとAIへの指示の改善に使う。

#### 6.4.1 コーディング規則の正本と適用(決定)

共通規則は教材と同じリポジトリで管理し、AIと人が同じ文書を見る方式を採用する。

| 対象 | 正本 | 役割 |
| --- | --- | --- |
| プログラム共通 | `packages/content/coding-rules.md` | 命名、責務の分け方、重複、説明とコードの一致など、講座をまたいで使う規則 |
| 講座の追加分 | `packages/content/courses/<slug>/coding-rules.md` | 言語・フレームワーク・講座で導入する書き方の規則 |
| 課題の評価 | `task.json`の`review`、`private/review.md` | 適用する規則のID、必須・任意の区別、課題固有の条件とよくある違反 |

- 規則には一意のID、確かめられる文、適用する言語・場面、導入する単元を持たせる。規則を未習の段階では合否の必須条件にしない。復習や確認A・Bには、出題時点までに導入した規則を適用する。
- 講座の規則は共通規則への追加とする。共通規則に例外が必要なら、対象・理由を共通の正本に記載する。課題のルーブリックだけで共通規則を上書きしない。
- 整形・禁止構文などは手元のlint・整形・ASTの検査へ対応させる(§6.2)。AIと人は、機械で判定しにくい規則について根拠のファイル・行を確認する。
- AIへの入力と人のレビュー画面は、適用する規則のIDと同じ本文を使う。レビュー結果に規則の内容ハッシュを残し、規則を改訂した後も当時の判断を確認できるようにする(§13)。
- `STYLE_GUIDE.md`のコード例の規則や教材の説明は、この正本を参照する。受講者が読む規則と、レビューの規則を別々に書き写さない。

ここで決めるのは正本の置き場所と追加規則との関係である。規則の本文・IDと読み込みの実装は、AIの一次レビューの作業で用意する。

### 6.5 一人ひとりを育てる

- **担当講師。** メンターは講師が担う。今は講師と受講者を結ぶ担当の仕組みがない。受講者ごとに担当講師を決め、キューとダッシュボードを担当分に絞れるようにする。新しいロールは作らない。
- **週次の育成メモ。** 予定と実績の差(§10)、スキルの状態、つまずき、支援の量、AIと人のレビュー結果から、AIが1人1枚の要約を作る。担当講師は5分で読み、一言の声掛けか、ペースの調整をする。
- **つまずきの検知。** 次のどれかが起きたら担当講師に知らせる。
  - 同じ課題で手元の失敗が続く。
  - ヒントを最後まで開く。
  - 数日進まない。
  - 確認Bに落ちる。
  - 人に回る提出が続く。
- **支援の記録。** ヒント・解答の表示、講師への相談、人のレビュー、AIチャットの利用を課題ごとに記録し、習得の水準(03 §7 の未確認・支援付き・自力・時間を空けて確認)に反映する。受講者自身にも見せる。
- **AIの所見を学びにつなげる。** 合格した提出にも、良かった点と次に試すこと(別解・読みやすさ)を短く返す。合格だけで終わらせない。
- **ピアレビュー(選択肢)。** `design-quality-basics`のレビュー単元から、受講者同士で自力・統合課題の提出をレビューする。レビューそのものを学習の証拠にし、担当講師はレビューの質を見る。

### 6.6 AIレビューの実装上の注意

- **判定はJSONで固定する。** 構造化出力(`output_config.format`)で返させる。今の下書きは、自由形式の応答をパースしている。返させる項目は次のとおり。
  - ルーブリックの各項目の結果(満たす・満たさない・判断できない)と、根拠のファイル・行
  - 確信度(高・中・低)
  - 所見(ファイル・行範囲・重さ・コメント)
  - 受講者への返信
- **判定はコードで決める。** 人に回すかどうかは、AIに直接言わせない。返ってきた項目の結果と確信度に、§6.3 のしきい値をコードで当てはめて決める。しきい値を変えても、AIへの指示を変えずに済む。
- **キャッシュを効かせる並びにする。** 変わりにくい部分ほど先頭に置く。順番は、レビューの指示、プログラム共通のコーディング規則、講座の追加規則、課題文、ルーブリック、解答例、よくある違反である。提出ごとに変わる部分(ファイル・結果・説明)は最後に置く。共通の規則までは全課題で、追加規則までは同じ講座で、課題文以降は同じ課題の提出が続く間、キャッシュから読まれる。既定の保持は5分で、1時間も選べる。
- **受講者が待つ処理にBatchは使わない。** Batchは費用が半分になるが、非同期で結果まで時間がかかる。次のような待たない処理に使う。
  - 週次の育成メモ。
  - 人が覆した判定を使った、AIへの指示としきい値の点検。
  - 類題の下書きの検証。
- **非同期のキューで処理する。** 今のAIエンドポイントは60秒に20回の制限がある。提出を受けたらキューに積み、順に処理する。受講者には「AIが確認中」と表示する。
- **解答例を漏らさない。** 解答例はAIの入力に使うが、受講者への返信に解答のコードを含めないよう指示し、返信を機械的に照合する。確認A・Bでは特に厳しくする。
- **モデルとAIへの指示は評価用データで選ぶ。** 人がレビューした過去の提出を評価用データにし、人の判定との一致率で選ぶ。指示とモデルの版を、レビュー結果ごとに記録する。

### 6.7 データの変更

- `submissions`を、1つの`code`列からファイル単位の保存(R2)へ変える。持たせる項目は次のとおり。上書きせず、試行ごとの履歴を残す。
  - 課題ID・内容ハッシュ・種別
  - 手元の結果・テストのハッシュ
  - 説明・支援の記録
- AIレビューの結果を持たせる。適用した規則のID・内容ハッシュ、ルーブリックの各項目の結果、確信度、人に回したかとその理由、所見、受講者への返信、モデル・指示・しきい値の版である。人の判定は、AIの判定と別に記録する。
- AIが合格にした提出を人が確認した記録を持たせる。確認した人、日時、結果(確認済み・コメント・覆した)、コメントである。
- 所見を、行番号だけでなくファイルと行範囲に付ける。
- スキルと証拠の表を足す。スキルID、水準、根拠になった提出、支援の有無、日時を持たせる。
- 講座のクリア条件に、課題の判定(AIまたは人の合格)を使う。今の問題は次の2つである。
  - VS Codeの課題(`code`レッスン)は課題合格の条件に入らず、完了は自己申告である。
  - 講師が合格にしても、レッスンは完了にならない。
- 未判定のAI所見が受講者に見えている(`ReviewResultView.tsx`)。新しい流れでは、AIで確定したもの、または人が確定したものだけを見せる。人に回した提出のAIの所見は、受講者向けのAPIから返さない。

## 7 復習

### 7.1 知識はSRS

今のSRS(`review_cards`、SM-2、1日20枚)をそのまま使う。カードの元を`knowledge.md`の知識問題に限り、スキルと結び付ける。

### 7.2 コードはパターン単位の類題

SRSは同じ設問を解き直させる。コードでは、同じ実装パターンの別の問題(類題)を時間を空けて出す。

- **パターンの台帳。** 単元の基礎課題は、「値・条件・境界・組合せ・利用場面」を変えた同じパターンの問題群である(03 §2)。その単位を`pattern`として登録する。
- **類題の在庫。** パターンごとに、練習用の課題(公開)と、確認A・B・復習用の予備(`private/variants/`)を持つ。予備は出題した時点で受講者のIDEに配る。受講者ごとに出題済みを記録し、見た問題を「未見」として出し直さない(03 §7)。
- **出す時期。** 自力で合格したパターンは、約3日後・約1週間後(=確認B)・約3週間後に類題を出す。支援付きでしか解けなかったパターンは間隔を短くし、補習の小問題3問と、翌日以降の未見問題へつなぐ(03 §7)。
- **評価。** 類題も通常の課題と同じ流れ(手元で実行 → 提出 → AIの一次レビュー)を通る。
- **作り方。** データや条件を差し替えられる課題は、テンプレートとパラメータから類題とテストを作る。AIで類題の下書きを作ってもよい。ただし、在庫に入れる前に次を満たす。
  - 解答例が全テストに通る。
  - 典型的な誤答(ミュータント)がテストで落ちる。
  - 人が承認する(今のDiscoveryと同じく承認制)。
- **毎日の復習画面。** 知識のカードと「今日の類題」1問を並べる。類題は「VS Codeで開く」から解く。

## 8 解答と非公開素材のUX

解答を「隠す」より、「出す順番」を設計する。練習で行き詰まらせないことと、自力確認の結果を正しく残すことを両立させる。

| 種別 | 取り組み中 | 合格後 | 備考 |
| --- | --- | --- | --- |
| 基礎・接続 | ヒントを段階的に開ける(方針 → 手がかりのコード → 解答例) | 解答例と解説を自動で開く。自分のコードと並べて見られる | ヒントや解答を開くと「支援付き」になる。罰ではなく記録 |
| 自力・修正 | ヒントは開ける。解答例は一定回数の挑戦後か合格後 | 解答例・別解と、選び方の理由 | 支援の段数を証拠に残す |
| 統合 | 仕様・状態見本・API契約へのリンクだけ | レビューの所見と解答例 | — |
| 確認A・B | 公式ドキュメントと文法の参照だけ(03 §7)。拡張はヒント・解答の表示を止める | 所見。Aの解答例は確定後に開く | 未出題の予備は見せない |

- ヒントと解答はIDEの課題パネルに出す。今のパネルは課題文と採点結果しか出さない。
- `private/`は、seedでD1・R2の非公開の場所へ入れる。公開APIは、解放条件を満たした受講者にだけ返す。AIレビューは解答例を読むが、受講者への返信に解答を含めない(§6.6)。
- 配布・印刷用のPDFは、新形式では課題文・参照元・解説だけにし、解答編を作らない。
- **公開前に確かめること。** 今の公開APIは課題のテストを受講者へ返す。新形式ではテストを配る前提なので問題ないが、解答例は返さないようにする。Webの`AIChatBot.tsx`は`@stella/shared/assignments`を読み込んでおり、課題の解答がWebのJSに含まれている可能性がある(未検証)。
- **正本の置き場所。** `private/`も含めて教材リポジトリ(`packages/content`)で管理する(決定)。リポジトリ(`otomatty/stella`)は公開なので、GitHubを直接読めば解答例と予備の類題は見える。そのうえで、アプリは解放条件を満たすまで受講者へ配らない(公開API・配布PDF・拡張に載せない)。

## 9 参照元(新設計05を採用)

- `packages/content/CLAUDE.md`の絶対ルール3「クレジット表記を教材本体に入れない」を、05に沿って書き換える。`STYLE_GUIDE.md`と`THEME_TO_COURSE.md`の外部素材の節も合わせる。
- 台帳は`packages/content/sources/registry.json`(05 §8 の`source-registry.json`)、使用箇所は単元の`references.json`に置く。トピック・まとめ・課題の冒頭(front-matter・`task.json`)には、参照元IDを書く。
- 表示は4か所にする。解説・課題の近く、単元の末尾の一覧、IDEの課題パネル、配布PDFである。
- 版は常に最新を配信するため(§13)、公開の関門はCIに置く。§9.1で必須とする単元について、`content:check`は次の場合に失敗させ、`main`へ入れない。
  - 未登録のsourceRefがある。
  - 技術のトップページだけを根拠にしている。
  - レビュー状態が`approved`でない。
  - 環境の定義がない。
- リンク切れは週1回の定期ジョブで確認する。タイムアウトやアクセス制限は削除と分け、手動確認として記録する(05 §9)。
- 残す講座は、新規・内容改訂の単元から必須にし、未改訂の既存単元は警告だけにする(§9.1)。

### 9.1 残す講座への適用(決定)

新形式の18講座には、初回の公開から05の参照元ルールを適用する。残す講座は次の範囲で段階的に適用する。参照元の対応だけを足すために旧形式を`format: 2`へ移す必要はない。

| 教材の状態 | 適用範囲 | 公開の扱い |
| --- | --- | --- |
| 新しく作る単元 | 単元の解説・参考例・図・課題すべて | 05の要件を満たすことを必須にする |
| 内容を改訂する既存単元 | 改訂する単元の解説・参考例・図・課題すべて | 改訂版の公開から必須にする |
| 内容を改訂していない既存単元 | 参照元の不足を検出する | 警告として一覧に残し、既存の公開を止めない |

内容の改訂には、説明、参考コード、図、課題・解答・評価条件、採用技術や環境の変更を含める。誤字・表記・レイアウトだけの修正と、カリキュラム切り替えに伴う講座の前提・`parent`の付け替えは、参照元を整備するための内容改訂には数えない。

公開の検査は、上の適用範囲と未改訂の範囲を区別する。未改訂の不足で、別の単元の新規作成・改訂を止めない。JSONやリンクの検査に加え、講師による資料と本文の対応確認を公開前に行う(05 §9)。

## 10 ペースの自動設定

今は、学習計画のデータがない。

- `stages.duration_hours`は教材から入らず、全講座で空である。ステージ一覧は、空のとき「約20時間」と固定値を出している。
- 受講登録の期日は、自分で開始した講座では入らない。

提案は次のとおり。

- **入力:** 講座・単元・課題の予定時間(`course.json`の`plannedHours`、`unit.json`、`task.json`)、プログラムの標準(週35時間)、受講者の週あたりの時間と開始日。
- **既定:** 受講者が`dev-env-basics`を始めた日を開始日にし、週35時間で計算する。週30時間なら約42週、週40時間なら約32週になる(00 §5)。受講者や担当講師が週の時間を変えると、残りを計算し直す。
- **出すもの:**
  - 今週の目安(単元とコマ)
  - 各講座の目標日
  - 予定との差。進んだ予定時間で測り、費やした時間では測らない。
  - 確認B。確認Aの合格から7日後に自動で予定する。
- **遅れたとき:** 罰を与えず、残りの予定を引き直す。差が1週間を超えたら担当講師に知らせる(§6.5)。補習の2〜4週間は別枠として、予定の計算に含めない。
- **開始診断:** 確認できたスキルの練習時間を予定から差し引く。確認A・Bは差し引かない(00 §5)。
- **データ:**
  - 受講者の設定(週の時間・開始日)をプロフィールへ足し、`/api/me`で編集できるようにする。
  - 予定日は保存せず、その都度計算する。
  - `duration_hours`は`plannedHours`から入れ、固定値の「約20時間」はなくす。

## 11 OS別の手順

可能である。ただし、今の描画は4系統(Webの`react-markdown`、VS CodeのWebView、PDF・動画、pptx)に分かれている。WebとVS Codeは生のHTMLを文字として出し、VS CodeのWebViewは画像も出せない。そこで範囲を絞る。

- **書ける場所を限る。** OS別のブロックは、まとめ(`doc.md`)と課題文(`README.md`)だけに書く。スライドと動画はOSに依存しない説明にし、pptxと動画の生成は変えない。
- **書き方:**

  ```markdown
  :::os windows
  PowerShellで次を実行します。
  :::
  :::os macos
  ターミナルで次を実行します。
  :::
  ```

- **見せ方:** OSのタブにし、既定は受講者のOSにする。拡張は`process.platform`で正確に分かる。Webは利用者のOS情報から推定し、プロフィールの設定で上書きできるようにする。「あなたのOS: Windows(変更)」と表示する。
- **画像:** `name.windows.png` / `name.macos.png`のように、OSごとに用意する。
- **PDF:** `dev-env-basics`のようにOS差が大きい講座は、OS別にPDFを作る。それ以外は、両方を見出し付きで並べる。
- **検査:** OS別のブロックは、WindowsとmacOSの両方がそろっていること、画像がOSごとにあることを確かめる。
- **環境診断:** 拡張がOSに応じて確認コマンドを変える(例:Windows PowerShellの`npm.cmd`、06 §3)。

## 12 学習画面の置き場所(判断材料)

未決のため、どちらの案にも寄せない。ただし、次はどちらに決めても変わらない。

- IDEに課題パネルが要る。出すものは、課題文・ヒント・実行・提出・AIと人のレビュー結果・参照元である。
- 環境診断と実行は拡張の仕事である。
- VS Code導入前の`dev-env-basics`の最初の単元(06のU00〜U01)は、ログインなしでブラウザで読める必要がある。今のWebは、未ログインではログイン画面しか出さない。
- 管理・レビュー・知識問題・SRSはアプリに置く。

| 観点 | VS Code(WebView)に置く | Webに置く |
| --- | --- | --- |
| 解説と演習の行き来 | 同じ画面で横に並べられる | ウィンドウを切り替える |
| VS Code導入前の閲覧 | できない(別途Webが要る) | できる |
| 環境の確認 | 拡張が端末の状態を読める | 読めない |
| 動画・図解 | 今のWebViewは画像すら出せず、作り直しが要る。動画の再生方式は要検証 | 今の仕組み(動画・スライド・図解)をそのまま使える |
| スマートフォンでの知識問題・SRS | できない | できる |
| 開発の手間 | 解説の描画をWebViewにも作り、2系統を保守する | 今の画面を使える |
| 印刷・PDF | 影響なし | 影響なし |
| 学習の中断と再開 | VS Codeを開けば続きから | ブラウザとVS Codeの両方を開く |

決めるための試行は、00 §6 の最初の試行に組み込む。`dev-env-basics`の導入案内から、VS Code内での学習開始、翌日の再開までを通す。観察する値は次のとおり。

- 画面を切り替えた回数
- 最初にHTMLの変更を表示できるまでの時間
- 途中で止まった場所
- 支援の量
- 翌日の再開にかかった時間

### 12.1 試行して決める手順(決定)

画面の置き場所は、`dev-env-basics`ができてから試行の結果で決める。Issue #26では、試行後に判断することと、次の比較手順を決めるところまでを対象とする。

1. ログインなしのWebの導入案内から、VS Codeの導入、拡張の接続まで進める。この入口はどちらの案でも用意する。
2. 同じ教材・課題を用い、解説をWebViewに置く案とWebに置く案で、HTMLの保存・表示・変更まで通す。翌日は、前日の続きから再開する。
3. 上記の5項目を案ごとに記録する。操作のつまずきと環境の不具合を分け、支援は回数・所要時間・内容を残す。動画・図解・参照元が読めることと、課題を再開できることも確認する。
4. 講師とオーナーが結果を比較する。WebView案で支援や再開時間が減るか、表示と保守の負担に見合うかを確かめ、採用する置き場所と理由を本書に残す。

試行前に採用先や結果を確定しない。旧講座の退役、講座の骨組み、新形式、共通規則の作業は先に進められる。
