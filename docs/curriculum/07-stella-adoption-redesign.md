00〜06の新カリキュラム(版2.2)を、stellaの教材形式・実行・評価・スキルツリーへ載せるための再設計案である。2026年10月5日時点のstella(`main`)を調べ、オーナーが決めた方針(§1)に沿って実装方法を提案する。学習画面の採用先は、`dev-env-basics`の試行後に決める。

本書の「講座」はstellaの`packages/content/courses/<slug>/`(D1の`stages`、画面の「ステージ」)を指す。新カリキュラムの「教材パック」は講座1つに対応させ、講座はslugの名前で呼ぶ。00〜06はM01〜M18の番号で書かれているため、番号との対応は§3.1の表で引く。新カリキュラムの「コース」(卒業までの全体)は、本書ではプログラムと呼ぶ。

## 2 設計の原則

1. **エディタはIDEにだけ置く。** LMS(Web)は、読む・知識問題に答える・進み具合と評価結果を見る・レビューする場所にする。コードを書く・実行する・提出する操作はIDEで完結させる。
2. **動作は受講者が確かめ、レビューは規則を見る。** 動くかどうかは、手元の実行結果で受講者が確かめて直す。AIと人のレビューは、テストやlintでは判定できないコーディング規則などを見る。サーバーではコードを実行しない。
3. **人の時間は、人にしか判断できないところに使う。** 人が必ず見るのは、人に回す条件(§6.3)に当たった提出だけにする。AIが合格にした提出は、人が好きなときに確認できる。講師は、残りの時間をつまずきの解消と励ましに使う。
4. **配信は常に最新にし、記録の側に「どの内容で何をしたか」を残す。** 版を固定しない代わりに、提出に教材の内容ハッシュを残す。
5. **残す講座は今の仕組みのまま動かす。** 新形式は旧形式と並走させ、残す講座を新形式へ移すことは前提にしない。

### 3.2 旧講座の削除

講座のディレクトリを消しても、D1のステージは消えない。seedは載っている講座をupsertするだけで、載っていない講座のステージは`published`のまま残る(`packages/shared/scripts/export-seed-sql.ts`)。

進捗を削除してよいため、既存の削除の仕組み`RETIRED_DEMO_STAGES`を使う。名前を「退役させる講座」の一覧に改め、次の19講座を載せる。これで、ステージと、その受講登録・進捗・提出・修了証が削除される。

it-basics, modern-css-basics, page-composition-basics, typescript-basics, typescript-node-basics, node-basics, db-design-basics, cli-basics, git-basics, fetch-api-basics, npm-build-basics, web-a11y-basics, frontend-testing-basics, rest-api-basics, web-security-basics, docker-basics, cicd-basics, linux-ops-basics, observability-basics

- **引き継ぐ6つのslugは一覧に載せない。** 載せると、新しい講座がupsertの直後に削除される。git-basicsで同じことが起き、一覧から外した経緯がある。
- 引き継ぐslugの講座は、ステージのUUIDが変わらず中身だけ入れ替わる。消えたレッスンと、その進捗はseedのpruneで削除される。
- typescript-basicsが参照していたTypeScriptの課題66問(`packages/shared/src/problems/`)は、どの講座からも参照されなくなる。今回はソースとD1の`assignments`を保持する。新形式のタスクには転用せず、整理はカリキュラムの切り替えと別に扱う。

### 3.3 it-basicsの削除

it-basicsはスキルツリーの唯一の根であり、4つの島の表示条件でもある。次を同じ変更で行わないと、検査やseedが落ちるか、島が誰にも見えなくなる。

| 対象 | 変更 | 変えない場合 |
| --- | --- | --- |
| fe-kamoku-a, aws-clf-c02-basics, ai-fluency-basics の`course.json` | `prerequisites: ["it-basics"]` → `["dev-env-basics"]` | `assertPrerequisiteGraph`が「存在しない講座」で落ちる。CIもseedも止まる |
| `packages/shared/src/skill-map/islands.ts` | AWS資格・情報処理資格・AI駆動開発・Salesforce案件の`requires`を`dev-env-basics`にする | 未知のslugは「決して満たされない」扱いになり、4島が全員から黙って消える |
| `packages/content/scripts/build_thumbnails.py` | `SPECS["it-basics"]`を消し、新しい講座の項目を足す | 引数なしの実行が「course.jsonがありません」で止まる |
| テスト | `manifest.test.ts`、`export-seed-sql.test.ts`、`islands.test.ts`がit-basicsを前提にしている | テストが落ちる |
| 文書 | `AGENTS.md`、`packages/content/CLAUDE.md`(唯一の前提なし講座・動画PoCの説明)、`helpContent.ts`の受講者向けヘルプ | 説明が古くなる |

動画のPoCは、it-basicsだけが全トピックの台本(`narration.json`)を持っている。PoCを続けるなら、`dev-env-basics`の解説トピックに移す。

### 3.5 Gitの共同作業の置き場所

Gitだけの講座は作らず、必要になる講座の単元に分けて置く。新設計は、道具をそれを必要とする教材で導入し(06 §3)、設計・品質・テストも各教材へ分散させる方針である。Gitも同じ扱いにする。

課題の提出はVS Code拡張から行うため、提出のためにGitHubやPRを早く覚える必要はない。そこで、共同作業の入口は、受講者が初めて「既存のアプリを壊さずに変える」`ui-integration-basics`に置く。

| 講座 | Gitで扱うこと | ここに置く理由 |
| --- | --- | --- |
| `dev-env-basics` | init、add・commit、diff、log(ローカルだけ) | 06 U05 のとおり。変更を記録して説明する |
| `html-css-basics`〜`react-ui-basics` | 単元ごとにcommitする習慣。修正演習で、壊した変更をrestoreで戻す | 新しい操作は足さず、反復で定着させる |
| `ui-integration-basics` | clone、branch、merge、コンフリクトの解消、GitHubアカウント、push、自分のリポジトリでのPR | 提供された既存アプリへ部品を組み込む最初の講座。変更をブランチに分け、既存機能を壊していないことを確かめてから取り込む流れが、そのまま単元の目的になる |
| `design-quality-basics` | PRのレビューとレビューへの対応、commitの単位、ピアレビュー(§6.5) | 新設計のこの講座に「レビュー」の単元がある |
| `deploy-ops-basics` | PRで動くCI、ブランチの保護、tag、revertによる切戻し | CIと切戻しの単元がある |
| `code-reading-basics` | fork・clone、履歴の調査(log・blame・bisect)、最小の変更をPRで出す | 未知のプロジェクトへの変更と回帰テストを扱う |
| `fullstack-capstone` | 一人でもブランチとPRで進め、PRとCIの記録を制作の証拠にする | 卒業判定の証拠(03 §9)になる |

`ui-integration-basics`で増える時間は、Gitの単元1つ(4〜6時間)を見込む。講座の70時間の中で調整し、プログラム全体の時間(1,260時間)は変えない。

Gitだけの講座(例:35時間)を`ui-integration-basics`の後に挟む案もある。ただし、全体が1,295時間になり、道具だけを切り出して教える形になるため勧めない。

## 4 教材の単位とファイル形式

### 4.1 単位の対応(決定)

新設計は、プログラム ＞ パック ＞ 単元(3〜10時間) ＞ 課題セット ＞ 課題で、1コマは60〜90分である(03 §3)。stellaは、講座 ＞ モジュール ＞ レッスン(LMSの1回分) ＞ トピック(2〜3分の動画1本)である。

| 新カリキュラム | stellaでの対応 |
| --- | --- |
| パック | 講座(ステージ) |
| 単元 | モジュール(D1のsection) |
| 1コマ | レッスン |
| 解説 | トピック(1 Takeaway、語彙台帳) |
| 課題 | 単元に属するタスク。`modules/<unit>/tasks/<task>/`に置く |

単元=モジュールの案を採用する。単元の3〜10時間を60〜90分のレッスンに分け、途中まで進めたことを記録できるためである。解説の語彙台帳・PDF・動画の仕組みも使える。新形式では、モジュールの意味を「大テーマ」から「単元」に変える。

### 4.2 何をどこで使うか

| 要素 | 正本 | 受講者が使う場所 |
| --- | --- | --- |
| 解説(スライド・動画・まとめ) | トピックの`slides.md`、レッスンの`doc.md` | 学習画面(§12で決める) |
| 知識問題 | レッスンの`knowledge.md` | アプリ。SRSの対象 |
| 演習課題(基礎・接続・自力・修正・統合) | 単元の`tasks/<id>/` | IDE(拡張の課題パネル)で解き、拡張から提出 |
| 確認A・B | `tasks/<id>/`と、配らない予備の類題 | 出題された時点でIDEに配る |
| 参照元 | 共通の台帳と単元の`references.json` | 解説・課題の近くと、単元の末尾 |
| ヒント・解答・解説 | `tasks/<id>/hints.md`、`private/` | 解放条件を満たしたあとに、IDEとアプリで |
| 進み具合・AIと人のレビュー結果 | D1 | アプリ |

LMSはタスクの一覧と状態だけを表示する。状態は、未着手・手元で合格・提出済み・AIで合格・講師の確認待ち・再提出・合格の7つとする(提出済みは、画面では「AIが確認中」と出す)。課題は「VS Codeで開く」から始め、Web上にエディタは置かない。今のWeb提出欄(`AssignmentSubmitPanel`の単一テキスト欄)は新形式では使わない。

### 4.3 ディレクトリ案

既存の`modules/<m>/<l>/<t>/`を単元・コマ・解説としてそのまま使い、単元の直下に`unit.json`・`references.json`・`tasks/`を足す。旧形式の講座と同じ読み込み処理(`packages/content/src/manifest.ts`)を拡張して扱える。

```text
packages/content/
  sources/registry.json          # 参照元の台帳(全講座で共有)
  environments/<id>.json         # 実行環境の定義(Node・ライブラリ・OS・ブラウザの版)
  skills.json                    # スキルIDの台帳
  patterns.json                  # 実装パターンの台帳(類題の単位)
  courses/<slug>/
    course.json                  # format: 2、plannedHours、environment ほか
    CURRICULUM.md
    modules/<unit>/              # 単元
      unit.json                  # 予定時間、使うスキル、評価するスキル、再利用する成果物
      references.json            # 本文・課題と参照元の対応
      <lesson>/                  # 1コマ
        <topic>/slides.md        # 解説。1 Takeaway・語彙台帳・4〜6枚は今の規則のまま
        doc.md                   # まとめ。OS別ブロックを書ける(§11)
        knowledge.md             # 知識問題
      tasks/<task>/
        task.json                # 種別、パターン、runner、提出ファイル、評価、支援
        README.md                # 課題文(IDEの課題パネルに出す)
        starter/                 # 配布するファイル
        tests/                   # 手元で走るテスト
        hints.md                 # 段階的なヒント
        private/                 # アプリは受講者へ配らない(リポジトリでは管理する。§8)
          solution/              # 解答例(AIレビューの入力にも使う)
          explanation.md         # 解説
          review.md              # コーディング規則の観点とよくある違反(AIレビューの入力)
          variants/              # 確認A・B・復習用の予備の類題
```

`task.json`の主な項目は次のとおりとする。

| 項目 | 内容 |
| --- | --- |
| `id` | `<講座slug>/<単元>/<課題>`。短い`q01`だけで結果を保存しない(04 §3) |
| `kind` | `basic` / `connection` / `independent` / `debug` / `integration` / `assessment-a` / `assessment-b` |
| `pattern` | 実装パターンのID。類題と復習の単位(§7) |
| `skills` | `uses`(使うスキル)と`assesses`(評価するスキル)を分ける(04 §1) |
| `runner` / `environment` | 実行定義のIDと実行環境の版(§5) |
| `submit` | 提出するファイルのglob、説明欄の要否、修正演習の記録欄の要否 |
| `review` | 課題ごとのルーブリック(確かめられる文で書いた必須・任意の項目)と、人に回す条件の追加分(§6.3) |
| `support` | ヒントの段数、解答を解放する条件(§8) |
| `sources` | 参照元ID(§9) |
| `estimatedMinutes` | 予定時間。ペースの計算に使う(§10) |
| `fixedStart` | `fixed-start/`を置く課題だけ。`covers`に開始点が動く実装を含む前の課題のIDを書く(§4.4) |

### 4.4 受講者の作業フォルダー

今の拡張は、課題ごとに`~/.stella/exercises/<課題ID>/`を作り、ワークスペースフォルダーとして追加している。その結果、ウィンドウが無題のマルチルートになる。新設計では、前の講座で作ったもの(`javascript-data-basics`の検証関数など)を後の講座で使い直すため、課題ごとにばらばらのフォルダーは合わない。

新形式の課題は、プログラム全体で1つの学習フォルダー(06 §3 の`web-training`)を使う(#31 で実装)。拡張はその中の`<講座slug>/<unit>/<task>/`へ配布ファイルを置く。旧形式の演習(QuickJS)は今の`~/.stella/exercises/`のまま。

- 学習フォルダーは、初回にホームへ`web-training`を作るか、既存のフォルダーを選ぶ。場所は拡張のglobalStateに覚える。ワークスペース設定には置かない(`stella.serverUrl`と同じ理由)。
- 学習フォルダーをウィンドウの唯一のフォルダーとして開く。開くと、ウィンドウが読み込み直されるか、学習フォルダーをすでに開いている別のウィンドウへ切り替わる。開く課題を全ウィンドウで共有する場所に控えておき、学習フォルダーだけを開いたウィンドウが起動したとき・前面に来たときに課題文を開く。受け取るのは1つのウィンドウだけ。このウィンドウが学習フォルダーだけを開いていれば、そのまま課題文を開く(上位のフォルダーや講座のフォルダー、マルチルートでは開き直す)。
- 配布ファイルは`GET /api/tasks/bundle`が返すREADME・starter・tests・`.stella/task.json`だけ。`private/`は返さない(解答の配信制御は#36)。
- 学習者のファイルは上書きしない。同じ名前のファイルがあれば止めて、準備先と衝突したファイルを表示する(04 §6)。
- Webの課題文レッスン(seedが`tasks.lesson_id`で結ぶ)と「単元の課題」の「VS Code で開く」が、一回限りの接続コード付きで課題を開く。
- `dev-env-basics`のGitの単元から、このフォルダーをGitで管理する。前の成果物を使う課題は、学習者自身のファイルを参照する。
- 前の実装が壊れていて進めない場合は「固定した開始点」を配る。使ったことを記録する(01 §4)。
  - 教材は課題の`fixed-start/`に置く。starterの代わりに置く一式で、testsと`protected`のファイルは通常の配布と同じにする。この課題の解答例は置けない。確認A・Bには置けない。
  - 受講者が拡張のコマンドで求めたときだけ`POST /api/tasks/fixed-start`が渡し、受け取りを`task_fixed_start_uses`に記録する。元の課題フォルダーは変えず、隣の`<task>-fixed-start/`に準備する。
  - 受け取った受講者のその課題の提出には、支援記録に`fixed-start`が入る(手元の記録が無くてもサーバーが足す)。合格は「支援付き」の証拠になる。
  - 開始点は前の課題の動く実装を含むので、どの課題の実装かを`task.json`の`fixedStart.covers`に書く(同じ講座のより前の課題。順序から推測しない)。受け取りの記録に受け取った時点の`covers`を残し、受け取ったあとのそれらの課題の提出にも`fixed-start`が入る(開始点を写して前の課題を出せるため)。受け取る前の提出は変えない(前後は提出の時刻と受け取りの時刻で決める。提出の処理中に届いた受け取りも、提出の時刻より前ならAIの判定の直前とスキルの証拠を作るときに数える)。前の課題が確認A・Bなら、その提出は人に回る。

### 4.5 既存の仕組みとの関係

- `course.json`に`format: 2`を足し、新形式の講座だけ`tasks/`・`unit.json`・`knowledge.md`を読む。残す講座は今のまま動く。
- 課題は`packages/shared/src/problems/`のTypeScriptファイルではなく、教材リポジトリの`tasks/`を正本にする。D1にはタスク用の表を新しく作り、今の`assignments`表(QuickJS用)は旧形式の講座に残す。
- `practice.md`の「解答例と解説」と確認クイズは、新形式では`private/`・`knowledge.md`へ分ける。受講者向けPDFの解答編は、新形式では作らない(§8)。
- 検査を足す。
  - `task.json`のスキーマ。
  - 解答例が手元のテストに通ること。
  - `private/`が配信物や公開APIに混ざらないこと。
  - 参照元(§9)とOS別ブロック(§11)。
  - 語彙台帳とスライド4〜6枚の検査は、解説トピックにそのまま使う。

## 5 演習の実行基盤(再設計の要件)

基盤はオーナーが再設計する。ここでは、新カリキュラムとstellaの現状から決まる要件をまとめる。合否は手元の実行とAIのレビューで決めるため、実行基盤は受講者の端末だけで完結させる。サーバーではコードを実行しない。

### 5.1 再設計前の状態 (2026年10月5日時点)

次は実行基盤を実装する前の状態で、再設計の出発点として残す。手元で実行する部分の実装後の状態は §5.5 にまとめた。

- 採点は拡張内のWebView(QuickJSとsql.js)だけで行う。DOM・`fetch`・タイマー・モジュール・Node APIがなく、1回3秒・32MBで止まる(`packages/code-runner/src/quickjs-runner.ts`)。
- 拡張は外部プロセスを起動しない(`child_process`・ターミナル・Tasks APIのどれも使っていない)。Workspace Trustも確認していない。
- 採点結果はサーバーへ送られない。合格すると、拡張が`POST /api/lesson-progress`でレッスン完了を送るだけで、サーバーはその値を信頼する。
- VS Codeから提出できるのは「採点で不合格だったとき」だけである(講師への引継ぎ)。合格したコードは誰も見ない。

### 5.2 runnerの一覧(案)

| runnerId | 使う講座 | 手元での実行 |
| --- | --- | --- |
| `static-preview` | dev-env-basics, html-css-basics | HTML・CSSの検査(拡張の中でファイルを読むだけ)。ローカルサーバーと画面幅別のスクリーンショットは入れない(下記) |
| `env-diagnose` | dev-env-basics | Node・npm・Gitの版を、環境定義と照合する |
| `node-test` | javascript-basics, javascript-data-basics, node-api-basics | Vitest |
| `dom-test` | dom-basics, ui-components-basics | Vitest + jsdom等 + Testing Library |
| `http-mock` | http-async-basics | 疑似応答と提供API |
| `react-test` / `storybook` | react-basics, react-ui-basics, ui-integration-basics | Vitest + Testing Library、Storybookの状態見本 |
| `e2e` | ui-integration-basics, nextjs-basics, deploy-ops-basics | Playwright |
| `api-test` | node-api-basics, auth-basics | APIテスト(Express/Hono) |
| `db` | sql-basics, auth-basics | PostgreSQL(PGlite。決定、下記) |
| `next-app` | nextjs-basics | `next build`と、`next start`で開いた画面のPlaywright |
| `ci-deploy` | deploy-ops-basics | GitHub Actions・公開先。CIの結果を提出に添える(設計は§5.5、未実装) |
| `quickjs`(旧) | fe-kamoku-b、CMSのプレビュー | 今のまま |

runnerごとの課題テンプレート(`package.json`・lockfile・テストとlint・整形の設定)は`packages/content/templates/runners/<runnerId>/`に置き、道具の版は`packages/content/environments/<runnerId>-01.json`に記録した(§5.5)。Node.jsは22.13以上の22系と24系に限る。道具の多くが奇数版(23)に対応しないため、環境の要件に使える版の一覧(`majors`)を足し、環境診断は23を「この版は使えません」とする。

- **db: PGliteに決める。** 2026年10月にPGlite 0.5.8(PostgreSQL 18.3)をNode.js 22とVitestで動かし、表の作成・挿入・検索、制約違反、トランザクションの取り消しを確かめた。`npm ci`だけで入り、WASMなのでOSごとのネイティブ部品が無い(WindowsとmacOSの実機での確認は§5.5の残りの作業に含める)。コンテナは、WindowsでWSL2と仮想化の有効化・管理者権限が要り、Docker Desktopは大きな組織では有料で、会社が管理する端末では入れられないことがある。最初の環境構築でつまずく箇所を増やすため、採らない。
  - 制限: 接続は1つだけで、同時接続とロックは扱えない。拡張機能は同梱のものだけ。`pg`などのドライバーからはつながず、テストはPGliteの`query`を使う。
  - 1つで約0.8GBのメモリを使い、作るのに2〜3秒かかる。テンプレートは空のDBを1回作って`clone()`(約0.5秒)で複製し、テストのファイルを1つずつ実行する。
  - コンテナは、Dockerを学ぶ`deploy-ops-basics`で学習の対象として扱う。
- **static-preview: ローカルサーバーと画面幅別のスクリーンショットは入れない。** static-previewは、Node.jsを入れる前でも、信頼していないフォルダーでも動くよう、拡張の中でファイルを読むだけにしている。
  - ローカルサーバーは、06のU06で受講者が自分で起動・停止すること自体が学習内容である。U06の「ローカルサーバー用スターター」は教材の配布物として作る。
  - 画面幅の確認にはブラウザーが要る。画面幅を扱う課題(html-css-basicsの画面幅の単元など、Node.jsを入れた後)は`e2e`のrunnerを使う。テンプレートに、幅375・768・1280pxで横にはみ出さないことをPlaywrightで確かめる例を入れた。
  - スクリーンショットを提出に添えてレビューに使うかは、提出に画像を載せる仕組みと合わせて、AIの一次レビューのあとに決める。

### 5.3 拡張に求めること

- 実行は、拡張に同梱した実行定義(runnerIdごとの固定の引数)だけで行う。WebView・LMS・課題ファイルから受け取った文字列をコマンドとして実行しない(04 §6)。
- `capabilities.untrustedWorkspaces`を宣言し、信頼していないフォルダーでは実行しない。
- `stella.serverUrl`をユーザー設定に限定する。ワークスペース設定(`.vscode/settings.json`)で上書きできると、学習用プロジェクトの設定一つでJWTが別のサーバーへ送られる(対応済み、§5.5)。
- 手元のテストが全部通ったときだけ、「提出」を押せるようにする。通らないときは「講師に相談」(今の引継ぎ)だけを出す。
- 提出・実行で読むのは、`submit`で宣言したファイルだけにする。今は作業フォルダーの全ファイルを再帰的に読むため、`node_modules`があると全部を読んでしまう。
- 配布したテストと設定ファイルの内容ハッシュを、提出に添える。改変されていれば、機械の照合で人に回す(§6.3)。
- Node導入前(`dev-env-basics`の前半)は、`static-preview`と手動確認だけで進められるようにする。

### 5.4 サーバーで実行しないことの前提

- 動くかどうかは、受講者が手元の実行結果で確かめて直す。AIと人のレビューは動作を判定せず、コーディング規則などを見る(§6.2)。
- テストは課題と一緒に受講者へ配るので、受講者は読める。確認A・Bの「未見」は、出題するまで課題そのものを見せないことで守る(§7・§8)。
- 手元の結果は改ざんできる。完全には防がず、提出時にテスト・設定のハッシュと、結果と提出ファイルの対応を機械で照合する。食い違えば人へ回す。

### 5.5 実装の状況

手元で実行する部分を実装した。

- **課題の定義:** `.stella/task.json`(§4.3 の`task.json`のうち、実行と提出に要る部分)。型と検証は`packages/shared/src/tasks/`。
- **実行エンジン:** `apps/vscode/src/runner/`。
  - runnerIdごとの固定の手順は`steps.ts`と`plans.ts`。
  - 起動は引数の配列だけで、シェルを通さない。時間切れ・中断ではプロセスごと止める。
  - 道具は受講者のPATHと課題フォルダーの`node_modules`から探す。
  - 結果のJSON(Vitest・ESLint・Playwright)を読み、提出ファイルと配布ファイルの内容ハッシュを取る。
- **拡張のコマンド:** `STELLA: 課題を確認する`、`STELLA: 開発環境を診断する`、`STELLA: 実行ログを表示する`。結果はパネルと`.stella/last-run.json`に残る。
- **安全面:** Workspace Trustで信頼したフォルダーでだけプロセスを起動する。`stella.serverUrl`・`stella.webUrl`はユーザー設定だけを読む。
- **確認:** Vitest・ESLint・Prettier・Playwrightの実際の出力で読み取りを確かめた。見本の課題は`apps/vscode/samples/`。
- **runnerごとのテンプレート:** `node-test`・`dom-test`・`http-mock`・`react-test`・`storybook`・`api-test`・`db`・`e2e`・`next-app`の9つを`packages/content/templates/runners/`に置いた。それぞれから作った見本(直す前の状態)を`apps/vscode/samples/`に足した。
  - Linuxで、9つの見本を実際の手順(`npm ci`→ESLint・Prettier→Vitest/Playwright/`next build`)で実行し、直す前は要修正、直した後は合格になることを確かめた。日本語と空白を含むフォルダーで実行した。ブラウザーの準備(`playwright install chromium`)の手順だけは、検証した環境でブラウザーをダウンロードしなかったため通していない(入っていたChromiumを使った)。
  - テンプレートと手順の食い違い(道具の有無、固定の版、lockfileが公開レジストリだけを指すこと、他のOS用のネイティブ部品がlockfileにあること、環境の要件で通るNode.jsの版がすべての依存の`engines`を満たすこと)は`templates.test.ts`、見本の定義は`samples.test.ts`が確かめる。
  - `api-test`はHonoにした。`app.request()`でポートを開かずにテストでき、ポートの衝突やWindowsのファイアウォールの確認が起きない。Express版は要るときに足す。
- **Windows・macOS:** npmの解決(`npm-cli.js`をNode.jsで直接起動)、PATHの探索(`.exe`・`.com`だけ)、時間切れ・中断での停止(`taskkill /T /F`)、長いパスと日本語のパスを、OSを差し替えた単体テストで確かめた。実機での確認は残っている。確認項目は`apps/vscode/samples/README.md`。

- **課題の配布(#31):** APIから課題を受け取り、学習フォルダーへ配る(§4.4)。`apps/vscode/src/open-task.ts`・`task-distribution.ts`・`training-folder.ts`。

次に足すものは次のとおり。

- 提出とAIの一次レビュー(§6)。実装の状況は§6.8。
- 課題パネルのヒント・解答の表示(§8)。
- WindowsとmacOSの実機での確認(Issue #37)。
- `ci-deploy`でCIの結果を提出に添える仕組み。設計は次のとおりとする。
  - 受講者は自分のGitHubリポジトリにpushし、GitHub Actionsの実行が成功したら、その実行のURL(`https://github.com/<owner>/<repo>/actions/runs/<数字>`)と公開先のURLを提出に添える。
  - 拡張は、入力されたURLの形だけを確かめる。GitHubには問い合わせず、トークンも扱わない。手元のコミット(`git rev-parse HEAD`、固定の引数)を結果に控える。
  - APIは提出を受けたときに、GitHubの公開API(`GET /repos/{owner}/{repo}/actions/runs/{id}`)で、実行が成功で終わったこと、コミットが控えと一致すること、課題が指定したワークフローであることを確かめ、結果を提出と一緒に保存する。
  - 照合できないとき(非公開のリポジトリ、APIの回数制限、食い違い)は講師の確認待ちにする(§6.3)。レビュー画面には実行と公開先へのリンクを出す。
  - 提出の形式・API・レビュー画面はAIの一次レビュー(#33)で変わるため、その後に実装する。

## 6 提出・評価・レビュー

### 6.1 2系統の評価

- **知識:** アプリで回答する。今の小テスト(単一選択・複数選択・正誤。サーバー側で採点)を使う。教材から投入できるのは今は単一選択だけなので、`knowledge.md`から複数選択・正誤も書けるようにする。
- **実装:** VS Code拡張から提出し、AIが一次レビューする。提出は次の6つを1組にする。
  - 宣言したファイル
  - 手元の実行結果
  - 配布したテストのハッシュ
  - 説明
  - 支援の記録
  - 課題の内容ハッシュ

### 6.2 提出から合否までの流れ

```text
手元で実行(拡張の「確認」。テスト・lint・整形)
  → 受講者が結果を見て直す。全部通ると「提出」が押せる
  → 提出(ファイル・結果・説明・支援の記録)
  → 機械の照合(テスト・設定のハッシュ、結果と提出ファイルの対応)
  → AIの一次レビュー(提出直後に自動。コーディング規則など)
      ├ 人に回す条件(§6.3)に当たらない → 合格で確定。所見を受講者へ返す
      │      人はいつでもこの提出を確認できる(§6.4)
      └ 人に回す条件に当たる → 人の最終レビュー(AIの下書き付き) → 合格 / 再提出
             受講者には「講師の確認待ち」だけを見せる
```

動作の判定と規則の判定を分ける。

- **動作:** 受講者が手元のテストで確かめて直す。提出できる時点で、テストは通っている。
- **機械で判定できる規則:** 整形・未使用の変数・禁止した構文などは、lintとASTの検査に入れて手元の実行に含める。
- **AIと人が見る規則:** 機械で判定しにくい規則を見る。たとえば、名前が意味を表しているか、関数の分け方と責務、重複や不要な複雑さ、単元で教えた書き方を使っているか、既存コードの書き方に合わせているか、説明とコードが一致しているか。

すべての課題が同じ流れを通る。課題の種別で変わるのは、提出に必要なものと、AIが重く見る規則である。

| 種別 | 提出に必要なもの | AIが重く見る規則 | 合格で残る証拠 |
| --- | --- | --- | --- |
| 基礎・接続 | ファイルと手元の結果 | 単元で教えた書き方、命名、既習の規則 | 練習(支援の有無を記録) |
| 自力 | 上記 + 短い説明 | 構成と責務の分け方、説明とコードの一致 | 練習。支援なしなら自力の傾向として記録 |
| 修正 | 上記 + 再現・原因・修正・回帰確認の記録(03 §6) | 記録と差分の整合、変更が必要な範囲に収まっているか | 練習 |
| 統合 | 上記 + 説明 | 既存コードの書き方と部品の契約に合わせているか、責務の置き場所 | 統合の証拠 |
| 確認A | 上記 + 説明。ヒントと解答は使えない | 上記に加え、説明が自分の設計判断を述べているか | スキルを「自力で確認」 |
| 確認B | 確認Aと同じ | 確認Aと同じ | スキルを「時間を空けて確認」 |

### 6.3 人に回す条件と確信度のしきい値

**ルーブリックは確かめられる文で書く。** 「読みやすさを1〜5で採点」のような尺度にはしない。「関数名が戻り値の意味を表している」「同じ処理を2か所以上に書いていない」のように、コードを見て当否を決められる文にする。AIは各項目について「満たす」「満たさない」「判断できない」のどれかと、根拠になるファイルと行を返す。

**確信度は数値ではなく3段階にする。** AIが自分で付けた0〜1の数値は、実際の正しさと対応しない。そこで、根拠を示せたかどうかで次の3段階を定義させる。

| 確信度 | 定義 |
| --- | --- |
| 高 | すべての必須項目に、コードの該当箇所を根拠として示せる |
| 中 | 根拠は示せるが、規則の解釈に幅がある項目がある |
| 低 | 根拠を示せない項目がある。または、提出が課題と対応していないように見える |

**しきい値(初期値。おすすめの値で決定):**

| 課題の種別 | AIで確定する | 人に回す |
| --- | --- | --- |
| 基礎・接続・自力・修正(練習) | 確信度が高・中で、必須項目をすべて満たす | 確信度が低、または必須項目に「満たさない」「判断できない」がある |
| 統合・確認A・確認B(証拠になる課題) | 確信度が高で、必須項目をすべて満たす | 確信度が中・低、または必須項目に「満たさない」「判断できない」がある |

練習は件数が多く、誤って合格にしても後の類題や確認で拾える。そのため中まではAIで確定する。統合と確認A・Bはスキルの証拠になるため、中から人に回す。

ほかに、次の場合はAIの判定によらず人に回す。

- 機械の照合で、テスト・設定のハッシュが一致しない、または結果と提出ファイルが食い違う。
- 確認A・Bで、許されていない支援(ヒント・解答の表示)の記録がある。
- AIが判定できなかった(拒否・タイムアウト・形式の誤り)。AIが止まっても、提出は人のキューで必ず受け止める。
- 受講者が講師への相談を求めた。

**しきい値の見直し:** 人がAI合格の提出を確認した記録(§6.4)と、人の最終レビューの結果を使い、月に1回見直す。

- 練習の「中」でAIが合格にした提出のうち、人が覆した割合が1割を超えたら、その講座の練習も中から人に回す。
- 人に回した提出のうち、人がそのまま合格にした割合が8割を超える種別は、条件が厳しすぎる。項目の書き方かしきい値を緩める。
- 課題ごとの「人に回した割合」が3割を超えたら、AIより先に課題文とルーブリックを疑う。

**受講者への見せ方:** 人に回した提出は、受講者には「講師の確認待ち」とだけ表示し、AIの所見は見せない。人が確定した後に、人が確定した所見だけを返す。確認待ちの間も、受講者は次の課題へ進める。同じ課題を出し直した場合は新しい提出で置き換え、AIが改めてレビューする。

### 6.4 人のレビューの負担を減らす

今のレビューは、テナントの全提出を新しい順に並べるだけである。並べ替え・絞り込みは「今後対応」で、AI下書きは講師が画面を開いてから作る。下書きは課題文・テスト・解答例を知らない。

1. **AIの下書きを提出時に作る。** 入力は、プログラム共通と講座の追加分のコーディング規則、課題文、課題ごとのルーブリック、解答例、よくある違反、手元の結果である。人が開いた時点で、判定案・所見・受講者への返信案がそろっている。
2. **人に回した理由でキューを分ける。** 規則の違反、確信度、AIの判定不能、ハッシュの不一致、相談を見分けられるようにする。理由、待ち時間、担当者で並べる。管理者もレビューできるようにする(今はAPIでは可能でも、画面に入口がない)。
3. **確定は1回の操作で。** 人はAIの判定案を承認するか、所見を直して再提出にする。
4. **コメント集。** パターンごとによくある違反と定型コメントを持ち、選んで直して送れるようにする。
5. **まとめて見る。** 同じ課題の提出を並べ、共通のつまずきは全体への補足やつまずき教材(Discovery)へ回す。
6. **AIが合格にした提出を、いつでも確認できる。** 期間は限定しない。
   - 一覧は講座・課題・受講者・確信度・日付で絞り込め、既定では確信度が中のものを先に並べる。
   - 人ができることは3つある。確認済みにする。判定を変えずにコメントを足す(受講者へ通知する)。再提出に覆す(合格とスキルの証拠を取り消し、理由を受講者へ通知する)。
   - 覆した記録は、しきい値の見直し(§6.3)とAIへの指示の改善に使う。
7. **AIの判定を校正する。** 人の最終レビューでAIの判定を覆した記録も残し、ルーブリックとAIへの指示の改善に使う。

#### 6.4.1 コーディング規則の正本と適用(決定)

共通規則は教材と同じリポジトリで管理し、AIと人が同じ文書を見る方式を採用する。

| 対象 | 正本 | 役割 |
| --- | --- | --- |
| プログラム共通 | `packages/content/coding-rules.md` | 命名、責務の分け方、重複、説明とコードの一致など、講座をまたいで使う規則 |
| 講座の追加分 | `packages/content/courses/<slug>/coding-rules.md` | 言語・フレームワーク・講座で導入する書き方の規則 |
| 課題の評価 | `task.json`の`review`、`private/review.md` | 適用する規則のID、必須・任意の区別、課題固有の条件とよくある違反 |

- 規則には一意のID、確かめられる文、適用する言語・場面、導入する単元を持たせる。規則を未習の段階では合否の必須条件にしない。復習や確認A・Bには、出題時点までに導入した規則を適用する。
- 講座の規則は共通規則への追加とする。共通規則に例外が必要なら、対象・理由を共通の正本に記載する。課題のルーブリックだけで共通規則を上書きしない。
- 整形・禁止構文などは手元のlint・整形・ASTの検査へ対応させる(§6.2)。AIと人は、機械で判定しにくい規則について根拠のファイル・行を確認する。
- AIへの入力と人のレビュー画面は、適用する規則のIDと同じ本文を使う。レビュー結果に規則の内容ハッシュを残し、規則を改訂した後も当時の判断を確認できるようにする(§13)。
- `STYLE_GUIDE.md`のコード例の規則や教材の説明は、この正本を参照する。受講者が読む規則と、レビューの規則を別々に書き写さない。

ここで決めるのは正本の置き場所と追加規則との関係である。規則の本文・IDと読み込みの実装は、AIの一次レビューの作業で用意する。

### 6.5 一人ひとりを育てる

- **担当講師。** メンターは講師が担う。受講者ごとに担当講師を決め、キューとダッシュボードを担当分に絞れるようにする。新しいロールは作らない。
- **週次の育成メモ。** 予定と実績の差(§10)、スキルの状態、つまずき、支援の量、AIと人のレビュー結果から、AIが1人1枚の要約を作る。担当講師は5分で読み、一言の声掛けか、ペースの調整をする。
- **つまずきの検知。** 次のどれかが起きたら担当講師に知らせる。
  - 同じ課題で手元の失敗が続く。
  - ヒントを最後まで開く。
  - 数日進まない。
  - 確認Bに落ちる。
  - 人に回る提出が続く。
- **支援の記録。** ヒント・解答の表示、講師への相談、人のレビュー、AIチャットの利用を課題ごとに記録し、習得の水準(03 §7 の未確認・支援付き・自力・時間を空けて確認)に反映する。受講者自身にも見せる。
- **AIの所見を学びにつなげる。** 合格した提出にも、良かった点と次に試すこと(別解・読みやすさ)を短く返す。合格だけで終わらせない。
- **ピアレビュー(選択肢)。** `design-quality-basics`のレビュー単元から、受講者同士で自力・統合課題の提出をレビューする。レビューそのものを学習の証拠にし、担当講師はレビューの質を見る。

#### 6.5.1 実装の状況と決定(#38)

- **担当講師(実装済み)。** 担当は`learner_instructors`(§10の作業で追加)で、管理者が設定画面で割り当てる。
  - 添削待ちキュー(`GET /api/submissions?assigned=mine`)と講師ダッシュボード(`GET /api/analytics/instructor?assigned=mine`)を、担当の受講者だけに絞れる。新形式と旧形式の提出の両方が対象である。
  - 画面の既定は「担当がいれば担当だけ」にする。担当講師は、まず自分の受講者を見るためである。担当のいない講師は、これまでどおり全員を見る。
  - 絞っても、ほかの受講者の提出の件数はキューに出す。担当のいない受講者の提出を取り残さないためである。
  - 管理者は担当を持たないので、既定は全員のままである。APIの既定もテナント全体のまま変えない。
- **手元の失敗を数える方法(決定・実装済み)。** 提出前の結果も送る。ただし、回数を数えるための要約に限る。
  - **送るとき:** 拡張は、配布した課題(`.stella/distribution.json`がある課題)を確認するたびに、合格・失敗・環境のエラーを送る。中断した実行と、配布記録のない見本は送らない。
  - **送り先:** 合格はこれまでの`POST /api/tasks/local-result`、失敗・エラーは`POST /api/tasks/local-runs`に分ける。前の版のAPIは`local-result`の本文を見ずに合格として扱うので、APIを戻したときに失敗が「手元で合格」として残らないようにするためである。
  - **送る範囲:** 課題ID、配布した版の内容ハッシュ、全体の結果、通らなかった手順の種類(`lint`・`test`など決まった語彙)、テストの合格・失敗の件数だけ。型と検証は`packages/shared/src/tasks/local-report.ts`。
  - **送らないもの:** コード、ファイル名、ファイルの内容ハッシュ、テスト名、メッセージ、ログ、道具の版、OS。時刻はサーバーが付ける。
  - **残し方:** 受講者・課題ごとに1行の回数(`task_local_runs`)だけを持ち、実行ごとの履歴は残さない。版が変わると、連続の失敗を数え直す。
  - **理由:** つまずきの検知に要るのは回数と時刻で、中身は要らない。ログやメッセージには、受講者のコードや端末のユーザー名が混ざる。提出前の試行錯誤は評価に使わない。受講者は自分の回数を課題一覧で見られる。
  - 提出のときの実行結果(`local_result`)は、これまでどおり提出と一緒に送る(§6.7)。
- **支援の記録(実装済み)。** 課題ごとに次を束ねて返す(`GET /api/task-support`)。受講者は課題一覧で、講師は学習ペースの画面で、同じ記録を見る。
  - 提出に添えた支援(ヒント・解答・固定した開始点・講師の実装支援・AIの解答生成)。拡張が`.stella/support.json`に残したものと、受講者の申告である。
  - 講師への相談(相談として送った提出)と、人のレビュー。正本は提出とレビューの表にあり、写さずに読むときに束ねる。
  - AIチャット。課題一覧の「AIに相談」から開いた相談だけを課題に結び付け、`task_support_events`に残す。記録するのは応答が届き始めた相談だけで、失敗・時間切れの相談は数えない。送る前に、記録されることを画面で知らせる。
  - 受講者本人には、今読めるステージ(公開中で、受講中か修了)の課題だけを返す。講師・管理者はテナントの範囲で見る。
  - ヒント・解答の表示(#36)と固定した開始点(#31)は、`task_support_events`に種類を書けば足せる。表は変えない。
- **習得の水準への反映(実装済み)。** これまでの判定(提出に添えた支援、相談としての提出)に加え、次があれば「支援付き」にする。
  - その提出より前の、サーバーが記録した支援(AIチャットなど)。
  - 同じ課題で、先に講師へ相談した提出。
  - 人のレビューは記録に出すが、支援付きにはしない。再提出の指摘を受けて直すのは通常の流れで、支援付きにすると一度で通らなかった提出がすべて支援付きになるためである。
- **つまずきの検知(一部実装)。** 15分ごとのcronで担当講師に通知する。知らせすぎないよう、同じ出来事は1度だけ送る。
  - 同じ課題で手元の失敗が続く: 同じ版で5回続けて失敗し、最初の失敗から1時間以上たった。環境のエラーは数えない。連続ごとに1度、受講者1人につき1日1通まで。
  - 数日進まない: 平日3日、学習の記録(視聴・完了・手元の確認・提出・復習・受講開始)がない。止まった期間ごとに1度。
  - 確認Bに落ちる: 確認Bが再提出・不合格になった。同じ課題の後の試行(`attempt`が大きい提出)が合格していれば知らせない。一度合格した後に落ちた場合は知らせる。提出ごとに1度。
  - 人に回る提出が続く(決定・実装済み): 受講者の新形式の提出(相談を除く)に当てたAIの一次レビューを新しい順にたどり、AIで確定した提出に当たるまでに、受講者の取り組みを理由に人に回した提出が3件続いたら知らせる。
    - 数える理由は、機械の照合の食い違い・確認A・Bの支援・必須項目の「満たさない」「判断できない」・確信度・課題ごとの追加条件である。AIや教材の都合(AIが判定できない・必須の評価項目がない・所見の位置ずれ・返信と解答例の重なり)だけで回った提出は、数えも切りもしない。講師への相談は受講者が選ぶ支援なので見ない。
    - 続きごとに1度(続きの最初の提出で通知IDを決める)。続きが伸びても知らせ直さず、AIで合格して切れた後の新しい続きは改めて知らせる。
    - 続きの並びと30日の期間は、受講者の提出の順(提出の日時)で見る。判定がやり直しなどで遅れて当たっても、提出の順は変わらないためである。
    - 知らせるのは、続きの中で最後に当たった判定が3日以内のときだけ。ここだけは判定が当たった時刻で見る。前の提出の判定が遅れて当たり、そこで続きがそろうこともあるので、最新の提出の判定の時刻で見るとそろった続きを取りこぼす。3日に絞るのは、導入時に過去の判定をまとめて送らないためである。
    - 3件にした理由: 1件・2件は、新しい単元の書き方に慣れる途中でも起きる。AIで合格した提出を挟まずに3件続けば、課題文か規則の読み方で迷っている見込みが高い。
  - ヒントを最後まで開く(#36)は、#36の作業の後に足す。
- **週次の育成メモ(実装済み)。** 担当講師の画面(講師ダッシュボード)に、担当する受講者ごとに前の週(月曜〜日曜)のメモを1枚出す。
  - **材料:** 予定と実績の差(生成した日の§10の計算)、学習の記録がある日数・視聴・完了・提出、その週に合格した課題、スキルの水準ごとの数とその週に上がったスキル、その週のつまずきの知らせ(通知IDの接頭辞を検知と共通の関数で組み立てて引く)と続いている手元の失敗、支援の量(提出に添えた支援は支援の時刻で週に配る。日曜に使った支援を月曜に提出しても、使った週に数える)、AIの一次レビュー(確定・人に回した数と理由・満たせなかった必須項目)と人の判定。数字と、課題・スキル・評価項目の名前だけを集める。
  - **AIに渡さないもの:** 受講者の名前・メール・ID、コード、所見の本文、講師のコメント。講師は画面で名前と並べて読むので、AIには要らない。
  - **書くもの:** 2〜3文の要約、3〜5個の気づき、勧める対応(一言の声掛け・ペースの調整・様子見)とその理由、受講者への一言の案。一言の案にはレビューの中身を書かせない(講師が確定する前のAIの所見を受講者に見せない、§6.3)。
  - **講師の対応:** その場で一言を直して送る(受講者への通知。本文は講師が書いた文だけ)か、既存の学習ペースの編集で週の時間・開始日を直す(担当講師と管理者だけが他者のペースを変えられる既存の権限)。様子見も記録できる。対応はメモに追記して残す。
  - **見せる範囲:** 今の担当講師と同じテナントの管理者だけ。受講者本人には返さない。担当を外れた講師は読めない。
  - **API:** `GET /api/mentor-memos?week=<月曜の日付>`(既定は前の週)と、`POST /api/mentor-memos/:id/actions`(`kind`は`message`・`pace`・`watch`。`message`は`message`に本文)。
  - **生成(決定):** 15分のcronが、担当のいる受講者ごとに前の週の行を積み(受講者・週で一意)、5件ずつ材料を集めてAIに書かせる。cronが週をまたいで止まったときのために、直近4週のうちまだ無い週も積む。ただしさかのぼるのは、そのテナントで最初にメモを作った週(機能を入れた週)より後の週だけで、メモが1枚も無いテナント(初めてのデプロイ)は前の週だけにする。後から担当を付けた受講者にも、この範囲で前の週のメモができる。Message Batches APIは使わない。週に1人1回と量が少なく費用の差は小さい一方、材料集め(1人あたり十数クエリ)はcronのD1のクエリ上限を他の処理と分け合うので、どのみち数件ずつに分けて回す。Batchにすると、材料を集め終えるまでの待ち・バッチIDの保存と回収・期限切れの扱いが増える。受講者が待つ処理ではないので、数件ずつで足りる。
  - **AIが使えないとき:** APIキーが無い・拒否・形式の誤りは、材料の数字から機械的な要約を作って確定する。時間切れ・一時的な失敗は次のcronで3回まで試し、最後は機械的な要約にする。
  - **材料を集められないとき:** 機械的な要約も材料が要るので、次のcronで3回まで試し、最後は「作れなかった」(`failed`)で終えて失敗の理由を残す。講師の画面には「この週のメモを作れませんでした」と出し、対応は受け付けない。処理の途中でWorkerが止まった試行が上限を超えたときも、材料を集め直さずに同じく終える。
  - **記録:** `mentor_memos`に、受講者・週・本文・材料の要約・出どころ(AI・機械的な要約)・使わなかった理由・モデルと指示の版・生成日時・講師の対応を残す。モデルは`MENTOR_MEMO_MODEL`(未設定なら`ANTHROPIC_MODEL`)。
- **未着手。** ピアレビュー。

### 6.6 AIレビューの実装上の注意

- **判定はJSONで固定する。** 構造化出力(`output_config.format`)で返させる。今の下書きは、自由形式の応答をパースしている。返させる項目は次のとおり。
  - ルーブリックの各項目の結果(満たす・満たさない・判断できない)と、根拠のファイル・行
  - 確信度(高・中・低)
  - 所見(ファイル・行範囲・重さ・コメント)
  - 受講者への返信
- **判定はコードで決める。** 人に回すかどうかは、AIに直接言わせない。返ってきた項目の結果と確信度に、§6.3 のしきい値をコードで当てはめて決める。しきい値を変えても、AIへの指示を変えずに済む。
- **キャッシュを効かせる並びにする。** 変わりにくい部分ほど先頭に置く。順番は、レビューの指示、プログラム共通のコーディング規則、講座の追加規則、課題文、ルーブリック、解答例、よくある違反である。提出ごとに変わる部分(ファイル・結果・説明)は最後に置く。共通の規則までは全課題で、追加規則までは同じ講座で、課題文以降は同じ課題の提出が続く間、キャッシュから読まれる。既定の保持は5分で、1時間も選べる。
- **受講者が待つ処理にBatchは使わない。** Batchは費用が半分になるが、非同期で結果まで時間がかかる。次のような待たない処理に使う。
  - 週次の育成メモ。ただし実装では、量が少なく材料集めを数件ずつ分ける必要があるため、Batchを使わずcronで数件ずつ書く(§6.5.1)。
  - 人が覆した判定を使った、AIへの指示としきい値の点検。
  - 類題の下書きの検証。
- **非同期のキューで処理する。** 今のAIエンドポイントは60秒に20回の制限がある。提出を受けたらキューに積み、順に処理する。受講者には「AIが確認中」と表示する。
- **解答例を漏らさない。** 解答例はAIの入力に使うが、受講者への返信に解答のコードを含めないよう指示し、返信を機械的に照合する。確認A・Bでは特に厳しくする。
- **モデルとAIへの指示は評価用データで選ぶ。** 人がレビューした過去の提出を評価用データにし、人の判定との一致率で選ぶ。指示とモデルの版を、レビュー結果ごとに記録する。

### 6.7 データの変更

- `submissions`を、1つの`code`列からファイル単位の保存(R2)へ変える。持たせる項目は次のとおり。上書きせず、試行ごとの履歴を残す。
  - 課題ID・内容ハッシュ・種別
  - 手元の結果・テストのハッシュ
  - 説明・支援の記録
- AIレビューの結果を持たせる。適用した規則のID・内容ハッシュ、ルーブリックの各項目の結果、確信度、人に回したかとその理由、所見、受講者への返信、モデル・指示・しきい値の版である。人の判定は、AIの判定と別に記録する。
- AIが合格にした提出を人が確認した記録を持たせる。確認した人、日時、結果(確認済み・コメント・覆した)、コメントである。
- 所見を、行番号だけでなくファイルと行範囲に付ける。
- スキルと証拠の表を足す。スキルID、水準、根拠になった提出、支援の有無、日時を持たせる。
- 講座のクリア条件に、課題の判定(AIまたは人の合格)を使う。今の問題は次の2つである。
  - VS Codeの課題(`code`レッスン)は課題合格の条件に入らず、完了は自己申告である。
  - 講師が合格にしても、レッスンは完了にならない。
- 未判定のAI所見が受講者に見えている(`ReviewResultView.tsx`)。新しい流れでは、AIで確定したもの、または人が確定したものだけを見せる。人に回した提出のAIの所見は、受講者向けのAPIから返さない。

### 6.8 実装の状況(Issue #33)

AIの一次レビューを実装した。§6.2〜§6.7のうち、次は動く。

- **コーディング規則:** 共通の正本`packages/content/coding-rules.md`と講座の追加分`courses/<slug>/coding-rules.md`を、1規則=1見出し(ID・規則・対象・導入、任意で例外)で書く。課題は`task.json`の`review.rules`で規則のIDと必須・任意を指す。`content:check`は、未知のID・別講座の規則・未習の規則を必須にした課題を止める。seedがD1の`coding_rules`へ入れ、AIと人は同じ本文を読む。
- **ルーブリックの書き方:** `content:check`は、尺度(「1〜5」など)や問いの形の項目を止める。`review.escalateWhen`は`optional-unmet`・`major-finding`だけを書ける。
- **キュー:** 提出と同じ書き込みで`ai_review_jobs`に積み、応答後に`waitUntil`でその1件を処理する。残りとやり直しはcron(15分ごと)が拾う。リースで二重処理を防ぎ、AIの呼び出しは60秒に20回までにする。Batchは使わない。受講者の課題の状態は「AIが確認中」(`submitted`)になる。出し直すと、判定前の前の試行(人に回したものも)を「新しい提出に置き換え」にする。
- **構造化出力:** `output_config.format`でルーブリックの結果と根拠・確信度・所見・受講者への返信を返させる。モデルは`AI_REVIEW_MODEL`(未設定なら`ANTHROPIC_MODEL`)。入力は§6.6の順に並べ、共通の規則・講座の規則・よくある違反の後ろでキャッシュを区切る。
- **判定:** しきい値(§6.3の表)をコードで当てる。根拠のファイル・行が提出に無い必須項目があれば、確信度を「低」に下げる。提出に無いファイル・行を指す所見は受講者に見せず、統合・確認A・Bではその時点で人に回す。照合の食い違い・確認A・Bの支援・相談は提出の時点で人に回し、AIの下書きだけを作る。確認A・Bの支援は、提出の申告に加えてサーバーの記録(課題のAIチャット・相談、#38)も見て、AIの結果を当てる直前にも確かめ直す。APIキー未設定・拒否・時間切れ(3回まで試す)・形式の誤り(同じ項目を2回返した応答を含む)も人に回す。
- **提出時の素材:** 課題の版のハッシュは非公開の素材(解答例・`private/review.md`)を含まないので、素材は内容ハッシュごとの版(`task_private_versions`)として追記だけで残す。seedは新しい版を足し、既存の版を書き換えない。提出は受け付けた時点の素材の版を記録し(課題の版が今の版と同じときだけ)、AIはその版で判定・照合する。版が記録されていない提出(導入前の提出を含む。素材だけの更新は課題の版を変えないので、当時の素材は分からない)や版が残っていない提出は、判定せずに人に回す。コーディング規則も seed で上書きされるので、提出は受け付けた時点の規則の版(AIに渡す規則の本文のハッシュ)を記録し、レビューの時点の版と食い違えば判定せずに人に回す。提出の版が参照する規則が正本から消えていた提出も同じく人に回す。
- **解答例の照合:** 返信と所見を、解答例の字句の並びと照合する。受講者の提出と配布物にある並びは除く。練習は返信を定型文に差し替えて確定し、確認A・B(と統合)は短い断片でも当てて人に回す。
- **確定:** AIで確定した提出は、人の合格と同じ処理で進捗・スキルの証拠・通知・修了に反映する。人が先に確定した提出と、新しい提出がある試行には、遅れて届いたAIの結果を当てない。AIの確認待ちのまま人が確定した提出は「講師が先に確定」にし(「AIが確認中」を残さない)、AIの結果は一致率の評価のために記録だけする(出し直しがあっても、その試行のAIの待ちは取り消さない)。
- **受講者への見せ方:** 受講者向けのAPIは、AIで確定した提出の返信と所見だけを返す。人に回した提出には「講師の確認待ち」だけを出す。旧形式の提出も、確定前の下書きは返さず、確定後は講師が採用した指摘だけを返す。
- **記録:** `ai_reviews`に、規則のIDと内容ハッシュ、ルーブリックの結果、確信度、人に回した理由、所見、返信、照合の結果、モデル・指示・しきい値の版を残す。人の判定は`submission_reviews`に別に残る。
- **講師の画面:** レビュー画面に、人に回した理由・確信度・ルーブリックの結果と根拠・所見・返信案を出す。返信案は総評へ入れられる。キューとダッシュボードの「AI下書き準備済」は、AIの一次レビューが記録済みの提出も数える。
- **評価:** `bun run --filter=@stella/api ai-review:eval`が、人がレビューした提出を評価用データ(JSONL)に書き出し、モデル・指示・しきい値の版ごとの一致率と§6.3の見直しの目安を出す。

残りは次のとおり。

- 候補のモデル・指示を、評価用データの提出に当て直して比べる仕組み。今は運用で切り替えた期間ごとの一致率を比べる。
- 人に回した理由で分けたキュー、AIが合格にした提出の確認(確認済み・コメント・覆す)の画面と記録(§6.4の2・6)。レビュー画面の作り直しはIssue #34で扱う。
- `dev-env-basics`の課題への`review.rules`の追加。評価条件の改訂になるので、参照元の確認(§9.1)と合わせて行う。

## 7 復習

### 7.1 知識はSRS

今のSRS(`review_cards`、SM-2、1日20枚)をそのまま使う。カードの元を`knowledge.md`の知識問題に限り、スキルと結び付ける。

### 7.2 コードはパターン単位の類題

SRSは同じ設問を解き直させる。コードでは、同じ実装パターンの別の問題(類題)を時間を空けて出す。

- **パターンの台帳。** 単元の基礎課題は、「値・条件・境界・組合せ・利用場面」を変えた同じパターンの問題群である(03 §2)。その単位を`pattern`として登録する。
- **類題の在庫。** パターンごとに、練習用の課題(公開)と、確認A・B・復習用の予備(`private/variants/`)を持つ。予備は出題した時点で受講者のIDEに配る。受講者ごとに出題済みを記録し、見た問題を「未見」として出し直さない(03 §7)。
- **出す時期。** 自力で合格したパターンは、約3日後・約1週間後(=確認B)・約3週間後に類題を出す。支援付きでしか解けなかったパターンは間隔を短くし、補習の小問題3問と、翌日以降の未見問題へつなぐ(03 §7)。
- **評価。** 類題も通常の課題と同じ流れ(手元で実行 → 提出 → AIの一次レビュー)を通る。
- **作り方。** データや条件を差し替えられる課題は、テンプレートとパラメータから類題とテストを作る。AIで類題の下書きを作ってもよい。ただし、在庫に入れる前に次を満たす。
  - 解答例が全テストに通る。
  - 典型的な誤答(ミュータント)がテストで落ちる。
  - 人が承認する(今のDiscoveryと同じく承認制)。
- **毎日の復習画面。** 知識のカードと「今日の類題」1問を並べる。類題は「VS Codeで開く」から解く。

## 8 解答と非公開素材のUX

解答を「隠す」より、「出す順番」を設計する。練習で行き詰まらせないことと、自力確認の結果を正しく残すことを両立させる。

| 種別 | 取り組み中 | 合格後 | 備考 |
| --- | --- | --- | --- |
| 基礎・接続 | ヒントを段階的に開ける(方針 → 手がかりのコード → 解答例) | 解答例と解説を自動で開く。自分のコードと並べて見られる | ヒントや解答を開くと「支援付き」になる。罰ではなく記録 |
| 自力・修正 | ヒントは開ける。解答例は一定回数の挑戦後か合格後 | 解答例・別解と、選び方の理由 | 支援の段数を証拠に残す |
| 統合 | 仕様・状態見本・API契約へのリンクだけ | レビューの所見と解答例 | — |
| 確認A・B | 公式ドキュメントと文法の参照だけ(03 §7)。拡張はヒント・解答の表示を止める | 所見。Aの解答例は確定後に開く | 未出題の予備は見せない |

- ヒントと解答はIDEの課題パネルに出す。今のパネルは課題文と採点結果しか出さない。
- `private/`は、seedでD1・R2の非公開の場所へ入れる。公開APIは、解放条件を満たした受講者にだけ返す。AIレビューは解答例を読むが、受講者への返信に解答を含めない(§6.6)。
- 配布・印刷用のPDFは、新形式では課題文・参照元・解説だけにし、解答編を作らない。
- **公開前に確かめること。** 今の公開APIは課題のテストを受講者へ返す。新形式ではテストを配る前提なので問題ないが、解答例は返さないようにする。Webの`AIChatBot.tsx`は`@stella/shared/assignments`を読み込んでおり、課題の解答がWebのJSに含まれている可能性がある(未検証)。
- **正本の置き場所。** `private/`も含めて教材リポジトリ(`packages/content`)で管理する(決定)。リポジトリ(`otomatty/stella`)は公開なので、GitHubを直接読めば解答例と予備の類題は見える。そのうえで、アプリは解放条件を満たすまで受講者へ配らない(公開API・配布PDF・拡張に載せない)。

## 9 参照元(新設計05を採用)

- `packages/content/CLAUDE.md`の絶対ルール3「クレジット表記を教材本体に入れない」を、05に沿って書き換える。`STYLE_GUIDE.md`と`THEME_TO_COURSE.md`の外部素材の節も合わせる。
- 台帳は`packages/content/sources/registry.json`(05 §8 の`source-registry.json`)、使用箇所は単元の`references.json`に置く。トピック・まとめ・課題の冒頭(front-matter・`task.json`)には、参照元IDを書く。
- 表示は4か所にする。解説・課題の近く、単元の末尾の一覧、IDEの課題パネル、配布PDFである。
- 版は常に最新を配信するため(§13)、公開の関門はCIに置く。§9.1で必須とする単元について、`content:check`は次の場合に失敗させ、`main`へ入れない。
  - 未登録のsourceRefがある。
  - 技術のトップページだけを根拠にしている。
  - レビュー状態が`approved`でない。
  - 環境の定義がない。
- リンク切れは週1回の定期ジョブで確認する。タイムアウトやアクセス制限は削除と分け、手動確認として記録する(05 §9)。
- 残す講座は、新規・内容改訂の単元から必須にし、未改訂の既存単元は警告だけにする(§9.1)。

### 9.1 残す講座への適用(決定)

新形式の18講座には、初回の公開から05の参照元ルールを適用する。残す講座は次の範囲で段階的に適用する。参照元の対応だけを足すために旧形式を`format: 2`へ移す必要はない。

| 教材の状態 | 適用範囲 | 公開の扱い |
| --- | --- | --- |
| 新しく作る単元 | 単元の解説・参考例・図・課題すべて | 05の要件を満たすことを必須にする |
| 内容を改訂する既存単元 | 改訂する単元の解説・参考例・図・課題すべて | 改訂版の公開から必須にする |
| 内容を改訂していない既存単元 | 参照元の不足を検出する | 警告として一覧に残し、既存の公開を止めない |

内容の改訂には、説明、参考コード、図、課題・解答・評価条件、採用技術や環境の変更を含める。誤字・表記・レイアウトだけの修正と、カリキュラム切り替えに伴う講座の前提・`parent`の付け替えは、参照元を整備するための内容改訂には数えない。

公開の検査は、上の適用範囲と未改訂の範囲を区別する。未改訂の不足で、別の単元の新規作成・改訂を止めない。JSONやリンクの検査に加え、講師による資料と本文の対応確認を公開前に行う(05 §9)。

## 11 OS別の手順

可能である。ただし、今の描画は4系統(Webの`react-markdown`、VS CodeのWebView、PDF・動画、pptx)に分かれている。WebとVS Codeは生のHTMLを文字として出し、VS CodeのWebViewは画像も出せない。そこで範囲を絞る。

- **書ける場所を限る。** OS別のブロックは、まとめ(`doc.md`)と課題文(`README.md`)だけに書く。スライドと動画はOSに依存しない説明にし、pptxと動画の生成は変えない。
- **書き方:**

  ```markdown
  :::os windows
  PowerShellで次を実行します。
  :::
  :::os macos
  ターミナルで次を実行します。
  :::
  ```

- **見せ方:** OSのタブにし、既定は受講者のOSにする。拡張は`process.platform`で正確に分かる。Webは利用者のOS情報から推定し、プロフィールの設定で上書きできるようにする。「あなたのOS: Windows(変更)」と表示する。
- **画像:** `name.windows.png` / `name.macos.png`のように、OSごとに用意する。
- **PDF:** `dev-env-basics`のようにOS差が大きい講座は、OS別にPDFを作る。それ以外は、両方を見出し付きで並べる。
- **検査:** OS別のブロックは、WindowsとmacOSの両方がそろっていること、画像がOSごとにあることを確かめる。
- **環境診断:** 拡張がOSに応じて確認コマンドを変える(例:Windows PowerShellの`npm.cmd`、06 §3)。

### 11.1 実装の状況

上の範囲を実装した。

- **記法:** 行頭の`:::os windows` / `:::os macos`で始め、行頭の`:::`だけの行で閉じる。空行だけを挟んで続くブロックを1組(タブ1つ)にする。入れ子、リスト・引用の中、未知のOS名は誤りとする。コードブロックの中の`:::`は記法として扱わない。
- **解析:** `packages/shared/src/markdown/os-blocks.ts`の1つを、Web・VS Code・PDF・検査が共有する。誤りのある本文も、その行を本文として残して描く。CMSで直した本文でも、画面から本文が消えない。
- **Web:** まとめ・課題文のテキストレッスンで、OSのタブにする。既定は、プロフィールの設定(`profiles.os_preference`、`POST /api/me`)、端末からの推定、Windowsの順に決める。タブの横に「あなたのOS: Windows(変更)」を出す。「変更」と設定画面の「教材のOS」から保存できる。タブの切り替えでは、設定を変えない。
- **VS Code:** レッスンのドキュメントと課題文のパネル(`STELLA: 課題文を表示する`)で、`process.platform`のOSのタブを開いておく。WebViewはスクリプトを使わず、ラジオボタンとCSSで切り替える。生のHTMLは、今までどおり文字として出す。
- **画像:** `<名前>.windows.png` / `<名前>.macos.png`の対で、トピックの`assets/`に置く。R2へは図解と同じ経路で上げる(SVGに加えてPNG・WebP・JPEG)。
- **PDF:** `course.json`に`"pdfByOs": true`を書いた講座(`dev-env-basics`)では、OS別のブロックを含むまとめ・課題文をOSごとのPDFにする。資料タブには「… (Windows).pdf」「… (macOS).pdf」が並ぶ。それ以外は、1つのPDFに「Windows の場合」「macOS の場合」の見出しで両方を並べる。OSで分けない資料のR2キーと版履歴は変わらない。分け方を変えたレッスンでは、作らなくなった資料に`archived_at`を付けて受講者の一覧から外す。行と版履歴は残すので、staffは旧版を取れる。
- **検査:** `content:check`(`scripts/check-os-blocks.ts`)が、記法の誤り、片方のOSしか無い組、書けない場所(スライド・知識問題・ヒントなど)のブロック、対になっていない画像を落とす。
- **環境診断:** OSごとに確認方法を変える必要はないと判断した。拡張はシェルを通さず、Windowsでも`npm.cmd`ではなく`npm-cli.js`をNode.jsで直接起動する(§5.5)。PowerShellの実行ポリシー(`npm.ps1`)は、拡張の診断に影響しない。影響を受けるのは受講者がターミナルで打つコマンドなので、教材のWindowsのブロックに`npm.cmd --version`と書く。道具の探し方(PATHの区切り、`PATHEXT`、npm本体の場所)は、既にOSごとに分けている。

次に足すものは次のとおり。

- `dev-env-basics`の本文(#41)で、OS別のブロックとOSごとの画像を使う。見本の単元にはまだ書いていない。
- 課題を配ったときに、課題文のパネルを開く(配布の流れ)。今は`README.md`をテキストのまま開く。

## 12 学習画面の置き場所(判断材料)

未決のため、どちらの案にも寄せない。ただし、次はどちらに決めても変わらない。

- IDEに課題パネルが要る。出すものは、課題文・ヒント・実行・提出・AIと人のレビュー結果・参照元である。

| 観点 | VS Code(WebView)に置く | Webに置く |
| --- | --- | --- |
| 解説と演習の行き来 | 同じ画面で横に並べられる | ウィンドウを切り替える |
| VS Code導入前の閲覧 | できない(別途Webが要る) | できる |

| スマートフォンでの知識問題・SRS | できない | できる |
| 開発の手間 | 解説の描画をWebViewにも作り、2系統を保守する | 今の画面を使える |
| 印刷・PDF | 影響なし | 影響なし |
| 学習の中断と再開 | VS Codeを開けば続きから | ブラウザとVS Codeの両方を開く |

- 画面を切り替えた回数
- 最初にHTMLの変更を表示できるまでの時間
- 途中で止まった場所
- 支援の量
- 翌日の再開にかかった時間
