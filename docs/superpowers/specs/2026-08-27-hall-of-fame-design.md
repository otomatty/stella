# 殿堂 (Hall of Fame) 設計書 (Phase 5)

日付: 2026-08-27
ステータス: 実装済み (Phase 5 + レビュー指摘対応)

## 目的

「この会社で学んだ人」の実名のストーリーを載せる場所を作る。ゲーミフィケーションの数値
(XP / レベル / クリア数) の延長ではなく、**先を歩いた人の物語**として読ませる。載る人は
運営が選び、載るかどうかは本人が決める。

実装の所在:

| 層 | ファイル |
|---|---|
| 純関数 (状態の門番・正規化) | `packages/shared/src/hall-of-fame/types.ts` |
| D1 読み書き / 「歩んだ道」の写し | `apps/api/src/lib/hall-of-fame-data.ts` |
| 公開読み出し・本人の記入 API | `apps/api/src/routes/hall-of-fame.ts` |
| 運営 API (管理者だけ) | `apps/api/src/routes/cms-hall-of-fame.ts` |
| 画面 | `apps/web/src/components/hall-of-fame/*`、`apps/web/src/components/admin/AdminHallOfFamePage.tsx` |
| スキーマ | `apps/api/drizzle/0038_hall_of_fame.sql` (additive)、`schema.ts` の `hallOfFameEntries` |

## 決定事項

| 論点 | 決定 |
|---|---|
| 誰が選ぶか | **管理者だけ** (`requireTenantAdmin`)。講師は関与しない — 受講者を日々評価する立場が選出に加わると、選ばれなかったことが評価に見える |
| 選出条件 | **公開しない**。API はしきい値も実績順の並びも持たず、候補一覧は表示名順 (実績順の一覧は条件の答え合わせになる) |
| 誰が載せるか | **本人**。管理者は「本人が書いて申請した内容」しか公開できない。代筆も、推薦からの直接公開も経路が無い |
| 載る中身 | 実名 / ジョブ (本人の名乗り・40字) / 引用 (80字) / 4 章 (各2000字) / 歩んだ道 (ステージ名) |
| 載らないもの | XP・レベル・クリア数・順位。**型の側から排除**する (`HallOfFamePathStage` は id と title だけ) |
| 辞退・取り下げ | いつでも。**監査ログに残さない** (`audit-actions.ts` の注記) |
| 見た目 | 夜空 × 金の固定トーン。アプリのテーマ (light/dark) を参照しない唯一の空間 (`.hof` / `index.css`) |
| 再推薦 | **しない**。辞退した人へ招待を送り直す口を作らない (`nominate` は 409) |

## 1. 状態機械

```
                    [なし]
                      │ admin: POST /api/cms/hall-of-fame/nominate
                      ▼
                 nominated ──────────── 本人: decline ──────► declined
                      │                                        (終端)
                      │ 本人: PUT /mine {submit:true}
                      │   ※ 全項目が埋まっているときだけ
                      ▼
                 submitted ──────────── 本人: decline ──────► declined
                      │  ▲
   admin: publish     │  │  admin: unpublish
   (+ expected_       │  │  (closed_at を刻む。同意はそのまま)
    submitted_at)     ▼  │
                 published ─────────── 本人: withdraw ─────► withdrawn
                                                              (終端)
```

- 一般に見えるのは `published` だけ (`isHallOfFamePublic`)。
- `published` からは本人が編集できない (`canEditOwnEntry`)。直すときは取り下げてから。
- `withdrawn` / `declined` は終端。再掲載は新しい招待から。
- 状態を書き換える更新はすべて `updateEntry(db, tenant, id, expectedStatus, patch)` を通す。
  D1 に比較交換は無いので、**更新条件に今の状態を含めて** 0 件更新で競合を検知する
  (2 タブで「公開」と「辞退」を同時に押しても、後から来た方が 409 で止まる)。

## 2. 同意の不変条件

仕組みの側で守る線。どれか 1 つでも破れたら殿堂は「本人の同意で載る場所」ではなくなる。

1. **`published` へ進めるのは `submitted` からだけ** (`canPublish`)。推薦しただけの行・辞退した行・
   取り下げた行から公開へ進む経路は存在しない。
2. **本文を書けるのは本人だけ。** 書き込みは `PUT /api/hall-of-fame/mine` (呼び出した本人の行)
   に限られ、運営 API に本文の PATCH は無い。他人の掲載 id を送れば 403。
3. **申請できるのは全項目が埋まっているときだけ** (`isHofContentComplete`)。欠けたまま管理者の
   手に渡ると、管理者が代わりに書き足す誘惑が生まれる。
4. **管理者が読んだ版だけを公開できる。** `publish` は `expected_submitted_at` を必須にし、
   本人が読み直しのあいだに出し直していれば 409「内容が更新されています。読み直してください」。
5. **申請前の下書きは誰にも見えない。** 管理者の一覧 (`staffPayload`) も、`submitted` /
   `published` 以外の行では本文 (ジョブ・引用・章・歩んだ道) を **空で返す**。画面で伏せるのでは
   なく API から出さない。記入画面の「この時点では誰にも見えません」がこれで真になる。
6. **辞退・取り下げは監査に残さない。** 断ると記録が残ると分かっている招待は断りにくい招待。
   運営に必要なのは「今この人が載っているか」だけで、それは行の状態が持っている。
7. **非公開化の行き先は `submitted`。** `nominated` へ戻すと「本人が申請した」事実まで消え、
   次の公開が同意の裏付けを失う。

### 辞退について画面が約束すること

実装が守れる範囲だけを書く。**「記録も残りません」とは書かない。**

> 辞退は運営の監査ログに残らず、学習にも評価にも影響しません。再度の招待は届きません。

行そのものは `declined` として残る (再推薦を止めるための最小限)。管理画面ではその実名を
畳んだ「辞退 (再推薦不可)」節に薄く置く — 消すと「なぜこの人を推薦できないのか」が画面から
読めなくなるため。日々見る本表からは外す。

## 3. 秘匿の決着事項

| 論点 | 決着 |
|---|---|
| 公開されていない掲載の id 直打ち | **存在ごと 404**。403 で書き分けると応答の違いから「誰が推薦されているか」「誰が辞退したか」が読める |
| 招待が無い / もう終わった招待 | 記入画面は理由を書き分けない (「現在お受け取りいただいている招待はありません」)。辞退したことを画面が繰り返し告げない |
| 申請前の下書き | 管理者にも渡さない (不変条件 5) |
| `path_snapshot` に入るステージ | **`stages.status = 'published'` のものだけ**。下書き・退役の教材名が全ロールに開いた画面へ出るのは、運営がまだ公開を決めていない教材名の漏洩 |
| 「歩んだ道」に霧 (視界) を掛けるか | **掛けない — 受容**。下記 |

### 霧を掛けない理由 (受容)

学びの地図の霧 (`skill-map`) は **自分の道から目移りしないため** の仕掛けであって、教材名の
秘匿ではない。殿堂に出るのは管理者が 1 件ずつ公開を判断した「先を歩いた人の物語」で、その道の
先が垣間見えることはゴール勾配として設計の意図どおり。

閲覧者ごとに道を伏せると、**同じ掲載が読む人によって別の物語になり**、本人が同意した「掲載される
内容」が確定しなくなる。よって視界による出し分けは入れない。止めるのは「写す瞬間に公開されて
いたか」だけで、それは `buildPathSnapshot` の `eq(stages.status, "published")` が担う
(`apps/api/src/lib/hall-of-fame-data.test.ts` が実 SQL で固定)。

## 4. 「歩んだ道」(`path_snapshot`)

- クリアの定義はスキルツリーと同じ **修了した受講登録 ∪ 失効していない修了証**。片方だけ見ると、
  修了証を手で出したステージや自動発行を切ったステージで殿堂とスキルツリーが食い違う。
- 並びは **点いた順**。件数も XP も載せない。カードは先頭 3 つ (`HOF_PATH_PREVIEW_COUNT`) まで。
- **参照ではなく写し**。公開したあとに教材が改名・退役しても、掲載は同意した時点の姿のまま残る。
- 応答は `{id, title}`。id は画面の key に使う (同名ステージで React が要素を取り違えない)。

## 5. 「この道をたどる」CTA

- 行き先はサーバが決める (`resolveFollowStage`)。掲載された道のうち、閲覧者のスキルマップで
  `unlocked` / `active` の最初のステージ。判定は自己開始 API と同じ評価器なので「押せるのに
  始められない」が起きない。
- 表示名は **閲覧者から見えている今の名前** (掲載時の写しは掲載者の記録)。
- 見つからなければ `null` で、画面は CTA ごと出さない。「あなたには辿れません」とは書かない。
- **計算するのは `student` のときだけ。** CTA は受講者の画面にしか出ないので、それ以外のロールで
  スキルマップを組み立てるのは捨てるための計算になる。管理者が受講者画面で試す場合、殿堂の詳細
  からは CTA が出ない (学びの地図から始める) — 意図した割り切り。

## 6. 入力の正規化 (`normalizeLine`)

殿堂に載るのは実名の隣に置かれる本人の文章なので、**見た目と実体がずれる字を通さない**。

1. 制御文字・書式文字 (`\p{Cc}` / `\p{Cf}`) を除去。U+202E (RLO) のような双方向制御が残ると、
   管理者が読んで公開を判断した文面と受講者に見える文面がずれる。**改行は章だけ許す**
   (1 行の項目に改行が入るとカードの前提が崩れる)。
2. `trim()`。
3. **コードポイント単位で** 上限まで切る。UTF-16 の `slice` は絵文字の途中で切って単独サロゲートを
   残し、以後の JSON 往復や描画を壊す。
4. 章の JSON は未知のキーを落とし、欠けたキーを空文字で埋める (`normalizeHofChapters`)。

## 7. スキーマ (`0038_hall_of_fame.sql`, additive)

新規テーブル 1 つだけ。**1 人 1 行** (`unique(tenant_id, user_id)`) で、推薦から取り下げまでを
同じ行の `status` で表す。履歴テーブルに分けないのは、必要なのが「今この人が載っているか」だけで、
辞退や取り下げの経緯を掘り返せる形にしておくこと自体が本人への圧力になるため。

- `chapters` の DEFAULT は `schema.ts` の `EMPTY_HOF_CHAPTERS` と同じ **4 キーを展開した JSON**。
  `'{}'` だと DB の既定値と ORM の既定値が食い違う。
- `path_snapshot` は `'[]'`。
- `user_id` は `profiles` へ `on delete cascade` — プロフィールを消せば殿堂の行も消える (実名を残さない)。
- 索引: `(tenant_id, user_id)` unique / `(tenant_id, status, published_at)`。

## 8. 監査

| action | いつ |
|---|---|
| `hof_nominate` | 管理者が推薦した |
| `hof_submit` | **本人が掲載を申請した** (= 公開への同意。後から必ず問われるので残す) |
| `hof_publish` | 管理者が公開した |
| `hof_close` | 管理者が非公開に戻した |

`decline` / `withdraw` は **記録しない** (不変条件 6)。
