# 外部アプリから STELLA を利用する

連携 API の基点は `/api/integrations/v1`。サーバーから呼び出すための API です。
管理者のログイン Cookie・セッショントークンとは独立しています。
グループ・メンバー・ステージの書き込みと、進み具合・できごとの読み取りに対応しています。

## 認証と運用

管理者が `/admin/integrations` で外部アプリごとにクライアントを作り、
必要な scope だけを選びます。トークンは作成・再発行の応答と、その直後の画面でだけ表示されます。
外部アプリのサーバーの secret に保存し、ブラウザ・ソースコード・ログへ含めないでください。
以後の一覧には先頭の識別部分だけが表示されます。STELLA の DB に保存するのは SHA-256 ハッシュです。

各リクエストに `Authorization: Bearer <トークン>` を付けます。
トークンに期限はありません。停止すると即時に使えなくなり、復帰すると同じトークンを使えます。
再発行すると古いトークンは無効になります。クライアントの最後の利用日時は約5分間隔で更新します。
画面を離れると発行したトークンは再表示できません。失った場合は再発行してください。

| scope | 許可する操作 |
| --- | --- |
| `groups:write` | 自分のグループの作成・更新 |
| `members:write` | グループへの受講者の追加・削除 |
| `stages:write` | グループのステージ設定の取得・置き換え |
| `progress:read` | グループの受講者の進捗の取得 (#206) |
| `events:read` | グループの受講者の出来事の取得 (#206) |

## 疎通確認

`GET /api/integrations/v1/me` は scope を必要としません。
自分のクライアントの名前・scope と、自分のグループのキー・名前・人数だけを返します。
受講者の ID・名前・メールや、ほかのクライアントのグループを含みません。

```json
{
  "client": { "name": "サンプル連携", "scopes": ["groups:write"] },
  "groups": [
    { "key": "sample:term-1", "name": "サンプルのグループ", "memberCount": 0 }
  ]
}
```

## グループの作成・更新

`PUT /api/integrations/v1/groups/{key}` は `groups:write` を必要とします。
Content-Type は `application/json`、本文は `{"name":"サンプルのグループ"}`。
キーは英数字・`:`・`-`・`_` の1〜100文字、名前は前後の空白を除いて1〜200文字です。
同じクライアント・同じキーへの再送は同じグループの名前を更新します。
常に200で `{"group":{"key":"sample:term-1","name":"サンプルのグループ"}}` を返します。
同じキーでもクライアントが異なれば別のグループです。
作成時は空のグループです。以下の API でメンバーを追加できます。

## メンバーの追加

`PUT /api/integrations/v1/groups/{key}/members` (`members:write`)。
本文は `members` 配列で、1回100人まで。空配列は何もしません。
一覧に無い人を外す操作ではありません。同じ一覧を再送しても重複しません。

```json
{
  "members": [
    { "email": "applicant@example.test", "displayName": "応募者の例", "externalId": "applicant-001" }
  ]
}
```

- メールは前後の空白を除き小文字にして、既存の招待と同じ形式検査をします。
- 未登録の人は既存の管理者招待と同じ関数で `student` として招待します。現在の方式では招待メールは送らず、Google ログイン待ちのアカウントを作ります。ログインが先だった人は既存の認証 ID を再利用します。
- `displayName` は省略可能、200文字まで。新規招待時の空欄・省略はメールの `@` より前を名前にします。既存の人の表示名は変更しません。
- `externalId` は省略可能、前後の空白を除いて1〜200文字、同一グループ内で一意です。省略は現在値を保ち、指定は更新、`null` は解除します。別の人が持つ ID を奪うことはできません。
- 無効なアカウントと管理者のアカウントは追加しません。
- 新しく参加した人にも、その時点のグループのステージ設定を適用します。再送でも修復・再適用します。

全体は200、入力順の `index` と各人の結果を返します。失敗した行があっても他の行を処理します。
配列自体が不正、または101人以上なら400です。

```json
{
  "results": [
    { "index": 0, "status": "invited", "id": "stella-profile-id" },
    { "index": 1, "status": "failed", "id": null, "code": "invalid_email" }
  ]
}
```

| status | 意味 |
| --- | --- |
| `invited` | 新規招待しグループへ追加した |
| `existing` | 既存アカウントをグループへ追加した |
| `already_member` | 既にグループにいる (外部 ID の更新もこの結果) |
| `failed` | この行は失敗、`code` を確認 |

| code | 意味 |
| --- | --- |
| `invalid_email` | メールの形式が不正 |
| `invalid_member` | 表示名・外部 ID の形式や長さが不正 |
| `external_id_conflict` | 同じグループの別の人が外部 ID を使用している |
| `not_invitable` | 無効なアカウント、または受講者以外 |
| `invite_failed` | 招待の作成に失敗。時間を空けて再送できる |

## メンバーの削除

`DELETE /api/integrations/v1/groups/{key}/members/{id}` (`members:write`)。
`id` は STELLA のプロフィール ID、`?by=external` を付けると外部 ID です。
成功は200で `{"removed":true}`。不存在・グループ外は同じ404です。
削除後の再送も404ですが、削除済みの状態は変わりません。
STELLA のアカウント・受講登録・進み具合は削除しません。

そのグループが作った割り当てのうち未着手 (受講登録無し) のものだけを削除し、
その際にそのグループが作った前提免除も削除します。
開始済みの割り当てと免除は残し、期限・案内文・案内元名を消します。
手動・他グループの割り当てや免除には触りません。

## グループのステージ設定

`PUT /api/integrations/v1/groups/{key}/stages` (`stages:write`) は一覧全体を置き換えます。
1回100ステージまで。空配列は設定をすべて外します。
`GET` は同じ scope で現在の設定を slug 順に返します。
PUT と GET の応答は、下の本文と同じ形 (省略した項目は `null` / `false`) です。

```json
{
  "stages": [
    {
      "slug": "devlab-ts-ch01",
      "due_at": "2026-12-10T09:00:00+09:00",
      "message": "期限までに事前課題に取り組んでください。",
      "exempt": true
    }
  ]
}
```

- `slug` は `audience: granted` のステージだけ。クライアントの `allowedStagePrefixes` のいずれかで始まる必要があります。空の許可一覧は何も指定できません。
- 親の鎖に `audience: granted` のステージがある場合は、その祖先もすべて同じ要求の `stages` に指定してください (順序は問いません)。`catalog` の祖先は指定不要です。親を自動では割り当てず、祖先にも接頭辞の制限が適用されます。
- `due_at` は省略・`null`、タイムゾーン付き ISO 日時 (秒必須)、または日付 `YYYY-MM-DD`。日付だけなら、**日本時間のその日の 23:59:59** とし、保存・応答は UTC の ISO 日時に揃えます (例: `2026-12-04` → `2026-12-04T14:59:59.000Z`)。時刻付きは指定された時刻を保ちます。存在しない日付は拒否します。
- `message` は省略・`null` または500文字以内。既存の案内と同じ上限です。
- `exempt` は省略時 `false`。`true` なら既存と同じ `via: staff` の前提免除を作ります。受講登録は作らず、始めるのは本人です。
- いずれかの入力が不正なら **要求全体を400** にし、設定も割り当ても変更しません。

```json
{
  "error": "Invalid stages",
  "errors": [ { "slug": "other-stage", "code": "prefix_not_allowed" } ]
}
```

ステージ別のコードは `invalid_stage` (形式・日時・文字数)、`duplicate_slug`、
`prefix_not_allowed`、`not_granted` (不存在または granted 以外)、
`parent_not_included` (granted の祖先が同じ要求に無い) です。
`parent_not_included` の `slug` は、指定が足りない祖先の slug を返します。

設定をグループ内の受講者に適用し、`stage_grants` の `due_at`・`message`・`source_name`
(クライアント名) に案内を保存します。ホーム・スキルツリーは既存の読み取り経路で表示します。
割り当ては人とステージで一意です。既に手動または別グループの割り当てがあれば、
その所有元と案内を保護し、上書き・所有権移動・免除の追加をしません。
このグループが作った行は `source_group_id` で区別します。

一覧から外したステージは、未着手の割り当てとそのグループの免除だけを削除します。
開始済みは残し、期限・案内文・案内元名を消します。`exempt` を false に戻す場合も、
そのグループが作った免除だけを解除し、手動や腕試しの免除は保ちます。

設定の置換・割り当て・免除は一つの D1 batch で処理します。
人数に比例する ID 配列を SQL のバインドへ展開せず、INSERT SELECT でまとめて適用します。
メンバー追加は各人の招待を個別に作り、成功した全員のメンバー行と全ステージの反映を一つの batch にまとめます。
招待が済んだあとに反映で内部障害が起きた場合も、再送で同じアカウントに追加を続けられます。

## 管理者の設定

`/admin/integrations` に「指定してよいステージの接頭辞」を追加しています。
カンマか空白で区切り、例として `devlab-` を指定します。設定変更は監査に残ります。
管理 API の作成・変更の項目名は `allowedStagePrefixes`、DB の列名は `allowed_stage_prefixes`。
最大100個、各1〜100文字の小文字英数字とハイフン (先頭は英数字) です。空文字の接頭辞は許しません。
既存クライアントは初期値が空なので、管理者が許可するまではステージを指定できません。
接頭辞の変更は今後の PUT を制限し、既存設定を自動では削除しません。
ステージ管理の割り当て一覧では、グループから作った行にグループ名を表示します。

## エラーと回数の制限

エラーの本文は `{"error":"説明"}`。HTTPステータスで扱いを分けてください。
認証・scope・入力の順で検査するため、不正な入力でも未認証なら401です。
認証・権限の判定の前に入力を解析しません。

| HTTP | 意味 |
| --- | --- |
| 400 | キーや名前などの入力が不正 |
| 401 | Bearer が無い、不正、停止済み。すべて `Unauthorized` |
| 403 | 必要な scope が無い (`Forbidden`) |
| 404 | 対象が見つからない、または自分のグループ・メンバーの範囲外 |
| 429 | 呼び出しが多すぎる。少なくとも1分待って再試行 |
| 500 | 内部エラー。時間を空けて再試行 |

クライアントごとに約120回/分を上限にします。認証後、scope の確認前に制限します。
Cloudflare のレート制限バインディングを使うため、厳密な全拠点合算の課金上限ではありません。
既存 API と同じく、バインディング未設定のローカル環境・制限サービスの障害時には制限を通します。
認証済みの呼び出しはクライアント ID・操作・対象グループ・応答ステータスを監査に記録します。
書き込みでは対象件数・成功件数も記録します。本文・トークン・メールアドレスの一覧を監査に含めません。

## 開発時の境界

後続のルートは `authenticateIntegration` → `requireScope` → `requireOwnGroup` /
`requireOwnGroupMember` を使用し、`errorResponse` でエラーを返してください。
共通部品は `apps/api/src/lib/integrations.ts` にあります。
グループを解決したルートは `c.set("integrationGroupId", group.id)` で監査の対象を指定します。
自分のグループでないキー、グループにいない profile ID は、存在を明かさず404にします。
`PUT` は自分の所有範囲での upsert なので、ほかのクライアントのキーと同じ綴りでも自分のグループを作ります。

staff のユーザー管理・成績台帳・割り当て一覧は `groupId` クエリで絞り込みます。
選択肢は `GET /api/admin/integration-groups` (staff のみ)。
グループでの絞り込みは既存の権限や受講者だけの集計条件に追加します。
クライアント管理の `/api/admin/integrations` とその配下は 管理者のみが利用できます。

## 判断したこと (PR 記載用)

- グループは連携クライアントが API で作る。クライアントを持たない管理者作成グループは追加しない。
- 受講者の削除時はメンバー行を外部キーの CASCADE で削除する。次の取得で人数・メンバーに反映する。
- トークンに有効期限を設けず、停止・再発行で無効にする。最後の利用日時を画面に表示する。
- 割り当て一覧のグループ絞り込み中は、全員向けの「案内の内容」の編集を止め、絞り込みの解除を案内する。既存の一括更新がグループ外にも及ぶ誤解を防ぐため。
- #205・#206 の境界確認に使えるよう、この issue に冪等なグループ作成・更新の1ルートを含める。

## 判断したこと (#205、PR 記載用)

- 既存の受講者の追加時に別の同意・通知は求めない。ホームに出る案内を知らせとし、表示名は変更しない。
- グループから外した人の割り当ては未着手だけ削除し、開始済みは残して案内を消す。
- 連携 API は受講者のアカウントを削除できない。削除は引き続き管理者のユーザー管理で行う。
- 手動・別グループの割り当てが先にある場合は保護する。現在の人×ステージの一意制約を維持し、複数元の案内を合成する仕組みは追加しない。
- 手動の staff 免除と区別して安全に削除するため、割り当てに加え `stage_unlocks` にも `source_group_id` を追加する。
- 日付だけの期限は、管理画面と同じ日本時間のその日の 23:59:59 とする。別の時刻を指定したい場合はタイムゾーン付き日時を送る。

## ブラウザでの確認

ローカル D1 に0079まで適用し、API `http://127.0.0.1:8787` と Web `http://localhost:5173` を起動します。

1. 管理者でログインし、`http://localhost:5173/admin/integrations` を開く。
2. 名前と `groups:write` を選んで作成する。トークンをコピーし、表示を閉じる。再読み込みで先頭部分だけになることを確認する。
3. コピーしたトークンで `/me` と `PUT /groups/sample:term-1` を呼び、「グループを見る」でキー・名前・人数を確認する。
4. scope を外して保存し、PUT が403になることを確認する。停止で `/me` が401、復帰で200になることを確認する。
5. トークンを再発行し、古いトークンで401、新しいトークンで200になることを確認する。
6. `/admin/users`・`/gradebook`・`/stages` の星から開く割り当て一覧でグループを選ぶ。空グループでは一覧が空になる。
7. `admin` で `/admin/integrations` を直接開き、権限エラーになることを確認する。
8. `/admin/audit` で作成・変更・再発行・API 呼び出しを確認する。

9. 接頭辞 `sample-` を保存し、トークンの `members:write`・`stages:write` を有効にする。上記のメンバー追加を架空のアドレスで行い、再送が `already_member` になることを確認する。
10. 実在する granted ステージに合う接頭辞を保存し、その slug・期限・案内・免除を PUT する。ステージ管理の割り当てにグループ名が出ることと、対象者のホームに案内が出ることを確認する。
11. 設定から外したときとメンバー削除時に、未着手は割り当てが消え、開始済みは進捗が残ることを確認する。

自動テストは架空の情報だけを使い、再送・権限・既存名の保護・手動割り当ての保護・削除・batch のロールバック・100人時のバインド上限を検証します。

## 進み具合を読む (#206)

`GET /api/integrations/v1/groups/{key}/progress` (`progress:read`)。
グループの現在のメンバー (student) と、`integration_group_stages` に設定したステージだけを返します。
グループの設定は、実際の割り当ての所有元が手動・別グループでも読み取り対象です。
`stage=<slug>` で1ステージに絞れます。未設定の slug は空の `stages` になります。
人は STELLA ID 順、1回200人。`hasMore: true` の間、`next` をそのまま `cursor` に渡してください。
ページの途中で `stage`・`at` を変える場合は cursor を外して先頭から読み直します。

```json
{
  "members": [{
    "id": "sample-profile", "externalId": "applicant-001",
    "email": "applicant@example.test", "displayName": "応募者の例",
    "lastActiveDate": "2026-11-16",
    "stages": [{
      "slug": "devlab-ts-ch01", "status": "started",
      "startedAt": "2026-11-01T00:00:00.000Z", "clearedAt": null,
      "progressUrl": "/task-manual-completion?userId=sample-profile&stageId=sample-stage",
      "units": [{ "id": "sample-unit", "title": "はじめの単元", "tasks": [{
        "id": "sample-task", "title": "事前課題",
        "status": "passed", "pendingReview": false,
        "passed": true, "passedAt": "2026-11-16T00:00:00.000Z", "source": "tests",
        "submissionUrl": "/submissions/sample-submission",
        "problems": { "total": 10, "passed": 10, "sources": ["tests"] }
      }] }]
    }]
  }],
  "next": null, "hasMore": false
}
```

- `id` は STELLA のプロフィール ID。`externalId` はメンバー追加時の外部 ID (未設定は null)。
- `lastActiveDate` は既存のつまずき検知と同じ日本時間の日付です。視聴・完了、手元の確認、本人の提出、復習、受講開始のうち最後の日を返し、記録がなければ null。手動合格は本人の活動に含めません。視聴の元記録が日単位なので、正確な時刻を作って返すことはしません。
- ステージの `status` は受講登録なしなら `assigned`、開始済みなら `started`、修了日時ありなら `cleared`。日時は UTC ISO 形式、未到達は null。
- `units` は課題を持つ単元、`tasks` は有効な通常課題です。予備の類題・無効な課題は含みません。
- 課題の `status` は現在の `task_progress.status` (記録なしは `not-started`)。`passed` は `passed` / `ai-passed` の確定合格です。手元のテスト合格 (`local-passed`) だけでは確定合格になりません。
- `pendingReview` は `instructor-pending` (人の確認待ち) かどうか。
- `source` は合格した提出の `review_source`: `tests` / `ai` / `human` / `manual`。未合格・出所未記録は null。複数の合格がある場合は最後の試行の出所です。
- 問題つきの課題だけ `problems` が付きます。分母は現在の定義の問題数。合格済みの課題は版が変わっても合格を保ち、未合格なら今の版の問題だけを数えます。削除済みの問題は数えません。`sources` は数えた問題の `task_problem_results.source` (`tests` / `manual`) の重複なしの一覧です。既存の手で済み画面と同じ `readTaskDefinition` / `countedProblemIds` を使います。
- `progressUrl` は受講者×ステージの成績確認画面、`submissionUrl` は合格した提出の詳細。STELLA の Web の origin に対する相対 URL で、閲覧には管理者のログインが必要です。

### 締切の時点の数 (`at`)

`at=2026-11-16T00:00:00Z` のように、タイムゾーンと秒を含む ISO 日時を指定します。
オフセットの `+` は URL エンコードしてください。指定時刻と同じ日時の記録も数えます。
完全な過去の画面や名簿・教材の版を復元する API ではありません。

| 項目 | `at` 指定時 |
| --- | --- |
| 人・外部 ID・名前・メール、設定ステージ、単元・課題の題、問題の分母 | 現在の設定・教材を返す |
| ステージの開始・修了日時と状態 | `at` 以下の開始・修了・取り消し・割当解除の履歴から、開始と修了それぞれで `seq` が最後のものを使う |
| 課題の `passed`・`passedAt`・出所・提出 URL | 提出ごとに `at` 以下の `task_passed` / `task_pass_revoked` の最新1件で判定。合格が1つでも残れば合格 |
| 問題の合格数・出所 | `at` 以下の `problem_passed` / `problem_pass_revoked` から、問題 ID・版ごとに最新の判定を取得し、合格のものだけ数える |
| 課題の `status`・`pendingReview`、人の `lastActiveDate` | **項目自体を省略**する |

ステージは現在の `enrollments.enrolled_at` / `completed_at` では判定しません。
開始は `stage_started` / `stage_unassigned`、修了は `stage_cleared` / `stage_clear_revoked` / `stage_unassigned` のうち、
それぞれ `occurredAt <= at` で保存番号 `seq` が最後の出来事を使います。
最後が開始・修了の出来事ならその日時を返し、取り消し・解除、または記録なしなら該当の日時は null です。
自動修了を締切後に取り消し・再修了しても、締切時点では最初の修了日時が残ります。
割当解除は開始と修了の両方を取り消します。再開した場合、以前の修了は新しい修了の出来事があるまで引き継ぎません。
`at` なしでは従来どおり現在の受講行を使います。修了取り消し・割当解除の日時は DB の時刻 (ミリ秒) です。

課題の合否は、提出の現在の `verdict` や `task_progress.passed_at` では絞りません。
提出ごとの最新が `task_pass_revoked` なら、その提出だけを合格から外します。別の提出の合格が残れば課題は合格です。
出所と提出 URL は残る合格の試行番号の降順、同じ番号なら提出 ID の昇順で選びます (`at` なしと同じ)。
合格日時は残っている合格のうち最初の日時です。同じ提出の合格を再確認しても初回日を保ち、取り消し後の再合格は新しい合格日から数えます。合格が1つも残らない、または対象の出来事が無ければ未合格で、日時・出所は null、提出 URL は省略します。
締切後に AI 合格を人が覆しても、締切時点の合格を保ちます。同時刻の出来事は索引への追記順で最後のものを使います。
問題の出所が締切後に `manual` から `tests` に変わっても、締切時点では `manual` として数えます。
未合格の課題は現在の版の問題だけ、確定合格した課題は旧版の合格も保持する、既存の数え方を使います。

手で済みの取り消しなどで提出・問題の結果が削除されても、削除時刻を合格の取り消しとして記録します。
削除前の `at` では合格を保ち、削除以後の `at` ではその提出・問題を数えません。
問題の結果の削除は、その問題について記録した各版の合格を取り消します。
判定変更の取り消しは新しいレビュー日時、削除の取り消しは DB の削除時刻 (ミリ秒) を使います。判定なしに戻してレビュー日時も無くなった場合は DB の時刻を使います。
導入前に上書き・削除された版・レビューも復元できません。
0080導入時に残る記録のうち、いずれかの連携グループに所属する人の分だけ、その保存日時で索引に移します。
以後の索引への記録も所属中だけです。参加前の記録は後から補わないため、`at` で索引を使う項目 (ステージの開始・修了、課題の合否・日時・出所・提出 URL、問題の合格数・出所) は参加前の履歴を復元できません。
締切の厳密な名簿・教材・確認待ちの状態が必要なアプリは、日ごとに応答を自分で控えてください。

## できごとを読む (#206)

`GET /api/integrations/v1/groups/{key}/events` (`events:read`)。
応答は `{"events":[...],"next":"不透明な位置","hasMore":false}`。
初回は `after` を省略し、2回目以降は受信した `next` を `after` にそのまま渡します。
1回500件まで、保存された順に返します。起きた日時 (`occurredAt`) の順とは、わずかに前後することがあります。
空のページでは渡された位置を保ちます。初回から空なら `next` は null。
`hasMore: false` でも後日、新しい出来事を同じ位置から取得できます。

各要素は `id`、`type`、`occurredAt` (UTC ISO)、`person: { id, externalId }`、
`stage` (slug)、課題があれば `taskId` を持ちます。

| type | 追加項目・意味 |
| --- | --- |
| `stage_started` | 受講開始 |
| `stage_cleared` | 修了 |
| `stage_clear_revoked` | 修了の取り消し。開始は残る |
| `stage_unassigned` | 受講の行の削除 (割当解除)。開始・修了の両方を取り消す |
| `task_passed` | `source`: 合格の出所 (未記録は null)、`submissionUrl` |
| `task_returned` | 合格していない提出への出し直し (`verdict=resubmit`)、`submissionUrl` |
| `task_pass_revoked` | その提出の合格の取り消し。`reason`: `resubmit` / `fail` / `removed`、`submissionUrl` |
| `problems_passed` | `count`: そのまとまりで合格した問題数、`problemsPassed`: その課題の今の合格数 |
| `problems_revoked` | `count`: そのまとまりで合格を取り消した問題数 (同じ問題の複数の版は1問)、`problemsPassed`: その課題の今の合格数 |

修了済みの受講の行を削除したときも、`stage_unassigned` の1件だけを返し、`stage_clear_revoked` を重ねて返しません。

`pass → resubmit` の訂正は `task_pass_revoked` (`reason: resubmit`) の1件にまとめ、同じ操作の `task_returned` は返しません。
`pass → fail` は `reason: fail`、判定なしへの変更・合格した提出の削除は `reason: removed` です。
削除された提出の URL は閲覧時に404になる場合があります。理由の本文は返しません。

問題の合格と取り消しはそれぞれ別に、位置より後に保存された分だけを、人×課題×出来事の時刻が同じで、保存順に連続する範囲ごとにまとめます。
前の応答に含まれた問題は次の集約に含めません。同じ課題・同じ日時でも、別のできごとが間に保存された場合は別のまとまりです。
まとまりの位置は、その中の最後の保存番号です。ID にもその範囲の番号を含め、別のまとまりと区別します。
位置は保存順に増える番号 (`seq`) を使うバージョン付きの不透明な文字列で、グループに結び付きます。
番号は行が削除されても使い回しません。起きた日時が前の出来事が後から保存されても、次の取得で読めます。
旧形式の日時を含む位置は使えません。形式変更後は `after` を省略して先頭から取得してください。
デコード・編集・別グループへの流用をせず、そのまま保存してください。不正な位置は400です。
同じ位置からの再取得は同じ順序と ID を返すので、受信側は `id` で重複を除けます。
`problemsPassed` は取得時点の数なので後の合格・取り消しで変わります。
メンバーの外部 ID とグループへの所属・ステージ設定も取得時点のものです。
新しい出来事が届けば末尾に増えます。削除された人・ステージの出来事は返しません。
過去の日時に訂正した記録も、新しく保存した分は保存順で続きに含まれます。

出来事索引は0080で導入します。導入時に残る開始・修了・レビュー・問題の合格のうち、
いずれかの連携グループに所属する人の分だけを取り込みます。グループが無ければ取り込みは0件です。
以後も、出来事が記録される時点でいずれかの連携グループに所属する人だけ、元行の変更と同じトランザクションのトリガーで追記します。
`PUT /groups/{key}/members` で人を追加するときに、参加前のできごとをさかのぼって書く処理は行いません。
どの連携グループにも所属していなかった期間のできごとは `events` に出ません。現在の状態は `progress` で読んでください。
別の連携グループへの所属中に記録済みのできごとは、現在の所属・ステージ設定の範囲で読めます。
元のレビューや問題の合格が上書きされても、既に出した出来事の ID と日時は維持します。
導入前に削除・上書きされた出来事は復元しません。

## 読み取りで返さないもの

提出コード、ファイルのパスや内容、レビュー本文、AI の所見、チャット、手で済みにした理由、
学んだ時間 (`study_activity` の量) は返しません。画面への URL だけを渡します。
自分の所有でないグループは404、scope がなければ403です。
応答はエラーも含め `Cache-Control: no-store`。サーバーにも応答キャッシュは持ちません。
#204 のクライアント単位の回数制限・呼び出しごとの監査をそのまま使います。

## 判断したこと (#206、PR 記載用)

- 学んだ時間は返さない。受講者に知らせる方法を決めてから、別の `activity:read` scope で足す。
- `at` は記録の日時から判定できる項目だけ。確認待ちなどの復元できない項目は省略し、外部アプリ側で日ごとに控える。
- キャッシュは持たず `no-store` とし、#204 のクライアント単位の制限で読み取り回数を抑える。
- 上書きされる元行から位置を毎回作り直すと再取得が不安定になるため、本文を持たない出来事索引とトリガーを追加する。
- 最後の活動の元記録に日別の記録が含まれるため、架空の時刻を付けず、既存の判定と同じ日本時間の `lastActiveDate` を返す。
- 連携に関係のない受講者の書き込みを増やさないため、出来事の記録・導入時の取り込みは連携グループの所属者だけにする。後からのメンバー追加では過去分を補わず、現在の状態は `progress` で読む。
