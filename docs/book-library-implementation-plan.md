# STELLA 本棚とPDF読み上げの実装計画

作成日 2026年10月11日  
状態 P1と処理基盤の実装済み範囲と後続計画（12章）  
[統合設計](book-library-design.md)

book-narratorの処理をSTELLAへ移植し、個人のPDFを登録してスマホで聴き、PCで関連演習に進む流れを完成させる。実装は登録から利用までを通す順で分割し、移植した処理の回帰テストとSTELLAの認可をそれぞれ確認する。既存book-narratorからは処理コードだけを移植する。ユーザーの指定により既存DB・R2・利用者・書籍データは移管せず、STELLAで新しく登録する。

## 1 到達点と順序

初期版の完成条件は、個人書籍と公開可能な社内教材で本棚・PDF処理・再生・個人の記録・LXP導線が使えることとする。初期版の機能を揃える実装と段階公開を分けて検証する。

| 段階 | レビュー単位 | 依存 | 到達点 |
| --- | --- | --- | --- |
| P0 | 移植元の固定と実行基盤の確認 | なし | 再利用するソース、実行依存、テスト構成が確定する |
| P1 | 書籍データと認可 | P0 | 本人とテナントを守る本棚APIが使える |
| P2 | PDF登録と書籍処理 | P1 | PDFが章本文と図版になり、再実行できる |
| P3 | 音声生成と認証付き配信 | P2 | 長い章を安全に生成・シーク・再開できる |
| P4 | リーダーと個人の記録 | P3 | STELLA内で読み聴きし、メモ・しおり・位置を保持できる |
| P5 | LXPと今日のプラン | P4 | 書籍の章と既存レッスンを往復できる |
| P6 | 社内教材と運用 | P5 | 共有教材、利用上限、清掃、運用画面が使える |
| P7 | 段階公開 | P6 | 新規登録で試用し、対象テナントへ公開する |

P2までは読む経路、P3で聴く経路、P5でLXPの往復が揃う。各段階は一つの巨大PRにせず、表に示すレビュー単位を必要に応じて分割する。フェーズの一部が先に公開されても、権限・削除・生成上限が未完成のAPIを通常利用者へ公開しない。

## 2 P0 移植元と実行基盤を確定する

実装前にbook-narratorのソースcommitと依存lockfileを記録し、移植する関数・処理・テストの対応表を作る。単体アプリをSTELLAから直接importしたり、隣接リポジトリへの絶対パスに依存する実装にはしない。

| 作業 | 主な変更先 | 完了条件 |
| --- | --- | --- |
| 既存の型検査・テスト・ビルドを実行 | book-narratorの既存スクリプト | 成功または既存の失敗を記録し、統合による失敗と区別できる |
| 処理コードの移植と入口分離 | `packages/book-core` | 章分割、OCR整形、読み上げ文、PDF、MP3の処理を個別に利用できる |
| Workerと内部RPCの足場 | `apps/narrator`、APIのEnv型 | 偽プロバイダでAPIから処理Workerへ接続できる |
| ローカルD1と非公開R2の共有 | API・処理Workerのローカル設定 | 両Workerが同じローカル資源を使い、別のDBを誤って作らない |
| 認証付きメディアの実証 | 検証用APIと短いサンプルMP3 | チケット、Range、シーク、期限後の再開がPC・スマホで成立する。正式テーブルはP1以降で実装 |
| 依存とテスト環境の整理 | Bun lockfile、workspaceの設定 | WebへWorker専用WASMが入らず、各workspaceを型検査できる |

現在STELLAのVitestは5系、book-narratorは4系とWorkers向けpoolを使っている。設定を単純に合体しない。Workers用テストは`apps/narrator/test`と専用configへ置き、対応するpeerDependenciesを確認して実行する。通常のNodeテストは既存のroot configを使い、rootの`test`から両方を必ず呼ぶ。

rootの`build`は現在WebとVS Codeを明示しているため、処理Workerのビルド検証を追加する。`typecheck`の対象からテストやscriptsを除外せず、新workspaceにもtypecheckスクリプトを用意する。移植元の非null assertion、コンソール出力、引用符・整形はSTELLAのBiome規則に合わせる。

最初の確認ではダミーの自社著作物を使い、実際の書籍を外部OCR・TTSへ送らない。処理Workerの公開HTTPは書籍操作を受け付けず、Service bindingの固定メソッドだけでジョブを扱う。

## 3 P1 書籍データ 本棚 認可

レビュー単位は「マイグレーションと認可」「本棚APIと入口」に分ける。

- `apps/api/src/db/schema.ts`と`apps/api/drizzle`に、書籍、PDF、章、音声、個人本棚、読者状態、メモ、ジョブの基礎テーブルを追加する。
- `packages/shared/src/library`に入力・応答の型、状態、上限、エラーの契約を追加する。
- `apps/api/src/lib/library-authz.ts`で本人、同じテナント、書籍の公開状態、プロフィールの無効化を評価する。
- `apps/api/src/routes/library*.ts`にcapabilities、本棚、書籍メタ情報のAPIを追加する。
- STELLAサイドバーに本棚を追加し、機能無効時・未設定時・空の本棚・通信失敗の表示を用意する。

書籍の所有者とテナントは`getCaller`で決定する。request bodyのowner ID、tenant ID、roleによって送り先や権限を変えさせない。個人本棚に追加しただけで共有書籍の原本編集権限が生まれないことも検証する。

完了条件は、同じテナントの別人、別テナント、講師、管理者、無効化利用者を含むAPIテストで私有書籍が漏れないこと。マイグレーションは既存STELLA DBに追加適用し、既存の受講・提出・教材seedに影響しないことを確認する。

## 4 P2 PDF登録 OCR 章分割

レビュー単位は「アップロード」「書籍Workflow」「処理画面と再実行」に分ける。

- 既存のPDF確認・自動分割Web Workerを移植し、タイトルの初期値、複数原本の順序、送信進捗を画面に表示する。著者が不明な資料も扱えるよう、既存の著者必須入力は見直す。
- `library-api.ts`にバイナリPUTの入口を追加し、部分送信、完了、上限・PDF検証をAPIへ移植する。
- ジョブと起動待ちを同じDB batchで保存し、内部RPCと定期的な再送でWorkflowsを起動する。
- BookWorkflow、OCRプロバイダ、図版切り出し、章分割、失敗理由、途中成果の利用を移植する。
- 処理状態、失敗工程、再実行、準備完了を本の詳細・本棚に表示する。初期版はポーリングし、ブラウザを閉じても処理が続く。
- 未完了uploadと一時ファイルの清掃を実装し、削除状態の書籍へ処理が書き戻せないことを確認する。

完了条件は、複数PDFが連続したページ範囲と章になり、図版・元PDFを本人だけが参照できること。上限超過、不正PDF、暗号化PDF、送信中断、OCRの途中失敗、起動RPCの失敗と重複再送を含むケースを通す。再実行で済んだOCR範囲を不必要に課金し直さないことも、偽プロバイダの呼出履歴で確認する。

## 5 P3 音声生成 配信 位置保存

レビュー単位は「TTS処理と生成上限」「メディア認証とRange配信」「位置保存」に分ける。

- AudioWorkflow、読み上げ文抽出、分割、MP3変換・連結、利用量記録を移植する。選択章の生成を既定にし、全章生成も選べるようにする。
- 章・利用者・テナントの同時処理枠と予算枠をDBで予約し、重複クリック・別タブによる二重生成を防ぐ。
- 生成中の本文修正と再生成が競合しないよう、入力改訂、処理世代、条件付き更新を導入する。
- `library_media_sessions`と配信APIを追加し、JWTをURLに入れず、短期チケットで音声とPDFを取得する。
- Range・HEADの配信とCORSを追加し、チケット更新、シーク、ダウンロード、失効を検証する。
- 本文位置と音声位置を別に保存し、再生終了、別端末からの再開、古い送信の再試行を扱う。

完了条件は、章の音声生成、途中位置からの再生、Range取得、速度変更、チケット期限後の再開が成立すること。共有解除・利用者無効化・原本削除後に新しいメディア要求を通さないことも必須とする。

音声品質は自社著作物の代表章で実測する。日本語、専門用語、縦書きOCRの結果、分割箇所の接続、図表・コードの省略を確認する。単体テストが通ったことだけでプロバイダ品質を合格にしない。

## 6 P4 リーダー しおり メモ

レビュー単位は「本棚・章画面」「共通プレイヤー」「個人記録と編集」に分ける。

- `components/library`とTanStack Routerのルートに、本棚、書籍詳細、章リーダー、OCR編集を追加する。
- `AppShell`に再生状態を持つProviderと共通プレイヤーを置き、ページ移動で再生を破棄しない。
- 動画・面談音声との同時再生を調停し、ログアウトで再生と利用者別キャッシュを消す。
- 認証付き図版、原本ページへの移動、音声省略箇所の表示を追加する。
- しおり、メモ、個人タグ、読書状態、端末間の位置復元を実装する。
- 本文修正・章分割・結合で改訂を記録し、参照が変わったメモと関連付けを通知する。
- 原本・Markdown・MP3の出力を移植する。一冊ZIPには上限を設ける。

完了条件は、PCで登録した書籍をスマホで再開し、戻ったPCでメモと位置が見えること。本文修正後の古い音声を現行と誤表示せず、章の作り直しで個人のメモを失わないこと。スマホの操作、キーボード、フォーカス、長いタイトル、表、図版を実画面で確認する。

正確な段落と音声の同期はこの段階に含めない。元ページと章の位置が分かることを初期版の基準にする。

## 7 P5 LXP 今日のプラン 学習記録

レビュー単位は「関連付けAPIと画面」「今日のプラン」「読書ログ」に分ける。

- 個人の章と、閲覧可能なステージ・レッスンを手動で関連付けるAPIを実装する。
- 章画面から関連レッスンへ進み、レッスン画面から読む章・ページへ戻る。書籍が存在しない、非公開になった、参照改訂が変わった場合も表示を定義する。
- `today-plan.ts`と`TodayPlan.tsx`に書籍の参照、item ID、本人の選択を追加する。既存の期限のある復習を維持し、30分・3項目を超える場合を扱う。
- 冪等な再生イベントを別テーブルで記録し、本人のホームに聴書履歴を表示する。シークを学習時間に加算しない。
- 章から既存演習への導線は、既存の「VS Codeで開く」に接続する。Webに新しいコード演習環境を作らない。

完了条件は、章を聴く、参考レッスンを開く、VS Codeの演習を行う、書籍へ戻る流れが成立すること。スキルツリーの霧・未割当の専用教材が関連候補やレスポンスから漏れないこと。読書・再生でレッスン完了、XP、クリア、修了証が増えないことも回帰テストで確認する。

## 8 P6 社内教材と運用

レビュー単位は「社内公開と公式リンク」「利用量・停止」「清掃・障害回復」に分ける。

- 同じテナントの承認済み自社著作物を本棚へ追加できるカタログと、公開担当者の公開・取り下げ操作を実装する。
- 社内教材の公式リンクと個人リンクを区別し、カタログを使ってもメモ・読書状態は各自で保持する。
- 市販書籍の共有停止をテナント設定で維持する。限定共有はプロフィールIDを使う後続機能として残す。
- 管理者に処理状態、利用量、概算費用、予約枠、失敗、停止・再試行の運用画面を提供する。個人本文・メモの閲覧権限は付与しない。
- 削除待ち、停止できなかったジョブ、期限切れupload、一時音声、失効チケットを清掃する。
- 外部エラーの表示と監査ログを整え、本文・メモ・チケットがログへ入らないことを確認する。

完了条件は、同じ社内教材を二人が自分の本棚へ追加し、異なる位置とメモを持てること。公開取り下げや削除後に新しい取得を拒否し、処理中削除でも原本・音声が再公開されないこと。本文を見ずに運用担当者が失敗工程と利用量を確認できること。

## 9 P7 段階公開

既存book-narratorのデータ移管は実施しない。所有者の対応付け、旧DBの取り込み、R2コピー、移行元の停止はこの計画の対象外とする。

自社著作物を新規登録してstagingで検証し、少数の利用者から対象テナントへ段階公開する。P2・P3で利用枠と外部送信の条件を実装してから、処理フラグを有効化する。

切り戻しは本棚・新規処理のフラグを無効化する。追加テーブルや原本を削除して戻さず、新規登録された書籍と個人の記録を保全する。WorkerのコードだけではDB・R2・進行中Workflowは戻らないため、加算マイグレーションと互換性のあるRPC契約を維持する。
## 10 検証とCIへの組み込み

| 検証 | 主なケース | 実行場所 |
| --- | --- | --- |
| 単体 | 章分割、読み上げ対象、ハッシュ、リンクの可視性、プランの上限、再生イベントの重複 | root Vitest |
| API認可 | 本人・別人・別テナント・全ロール・無効化、検索・図版・ダウンロード・メディアの拒否 | Hono route harness |
| DBと処理 | 既存DBへの追加適用、複合制約、Workflowの再実行、起動待ち、削除中・改訂中の生成 | Workers用VitestとD1実適用 |
| HTTPスモーク | JWT、PDF送信、偽OCR/TTS、章、音声Range、位置、メモ、関連リンク、削除、清掃 | ローカルAPIと処理Worker |
| ブラウザ | 本棚、登録、読書状態、しおり、メモ、ミニプレイヤー、ページ移動、LXPへの往復 | PCの実画面と主要導線のE2E |
| 実機と実API | 長い音声、画面ロック、Media Session、原本表示、チケット更新、OCR品質・TTS品質 | stagingとiOS Safari・Android Chrome |

既存の`.github/workflows/ci.yml`を検証ゲートの正本とし、`verify`と`core-loop`の名前を変えない。`verify`にWorker専用テストとビルド検証を追加する。`core-loop`には同じローカル環境で書籍スモークも実行する手順を追加し、既存のstage作成から修了までのスモークを維持する。deploy側へ検証手順を書き写さない。

追加するコマンドは`test:narrator`、`smoke:library`、処理Workerのビルド・ローカル起動とし、rootの既存コマンドから実行漏れがないようにする。P0・P1の処理検証は `test:narrator` で実Worker・D1・R2・JWTを組み合わせて実行する。`smoke:library` はP2以降に追加する。

Cloudflareの資源とCIの接続先はstagingとproductionで分ける。デプロイはGitHub Actionsで、加算DB migration、処理Worker、STELLA API、Webの順に更新する。既存の教材画像・PDF同期・seedの変更判定を維持し、書籍アップロードをGit教材の配信経路へ混ぜない。

処理用プロバイダの秘密値は処理Workerへ置く。偽プロバイダで通常CIを動かし、本物のOCR・TTSの確認は承認済みのサンプルによるstaging検証で行う。APIや処理Workerのbinding未設定時は書籍機能だけを利用不可にし、通常のSTELLA APIとログインを継続できるようにする。

## 11 公開の判定

| 判定項目 | 合格条件 |
| --- | --- |
| 個人の情報 | API、検索、本文、メディア、ログ、管理画面から他人・他テナントの私有情報が漏れない |
| 読書の継続 | PC登録、スマホ再生、PCでメモ確認・演習の往復が成立する |
| 障害からの回復 | 送信・OCR・TTS・RPCの失敗を再試行でき、二重登録・二重生成・位置の巻き戻りを抑えられる |
| 内容と音声 | 本文と音声の改訂が一致し、古い音声や変わった参照箇所を明示できる |
| 削除と費用 | 削除後に処理が再公開せず、予約上限で新規生成を止め、利用量を追える |
| LXP評価 | 読書履歴と演習・確認結果を分け、霧・専用教材の既存制御を維持する |
| 既存機能 | typecheck、Node・Workersテスト、lint、教材検査、build、既存core-loopが通る |
| 運用条件 | 外部送信、共有、保管、プロバイダ、利用枠の適用条件が明確である |

工数はP0の処理移植と認証付きメディアの実証後に見積もる。実装の量だけでなく、長いPDFの実測、スマホのバックグラウンド再生、処理対象のページ数が期間を左右するため、この段階では確定日を置かない。最初の着手単位はP0とP1とし、その完了時にP2以降の見積もりと公開範囲を更新する。

## 12 実装状況

P1として、`library_books` と `library_shelf_entries` の加算スキーマ（0062）、本人の本棚API・画面、JWT・テナント・ロール・無効化利用者の認可テストを実装した。

P2の土台として、処理Worker（`apps/narrator`）、`packages/book-core`、PDF・ページ・図版・章・音声・ジョブのテーブル（0063）、削除後のR2清掃、非公開R2の確認とデプロイ手順を追加した。`library_books` には0063で処理状態（`status`）、削除世代（`generation`）、ページ数、章計画の列を足す。OCR・図版・章分割・TTSは偽プロバイダで検証した。P2では、原本の登録・送信・削除（P2-a）と、処理の予約・起動・状態・再実行（P2-b）のAPIを追加した。書籍の画面 `/library/$bookId`（P2-c）で、PDFの確認・自動分割・送信、処理の開始と状態の表示、再実行、章の一覧（題名とページ範囲）まで使える。図版・元PDFの参照はP3、章本文を読む画面はP4。OCRの前に、利用者とテナントの月間ページ上限（既定2000・20000ページ、JSTの暦月）に対して読み取るページを予約し、超えたら理由を示して処理を止める（`library_ocr_reservations`、migration 0065）。本番の処理Workerは `LIBRARY_PROCESSING_ENABLED=1` とし、narratorのsecret `GEMINI_API_KEY` を設定した時点から処理できる。止めるときはフラグを`0`に戻す（登録済みの書籍と記録は残る）。

メモ・しおり・再開位置のテーブル（`library_annotations`・`library_reader_states`）はP4、公開範囲の列（`visibility`・`publication_status`）はP6で追加する。メディアチケット・Rangeの検証はテスト専用APIだけで、スマホ実機・長い音声・本物のプロバイダ品質は未検証である。

[開発・検証・デプロイ手順](book-library-development.md)を参照。
