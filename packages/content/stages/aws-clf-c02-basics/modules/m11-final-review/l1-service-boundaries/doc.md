# レッスン11-1 まぎらわしいサービスの切り分け

## このレッスンの目標

- [ ] 記録・ストレージ・セキュリティ・サインイン・移行の5組を、設問のキーワードから1つに決められる
- [ ] 誤答の選択肢がどんな形で作られるかを言葉にできる
- [ ] 模試で間違えた組を、この5枚の表に戻って確認できる

M10の模擬試験を解き終えたら、次にやるのは知らないサービスを増やすことではありません。**似ているサービスの境界をはっきりさせること**です。本番の設問は、まったく無関係な4択ではなく「どれも当てはまりそうな4択」で作られます。このレッスンでは、誤答が集中する5つの組を、それぞれ1つの軸で切り分けます。

## 11-1-1 記録の3つを動詞で分ける

> **CloudWatchは数値とログ、CloudTrailは操作の証跡、Configは設定の状態を記録する**

3つとも「あとから見返すために記録する」サービスです。違うのは記録する対象だけで、機能の優劣ではありません。

| 知りたいこと | 選ぶもの |
| --- | --- |
| CPU使用率が80%を超えたら知らせてほしい | CloudWatch |
| 先週このバケットを削除したのは誰か | CloudTrail |
| すべてのEC2に暗号化の設定が入っているか | Config |

設問のキーワードで反射できるようにしておきます。

- 「メトリクス」「アラーム」「しきい値」「ログの収集」→ CloudWatch
- 「誰が・いつ・どのAPIを」「監査」「証跡」→ CloudTrail
- 「設定が基準どおりか」「構成の変更履歴」→ Config

迷ったら **数値か・人の操作か・設定か** の3択に落としてください。3つは競合ではなく分担なので、実務では併用します。「CloudWatchのアラームで気づき、CloudTrailで誰の操作かを追い、Configで設定が基準から外れた時点を特定する」という流れが典型です。

## 11-1-2 ストレージは接続の形で選ぶ

> **ストレージは、置くだけならS3・1台に付けるならEBS・複数台で共有するならEFSと接続の形で選ぶ**

S3・EBS・EFSはどれもデータを保存できます。設問文の「保存したい」だけを読むと3つとも正解に見えるので、決め手は**どう繋いで使うか**に置きます。

| 設問の言い回し | 選ぶもの |
| --- | --- |
| 画像・ログ・バックアップを大量に置きたい | S3 |
| EC2のシステムディスクやDBのデータ領域が要る | EBS |
| 複数のEC2から同じファイルを同時に読み書きしたい | EFS |
| Windows向けのSMB共有フォルダーが要る | FSx |
| ほとんど読まないデータを最安で保管したい | S3 Glacier系のクラス |

最後の行だけはサービス名ではなくS3の中のストレージクラスの話です。「アーカイブ = S3の中で安いクラスを選ぶ」と覚えておくと、EBSやEFSに引っ張られません。

誤答の選択肢は、次の3つの形で作られます。言い切って否定できるようにしておいてください。

- 「S3をEC2にマウントして普通のフォルダーとして使う」→ S3はAPIで読み書きするオブジェクトストレージです
- 「EBSを複数のEC2で同時に共有する」→ 共有が要るならEFSです
- 「アーカイブ用に安いEBSを選ぶ」→ 長期保管はS3のGlacier系です

## 11-1-3 セキュリティサービスは動詞で分かれる

> **セキュリティサービスは、防ぐ・気づく・見つけるという動詞で持ち場が分かれる**

配点30%のドメイン2は、サービス名がいちばん多い領域です。名前を丸暗記しても5つ並んだ選択肢からは選べないので、動詞の軸を先に決めます。

| 動詞 | サービス | 持ち場 |
| --- | --- | --- |
| 防ぐ | WAF | Webアプリを狙う攻撃を入口で遮る |
| 防ぐ | Shield | DDoS攻撃から守る |
| 気づく | GuardDuty | 不審な振る舞いを継続的に検出する |
| 気づく | Inspector | EC2やコンテナイメージの脆弱性を診断する |
| 見つける | Macie | S3の中の個人情報を見つける |
| まとめる | Security Hub | 上の結果を1画面に集約する |

実際の設問は、2択まで絞れた後の判断で決まります。次のスラッシュの左右が、その2択です。

- 「Webアプリへの攻撃」→ WAF / 「大量のトラフィックで落とされる」→ Shield
- 「不審な通信・振る舞い」→ GuardDuty / 「既知の脆弱性・パッチ漏れ」→ Inspector
- 「S3に個人情報が紛れていないか」→ Macie
- 「複数の検出結果をまとめて見たい」→ Security Hub

Shieldには段階があります。一般的なDDoS攻撃からの保護は、すべての利用者に追加費用なしで自動的に適用されます(Shield Standard)。設問で「追加費用なし」「自動的に」とあればこの標準の層を指し、より大きな攻撃への対応や専門チームの支援が要る場合が上位の層(Shield Advanced)です。

## 11-1-4 ログインまわりは担当で分ける

> **ログインまわりは、権限を定義するIAM・従業員の入口のIdentity Center・アプリ利用者のCognitoで担当が違う**

「ログイン」と聞くとIAMを反射で選びたくなりますが、IAMで答えると間違いになる設問が存在します。

- **IAM Identity Center** — 従業員がAWSへサインインする入口をまとめる仕組みです(旧AWS SSO)。複数アカウントをまたぐ場合によく使われますが、アカウントが1つでも使えます
- **Cognito** — 自社が作ったアプリの、一般利用者向けのログイン機能です

| 見分けるもの | 仕組み |
| --- | --- |
| AWSを操作する権限を定義する | IAM(ユーザー・グループ・ロール・ポリシー) |
| 従業員がAWSへサインインする入口 | IAM Identity Center |
| 自社アプリの一般利用者が会員登録してログインする | Cognito |

いちばん太い線は「AWSを**操作する**側か、アプリを**使う**側か」です。設問に「従業員」「社内」とあればIAM系、「顧客」「アプリの利用者」とあればCognitoで切ります。操作する側の中では、権限を定義するのがIAM、サインインの入口を用意するのがIAM Identity Centerという分担になります。

分ける軸はアカウントの数ではない点に注意してください。**従業員のサインインは、アカウントが1つでもIAM Identity Center(または外部のIDプロバイダーとの連携)が現在の推奨**で、一時的な認証情報でサインインします。長期のアクセスキーを持つIAMユーザーは、それが避けられない例外的な用途に限るのがAWSの案内です。試験では、IAMは「AWSを操作する権限を定義する仕組み」として問われます。

認証と混ざりやすい隣人も、ここで持ち場を分けておきます。

- **Organizations** — 複数アカウントを束ねて請求とポリシーをまとめます。ログインの仕組みではありません
- **Control Tower** — 複数アカウント環境を、決まりごと付きで最初から敷きます

## 11-1-5 移し方は量と中身で決まる

> **データの移し方は、回線で送りきれない量ならSnow、データベースならDMS、回線越しの同期ならDataSyncを選ぶ**

移行の設問は「オンプレミスからAWSへ移したい」で始まる型が多く、Snow・DMS・DataSync・Storage Gatewayがまとめて選択肢に並びます。決め手は **量・中身・回線を使うかどうか** の3つです。

| 状況 | 選ぶもの |
| --- | --- |
| 数十TB以上あり、回線で送ると数か月かかる | Snowファミリー |
| 稼働中のデータベースを止めずに移したい | DMS |
| オンプレのファイルサーバーからS3やEFSへ回線で転送したい | DataSync |
| 移行後もオンプレからAWSのストレージを使い続けたい | Storage Gateway |

最後の行だけは「移す」ではなく「橋渡し」です。移すのは1回きりの作業、Storage Gatewayは移した後も使い続ける道具、と区別してください。

移行を支える2つも、消去法で迷わないために名前と一言だけ対応づけます。

- **Application Discovery Service** — 移行前にオンプレの資産を棚卸しする
- **Migration Hub** — 複数の移行の進捗を1画面で追う

「何を移すか決める前」がDiscovery、「移している最中の管理」がMigration Hubです。なお、8-1-4で学んだ **7R** は移行のやり方の分類であって、ここで扱った運ぶ道具とは別の話です。設問で混ざらないように分けておいてください。

## もっと知りたい人へ

- 5つの表は、M10の反射表と重ねて使えます。反射表で思い出せなかった行があれば、このレッスンの該当する表へ戻ってください
- 切り分けの軸(動詞・接続の形・ログインする人・量と中身)は、名前が変わっても残る考え方です。サービス名が増えても、この軸に当てはめて整理できます
