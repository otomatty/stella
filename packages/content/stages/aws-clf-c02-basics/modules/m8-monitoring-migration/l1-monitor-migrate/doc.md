# レッスン8-1 監視と移行

## このレッスンの目標

- [ ] CloudWatch・CloudTrail・Configを「どうなっているか/誰が何をしたか/どう変わったか」で区別できる
- [ ] CAFとWell-Architectedの使いどころの違いを言える
- [ ] 移行戦略の7Rと、データ移送の道具(Snow・DMS・DataSync)を選び分けられる

## 8-1-1 CloudWatchで測って知らせる

> **CloudWatchはメトリクスとログを集め、しきい値を超えたらアラームで知らせる**

動かし始めたシステムは「今どうなっているか」が見えないと運用できません。CPUが張り付いても、気づくのが利用者からの苦情では遅すぎます。

**CloudWatch** はAWSの計器盤です。3つの言葉をセットで覚えてください。

- **メトリクス** — CPU使用率などの数値の測定値
- **ログ** — 出来事の記録の文章(CloudWatch Logsが収集)
- **アラーム** — しきい値超えをきっかけに、通知や自動対応を出す仕組み

| 流れ | 例 |
| --- | --- |
| 測る | EC2のCPU使用率をメトリクスとして収集 |
| 判定 | 「5分間80%以上」のしきい値を超えた |
| 知らせる | アラームがSNSへ通知(担当者へメール) |
| 自動対応 | Auto Scalingに台数追加を指示もできる |

通知先にSNS(M6)、自動対応にAuto Scaling(M3)と、既習のサービスがここでつながります。試験では「モニタリング」という語が見えたらCloudWatchです。

## 8-1-2 CloudTrailは操作の記録

> **CloudTrailは「誰が・いつ・何を」操作したかというAPI呼び出しの証跡を記録する**

「誰がこのサーバーを消したのか」を後から調べたい日が来ます。監査でも「操作の記録を見せてください」と言われます。後から検証できる操作の記録を **証跡** と呼び、**CloudTrail** がそれを担います。

M2で学んだとおり、コンソールもCLIもSDKも裏はすべてAPI呼び出しです。だから、どの入口からの操作でも同じ「誰が・いつ・何を」の形で記録されます。ただし範囲には注意してください。既定で記録されるのは**管理イベント**(リソースの作成・変更・削除などの管理API操作)です。S3オブジェクトの読み書きやLambdaの呼び出しといったデータイベントは既定では記録されず、対象を指定して追加で有効化します。

| 記録される内容 | 例 |
| --- | --- |
| 誰が | IAMユーザー suzuki |
| いつ | 2026-08-27 14:03 |
| 何を | EC2インスタンスの削除を実行 |

もう1つ、**Config** をここで覚えます。リソースの設定の変遷を記録し、ルールに照らして評価するサービスです。3つの記録係は疑問文で区別します。

- CloudWatch = 数値と状態(**どうなっているか**)
- CloudTrail = 操作の証跡(**誰が何をしたか**)
- Config = 設定の変遷(**構成がどう変わってきたか**)

この3択の区別は、ドメイン2の定番出題です。

## 8-1-3 CAFは移行準備の枠組み

> **クラウド導入フレームワーク(CAF)は、組織の移行準備を6つの視点で点検する枠組み**

既存システムのクラウドへの引っ越しを **移行** と呼びます。移行は技術だけの話ではなく、人材・体制・お金の決め方が整わないと進みません。

**CAF**(Cloud Adoption Framework)は、組織の移行準備を6つの視点で点検する公式の枠組みです。6つの個別暗記より、まず「ビジネス面3つ+技術面3つ」の構造を覚えてください。

| 面 | 視点 |
| --- | --- |
| ビジネス面 | ビジネス / 人材 / ガバナンス |
| 技術面 | プラットフォーム / セキュリティ / オペレーション |

M1のWell-Architectedとの混同がひっかけの定番です。

- **CAF** = 移行の**前**に、**組織**の準備を点検する
- **Well-Architected** = 設計する**とき**に、**システム**の良し悪しを点検する

問題文に「組織」「人材」「移行計画」の語が見えたらCAFです。

## 8-1-4 移行戦略の7R

> **移行のやり方は、そのまま運ぶリホストから作り直すリファクタリングまで、7つのRから選ぶ**

「全部作り直す」は高くつき、「そのまま運ぶだけ」ではクラウドの旨みが薄い——システムごとにやり方を選ぶ型が、頭文字Rの7戦略 **7R** です。まず代表の3つを固めます。

| 戦略 | 一言 | 例 |
| --- | --- | --- |
| **リホスト** | そのまま運ぶ(lift and shift) | サーバーをそのままEC2へ |
| **リプラットフォーム** | 少しだけ調整して運ぶ | DBだけRDSに置き換え |
| **リファクタリング** | クラウド前提に作り直す | サーバーレスに再設計 |

下に行くほど手間は大きく、クラウドの効果も大きくなります。残りの4つは名前と一言だけで十分です。

- リパーチェス = 買い替える(SaaSへ乗り換え)
- リタイア = 廃止する
- リテイン = 今は残す(移行しない)
- リロケート = 仮想化基盤の環境ごと移す

「廃止(リタイア)も保留(リテイン)も戦略のうち」という点が意外と問われます。

## 8-1-5 データの引っ越し道具

> **回線で送りきれない大容量はSnowファミリーで運び、データベースはDMSで動かしたまま移す**

ペタバイト級のデータを回線で送ると数か月かかる計算になることがあり、業務中のデータベースは止めて引っ越すわけにいきません。「量」と「止められなさ」に応じた道具を3つ覚えます。

| 道具 | 一言 | 向く場面 |
| --- | --- | --- |
| **Snowファミリー** | データを物理装置に入れて配送で運ぶ | 回線では間に合わない大容量 |
| **DMS** | データベースを動かしたまま移す | 止められない業務DB |
| **DataSync** | ファイルを回線で自動転送 | オンプレのファイルをS3等へ定期同期 |

物理輸送(Snowファミリー)という選択肢の存在自体が試験ポイントです。シナリオの言い回しはほぼ固定で、「ネットワーク経由では現実的でないペタバイト級」ならSnow、「ダウンタイム最小でDB移行」ならDMS、「継続的なファイル転送」ならDataSyncです。
