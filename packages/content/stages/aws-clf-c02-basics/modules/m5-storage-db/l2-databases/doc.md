# レッスン5-2 データベース

## このレッスンの目標

- [ ] RDSが「何を任せられて、何が自分の仕事か」を説明できる
- [ ] Aurora・DynamoDB・ElastiCacheの用途の一言を言える
- [ ] ワークロードの説明文からデータベースを選び分けられる

## 5-2-1 RDSはマネージドなRDB

> **RDSは、バックアップやパッチ適用をAWSに任せられるマネージドなリレーショナルデータベース**

顧客・注文・在庫など、業務データの多くは「表」で管理されます。データを表の形で管理し、**SQL** という言語で操作するデータベースを **リレーショナルデータベース**(RDB)と呼びます。

EC2に自分でDBソフトを入れると、インストール・パッチ適用・バックアップがすべて自分の仕事になります。**RDS**(Relational Database Service)は、MySQL・PostgreSQLなどのエンジンを選んで使うマネージドなRDBで、この運用をAWSに任せられます。

| 作業 | EC2に自分で構築 | RDS |
| --- | --- | --- |
| インストール | 自分 | 不要 |
| パッチ適用 | 自分 | AWS(設定に応じて自動) |
| バックアップ | 自分 | 自動 |
| SQLの操作・設計 | 自分 | 自分 |

最後の行が大事です。中身(データ・SQL・テーブル設計)は変わらず自分の仕事です。

もう1つ、**マルチAZ配置** を覚えてください。別のAZに予備を用意し、障害時に自動で切り替える構成です。「データベースを止めたくない」というシナリオでは、RDSのマルチAZ配置が答えの軸になります。M2で学んだ「複数AZに分ける」型のデータベース版です。

## 5-2-2 Auroraはクラウド設計のRDB

> **Auroraは、MySQL / PostgreSQL互換のままクラウド向けに再設計された高性能データベース**

RDSで運用は任せられました。さらに性能と可用性を上げたい場合の選択肢が **Aurora** です。AWSがクラウド前提で設計し直したリレーショナルデータベースで、MySQL / PostgreSQLと互換性があるため、アプリからは同じように見えます。

| | RDS(MySQL等) | Aurora |
| --- | --- | --- |
| 中身 | 既存のDBソフトのマネージド版 | クラウド前提の再設計 |
| 互換性 | 各エンジンそのまま | MySQL / PostgreSQL互換 |
| 性能・可用性 | 標準的 | より高い(データを3つのAZへ複製) |

試験では「MySQL互換で、より高い性能と可用性のマネージドDB」がAuroraの合図です。AuroraはRDSファミリーの一員として提供されます。使った分だけ自動伸縮するサーバーレス版もある、と名前だけ知っておけば十分です。

## 5-2-3 DynamoDBはNoSQL

> **DynamoDBは、キーと値で引くNoSQLデータベースで、ミリ秒の応答のまま自動でスケールする**

表とSQLは万能ではありません。「ユーザーIDでセッション情報を引くだけ」を秒間数十万回、のような使い方には別の道具が向きます。

表とSQLの形にこだわらないデータベースの総称が **NoSQL** で、キー(鍵)で値を出し入れする最も単純な形を **キーバリュー** 型と呼びます。**DynamoDB** はそのサーバーレスなサービスで、ロッカーの番号札のように「番号で入れて番号で出す」使い方を、ミリ秒の応答のまま自動スケールでさばきます。サーバーやOSの管理は登場しません。

| | RDS / Aurora | DynamoDB |
| --- | --- | --- |
| データの形 | 表と表の関係 | キーと値 |
| 操作 | SQL | キーで出し入れ |
| 規模の伸ばし方 | サイズ変更が中心 | 自動で水平にスケール |
| 典型用途 | 会計・在庫・注文 | セッション・ゲーム・IoT |

「ミリ秒」「サーバーレスなNoSQL」「自動スケール」がDynamoDBの合図です。逆に「表同士を結合した複雑な集計」が要るならRDS / Auroraに戻します。

## 5-2-4 ElastiCacheはインメモリ

> **ElastiCacheは、よく読むデータをメモリ上に置いて応答を速くするインメモリのキャッシュサービス**

同じ人気商品の情報を1秒間に何千回もデータベースへ聞きに行くのは無駄です。ディスクではなく高速なメモリにデータを置くことを **インメモリ** と呼び、よく読む答えの写しをメモリに置いて返すマネージドなキャッシュサービスが **ElastiCache** です。RedisやMemcachedという既存のキャッシュソフトのマネージド版として提供されます。

| 読み方 | 経路 | 速さ |
| --- | --- | --- |
| キャッシュなし | アプリ → DB(ディスク) | 毎回ディスクの速さ |
| ElastiCache | アプリ → キャッシュ(メモリ) | メモリの速さ。DBの負荷も減る |

効き目は「応答が速くなる」と「DBの負荷が減る」の2つです。M2のCloudFrontが「配信の手前」のキャッシュなら、ElastiCacheは「DBの手前」のキャッシュです。キャッシュは消えてもよい写しで、正本はDB側に残す——この関係も覚えてください。

## 5-2-5 データベースの選び分け

> **表のデータを厳密に扱うならRDS、決まったキーで速く引くならDynamoDBと、データの形と用途で選ぶ**

役者がそろったので、判定表を作ります。判定の軸は「データの形」と「用途」です。

| 用途の一言 | 選ぶ |
| --- | --- |
| 注文・在庫・会計(表と集計) | RDS |
| RDSと同じ用途で、より高性能に | Aurora |
| セッション・IoT(キーで大量高速) | DynamoDB |
| よく読む答えの写しを速く返す | ElastiCache |

迷ったときの判定順です。

1. SQL・結合・トランザクションの語がある? → RDS / Aurora
2. キーで引く・ミリ秒・自動スケール? → DynamoDB
3. 読み取りの高速化・DBの負荷軽減? → ElastiCache
4. 「大量データの分析・集計の倉庫」の話 → 分析用のRedshift(M6)。ここと混同しない

なお、稼働中のデータベースを止めずにAWSへ移すサービス(DMS)はM8「移行」で扱います。

## もっと知りたい人へ

- CLF-C02のin-scopeには、この他にもDocumentDB(文書型)やNeptune(グラフ型)などの専用データベースが並びます。名前と「データの形」の対応だけ拾っておけば十分です
- 「目的別データベース」(purpose-built databases)という言葉は、「1つのDBで全部やらず、形に合わせて選ぶ」というこのレッスンの方針そのものです
