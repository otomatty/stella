# レッスン1-2 Well-Architected

## このレッスンの目標

- [ ] Well-Architectedフレームワークが何かを1文で説明できる
- [ ] 6本の柱の名前をすべて挙げられる
- [ ] シナリオを読んで、どの柱の話かを判定できる

## 1-2-1 Well-Architectedとは

> **Well-Architectedフレームワークは、良い設計かどうかを6本の柱で点検するAWS公式の枠組み**

「この構成で大丈夫?」という不安に、経験者の勘だけで答えると見落としが出ます。**Well-Architected** フレームワークは、「良く設計されている」ことをAWSが公式に定義した点検の枠組みです。点検の観点を **柱** と呼び、全部で6本あります。

| # | 柱 |
| --- | --- |
| 1 | 運用上の優秀性 |
| 2 | セキュリティ |
| 3 | 信頼性 |
| 4 | パフォーマンス効率 |
| 5 | コスト最適化 |
| 6 | 持続可能性 |

大事なのは、これが「設計の答えを出す道具」ではなく「問いのリスト」だという点です。試験では「6本の柱に含まれるものはどれか」という名前当ての問題がそのまま出ます。「俊敏性」「弾力性」は利点(M0・M1)の語であって柱の名前ではありません。また、古い資料には柱が5本と書かれていることがあります。持続可能性が加わって現在は6本です。

## 1-2-2 柱の前半 運用・セキュリティ・信頼性

> **運用上の優秀性・セキュリティ・信頼性の柱は、回し方・守り方・止めない仕組みを問う**

柱の名前を覚えただけでは、「この改善はどの柱か」というシナリオ問題で選べません。柱ごとの「問い」を1行で言えるようにします。前半3本のラベルは「回す・守る・止めない」です。

| 柱 | 問い | シナリオの例 |
| --- | --- | --- |
| **運用上の優秀性** | 日々の運用を改善し続けているか | 手作業の運用を自動化したい |
| セキュリティ | データと仕組みを守れているか | 権限を最小限にしたい |
| **信頼性** | 障害が起きても回復して動き続けるか | 1台壊れても止めたくない |

見分けのコツは、問題文のキーワードです。

- 「自動化・手順・改善」→ 運用上の優秀性
- 「権限・暗号・保護」→ セキュリティ
- 「障害・復旧・冗長」→ 信頼性

セキュリティの柱の中身(共有責任、IAM、暗号化)はM7で1日かけて扱います。ここでは「柱の1本である」ことだけ覚えれば十分です。

## 1-2-3 柱の後半 性能・コスト・持続可能性

> **パフォーマンス効率・コスト最適化・持続可能性の柱は、資源の使い方の無駄を問う**

後半3本はどれも「資源の使い方」の柱で、無駄を速さ・お金・環境の3方向から見ます。

| 柱 | 問い | シナリオの例 |
| --- | --- | --- |
| **パフォーマンス効率** | 要件に合う資源を効率よく使えているか | 新しいインスタンスの世代へ更新したい |
| **コスト最適化** | 不要な支出をなくせているか | 使っていない資源を止めたい |
| **持続可能性** | 環境への影響を減らせているか | 消費エネルギーを減らしたい |

「パフォーマンス効率」と「コスト最適化」は同じ改善(たとえばライトサイジング)が両方に効くため混ざりやすい柱です。問題文の目的語で区別してください。

- 「速く・最新・効率よく」→ パフォーマンス効率
- 「安く・無駄なく・請求」→ コスト最適化
- 「環境・エネルギー・CO2」→ 持続可能性

6本の柱は「運・セ・信・パ・コ・持」の頭文字で暗唱できるようにしておくと、名前当ての問題を数秒で処理できます。

## もっと知りたい人へ

- Well-Architected Framework の柱の解説(公式): https://docs.aws.amazon.com/wellarchitected/latest/framework/the-pillars-of-the-framework.html
- 各柱には「設計原則」の一覧もあります。余裕があれば、信頼性の柱の設計原則(障害に備える考え方)だけでも読んでおくと、M2以降の高可用性の話がつながります
