# レッスン3-1 CI で品質を守る

## このレッスンの目標

- [ ] CI が何を合図に何をする仕組みか説明できる
- [ ] CI が赤い PR にどう対応すべきか判断できる
- [ ] カバレッジを目標ではなく道具として使える

## 3-1-1 CI はテストを共通の環境で自動実行する

> **CIはプッシュやPRを合図に、テストを全員共通の環境で自動実行する仕組みである**

手元でテストを書けるようになっても、**実行し忘れ** は防げません。急いでいるとき、疲れているとき、人は忘れます。意志で解決しようとするのではなく、仕組みにします。

**CI** は、コードの変更を合図にテストを自動で実行する仕組みです。コードを保管する場所を **リポジトリ**、何を合図に何をするかを書いた手順書を **ワークフロー** と呼びます。

```yaml
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install pytest
      - run: pytest
```

読むべきなのは2か所だけです。`on` が **合図**(プッシュされたとき、PR が出されたとき)、`steps` が **やること**です。書き方の細かい構文は、必要になったときに調べれば十分です。

`steps` の1つ目にある `actions/checkout` は、**リポジトリのコードを実行環境に持ってくる** 手順です。CI の実行環境は毎回まっさらな状態から始まるので、これが無いとコードが1つも無い場所で `pytest` が走ります。

このとき pytest は `no tests ran` と表示して終了コード5を返すので、**CI は赤くなります**。ただし「テストが失敗した」わけではないので、失敗出力を探しても赤い `assert` の行は1つも見つかりません。CI が赤いのに失敗したテストが見当たらないときは、**集まったテストの件数** を見てください。0件なら、原因はテストではなく手順のほうにあります。

CI が入ると、手元との違いがはっきりします。

| | 手元 | CI |
| --- | --- | --- |
| 実行 | 人が思い出したとき | 毎回、自動で |
| 環境 | 人によって違う | 全員同じ |
| 結果 | 自分だけが見る | PR に表示される |

**「自分の環境では通る」が通用しなくなる** のが、CI のいちばんの効能です。環境の違いによる不具合も、ここで表に出ます。

## 3-1-2 赤のままマージしない

> **CIが赤のままマージしないルールが、mainブランチの品質を守る**

CI を入れたのに効いていないチームには、たいていこのルールがありません。

作業を枝分かれさせる単位を **ブランチ** と呼び、本流を **mainブランチ** と呼びます。全員が main から枝を作って作業し、終わったらマージして戻します。テストが全部通った状態が **グリーン** です。

赤いままマージすると、次の順で壊れていきます。

1. main が壊れる
2. main を取り込んだ枝から順に赤くなる
3. 自分のせいか判断できず、赤を無視し始める
4. CI が意味を失う

2 について補足すると、すでにある枝の CI 結果が勝手に赤に変わるわけではありません。赤くなるのは、**壊れた main から新しく枝を作った人**、**main を取り込んだ人**、そして **PR に新しくコミットを push した人** です(PR の CI は多くの場合、その PR を main にマージした結果に対して走るので、push のたびに最新の main を巻き込んだ状態で実行されます)。なお、前回の実行を再実行しただけでは変わりません。同じコミットに対して走り直すだけだからです。

放っておいても直らず、触った人から順に巻き込まれていきます。

4 に到達したチームは、CI を止めたのと同じ状態です。しかも「CI はあるのに事故が起きる」ぶん、たちが悪くなります。

自分の PR が赤いときは、次のように動いてください。

| 状況 | すること |
| --- | --- |
| 自分の変更が原因 | 直して push し直す |
| 元から赤い | 先に main を直す(自分の PR は待つ) |
| 原因が不明 | 落ちたテスト名を添えて相談する |

「とりあえずマージ」は選択肢にありません。これは技術ではなくルールなので、チームで合意していないと機能しません。

## 3-1-3 CI が遅いと開発が止まる

> **CIの実行時間が長いと開発が止まるため、速い単体テストを中心に据える**

PR を出してから結果が出るまで40分かかると、待つのが嫌になります。すると人は、変更をまとめて大きな PR にします。大きな PR はレビューが雑になり、事故が増えます。**遅い CI は、レビューの質まで下げます。**

直して、確かめて、また直す、という周期を **フィードバックループ** と呼びます。1周が長いほど、1回の変更が大きく雑になります。速さは快適さの話ではなく、変更の品質の話です。

遅さは、たいていピラミッドの上から来ます。

| 種類 | 1件あたり | 本数の目安 |
| --- | --- | --- |
| 単体 | ミリ秒 | 多い |
| 結合 | 秒 | 中くらい |
| E2E | 分 | 少ない |

単体テストは1000本でも数秒ですが、E2Eテストは10本足すだけで分単位で伸びます。テストピラミッドの形が崩れると、CI は一気に遅くなります。

速く保つ工夫は3つです。

- 単体テストで守れるものは、単体テストで守る
- 遅いテストは、本数ではなく **必要性** で選ぶ
- どのテストが遅いかを **測ってから** 減らす

勘で減らすと、必要なテストを削ってしまいます。`pytest --durations=10` で遅い順に10件を出し、上位から検討してください。

## 3-1-4 カバレッジは証明ではなく道具

> **カバレッジは品質の証明ではなく、テストされていない場所を見つける道具である**

テストを実行したときに通った行の割合を **カバレッジ** と呼びます。数字で出るので分かりやすく、そのぶん独り歩きしやすい指標です。

まず押さえるべきなのは、カバレッジが示すのは **通ったかどうかだけ** で、**正しいと確かめたかどうかではない** ことです。

```python
def test_calc_total():
    calc_total([100, 200])   # 呼んだだけ。assert が無い
```

このテストでもカバレッジは100%になります。しかし `calc_total` を壊しても赤くなりません。カバレッジを目標にすると、こうしたテストが量産されます。

正しい使い方は、**数字を上げに行くのではなく、低い場所を見に行く** ことです。

- 0%のファイルは「まだ誰も守っていない」印
- 分岐の片方だけ通っている箇所は、境界値のテストが抜けている可能性が高い
- 見つけた場所が重要なら、そこにテストを足す

レポートは順位表ではなく、**地図** として使ってください。

## もっと知りたい人へ

- `pytest --durations=10` で、遅いテストの上位10件が表示されます。CI を速くするときの最初の一手です
- カバレッジの計測には `pytest-cov` などの追加パッケージを使います。CI のレポートに出しているチームも多いので、自分のプロジェクトの設定を一度見てみてください
