# レッスン0-1 テストを書く理由

## このレッスンの目標

- [ ] 手動確認と自動テストのコストの違いを説明できる
- [ ] テストが「早く気づくための仕組み」であることを説明できる
- [ ] 単体・結合・E2E の3種類を、速さと本数の観点で区別できる

## 0-1-1 自動テストは一度書けば毎回実行できる

> **手動確認は変更のたびに同じコストがかかるが、自動テストは一度書けば毎回実行できる**

コードを直したあと、正しく動くかを人が目で確かめることを **手動確認** と呼びます。画面を開いて操作する、スクリプトを実行して出力を眺める、といった作業です。

手動確認には、避けられない性質があります。**変更するたびに、まったく同じ手間がもう一度かかる** ことです。1回3分の確認でも、20回直せば1時間になります。しかも人がやるので、疲れてくると一部しか見なくなり、見落としが増えます。

そこで、確認そのものをプログラムとして書きます。これが **自動テスト** です。

```python
def test_calc_total():
    # 注文の金額を合計できることを確かめる
    assert calc_total([100, 200]) == 300
```

この1行が、手で確かめていた作業の代わりになります。何度コードを直しても、テストを実行するだけで同じ確認が終わります。

| | 手動確認 | 自動テスト |
| --- | --- | --- |
| 1回目 | 速い | 書く手間がかかる |
| 10回目 | 10回ぶんかかる | 実行するだけ |
| 見落とし | 増える | 減る |

1回目は自動テストのほうが損をします。テストは投資なので、**何度も直す場所ほど得になる** と考えてください。一度書いて二度と触らないスクリプトに、無理にテストを書く必要はありません。

## 0-1-2 テストは壊したことに最も早く気づく仕組み

> **テストは壊したことに最も早く気づく仕組みであり、品質はマージ前に担保する**

現場で怖いのは、直した場所そのものより、**関係ないと思っていた機能が一緒に壊れる** ことです。動いていたものが動かなくなる事故を **デグレ** と呼びます。

デグレは、気づくのが遅いほど高くつきます。

| 気づく場所 | 直すコスト |
| --- | --- |
| 手元でテスト実行 | 数分 |
| PR のレビュー中 | 数十分 |
| リリース後 | 数日 + 謝罪 |

チーム開発では、自分の変更をいきなり本流のコードに入れることはしません。変更をまとめて「取り込んでください」と依頼するのが **プルリクエスト**(PR)です。そして実際に取り込む操作が **マージ** です。

品質は、マージしたあとに検査して上げるものではなく、**マージする前に担保するもの** です。テストは、そのために「壊した瞬間に最も早く教えてくれる」役割を担います。

なお、テストは品質を作り出す道具ではありません。品質を作るのはコードを書く人で、テストはそれが壊れたことを教えるだけです。ここを取り違えると「テストを書いたのにバグが出た」という誤解につながります。

## 0-1-3 テストピラミッドで割り振りを決める

> **テストピラミッドでは、速く安い単体テストを土台に、結合・E2E を上に少なく積む**

「テストを書こう」と決めても、どこから書くかで迷います。よくある失敗は、画面から通しで確かめるテストばかり作ってしまい、実行に何十分もかかって誰も回さなくなることです。

テストは、確かめる範囲によって3種類に分けられます。

- **単体テスト** — 関数1つの振る舞いを確かめる
- **結合テスト** — 部品どうしのつながりを確かめる
- **E2Eテスト** — 利用者と同じ手順で、通しで確かめる

この3種類には、はっきりした性格の違いがあります。

| 種類 | 速さ | 本数 | 見つかる不具合 |
| --- | --- | --- | --- |
| 単体 | 速い | 多い | ロジックの誤り |
| 結合 | 遅い | 中くらい | つなぎ目の誤り |
| E2E | とても遅い | 少ない | 通しで動かない |

上に行くほど本番に近い確認ができますが、そのぶん遅く、壊れやすくなります。そこで、**速くて安い単体テストを土台に多く書き、上に行くほど本数を減らす** 形を目指します。この配分の考え方が **テストピラミッド** です。

ピラミッドは「単体テストが偉い」という話ではありません。**どの種類を何本書くか** の地図です。この講座は、まず土台の単体テストを書けるようにし、そのあと結合テストの使いどころ(M4)へ進みます。

## もっと知りたい人へ

- テストの分類名は現場によって揺れます。「結合テスト」と「統合テスト」、「E2E」と「システムテスト」はほぼ同じ意味で使われます。名前より、**どこまでを本物で確かめているか** に注目してください
- ピラミッドの形が崩れて、E2E が最も多い状態を「アイスクリームコーン」と呼ぶことがあります。遅くて不安定なテストが上に載った状態の呼び名です
