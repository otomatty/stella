# レッスン4-1 結合テストで「つなぎ目」を守る

## このレッスンの目標

- [ ] 結合テストが検出できる不具合の種類を説明できる
- [ ] テストダブルで依存先を差し替えられる
- [ ] 依存先を本物にするか代役にするかを、理由を言って選べる

## 4-1-1 結合テストはつなぎ目の不具合を捕まえる

> **結合テストは、部品単体ではなくDBや外部APIとの「つなぎ目」で起きる不具合を検出する**

関数ごとの単体テストが全部緑なのに、つないだ瞬間に動かないことがあります。部品はどれも正しいのに、組み立てると動かない状態です。

自分のコードが頼っている相手を **依存先**、依存先とのやり取りの境目を **つなぎ目** と呼びます。代表的な依存先が **データベース**(DB)や外部の API です。

つなぎ目には、単体テストでは絶対に出ないバグが住んでいます。

| 場所 | よくあるバグ |
| --- | --- |
| DB | 列名の綴り違い / 型の不一致 |
| 外部API | レスポンスの形の思い込み |
| ファイル | 文字コード / 改行の違い |

どれも「自分の関数の中」には存在しません。関数のロジックは正しいのに、相手に渡す形や、相手から返る形の理解が間違っているのです。

確かめている場所が違う、と整理してください。

- **単体テスト** — 関数の中のロジック
- **結合テスト** — 関数と依存先の **やり取り**

片方でもう片方を代用することはできません。両方必要です。

## 4-1-2 テストダブルは依存先の代役

> **テストダブル(モック等)は、本物の依存先の代わりに振る舞いを差し替える部品である**

依存先を毎回本物にすると、困ることがあります。外部の API を叩けば遅く、課金され、相手が落ちていれば自分のコードが正しくてもテストが赤くなります。**自分の都合で結果を決められない相手** をテストに入れると、テストは不安定になります。

そこで代役を用意します。これが **テストダブル** です。ダブルは映画のスタントダブル(代役)と同じ語です。呼ばれ方まで記録できる代役を **モック** と呼びます。本物と入れ替えることを **差し替え** と言います。

```python
class FakeRateApi:
    def get_rate(self):
        return 150.0


def test_converts_to_yen():
    assert to_yen(10, FakeRateApi()) == 1500.0
```

特別な道具は要りません。**同じメソッドを持つクラスを渡すだけ** でも代役になります。Python には `unittest.mock` という標準の仕組みもありますが、まずはこの形で十分です。

代役にできることは3つあります。

| したいこと | 代役の使い方 |
| --- | --- |
| 決まった値を返させる | 固定値を返す |
| エラーを起こさせる | 例外を投げさせる |
| 呼ばれたか確かめる | 呼び出しを記録する |

とくに大きいのが2つ目です。**本物では起こしにくい失敗** を、代役なら簡単に再現できます。通信エラーやタイムアウト時の動きは、代役でしか確かめられないことが多くあります。

## 4-1-3 本物かダブルかは不具合の場所で選ぶ

> **依存先を本物にするかテストダブルにするかは、検証したい不具合がどこで起きるかで選ぶ**

代役は便利なので、つい全部を代役にしたくなります。しかし全部モックにしたテストは、緑なのに本番で落ちます。逆に全部本物にすると、遅くて誰も回さなくなります。**どちらの極端も失敗します。**

判断の基準は1つです。**検証したい不具合が、どこで起きるか。**

| 確かめたいこと | 依存先 |
| --- | --- |
| 保存した行が正しく読めるか | 本物(テスト用のDB) |
| 通信が失敗したときの動き | 代役(例外を投げさせる) |
| 金額の計算ロジック | 依存させない(単体テスト) |

3行目が特に大事です。**そもそも依存を持ち込まない** 選択肢が、いちばん速くて壊れにくくなります。

代役を使うと消える保証もあります。

```python
class FakeRateApi:
    def get_rate(self):
        return 150.0   # 本物のキー名が違っても気づけない
```

代役は「自分が思っている相手の姿」でしかありません。相手の実際の形についての思い込みが間違っていても、テストは緑のまま通ります。だから、**つなぎ目そのものを確かめたいときに代役を使ってはいけません。**

## 4-1-4 単体で守れるものを結合に持ち込まない

> **結合テストは遅く壊れやすいため、単体テストで守れるものを結合テストに持ち込まない**

「もう一回流したら通った」が口癖になったら危険信号です。実行のたびに結果が変わるテストを **壊れやすいテスト** と呼びます。依存先が増えるほど、揺らぐ要因が増えます。

- 実行順で結果が変わる(前のテストのデータが残っている)
- 時刻・通信・並列実行など、制御できない要因を含む

厄介なのは、**赤を信用しなくなること** です。再実行して緑になったら通す、という運用になった時点で、そのテストは緑も信用できません。テスト全体の価値が下がります。

対策は、置き場所を分けることです。

| 確かめたいこと | 置き場所 |
| --- | --- |
| 割引の計算パターン20通り | 単体テスト |
| 割引後の金額が保存できる | 結合テスト1本 |

20通りを DB 経由で回せば20倍遅くなりますが、確かめているのは同じ計算ロジックです。**パターンは単体テストで、つなぎ目は結合テスト1本で** 守ってください。これが、テストピラミッドの形を保つ実務上の理由です。

## もっと知りたい人へ

- テストダブルには、返す値を決めておくだけの「スタブ」、呼ばれ方を検証する「モック」など細かい分類があります。名前より、**何を確かめたいか** で選んでください
- 本物の DB を使う結合テストでは、テストごとにデータを作り直すのが基本です。fixture の後片付けがそのまま役に立ちます
