# レッスン4-1 演習 — 結合テストで「つなぎ目」を守る

対象トピック: 4-1-1 〜 4-1-4

## 手元で試す

外貨の金額を円に変換する関数を作ります。為替レートは外部の API から取る想定です。

```python
# rate.py
def to_yen(amount, rate_api):
    return amount * rate_api.get_rate()
```

代役を渡すテストを書きます。

```python
# test_rate.py
import pytest

from rate import to_yen


class FakeRateApi:
    def get_rate(self):
        return 150.0


class BrokenRateApi:
    def get_rate(self):
        raise ConnectionError("通信に失敗しました")


def test_converts_to_yen():
    assert to_yen(10, FakeRateApi()) == 1500.0


def test_raises_when_api_is_down():
    with pytest.raises(ConnectionError):
        to_yen(10, BrokenRateApi())
```

```bash
pytest
```

2件とも通ることを確かめてください。本物の API は一度も呼んでいません。確かめられたら、次もやってみましょう。

1. `rate.py` の呼び出しと `FakeRateApi` / `BrokenRateApi` のメソッド名を、**3か所まとめて** `get_exchange_rate` に改名して実行する。2件とも緑のまま通るが、本物の API のメソッド名が `get_rate` のままならこのコードは本番で落ちる。代役と自分のコードだけで辻褄が合っている状態を確かめる(確かめたら戻す)
2. `to_yen` に「レートが0以下ならエラーにする」仕様を足し、その確認を代役で書く
3. 2 で書いたテストが、本物の API を使わずに済んでいる理由を説明してみる

## 演習問題

### 問1(基本)

次のうち、単体テストでは検出できないものはどれですか。理由も書いてください。

1. 消費税の計算で端数の処理を間違えている
2. SQL の列名を `totl` と綴り間違えている
3. 空のリストを渡すとエラーになる

### 問2(基本)

外部 API を呼ぶテストを本物のまま CI で回すと、どんな問題が起きますか。2つ挙げてください。

### 問3(応用)

「DB に保存した注文を、あとから正しく読み出せるか」を確かめたいとき、DB を代役にするべきですか。理由とともに答えてください。

### 問4(応用)

割引の計算パターンを30通り確かめたいとき、すべて DB を経由する結合テストで書くと何が問題になりますか。より良い書き方も答えてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

2 です。列名の綴り違いは、自分の関数の中ではなく DB とのつなぎ目で起きるためです。単体テストは関数の中のロジックしか見ていないので、実際に DB とやり取りしないと検出できません。

</details>

<details>
<summary>問2の解答例</summary>

1つは、実行が遅くなり、呼び出し回数によっては課金が発生することです。もう1つは、相手が落ちていたりレート制限に当たったりすると、自分のコードが正しくてもテストが赤くなることです。

</details>

<details>
<summary>問3の解答例</summary>

代役にすべきではありません。確かめたい不具合(列名の綴り、型の不一致、保存と読み出しの食い違い)は、まさに DB とのつなぎ目で起きるためです。代役にすると、その保証が消えます。テスト用の DB を使って本物で確かめます。

</details>

<details>
<summary>問4の解答例</summary>

30通りすべてが DB 経由になるため実行が遅く、DB の状態に依存して壊れやすくなります。しかも確かめているのは同じ計算ロジックです。計算パターンは単体テストで30通り確かめ、「割引後の金額が保存できる」ことだけを結合テスト1本で確かめます。

</details>

## 確認クイズ

### Q1. 結合テストが検出するのは、どんな不具合ですか。

- A. DB や外部 API とのつなぎ目で起きる不具合
- B. 関数の中の計算ロジックの誤り
- C. コードの書式の乱れ

<details>
<summary>答え</summary>

**A** — 列名の綴り違いやレスポンスの形の思い込みは、関数の中には存在しません。

</details>

### Q2. テストダブルとは何ですか。

- A. 本物の依存先の代わりに、振る舞いを差し替える部品
- B. 同じテストを2回実行する仕組み
- C. テストの実行結果を保存しておくファイル

<details>
<summary>答え</summary>

**A** — 代役です。固定値を返させたり、例外を投げさせたりできます。

</details>

### Q3. 通信が失敗したときの動きを確かめたいとき、依存先はどうしますか。

- A. 代役にして、例外を投げさせる
- B. 本物の API を使い、相手が落ちるのを待つ
- C. テストを書かない

<details>
<summary>答え</summary>

**A** — 本物では起こしにくい失敗を再現できるのが、代役の大きな利点です。

</details>

### Q4. 依存先を本物にするか代役にするかは、何で決めますか。

- A. 検証したい不具合がどこで起きるか
- B. 書くのがどちらが楽か
- C. チームの人数

<details>
<summary>答え</summary>

**A** — つなぎ目の不具合を確かめたいなら本物、自分のロジックを確かめたいなら代役です。

</details>

### Q5. 「再実行したら通った」を繰り返しているテストの何が問題ですか。

- A. 赤も緑も信用できなくなり、テスト全体の価値が下がる
- B. 実行するたびにコードが書き換わる
- C. カバレッジが下がる

<details>
<summary>答え</summary>

**A** — 壊れやすいテストは、通ったことの意味も失わせます。依存先を減らすのが対策です。

</details>
