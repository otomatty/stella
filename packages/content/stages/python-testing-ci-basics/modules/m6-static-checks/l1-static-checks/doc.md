## 6-1-1 lint は実行前に危ない書き方を指摘する

> **lintは、バグになりやすい書き方をテスト実行前に機械が指摘する仕組みである**

コードを実行せずに調べて、危うい書き方を指摘することを **lint**、それを行う道具を **リンター** と呼びます。

```python
def calc_total(prices):
    tax_rate = 0.1        # 使われていない変数
    total = 0
    for price in prices:
        total += pirce    # 名前の綴り違い
    return total
```

使われていない変数は「消し忘れ」か「使うつもりだった処理の書き忘れ」のどちらかです。名前の綴り違いは、実行して初めてエラーになります。lint は、こうした誤りを **実行する前に** 見つけます。

テストと lint は、役割が違います。

| | 見つけるもの | 実行 |
| --- | --- | --- |
| テスト | 振る舞いの誤り | 動かす |
| lint | 書き方の危うさ | 動かさない |

どちらかで代用することはできません。テストが無い場所は、テストでは守れないからです。lint は全コードを一様に調べるので、テストが書かれていない場所にも効きます。

lint は実行が速いので、CI の最初に置くことが多くなります。数秒で落ちてくれれば、数分かかるテストを待たずに済みます。Python では `ruff` や `flake8` といったリンターが使われますが、**どの道具かより、CI で毎回回っているかどうか** が大事です。

## 6-1-2 整形の自動化でレビューが本質に集中する

> **フォーマッタで整形を自動化すると、レビューが本質的な指摘に集中できる**

コードの見た目を機械的に整える道具が **フォーマッタ** です。そして、人が変更を読んで確認する作業が **コードレビュー** です。

```python
x = {'total':300,  'tax':30}
```

```python
x = {"total": 300, "tax": 30}
```

中身は同じで、書き方だけがそろいました。**実行結果は1文字も変わりません。** だからこそ、議論の余地がありません。「決めた形に全部そろえる」ことに価値があり、どの形が美しいかは問題ではありません。

整形を自動化すると、2つの効果があります。1つは、レビューから見た目の指摘が消えることです。もう1つは、差分が読みやすくなることです。空白の変更だらけの差分では、本当の変更が埋もれます。

何をどこに任せるかを整理しておきます。

| 種類 | 例 |
| --- | --- |
| フォーマッタ | 空白・改行・引用符 |
| lint | 未使用の変数・危うい書き方 |
| コードレビュー | 仕様の解釈・設計・命名 |

人は3行目だけをやります。人にしかできない指摘に時間を使えるようにするのが、自動化の目的です。

## 6-1-3 型チェッカーは実行せずに食い違いを見つける

> **型ヒントと型チェッカーは、実行しなくても引数や戻り値の食い違いを検出できる**

引数や戻り値の種類を書き添えるのが **型ヒント** です。そして、書かれた型と実際の使われ方を照合して食い違いを指摘する道具が **型チェッカー** です。

```python
def calc_total(prices: list[int]) -> int:
    return sum(prices)


calc_total("100")   # 型チェッカーが指摘する
```

`prices: list[int]` が「整数のリストを受け取る」、`-> int` が「整数を返す」という意味です。

注意点が1つあります。**Python の型ヒントは、実行時には強制されません。** 書いただけでは何も起きず、型チェッカー(`mypy` など)を回して初めて効きます。CI に入れていないと、書いてあるだけの飾りになります。

型チェッカーが強いのは、**テストが通っていない経路** です。文字列を渡すべき関数に数値を渡していても、その経路のテストが無ければ本番まで気づけません。型チェッカーは、コード全体を一様に照合します。

この講座で扱った守り方を並べると、こうなります。

| 守り方 | 見つかるもの |
| --- | --- |
| 型チェッカー | 引数・戻り値の食い違い |
| lint | 危うい書き方 |
| テスト | 振る舞いの誤り |

3つは補い合う関係で、CI で全部回すと抜けが減ります。ここまで来たら、あとは実際のコードに1本テストを書くところから始めてください。**バグを1つ直すたびに再現テストを1本残す** だけでも、半年後のコードはまったく違うものになります。

## もっと知りたい人へ

- 型ヒントは、少しずつ足せます。全部のファイルに書く必要はなく、よく壊れる関数から始めるのが現実的です
- フォーマッタや lint は、エディターの保存時に自動実行する設定にしておくと、CI で落ちる前に手元で直せます
