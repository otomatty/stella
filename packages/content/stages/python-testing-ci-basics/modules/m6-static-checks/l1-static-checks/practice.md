# レッスン6-1 演習 — テスト以外の自動チェック

対象トピック: 6-1-1 〜 6-1-3

## 手元で試す

リンターを1つ入れて、実行前に指摘が出ることを確かめます。

```bash
pip install ruff
```

わざと問題のあるファイルを作ります。

```python
# messy.py
def calc_total(prices):
    tax_rate = 0.1
    total = 0
    for price in prices:
        total  +=  price
    return total


labels = {'total':'合計',  'tax':'消費税'}
```

```bash
ruff check messy.py
```

`tax_rate` が使われていないことを指摘されます。次に、整形も試します。

```bash
ruff format messy.py
```

`total  +=  price` の余分な空白が詰められ、引用符が `"` にそろいます。指摘された `tax_rate` は消えないことにも注目してください。**整形は書き方をそろえるだけで、危うさは直しません。** 確かめられたら、次もやってみましょう。

1. `total += price` を `total += pirce` に書き換えて `ruff check` を実行し、実行しなくても綴り違いが分かることを確かめる(確かめたら戻す)
2. `calc_total` の1行目を `def calc_total(prices: list[int]) -> int:` に書き換えて、型ヒントを足す
3. 自分が関わっているリポジトリの CI に、lint・フォーマット・型チェックのどれが入っているか確認する

## 演習問題

### 問1(基本)

テストと lint は、それぞれ何を見つけますか。1文ずつで説明してください。

### 問2(基本)

CI で lint をテストより先に実行することが多いのはなぜですか。

### 問3(応用)

「フォーマッタを入れると、自分の書きたい書き方ができなくなる」という意見に、1〜2文で答えてください。

### 問4(応用)

次の関数に型ヒントを書き足してください。また、型ヒントを書いただけでは食い違いが検出されない理由も説明してください。

```python
def make_label(name, count):
    return f"{name}: {count}件"
```

## 解答例と解説

<details>
<summary>問1の解答例</summary>

テストは、コードを実行して振る舞いが期待どおりかを確かめます。lint は、コードを実行せずに、バグになりやすい書き方や未使用の変数などを指摘します。

</details>

<details>
<summary>問2の解答例</summary>

lint はテストより実行が速いためです。数秒で落ちてくれれば、数分かかるテストの完了を待たずに直し始められます。フィードバックループが短くなります。

</details>

<details>
<summary>問3の解答例</summary>

フォーマッタが決めるのは空白や改行など実行結果が変わらない部分だけで、設計や命名は各自の判断のままです。見た目の議論は決着しても品質が上がらないため、機械に任せてレビューの時間を本質的な指摘に使います。

</details>

<details>
<summary>問4の解答例</summary>

```python
def make_label(name: str, count: int) -> str:
    return f"{name}: {count}件"
```

Python の型ヒントは実行時に強制されないためです。書いただけでは何も起きず、型チェッカー(`mypy` など)を実行して初めて食い違いが指摘されます。CI に入れていないと、飾りのままになります。

</details>

## 確認クイズ

### Q1. lint の説明として正しいものはどれですか。

- A. コードを実行せずに、バグになりやすい書き方を指摘する
- B. コードを実行して、振る舞いが正しいかを確かめる
- C. テストの実行時間を短縮する

<details>
<summary>答え</summary>

**A** — 動かさずに調べます。テストが書かれていない場所にも一様に効きます。

</details>

### Q2. lint とテストの関係として正しいものはどれですか。

- A. 見つけるものが違うので、両方 CI で回す
- B. lint があればテストは要らない
- C. テストがあれば lint は要らない

<details>
<summary>答え</summary>

**A** — 振る舞いの誤りと書き方の危うさは別ものです。どちらかで代用はできません。

</details>

### Q3. フォーマッタが変えるのはどれですか。

- A. 空白・改行・引用符など、実行結果が変わらない部分
- B. 変数名や関数名
- C. アルゴリズムの実装

<details>
<summary>答え</summary>

**A** — 実行結果が変わらないからこそ、議論の余地なく自動化できます。

</details>

### Q4. 整形を自動化すると、コードレビューはどう変わりますか。

- A. 仕様の解釈・設計・命名といった、人にしかできない指摘に集中できる
- B. レビュー自体が不要になる
- C. 差分が読みにくくなる

<details>
<summary>答え</summary>

**A** — 見た目の指摘が消え、差分からも空白の変更が消えます。

</details>

### Q5. Python の型ヒントについて正しいものはどれですか。

- A. 実行時には強制されず、型チェッカーを回して初めて食い違いが分かる
- B. 書いた時点で、実行時に必ずエラーになる
- C. テストを書けば型チェッカーは不要になる

<details>
<summary>答え</summary>

**A** — CI に型チェッカーを入れていないと、型ヒントは飾りのままになります。

</details>
