# レッスン2-1 テストの失敗を読んで直す

## このレッスンの目標

- [ ] 失敗出力から必要な4か所を拾える
- [ ] コードのバグとテスト自体の誤りを切り分けられる
- [ ] 再現テストを書いてからバグを直せる

## 2-1-1 失敗出力は決まった順に読む

> **失敗出力は「どのテストが・どの行で・何を期待して・何が返ったか」の順に読む**

テストが赤くなると、画面いっぱいに赤い文字が出ます。慣れないうちは、どこを見ればいいのか分からず、先輩に画面を見せて指さしてもらうことになります。

この赤い表示のかたまりを **失敗出力** と呼びます。読み方さえ決まっていれば、量は関係ありません。上から順に読むのではなく、**次の4か所を拾いに行きます**。

```text
_______________ test_calc_total _______________   ← どのテストが

test_order.py:8: in test_calc_total               ← どの行で
    assert calc_total([100, 200]) == 300
E   assert 250 == 300                             ← 何が / 何を期待して
```

1. **どのテストが** — 区切り線に挟まれたテスト名
2. **どの行で** — ファイル名と行番号
3. **何を期待して** — `assert` 行の右側(期待値)
4. **何が返ったか** — `E` の行に出る実際の値

関数の中でエラーが出た場合は、呼び出しの経路をたどった **トレースバック** も表示されます。これも同じで、**自分が書いたファイルの行** を上から探すのが近道です。

長い出力は、いちばん下から読むほうが速いこともあります。末尾には要約が出ます。

```text
FAILED test_order.py::test_calc_total - assert 250 == 300
1 failed, 3 passed
```

失敗したテスト名と件数が並びます。全部を読む必要はありません。

## 2-1-2 失敗にはバグとテストの誤りがある

> **テストの失敗には「コードのバグ」と「テスト自体の誤り」の2種類がある**

赤を見た瞬間にコードを直し始めると、事故が起きます。よくあるのは、期待値のほうが間違っていたのに実装を書き換えてしまい、正しかったコードを壊すパターンです。

実装が仕様どおりでない誤りが **バグ** です。一方、テストの期待値や準備コードの書き間違いは、テスト側の誤りです。**テストも人が書くので間違えます。**

直す前に、次の順で決めてください。

1. 仕様(何が正しいか)を確認する
2. 実際の値と、仕様が求める値を比べる
3. ずれているのが実装なら、コードを直す
4. ずれているのが期待値なら、テストを直す

**仕様が先** です。仕様が曖昧で判断できないなら、そこで手を止めて確認するのが正しい行動です。テストを通すこと自体が目的になると、仕様に反する実装ができあがります。

```python
def test_calc_shipping():
    # 仕様は「5000円以上で送料0円」
    assert calc_shipping(5000) == 500   # 期待値が誤り
```

これは実装が正しくても赤くなります。境界値の期待値ミスは実際によくあります。ここでコードを直してしまうと、仕様に反する実装が完成します。

なお、実装もテストも正しいのに赤くなる場合があります。**環境が原因** のときです。必要なパッケージが入っていない、設定ファイルが無い、依存先のサービスが落ちている、といった理由です。この場合、直す先はコードでもテストでもなく実行環境です。見分け方は、失敗が `assert` の行ではなく、その手前のエラー(`ImportError` や接続エラーなど)で起きていることです。**赤い = コードかテストが悪い、と決めつけない** でください。環境が原因の失敗は M3 と M4 で具体的に扱います。

## 2-1-3 再現テストを書いてから直す

> **再現手順をテストとして書いてから直すと、同じバグの再発を防げる**

半年前に直したはずのバグが、また同じ形で報告されることがあります。直した記憶は残っていても、**直したことはコードに残っていない** からです。

バグを再現させるために書くテストを **再現テスト** と呼びます。直す前に書くので、最初は必ず赤くなります。「赤いテストをわざわざ書く」ことに抵抗があるかもしれませんが、この赤が **バグを再現できた証拠** です。

手順は4段です。

1. 報告された入力で、失敗するテストを書く
2. 赤くなることを確認する(再現できた証拠)
3. コードを直す
4. 緑になることを確認する

2を飛ばさないでください。書いたテストが最初から緑なら、それはバグを再現できていません。再現できていない状態で直しても、直ったかどうか分かりません。

```python
def test_returns_zero_for_empty_list():
    # 報告: 注文0件で合計がエラーになる
    assert calc_total([]) == 0
```

このテストは、直したあともずっと残ります。次に誰かが同じ場所を壊したら、その場で赤くなります。**バグの数だけテストが増えていくのが、健全な育ち方** です。

## もっと知りたい人へ

- `pytest -x` を付けると、最初の失敗で実行を止めます。赤が大量に出て読みにくいときに便利です
- `pytest --lf`(last failed)は、前回失敗したテストだけを実行します。直しながら回すときに速くなります
