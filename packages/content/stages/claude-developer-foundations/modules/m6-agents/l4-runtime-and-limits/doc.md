# レッスン6-4 動かす場所と止まる条件

## このレッスンの目標

- [ ] 回数と費用の上限を決め、止まった理由ごとに結果を扱えます。
- [ ] ループとツールの運用をどこが担うかを見て、動かす場所を選べます。
- [ ] 監査で確かめたい手順と記録を決められます。

## 6-4-1 止まる条件を決める

> **エージェントには最大ターン数と予算の上限を決め、結果の種別を見てから結果を使います。**

棚卸しの集計で、商品一覧と倉庫の在庫表を順に読みます。ツールを使い終えて、Claude がツールを呼ばずに答えるとループが終わります。6-3-1 で見たように、`maxTurns` と `maxBudgetUsd` は指定しないと無制限です。回数には、ツールの結果を読んで最後に答えるターンの分も見込みます。

費用は、モデルの応答を受け取ったあとで `maxBudgetUsd` と照合します。上限に達した応答の費用も加わるので、設定額を超えることがあります。サブエージェントの費用も含み、動いていたサブエージェントが停止するまでの分もかかり得ます。運用で使える金額をもとに、余裕を取って設定します。

画面の表示は、最後に届く `ResultMessage` の `subtype`（結果の種別）で分けます。

| `subtype` | 実行の状態 | 画面に出すこと |
| --- | --- | --- |
| `success` | 正常に終了 | `result` の集計結果 |
| `error_max_turns` | ターン数の上限に到達 | 回数の上限で中断 |
| `error_max_budget_usd` | 予算の上限に到達 | 予算の上限で中断 |
| `error_during_execution` | 実行中にエラーや取り消しで停止 | 実行が中断したこと |
| `error_max_structured_output_retries` | 許された試行で有効な構造化出力を得られなかった | 所定の形式の出力を得られなかったこと |

`result` を持つのは `success` だけです。どの種別にも、`session_id`（セッション ID）、`total_cost_usd`（費用）、`num_turns`（ターン数）があります。途中まで進んだ実行もこれらを控え、停止した理由と合わせて追えるようにします。

## 6-4-2 動かす場所を選ぶ

> **自分で運用するなら Agent SDK、長時間の作業を任せるなら Managed Agents を選びます。**

6-1 で選んだ運用先を、誰がループと状態を持つかで比べます。

| 手段 | ループと状態を持つところ | 選ぶ条件 |
| --- | --- | --- |
| Messages API | アプリがループを書き、履歴を管理する | 呼び出しごとの細かい制御が要る |
| Agent SDK | 自社で運用するプロセスに Claude Code と同じループを組み込む | SDK のループを使い、実行基盤を自分で管理する |
| Managed Agents | Anthropic がループとセッションの基盤を運用する | 長時間や非同期の作業をサービスに任せる |

Agent SDK では、実行中の 1 セッションに 1 つのプロセスが対応し、状態はそのホストのディスクに置かれます。自社でホストを切り替えるなら、6-3-3 の保存先も運用の対象です。

Managed Agents では、「どう動くか」と「どこでツールを動かすか」を別々に設定できます。

| 要素 | 設定や記録の中身 |
| --- | --- |
| Agent | モデル、システムプロンプト、ツール、MCP サーバー、Skill（作業手順や知識のまとまり）。設定には版がある |
| Environment | サンドボックス（ツールを動かす隔離環境）の設定 |
| Session | Agent と Environment を指定して始める、案件ごとの作業 |
| Events | 依頼や処理結果、進み具合をアプリとセッションの間でやり取りする記録 |

既定のクラウド環境では、セッションごとに Anthropic が新しいコンテナーを用意します。社内の台帳を自社管理の場所で読む必要があれば、サンドボックスを自社基盤で運用します。その場合も Claude とループは Anthropic 側で動き、会話とツール結果は Anthropic に届きます。Anthropic がループを運用するこの構成は、ZDR（データを保持しない契約）と HIPAA（米国の医療情報保護に関する要件）の対象外です。

Agent SDK の `maxTurns` を移す場合、Managed Agents ではアプリ側でターンを数えます。予算はセッションに設定できます。組み込みツールと MCP の許可は、ツールごとの使い方に合わせます。

| 許可の方針 | 実行の判断 |
| --- | --- |
| `always_allow` | 自動で実行する |
| `always_ask` | 人の確認を待ってから実行する |
| `auto` | サーバーが呼び出しごとに実行・拒否・確認待ちを判断する |

必ず人が確認する対象には `always_ask` を選びます。独自ツールはアプリで実行するので、承認が要るなら呼び出しのイベントを受けたアプリで扱います。

## 6-4-3 監査が要るなら手順を固定する

> **監査や誤りの許容度が厳しい業務は、手順を固定したワークフローにします。**

監査では、業務が決められた規程どおりに進んだかを記録から確かめます。経費申請で領収書を照合してから集計する決まりがあれば、6-2 のようにコードで段の順序を決めます。説明するときに備え、各段で用いた入力と結果も残します。

| 段 | あとで確かめたいこと |
| --- | --- |
| 領収書を照合する | どの証票とどの明細を照合したか |
| 金額を集計する | 照合済みのどの明細を合計に入れたか |
| 担当者に報告する | どの版の規程を使い、何を報告したか |

調査先や次の手順が案件ごとに変わる仕事では、エージェントにその場の判断を任せられます。費用と誤りが積み重なり得るので、止まる条件を決め、隔離した環境で許す操作を絞って試します。

複数のエージェントは、広い範囲を独立して調べられ、費用に見合う価値がある仕事で検討します。トークンの使用量は 1 つで動く場合の数倍になることがあります。同じ変更の前提を共有する作業や、互いの結果を待つ作業では調整が増えます。
