# 解説

5xx だけを警報にすると、429、400、413、認証の失敗と、HTTP 200 の拒否・上限・空の応答・形の崩れが残りません。ステータスを先に見るのは、400 の応答に停止理由が混ざっていても、リクエストを直す操作にするためです。

429 は待ってから送り直せます。500 と 529 は間隔を空けて送り直せます。400 と 413 は本文か大きさを直すまで同じリクエストでは通りません。拒否は同じモデルへ送り直しても原因が残るので、別のモデルへ回します。上限は量を増やすか続きを受け取ります。`pause_turn` は成功した応答ですが、assistant の内容を変えずに送り直すのはアプリのループなので、層は integration です。

空の `end_turn` は、出力が上限に届いたのではありません。ツール結果の直後にテキストを足すと、履歴が「ツールのたびに利用者の発言がある」形になり、モデルは自分の番が終わったと判断して空で返すことがあります。上限を上げても、その履歴は残ります。直す場所はメッセージの組み立てです。

JSON として読めない本文は、モデルが前置きを足した結果です。アプリ側で正規表現を足すより、構造化出力で形を指定します。空で、かつツール結果のあとにテキストがある記録は、形の問題より先に組み立ての問題にします。

別解として `errorType` の文字列で分ける方法があります。この課題ではステータスが正本です。401 と 403 は種類の名前が違っても、資格情報を直す操作は同じです。
