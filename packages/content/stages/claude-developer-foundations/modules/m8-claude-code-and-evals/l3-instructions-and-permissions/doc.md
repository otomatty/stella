# レッスン8-3 約束と権限を重ねる

## このレッスンの目標

- [ ] どの CLAUDE.md がいつ読み込まれるかを説明できます。
- [ ] 対象のファイルだけにルールを読み込ませる設定を書けます。
- [ ] 権限のルールが重なったときの結果を判定し、作業に合うモードを選べます。

## 8-3-1 CLAUDE.md は重ねて読まれる

> **複数の場所にある CLAUDE.md は、広い範囲から順に重ねて読み込まれます。**

注文管理のリポジトリでは、会社の約束、チームの手順、自分だけのメモを別々に置けます。

| 読む順 | 置き場所 | 書くことの例 |
| --- | --- | --- |
| 1 | 組織が管理する CLAUDE.md | 社内の作業記録に必要な項目 |
| 2 | `~/.claude/CLAUDE.md` | 自分の全プロジェクトで使う書き方 |
| 3 | `./CLAUDE.md` または `./.claude/CLAUDE.md` | チームで使うテストの手順 |
| 4 | `./CLAUDE.local.md` | このプロジェクトだけで使う手元の試験データ |

起動時は上のディレクトリから作業ディレクトリまでをたどり、各階層で共有の指示を読んだあとにローカルの指示を足します。リポジトリ直下で起動した場合、`orders/CLAUDE.md` は、注文のファイルを初めて読んだり編集したりする時点で加わります。

読み込んだ文章は Claude への指示になります。前の指示も残るので、同じ作業について食い違う記述があれば、両方を見直します。1 ファイルは 200 行より短く保ちます。たとえば `@docs/order-workflow.md` と書くと、別のファイルを取り込めます。取り込んだ文章もコンテキストを使います。

## 8-3-2 ファイルで絞る約束

> **特定のファイルにだけ効かせたい約束は、パスを指定したルールファイルに書きます。**

在庫のテストでだけ「在庫が 0 件の例を含める」と伝えたいとします。`.claude/rules/inventory-tests.md` に次のように書きます。

```markdown
---
paths: ["tests/inventory/**/*.test.ts"]
---
在庫が 0 件の例を含めてください。
```

`paths` に書く glob は、ファイルのパスをまとめて表す書き方です。この例では `tests/inventory/` 以下の `.test.ts` が対象です。Claude が一致するファイルを読むか編集すると、そのルールを読み込みます。

`.claude/rules/` 以下の Markdown はサブディレクトリも読み込みの対象です。`paths` の指定がないファイルは、`.claude/CLAUDE.md` と同じ扱いで起動時に読み込みます。ユーザーの `~/.claude/rules/` は、プロジェクトのルールより先に読みます。

会話を圧縮すると、プロジェクト直下の CLAUDE.md とパス指定のないルールは、ディスクから読み直されます。会話での指示、パス指定のあるルール、サブディレクトリの CLAUDE.md は、会話のほかの内容とともに要約されます。後ろの 2 つは、対象のファイルを再び扱うと読み直されます。

## 8-3-3 拒否が先に決まる

> **権限のルールは拒否・確認・許可の順に判定され、拒否が最優先です。**

チームでは公開用のコマンドをまとめて止めています。担当者は、試験用の公開だけ許可するルールを自分の設定に足しました。

| 設定ファイル | ルールの種類 | 一致する条件 |
| --- | --- | --- |
| `.claude/settings.json` | `deny`（拒否） | `Bash(npm run publish-*)` |
| `.claude/settings.local.json` | `allow`（許可） | `Bash(npm run publish-preview)` |

一覧の項目は設定ファイルをまたいで足されます。`npm run publish-preview` は両方に一致しますが、`deny` が先に決まるので実行は拒否されます。次に調べるのは、`ask`（確認）、`allow`（許可）の順です。たとえば、拒否に一致せず確認と許可の両方に一致した操作は、人の確認に進みます。

ルールの条件の細かさで順序は変わりません。どの設定に書いた拒否も、別の場所の許可や権限モードで取り消すことはできません。`deny` に `Bash` のようにツール名だけを書くと、Claude の候補からそのツール自体が外れます。

## 8-3-4 権限モードを選ぶ

> **権限モードは、作業の危険度に合わせて選びます。**

権限モードは、各操作でどこまで人の確認を求めるかを決めます。調査、実装、自動実行で同じモードを使う必要はありません。

| モード | どう動くか | 選ぶ場面 |
| --- | --- | --- |
| `default`（Manual） | 編集や多くのコマンドの前に確認する | 初めて触るリポジトリで一つずつ確認する |
| `acceptEdits` | 編集や一部のファイル操作を確認なしで行う | 方針を確認したうえで、編集を繰り返す |
| `plan` | ソースを編集せずに調査して計画を作る | 実装前に影響を調べる |
| `auto` | 別のモデルが操作を分類し、通すかを審査する | 確認の回数を減らしつつ、操作の審査を続ける |
| `dontAsk` | 確認が必要な操作を拒否する | CLI で人が待機しない検査を行う |
| `bypassPermissions` | 通常の権限確認を省く | 他の作業から隔離したコンテナーや VM の中でだけ使う |

CLI の起動時は `--permission-mode` で指定できます。設定ファイルで既定を選ぶ項目は `permissions.defaultMode` です。共有とローカルのプロジェクト設定に書いた `auto` と `bypassPermissions` は、既定のモードにはなりません。`bypassPermissions` を使う場合は、起動時に有効にします。

`auto` ではモデルが操作を審査します。発生を必ず防ぎたい操作は、前に学んだ拒否のルールか、ツールの実行前に止めるフックで制限します。
