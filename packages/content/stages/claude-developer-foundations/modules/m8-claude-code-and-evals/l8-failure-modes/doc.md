# レッスン8-8 失敗の種類から原因を探す

## このレッスンの目標

- [ ] HTTP ステータスと停止理由から、最初に調べる場所を選べます。
- [ ] 提案止まり、履歴の欠落、出力形式の崩れを調べられます。
- [ ] 実行記録と実際の結果から、修正すべき場所を選べます。

## 8-8-1 どの層の失敗かを分ける

> **失敗は、まず HTTP のエラーか、成功した応答の中身かで分けます。**

配送案内の返答が途中で切れました。障害モードとは、こうした失敗の現れ方を表す種類です。
まず HTTP ステータスを見て、アプリと API の間でリクエストが失敗したかを調べます。
HTTP 4xx・5xx のときはエラー情報を読み、M2 の扱いに沿って入力の修正や送り直しを選びます。

HTTP 200 のときは、1-3 で学んだ `stop_reason` と応答の中身を見ます。
`refusal` は安全の仕組みによる拒否、`max_tokens` は出力が上限に届いて止まった印です。
5xx だけを監視していると、どちらも数えられません。
監視では HTTP エラーと停止理由を分け、拒否は独立した信号として数えます。

`end_turn` で応答が終わっていても、回答の内容は確かめます。
たとえば資料にない配送日なら、7-2 で学んだように、回答を原文と照合します。

## 8-8-2 提案で終わってしまう

> **実行してほしいときは、依頼に実行する操作を明記します。**

手順書の「修正案を出せますか」と依頼すると、変更の候補が返ることがあります。
実施を期待していたのに提案などで止まることを、行動不足と呼びます。
編集用のツールが利用できるなら、まずモデルに届いた依頼を読みます。

| 依頼したかったこと | 依頼の書き方 |
| --- | --- |
| 変更案の検討 | 配送手順の受付時刻を変える案を出してください |
| 変更の実施 | delivery.md の受付時刻を 16 時に変更してください。編集した箇所を知らせてください |

実行を指定しても変わらない場合は、編集ツールの呼び出しや権限の判定を調べます。
完了はツールの結果やファイルの差分で確かめます。

## 8-8-3 前の指示を忘れる

> **途中の指示が消えたら、圧縮や削除で外れていないかを履歴で確かめます。**

前の応答では使えた条件が、後の応答で使えなくなることを、コンテキストの喪失と呼びます。
たとえば圧縮のあとだけ配送の締切を誤るなら、元の会話とモデルに届いた履歴を比べます。
ハーネス（実行を管理するアプリ側）の履歴の組み立てや、API のコンテキストの編集を調べます。

| 順 | 確かめること | 直す場所 |
| --- | --- | --- |
| 1 | 圧縮結果を入れ忘れたか、置く場所を誤ったか | 以前の履歴を置き換えるとき、返ったブロックをそのまま先頭に置く |
| 2 | 圧縮で必要な画像や文書が外れたか | 後のターンで要る資料を再度渡す |
| 3 | 途中の指示が要約から漏れたか | 要約で残す条件を指定するか、必要な指示を改めて入れる |
| 4 | コンテキストの編集で古いツール結果が削除されたか | ツール結果を残す範囲を調整する |

たとえば、圧縮結果そのものが抜けていたら、アプリの履歴の組み立てを直します。
`max_tokens` を上げると出力に割ける量が増えます。履歴から外れた情報は戻りません。

## 8-8-4 形が崩れてくる

> **出力の形が崩れるなら、構造化出力で必要な形を指定します。**

配送記録から一定の項目を取り出して集計するとします。
前置きが付いたり、応答ごとに項目名が変わったりすると、集計で読めないことがあります。
期待する形から出力が外れる現象を、フォーマットのドリフトと呼びます。

プログラムで読むデータには 4-2-1 の構造化出力を使い、項目名・型・必須項目を指定します。

| 必須の項目 | 指定する形 |
| --- | --- |
| `deliveryId` | 文字列 |
| `status` | `shipped` または `pending` |

返ったデータは 4-2-2 で学んだとおり、停止理由を確かめてから読みます。
人が読む報告の見出しや書きぶりをそろえたいときは、4-1-2 のように完成例を添えます。

## 8-8-5 原因のある場所を直す

> **対策は、失敗の原因がある場所に合わせて選びます。**

トランスクリプトは、入力・ツール呼び出し・応答を順に追える記録です。
どこで期待と食い違ったかをたどり、原因のある場所で修正します。

| 障害モード | 見え方 | 原因の層 | 直す場所 |
| --- | --- | --- | --- |
| ハルシネーション | 資料にない配送日を断定する | 回答の根拠 | 不明と返すことを認め、根拠の引用を先に抜き出し、回答に出典を付ける（7-2-1、7-2-2） |
| 拒否 | HTTP 200 で `refusal` が返る | モデルの安全判定 | 途中までの出力を捨てて拒否として記録し、想定内の入力なら別のモデルに回す（1-3-3） |
| 行動不足 | 編集の提案だけが返り、ファイルが変わらない | 依頼の動詞 | 対象と実行する操作を明記する |
| コンテキストの喪失 | 圧縮後に前の条件が使われない | 入力履歴の組み立て | 圧縮ブロック、資料、指示、ツール結果を順に調べる |
| フォーマットのドリフト | 項目名や出力の形が外れる | 出力形式の指定 | 集計用のデータを構造化出力にする |
| 一貫性のない出力 | 形は同じでも同じ配送を別の状態と判断する | 判断基準や参照資料 | 形式と判断例を示し、同じ資料を参照させ、複雑なら根拠抽出と判断に分ける |

同じ入力でも、判定が毎回同じになるとは限りません。
一貫性を直すときは同じ入力で複数回実行し、基準に合った結果が続くかを見ます。

停止理由に応じて、アプリの処理も直します。

- `max_tokens` で文章が途切れたら、上限を上げるか続きを求めます。不完全な `tool_use` なら実行前に、上限を上げて送り直します。
- 空の `end_turn` なら、ツール結果直後のテキストや、完了応答をそのまま再送していないかを調べます。原因があればメッセージの組み立てを直します。
- `refusal` は拒否として処理します。同じモデルへの送り直しを繰り返しても、拒否の原因は解消されません。

「保存しました」という応答で評価が合格しているのに、データベースに行がないこともあります。
記録からツールに渡った入力を確認し、データベースも調べます。
保存の成否をメッセージだけで採点していた場合は、採点器を直して同じ評価を回します。
