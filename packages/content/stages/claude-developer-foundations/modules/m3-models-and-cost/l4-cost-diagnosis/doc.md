# レッスン3-4 費用の原因を見つけて直す

## このレッスンの目標

- [ ] 資料の更新頻度と会話の伸び方に合わせて、キャッシュの区切りを置けます。
- [ ] 読み込みが減ったときに調べる場所を選び、修正の効果を確かめられます。
- [ ] 使用量の内訳から費用を計算し、金額の大きい項目に効く手段を選べます。

## 3-4-1 変わる頻度で区切る

> **変わる頻度の違う部分は、それぞれの終わりにキャッシュの区切りを置きます。**

施設の貸出窓口では、共通のツールと指示で、契約先ごとの利用条件を調べます。資料の改訂は日に数回で、同じ版に違う質問が何度も届きます。質問の末尾にだけ区切りを置いていたため、質問の違いで前回の書き込みと一致しません。資料の末尾まで一致していても、そこには読み込める記録がありません。

期限を延ばしても、質問が違えばキャッシュは一致しません。小さいモデルに替えたり指示を削ったりすると、応答の挙動も変わります。この例では、送る内容を保ったまま区切りの位置を直します。

| リクエストの順序 | 変わる頻度 | 区切りの位置 |
| --- | --- | --- |
| ツールの定義 → 共通の指示 | ほぼ変わらない | 指示の末尾 |
| 契約先の資料 | 日に数回 | 資料の末尾 |
| 今回の質問 | 毎回 | 置かない |

同じ版への質問が続けば、資料まで読み込めます。資料を改訂した最初のリクエストでは、指示の末尾までを読み込み、更新分を書き込みます。両方の区切りまでの長さが、モデルの必要とする最低の長さを満たす例です。区切りは最大 4 つで、置くこと自体に料金はかかりません。

試験ガイドでは、3-2 で扱った区切り 1 つの置き方を「単一」、更新頻度の違う部分に複数置く方法を「階層型」と呼びます。次の、会話の末尾を追う方法は「ローリング」です。

## 3-4-2 伸びる会話を追いかける

> **伸びていく会話では、最後のブロックに区切りを置いて、前のターンまでを読み込みます。**

修理の受付では、機種を尋ねたあとに症状を聞きます。先に送ったブロックを変えずに、応答と次の発言を後ろに足すため、前回のリクエスト全体が今回の前半に残ります。有効期間内で、各区切りまでの長さは足りているとします。

| ターン | 今回の区切り | 読み込みと書き込み |
| --- | --- | --- |
| 1 | 8 番 | 8 番までを書き込む |
| 2 | 13 番 | 8 番までを読み、9〜13 番を追加で書き込む |
| 3 | 34 番 | 34〜15 番を調べるため、13 番の記録を見つけられない |

読み込みでは、区切り自身を含めて最大 20 か所をさかのぼります。1 ターンで足すブロックが 20 未満なら、前回の位置が探索範囲に残ります。この例のターン 3 では、前回の 13 番にも区切りを残すと、そこから読み込めます。

自動キャッシュを使うと、リクエストの最上位に `cache_control: { type: "ephemeral" }` を指定するだけで、キャッシュできる最後のブロックに区切りが進みます。最大 4 つのうち 1 つを使い、探索範囲は同じです。毎回作り直す質問と、前の質問が履歴に残る会話とで、どこまでが同じかを確かめて使います。

## 3-4-3 外れた原因を探す

> **キャッシュが読まれないときは、区切りより前に毎回変わる値がないかを先に調べます。**

点検の案内を 10 秒おきに送り、`usage` を確かめます。毎回書き込みがあるのに読み込みが 0 なら、まず前回と今回で区切りまでの内容を比べます。点検アプリでは、最近足した現在時刻が `system` の先頭にありました。時刻を区切りの後ろに移し、読み込みが増えるかを確かめます。乱数やその回だけの発言を前半に入れたときも同じ手順で調べます。

| 変えたもの | 読み込めなくなる範囲 |
| --- | --- |
| ツールの定義 | ツールの定義・指示・会話のすべて |
| `tool_choice` や画像の有無 | `messages` |
| 考える過程の設定 | `messages`。モデルによってはツールの定義や指示も含む |
| `output_config.format` | その会話のプロンプトキャッシュ |

API のキャッシュの診断を使うと、比較する場所を絞れます。最初のリクエストで `diagnostics.previous_message_id` を `null` にして診断を有効にします。次はそこに前回の**応答の `id`** を渡します。`system_changed` なら指示を、`tools_changed` ならツールの定義を見ます。モデルや会話の履歴が違うことも分かります。診断は入力の差を示し、実際に読み込んだ量は `usage` で確かめます。

同じ前半が続くのに読まれないときは、前回の書き込みの有無、区切りの距離、送信間隔を確認します。読み込みと書き込みがともに 0 なら、3-2-3 と同じように最低の長さも確認します。最低の長さはモデルによって 512〜4,096 トークンで、足りなくてもエラーにはなりません。数秒おきに一致する前半を読むなら、5 分の期限は読み込むたびに無料で延びます。1 時間に延ばすと書き込みの単価が上がります。

## 3-4-4 いちばん大きい費用から直す

> **使用量の内訳でいちばん大きい項目を見つけ、その項目に効く手段を選びます。**

問い合わせ 1,000 件を、通常入力 100 万トークンあたり 1 ドルと仮定して計算します。表のトークン数は 1,000 件の合計です。出力は入力の 5 倍、キャッシュ読み込みは 0.1 倍のモデルとします。

| `usage` の項目 | トークン | 倍率 | 1,000 件の費用 |
| --- | ---: | ---: | ---: |
| `input_tokens`（通常入力） | 800 万 | 1 | 8.00 ドル |
| `cache_creation_input_tokens`（5 分の書き込み） | 80 万 | 1.25 | 1.00 ドル |
| `cache_read_input_tokens`（読み込み） | 100 万 | 0.1 | 0.10 ドル |
| `output_tokens`（出力） | 40 万 | 5 | 2.00 ドル |
| 合計 |  |  | 11.10 ドル |

いちばん大きい通常入力の 800 万トークンのうち、600 万が繰り返し送る資料だと分かりました。区切りを直して、資料の 60 万が新規の書き込み、540 万が読み込みになったとします。資料の 6 ドルは、5 分の書き込み `0.60 × 1.25` と読み込み `5.40 × 0.1` を合わせた 1.29 ドルに下がります。全体は 6.39 ドルで、1,000 件あたり 4.71 ドル減ります。同じ 60 万トークンの書き込みを 1 時間の倍率 2 で計算すると、その分だけで 0.45 ドル高くなります。

| 内訳と処理の条件 | 試す手段 |
| --- | --- |
| 通常入力に繰り返し送る前半が多い | 区切りを置き、書き込みと読み込みの量を測り直す |
| 大量に処理し、結果を待てる | バッチで入力・出力とも 50% 引き。キャッシュの倍率とも重なる |
| 出力の費用が大きい | effort を下げるか、答えの長さを指定して、必要な情報が残るかを評価する |

たとえば表と同じ内訳をバッチでも得られた場合、変更前の 11.10 ドルは 5.55 ドルになります。バッチでのキャッシュの命中は保証されないため、移行後の実際の内訳でも見積もります。出力では、長いコーディング作業で `high` から `medium` にして費用が約 3〜5 割下がった測定例があります。自分の処理では、出力の費用と品質を一緒に測ります。`max_tokens` は途中で出力を切る上限で、モデルはこの上限に合わせて回答を組み立てず、切れた応答にも使った分の料金がかかります。

エージェントが何度も同じ履歴を送る処理では、入力 3 項目の合計に占める読み込みの割合も見ます。実運用の測定では、入力の 8 割以上を読み込む例が多くありました。割合が落ちたら、使用量と合わせて、いつから前半を使い回せなくなったかを調べます。
