# レッスン3-2 プロンプトキャッシュ

## このレッスンの目標

- [ ] プロンプトキャッシュが得になる場面と、料金の仕組みを説明できます。
- [ ] キャッシュが効く順にプロンプトを並べ、cache_control を正しい位置に付けられます。
- [ ] 応答の usage から、キャッシュが効いたかを確かめられます。

## 3-2-1 同じ前半を使い回す

> **毎回同じ前半のプロンプトは、プロンプトキャッシュで使い回します。**

プロンプトキャッシュは、プロンプトの前半を処理した結果を一時的に覚えさせ、次のリクエストで使い回す仕組みです。使い回した部分は、処理の時間も費用も小さくなります。次のような場面に向きます。

- 例をたくさん入れたプロンプト
- 長い資料や背景の情報
- 同じ指示で繰り返す作業
- 長く続く会話

使い回す前半の終わりのブロックに、`cache_control` を付けます。

```js
const message = await client.messages.create({
  model,
  max_tokens: 1024,
  system: [{ type: "text", text: manual, cache_control: { type: "ephemeral" } }],
  messages: [{ role: "user", content: question }],
});
```

リクエストが届くと、`cache_control` を付けたブロックまでの前半が最近キャッシュされたかを確かめます。あれば読み込んで使い、なければ全部を処理して、応答が始まった時点で前半をキャッシュに書き込みます。

キャッシュの期限は既定で 5 分です。キャッシュが使われるたびに、追加の費用なしで期限が延びます。5 分では短いときは、追加の料金で 1 時間にできます(`cache_control: { type: "ephemeral", ttl: "1h" }`)。

料金は、通常の入力の料金に次の倍率をかけたものです。

| 種類 | 倍率 |
| --- | --- |
| キャッシュの書き込み(5 分) | 1.25 倍 |
| キャッシュの書き込み(1 時間) | 2 倍 |
| キャッシュの読み込み | 0.1 倍(Claude Opus 5.5・Claude Sonnet 5.5 は 0.05 倍、Claude Fable 5.1 は 0.025 倍) |

書き込みは通常より高く、読み込みはずっと安いので、同じ前半を 2 回以上使うときに得になります。この倍率は Message Batches API の割引とも重なります。

## 3-2-2 変わる部分は後ろに置く

> **キャッシュは前から一致した部分に効くので、変わる部分は後ろに置きます。**

キャッシュは、`tools`・`system`・`messages` の順に並べたプロンプトの前半について、`cache_control` を付けたブロックまでが一致しているかで決まります。途中の 1 か所でも違えば、そこから後ろは使い回せません。そのため、次の順に並べます。

| 位置 | 置くもの |
| --- | --- |
| 前 | ツールの定義・指示・資料・例など、毎回同じもの |
| キャッシュの区切り | 毎回同じ部分の、最後のブロックに `cache_control` を付ける |
| 後ろ | 今の時刻・利用者ごとの情報・質問など、毎回変わるもの |

`cache_control` を付けた位置を、キャッシュの区切りと呼びます。キャッシュに書き込まれるのは区切りの位置だけです。よくある誤りは、毎回変わるブロックに区切りを置くことです。

```js
// 誤り: 時刻を含む質問に区切りを置くと、毎回書き込みになり、読み込みが起きない
{ role: "user", content: [{ type: "text", text: `${now}\n${question}`, cache_control: { type: "ephemeral" } }] }
```

この場合は、毎回同じ部分の最後(たとえば資料のブロック)に区切りを移します。リクエストの一番上に `cache_control` を 1 つ書くと、最後のブロックに自動で区切りを置く書き方もあります。会話が伸びるたびに区切りが進むので長い会話に向きますが、最後のブロックが毎回変わる並べ方では同じ誤りになります。

区切りは 1 つのリクエストに 4 つまで置けます。変わる頻度の違う部分(ツールの定義・指示・会話)を分けてキャッシュしたいときに使います。

前のほうを変えると、そこから後ろのキャッシュはすべて使えなくなります。たとえばツールの定義を変えると、system と messages のキャッシュも使えなくなります。

## 3-2-3 キャッシュの効きを確かめる

> **キャッシュが効いたかは、応答の usage の値で確かめます。**

`usage` は、応答に付いてくるトークン数の内訳です。ストリーミングでは `message_start` のイベントに入ります。入力については次の 3 つを見ます。

| 値 | 意味 |
| --- | --- |
| `cache_read_input_tokens` | キャッシュから読み込んだトークン数 |
| `cache_creation_input_tokens` | 今回キャッシュに書き込んだトークン数 |
| `input_tokens` | 最後の区切りより後ろの、キャッシュに関わらないトークン数 |

`input_tokens` は入力全体ではありません。入力の合計は 3 つの和です。

```js
const { usage } = message;
const totalInput =
  usage.cache_read_input_tokens + usage.cache_creation_input_tokens + usage.input_tokens;
```

`cache_read_input_tokens` と `cache_creation_input_tokens` がどちらも 0 なら、キャッシュされていません。よくある理由は、前半が短すぎることです。キャッシュできる最低の長さはモデルごとに決まっていて、Claude Opus 5.5・Claude Sonnet 5.5・Claude Haiku 5.5 では 512 トークンです。短い前半に `cache_control` を付けても、エラーにはならず、キャッシュされないまま処理されます。

キャッシュは、書き込んだリクエストの応答が始まってから使えるようになります。同じ前半のリクエストを並べて送るときは、最初の応答が始まるのを待ってから残りを送ります。
