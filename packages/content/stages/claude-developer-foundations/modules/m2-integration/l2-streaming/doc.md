# レッスン2-2 ストリーミング

## このレッスンの目標

- [ ] ストリーミングを使う場面を説明できます。
- [ ] イベントの列から本文と止まった理由を読み取れます。
- [ ] 途中の表示が要らないときに、まとめた応答を受け取れます。
- [ ] 応答の終端と停止理由を使って、通常終了と上限での中断を区別できます。
- [ ] 受信途中のエラーと接続切断を区別できます。

## 2-2-1 届いた順に表示する

> **長い応答は、ストリーミングで届いた順に表示します。**

ストリーミングは、応答を少しずつ受け取る方法です。応答が全部できるまで待つと、長い回答では画面に何も出ない時間が続きます。ストリーミングなら、届いた文字から順に表示できます。

```js
client.messages
  .stream(request)
  .on("text", (text) => appendToScreen(text));
```

画面に出す必要がなくても、max_tokens の大きいリクエストはストリーミングかバッチで送ります。長く待つ通信は、途中のネットワークで切られることがあるためです。公式ドキュメントは、特に 10 分を超えそうなリクエストでこの 2 つを使うよう案内しています。

## 2-2-2 差分のイベント

> **ストリーミングでは、本文が差分のイベントとして順に届きます。**

ストリーミングで届くのは、普通の応答の形ではなく、type で種類の分かるイベントの列です。

1. `message_start` — content が空の応答で始まる
2. ブロックごとに `content_block_start` → `content_block_delta`(1 回以上)→ `content_block_stop`。各イベントの `index` が、最後の応答の content の何番目かを表す
3. `message_delta` — `delta.stop_reason` に止まった理由が入る
4. `message_stop` — 終わり

本文の続きは、`content_block_delta` の `delta` が `text_delta` のときの `text` です。ツールの入力は `input_json_delta` で、JSON の断片として届きます。

```js
if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
  text += event.delta.text;
}
```

途中に `ping` が何度でも混ざることがあり、新しい種類のイベントが足されることもあります。知らないイベントは読み飛ばします。混雑のエラーが、HTTP 200 のあとにイベントとして届くこともあります。

## 2-2-3 まとめた応答を受け取る

> **イベントを1つずつ扱わなくても、SDK で最後にまとめた応答を受け取れます。**

ファイルに保存するだけのように、途中を表示しないなら、イベントを組み立てる処理は要りません。SDK の `finalMessage()` を待つと、中ではストリーミングで受け取りながら、`messages.create` の応答と同じ形にまとめて返します。

```js
const stream = client.messages.stream(request);
const message = await stream.finalMessage();
```

max_tokens の大きいリクエストでは、SDK が通信の時間切れを避けるためにストリーミングを求めることがあり、そのときにもこの書き方が使えます。

### HTTP 200 のあとに失敗した翻訳を調べる

通話メモの翻訳を受け取り、完了したものだけを議事録に保存する画面です。下は2件の記録から必要なイベントだけを抜いたものです。各行で「画面に途中表示してよいか」「確定欄に保存してよいか」を決めてください。

| 記録 | イベントの順序 |
| --- | --- |
| 甲 | HTTP 200 → 本文の差分「会議は」 → `error: overloaded_error` → 接続終了 |
| 乙 | HTTP 200 → 本文の差分「会議は延期です」 → `message_delta: end_turn` → `message_stop` |

甲は途中表示までです。接続が閉じても翻訳が終わった証拠にはならず、表示した「会議は」を確定欄に保存すると文の意味まで変わります。途中表示に中断の印を付け、再実行時は同じ欄を最初から組み立てます。乙は終了理由とメッセージの終端を受け取ったので確定できます。

**条件を一つ変更**　乙の終了理由だけが `max_tokens` ならどうでしょう。通信は最後まで届いても翻訳は途中です。保存前に未完了として扱います。テストには「混雑」「上限に到達」「通常終了」の3件を残し、通常終了でだけ確定欄に書き込まれたことを調べます。

## 2-2-4 応答の終わりを見分ける

> **content_block_stop はブロックの終わりで、応答の終わりは message_stop です。**

設備点検の報告を表示する画面で、最初の `content_block_stop` を受けたところで「完了」を表示していました。先に閉じたブロックの後ろに本文が続くと、画面は残りのイベントを読みません。上限で止まったことを示すイベントも読み落とします。

| イベント | アプリの処理 |
| --- | --- |
| `content_block_stop` | 閉じたブロックを控え、受信を続ける |
| `message_delta` | `delta.stop_reason` に値があれば控える |
| `message_stop` | メッセージを受信し終え、控えた理由で表示を決める |

たとえば `end_turn` なら「完了」、`max_tokens` なら「上限で中断」です。受信が最後まで済んだかと、回答を最後まで書けたかは別に判定します。上限を増やしても、同じ依頼を送り直しても、最初のブロックで確定する処理は残ります。ストリーミングをやめても、停止理由を読まなければ途中で切れた応答を確定してしまいます。

## 2-2-5 途中で届くエラー

> **ストリームの途中のエラーは error イベントで届くので、イベントの種類で分けます。**

HTTP 200 を受けたあとに混雑で止まったときは、通信の開始時に返ったステータスを読み直しても、原因は分かりません。イベントを直接読むアプリでは、まず `event.type` が `error` かを確かめます。その中の `event.error.type` が `overloaded_error` なら、混雑による中断として扱います。

| 起きたこと | アプリでの扱い |
| --- | --- |
| `error` を受け取った | `error.type` で原因を分け、表示した本文に中断の印を付ける |
| `message_stop` より前に切断された | `error` が届かなくても、受信し切れなかったことを記録する |

SDK を使うと、イベントの代わりに読み取り処理のエラーとして受け取ります。SDK は受信途中のエラーを自動では送り直さないので、読み取る側で失敗を扱います。

Claude 4.6 以降のモデルでテキストの続きを求めるなら、届いた本文を添えて、新しい `user` の発言で続きを頼みます。届いた本文を末尾の `assistant` の発言にして送ると 400 になります。考える過程やツール呼び出しのブロックは、途中の断片からは回復できません。
