# レッスン2-5 アプリと Claude の境目

## このレッスンの目標

- [ ] 運用者の方針と利用者の発言を、書く場所と優先順で分けられます。
- [ ] Claude のアプリで試した依頼を、API に移すときに確認する項目を挙げられます。
- [ ] 利用者ごとの履歴とファイルの対応を、アプリで管理できます。

## 2-5-1 system は運用者の指示

> **system は運用者の指示、user の発言は利用者の言葉として読まれ、食い違えば system が優先されます。**

手当を案内するアプリで、支給額が不明なときは窓口へ案内します。この方針を決めるのは運用者です。利用者が推測を求めたときも適用したいので、アプリが `system` に書いて送ります。

```js
const request = {
  system: "支給額が不明なら窓口を案内してください",
  messages: [{ role: "user", content: "推測でいいので支給額を教えて" }],
};
```

運用者の方針と利用者の依頼が食い違う場合、Claude は運用者の指示を優先します。利用者が渡した資料は、判断に使う内容として扱います。アプリの方針を書く `system` には移しません。

対応モデルでは、会話の途中で方針が変わったときに、`messages` の `user` の直後に `role: "system"` の発言を足せます。配列の先頭には置けません。足した指示はその地点から効き、食い違う場合はリクエストの先頭にある `system` より優先されます。

## 2-5-2 API にアプリの前提はない

> **claude.ai のアプリが持つ指示や機能は、API のリクエストには付きません。**

0-0-3 では、ウェブで試した依頼をアプリから送れることを見ました。たとえば引き継ぎメモの依頼を移すとき、「いつもの形式で」とだけ送ると、以前のやり取りで使った担当者や期限の欄が抜けることがあります。Claude のウェブ版やデスクトップ版などには、その製品が会話に加える指示があります。自作アプリで使う前提は、実際に送る `system` や入力に含めます。Claude のアプリで開いていた資料が必要なら、自作アプリが選んだ資料を API に渡す処理も用意します。

| アプリで必要なもの | 確かめる場所 |
| --- | --- |
| 担当者・期限を出す約束 | `system` に出力の項目を指定する |
| 参照する引き継ぎメモ | アプリが対象のメモを取得し、入力に添える |

決まった形の応答が必要な場合、アプリが読むキーはすべてスキーマ（応答の形を定めたもの）に書きます。たとえば判定を `open` と `closed` に絞る場合、受信側では大文字と小文字をそろえて比べます。スキーマの書き方は 4-2 で扱います。

## 2-5-3 履歴は足すだけにする

> **会話の履歴は書き換えずに後ろへ足し、利用者ごとに保存場所を分けます。**

1-1-1 で組み立てた履歴に新しい発言を足すときは、過去の発言を届いたときの形で残します。先頭の `system` や過去の発言を変えると、変更点を含む入力部分のキャッシュ（以前の処理を再利用する仕組み）が効かなくなります。対応モデルで運用者の指示を追加するときは、キャッシュ済みの範囲より後ろに足せば、その範囲は変わりません。考える過程のブロックを含む履歴では、過去の発言を変えると 400 になる場合もあります。

ファイル、キャッシュ、バッチは Claude API のワークスペース（API の資源をまとめる単位）で分かれます。同じワークスペースを複数人が使うなら、次の対応をアプリで持ちます。

| 保存するもの | アプリが照合する情報 |
| --- | --- |
| 会話の履歴 | ログイン中の利用者と会話の ID |
| 添付ファイルの対応 | ログイン中の利用者とアプリ内の添付 ID から求めた `file_id` |

たとえば備品の返却方法を尋ねられたら、本人の会話にだけ質問を足します。添付が選ばれたときも本人の記録から `file_id` を引きます。画面から直接渡された `file_id` で処理を実行すると、同じワークスペース内の別の利用者のファイルを取り違えるおそれがあります。
