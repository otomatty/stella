# 5-1-1
# テストがないと本番に出せない

Salesforce開発入門 — Module 5 / レッスン5-1

<!-- ノート: Module 5の始まりです。他の基盤と違い、テストが「推奨」ではなく「関門」になっている点を最初に置きます。 -->

---

## なぜ必要か

- コードは書き終わったのに、リリースがエラーで止まる
- テストは後回しにするつもりだったのに、後回しにできない

<!-- ノート: つかみ。スケジュールの見積りに直結する。テストを工数に入れ忘れると必ず遅れる。 -->

---

## 結論

**Apex は、テストでコードの 75% 以上を通していないと本番組織へ出せない**

- **テストクラス** — Apex を動かして結果を確かめるための Apex
- **コードカバー率** — テストで実行された行の割合

<!-- ノート: 結論を言い切る。他の基盤では方針だが、ここでは仕組みとして強制される。0-1-3で触れた「コードには保守の約束が付く」の具体形。 -->

---

## テストクラスの形

```apex
@isTest
private class OrderServiceTest {
  @isTest
  static void countsOrders() {
    // ここで対象のコードを動かす
  }
}
```

- `@isTest` を付けたクラスとメソッドがテストになる

<!-- ノート: 最小のコード。@isTestが2か所に付く形を覚えてもらう。テストクラス自身はカバー率の分母に入らない、と補足する。 -->

---

## 75% は目安ではなく関門

| 状態 | リリース |
| --- | --- |
| 組織全体 74% | 止まる |
| 組織全体 75% 以上 | 進める |
| 素通しのトリガが 1 つでもある | 止まる |

- 全体が足りていても、トリガは 1 つずつ通す必要がある

<!-- ノート: 対比枠。3行目が見落とされやすい。クラスは全体平均で救えるが、トリガだけは1本ずつ最低1行のカバレッジが要る。数字を満たすだけの空テストは5-1-3で潰す、と口頭で予告する。 -->
