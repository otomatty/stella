## なぜ必要か

- Apex はサーバー上で動くので、途中で止めて覗くことができない
- エラーメッセージだけでは、どこまで進んだのかわからない

<!-- ノート: つかみ。4-1-1で「サーバーで動く」と言ったことの帰結。手元の道具が使えないぶん、別の手が要る。 -->

---

## 結論

**サーバー上で何が起きたかは、デバッグログを取って読む**

- **デバッグログ** — 実行中の出来事を記録したもの
- ユーザを指定して収集を有効にすると、その人の操作ぶんが残る

<!-- ノート: 結論を言い切る。設定でログを取る対象と期間を決める。取りっぱなしにはできず、期限が来ると自動で止まる点も添える。 -->

---

## 自分で印を残す

```apex
System.debug('取得件数: ' + rows.size());
```

- 知りたい値を、通り道に置いておく

<!-- ノート: 最小のコード。printfデバッグと同じ発想。テストの中でも同じように使える、と補足する。 -->

## ログで確かめられること

| 見出し | わかること |
| --- | --- |
| `SOQL_EXECUTE_BEGIN` | どのクエリが何回走ったか |
| `LIMIT_USAGE` | 上限をどこまで使ったか |
| `FATAL_ERROR` | どこで止まったか |

- 4-2-3 の書き方の良し悪しは、ここで数字として見える

<!-- ノート: 対比枠。ログは読む場所を決めておくと怖くない。特にLIMIT_USAGEは、ループの中のSOQLを見つける最短経路になる。 -->
