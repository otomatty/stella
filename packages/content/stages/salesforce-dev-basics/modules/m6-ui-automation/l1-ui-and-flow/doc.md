# レッスン6-1 画面と自動化の作り方

## このレッスンの目標

- [ ] レコードページを設定画面で組み立てられる
- [ ] Flow と Apex トリガのどちらを使うか選べる
- [ ] LWC のフォルダ構成を読める

## 6-1-1 レコードページを組み立てる

> **レコードページは、部品を置く設定画面で組み立てる**

「商談の画面に関連する見積を出したい」と頼まれたとき、他の基盤の経験がある人ほど HTML を書く場所を探してしまいます。ここでも順番は同じです。

- **レコードページ** — 1 件のレコードを表示する画面
- **コンポーネント** — 画面に置ける部品
- **Lightning アプリケーションビルダー** — 部品を並べて画面を作る設定画面

標準の部品だけでかなりの要件が満たせます。

| 部品 | 出るもの |
| --- | --- |
| 項目のセクション | レコードの項目 |
| 関連リスト | 子レコードの一覧 |
| カスタムのコンポーネント | 自作の部品 |

冒頭の「関連する見積を出したい」は、関連リストで済む場合が多いはずです。並べ替えも表示条件の設定もクリックでできます。

同じオブジェクトでも、割り当てるページをプロファイルごとに分けられます。営業には簡潔な画面、管理者には全項目の画面、といった作り分けです。1 つの画面を条件分岐だらけにする前に、割り当てで分ける手があります。

## 6-1-2 自動化は Flow に寄せる

> **クリックで書ける自動化は Flow に寄せ、Apex は Flow で書けないときに使う**

Module 4 でトリガを覚えた直後は、何でもトリガで解こうとしがちです。「保存したら承認依頼を送る」のような要件は、クリックで作れます。

**Flow** は処理の流れを画面上で組み立てる、設定側の自動化の仕組みです。レコードの保存時に動かすこともでき、条件分岐・レコードの作成更新・画面つきの入力まで扱えます。かつては複数の自動化の仕組みがありましたが、いまは Flow が正面です。

| | Flow | Apex トリガ |
| --- | --- | --- |
| 作り方 | クリック | コード |
| リリースの関門 | Apex テストクラスは不要 | テストクラスが必須 |
| 直せる人 | 管理者も | 開発者だけ |

「テストが不要」という意味ではありません。Flow にも Debug 実行と Flow テストがあり、
まとめて更新したときの件数も確かめる必要があります。違うのは、5-1-1 のコードカバー率という
**リリースの関門**に掛からないことです。

効いてくるのは運用に入ったあとです。Apex にすると、些細な変更でもリリース手順が必要になります。

Apex を選ぶ場面もはっきりあります。

- 複雑なくり返しや、大量データの処理が要る
- Flow では表現できない条件がある
- 外部システムとやり取りする

「Flow では無理だから Apex にした」と説明できるかどうかが、選択の基準です。

## 6-1-3 LWC は 3 つのファイル

> **LWC は HTML・JavaScript・設定ファイルの 3 つで 1 つの部品になる**

標準の部品では足りない画面を頼まれることもあります。**LWC**(Lightning Web コンポーネント)は、自作の画面部品を作る仕組みです。Web 標準に近い書き方なので、JavaScript の知識がそのまま効きます。

3 つのファイルを、同じ名前のフォルダにまとめて置きます。

| ファイル | 役割 |
| --- | --- |
| `orderList.html` | 見た目 |
| `orderList.js` | ふるまい |
| `orderList.js-meta.xml` | どこに置ける部品かの設定 |

3 つ目が無いと、6-1-1 の設定画面の部品一覧に出てきません。「作ったのに置けない」で詰まる原因はたいていここです。

データの取り方にも順番があります。0-1-3 の「標準が先」が、ここでも同じ形で効きます。

![標準の部品・データサービス・Apex の順に試すことを示した3層の図](t3-lwc/assets/lwc-data-order.svg)

| 試す順番 | 使うもの |
| --- | --- |
| 1 | 標準の部品(`lightning-record-form` など) |
| 2 | **Lightning データサービス**(`lightning/uiRecordApi` の wire アダプタ) |
| 3 | Apex のメソッド |

レコードの表示・作成・編集は、上の 2 つでほとんど賄えます。データサービスを通すと、キャッシュも更新の反映もアクセス権の確認も基盤がやってくれます。**Apex は必須ではありません。** 上の 2 つでは表現できない検索や集計が要るときに、初めて書きます。

Apex を選んだときは、画面からの呼び出しを許す印をメソッドに付けます。そして Module 4 で見た作法(一括処理)と Module 2 で見たアクセス権の確認が、そのまま自分の責任になります。上から順に試すのは、この責任を負わずに済ませるためでもあります。

この講座では実装までは扱いません。案件のリポジトリを開いたときに、どのファイルが何をしているか読めれば十分です。
