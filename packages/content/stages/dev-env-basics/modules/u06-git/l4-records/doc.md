# レッスン6-4 記録の残し方

## このレッスンの目標

- [ ] コミットの説明を、変更内容が分かる1行で書けます。
- [ ] 提出に、ファイル・変更箇所と内容・理由を添えられます。

## 6-4-1 コミットの説明

> **コミットの説明には、何を変えたかを 1 行で書きます。**

一覧を読む未来の自分や、確認する相手に向けて書きます。
「修正」「できた」だけでは、何を変えたかが分かりません。

| 説明の例 | 読み取りやすさ |
| --- | --- |
| 修正 | 対象も内容も分かりません |
| index.html の見出しを学習予定に変える | 対象と変更が分かります |

長い操作履歴を書き写す必要はありません。
どのファイルの何を変えたかが分かる1行にします。
コミットしたら、一覧でその説明が残ったかを見ます。

## 6-4-2 変更を説明して提出する

> **変更を説明するときは、どのファイルのどこを、なぜ変えたかを書きます。**

説明を添えた提出は、変更の内容と意図を文章で伝える提出です。
説明が必要な課題では、提出するときに説明の欄が出ます。
この単元の「変更を記録して説明する」で初めて使います。
手元の確認が通ったら「提出する」へ進み、説明の欄に書きます。

説明には、次の3点を含めます。

1. 変えたファイル名。
2. 変えた場所と、変更前後の内容。
3. その変更をした理由。

別の練習の例です。

```text
index.html の h1 を変えました。
「学習メモ」を「今日の学習メモ」にしました。
今日の内容だと読んだ人に分かるようにするためです。
```

`git diff` に出た差分を読み、自分の言葉で説明します。
記号や表示をそのまま貼るだけでなく、変化の意味を書きます。
保存したファイルと説明が一致するか、送る前に照合します。
実務のレビューでも、理由があると変更の意図を確かめやすくなります。

## うまくいかないとき

説明に迷ったら、差分のファイル名と変更前後の文字を読みます。
なぜ課題の条件に合わせたのかを1文で添えます。
実際に変えていないことは、説明に書きません。
