# レッスン4-2 演習 — 経験ベースの技法

対象トピック: 4-2-1 〜 4-2-4

## 手元で試す

このレッスンは実行するコードがありません。代わりに、**モジュール3で作った送料計算のケース表を持ってきて、チェックリストで育てます**。紙かエディタで手を動かしてください。

### ① モジュール3のケース表を書き出す

レッスン3-2 で境界値分析を当てた、あの仕様です。

> **仕様**: 購入額 3,000 円以上なら送料は 0 円。3,000 円未満なら 500 円。購入額は 1 円以上の整数で、それ以外はエラー。

境界値分析で作った 4 件を、まず書き出してください。

| # | 入力(購入額) | 期待結果 | 根拠 |
| --- | --- | --- | --- |
| 1 | 2,999 円 | 送料 500 円 | 3,000 円の境界の外側 |
| 2 | 3,000 円 | 送料 0 円 | 3,000 円の境界の内側 |
| 3 | 0 円 | エラー | 1 円の境界の外側 |
| 4 | 1 円 | 送料 500 円 | 1 円の境界の内側 |

「根拠」の列があることに注目してください。ここまでは全部「境界値分析」で説明がつきます。

### ② チェックリストを当てて 3 行足す

定番 5 観点を上から順に当てます。**最低 3 行を足してください**。根拠の列には「チェックリスト(観点名)」と書きます。

| 観点 | この仕様に当てると | 既に表にあるか |
| --- | --- | --- |
| 空 | 購入額が未入力(空文字)のまま送信 | |
| 0 | 購入額 0 円 | |
| 負数 | 購入額 -1 円 | |
| 重複 | 同じ商品を 2 回カートに入れる | |
| 長すぎ | 購入額 10 億円 / 小数点付きの値 | |

「既に表にあるか」を先に埋めてください。0 円は #3 で既にあります。残りは表にありません。

足したあと、次を確かめてください。

- 足した行の期待結果を、**仕様から答えられますか**。答えられない行がありませんか
- 答えられない行は、仕様の穴です。「10 億円のときどうする?」は仕様に書かれていません。そのことをメモに残してください(これがレッスン4-3 につながります)
- 根拠の列が全行埋まっていますか。埋まっていない行は、なぜ試すのかを説明できない行です

### ③ 探索のチャーターを 1 枚書く

表を実行し終えたあと、45 分だけ探索的テストをするとします。チャーターを 4 行で書いてください。

| 項目 | 書くこと |
| --- | --- |
| 対象 | |
| 目的 | |
| 時間 | |
| 記録 | |

目的の欄に「いろいろ試す」と書きたくなったら、それは目的になっていません。「何が起きないことを確かめたいのか」を 1 文で書いてください。

## 演習問題

### 問1(基本)

「会員登録フォーム(メールアドレスとパスワードを入力して登録)」に、チェックリストの 5 観点を当ててください。該当しない観点があれば「該当なし」と書いてください。

### 問2(基本)

チェックリストで当てた結果を、「該当なし」も含めて全部書き残すのはなぜですか。1〜2 文で答えてください。

### 問3(応用)

次の会話を読んで、問題点を指摘してください。

> リーダー: 「テストは終わった?」
> 担当者: 「はい、2 時間くらい画面をいろいろ触ってみましたが、特に問題ありませんでした」

### 問4(応用)

新しいチームで「ケース表は作らない。経験のあるメンバーが触って確かめるほうが速い」という方針が出ました。この方針で失われるものを 3 つ挙げ、どう修正することを提案しますか。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

| 観点 | メールアドレス | パスワード |
| --- | --- | --- |
| 空 | 空のまま登録 | 空のまま登録 |
| 0 | 該当なし(数値ではない) | 該当なし |
| 負数 | 該当なし | 該当なし |
| 重複 | 登録済みメールで再登録 | 該当なし(重複してよい) |
| 長すぎ | 300 文字のメール | 1,000 文字のパスワード |

「0」「負数」は数値の観点なので、文字列の入力欄には該当しません。該当しないと判断したこと自体を書き残すのが要点です。

なお、パスワードには「長すぎ」の裏返しである「短すぎ」も効きます。定番 5 つは出発点で、扱うものに合わせて継ぎ足していきます。

</details>

<details>
<summary>問2の解答例</summary>

空欄のままだと、**見落としたのか、当てたうえで該当なしと判断したのか**が区別できないからです。あとから読む人(自分も含む)は、空欄を見て「まだやっていない」と読みます。当てた記録が残っていれば、次の人はそこから先を考えられます。

</details>

<details>
<summary>問3の解答例</summary>

問題点は 2 つです。

- **何をテストしたかを説明できていません**。「いろいろ触った」では、どの機能のどんな観点を見たのかが分かりません。他の人が引き継げず、次回に同じ範囲を再現することもできません
- **目的と時間が事前に決まっていません**。これは探索的テストではなく、ただ触っただけです

修正するなら、先にチャーター(対象・目的・時間・記録)を書いてから始め、終わったら試した操作と気づきのメモを添えて報告します。「会員登録フォームの異常入力を 45 分、二重登録が起きないかを中心に確認。メモは別紙」と言えれば、報告として成立します。

</details>

<details>
<summary>問4の解答例</summary>

失われるもの:

- **網羅の説明**。「何をテストしたか」を報告できないので、リリース判断の材料になりません
- **品質の安定**。経験のあるメンバーが抜けた瞬間に、見つかる欠陥の量が変わります
- **リグレッションの資産**。再実行できないので、変更のたびに同じ勘を頼ることになります

提案としては、順番を入れ替えるだけで足ります。**先に系統的な技法でケース表を作り、そのうえで経験のあるメンバーの探索を 45 分重ねる**。経験ベースをやめるのではなく、網を張ってから使う形にします。探索で見つけた欠陥はケース表に足して、次からは表の側で捕まえられるようにします。

</details>

## 確認クイズ

### Q1. エラー推測とはどのような技法ですか。

- A. 仕様書に書かれた条件を組み合わせて表にする技法
- B. コードの分岐を数えてテストケースを作る技法
- C. 過去の欠陥や勘所から、壊れそうな入力を狙ってケースにする技法

<details>
<summary>答え</summary>

**C** — 出発点が仕様でもコードでもなく、人の経験である点が特徴です。こうした技法をまとめて経験ベースの技法と呼びます。

</details>

### Q2. エラー推測を技法として成立させるために、最も大事なことはどれですか。

- A. 経験の長いメンバーだけが担当すること
- B. 推測した内容をケース表の行として書き残すこと
- C. 仕様書に載っている入力だけを選ぶこと

<details>
<summary>答え</summary>

**B** — 頭の中で疑って触るだけでは、再現も引き継ぎもできません。「明示的にテストケースへ変える」が定義の中心です。

</details>

### Q3. チェックリストの定番 5 観点に **含まれない** ものはどれですか。

- A. 空
- B. 平均値
- C. 重複

<details>
<summary>答え</summary>

**B** — 定番は「空・0・負数・重複・長すぎ」の 5 つです。平均値のような真ん中の値は、同値分割の代表値としては使いますが、壊れやすい入力の定番ではありません。

</details>

### Q4. 探索的テストで、事前に決めておくものはどれですか。

- A. 対象・目的・時間(テストチャーター)
- B. 実行するテストケースの中身をすべて
- C. 何も決めない。決めた時点で探索的テストではなくなる

<details>
<summary>答え</summary>

**A** — 決めないのはケースの中身だけです。目的と時間まで決めないなら、それはただ触っているだけで、報告もできません。

</details>

### Q5. 系統的な技法と経験ベースの技法の使い方として、適切なのはどれですか。

- A. 経験ベースで一通り触り、問題が出たらケース表を作る
- B. どちらか一方を選び、混ぜない
- C. 先に系統的な技法で網を張り、そのうえで経験ベースを重ねる

<details>
<summary>答え</summary>

**C** — 経験ベースは網の外を突く補完役です。順番を逆にすると、何を試したかを説明できなくなります。

</details>
