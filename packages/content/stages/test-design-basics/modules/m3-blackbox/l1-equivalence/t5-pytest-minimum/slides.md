## なぜ必要か

- ケース表はできたが、実行するのは毎回人の手
- 3 件なら回るが、リリースのたびに回すと決めた瞬間に重くなる
- 表のまま置いておくと、コードが変わっても誰も気づかない

<!-- ノート: つかみ。表は設計の成果物ですが、そのままではリグレッションテストの資産になりません。 -->

---

## 結論

**pytest は test_ で始まる関数の assert が成り立つかでテストの合否を決める**

- **pytest** — Python の自動テストを実行するツール
- **テスト関数** — `test_` で始まる名前の関数。pytest はこれだけを集める
- **assert** — 条件が真であることを主張する文。偽なら失敗する

<!-- ノート: 結論を言い切る。覚えることは 2 つの決まりだけです。名前が `test_` で始まること、判定は `assert` で書くこと。 -->

---

## ケース表の 1 行をコードにする

```python
# test_shipping.py
from shipping import shipping_fee

def test_under_3000_costs_500():
    assert shipping_fee(1500) == 500
```

`shipping_fee(1500)` が入力、`== 500` が期待結果です。

<!-- ノート: コードの枠。代表値 1,500 円のケースがそのまま 1 関数になりました。ターミナルで `pytest` と打つと `1 passed` と出ます。 -->

---

## 集めてもらえない書き方

| 書き方 | 何が起きるか |
| --- | --- |
| 関数名を `check_...` にする | 集められず `no tests ran` になる |
| ファイル名を `shipping_tests.py` にする | 同じく集められない |
| `print` で結果を出す | 人が読まないと合否が分からない |

<!-- ノート: 失敗例の枠。`no tests ran` は「失敗」ではなく「1 つも集まっていない」です。赤い行が出ないので見落としやすい。 -->
