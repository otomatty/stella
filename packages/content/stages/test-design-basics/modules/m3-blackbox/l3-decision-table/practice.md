# レッスン3-3 演習 — デシジョンテーブル

対象トピック: 3-3-1 〜 3-3-4

## 手元で試す

**①仕様からケース表を書く → ②表を pytest に写して実行する**。今回の「ケース表」はデシジョンテーブルです。

### ① デシジョンテーブルを書く

次の仕様を読んでください。

> **仕様**: 注文の割引率を返す。プレミアム会員なら 10% 引き。クーポンを持っていて、かつ期限内ならさらに 5% 引き。どちらも当てはまらなければ 0%。

条件を Y/N で答えられる形に言い換えて 3 つ挙げ、8 列のデシジョンテーブルを書いてください。

| 条件 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | | | | | | | | |
| | | | | | | | | |
| | | | | | | | | |
| **割引率** | | | | | | | | |

Y/N は考えながら並べず、二進数を数える要領で機械的に並べてください。書けたら簡約して 6 列にします。「−」を書いてよいのは、その条件が結果に効いていないと確かめた列だけです。

| 条件 | R1 | R2 | R3 | R4 | R5 | R6 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |
| | | | | | | |
| | | | | | | |
| **割引率** | | | | | | |

埋めたら、次を確かめてください。

- 簡約前の列は 8 本ちょうどですか。7 本なら漏れ、9 本なら重複です
- 「−」を書いた列は、その条件を Y にしても N にしても割引率が変わらないと確かめましたか
- 割引率が同じ列を、条件を見ずにまとめていませんか

### ② 表を pytest に写す

作業用のフォルダに次の 2 ファイルを置いてください。

```python
# discount.py
def discount_rate(is_premium, has_coupon, coupon_valid):
    rate = 10 if is_premium else 0
    if has_coupon and coupon_valid:
        rate += 5
    return rate
```

```python
# test_discount.py
import pytest

from discount import discount_rate


@pytest.mark.parametrize("premium, coupon, valid, rate", [
    (False, False, True, 0),   # R1: クーポンなし(期限は「−」→ True を採用)
    (False, True, False, 0),   # R2: クーポンあり・期限切れ
    (False, True, True, 5),    # R3: 一般 + 有効クーポン
    (True, False, True, 10),   # R4: プレミアム(期限は「−」→ True を採用)
    (True, True, False, 10),   # R5: プレミアム + 期限切れクーポン
    (True, True, True, 15),    # R6: プレミアム + 有効クーポン
])
def test_discount_rate(premium, coupon, valid, rate):
    assert discount_rate(premium, coupon, valid) == rate
```

ターミナルで実行します。

```bash
pytest -v
```

`6 passed` と表示されれば成功です。`-v` の出力に 6 行並びます。①で書いた表の 6 列と、1 対 1 で対応していることを確かめてください。

確かめられたら、次の改造をしてみましょう。

1. `discount.py` の `if has_coupon and coupon_valid:` を `if has_coupon:` に書き換えて実行し、**どのルールが落ちるか**を確かめる(確かめたら戻す)
2. `rate = 10 if is_premium else 0` を `rate = 0` に書き換えて実行し、落ちるルールが 1 とは別であることを確かめる(確かめたら戻す)
3. R1 と R4 の「−」を採用した値を `False` に書き換えて実行し、結果が変わらないことを確かめる。変わらないことが「−」の根拠です

## 演習問題

### 問1(基本)

「会員か」「クーポンがあるか」「キャンペーン期間中か」という 3 つの条件があります。簡約する前のルールは何列になりますか。理由も書いてください。

### 問2(基本)

次のデシジョンテーブルには問題があります。指摘してください。

| 条件 | R1 | R2 | R3 |
| --- | --- | --- | --- |
| プレミアム会員か | N | Y | Y |
| クーポンがあるか | N | N | Y |
| **割引率** | **0%** | **10%** | **15%** |

### 問3(応用)

次の仕様をデシジョンテーブルにし、簡約してください。

> **仕様**: 送料を返す。購入額が 3,000 円以上なら 0 円。3,000 円未満でも、プレミアム会員なら 0 円。どちらでもなければ 500 円。ただし、離島への配送のときは上の条件にかかわらず 800 円。

### 問4(応用)

問3で作った表を `pytest.mark.parametrize` に写すと、テストは何件になりますか。また、簡約せずに写した場合との違いを、テストの強さの観点で述べてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

8 列です。条件が 3 つあり、それぞれが Y / N の 2 通りを取るので、2 × 2 × 2 = 8 通りの組み合わせがあります。条件が n 個なら 2 の n 乗です。

この数を先に出しておくのが大事です。表を書き終えたときに列が 8 本でなければ、漏れか重複があると分かります。

</details>

<details>
<summary>問2の解答例</summary>

列が 1 本足りません。条件が 2 つなので 4 列あるはずですが、3 列しかありません。抜けているのは「プレミアム会員ではないが、クーポンはある」(N / Y)の組み合わせです。

抜けた列は、そのままテストの穴になります。しかも表を見ただけでは気づきにくいので、列の数を先に数えておく習慣が効きます。

</details>

<details>
<summary>問3の解答例</summary>

条件は「離島か」「購入額 3,000 円以上か」「プレミアム会員か」の 3 つで、簡約前は 8 列です。離島のときは他の条件が効かないので、そこが「−」になります。

| 条件 | R1 | R2 | R3 | R4 | R5 |
| --- | --- | --- | --- | --- | --- |
| 離島か | Y | N | N | N | N |
| 3,000 円以上か | − | Y | Y | N | N |
| プレミアム会員か | − | Y | N | Y | N |
| **送料** | **800** | **0** | **0** | **0** | **500** |

R1 が 4 列ぶんをまとめた列です。8 列が 5 列になりました。R2 と R3 はプレミアム会員かどうかが効いていないので、さらに「−」でまとめて 4 列にすることもできます。どちらでも正解ですが、まとめるたびに「本当に効いていないか」を確かめてください。

</details>

<details>
<summary>問4の解答例</summary>

5 件(さらに簡約したなら 4 件)です。簡約せずに 8 件書いた場合と比べると、テストの件数は減りますが、**カバーしている組み合わせの範囲は同じ**です。「−」は「どちらでも結果は変わらない」と確認した印なので、片方を試せばもう片方も同じだと言えるからです。

ただし、その確認が間違っていた場合は違います。たとえば「離島かつプレミアム会員」だけ実装が別の分岐を通っていたなら、R1 で選ばなかったほうの値でだけ壊れます。簡約は「仕様の上で効いていない」という判断に依存していて、実装がその通りとは限りません。壊れると影響が大きい機能では、簡約を控えて全列を書く判断もあります。

</details>

## 確認クイズ

### Q1. 条件が 3 つあるとき、簡約前のルールは何列になりますか。

- A. 3 列
- B. 8 列
- C. 6 列

<details>
<summary>答え</summary>

**B** — 2 の 3 乗で 8 通りです。列の数を先に出しておくと、書き終えたときに漏れや重複に気づけます。

</details>

### Q2. デシジョンテーブルの「ルール」とは何を指しますか。

- A. 表の書き方の決まりごと
- B. 表の 1 行に書かれた条件
- C. 表の 1 列。条件の真偽の組み合わせ 1 通り

<details>
<summary>答え</summary>

**C** — 行が条件、列がルールです。ルール 1 列がテストケース 1 件になります。

</details>

### Q3. 表の中の「−」はどんな意味ですか。

- A. その条件は Y でも N でも結果が変わらない
- B. その条件はまだ決まっていない
- C. そのルールはテストしなくてよい

<details>
<summary>答え</summary>

**A** — 効いていないと確かめた条件にだけ書きます。確かめずに書くと、その組み合わせでだけ起きる欠陥を見逃します。

</details>

### Q4. 「割引率が同じ 2 つの列は、条件を見ずにまとめてよい」という意見は正しいですか。

- A. 正しい。結果が同じなら区別する意味はない
- B. 正しくない。条件が効いていないと確かめたときだけまとめられる
- C. 正しい。列は少ないほどよい

<details>
<summary>答え</summary>

**B** — たまたま結果が同じ列どうしをまとめると、その組み合わせでだけ起きる欠陥を見逃します。簡約は結果ではなく条件の意味を見て行います。

</details>

### Q5. デシジョンテーブルをテストコードに写すとき、コメントに `# R3` と書く目的はどれですか。

- A. 表のどの列に当たるかを残し、仕様変更時に対応を追えるようにするため
- B. pytest がルール名として認識するため
- C. テストの実行順を指定するため

<details>
<summary>答え</summary>

**A** — 設計とコードの対応が切れると、表は飾りになります。コードにあって表に無い組が見つかれば、表の更新漏れだと分かります。

</details>
