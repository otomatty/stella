# レッスン3-5 演習 — 技法の使い分け

対象トピック: 3-5-1 〜 3-5-3

## 手元で試す

**①仕様からケース表を書く → ②表を pytest に写して実行する**。今回は 1 つの機能に 3 つの技法を重ねます。

### ① 技法を選んでケース表を書く

次の仕様を読んでください。

> **仕様**: 注文をキャンセルすると返金額を返す。キャンセルできるのは 受付 と 支払済 の注文だけで、発送済 と キャンセル の注文はエラーになる。返金額は、受付ならまだ支払っていないので 0 円。支払済なら購入額の全額を返す。ただしキャンセル手数料として、購入額が 10,000 円以上のときは 500 円を差し引く。プレミアム会員は手数料がかからない。

まず、この仕様の中から **技法を選ぶ手がかり**を探します。仕様の文に線を引き、次の表を埋めてください。

| 仕様のどの部分か | 選ぶ技法 | 狙う欠陥 |
| --- | --- | --- |
| | | |
| | | |
| | | |

次に、外側から内側の順(状態遷移 → デシジョンテーブル → 境界値分析)でケース表を作ります。

| # | 状態 | 購入額 | プレミアム会員か | 期待結果 | どの技法から |
| --- | --- | --- | --- | --- | --- |
| 1 | | | | | |
| 2 | | | | | |
| 3 | | | | | |
| 4 | | | | | |
| 5 | | | | | |
| 6 | | | | | |
| 7 | | | | | |

埋めたら、次を確かめてください。

- 発送済とキャンセルの状態のケースがありますか。無ければ状態遷移の観点が抜けています
- 9,999 と 10,000 の両方がありますか。片方だけなら境界値になっていません
- 「プレミアム会員 × 10,000 円以上」のケースがありますか。手数料が 0 円になる組み合わせです
- 「どの技法から」の列が空の行はありませんか。書けない行は、根拠がない行です

最後に、**この仕様で期待結果が書けない場所**を探してください。1 つ以上あります。見つかったら、仕様への質問の形で 1 行書いてください。埋めずに残すのが正解です。

### ② 表を pytest に写す

作業用のフォルダに次の 2 ファイルを置いてください。

```python
# refund.py
CANCELLABLE = {"受付", "支払済"}


def cancel_refund(status, total, is_premium):
    if status not in CANCELLABLE:
        raise ValueError(f"{status} の注文はキャンセルできません")
    if status == "受付":
        return 0
    fee = 500 if total >= 10000 and not is_premium else 0
    return total - fee
```

```python
# test_refund.py
import pytest

from refund import cancel_refund


@pytest.mark.parametrize("status", ["発送済", "キャンセル"])
def test_cannot_cancel(status):
    with pytest.raises(ValueError):
        cancel_refund(status, 5000, False)


def test_accepted_order_refunds_nothing():
    assert cancel_refund("受付", 5000, False) == 0


@pytest.mark.parametrize("total, premium, expected", [
    (9999, False, 9999),    # 10,000 円の境界の外側: 手数料なし
    (10000, False, 9500),   # 10,000 円の境界の内側: 手数料 500 円
    (10000, True, 10000),   # プレミアム会員は手数料なし
    (9999, True, 9999),     # プレミアム会員・10,000 円の境界の外側
])
def test_paid_order_refund(total, premium, expected):
    assert cancel_refund("支払済", total, premium) == expected
```

ターミナルで実行します。

```bash
pytest -v
```

`7 passed` と表示されれば成功です。①の表 7 行と 1 対 1 に対応します(状態遷移から 2 件、受付の返金 1 件、支払済の境界値×デシジョンテーブルで 4 件)。`-v` の出力を見て、3 つの技法から出たケースがそれぞれ何件あるかを数えてください。

確かめられたら、次の改造をしてみましょう。

1. `refund.py` の `total >= 10000` を `total > 10000` に書き換えて実行し、落ちるのが境界値のケースだけであることを確かめる(確かめたら戻す)
2. `and not is_premium` を消して実行し、落ちるのがデシジョンテーブルから出たケースであることを確かめる(確かめたら戻す)
3. `CANCELLABLE` に `"発送済"` を足して実行し、落ちるのが状態遷移から出たケースであることを確かめる(確かめたら戻す)

3 つの改造で落ちるケースが重なっていないことが、「技法ごとに違う欠陥を狙っている」ということの意味です。

## 演習問題

### 問1(基本)

次の 3 つの仕様文それぞれに、使うべき技法を答えてください。

1. 「パスワードは 8 文字以上 32 文字以下」
2. 「下書きの記事は公開できるが、公開済みの記事は再公開できない」
3. 「有料会員かつ初回購入なら 20% 引き、有料会員のみなら 10% 引き」

### 問2(基本)

「1 つの機能には技法を 1 つだけ選ぶべきだ」という意見に反論してください。

### 問3(応用)

キャンセル機能のケース表を作っていたら、「発送済の注文をキャンセルできない」ことは分かりましたが、そのときエラーにするのか、それとも返品扱いにするのかが仕様書に書かれていませんでした。どうすべきか、理由とあわせて書いてください。

### 問4(応用)

ある担当者が、キャンセル機能のテストを「境界値分析で 10,000 円の前後を試したので完了」と報告しました。この報告に足りない観点を 2 つ挙げてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

1. **同値分割 + 境界値分析**。「8 文字以上 32 文字以下」は範囲なので、境界が 2 か所(8 のところと 32 のところ)あります
2. **状態遷移**。「下書き」「公開済み」という状態があり、同じ「公開する」操作でも状態によって結果が変わります
3. **デシジョンテーブル**。「有料会員か」「初回購入か」の 2 条件が絡むので、4 通りの組み合わせを並べます。仕様文には 2 通りしか書かれていないので、残り 2 通りの期待結果は仕様への質問になります

3 番のように、技法を当てただけで仕様の穴が出ることがあります。

</details>

<details>
<summary>問2の解答例</summary>

技法ごとに狙っている欠陥の種類が違うからです。1 つの技法で覆えるのは仕様の 1 つの側面だけなので、他の側面はまったく試されません。

キャンセル機能の例では、状態遷移で遷移カバレッジ 100% を達成しても、返金額の手数料の境界(10,000 円)は一度も試されません。逆に境界値分析だけでは、発送済の注文をキャンセルできてしまう欠陥が残ります。

また、狙う場所が違うので重ねてもケースの重複は少なく、件数が技法の数だけ倍になるわけではありません。

</details>

<details>
<summary>問3の解答例</summary>

推測で埋めず、仕様の空欄として持ち出します。ケース表の期待結果の欄を空けたまま、「発送済の注文でキャンセル操作をしたとき、エラーにしますか、それとも返品の受付として扱いますか」と質問します。

推測で「エラー」と書いてしまうと、その瞬間に質問が消えて、仕様が確定したように見えます。実装者が別の推測(返品扱い)をしていた場合、テストが失敗したときに「テストのほうが間違っている」という話になり、決着に時間がかかります。

決めるのは仕様を持っている人であって、テスト担当者ではありません。質問には選択肢を添えると、その場で決まりやすくなります。

</details>

<details>
<summary>問4の解答例</summary>

1 つ目は **状態遷移の観点**です。キャンセルできる状態(受付・支払済)とできない状態(発送済・キャンセル)の区別が試されていません。境界値のケースはすべて支払済の注文で作られているはずなので、他の 3 状態が一度も出てきません。

2 つ目は **条件の組み合わせの観点**です。プレミアム会員かどうかで手数料の有無が変わりますが、境界値だけを試すと「一般会員 × 9,999 円」「一般会員 × 10,000 円」の 2 件で終わり、プレミアム会員の組み合わせが抜けます。手数料が 0 円になる経路が一度も通らない状態です。

「境界値分析をやった」は、技法を 1 つ当てたという意味であって、その機能のテストが終わったという意味ではありません。

</details>

## 確認クイズ

### Q1. 「注文の合計金額が 5,000 円未満なら手数料 300 円」という仕様に、まず当てるべき技法はどれですか。

- A. 状態遷移
- B. デシジョンテーブル
- C. 同値分割 + 境界値分析

<details>
<summary>答え</summary>

**C** — 「〜未満」は範囲を表す言葉です。仕様の書かれ方の形が、選ぶ技法の手がかりになります。

</details>

### Q2. 「公開済みの記事は再公開できない」という仕様に当てるべき技法はどれですか。

- A. 状態遷移
- B. 境界値分析
- C. 同値分割

<details>
<summary>答え</summary>

**A** — 「公開済み」という状態があり、同じ操作でも状態によって結果が変わります。「〜のあとは」「ステータスが〜のとき」は状態遷移の手がかりです。

</details>

### Q3. 1 つの機能に複数の技法を重ねる理由はどれですか。

- A. テストケースの件数を増やすため
- B. 技法ごとに狙っている欠陥の種類が違うから
- C. どの技法が正しいか分からないため

<details>
<summary>答え</summary>

**B** — 1 つの技法で覆えるのは仕様の 1 つの側面だけです。狙う場所が違うので、重ねてもケースの重複はあまり増えません。

</details>

### Q4. 技法を重ねるとき、扱いやすい順序はどれですか。

- A. 境界値分析 → デシジョンテーブル → 状態遷移
- B. 順序はどれでも同じ
- C. 状態遷移 → デシジョンテーブル → 境界値分析

<details>
<summary>答え</summary>

**C** — 外側から内側へ、が原則です。逆から始めると、そもそもその機能を使えない状態のケースを大量に作ってしまいます。

</details>

### Q5. デシジョンテーブルの 1 列に期待結果が書けませんでした。正しい振る舞いはどれですか。

- A. もっともらしい値を推測して埋め、先へ進む
- B. 空欄のまま、仕様を決める人への質問として持ち出す
- C. その列を表から削除する

<details>
<summary>答え</summary>

**B** — 期待結果が書けないのは、合格の条件が決まっていないということです。推測で埋めると質問が消え、実装者の推測と食い違ったときに決着が長引きます。空欄は成果物です。

</details>
