# レッスン2-3 変更に伴うテスト

## このレッスンの目標

- [ ] 確認テストとリグレッションテストの目的の違いを説明できる
- [ ] 変更のあとに何を流すべきかを判断できる
- [ ] 自動化の価値を「実行の回数」で説明できる

## 2-3-1 確認テスト

> **確認テストは「直した欠陥が本当に直ったか」を確かめる**

「修正しました」と言われたので、画面をひととおり触って問題なさそうだったから閉じた。翌週、同じ手順で同じ故障が再発して報告が戻ってきた。よくある話です。触ったのは自分の思いついた操作であって、報告にあった再現手順ではなかったからです。

**確認テスト** は、修正後に、故障を再現させた手順をもう一度なぞるテストです。デバッグの出口に必ず置く一手だと考えてください。

| 手順 | やること |
| --- | --- |
| 1 | 報告にある再現手順を、そのままなぞる |
| 2 | 故障が起きないことを確かめる |
| 3 | 同じ手順を修正前の版でも試し、再現することを確かめる |

3 は省かれがちですが、これが無いと「そもそも再現しなかっただけ」と区別できません。修正前で再現し、修正後で再現しない。この 2 つがそろって初めて、直ったと言えます。

ここで大事なのは、再現手順がそのままテストケースになるという点です。報告に書かれた手順が具体的であればあるほど、確認テストは機械的に実行できます。逆に「たまに落ちます」という報告は、確認テストを作れません。欠陥の報告の書き方は、あとのモジュールで正面から扱います。

## 2-3-2 リグレッションテスト

> **リグレッションテストは「変更が別の場所を壊していないか」を確かめる**

送料の判定を 1 行だけ直したら、注文完了メールの金額がずれた。直した本人は、メールの処理を触った覚えがありません。変更の影響は、変更した場所の外へ出ます。

**リグレッションテスト** は、変更前に動いていた部分が、いまも動くことを確かめるテストです。確認テストが「直した場所」を見るのに対して、リグレッションテストは「それ以外」を見ます。目的が違うので、両方が必要です。

| テスト | 対象 |
| --- | --- |
| 確認テスト | 3,000 円ちょうどで送料が 0 円になる |
| リグレッションテスト | 2,999 円で従来どおり 500 円になる |
| リグレッションテスト | 注文完了メールの金額が請求額と一致する |

リグレッションテストの中身は、既存のテストケースの再実行です。新しく作るものではなく、これまでに作ったものを流し直します。だからテストケースは資産として貯まっていきます。

どこまで流すかは、変更の影響範囲の見立てで決まります。送料の計算に触ったなら、送料を使っているところ(請求額の表示、メール、集計)まで広げる。この見立てが外れると、今回のように思わぬところが壊れます。影響範囲が読み切れないときは、広く流すのが安全側の判断です。

## 2-3-3 リグレッションと自動化

> **繰り返し実行するテストほど、自動化の価値が高い**

リリースのたびに、200 件の手順書を 2 人で 3 日かけて流している現場があります。手で回す限り、コストは回数に比例します。3 日かかるとなれば、小さな修正のときほど「今回は省こう」という判断が出てきます。

**自動テスト** は、人が操作しなくても実行と合否判定ができる形にしたテストです。判断の軸は「何回流すか」です。1 回しか流さないテストの自動化は、作る手間のぶんだけ割に合いません。

| テスト | 実行の回数 | 自動化の価値 |
| --- | --- | --- |
| コンポーネントテスト | 変更のたび、毎日 | 高い |
| リグレッションテスト | リリースのたび | 高い |
| 確認テスト | 修正のたび 1 回 | 中(資産として残せば高い) |
| 初回の探索的な操作 | 1 回 | 低い |

確認テストが「中」なのには理由があります。直ったかを見る用途としては 1 回で終わりますが、そのケースを残しておけば、次からはリグレッションテストの一部になります。「一度出た欠陥は、二度と同じ形では出さない」という守りが、こうして積み上がっていきます。

なお、自動化するかどうかの判断には、作るコストと維持するコストも関わります。ここでは「繰り返す回数が多いほど価値が高い」という軸だけを押さえてください。費用の側から見た判断は、モジュール5でもう一度扱います。

## もっと知りたい人へ

- 「確認テスト」は現場によって「再テスト」「デグレ確認」など別の呼び方をされることがあります。呼び方より、直した場所とそれ以外を分けて考えているかどうかが大事です
- リグレッションテストの範囲を毎回すべてにできない場合は、変更の影響範囲と、壊れたときの影響の大きさで絞ります。この絞り方はモジュール5のリスクベースの優先順位で扱います
