# レッスン2-3 演習 — 変更に伴うテスト

対象トピック: 2-3-1 〜 2-3-3

## 手元で試す

このレッスンも紙の上の課題です。同じファイルに書き足してください。

次の欠陥報告と修正内容を題材にします。

> **報告**: 会員として購入額 3,000 円ちょうどで注文すると、送料 500 円が請求される。会員でログインし、商品を 1 点だけカートに入れ、金額が 3,000 円ちょうどになる状態で注文確認画面を開くと再現する。
>
> **修正**: 料金計算 API の送料判定で、条件が「3,000 円より大きい」になっていたので「3,000 円以上」に直した。

まず、この修正に対する **確認テスト** を書きます。

| 手順 | 具体的に何をするか | 期待する結果 |
| --- | --- | --- |
| 1 | | |
| 2 | | |
| 3 | | |

3 行目には、修正前の版で同じ手順を試して再現することの確認を書いてください。ここを書き忘れる人が多い場所です。

次に、この修正に対する **リグレッションテスト** を 4 件書きます。「送料の判定に触った」という事実から、影響が及びそうな場所を先に列挙してから、テストの形にしてください。

| # | 確かめること | なぜ影響を受けそうか |
| --- | --- | --- |
| 1 | | |
| 2 | | |
| 3 | | |
| 4 | | |

書けたら、次を確かめてください。

- 4 件のうち、料金計算 API の外側(表示・メール・集計など)に出ているものはいくつありますか。0 件なら、影響範囲の見立てが狭すぎるかもしれません
- 確認テストの表に書いた内容が、リグレッションテストの表にも混ざっていませんか。直した場所そのものは確認テストの担当です

最後に、いま書いた 7 件それぞれについて、自動化の価値を「高い / 中 / 低い」で判定し、理由を「何回流すか」の言葉で 1 行書いてください。

## 演習問題

### 問1(基本)

確認テストとリグレッションテストの目的の違いを、それぞれ 1 文で書いてください。

### 問2(基本)

確認テストで「修正前の版でも同じ手順を試す」のはなぜですか。

### 問3(応用)

ある現場では、リグレッションテストを手作業で 3 日かけて流しています。そのため、小さな修正のときは省略しています。この状態にどんなリスクがあり、どう手を打てるか書いてください。

### 問4(応用)

「確認テストは 1 回しか流さないから、自動化する価値は低い」という意見があります。この意見に一部同意しつつ、別の見方を添えて答えてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

確認テストは「直した欠陥が本当に直ったか」を確かめるテストです。リグレッションテストは「変更が別の場所を壊していないか」を確かめるテストです。前者は直した場所、後者はそれ以外が対象で、目的が違うので両方が必要になります。

</details>

<details>
<summary>問2の解答例</summary>

修正前で再現しないなら、その手順ではもともと故障が起きなかったということになり、修正後に起きなくても「直った」証拠になりません。修正前で再現し、修正後で再現しない。この 2 つがそろって初めて直ったと言えます。

</details>

<details>
<summary>問3の解答例</summary>

リスクは、省略した回に限って別の場所が壊れ、それがリリース後に発覚することです。小さな修正ほど影響は無いと思われがちですが、送料の判定を 1 行直した例のように、変更の大きさと影響の広さは比例しません。手としては、繰り返し流すテストから順に自動化することです。特に、コンポーネントテストのレベルまで下ろせるものは実行が速く、毎回流しても負担になりません。

</details>

<details>
<summary>問4の解答例</summary>

「直ったかを見る」用途としては 1 回で終わるので、その意味では同意できます。ただし、そのテストケースを捨てずに残せば、次の変更からはリグレッションテストの一部として繰り返し流されます。そう考えると、確認テストは自動化した資産の入口です。一度出た欠陥を二度と同じ形で出さない、という守りがここで積み上がります。

</details>

## 確認クイズ

### Q1. 確認テストが確かめるものはどれですか。

- A. 変更していない機能が壊れていないか
- B. 発注者が業務として使えるか
- C. 直した欠陥が本当に直ったか

<details>
<summary>答え</summary>

**C** — 修正後に、故障を再現させた手順をもう一度なぞります。再現手順がそのままテストケースになります。

</details>

### Q2. リグレッションテストが確かめるものはどれですか。

- A. 変更が別の場所を壊していないか
- B. 修正した箇所が仕様どおりに直ったか
- C. 新しく追加した機能の性能

<details>
<summary>答え</summary>

**A** — 変更前に動いていた部分がいまも動くことを確かめます。中身は既存のテストケースの再実行です。

</details>

### Q3. 確認テストで、修正前の版でも同じ手順を試すのはなぜですか。

- A. 修正前の版の性能を測るため
- B. もともと再現しなかっただけ、という可能性を除くため
- C. 修正前の版に戻す準備をするため

<details>
<summary>答え</summary>

**B** — 修正前で再現し、修正後で再現しない。この 2 つがそろって初めて直ったと言えます。

</details>

### Q4. 自動化の価値を判断する軸として、このレッスンで示したものはどれですか。

- A. そのテストを何回流すか
- B. そのテストを誰が作ったか
- C. そのテストが属するテストレベルの名前

<details>
<summary>答え</summary>

**A** — 繰り返し実行するテストほど、自動化の価値が高くなります。1 回しか流さないテストの自動化は割に合いません。

</details>

### Q5. 確認テストのケースを捨てずに残すと、何が起きますか。

- A. 確認テストとしての効力が失われる
- B. 次の変更からはリグレッションテストの一部として繰り返し流される
- C. テストレベルがシステムテストに変わる

<details>
<summary>答え</summary>

**B** — 一度出た欠陥を二度と同じ形で出さないための守りとして積み上がります。だから確認テストの自動化にも価値が出ます。

</details>
