# レッスン2-1 演習 — テストレベル

対象トピック: 2-1-1 〜 2-1-5

## 手元で試す

このレッスンにも実行するコードはありません。レッスン1-1 から使っているファイルに書き足してください。

題材は、この講座で通して使うオンラインストアです。次の 2 つを対象にします。

- **会員登録フォーム** — メールアドレス・パスワード・生年月日を入力して登録する
- **料金計算 API** — 購入額と会員区分を受け取り、割引額・送料・請求額を返す(送料は購入額 3,000 円以上で無料)

まず、この 2 つについて「確かめたいこと」を思いつくままに 8 個書き出してください。粒度はばらばらで構いません。

次に、書いた 8 個を 4 つのレベルに振り分けます。

| レベル | 振り分けた項目 |
| --- | --- |
| コンポーネント | |
| 統合 | |
| システム | |
| 受け入れ | |

振り分けたら、次を確かめてください。

- 空欄になったレベルはありますか。そこは、いま自分の頭から抜け落ちているレベルです
- コンポーネントの欄に「画面で〜する」と書いていませんか。画面が出てきたら、それはコンポーネントより上のレベルです
- 受け入れの欄には「動くか」ではなく「使えるか」の言葉で書けていますか

最後に、統合の欄の項目を 1 つ選び、つなぎ目で起きうる食い違いを「形式・単位・想定外の値・順序」の 4 つの型に当てはめて、1 つずつ書き出してください。4 つ全部が埋まらなくても構いません。埋まらなかった型は、その部品では起きにくい理由を 1 行で説明してみてください。

## 演習問題

### 問1(基本)

次の 4 つは、それぞれどのテストレベルの作業ですか。

1. 送料を計算する関数に 2,999 を渡して、戻り値が 500 であることを確かめる
2. 会員登録フォームから送った生年月日が、会員登録 API に正しい形式で届くことを確かめる
3. 発注者が自分の業務手順どおりに操作して、運用を開始してよいか判断する
4. 新規会員として登録し、そのまま初回注文を完了できることを確かめる

### 問2(基本)

コンポーネントテストを「速い」と表現するとき、速さは何の役に立ちますか。2 つ挙げてください。

### 問3(応用)

会員登録 API の担当者は「自分のテストは全部通っている」と言い、フォームの担当者も同じことを言っています。それでも生年月日がずれて保存されます。この状況を、テストレベルの言葉で説明してください。

### 問4(応用)

ある案件で、システムテストが全件合格したあとの受け入れテストで「この画面では業務が回らない」と指摘されました。この指摘は欠陥でしょうか。理由を添えて答えてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

1 はコンポーネントテスト、2 は統合テスト、3 は受け入れテスト、4 はシステムテストです。判断の手がかりは「何を 1 つのかたまりとして扱っているか」です。1 は関数 1 つ、2 は 2 つの部品の間、4 は通しの流れ、3 は業務としての目的です。

</details>

<details>
<summary>問2の解答例</summary>

1 つは、数を打てることです。1 件が一瞬で終わるので、入力のパターンを多く試せます。もう 1 つは、変更のたびに気軽に流せることです。速いテストは省かれずに残り、結果として変更のたびに壊れていないかを確かめられます。

</details>

<details>
<summary>問3の解答例</summary>

どちらもコンポーネントテストのレベルまでしか行っていない、という状況です。それぞれの部品の中身は仕様どおりでも、日付の形式についての約束の解釈が両者で違っています。この食い違いは部品の内側には無く、つなぎ目にあります。統合テストのレベルを誰も担当していないことが原因です。

</details>

<details>
<summary>問4の解答例</summary>

仕様どおりに動いているなら、それは欠陥ではなく「求めていたものとの差」です。受け入れテストは「仕様どおりか」ではなく「業務で使えるか」を問うレベルなので、この指摘はそのレベルで正しく出た結論だと言えます。対処は修正ではなく、要望の聞き方や仕様の決め方に返す形になります。ただし、その差を受け入れテストまで持ち越したこと自体は、進め方の課題として残ります。

</details>

## 確認クイズ

### Q1. テストレベルは何によってテストを分けた区分ですか。

- A. テストを担当する人の経験年数
- B. テストの対象とするかたまりの大きさ
- C. テストにかかる時間の長さ

<details>
<summary>答え</summary>

**B** — テストは対象の大きさごとに 4 つのレベルに分けて行います。レベルが違えば、目的も見つかる欠陥の種類も変わります。

</details>

### Q2. コンポーネントテストの説明として正しいものはどれですか。

- A. 画面から通しで操作して、業務が回るかを確かめる
- B. 発注者が受け取ってよいかを判断する
- C. 関数やクラスの単位で、小さく速いテストを数多く回す

<details>
<summary>答え</summary>

**C** — 対象が小さいので速く、失敗したときに疑う場所も狭くて済みます。速いから数を打てます。

</details>

### Q3. 「金額を送る側は円、受ける側は銭として扱っていた」という欠陥は、どのレベルで狙うのが適切ですか。

- A. 統合テスト
- B. コンポーネントテスト
- C. 受け入れテスト

<details>
<summary>答え</summary>

**A** — 部品どうしのつなぎ目に潜む欠陥は統合テストで狙います。送る側・受ける側のどちらを単体で見ても正しく見えるため、つないだ状態でしか表に出ません。

</details>

### Q4. システムテストの視点として正しいものはどれですか。

- A. 関数の内部の分岐をすべて通す
- B. 利用者の視点で全体の振る舞いを確かめる
- C. 部品どうしの受け渡しの形式だけを確かめる

<details>
<summary>答え</summary>

**B** — 見る単位が「部品」から「利用者がやりたいこと」に変わります。ここで見つかる欠陥は、流れが途切れる形で現れます。

</details>

### Q5. 受け入れテストがほかのレベルと最も違う点はどれですか。

- A. 発注者や利用者が主体となり、「使えるか」を判断する
- B. テスト担当者が仕様書との一致だけを確認する
- C. 開発者がコードの構造を根拠にテストを作る

<details>
<summary>答え</summary>

**A** — ほかの 3 レベルは「作ったものが正しいか」を見ますが、受け入れテストは「求めたものが届いたか」を見ます。結論も、欠陥の一覧ではなく受け取る / 受け取らないになります。

</details>
