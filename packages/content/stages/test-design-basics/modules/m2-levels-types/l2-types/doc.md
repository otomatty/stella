# レッスン2-2 テストタイプ

## このレッスンの目標

- [ ] 機能テストと非機能テストの問いの違いを説明できる
- [ ] ブラックボックスとホワイトボックスの根拠の違いを説明できる
- [ ] テストレベルとテストタイプが別の軸であることを説明できる

## 2-2-1 機能テスト

> **機能テストは「仕様どおりに動くか」を確かめる**

「テストの一覧を出して」と言われて、操作の手順だけが並んだ表を出したことはないでしょうか。手順は書けても、それが何を確かめたテストなのかは読む人に伝わりません。

前のレッスンで扱ったテストレベルは「どこで」テストするかの軸でした。ここからは「何を」確かめるかの軸を足します。この軸で分けたまとまりを **テストタイプ** と呼びます。

その代表が **機能テスト** です。決められた入力に対して、決められた結果になるかを見るテストタイプです。

| 確かめること | 期待する結果 |
| --- | --- |
| 正しい入力で登録する | 会員が 1 件登録される |
| メールアドレスを空で送る | エラーが表示され、登録されない |
| 登録済みのメールアドレスを送る | 重複エラーが表示される |

どれも「そうなると決めてあること」を確かめています。表の 1 行が 1 テストケースに対応します。

テストタイプはテストレベルと直交する軸です。つまり、コンポーネントテストでも機能テストはできますし、システムテストでも機能テストはできます。「どこで」と「何を」は別々に決めるものだと覚えてください。

## 2-2-2 非機能テスト

> **非機能テストは性能や使いやすさなど「どう振る舞うか」を確かめる**

料金計算 API が、正しい金額を返している。しかし応答に 8 秒かかる。「動いています」と報告しても、利用者からは「使えない」と言われます。

**非機能テスト** は、結果の正しさではなく、その出しかたの性質を見るテストタイプです。機能テストが「何を返すか」を問うのに対して、非機能テストは「どう返すか」を問います。品質は、この両方で決まります。

| 見る性質 | 確かめること |
| --- | --- |
| 性能 | 同時 100 件でも 1 秒以内に返るか |
| 使いやすさ | エラー文で利用者が次の操作を選べるか |
| セキュリティ | 他人の会員 ID の金額を引けないか |
| 移植性 | 主要なブラウザーで表示が崩れないか |

非機能テストには 1 つ注意点があります。基準の数値を先に決めておかないと、テストになりません。「速いこと」は合否を判定できませんが、「1 秒以内」なら判定できます。「使いやすいこと」も同じで、何をもって使いやすいと言うのかを決める必要があります。

基準が決まっていない非機能要件を見つけたら、それを指摘するのもテスト担当者の仕事です。この考え方は、曖昧な仕様への向き合い方としてあとのモジュールでも扱います。

## 2-2-3 ブラックボックステスト

> **ブラックボックステストは中身を見ず、入力と出力だけで確かめる**

コードを読んでからテストを作ると、実装と同じ勘違いをそのまま写してしまうことがあります。「この条件は `>` でよい」と実装者が思い込んでいれば、テストも `>` を前提に書かれ、両方そろって間違ったまま合格します。

**ブラックボックス** は、内部の作りを見ずに、仕様だけを根拠にテストを作る考え方です。

| 入力(購入額) | 期待する送料 | 根拠 |
| --- | --- | --- |
| 2,999 円 | 500 円 | 3,000 円未満は有料 |
| 3,000 円 | 0 円 | 3,000 円以上は無料 |

この表では、関数の中で条件をどう書いているかを一切見ていません。根拠の列に仕様の文が入っていることが、ブラックボックスの目印です。

根拠が仕様なので、実装を書き換えてもテストは生き残ります。関数を 2 つに分けようが、内部の書き方を変えようが、「3,000 円で送料が 0 円になる」という約束が変わらない限り、このテストはそのまま使えます。この講座で扱う技法の大半はこちら側です。

## 2-2-4 ホワイトボックステスト

> **ホワイトボックステストはコードの構造を見てテストを作る**

仕様から作ったテストは全部通ったのに、コードには一度も通らない行が残っていた。そこに書かれていた例外処理が、本番で初めて実行されて落ちた。こうしたことが起こります。仕様だけを根拠にすると、実装にしか存在しない道を踏み損ねるからです。

**ホワイトボックス** は、内部の分岐や処理の流れを根拠にテストを作る考え方です。目的は「まだ通していない道を探す」ことにあります。対象が小さいほど道を数えやすいので、コンポーネントテストと相性がよい進め方です。

| | ブラックボックス | ホワイトボックス |
| --- | --- | --- |
| 根拠 | 仕様 | コードの構造 |
| 得意 | 仕様の見落とし | 通っていない分岐 |
| 苦手 | 実装だけにある道 | 書かれていない機能 |

どちらが上ということはありません。見つけられない欠陥の種類が違うだけです。ホワイトボックスだけでテストを作ると、「そもそも実装されていない機能」には永遠に気づけません。コードに無いものは、コードを見ても出てこないからです。

だから両方を重ねます。まず仕様を根拠にテストを作り、そのあとで「コードのどこを通っていないか」を確かめる。この順番は、あとのモジュールでカバレッジを扱うときにもう一度出てきます。

## もっと知りたい人へ

- 現場では「単体テスト = ホワイトボックス」と対応づけて語られることがありますが、これは正確ではありません。コンポーネントテストのレベルでも、仕様を根拠にすればブラックボックスです。レベルとタイプ、そして根拠は、それぞれ別の軸です
- 非機能テストの分類は、品質特性の一覧として整理されています。現場の非機能要件を書くときは、性能・使いやすさ・セキュリティ・移植性といった観点の一覧を手元に持っておくと、抜けに気づきやすくなります
