# レッスン5-3 欠陥レポート

## このレッスンの目標

- [ ] 欠陥レポートを、再現手順・期待・実際・環境の 4 部で書ける
- [ ] 「動きません」のような曖昧な表現を、値に置き換えられる
- [ ] 深刻度と優先度を区別して付けられる

## 5-3-1 欠陥レポートの目的

> **欠陥レポートは、直す人が再現できるだけの情報を届ける文書である**

「検索が動きません」という 1 行の報告が届きます。開発者が試すと、普通に動きます。「再現しませんでした」で差し戻され、3 往復して、ようやく「商品名に空白を含めたときだけ」だと分かる。この 3 往復のあいだ、欠陥は 1 ミリも直っていません。

**欠陥レポート** は、見つけた故障を、直す人に伝えるための文書です。読み手は開発者で、ゴールは「読んで、手元で同じ故障を起こせる」ことです。文章の上手さではなく、**往復ゼロで再現できるか**が唯一の評価基準になります。

中身は 4 つの部品でできています。

| 部品 | 書くこと |
| --- | --- |
| 再現手順 | 環境と操作を、そのままなぞれる粒度で |
| 期待した結果 | 仕様ではこうなるはず |
| 実際の結果 | 実際にはこうなった |
| 環境 | ブラウザー・OS・アカウント・データ |

この 4 つで足ります。逆に、どれか 1 つ欠けると往復が始まります。

書かないほうがよいものもあります。

- **原因の推測を断定で書く**(「キャッシュのバグです」) — 原因を調べて直すのはデバッグの仕事で、テストの仕事ではありません。推測を書くなら「〜かもしれません」と添える程度にとどめます
- **誰かを責める書き方**(「またあの機能です」) — 読んだ人の手が止まります
- **複数の故障を 1 通にまとめる** — 片方だけ直った状態で閉じられ、もう片方が消えます

モジュール1で、テストは欠陥を見つける活動、デバッグは原因を探して直す別の活動だと確認しました。役割の線を越えないことが、結局いちばんの早道です。

## 5-3-2 再現手順

> **再現手順には環境と操作を、読んだ人がそのままなぞれる粒度で書く**

「カートで送料がおかしくなります」と報告しても、開発者が同じ画面を開くと送料は正しく出ます。あとで分かったのは、**クーポンを適用したあとに商品を追加したとき**だけの故障だったこと。報告した本人も、そのときは「カートを開いた」としか覚えていませんでした。

**再現手順** は、故障を起こすまでの操作を順番に並べたものです。粒度の基準は「その機能を知らない人が、迷わず同じ操作をできるか」です。

| | 書き方 |
| --- | --- |
| 悪い | カートで送料がおかしくなる |
| 良い | 1. 一般会員でログイン(test-user01) / 2. 商品「マグカップ 2,000 円」をカートに入れる / 3. クーポン `SEND100` を適用 / 4. 商品「ノート 1,500 円」を追加 / 5. カート画面の送料欄を見る |

番号付きで、1 行 1 操作。5 行あれば大抵の故障は再現できます。使ったデータ(商品名・金額・アカウント)は必ず具体値で書いてください。「適当な商品を入れる」は手順ではありません。どの商品かで結果が変わるからです。

環境も手順の一部です。次の 4 つは毎回書きます。

- ブラウザーと版(Chrome 126 / Safari 17)
- OS と端末(Windows 11 / iPhone 15、画面幅)
- アカウントとデータ(一般会員か、プレミアム会員か)
- いつ起きたか(日時。時間帯で変わる不具合があるため)

「私の環境では再現しません」の半分は、ここが書かれていないことが原因です。

テストケースを実行していて見つけた故障なら、そのケースの入力・手順がそのまま再現手順になります。ケース表を書いてから実行する利点の 1 つが、これです。

## 5-3-3 期待と実際

> **「動きません」ではなく、期待した結果と実際の結果の差分を書く**

手順を丁寧に 5 行書いても、最後の行が「送料の表示がおかしいです」だと止まります。開発者は手順どおり操作して、送料 500 円という表示を見て、「これで合っているのでは?」と返してきます。また 1 往復です。

手順が完璧でも、何が異常かを共有していないと進みません。書くのは 2 行です。

| 項目 | 書くこと |
| --- | --- |
| 期待した結果 | 送料は 0 円(購入額 3,500 円は 3,000 円以上のため。仕様書 4.2) |
| 実際の結果 | 送料 500 円と表示された(スクリーンショット添付) |

具体値と根拠の 2 点セットにします。「仕様書 4.2」のような根拠があると、実は仕様の解釈のほうが間違っていた、というときにすぐ分かります。期待を書かないレポートは、この可能性を最初から潰しています。

曖昧な言葉は、値に置き換えます。

| 曖昧 | 値で書くと |
| --- | --- |
| 動きません | ボタンを押しても画面が変わらない(エラー表示も出ない) |
| 遅いです | 検索結果が出るまで 14 秒(仕様は 3 秒以内) |
| 表示が変です | 金額が `¥1,500` ではなく `1500.0` と表示される |

値に置き換えると、期待との差が自動的に見えてきます。テストケースの期待結果を書くときと、まったく同じ作法です。受け入れ基準が書かれている機能なら、その文をそのまま期待の欄に引用できます。

## 5-3-4 深刻度と優先度

> **深刻度は影響の大きさ、優先度は直す順番で、別のものさしである**

トップページのロゴが旧ロゴのまま出ていました。画面は壊れていないので「軽微」と付けて報告したところ、翌朝、広報から「今日から新ブランドで発表するので最優先で直してほしい」と連絡が来ました。

影響の大きさと、直す急ぎ具合は一致しません。だから、ものさしを 2 本持ちます。

- **深刻度** — その故障が製品と利用者に与える影響の大きさ。テスト担当者が付けます
- **優先度** — いつ直すかの順番。事業の都合を含めて、開発側や企画が決めます

誰が付けるかが違う、と覚えるとずれにくくなります。だから、深刻度が低くても優先度が高い、その逆もありえます。

| | 優先度 高 | 優先度 低 |
| --- | --- | --- |
| **深刻度 高** | 請求額が二重に計上される | 誰も使っていない旧管理画面が落ちる |
| **深刻度 低** | 発表前日のロゴが旧版のまま | ヘルプページの誤字 |

右上と左下が「ずれる」例です。この 2 マスがあることを知っていれば、「軽微なのに最優先なんですか」という噛み合わない会話をせずに済みます。

付けるときのコツをまとめます。

- 深刻度は**事実**で決める(お金・データ・安全に影響するか)
- 優先度は**都合**で決まる(リリース日、発表、契約)
- 迷ったら、プロダクトリスクの見積もりを見る。影響の列がそのまま深刻度の材料になる
- 深刻度を勝手に上下させない。交渉するのは優先度のほう

未修正で残っている高深刻度の件数は、そのまま終了基準の判定材料になります。レッスン5-2 で書いた「未修正の重大欠陥がゼロ」という条件は、深刻度が付いていて初めて数えられます。

## もっと知りたい人へ

- 欠陥レポートの書式は、チームの課題管理ツールにテンプレートとして登録できます。4 部の見出しを空欄で置いておくだけで、書き漏れが減ります
- スクリーンショットや画面の録画は、実際の結果を伝える強力な補助です。ただし、画像だけでは検索できないので、文章は必ず書いてください
- 深刻度の段階(致命的・重大・中・軽微など)はチームごとに定義が違います。参加したら、まず定義表を確認してください
