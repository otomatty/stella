# レッスン5-2 演習 — リスクベースの優先順位

対象トピック: 5-2-1 〜 5-2-4

## 手元で試す

このレッスンは実行するコードがありません。**EC サイトのリリース 1 回ぶんを、リスク評価表から終了基準まで一気に設計します**。紙かエディタで手を動かしてください。

### ① リスク評価表を作る

次の状況だとします。

> **状況**: EC サイトの改修リリース。テスト期間は 2 週間、担当は 2 人。今回の変更は「送料無料の境目を 3,000 円から 5,000 円に変更」と「会員登録にパスワード強度チェックを追加」。

対象の 6 機能に、影響と起きやすさを「大・中・小」で付け、リスクレベルを決めてください。

| 機能 | 影響 | 起きやすさ | リスクレベル | 根拠 |
| --- | --- | --- | --- | --- |
| 送料計算 | | | | |
| 会員登録フォーム | | | | |
| 料金計算 API(請求額) | | | | |
| 注文ステータス遷移 | | | | |
| 商品検索 | | | | |
| お知らせの表示順 | | | | |

**根拠の列を必ず埋めてください**。「今回変更した」「過去に欠陥が多い」「お金に直結する」など、他の人が読んで納得できる一言で十分です。埋まらない行は、まだ見積もれていない行です。

### ② 厚みを決める

リスクレベルごとに、当てる技法とケース数の目安を書きます。

| リスクレベル | 当てる技法 | ケース数 |
| --- | --- | --- |
| 高 | | |
| 中 | | |
| 低 | | |

書けたら、①の 6 機能の合計ケース数を計算してください。2 人 × 2 週間で実行しきれる量になっていますか。多すぎる場合は、リスクレベルを下げるのではなく、**低リスクの厚みをさらに削る**ところから調整します。

### ③ 実行順と基準を書く

- ①の 6 機能を、実行する順番に並べ替えてください。並べ替えの理由(リスクレベル / 依存関係 / 欠陥の見つかりやすさ)をそれぞれに 1 語で添えます
- 開始基準を 3 行、終了基準を 3 行で書いてください
- 書いた終了基準を読み返し、「誰が見ても同じ判定になるか」を確かめます。「一通り確認できたら」のような行があれば、数値か状態に書き直してください

## 演習問題

### 問1(基本)

「めったに使われない管理画面の一括削除機能。使うのは月に 1 回、社内の担当者 1 人だけ。ただし誤動作すると全注文データが消える」— この機能の影響と起きやすさを見積もり、リスクレベルを判断してください。

### 問2(基本)

開始基準・終了基準を「テストを始める前」に決める理由を、1〜2 文で説明してください。

### 問3(応用)

次の終了基準を読んで、問題のある行を指摘し、書き直してください。

> 1. テストケースを一通り実行した
> 2. カバレッジが 100% になった
> 3. 重大なバグが出なくなった

### 問4(応用)

リリース前日、終了基準の「未修正の重大欠陥がゼロ」を 1 件だけ満たしていません。開発リーダーから「1 件くらい大丈夫でしょう。基準のほうを『重大欠陥 1 件まで可』に直しておいて」と言われました。どう対応しますか。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

- **影響: 大** — 全注文データが消えるのは、事業として復旧できない損害です
- **起きやすさ: 中〜低** — 月 1 回しか使われないので実行機会は少ないですが、その分テストも手薄で、欠陥が残っている可能性はあります
- **リスクレベル: 高**

利用頻度の低さで影響が薄まることはありません。「めったに起きないが、起きたら終わり」は厚く見るべき典型です。逆に、頻度の低さを理由に薄くすると、いちばん確認されない場所に最大の損害が残ります。

</details>

<details>
<summary>問2の解答例</summary>

終盤に決めると、そのとき通したい結論に合わせて基準がゆがむからです。あとから作った基準は、必ず達成できる形で書かれます。先に決めて関係者に見せておけば、判断が個人の度胸や、その日の空気から切り離せます。

</details>

<details>
<summary>問3の解答例</summary>

3 行とも書き直しが要ります。

| 元の行 | 問題 | 書き直し |
| --- | --- | --- |
| 一通り実行した | 「一通り」の範囲が人によって違う | 高リスク機能のケースが 100%、中リスクが 90% 以上実行済み |
| カバレッジ 100% | 書かれていないコードの欠陥は測れない。単独では基準にならない | 変更した関数のブランチカバレッジが 80% 以上(ほかの基準と併用) |
| 重大なバグが出なくなった | 出なくなったのか、探せていないのかが区別できない | 未修正の深刻度「高」がゼロ。直した欠陥の確認テストが全件完了 |

共通するのは、誰が見ても同じ判定になる形にすることです。

</details>

<details>
<summary>問4の解答例</summary>

基準を書き換えるのは断ります。基準を後から緩めると、その基準は今後どのリリースでも意味を持たなくなります。

代わりに、判断できる材料を渡します。

- その 1 件の深刻度が「高」である根拠(どんな損害が出るか)
- 回避策があるか(手動対応で凌げるか、影響する利用者は何人か)
- 直すのに必要な時間と、リリースを 1 日遅らせた場合の影響

そのうえで、「終了基準を満たしていない状態でリリースする」という判断を、責任を持つ人が明示的に下せる形にします。リリースを止める権限はテスト担当にはありませんが、**満たしていないと書く**ことはできます。基準を書き換えると、この記録が残りません。

</details>

## 確認クイズ

### Q1. プロダクトリスクの見積もり方として、正しいものはどれですか。

- A. 過去に欠陥が出た件数だけで決める
- B. 利用者の数が多い機能ほど高くする
- C. 壊れたときの影響と、欠陥が潜んでいそうな度合いを掛け合わせる

<details>
<summary>答え</summary>

**C** — 影響 × 起きやすさの 2 軸です。過去の欠陥数や利用者数は、それぞれ片方の材料にはなりますが、単独では決められません。

</details>

### Q2. リスクベースドテストで、低リスクの機能に対する扱いとして適切なのはどれですか。

- A. リスクが低くてもケース数は他と揃える。公平さが大事だから
- B. 代表値を 1 件通す程度に薄くし、その判断を根拠つきで書き残す
- C. まったくテストしない。低リスクなので不要

<details>
<summary>答え</summary>

**B** — 薄くする判断も、根拠を書けば設計です。手抜きとの違いは書いてあるかどうかだけで、ゼロにするのとも違います。

</details>

### Q3. テストの実行順を決める材料として、このレッスンで挙げていないものはどれですか。

- A. ケースを書いた人の担当年数
- B. リスクレベル
- C. 依存関係(前提になる機能)

<details>
<summary>答え</summary>

**A** — 材料はリスクレベル・依存関係・欠陥の見つかりやすさの 3 つです。誰が書いたかは順番の理由になりません。

</details>

### Q4. 終了基準として使えるものはどれですか。

- A. 不安がなくなったら終わり
- B. バグが出なくなったら終わり
- C. 高リスクのケースが 100% 実行済みで、未修正の重大欠陥がゼロ

<details>
<summary>答え</summary>

**C** — 誰が見ても同じ判定になります。A は人によって違い、B は探すのをやめても達成できてしまいます。

</details>

### Q5. 開始基準と終了基準を決める時期として、適切なのはどれですか。

- A. テストを始める前に決めて、関係者に見せておく
- B. テストの終盤に、状況を見ながら決める
- C. リリース判断の会議の場で、その都度決める

<details>
<summary>答え</summary>

**A** — 終盤に決めると、通したい結論に合わせて基準がゆがみます。先に決めることで、判断がその日の空気から切り離せます。

</details>
