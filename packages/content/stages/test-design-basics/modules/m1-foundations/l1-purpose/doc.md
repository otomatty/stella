# レッスン1-1 テストは何のためにあるか

## このレッスンの目標

- [ ] テストの目的を「品質の情報を届けること」として説明できる
- [ ] テストとデバッグ、品質保証とテストの関係を区別できる
- [ ] テストが実行だけでない一連の活動であることを説明できる

## 1-1-1 テストという活動

> **テストはソフトウェアの品質に関する情報を関係者に届ける活動である**

「テストは終わりましたか」と聞かれたとき、何と答えればよいか迷ったことはないでしょうか。「一通りやりました」と答えたのに、リリース後に問い合わせが来る。こうしたすれ違いは、テストの目的があいまいなまま作業だけを進めたときに起きます。

まず 2 つの言葉を決めておきます。**品質** とは、利用者の目的に対して、そのソフトウェアがどれだけ役に立つかのことです。そして **テスト** は、その品質がいまどうなっているかを調べて伝える活動です。

ここで大事なのは、テストの成果物が「見つけた不具合そのもの」ではないという点です。テストが本当に生み出しているのは、**関係者が判断に使える情報** です。

| 相手 | 知りたいこと |
| --- | --- |
| 開発者 | どこがどう壊れているか |
| 開発リーダー | 出せる状態か、あと何が残っているか |
| 発注者 | 期日どおりに使い始めてよいか |

同じテスト結果でも、相手によって伝えるべき粒度は変わります。開発者には再現できるだけの詳しさが要りますが、発注者に必要なのは「出してよいか」という判断材料です。この「誰に何を届けるか」という視点は、この講座の最後(品質の報告)でもう一度扱います。

## 1-1-2 テストとデバッグ

> **テストは欠陥を見つける活動で、デバッグは原因を探して直す別の活動である**

テストの途中で気になる挙動を見つけ、そのまま原因を追いかけて半日が過ぎた。よくある光景です。あとで「テストに時間がかかりました」と報告することになりますが、実際に時間を使ったのは原因調査でした。

この 2 つは別の作業です。**欠陥** とは、コードや設計に埋め込まれた正しくない箇所を指します。そして **デバッグ** は、その欠陥の位置と原因を突き止めて修正する作業です。

| | テスト | デバッグ |
| --- | --- | --- |
| 目的 | 欠陥があることを示す | 欠陥を取り除く |
| 出力 | 「この操作で結果が違う」 | 「この行の条件が逆だった」 |
| 終わり方 | 報告した時点 | 直って再確認できた時点 |

同じ人が両方を担当することは珍しくありません。それでも、いま自分がどちらをしているかを意識できると、時間の使い道を説明できるようになります。「テストを 2 時間、原因調査を 3 時間」と分けて報告できれば、次の見積もりの精度も上がります。

## 1-1-3 品質保証とテスト

> **品質保証(QA)はプロセス全体を良くする活動で、テストはその一部である**

不具合が出るたびに「テストが甘い」と言われる現場があります。しかしテストを増やしても、同じ種類の不具合が翌月また出てきます。出口だけを厚くしても、入口の作り方が変わっていないからです。

**品質保証**(QA)とは、良いものが出来上がる作り方そのものを整える活動です。テストは、その作り方が機能しているかを確かめる手段のひとつにすぎません。

| 打ち手 | 効く場所 |
| --- | --- |
| 仕様のレビュー | 作る前 |
| コーディング規約 | 作っている最中 |
| **テスト** | 出来上がったもの |
| ふりかえり | 次の周回 |

「QA 担当 = テストをする人」と理解されていることがありますが、これは狭すぎる読み方です。テストだけを厚くしても、残りの 3 つが弱いままなら同じ不具合は戻ってきます。テスト担当者が仕様のレビューに参加したり、見つけた欠陥の傾向をふりかえりに持ち込んだりするのは、この 4 つを回すための動きです。

## 1-1-4 テストは実行だけではない

> **テストは実行だけでなく、計画・分析・設計・実装・完了報告まで含む一連の活動である**

「テストは 3 日で」と言われたとき、多くの人は動かす時間だけを思い浮かべます。そして実際に動かす段になって「何を確かめるんでしたっけ」と手が止まります。確かめる内容を決める時間が、どこにも計上されていなかったからです。

テストは一連の活動です。この流れを **テストプロセス** と呼びます。そして中でも「何をどう確かめるか」を決める作業が **テスト設計** で、この講座の中心になります。

| 活動 | やること |
| --- | --- |
| 計画 | どこまでやるか、いつ終わるかを決める |
| 分析 | 仕様から「何をテストすべきか」を洗い出す |
| 設計 | **テストケース**(確かめる手順 1 本)を作る |
| 実装 | 手順やテストコードを実行できる形にする |
| 実行 | 実装したテストを走らせ、結果を記録する |
| 完了報告 | 結果をまとめ、判断材料として届ける |

**テストケース** は、確かめることを 1 本の手順として書いたものです。ここでは「テストの最小単位」という程度の理解で構いません。何をどう書くかは、技法を扱うモジュールで正面から扱います。

「実装」と「実行」は別の活動です。手順やコードを実行できる形にするまでが実装で、それを走らせるのが実行です。そして 6 つのうち、コードの完成を待たないと始められないのは実行だけです。分析と設計は、コードが完成していなくても始められます。この性質が、あとで学ぶ「早く始めるほど安い」という原則につながっていきます。

## もっと知りたい人へ

- 「テスト」「QA」「品質保証」は、現場によって指す範囲が違います。新しい現場に入ったら、その組織でこれらの語が何を指しているかを最初に確認しておくと、期待のずれを防げます
- テスト担当と開発担当が分かれていない小さなチームでも、テストプロセスの 6 つの活動そのものは無くなりません。誰が担うかが変わるだけです
