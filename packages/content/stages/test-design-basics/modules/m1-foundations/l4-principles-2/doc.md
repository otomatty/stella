# レッスン1-4 テストの 7 原則 II

## このレッスンの目標

- [ ] 同じテストを回し続けたときに起きることを説明できる
- [ ] テストのやり方が対象と状況で変わる理由を説明できる
- [ ] 欠陥ゼロが目的ではないことを説明できる

## 1-4-1 殺虫剤のパラドックス

> **同じテストを繰り返すだけでは、新しい欠陥は見つからなくなる**

毎回同じ 200 件のテストを回し、いつも全部通る。品質は安定している、と思っていたら利用者から不具合の連絡が来る。緑が続くこと自体は、安心の根拠になりません。

同じ薬をまき続けると虫が効かなくなる様子になぞらえて、この現象を **殺虫剤のパラドックス** と呼びます。理由は単純で、そのテストケースが狙っていた欠陥は、もう取り除かれているからです。同じ入力を何度通しても、同じ結果が返るだけです。

だからといって、既存のテストが無駄なわけではありません。テストには 2 つの使い道があり、その 2 つで価値の減り方が違います。

| テストの使い道 | 同じケースを回す価値 |
| --- | --- |
| 壊れていないことを守る | 高い。毎回回してよい |
| 新しい欠陥を見つける | 下がり続ける。ケースを足す・見直す |

守る力は落ちません。変更のたびに回せば、動いていたものが壊れたことをすぐ教えてくれます。落ちるのは **見つける力** のほうです。

実務での答えは、既存ケースを資産として残しつつ、見つけるための新しいケースを定期的に足すことです。仕様が変わった場所、最近手を入れた場所、これまで誰も試していない入力。こうした「まだ薬をまいていない場所」を探すのが、テスト設計を続ける理由になります。

## 1-4-2 テストはコンテキスト次第

> **正しいテストのやり方は、対象と状況によって変わる**

前の案件のテスト計画書をそのまま流用したくなることがあります。手順の再利用そのものは悪くありませんが、前提の確認を飛ばすと、対象に合わないやり方を持ち込むことになります。結果として、過剰か不足のどちらかになります。

**コンテキスト** とは、対象の性質、失敗したときの影響、期日、体制といった前提条件のことです。テストに唯一の正解手順は無く、このコンテキストに合わせて選びます。

| 対象 | 失敗の影響 | テストのやり方 |
| --- | --- | --- |
| 社内の勉強会申込 | 申し込み直し | 主要な流れを手で確認 |
| 医療機器の患者登録 | 人命に関わる | 記録を残し、第三者が再確認 |

どちらも「名前とメールアドレスを登録する画面」かもしれません。機能の見た目は同じでも、失敗したときの影響が違えば、かけるべき厚みは変わります。1-3-4 でモジュールごとに厚みを変えたのと同じ発想を、案件全体に広げたものだと考えてください。

新しい現場に入ったら、まずコンテキストを確認してください。「この機能が止まると誰が困るか」「どれくらいの頻度でリリースするか」「テストの記録はどこまで残す必要があるか」。この 3 つが分かると、やり方の当たりが付きます。

## 1-4-3 欠陥ゼロの落とし穴

> **欠陥を全部直しても、利用者の役に立たなければ失敗である**

報告された欠陥をすべて直し切って、自信を持ってリリースする。ところが利用者からは「これでは業務に使えない」と言われる。作業としては完璧なのに、結果が伴わない状態です。

これを **欠陥ゼロの落とし穴** と呼びます。品質は欠陥の数ではなく、目的をどれだけ果たせるかで決まるからです。

| 見ているもの | 判定 |
| --- | --- |
| 欠陥の件数 | 0 件。仕様どおり動く |
| 利用者の目的 | 1 件の申請に 15 画面。誰も使わない |

仕様どおりに動くことと、役に立つことは別です。仕様そのものが利用者の目的に合っていなければ、その仕様を完璧に満たしても失敗になります。

ここで 1-1-1 に戻ります。テストの目的は、品質に関する情報を関係者に届けることでした。届ける情報は「欠陥が何件あったか」だけではありません。「この流れは操作が多すぎて、現場では使われないと思われる」という気づきも、立派な品質の情報です。欠陥ゼロは手段であって、目的ではありません。

Module 1 はここまでです。テストとは何か、何を見つけようとしているのか、そしてテストという活動が持つ性質を押さえました。次のモジュールからは、この活動を「どこで・何を」やるかという地図に入っていきます。

## もっと知りたい人へ

- 殺虫剤のパラドックスへの対処として、既存のテストケースを定期的に見直す時間をあらかじめ計画に入れておく現場があります。新しいケースを足す作業は、意識して枠を取らないと後回しになりがちです
- 「使いにくい」という気づきを欠陥として報告してよいかは、現場のルールによります。欠陥として扱われない場合でも、記録に残して次の仕様を決める場に持ち込む価値はあります
