# レッスン1-3 テストの 7 原則 I

## このレッスンの目標

- [ ] 「バグはありません」と言えない理由を説明できる
- [ ] 全数テストが不可能なことを、数を挙げて説明できる
- [ ] テストを早く始める理由と、厚みを偏らせる理由を説明できる

## 1-3-1 欠陥がないことは示せない

> **テストは欠陥の存在は示せるが、欠陥がないことは証明できない**

テストが全部通ったとき、つい「バグはありません」と報告してしまいがちです。ところがリリース後に不具合が出ると、その一言のせいで報告そのものの信用が落ちます。

長年言われてきた **テストの原則** の 1 つ目が、これを戒めるものです。テストが緑になっても、それは **用意したテストの範囲では故障が起きなかった** という意味しかありません。試していない入力は必ず残っています。前のレッスンで見たとおり、欠陥は「それを通る入力」が来るまで表に出ないからです。

では、どう報告すればよいでしょうか。

| 言い方 | 評価 |
| --- | --- |
| 「バグはありません」 | 証明できないことを言っている |
| 「設計した 42 件で故障は出ませんでした」 | 事実。範囲が読み手に伝わる |

下の言い方には範囲が添えられています。読み手は「では、その 42 件はどこを見ているのか」と次の質問ができます。これは 1-1-1 で扱った「判断に使える情報を届ける」ことそのものです。範囲を隠さないほうが、結果的に信用されます。

## 1-3-2 全数テストは不可能

> **入力の組み合わせは爆発するので、すべてを試すことはできない**

「念のため全パターン試しておいて」と頼まれることがあります。素直に数え始めると終わらず、結局その場の勘で数件だけ選ぶことになります。全部やるか、勘でやるかの二択になっている状態です。

考えうる入力をすべて試すことを **全数テスト** と呼びます。そして現実の機能では、テストケースの数がすぐに天文学的になります。8 文字のパスワードで数えてみます。

| 使える文字 | 組み合わせ |
| --- | --- |
| 数字だけ(10 種) | 1 億通り |
| 英小文字 + 数字(36 種) | 約 2.8 兆通り |
| 英大小 + 数字 + 記号(94 種) | 約 6,000 兆通り |

最後の行を 1 件 0.001 秒で試せたとしても、終わるまでに 20 万年かかります。これは入力欄 1 つの話です。実際の画面には入力欄が何個も並び、それぞれの組み合わせが掛け算で効いてきます。

つまり、テストは **必ず選ぶ** ことになります。問題は選ぶかどうかではなく、**選び方に根拠があるか** です。勘で 5 件選ぶのと、技法で 5 件選ぶのとでは、同じ 5 件でも見つかる欠陥の量が変わります。この講座の中心である設計技法は、この根拠を与えるためにあります。

## 1-3-3 早期テストの原則

> **テストは早く始めるほど、欠陥を安く直せる**

コードが完成してからテストを始め、そこで仕様の矛盾に気づく。直すには設計からやり直しですが、期日はもう目の前です。よくある行き詰まり方です。

**早期テスト** とは、実行より前の活動、つまり仕様のレビューやテスト設計から始めることです。1-1-4 で見たとおり、テストプロセスの分析と設計は、コードが無くても始められます。仕様を読んでテストケースを作ろうとすると、その時点で「この条件のときどうなるのか書いていない」といった抜けが見つかります。

早く見つけるほど得をする理由は、直す対象の数で見ると分かりやすくなります。

| 見つけた時期 | 直すもの |
| --- | --- |
| 仕様レビュー | 仕様書の一文 |
| テスト設計 | 仕様書 + 設計書 |
| コード完成後 | 設計 + コード + 既存のテスト |
| リリース後 | 上の全部 + 影響を受けた利用者への対応 |

下に行くほど、1 件の修正が巻き込む範囲が増えます。リリース後まで行くと、技術的な修正に加えて、問い合わせ対応やお詫び、データの復旧といった作業がぶら下がります。同じ 1 文字の間違いでも、気づいた時期でコストが二桁変わることは珍しくありません。

## 1-3-4 欠陥の偏在

> **欠陥は少数のモジュールに集中する**

限られた時間を、全機能に均等に配りたくなります。公平に見えるからです。しかしふたを開けると、不具合は特定の 1 機能からばかり出ています。

**モジュール** とは機能のまとまりのことで、画面 1 つ、API 1 本といった単位を指します。そして欠陥がごく一部のモジュールに集中する傾向を **欠陥の偏在** と呼びます。複雑な計算がある、仕様変更が続いている、担当者が何度も替わった、といった場所に集まります。

偏っているのなら、テストの厚みも偏らせるのが合理的です。

| モジュール | 出た欠陥 | 次のテストの厚み |
| --- | --- | --- |
| 料金計算 | 18 件 | 厚く |
| 会員登録 | 3 件 | 標準 |
| お知らせ表示 | 0 件 | 薄く |

過去に出た欠陥の数は、次にどこが壊れるかの手がかりになります。ただし、薄くする側をゼロにはしません。欠陥が出ていないのは「本当に堅い」のか「まだ誰も試していない」のか、区別が付かないからです。薄くしても、主要な流れは必ず 1 本通しておきます。

なお、厚みを決める材料は過去の欠陥数だけではありません。壊れたときの影響の大きさも効いてきます。この考え方は、リスクを扱うモジュールで正面から扱います。

## もっと知りたい人へ

- 「テストが全部通った」という報告に範囲を添える習慣は、そのままテスト完了報告の書式につながります。件数だけでなく「どの機能を、どの観点で」まで書けると、読み手が次の判断をできます
- 早期テストは「テスト担当が早く動く」だけの話ではありません。仕様を書く人が「これはどうテストするのか」を書きながら考えると、仕様そのものが具体的になります
