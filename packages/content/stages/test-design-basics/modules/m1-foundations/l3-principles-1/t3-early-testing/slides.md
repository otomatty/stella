# 早期テストの原則

テスト設計入門 — Module 1 / レッスン1-3

<!-- ノート: 3つ目の原則。テストの開始時期を、コードが出来上がった後から前へずらす話です。 -->

---

## なぜ必要か

- コードが完成してからテストを始め、そこで仕様の矛盾に気づく
- 直すには設計からやり直しで、期日はもう目の前にある

<!-- ノート: つかみ。見つけた時期が遅いほど、直す範囲が広がる。ここで結論は言わない。 -->

---

## 結論

**テストは早く始めるほど、欠陥を安く直せる**

- **早期テスト** — 実行より前の活動、つまり仕様のレビューやテスト設計から始めること
- 仕様を読んでテストケースを作る時点で、矛盾や抜けが見つかる

<!-- ノート: 結論を言い切る。テストプロセスの分析・設計は、コードが無くても始められる。ここが早期テストの実体。 -->

---

## 実務例: 見つけた時期と直す範囲

| 見つけた時期 | 直すもの |
| --- | --- |
| 仕様レビュー | 仕様書の一文 |
| テスト設計 | 仕様書 + 設計書 |
| コード完成後 | 設計 + コード + 既存のテスト |
| リリース後 | 上の全部 + 影響を受けた利用者への対応 |

<!-- ノート: 具体例の枠。金額ではなく「直す対象の数」で見せる。下に行くほど巻き込む範囲が増える。 -->
