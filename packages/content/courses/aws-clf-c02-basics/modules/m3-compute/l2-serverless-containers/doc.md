# レッスン3-2 サーバーレスとコンテナ

## このレッスンの目標

- [ ] サーバーレスの意味とLambdaの課金(リクエスト + 実行時間)を説明できる
- [ ] コンテナ・ECS・EKS・Fargateの関係を1文ずつで言える
- [ ] シナリオからEC2・Lambda・コンテナ系・Elastic Beanstalkを選び分けられる

## 3-2-1 Lambdaはサーバーレス

> **Lambdaはサーバーを管理せずにコードを実行でき、課金はリクエスト回数と実行時間で、待機中は0円**

「画像がアップロードされたら縮小する」だけの処理のために、24時間サーバーを起動しておくのは大げさです。EC2ならOSの管理も待機中の料金も発生します。

サーバーの存在を意識せずに使える提供形態を **サーバーレス** と呼びます。サーバーが無いのではなく、「見えない・管理しない」という意味です。**Lambda** はその代表で、コードを置くだけで、きっかけ(ファイルの到着、時刻など)に応じて実行されます。

| | EC2 | Lambda |
| --- | --- | --- |
| 管理するもの | OSから上すべて | コードだけ |
| 課金 | 起動している間ずっと | リクエスト回数 + 実行時間 |
| 向く処理 | 常時稼働のアプリ | きっかけに応じた短い処理 |

課金は「呼ばれた回数(リクエスト)」と「動いた時間(実行時間)」の2要素で決まり、待機中は0円です。この「待っている間は払わない」形がLambdaの経済的な効き目です。試験では「サーバーのプロビジョニング(事前準備)や管理なしで実行したい」「アイドル時間に課金されたくない」という言い回しでLambdaが答えになります。なお実行時間には上限があり、長時間動き続ける処理には不向きです。

## 3-2-2 コンテナはアプリを箱ごと運ぶ

> **コンテナはアプリと動作環境をひとまとめに運ぶ技術で、AWSではECSとEKSが実行を管理する**

「自分のPCでは動いたのに、サーバーでは動かない」の原因は、アプリの周りの環境(ライブラリやバージョン)の差です。アプリと依存する環境を1つに梱包して運ぶ技術が **コンテナ** です。

| | 仮想サーバー | コンテナ |
| --- | --- | --- |
| 梱包の単位 | OSごと | アプリと環境だけ |
| 起動 | 分単位 | 秒単位 |
| 同じ動き | 環境差でずれうる | どこでも同じ |

コンテナが多数になると、「どのサーバーでどのコンテナを動かすか」を管理する係が要ります。AWSの管理サービスは2つです。

- **ECS** — AWS独自のコンテナ管理サービス。AWSに閉じてシンプルに使いたいとき
- **EKS** — コンテナ管理の標準ソフトである **Kubernetes** のマネージド版。標準に合わせたい・既に使っているとき

CLF-C02ではこの1行ずつの選び分けまでで十分です。

## 3-2-3 Fargateはサーバーの面倒を見ない

> **Fargateを使うと、コンテナをホストサーバーの管理なしで実行できる**

ECSでコンテナを動かす場合も、載せる先のEC2インスタンスは誰かが管理しなければなりません。コンテナは軽くなったのに、土台のサーバー管理が残っています。

**Fargate** は、ECS / EKSの実行基盤になるサーバーレスなコンテナ実行環境です。「コンテナ版のサーバーレス」と覚えてください。

| 実行方式 | コンテナの土台 | 土台の管理 |
| --- | --- | --- |
| ECS on EC2 | EC2インスタンス | 自分 |
| ECS on **Fargate** | Fargate | AWS |

試験では「コンテナを使いたいが、サーバーのプロビジョニングや管理はしたくない」がFargateの合図です。コードだけを動かすならLambda、コンテナごと動かすならFargate、という並びで選択肢に出ます。

## 3-2-4 コンピュートの選び分け

> **常時動かす自由度ならEC2、イベントごとの短い処理ならLambda、丸ごと任せるならElastic Beanstalkと用途で選ぶ**

最後に1つ、**Elastic Beanstalk** を足します。コードを渡すと、裏でEC2・ELB・Auto Scalingなどの構成まで面倒を見てくれるPaaS型のサービスです。「デプロイを簡単にしたい」「環境ごと任せたい」が合図です。

コンピュートの判定表を作って締めます。

| 用途の一言 | 選ぶ |
| --- | --- |
| OSから自由に、常時稼働 | EC2 |
| きっかけごとの短い処理、管理ゼロ | Lambda |
| コンテナで動かす | ECS / EKS(土台を任せるならFargate) |
| コードを渡して環境は丸ごとおまかせ | Elastic Beanstalk |

迷ったときの判定順は次のとおりです。

1. 問題文に「コンテナ」とある? → ECS / EKS / Fargate
2. 「イベントのたび」「サーバー管理なし」? → Lambda
3. 「デプロイを簡単に」「環境ごと任せたい」? → Elastic Beanstalk
4. それ以外の自由なサーバー用途 → EC2

## もっと知りたい人へ

- Lambdaのきっかけ(トリガー)になる「イベント」の仕組みは、M6のEventBridgeでもう一度登場します
- Beanstalkを使っても、裏で動くのはEC2などおなじみの部品です。「隠れているだけで消えてはいない」という感覚は、M7の責任分担の理解にも役立ちます
