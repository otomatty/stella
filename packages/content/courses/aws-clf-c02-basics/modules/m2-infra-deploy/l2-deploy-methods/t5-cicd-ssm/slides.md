# 届ける流れと日常運用の自動化

AWS Cloud Practitioner 入門 — Module 2 / レッスン2-2

<!-- ノート: M2の締め。環境の構築(IaC)の次は、アプリを届ける流れと日々の運用も自動化する、というトピックです。 -->

---

## なぜ必要か

- 環境はテンプレートで作れるようになった。ではアプリの新しい版はどう届けるか
- 手作業のリリースは、手順漏れとやり直しの温床になる
- 数十台のサーバーへのパッチ適用も、1台ずつ入って作業するわけにいかない

<!-- ノート: つかみ。IaCで環境の構築は自動化した。残る手作業は「リリース」と「日常運用」の2つです。 -->

---

## 結論

**ビルドからデプロイまでの流れはCodePipeline、サーバー群の日常運用はSystems Managerが自動化する**

- コードの変更を自動でテスト・リリースまで運ぶ考え方を **CI/CD** と呼ぶ
- **CodePipeline** = CI/CDの流れ(パイプライン)を組み立てるサービス
- **Systems Manager** = 多数のサーバーの運用作業をまとめて行うサービス

<!-- ノート: 結論。どちらも「繰り返す手作業を仕組みに変える」道具です。 -->

---

## 最小の例

| 道具 | 一言 | 向く場面 |
| --- | --- | --- |
| **CodePipeline** | 届ける流れの自動化 | コード変更のたびにビルド〜デプロイを自動実行 |
| **Systems Manager** | 日常運用の一括化 | 多数のサーバーへのパッチ適用・コマンド一斉実行 |
| CloudFormation | 環境の構築の自動化 | 同じ環境を繰り返し作る(前トピック) |

<!-- ノート: 3つの並びで整理。作るのがCloudFormation、届けるのがCodePipeline、日々世話するのがSystems Manager。 -->

---

## 試験での聞かれ方

- 「コードの変更を自動でビルド・テスト・デプロイしたい」→ CodePipeline(CI/CD)
- 「多数のEC2へのパッチ適用を一元管理したい」→ Systems Manager
- 「同じ環境を繰り返し構築したい」→ CloudFormation(混同注意)

<!-- ノート: 補強枠。3つとも「自動化」で問われるので、作る・届ける・世話するの動詞で切り分けます。 -->
