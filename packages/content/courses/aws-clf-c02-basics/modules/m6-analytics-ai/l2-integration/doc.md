# レッスン6-2 つなぐサービス

## このレッスンの目標

- [ ] 疎結合の利点をSQSの動きで説明できる
- [ ] SQS(ためる)とSNS(配る)を使い分けられる
- [ ] EventBridge(きっかけ)とStep Functions(段取り)の役割を言える

## 6-2-1 SQSはキューで疎結合

> **SQSは処理の依頼をキューにためて、受け手が自分のペースで取り出せるようにする**

注文を受けるたびに後続の処理(在庫・請求)を直接呼ぶ作りだと、後続が落ちた瞬間に注文の受付ごと止まります。部品同士を直接つながない設計を **疎結合** と呼び、その基本部品が **キュー**(依頼を順番に並べる待ち行列)です。**SQS**(Simple Queue Service)はキューのマネージドなサービスです。

| | 直接呼ぶ(密結合) | SQSを挟む(疎結合) |
| --- | --- | --- |
| 後続が停止中 | 受付ごと失敗 | 依頼はキューに残る |
| 復旧後 | 依頼は消えている | たまった分から再開 |
| 急な大量注文 | 後続が溺れる | ペースを保って処理 |

効き目は「止まっても失わない」「急いでも溺れない」の2つです。試験では「コンポーネント間を疎結合にしたい」「処理の失敗でメッセージを失いたくない」がSQSの合図です。キューは基本的に1対1の受け渡しで、1対多の配信は次のSNSの出番です。

## 6-2-2 SNSは通知の一斉配信

> **SNSは、1つの知らせを複数の宛先へ同時に配るパブリッシュ/サブスクライブ型の通知サービス**

「注文が入った」をメール係・在庫係・分析係のすべてに知らせたいとき、1件ずつ個別に送る作りでは宛先が増えるたびに改修が要ります。

発行者はトピック(掲示板)へ置くだけ、購読者は受け取るだけ——この配信方式を **パブリッシュ/サブスクライブ**(pub/sub)と呼びます。**SNS**(Simple Notification Service)はそのマネージドなサービスです。

| 手順 | 起きること |
| --- | --- |
| 1 | 発行者が「注文成立」をトピックへ発行 |
| 2 | 購読しているメール・SQS・Lambdaへ同時に配信 |
| 3 | 宛先が増えても発行側は無変更 |

発行者が宛先を知らなくてよい、という点が疎結合の効き目です。SQSとの使い分けは1語で覚えます。

- **SQS = ためる**(依頼を1つの受け手が処理する。1対1)
- **SNS = 配る**(知らせを多くの受け手へ届ける。1対多)

SNSの後ろに複数のSQSをつなぎ、1つの出来事を複数の処理系へ分配する構成を「ファンアウト」と呼びます。名前だけ知っておけば十分です。

## 6-2-3 イベントで自動につなぐ

> **EventBridgeは出来事をきっかけに処理をつなぎ、Step Functionsは複数の処理の順番を管理する**

「ファイルが届いたら処理を始める」を人が見張るのは無駄です。出来事(イベント)をきっかけに処理が動く設計を **イベント駆動** と呼びます。

- **EventBridge** — イベントの受け付けと振り分けの係です。「注文成立が起きたらLambdaを動かす」のようなルールを置けます。毎晩2時に起動、のようなスケジュール起動も守備範囲です
- **Step Functions** — 複数ステップの流れ(ワークフロー)の進行係です。「検品→請求→発送」を順番に流し、失敗時の再試行や分岐も管理します

| 場面 | 使う |
| --- | --- |
| 出来事が起きたら処理を動かす | EventBridge |
| 決まった時刻に処理を起動する | EventBridge(スケジュール) |
| 複数の処理を順序立てて、失敗時は再試行 | Step Functions |

統合サービスの4点セットを1語ずつでまとめて、このモジュールを締めます。

**ためる=SQS、配る=SNS、きっかけ=EventBridge、段取り=Step Functions**

## もっと知りたい人へ

- Lambdaのきっかけ(トリガー)には、EventBridgeのほかS3のイベントやSQSのメッセージ到着もなれます。M3の「きっかけごとの短い処理」とここがつながります
- API Gatewayという「アプリの窓口(API)を作る」サービスも統合の仲間です。名前と役割だけ拾っておいてください
