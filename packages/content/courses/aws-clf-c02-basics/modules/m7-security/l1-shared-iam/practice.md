# レッスン7-1 演習 — 共有責任とIAM

対象トピック: 7-1-1 〜 7-1-5

## 手元で試す

共有責任の「動く境界」を自分の手で引くワークです。

1. 紙に3本の縦の柱を描き、上から EC2 / RDS / S3 と見出しを付ける
2. 各柱を上下に分け、上を「AWSの責任」、下を「利用者の責任」とする。境界線の高さを、右の柱ほど上げて(利用者の担当が減るように)描く
3. 次の項目を、それぞれの柱のどちら側かに書き込む: 物理警備 / ハードウェア / OSのパッチ / DBエンジンのパッチ / データの分類 / アクセス権の設定
4. 「データとアクセス権」だけは3本すべてで利用者側に来ることを、丸で囲んで確認する
5. 余白に、自分のAWSアカウント(または会社のアカウント)で「最初にやる3点セット」を書く(ルートにMFA / 日常用IAMユーザー / ルートは特別な作業だけ)

この1枚が、配点30%のドメイン2の核心です。M9の総復習でも見返してください。

## 演習問題

### 問1(基本)

共有責任モデルにおけるAWSの責任と利用者の責任を、「OF / IN」の対比を使ってそれぞれ1文で書いてください。

### 問2(基本)

「EC2のゲストOSへのパッチ適用」「RDSのデータベースエンジンへのパッチ適用」は、それぞれ誰の責任ですか。理由も1文ずつ添えてください。

### 問3(応用)

新しく入社したメンバー10人に、開発チーム用の権限を配ります。IAMのユーザー・グループ・ポリシーをどう組み合わせるのが定石か、最小権限の原則にも触れて説明してください。

### 問4(応用)

「EC2上のアプリにアクセスキーをハードコードしてS3へアクセスしている」というコードレビュー指摘を受けました。何が問題で、どう直すべきかを2〜3文で書いてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

AWSは Security OF the Cloud、つまりデータセンター・ハードウェア・基盤ソフトといったクラウド本体の安全に責任を持ちます。利用者は Security IN the Cloud、つまり自分のデータ・アクセス権の設定・OSやアプリの設定といったクラウドの中身の安全に責任を持ちます。

</details>

<details>
<summary>問2の解答例</summary>

EC2のゲストOSのパッチは利用者の責任です。EC2はIaaSで、OSから上は利用者の管理範囲だからです。RDSのDBエンジンのパッチはAWSの責任です。RDSはマネージドサービスで、エンジンの運用を任せる契約だからです。

</details>

<details>
<summary>問3の解答例</summary>

開発チーム用のIAMグループを作り、開発の仕事に必要な操作だけを許可するポリシーをグループに付けます。10人はIAMユーザーとして作成し、そのグループに入れます。個人に直接ポリシーを付けず、権限は「仕事に必要な最小限」に絞るのが最小権限の原則です。

</details>

<details>
<summary>問4の解答例</summary>

アクセスキーは長期に有効な鍵なので、コードに埋め込むと漏えい時に長期間悪用され、無効化・差し替えも大変です。EC2にS3への最小権限を持つIAMロールを付与し、アプリはロールが自動発行する一時的な認証情報を使う形に直します。これでコードから鍵そのものが消えます。

</details>

## 確認クイズ

### Q1. 共有責任モデルで、常に利用者の責任になるものはどれですか。

- A. データセンターの物理警備
- B. ハードウェアの保守
- C. 自分のデータの分類とアクセス権の設定
- D. 基盤となるネットワーク設備の維持

<details>
<summary>答え</summary>

**C** — データとアクセス権は、どのサービスを使っていても常に利用者側です。データセンターの物理警備・ハードウェアの保守・基盤ネットワークの維持は、クラウド本体(AWS側)です。

</details>

### Q2. 「RDSのデータベースエンジンへのパッチ適用」は誰の責任ですか。

- A. 利用者
- B. AWS
- C. サードパーティの監査法人
- D. 通信事業者

<details>
<summary>答え</summary>

**B** — RDSはマネージドサービスで、エンジンの運用はAWS側です。EC2に自分で入れたDBなら利用者側になる、という対比で覚えます。

</details>

### Q3. ルートユーザーの扱いとして最も適切なものはどれですか。

- A. 日常の管理作業すべてに使う
- B. MFAを設定し、ルートにしかできない作業だけに限定して使う
- C. パスワードをチームで共有して使う
- D. 削除して無効化する

<details>
<summary>答え</summary>

**B** — ルートは全能なので日常では使わず、MFAで守って封印します。ルートにしかできない作業があるため削除はしません。

</details>

### Q4. 「業務に必要な最小限のアクセス許可だけを与える」原則を何と呼びますか。

- A. 規模の経済
- B. 最小権限
- C. 弾力性
- D. 疎結合

<details>
<summary>答え</summary>

**B** — 最小権限(least privilege)です。IAMのポリシー設計の大原則で、そのまま用語問題として出ます。

</details>

### Q5. 「EC2上のアプリケーションに、S3の特定バケットへアクセスする権限を安全に与える」方法として最も適切なものはどれですか。

- A. 管理者のIAMユーザーのアクセスキーを、アプリの設定ファイルに書く
- B. アプリ専用のIAMユーザーを作り、アクセスキーをソースコードに埋め込む
- C. 必要最小限の権限を持つIAMロールをEC2に付与する
- D. S3のフルアクセス権限を持つIAMロールをEC2に付与する

<details>
<summary>答え</summary>

**C** — ロールなら一時的な認証情報が自動発行され、コードに長期の鍵を書く必要がありません。アクセスキーを設定ファイルやソースコードに書く方法は、漏えい時に長期間悪用される定番の事故パターンです。S3のフルアクセス権限を持つロールは、ロールを使っていても「フルアクセス」が最小権限の原則に反します。ロール+最小権限、の両方そろって正解です。

</details>
