# レッスン7-1 共有責任とIAM

## このレッスンの目標

- [ ] 共有責任モデルの分担を、サービス種別(EC2/RDS/S3)に応じて判定できる
- [ ] ルートユーザーの扱いとMFAの役割を説明できる
- [ ] IAMのユーザー・グループ・ポリシー・ロールを使い分けられる

## 7-1-1 共有責任モデル

> **AWSは「クラウド本体の」安全を、利用者は「クラウドの中の」安全を守るのが共有責任モデル**

「クラウドだからセキュリティはAWSにお任せ」は危険な誤解です。セキュリティの分担を定めた公式の考え方が **共有責任モデル** で、英語の前置詞の対で覚えるのが定石です。

- Security **OF** the Cloud(クラウド **本体の** 安全)— AWSの責任
- Security **IN** the Cloud(クラウド **の中の** 安全)— 利用者の責任

| 担当 | 例 |
| --- | --- |
| AWS(本体) | データセンターの物理警備、ハードウェア、基盤ソフト |
| 利用者(中身) | 自分のデータ、アクセス権の設定、OSやアプリの設定 |

建物の耐震・警備はビルのオーナー(AWS)、部屋の施錠と貴重品の管理は入居者(利用者)、という例えがぴったりです。試験では「物理セキュリティは誰?」(AWS)、「S3バケットの公開設定ミスは誰?」(利用者)のように、設問の対象が「本体」か「中身」かだけを判定します。

## 7-1-2 境界はサービス種別で動く

> **任せる範囲が広いサービスほどAWSの責任範囲が増え、EC2 → RDS → S3の順で利用者の担当は減る**

共有責任の線は1本の固定線ではありません。M2で学んだIaaS/PaaS/SaaSの「マネージドの度合い」の軸が、そのまま責任の軸になります。

| 作業 | EC2 | RDS | S3 / Lambda |
| --- | --- | --- | --- |
| OSのパッチ | 利用者 | AWS | AWS(そもそも見えない) |
| ソフトの面倒 | 利用者 | AWS(DBエンジン) | AWS |
| データと権限 | 利用者 | 利用者 | 利用者 |

表を縦に読むと、右の列(マネージドの度合いが高い)ほど利用者の行が減ります。ただし最下行——**自分のデータと、アクセス権の設定は、どのサービスでも常に利用者の責任**です。この例外のなさが最重要ポイントです。

試験のパッチ3連問はほぼこのまま出ます。「EC2のゲストOSのパッチは誰?」(利用者)、「RDSのDBエンジンのパッチは誰?」(AWS)、「Lambda利用時のサーバー管理は誰?」(AWS)。パッチの主語がどのサービスのどの層かを読み取ってください。

## 7-1-3 ルートユーザーは金庫にしまう

> **ルートユーザーは日常では使わず、MFAを付けて必要なときだけ取り出す**

AWSの契約単位を **AWSアカウント** と呼びます。アカウントを作ると、すべての操作ができる **ルートユーザー** が最初から1人存在します。このIDが乗っ取られたら環境ごと乗っ取られるため、扱いが決まっています。

**MFA**(多要素認証)は、パスワードに加えてもう1要素(認証アプリの数字など)で本人確認する仕組みです。最初にやる3点セットはこうです。

1. ルートユーザーにMFAを設定する
2. 日常作業用のユーザーを別に作る(次トピックのIAM)
3. ルートは、解約や一部の請求設定など「ルートにしかできない作業」だけに使う

「ルートにしかできない作業」が存在するので、封印はしても廃棄はしません。試験では「ルートユーザーの保護としてまずやること」(MFAの有効化)が定番で、「日常の管理作業にルートを使う」は誤りの選択肢として並びます。MFAはルートに限らず全ユーザーに推奨です。

## 7-1-4 IAMは最小権限で配る

> **IAMはユーザー・グループ・ポリシーで権限を管理し、仕事に必要な最小権限だけを許可する**

日常の権限は **IAM**(Identity and Access Management)で配ります。部品は3つです。

| 部品 | 役割 |
| --- | --- |
| **IAMユーザー** | 操作する人(またはアプリ)のID |
| **IAMグループ** | ユーザーの束(開発チーム、経理など) |
| **ポリシー** | 「何を許可するか」を書いた文書 |

運用の定石は「ポリシーをグループに付け、ユーザーをグループに入れる」です。個人に直接権限を付けると、異動のたびに棚卸しが破綻します。

そして原則が **最小権限**(least privilege)です。仕事に必要な権限だけを与え、「念のため広めに」を許しません。試験では「必要最小限のアクセス許可を与える原則を何と呼ぶか」がそのまま出ます。権限は役割・仕事に合わせるもので、人の偉さに合わせるものではありません。

## 7-1-5 IAMロールは一時的な鍵

> **IAMロールは人やサービスに一時的な権限を貸し出す仕組みで、アクセスキーの埋め込みをなくせる**

EC2上のアプリからS3を読みたいとき、権限をどう持たせるべきでしょうか。プログラム用のID/パスワードに当たる鍵を **アクセスキー** と呼びますが、これをコードに書き込むと、漏れたときに長期間悪用され、書き換えも大変です。

**IAMロール** は「かぶると権限が付く帽子」です。特定の人に固定されず、引き受けている間だけ一時的な認証情報が自動発行されます。

| | IAMユーザー+アクセスキー | IAMロール |
| --- | --- | --- |
| 鍵の性質 | 長期に固定 | 一時的・自動更新 |
| コードへの記載 | 必要になりがち | 不要 |
| 漏えい時 | ずっと使われる | すぐ期限切れ |

EC2にロールを付ければ、アプリは鍵なしでS3へアクセスできます。試験では「EC2のアプリにS3への権限を安全に与える方法」「認証情報をコードに埋め込まない方法」がIAMロールの合図です。一時的に別のアカウントへ権限を貸す場合にもロールを使います。
