# レッスン5-1 小さな修正を通しでやる

## このレッスンの目標

- [ ] 通しで練習する1本を、影響範囲とできの基準から選べる
- [ ] 4つの段を通した変更をプルリクエストに出し、レビューを受けるまでを説明できる
- [ ] 同じ指示の繰り返しに気づいて、仕組み化する番だと判断できる

## 5-1-1 通す1本は小さく選ぶ

> **通しで練習する1本は、影響範囲が小さくて完了を言い切れる修正を選びます**

ここまでで、道具と進め方はそろいました。最後のモジュールでやるのは、それを1本の修正で最初から最後まで通すことです。まず決めるのは、何を題材にするかです。

題材選びを外すと、練習になりません。初めての1本に「前から気になっていた大きな作り直し」を選ぶと、途中でどこまで直ったのか分からなくなります。ワークフローを覚えるはずが、大工事の遭難になります。

選ぶ条件は2つです。**影響範囲** が小さいことと、できの基準を言い切れることです。影響範囲とは、その修正が触る範囲、つまり直したところが波及する先の広さです。

```text
題材の例    一覧画面の日付の表示が崩れているのを直す
            APIのレスポンスに項目を1つ足す
影響範囲    触るのはファイル1〜2本まで
できの基準  その画面が崩れずに表示される / 既存のテストが通る
```

見分け方は簡単です。依頼に書くできの基準が1〜2行で書けるなら、その1本は通しに向いています。書き出すと切りがないなら、まだ大きすぎます。

| | 通しに向く1本 | 向かない1本 |
| --- | --- | --- |
| 影響範囲 | ファイル1〜2本 | リポジトリ全体 |
| できの基準 | 1〜2行で書ける | 書き出すと切りがない |
| 完了 | 言い切れる | だいたい直った止まり |

向かない1本が悪い仕事なのではありません。ワークフローを身につける題材に向かない、というだけです。大きな修正は、小さな1本を何度か通したあとで、区切って持ち込みます。

## 5-1-2 通した変更はレビューに出す

> **4つの段を通した変更は、プルリクエストに出して人のレビューを受けてから取り込みます**

1本を選んだら、Explore → Plan → Code → Commit の4つの段をそのまま通します。ここまではM3で扱ったとおりで、新しいことはしません。

問題はその先です。差分を自分で読み、動作確認まで済ませても、自分ひとりの目には限界があります。しかも今回の変更は、自分の手だけで書いたものではありません。「エージェントが書いたので大丈夫です」は、チームに対する説明になっていません。

そこで、取り込む前にもう1枚、人の目を通します。ブランチの変更を取り込む前に見てもらう場が **プルリクエスト** です(Git入門研修で扱った語です)。取り込む前に人が変更を読んで見る工程が **レビュー** です。

```text
ブランチを切る → Exploreから4つの段を通す → Commitでコミットに区切る
→ プルリクエストを出す(何を直したか / どう確かめたか を書く)
→ レビューで指摘を受けて直す → 取り込む
```

プルリクエストに書くのは2つです。何を直したかと、どう確かめたかです。動作確認で何を走らせたかを書いておくと、レビューする人は同じところを二度確かめずに済みます。

| | そのまま取り込む | プルリクエストに出す |
| --- | --- | --- |
| 読む人 | 自分だけ | 自分と、レビューする人 |
| 残るもの | コミットだけ | 直した理由とやり取り |
| 見落とし | そのまま入る | もう一度読まれる |

指摘を受けたら、その直しもまた同じ4つの段で進められます。小さな直しなら、指摘の箇所を指し示して1段だけ書かせ、差分を読んでコミットする。ここでも型は変わりません。

エージェントに書かせた変更ほど、読む人を増やす価値があります。速く書けるようになったぶんを、確かめる側に回すという配分です。

## 5-1-3 繰り返しが見えたら仕組み化する

> **同じ指示を毎回書いていると気づいたら、次はそれを仕組みとして置く番です**

1本を通せるようになると、2本目、3本目が来ます。そのうち、依頼のたびに同じ前置きを書いている自分に気づきます。

```text
毎回書いている  「テストはこのコマンドで走らせて」
                「直したら必ずこの手順で確かめて」
                「この書き方に合わせて」
判断            3回書いたら、それは仕組みにする候補
```

依頼のたびに毎回書いている同じ内容の指示が **繰り返し** です。その指示を、毎回書かずに済むよう先に置いておくことが **仕組み化** です。

手で書き続けることの費用は、手間よりも、書き忘れた回だけ結果がぶれることにあります。前回はうまくいったのに今回はずれた、その理由が思い出せない。原因はたいてい、書き忘れた1行です。

| | 毎回書く | 仕組みとして置く |
| --- | --- | --- |
| 手間 | 依頼のたびに同じ文 | 一度置けば効き続ける |
| ぶれ | 書き忘れた回だけ抜ける | 抜けにくい |
| この講座 | ここまでが範囲 | 名前だけ紹介 |

置き場所にはいくつか名前があります。CLAUDE.mdファイル、Skills、サブエージェント、hooks、MCP、GitHubの@claude Action です。名前を挙げるのはここまでで、それぞれが何をどう設定するものかは次の講座で扱います。

このトピックで持ち帰るのは、作り方ではなく判断です。同じ指示を3回書いたら、そこが仕組みの出番だと気づけること。それだけで十分です。

これで、1つの修正を選び、4つの段で通し、レビューに出して取り込むところまでが1周しました。この型は、扱うコードが変わっても同じです。

## もっと知りたい人へ

- 題材の大きさに迷ったら、「レビューする人が15分で読み切れるか」を目安にしてみてください。読み切れない大きさは、たいてい分けたほうが速く終わります
- プルリクエストの出し方や粒度そのものは、Git入門研修の範囲です。この講座では「人に見せる単位」としてだけ扱いました
- 仕組み化の具体的なやり方は、この講座では扱いません。まずは繰り返しに気づくところまでを習慣にしてください
- 画面の並びやコマンドの名前は変わります。実際に使うときは、製品のドキュメントで確認してください
