# レッスン5-1 演習 — 小さな修正を通しでやる

対象トピック: 5-1-1 〜 5-1-3

## 手元で試す

この講座の総仕上げです。小さな修正を1本選び、Explore → Plan → Code → Commit で通します。

1. 手元にクローンしたリポジトリをVS Codeで開き、Claude Codeのパネルを出します
2. 直す1本を選びます。触るのがファイル1〜2本で、できの基準が1〜2行で書けるものにします
3. 作業用のブランチを切ります
4. **Explore** — 対象のコードを読ませて、現状を説明させます。関係するフォルダを指し示して範囲を狭めます
5. **Plan** — Planモードで計画だけ出させ、自分で読んで過不足を直します
6. **Code** — 一段ずつ書かせ、そのつど確かめます。ずれたら中断して計画まで戻します
7. **Commit** — 差分を自分で読み、テストを走らせて動作確認してから、コミットで区切ります
8. プルリクエストを出します。本文には「何を直したか」と「どう確かめたか」を書きます
9. 会話が長くなっていたら、この1本が終わったところで `/clear` を使い、次の1本に持ち越さないようにします

**Claude Code が使えない環境の受講者は、1〜9 を飛ばして構いません。** 代わりに、紙(またはメモ帳)の上で次の3つを書けば演習は成立します。

- 直近の業務から、通しに向く修正を1本選び、できの基準を1〜2行で書く
- その1本について、4つの段でそれぞれ自分が何をするかを1行ずつ書く
- プルリクエストの本文を、「何を直したか」「どう確かめたか」の2項目で下書きする

## 演習問題

### 問1(基本)

通しで練習する1本を選ぶときの条件を2つ挙げ、それぞれを1文で説明してください。

### 問2(基本)

4つの段を通してコミットまで済ませた変更を、そのまま取り込まずにプルリクエストへ出す理由を2つ書いてください。

### 問3(応用)

次の3つの候補から、通しの1本に向くものを1つ選び、残り2つが向かない理由を書いてください。

- ア: 一覧画面の日付が「2026/1/5」と「2026-01-05」で混ざっているのを片方にそろえる
- イ: 認証のしくみを別方式に入れ替える
- ウ: 動きが遅いところをリポジトリ全体で洗い出して速くする

### 問4(応用)

3本目の修正を通したところで、依頼のたびに「テストはこのコマンドで走らせて」と同じ1行を書いていることに気づきました。このとき取るべき判断を1〜2文で書いてください。設定のやり方は書かなくて構いません。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

1つ目は、影響範囲が小さいことです。触るファイルが1〜2本に収まっていれば、差分を自分で読み切れます。2つ目は、完了を言い切れることです。できの基準が1〜2行で書けるなら、どこで終わりかを自分でもレビューする人にも示せます。

</details>

<details>
<summary>問2の解答例</summary>

1つ目は、自分ひとりの目には限界があるからです。差分を読んで動作確認まで済ませても、見落としはもう一度読まれることで見つかります。2つ目は、直した理由とやり取りが残るからです。コミットだけでは、なぜその直し方にしたのかが後から追えません。

</details>

<details>
<summary>問3の解答例</summary>

向くのはアです。触る箇所が限られ、「表示がどちらかの形にそろっている」というできの基準を1行で書けます。イは認証の入れ替えで、影響範囲がリポジトリ全体に及び、確かめることも多すぎます。ウは対象を洗い出すところから始まるため、どこで完了かを最初に言い切れません。イもウも仕事としては正当ですが、ワークフローを覚える題材には向きません。

</details>

<details>
<summary>問4の解答例</summary>

3回書いた指示なので、これからも書き続ける指示だと判断します。毎回書くのをやめて、仕組みとして置く候補に入れます。書き忘れた回だけ結果がぶれるのを防ぐのが目的です。

</details>

## 確認クイズ

### Q1. 通しで練習する1本を選ぶ基準として適切なものはどれですか。

- A. 前から気になっていた、いちばん大きな作り直し
- B. 影響範囲が小さくて、完了を言い切れる修正
- C. 自分がまだ一度も読んだことのない領域の修正

<details>
<summary>答え</summary>

**B** — 条件は2つです。触る範囲が小さいことと、できの基準を1〜2行で書けることです。

</details>

### Q2. 「APIのレスポンスに項目を1つ足す」と「認証のしくみを別方式に入れ替える」。通しの1本に向くのはどちらで、その理由はどれですか。

- A. 後者。難しいほうが練習になるため
- B. 前者。触る範囲が限られ、できの基準を短く書けるため
- C. どちらでも同じ。1本の大きさは結果に関係しないため

<details>
<summary>答え</summary>

**B** — 大きな修正が悪いのではなく、ワークフローを覚える題材に向かないという話です。

</details>

### Q3. 差分を読み、テストも通り、コミットまで済ませました。次にすることとして適切なものはどれですか。

- A. 自分で確かめたので、そのまま取り込む
- B. プルリクエストを出して、人のレビューを受けてから取り込む
- C. エージェントが書いた変更なので、確認は不要と伝えて取り込む

<details>
<summary>答え</summary>

**B** — 自分ひとりの目には限界があります。取り込む前にもう1枚、人の目を通します。

</details>

### Q4. プルリクエストの本文に書くとよい内容の組み合わせはどれですか。

- A. 何を直したか / どう確かめたか
- B. 使ったツールの一覧 / かかった時間
- C. 会話のやり取りを全文そのまま

<details>
<summary>答え</summary>

**A** — 確かめ方まで書いておくと、レビューする人が同じところを二度確かめずに済みます。

</details>

### Q5. 依頼のたびに「直したら必ずこの手順で確かめて」と書いていることに気づきました。この気づきが意味するものはどれですか。

- A. 依頼の書き方が下手なので、書くのをやめるべきだという合図
- B. 繰り返しなので、仕組みとして置く番だという合図
- C. その手順自体が不要だという合図

<details>
<summary>答え</summary>

**B** — 3回書いた指示は、これからも書き続ける指示です。手で書き続ける費用は、手間よりも書き忘れによるぶれにあります。

</details>
