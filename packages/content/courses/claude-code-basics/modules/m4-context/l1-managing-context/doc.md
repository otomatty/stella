# レッスン4-1 長くなった会話を切る

## このレッスンの目標

- [ ] 会話が長くなるとコンテキストに何が起きるかを説明できる
- [ ] いまの使用量を確かめる手段を言える
- [ ] `/compact` と `/clear` のどちらを使う場面かを選べる

## 4-1-1 会話が長いほど余裕が減る

> **会話はまるごとコンテキストとして読み直されるため、長くなるほどコンテキスト上限に近づきます**

朝から同じパネルで頼み続けていると、午後になって返事が噛み合わなくなることがあります。自分の頼み方は変えていないのに、朝と同じようには通らない。原因は多くの場合、会話の長さの側にあります。

判断のもとになる前後の情報を **コンテキスト** と呼びます。講座1で扱った語です。一度に読める量には上限があり、それが **コンテキスト上限** です。これも講座1で扱った語です。上限の実際の値は製品やその時々で変わるので、ここでは「上限がある」という事実だけを使います。

Claude Code の会話では、自分が打った文章だけが積み上がるのではありません。エージェントループが1周するたびに、読ませたファイルの中身も、実行したコマンドの結果も、出てきた差分も、会話の一部として積まれていきます。

```text
1つ目の依頼   依頼 + 読ませたファイル + 出てきた差分
2つ目の依頼   1つ目のぶん + 今回のぶん をまとめて読み直す
3つ目の依頼   1つ目 + 2つ目 + 今回 をまとめて読み直す
```

自分が打った文字数の感覚より、積み上がりはずっと速く進みます。大きなファイルを1つ読ませただけで、一気に増えることもあります。

| | 始めたばかり | 長く続いた会話 |
| --- | --- | --- |
| 積まれているもの | いまの依頼だけ | 前の作業ぜんぶ |
| 上限までの余裕 | 大きい | 小さい |
| 関係ない話の混ざり | ほぼない | 増える |

困るのは、上限に当たることだけではありません。もう終わった作業の話が読み直され続けること自体が、返事の精度を下げます。会話の長さは、放っておくと勝手に増える性質のものだと考えてください。

## 4-1-2 /contextで今の使用量を見る

> **`/context`は、いまコンテキストをどれだけ使っているかを確かめるスラッシュコマンドです**

会話が長いかどうかは、見た目では分かりません。「そろそろ長いかな」は勘であって、当たっているとは限りません。手詰まりになってから気づくと、作業の途中で慌てて手を打つことになります。

ここで使うのが、**使用量を見る** 役割の道具です。その役割に付いている名前が `/context` です。パネルに `/` で始まる語を打って使う会話の中の操作を **スラッシュコマンド** と呼びます。

名前ではなく役割で覚えてください。製品の名前や表示は変わることがありますが、「使用量を見る手段がある」という考え方は変わりません。

```text
やりたいこと   いまどれだけ使っているか知りたい
打つもの       /context
分かること     使用量の目安 / 上限までの余裕
```

数字そのものを覚える必要はありません。余裕が大きいか小さいかが読めれば十分です。

| 場面 | 見る意味 |
| --- | --- |
| 長い作業の区切り | このまま続けてよいか決められる |
| 返事が噛み合わなくなった | 原因が会話の長さかを切り分けられる |
| 大きなファイルを読ませた直後 | 一気に増えていないか分かる |

常に見るものではありません。区切りのときと、様子がおかしいと感じたときの2つで足ります。とくに「噛み合わない原因が長さなのかどうか」を切り分けられる点は、頼み方を直す前に確かめる価値があります。

## 4-1-3 /compactで要点だけ残す

> **`/compact`は、ここまでの会話を要約して、続きに要る要点だけを残します**

まだ同じ修正の途中なのに、余裕が減ってきた。よくある場面です。ここまでの経緯は続きに要るので、会話をまるごと捨てるわけにはいきません。「続けたい」と「減らしたい」が同時に立っています。

このときに使うのが、**要約して残す** 役割の道具です。その役割に付いている名前が `/compact` です。中身を短くまとめ直したものを **要約** と呼びます。捨てるのではなく詰める、と考えると分かりやすいです。

```text
前         依頼 + 読ませたファイル + 試したコマンド + 差分 …
/compact   ここまでを要約に置き換える
後         「どこを直しているか」「決めた方針」+ この先の会話
```

会話そのものは続いています。中身が短い形に入れ替わっただけです。だから、そのまま同じ作業の続きを頼めます。

| 会話にあったもの | 要約のあと |
| --- | --- |
| いま何を直しているか | 残る |
| 決めた方針・できの基準 | 残る |
| 途中で読んだファイルの中身そのもの | 落ちることがある |

要約である以上、細部は落ちます。落ちて困るものがあるなら、要約の前に自分で書き留めておくか、あとでもう一度伝え直します。何が残っていてほしいかを決めるのは自分の側の仕事です。

## 4-1-4 /clearは話題が変わったら使う

> **`/clear`は会話を空にするので、前の作業を持ち越したくないときに使います**

午前の修正が終わり、午後はまったく別のファイルに取りかかるとします。このとき前の作業の話が残っていると、関係ない前提を引きずった返事が返ってきます。「さっきのファイルに合わせますね」と言われても、もうそのファイルは関係ありません。

ここで使うのが、**空にする** 役割の道具です。その役割に付いている名前が `/clear` です。空にすると、コンテキストは会話を始めたばかりの状態に戻ります。

順番があります。空にする前に、その作業を区切っておきます。

```text
午前     表示崩れを直した会話が続いている
区切り   差分を読んでコミットまで済ませる
/clear   会話を空にする
午後     別の修正を、前の作業を持ち越さずに頼める
```

読んでいない差分を残したまま空にすると、経緯だけが消えて、手元の変更が宙に浮きます。区切ってから切り替えてください。

| いまの状況 | 使うもの |
| --- | --- |
| 同じ作業の続き。経緯が要る | 要約して残す(`/compact`) |
| 別の作業に移る。経緯は要らない | 空にする(`/clear`) |

判断の軸は「続きかどうか」の1つだけです。迷ったら、これから出す依頼が前の会話を根拠にするかどうかを考えてください。根拠にするなら要約して残す、しないなら空にする。この見分けができれば、会話の長さは自分で管理できます。

## もっと知りたい人へ

- 会話が長くなること自体は失敗ではありません。1つの作業を丁寧に進めれば会話は必ず伸びます。伸びたときに切る手段を持っているかどうかが差になります
- 上限の値やコマンドの名前は変わることがあります。実際に使うときは、製品のドキュメントで確認してください
- 使用量を見る・要約して残す・空にする、という3つの役割で覚えておくと、名前が変わっても同じ判断ができます
