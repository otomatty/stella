# 開いたフォルダが作業の範囲

Claude Code入門 — Module 1 / レッスン1-1

---

## なぜ必要か

- 手元のパソコンには、仕事と関係のないファイルもたくさんある
- 「どこまで読まれるのか」が分からないままだと、頼むのが不安になる

<!-- ノート: つかみ。範囲が見えない不安を共有します。ここで結論は言いません。 -->

---

## 結論

**手元にクローンしたリポジトリをVS Codeで開くと、そのフォルダの中が作業の範囲になります**

- **リポジトリ** — プロジェクトのファイル一式です(Git入門研修で扱った語です)
- **クローン** — それを手元にまるごと複製することです(同じく Git入門研修の語です)
- **フォルダ** — ファイルをまとめる入れ物です
- **作業の範囲** — Claude Codeが読み書きの相手にする範囲です

<!-- ノート: 結論を言い切ります。Gitの2語は1行ずつの復習に留め、深入りしません。範囲を決めているのは設定ではなく「何を開いたか」だと強調します。 -->

---

## 開いたものが、そのまま範囲になる

```text
手元        ~/work/shop-web       ← クローンしたリポジトリ
VS Codeで開く  shop-web フォルダ
作業の範囲    shop-web の中のファイルとフォルダ
範囲の外      同じパソコンの他のフォルダ
```

<!-- ノート: 最小の例です。開いたフォルダの中と外、という線が1本引かれるだけだと読み上げます。 -->

---

## どこを開くかで変わる

| 開いたもの | 作業の範囲 | 起きること |
| --- | --- | --- |
| リポジトリの根っこ | プロジェクト全体 | 関係するファイルにたどり着ける |
| 深い階層のフォルダ1つ | その中だけ | 呼び出し元が見えず、話がかみ合わない |
| パソコンの家フォルダ | 広すぎる | 関係ないファイルまで範囲に入る |

<!-- ノート: 対比の枠です。既定はリポジトリの根っこを開くこと。狭すぎても広すぎても困る、という両側の失敗を1枚で見せます。 -->
