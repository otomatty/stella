# レッスン7-1 テーブルを作る

## このレッスンの目標

- [ ] `CREATE TABLE` でテーブルを定義できる
- [ ] 列にデータ型を指定できる
- [ ] 主キーが何のためにあるかを説明できる

## 7-1-1 CREATE TABLEで表を定義する

> **CREATE TABLE で、テーブルの名前と列の一覧をあらかじめ決めておく**

ここまでは、既にあるテーブルからデータを取り出したり書き込んだりしてきました。新しい機能を作るときは、その入れ物から用意する必要があります。

```sql
CREATE TABLE products (
  id    INTEGER,
  name  TEXT,
  price INTEGER
);
```

- **CREATE TABLE** — テーブルを作るSQL文
- **スキーマ** — テーブルと列の定義。データの設計図

表計算ソフトなら、まず入力を始めてから列を足していくこともできます。しかしデータベースでは、**先に形を決めてから行を入れます**。定義していない列に値を入れようとすれば、エラーになります。

窮屈に見えるかもしれませんが、これは利点です。形が決まっているから、後から誰が見ても同じ構造で読めますし、間違った形のデータが入るのを入口で止められます。

## 7-1-2 列にはデータ型を決める

> **列ごとにデータ型を決めると、その列に入る値の種類がそろう**

価格の列に「200円」という文字列が混ざると、`SUM` で合計を計算できません。入れる人ごとに書き方が違えば、後の集計が壊れます。

**データ型** は、その列に入れてよい値の種類です。

```sql
CREATE TABLE orders (
  id       INTEGER,   -- 整数
  customer TEXT,      -- 文字列
  total    REAL       -- 小数
);
```

まずは3つ覚えれば十分です。

| 型 | 入る値 | 例 |
|---|---|---|
| `INTEGER` | 整数 | `1` `250` |
| `TEXT` | 文字列 | `'ノート'` |
| `REAL` | 小数 | `1.5` |

日付を入れる列は、多くの場合 `TEXT` にして `'2026-04-12'` の形にそろえます。書き方をそろえておけば、文字列のまま並べ替えても日付順になります。

1つ注意があります。**SQLite は宣言した型と違う値も受け付けます**(型親和性という緩い仕組みのため)。`INTEGER` の列に `'abc'` を入れても、そのまま入ってしまいます。逆に `TEXT` の列に `'200'` `'120円'` `'abc'` が混ざっていても `SUM` は計算でき、それぞれ 200・120・0 と読み替えられて合計 320 が返ります。**エラーにならず、黙って違う数字が出る**のがいちばん厄介な点です。

つまりデータ型は、SQLite では「入れる値をそろえる約束」として働きます。宣言どおりに拒否させたい場合は、SQLite なら `CREATE TABLE ... STRICT`、PostgreSQL や MySQL なら宣言だけで拒否されます。どの環境でも、**型を決めておくこと自体に意味がある**のは変わりません。

## 7-1-3 主キーで行を1つに特定する

> **主キーは行を1つに特定するための列で、同じ値を2回入れられない**

同姓同名の会員がいると、名前では1人に絞れません。`UPDATE` や `DELETE` の対象を確実に1件へ決めるには、重複しない目印が要ります。

**主キー**(`PRIMARY KEY`)は、その行を一意に決める列です。

```sql
CREATE TABLE products (
  id    INTEGER PRIMARY KEY,
  name  TEXT,
  price INTEGER
);
```

主キーには2つの約束が付きます。

- **重複を許さない** — 同じ `id` を2回入れようとするとエラーになる
- **空(NULL)を許さない** — 必ず値が入る、というのが SQL 標準の約束

この2つがあるから、`WHERE id = 1` と書けば必ず1件に決まります。

ただし NULL については、**SQLite だけ約束を守りません**。上の `INTEGER PRIMARY KEY` に `NULL` を入れると、拒否されずに**空いている番号が自動で振られます**(結果として空の行はできないので実害はありません)。困るのは `TEXT` の主キーや複数列の主キーで、こちらは `NULL` がそのまま入り、**`NULL` の行を何行でも作れてしまいます**。

対策は簡単で、主キーの列には `NOT NULL` も書いておくことです。SQLite でも拒否されるようになり、他のデータベースでも意味は変わりません。

```sql
CREATE TABLE tags (
  code TEXT PRIMARY KEY NOT NULL,
  name TEXT
);
```
レッスン6-1で `WHERE id = ...` を使って書き換えや削除をしていたのは、`id` が主キーだったからです。

そしてモジュール4の `JOIN ... ON` を思い出してください。テーブルどうしをつなぐときの目印にしていた列も、主キーでした。**主キーは、行を特定するための共通の目印** として、SQLのあちこちで使われています。

どの列を主キーにするか、テーブルをどう分けるか、といった設計の判断は、次の講座(データベース設計入門)で扱います。この講座では、SQLの書き方としてここまでを押さえておけば十分です。
