# レッスン5-1 コミット前のやり直し

## このレッスンの目標

- [ ] git restore で作業中の変更を捨てて、最後のコミットに戻せる
- [ ] restore で捨てた変更は取り戻せないことを説明できる
- [ ] git restore --staged で add だけを取り消せる

## 5-1-1 git restoreで戻す

> **git restore ファイル名 で、作業中の変更を捨てて最後のコミットに戻せる**

直しているうちに、動いていたファイルを壊してしまうことがあります。まだコミットしていない段階なら、`git restore` で戻せます。

```bash
# 日報.md を編集して壊してしまった(まだコミットしていない)
git restore 日報.md
# → 日報.md が最後にコミットした内容に戻る
```

- 戻り先は「そのファイルを最後にコミットした状態」です
- 消えるのはコミット前の編集だけで、履歴は変わりません
- 指定したファイルだけが戻ります。他のファイルには触りません

エディタの「元に戻す」(Ctrl+Z)で少しずつ戻るのと違い、最後の記録まで一気に戻れるのが実務での強みです。

## 5-1-2 restoreは取り戻せない

> **restore で捨てた変更は取り戻せない(コミット前の変更は守られていない)**

restore は便利ですが、危険な性質とセットで覚える必要があります。捨てた編集は、ゴミ箱のようにどこかへ残ってはいません。

```text
10:00 日報.md に30分かけて追記(コミットしていない)
10:30 git restore 日報.md   # ← 追記が全部消える
10:31 「元に戻すコマンドは?」 → 無い
```

理由ははっきりしています。Git が守っているのは **コミットした変更だけ** だからです。コミット前の編集は履歴のどこにも記録されておらず、Git の管理の外にあります。

実務の指針は1つです。捨てるか迷う変更なら、restore の前にいったんコミットして残しておくのが安全です。

## 5-1-3 --stagedでaddを取り消す

> **git restore --staged で add だけを取り消す(ファイルの中身は変わらない)**

やり直したいのは編集そのものではなく、add の操作だけということもあります。関係ないファイルまで add してしまった場面です。

```bash
git add 価格表.md            # 間違えて載せてしまった
git restore --staged 価格表.md
# → 次のコミットから外れる。編集した中身はそのまま
```

`--staged` が付くと、restore の対象がステージングエリア(次のコミットの下書き)に変わります。下書きから降ろすだけなので、作業中のファイルには一切触りません。

| コマンド | 消えるもの | ファイルの中身 |
| --- | --- | --- |
| `git restore ファイル名` | 作業中の編集 | 最後のコミットに戻る |
| `git restore --staged ファイル名` | add(下書きへの登録) | 変わらない |

同じ restore でも `--staged` の有無で効果がまったく違います。「編集を捨てるのか、add を取り消すのか」を言葉にしてから打ちましょう。

## 5-1-4 戻す前にstatus

> **どこまで戻るのかを status と diff で確かめてから戻す**

restore で捨てた変更は取り戻せません。それでも急いでいると勢いで打ってしまい、必要な編集まで消す事故が起きます。対策は、打つ前の手順を型にしてしまうことです。

```bash
git status           # 変わっているファイルはどれか
git diff 日報.md     # 消えるのはこの変更でよいか
git restore 日報.md  # 納得してから戻す
```

- status で「どのファイルが変わっているか」を一覧します
- diff で「これから捨てる変更の中身」を自分の目で読みます
- 「消してよい」と言えたときだけ restore を打ちます

確認 → 確認 → 実行。実務でもこの3行は毎回セットです。
