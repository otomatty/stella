# レッスン0-1 なぜ履歴が要るのか

## このレッスンの目標

- [ ] コピーを増やすファイル管理の問題点を説明できる
- [ ] バージョン管理が何を記録するしくみかを説明できる
- [ ] 履歴があると「戻れる」「分担できる」ことを例で説明できる

## 0-1-1 コピーで増やす管理は破綻する

> **「最終版_v2_修正」とコピーを増やす管理は、どれが本物か分からなくなる**

資料でもプログラムでも、作ったものには必ず直し(**変更**)が入ります。直す前の状態も残したくて、多くの人がまずファイルのコピーを作ります。

```text
企画書.md
企画書_最終版.md
企画書_最終版_v2.md
企画書_最終版_v2_修正.md   # ← どれを開けばいい?
```

この管理には2つの問題があります。

- どれが最新か、名前だけでは分からない(「最終版」が3つある)
- 何をなぜ変えたのかが、どこにも残らない

1人でも混乱しますが、チームで共有した瞬間に致命的になります。古い方を直してしまい、他人の直しを消してしまう事故は、この管理方法が原因で実際によく起きています。

## 0-1-2 バージョン管理は変更の記録

> **バージョン管理は「いつ・誰が・何を・なぜ」変えたかを記録するしくみ**

欲しいのはファイルの複製ではなく、変更のいきさつが分かるしくみです。それが **バージョン管理** です。

- 変更のたびに **記録** を1つ残す
- 積み重なった記録の列を **履歴** と呼ぶ

```text
2/10 10:00  佐藤  企画書を作成       (たたき台)
2/12 14:00  田中  価格表を修正       (単価改定のため)
2/15 09:30  佐藤  スケジュールを追記  (会議の決定を反映)
```

ファイルは「企画書.md」1つだけのまま、記録の側が増えていきます。「いつ・誰が・何を・なぜ」の4点がそろっているので、後から誰が見ても変更のいきさつを追えます。

## 0-1-3 履歴があれば戻れる

> **履歴が残っていれば、壊れる前の状態にいつでも戻れる**

直したつもりが、動いていたものを壊してしまうことは必ず起きます。上書き保存してしまった後では、記録がなければ打つ手がありません。

履歴があれば話が変わります。

```text
記録1: 一覧画面を作成      ← ここに戻れる
記録2: 検索機能を追加      ← ここにも戻れる
記録3: 表示を高速化(失敗)  ← いまここ。壊れた
```

記録2まで戻せば、検索機能まで動く状態がそのまま返ってきます。ファイルの中身を覚えておく必要はなく、記録を選ぶだけです。

「戻れる」と分かっていることは安心感でもあります。思い切った変更に挑戦できるのは、履歴という保険があるからです。

## 0-1-4 履歴があれば分担できる

> **履歴のしくみがあると、複数人が同じファイル群を並行して編集できる**

開発は1人ではやりません。同じプログラムを何人もで直していきます。共有フォルダのファイルを順番待ちで直すやり方では、待ち時間だらけになるうえ、上書きで他人の直しが消える事故も防げません。

履歴のしくみがあると、並行作業が成り立ちます。

```text
佐藤: 記録A「一覧画面を修正」─┐
                              ├→ 2人の変更を合流して1つに
田中: 記録B「検索条件を追加」─┘
```

- 各自の変更が記録として残るから、後から突き合わせて合流できる
- 誰の変更も消えない。順番待ちも要らない

合流の具体的なやり方は、この研修の後半(ブランチとマージ)で手を動かして学びます。ここでは「記録があるから並行作業が成り立つ」という一点を覚えておけば十分です。
