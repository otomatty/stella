# レッスン3-2 秘密情報を守る

## このレッスンの目標

- [ ] 秘密情報をコミットしてはいけない理由を説明できる
- [ ] 秘密をコミットしてしまったとき、最初にすべきことを言える
- [ ] 秘密を .env に分けて .gitignore する予防の型を使える

## 3-2-1 秘密はコミットしない

> **パスワードやAPIキーは、コミットしてはいけない**

プログラムを動かすには、データベースのパスワードや外部サービスの鍵が必要になります。外部サービスを使うための合鍵の文字列を **APIキー** と呼びます。こうした、漏れると悪用されるものが **秘密情報** です。

コードのそばに書いておけばすぐ動きます。だから、つい一緒に記録したくなります。

```text
// 接続の設定をコードに直接書いてしまった例
apiKey = "sk-a1b2c3d4..."   // ← これをコミットしてはいけない
```

コミットは履歴に残り、そのリポジトリを共有した相手全員に見えます。GitHub の公開リポジトリに上げれば、世界中から見える状態です。公開されたAPIキーは自動巡回のプログラムに数分で拾われ、悪用されます。会社への高額請求や、お客様の情報の流出に直結する事故です。

「動けばよい」の一歩先、「これは秘密情報か?」と考えてからコミットする習慣を、ここで付けてください。

## 3-2-2 削除コミットでは消えない

> **一度コミットした秘密は削除コミットでは消えない(まずキーを無効化する)**

うっかりAPIキーをコミットしてしまったら、どうすればよいでしょうか。多くの人がまず「ファイルを消してコミットし直せば大丈夫」と考えます。この直感が危険です。

コミットはその時点のスナップショットとして履歴に全部残ります。削除のコミットも「1つの新しい記録」にすぎません。

```text
記録1: 設定ファイルを追加(APIキー入り) ← ここに残り続ける
記録2: APIキーの行を削除
```

記録2の後でも、履歴をさかのぼって記録1を開けば、キーは丸見えです。「消したつもりで公開を続ける」のが最悪のパターンです。

だから、漏れた鍵への一手目は Git の操作ではありません。**キーの発行元(サービスの管理画面など)で、その鍵を無効化して使えなくする**ことです。無効化してしまえば、履歴に残っていても悪用はできません。そのうえで、新しい鍵を安全な置き方(次のトピック)で使い直します。

## 3-2-3 秘密はファイルを分ける

> **秘密は設定ファイル(.envなど)に分けて、最初から .gitignore しておく**

「コミットしない」と決めても、コードの中に鍵が書いてある限り、いつかは混ざります。人の注意力に頼る対策は必ず破られるので、最初から混ざらない置き方にします。

定番が **.env** です。秘密情報をまとめて書いておく設定ファイルで、コードには鍵を書かず、.env から読み込む作りにします。

```text
# .env の中身(コミットしない)
API_KEY=sk-a1b2c3d4...

# .gitignore に最初から書いておく
.env
```

ポイントは2段構えです。

- **分ける**: 鍵を触るファイルを .env の1つに限定する
- **無視する**: プロジェクトを始めた直後に、.gitignore へ `.env` を書いておく

この形にしておけば、.env は status に現れず、うっかり add のしようがありません。コード側はいくらコミットしても安全です。チーム開発でもこの型が標準で、各自が自分の .env を手元に持ち、中身は履歴に載せずに受け渡します。
