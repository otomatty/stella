# レッスン7-2 コンフリクト

## このレッスンの目標

- [ ] コンフリクトが「故障ではなく質問」であることを説明できる
- [ ] マーカーを読み、編集→add→commit で解決できる
- [ ] 迷ったときは git merge --abort で仕切り直せる

## 7-2-1 コンフリクトは質問

> **コンフリクトは「同じ箇所を両方が変えたのでどちらにするか」という質問(故障ではない)**

マージすると、こんな赤い表示が出ることがあります。

```bash
git merge fix-greeting
# CONFLICT (content): Merge conflict in practice.txt
# Automatic merge failed; fix conflicts and then commit the result.
```

初めて見ると「壊してしまった」と焦りますが、これは **コンフリクト**(衝突)という状態で、故障でも失敗でもありません。

同じ行を両方のブランチが別々に変えていた場合、どちらが正しいかは Git には決められません。そこで Git は勝手に決めずに、作業を止めて人に質問しています。出力をよく読むと「直してからコミットしてください」と、次の一手まで書いてあります。

落ち着いて質問に答えれば、コンフリクトは必ず解決できます。

## 7-2-2 マーカーの読み方

> **<<<<<<< / ======= / >>>>>>> は、両方の言い分の区切り**

コンフリクトしたファイルを開くと、Git が書き込んだ記号の行が入っています。この3つの行を **マーカー** と呼びます。

```text
<<<<<<< HEAD
単価: 1,200円
=======
単価: 1,500円
>>>>>>> update-price
```

読み方は1つだけです。

| 区間 | 意味 |
| --- | --- |
| `<<<<<<< HEAD` 〜 `=======` | 今いる枝(HEAD)の内容 |
| `=======` 〜 `>>>>>>> 枝名` | 取り込もうとした枝の内容 |

この例では、今いる枝は 1,200円、update-price は 1,500円 に同じ行を変えていました。上があなたの枝の言い分、下が相手の枝の言い分です。どちらにするかを決めるのは、次の人間の仕事です。

## 7-2-3 直し方は編集→add→commit

> **あるべき形に編集してマーカーを消し、add して commit すれば解決**

コンフリクトの解決に、特別な解除コマンドはありません。いつもの「記録の手順」でマージを完了させます。

```bash
# 1. ファイルを編集し、マーカーごと「あるべき1つの形」にする
git add practice.txt              # 2. 直した結果を選ぶ
git commit -m "単価改定を反映"     # 3. コミットして完了
```

1 の編集では、どちらかの言い分を残しても、両方を活かした第3の形にしても構いません。大事なのは、マーカーの3行(`<<<<<<<` / `=======` / `>>>>>>>`)を消して、「あるべき1つの形」だけを残すことです。

- add は「この形で解決した」という宣言になる
- commit まで終えると、それがマージコミットになる
- マーカーの消し忘れが無いか、コミット前に見直す

## 7-2-4 --abortでやり直す

> **迷ったら git merge --abort で、マージ前の状態に戻ってやり直せる**

コンフリクトの数が多いと、どう直すべきか迷うこともあります。中途半端に直しかけたまま進めるより、一度仕切り直すのが正解です。

```bash
git merge --abort
git status
# On branch main
# nothing to commit, working tree clean
```

--abort(中止)を打つと、コンフリクトは無かったことになり、手元はマージを打つ前の状態にきれいに戻ります。戻ったかどうかは思い込みではなく `git status` で確かめてください。

何度でもやり直せるので、マージを怖がる必要はありません。落ち着いて作戦を立て直してから、もう一度マージに挑戦できます。

## 7-2-5 小さくこまめに

> **小さく分けてこまめに取り込むほど、コンフリクトは小さくなる**

解決の腕前より効くのが、そもそもコンフリクトを大きくしない働き方です。

```text
数週間ためこんだ大きなブランチ → 何十か所ものコンフリクト
数日で合流する小さなブランチ   → 出てもすぐ答えられる数か所
```

コンフリクトの大きさは「枝が離れていた期間」と「変更量」で決まります。枝が長生きするほど相手との差は開き、合流のときにまとめて精算することになります。

- 作業を小さく区切り、終わったら早く合流する
- 「まとめて後で」が、コンフリクトを一番育てる

同じ仕事量でも、分けてこまめに取り込めば、コンフリクトはほとんど問題にならなくなります。
