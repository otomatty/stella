# レッスン2-2 演習 — diffを使い分ける

対象トピック: 2-2-1 〜 2-2-3

## ハンズオン

手元の VS Code のターミナルで試します。レッスン2-1 で使った `~/git-practice` の続きです。

1. 練習用リポジトリに移動し、価格表ファイルを作ってコミットしておきます。VS Code で `price.txt` を新規作成し、次の1行を書いて保存してから、ターミナルでコミットします

   ```text
   単価: 1,000円
   ```

   ```bash
   cd ~/git-practice
   git add price.txt
   git commit -m "価格表を追加"
   ```

2. VS Code で `price.txt` を開き、`単価: 1,000円` を `単価: 1,200円` に書き換えて保存します

3. まだ add していない状態で diff を読みます。`-` と `+` の行が表示されることを確認してください

   ```bash
   git diff
   ```

4. add してから、もう一度同じコマンドを打ちます。今度は何も表示されないことを確認してください

   ```bash
   git add price.txt
   git diff
   ```

5. add 済みの変更を表示します。手順3と同じ変更が見えることを確認してください

   ```bash
   git diff --staged
   ```

6. コミットされる内容を最終確認できたので、記録します

   ```bash
   git commit -m "価格表の単価を更新"
   ```

7. 仕上げに `git status` を打ち、手元がきれいになったことを確かめます

## 演習問題

### 問1(基本)

`git diff` と `git diff --staged` は、それぞれ何を見せるコマンドですか。1行ずつで答えてください。

### 問2(基本)

ファイルを編集して `git add` した直後に `git diff` を打つと、何も表示されませんでした。変更は消えてしまったのでしょうか。理由も答えてください。

### 問3(応用)

同僚が「コミットしたら、動作確認用の試し書きの行まで一緒に記録されていた」と困っています。この事故を防ぐために、commit の直前に何をすべきだったかを説明してください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

- git diff: まだ add していない変更を見せる
- git diff --staged: add 済みの変更(次のコミットに入る内容)を見せる

2つの diff は見る場所が違うだけで、役割はどちらも「変更を読むこと」です。

</details>

<details>
<summary>問2の解答例</summary>

消えていません。add でステージングエリアに載ったため、「未 add の変更」を見せる git diff の守備範囲から外れただけです。

git diff --staged を打てば、その変更が表示されます。

</details>

<details>
<summary>問3の解答例</summary>

commit を打つ前に git diff --staged で、コミットされる内容を読むべきでした。

覚えのない行(試し書きなど)があれば、コミット前に気づいてファイルを直せます。コミット直前の diff --staged を習慣にするのが対策です。

</details>

## 確認クイズ

### Q1. git diff(オプションなし)が見せるものはどれですか。

- A. まだ add していない変更
- B. add 済みの変更
- C. 過去のコミットの一覧

<details>
<summary>答え</summary>

**A** — 素の git diff の守備範囲は「まだ add していない変更」です。add 済みの変更は表示されません。

</details>

### Q2. add 済みの変更(次のコミットに入る内容)を確かめたいとき、打つコマンドはどれですか。

- A. git diff
- B. git diff --staged
- C. git status

<details>
<summary>答え</summary>

**B** — --staged を付けると、ステージングエリアに載っている変更が表示されます。ここに出た内容がそのまま次のコミットに入ります。

</details>

### Q3. ファイルを編集して add した直後、git diff の表示が空でした。この状態の説明として正しいものはどれですか。

- A. 変更が失われたので、編集をやり直す必要がある
- B. 変更はステージングエリアに載っており、git diff の守備範囲の外にあるだけ
- C. Gitが壊れているので、リポジトリを作り直す必要がある

<details>
<summary>答え</summary>

**B** — 表示が空なのは「未 add の変更がない」という意味です。変更は消えておらず、git diff --staged で確認できます。

</details>

### Q4. 「試し書きの行を入れたまま記録してしまう」事故を防ぐ習慣として、最も適切なものはどれですか。

- A. コミットの直前に git diff --staged を読む
- B. コミットした直後に git status を打つ
- C. 編集のたびにファイルのコピーを取っておく

<details>
<summary>答え</summary>

**A** — コミットされる内容を記録の直前に自分の目で確かめれば、覚えのない行にコミット前に気づけます。コピーを増やす管理には戻りません。

</details>
