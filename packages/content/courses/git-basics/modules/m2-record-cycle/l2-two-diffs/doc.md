# レッスン2-2 diffを使い分ける

## このレッスンの目標

- [ ] git diff が「まだ add していない変更」を見せることを説明できる
- [ ] git diff --staged で add 済みの変更を確かめられる
- [ ] コミット直前に diff --staged を読む習慣の意味を説明できる

## 2-2-1 git diffは未addの変更

> **git diff が見せるのは、まだ add していない変更**

add してから git diff を打つと、何も表示されません。「さっきの変更が消えた?」と焦る場面ですが、消えてはいません。

git diff の守備範囲は「作業中のファイルとステージングエリアの差」です。add した変更はステージングエリアに載ったので、git diff の守備範囲の外に移っただけです。

```bash
git diff
# +単価: 1,200円 が表示される
git add price.txt
git diff
# (何も表示されない = 未addの変更がない)
```

表示が空なのは「未 add の変更がない」という意味であって、変更が失われたわけではありません。

## 2-2-2 --stagedはadd済みの変更

> **git diff --staged で、add 済みの変更(コミットされる内容)を見る**

add 済みの変更こそ、一番確かめたい内容です。次のコミットにそのまま入るからです。それを見せてくれるのが `--staged` オプションです。

```bash
git add price.txt
git diff --staged
# +単価: 1,200円
# ↑ 次のコミットに入る変更が表示される
```

2つの diff は、見る場所が違います。

| コマンド | 見せるもの |
| --- | --- |
| git diff | まだ add していない変更 |
| git diff --staged | add 済みの変更(次のコミットに入る内容) |

diff --staged は「コミットされる内容の試し刷り」と考えると覚えやすいです。

## 2-2-3 コミット前にdiffを読む

> **コミットの直前に diff --staged を読む習慣が、入れ間違いを防ぐ**

「動作確認の試し書きを入れたまま記録した」「消したつもりの行が残っていた」は、実務の定番事故です。コミットしてから気づくと、直すのに余計な手間がかかります。

そこで、commit を打つ手前で必ず1回、diff --staged を読みます。

```bash
git diff --staged              # 入る内容を最終確認
# +単価: 1,200円
# +test ← 覚えのない行に気づける
git commit -m "価格表の単価を更新"
```

覚えのない行に気づいたら、コミットする前にファイルを直して add からやり直せます。送信前にメールを読み返すのと同じで、数秒の確認が事故の大半を防ぎます。
