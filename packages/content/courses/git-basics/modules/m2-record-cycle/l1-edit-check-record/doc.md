# レッスン2-1 変更→確認→記録のサイクル

## このレッスンの目標

- [ ] status に出る modified の意味を説明できる
- [ ] git diff で変更の中身を確かめ、- と + の行を読める
- [ ] 編集 → status → diff → add → commit の流れを手で回せる

## 2-1-1 modifiedの意味

> **コミット済みのファイルを編集すると modified(変更あり)になる**

Module 1 では、新しいファイルを add して commit するところまでを学びました。しかし実務はそこで終わりません。コミットしたファイルも、翌日にはまた直すことになります。

一度コミットしたファイルを編集してから git status を打つと、こう表示されます。

```bash
git status
# Changes not staged for commit:
#   modified:   nippou.txt
```

**modified** は「記録済みのファイルが、最後のコミットと違う中身になっている」という状態の名前です。Module 1 で見た Untracked と対で覚えましょう。

| 表示 | 意味 |
| --- | --- |
| Untracked | Gitがまだ見ていない新しいファイル |
| modified | コミット済みのファイルに変更がある |

どちらも故障ではなく、status が今の状態を教えてくれているだけです。

## 2-1-2 git diffで変更を読む

> **git diff で「これから記録しようとしている変更」を読める**

git status で分かるのは「どのファイルが modified か」までです。中のどの行をどう変えたのかは、status には出てきません。

そこで使うのが git diff です。

```bash
git diff
```

diff(差分)は、編集した箇所だけを抜き出して表示します。変わっていないファイルは表示されません。

- status が教えるのは「ファイル名」
- diff が教えるのは「中身の変わった行」

「昨日どこを直したんだっけ」と思ったら、記録する前に diff で自分の変更を読み返せます。この「記録前に読める」ことが、後の入れ間違い防止につながります。

## 2-1-3 diffの読み方

> **diff は - の行が変更前、+ の行が変更後**

git diff を打つと、行頭に記号の付いた行が並びます。読むべき記号は2つだけです。

- `-` の行: 消えた(直される前の)内容
- `+` の行: 新しく書かれた内容

価格表を直したときの表示例です。

```text
-単価: 1,000円
+単価: 1,200円
+※ 4月から改定
```

これは「1,000円 の行を 1,200円 に書き換え、注記を1行追加した」と読めます。

- `-` と `+` がペアで並ぶ → 行の書き換え
- `+` だけ → 行の追加
- `-` だけ → 行の削除

この2記号が読めれば、diff の本体は読めたも同然です。

## 2-1-4 基本サイクル

> **編集 → status → diff → add → commit が日々の基本サイクル**

コマンドを個別に覚えても、実務では「次に何を打つか」で手が止まります。そこで、1日の作業を1つの型として覚えてしまいます。

```bash
git status                     # 何が変わった?
git diff                       # どう変わった?
git add nippou.txt
git commit -m "日報に進捗を追記"
```

ポイントは、確認の2つ(status と diff)が真ん中に挟まっていることです。

1. 編集する
2. status で「何が変わったか」を確かめる
3. diff で「どう変わったか」を確かめる
4. add で記録するファイルを選ぶ
5. commit で記録する

「読まずに記録しない」がこの型の意味です。このサイクルを1日に何度も回すのが、Gitを使う日常になります。
