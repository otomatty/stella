# レッスン10-2 ブランチの運用

## このレッスンの目標

- [ ] 「種類/内容」の型でブランチ名を付けられる
- [ ] 作業を始めるときの「main を pull してから枝を出す」手順を実行できる
- [ ] 枝を短命に保つ理由をコンフリクトと結びつけて説明できる

## 10-2-1 枝名は種類/内容

> **ブランチ名は feature/login-form のように「種類/内容」の型で付ける**

チームのリポジトリにはブランチがいくつも並びます。`test` や `sato-work` のような名前では、開かないと何の作業か分かりません。ブランチ一覧は他人も見るので、名前だけで中身が伝わることが大事です。コミットメッセージと同じ構図です。

定番の型が「種類/内容」です。

```bash
git switch -c feature/login-form    # ログイン画面を作る作業
git switch -c fix/price-rounding    # 価格の丸め誤差を直す作業
```

| 部分 | 書き方 | 例 |
| --- | --- | --- |
| 種類 | 作業の分類 | `feature`(機能追加)、`fix`(不具合修正) |
| 内容 | 英小文字とハイフンで短く | `login-form`、`price-rounding` |

名前を見ただけで「種類」と「中身」が分かれば、ブランチ一覧がそのまま作業の地図になります。ここでもチームの決まりがあればそちらを優先します。

## 10-2-2 最新のmainから出す

> **作業を始める前に main を pull してから、そこで枝を出す**

チーム開発では、他の人の作業が毎日 main に合流していきます。自分が何もしなくても main は進むので、手元の main は pull しない限りどんどん古くなります。古い main から枝を出すと、出発点の時点で既にチームとズレた状態になり、合流のときの差が大きくなります。

そこで、作業を始めるときは毎回この3ステップを型として実行します。

```bash
git switch main                      # 1. mainに戻る
git pull                             # 2. 最新に追いつく
git switch -c feature/report-search  # 3. そこから枝を出す
```

どれも既に学んだコマンドです。新しい知識は「この順に毎回やる」という運用だけです。出発点が新しいほど合流の差は小さくなります。

## 10-2-3 枝は長生きさせない

> **長生きした枝ほど戻しにくい(1〜数日で PR にして返す)**

枝の上で作業を続けているあいだも、main には他の人の変更が合流し続けます。つまり時間がたつほど main との差は自動的に開き、差が開くほどコンフリクトが増えて、合流そのものが大仕事になります。

```text
NG: feature/renewal を3週間育てる
    → mainと大きくズレて、合流時にコンフリクトの山

OK: 作業を3つに分け、それぞれ1〜2日で PR にして返す
    → 1回ごとの差が小さく、すぐ合流できる
```

同じ作業量でも、返し方で合流の苦労はまったく違います。小さく返すほうがコンフリクトが減るだけでなく、レビューする人も差分を読みやすくなります。枝の寿命が1週間を超えそうになったら、作業の分け方を疑うのが目安です。
