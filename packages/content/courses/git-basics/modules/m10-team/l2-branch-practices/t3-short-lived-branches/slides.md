# 10-2-3
# 枝は長生きさせない

Git入門研修 — Module 10 / レッスン10-2

<!-- ノート: 名前、出発点ときて、最後は枝の寿命です。どれくらいで返すのが良いのかを押さえます。 -->

---

## なぜ必要か

- 作業しているあいだも、main には他の人の変更が合流し続ける
- 枝の上で作業を続けるほど、main との差は開いていく

<!-- ノート: 自分の枝が止まっていても、mainは進みます。時間そのものが差を生む、という感覚が大事です。 -->

---

## 結論

**長生きした枝ほど戻しにくい(1〜数日で PR にして返す)**

- 差が開くほどコンフリクトが増え、合流が大仕事になる
- 大きな作業は小さく分けて、こまめに返す

<!-- ノート: 数週間育てた枝の合流は、それ自体が1つの仕事になってしまいます。小さく返すほうが、自分もレビューする人も楽です。 -->

---

## よくある間違い

```text
NG: feature/renewal を3週間育てる
    → mainと大きくズレて、合流時にコンフリクトの山

OK: 作業を3つに分け、それぞれ1〜2日で PR にして返す
    → 1回ごとの差が小さく、すぐ合流できる
```

<!-- ノート: 同じ作業量でも、返し方で合流の苦労がまったく違います。枝が1週間を超えそうなら分け方を疑う、が目安です。 -->

---
