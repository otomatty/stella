# レッスン10-2 演習 — ブランチの運用

対象トピック: 10-2-1 〜 10-2-3

## ハンズオン

手元の VS Code のターミナルで試します。レッスン10-1 の演習で作った `git-practice-m10` をそのまま使います(無い場合は新しいフォルダで `git init` し、適当なファイルを1つコミットしてから始めてください)。

このリポジトリにはリモートが無いので、`git pull` の手順は口に出して確認するだけにし、枝の名前と出し方・返し方を練習します。

1. 「種類/内容」の型で枝を出す

   ```bash
   git switch main
   git switch -c feature/add-agenda
   ```

2. エディタで `meeting-notes.txt` に「議題: 新オフィスの見学日程」と1行追記して保存する
3. 枝の上でコミットする

   ```bash
   git add meeting-notes.txt
   git commit -m "feat: 議事メモに次回の議題を追加"
   ```

4. main に戻って合流し、済んだ枝を消す(枝を長生きさせない練習)

   ```bash
   git switch main
   git merge feature/add-agenda
   git branch -d feature/add-agenda
   ```

5. `git log --oneline` で、枝の作業が main に入ったことを確かめる
6. 最後に、リモートがある実務での「作業を始めるときの型」を声に出して言う
   (main に戻る → pull で最新に追いつく → そこから枝を出す)

## 演習問題

### 問1(基本)

次のブランチ名を「種類/内容」の型に直してください。作業内容は「日報画面の日付が1日ズレる不具合を直す」です。

```text
sato-work
```

### 問2(基本)

明日の朝、「会員一覧に CSV 出力を足す」作業を始めます。最初にターミナルで打つコマンドを、順番どおり3行で書いてください(リモートはあるものとします)。

### 問3(応用)

同僚が「大型リニューアルの枝を1か月育てていて、そろそろ main に合流したい」と言っています。この合流で何が起きそうですか。また、次からどうすべきだったかを1〜2文で書いてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

```text
fix/daily-report-date
```

不具合修正なので種類は `fix`、内容は英小文字とハイフンで短く書きます。`fix/report-date-off-by-one` のように、中身が伝われば言葉選びは多少違っても構いません。

</details>

<details>
<summary>問2の解答例</summary>

```bash
git switch main
git pull
git switch -c feature/member-csv-export
```

「main に戻る → 最新に追いつく → そこから枝を出す」の3ステップです。pull を挟まずに枝を出すと、古い main が出発点になってしまいます。

</details>

<details>
<summary>問3の解答例</summary>

1か月ぶんの main との差が積もっているので、大量のコンフリクトが起きて、合流の解決作業そのものが大仕事になりそうです。次からは作業を小さく分けて、1〜数日ごとに PR にして返すべきでした。

</details>

## 確認クイズ

### Q1. ブランチ名の付け方として、このレッスンの型に合っているものはどれですか。

- A. `feature/login-form` のように「種類/内容」で付ける
- B. `tanaka-0415` のように「担当者と日付」で付ける
- C. `new-branch-2` のように連番で付ける

<details>
<summary>答え</summary>

**A** — 名前だけで「種類」と「中身」が分かるのが型の目的です。担当者名や連番では、開かないと何の作業か分かりません。

</details>

### Q2. 作業を始めるときの正しい順番はどれですか。

- A. 枝を出す → main に戻る → pull する
- B. main に戻る → pull する → 枝を出す
- C. pull する → 枝を出す → main に戻る

<details>
<summary>答え</summary>

**B** — 最新の main を出発点にするため、「戻る → 追いつく → 枝を出す」の順で行います。pull より先に枝を出すと、古い main が出発点になります。

</details>

### Q3. 「枝を長生きさせない」のはなぜですか。

- A. 古いブランチはGitが自動で削除してしまうため
- B. ブランチが増えるとリポジトリの容量が足りなくなるため
- C. mainとの差が開くほどコンフリクトが増え、合流が大変になるため

<details>
<summary>答え</summary>

**C** — 作業中も main には他の人の変更が合流し続けます。時間がたつほど差が開くので、1〜数日で PR にして返します。

</details>

### Q4. 手元の main が古くなっていく理由として正しいものはどれですか。

- A. 他の人の作業が main に合流し続けるのに、pull しないと手元に反映されないため
- B. Gitが一定期間ごとに手元のコミットを自動で削除するため
- C. ブランチを出すたびに main の中身が減っていくため

<details>
<summary>答え</summary>

**A** — チーム開発では自分が何もしなくても main は進みます。だから作業を始める前に pull で追いつくのが型になります。

</details>
