# レッスン10-4 演習 — 困ったときの型

対象トピック: 10-4-1 〜 10-4-4

研修の総仕上げの演習です。これまで学んだコマンドだけで、困った場面を安全にくぐり抜ける練習をします。

## ハンズオン

手元の VS Code のターミナルで試します。`git-practice-m10` を開いてください(無い場合は新しいフォルダで `git init` し、`meeting-notes.txt` を1つコミットしてから始めてください)。

### その1: エラーを読んで一手を打つ

1. main にいることを確かめてから、`meeting-notes.txt` に1行追記して保存する(コミットはしない)
2. 変更を残したまま枝を切り替えようとして、エラーを出す

   ```bash
   git switch -c feature/error-reading
   ```

   ※ この操作でエラーが出ない場合もあります(切り替え先に変更をそのまま持っていけるため)。出なかったら、エラー文の代わりに 10-4-2 の doc のメッセージ例を読んで次へ進んでください
3. エラーが出たら最後の行を読み、書いてある一手(commit か stash)を選んで実行する
4. `git status` で、変更が片付いて枝を切り替えられる状態になったことを確かめる

### その2: 間違った枝でのコミットを立て直す

1. main に切り替え、わざと main のままコミットしてしまう

   ```bash
   git switch main
   ```

   `meeting-notes.txt` に「持ち物: プロジェクター」と1行追記して保存し、

   ```bash
   git add meeting-notes.txt
   git commit -m "feat: 会議の持ち物リストを追加"
   ```

2. `git status` と `git log --oneline` で現在地を確かめる(mainにいて、コミット済み)
3. その場から新しい枝を出して、コミットごと移す

   ```bash
   git switch -c feature/bring-list
   git log --oneline   # さっきのコミットがこの枝に乗っている
   ```

4. 最後に確認: 手元の main 側にも記録が残っています。実務でここから main を戻したくなったら、履歴を消すコマンドを打つ前に人に聞く——と声に出して言ってから終わります

## 演習問題

### 問1(基本)

「なんか変だ」と思ったとき、最初に打つ3つのコマンドと、それぞれで何が分かるかを書いてください。

### 問2(基本)

`git push` をしたら、次のメッセージが出ました。次に打つべき一手を答えてください。

```text
! [rejected]        main -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. ... You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
```

### 問3(応用)

新人の同僚から「リポジトリがぐちゃぐちゃになった。ネットで見つけた `reset --hard` を打とうと思う」と相談されました。止めるべき理由と、代わりに勧める行動を2〜3文で書いてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

```bash
git status          # 今どの枝にいて、何が変更中・ステージ済みか
git log --oneline   # どこまでコミットできているか
git diff            # まだ記録していない変更の中身
```

3つとも見るだけの安全なコマンドです。現在地が分かれば、次の一手はたいてい絞れます。

</details>

<details>
<summary>問2の解答例</summary>

`git pull` です。

hint の行に「先にリモートの変更を取り込んでから push し直して(`git pull`)」と次の一手がそのまま書いてあります。リモートに自分の持っていないコミットがあるので、pull で取り込んでから push します。

</details>

<details>
<summary>問3の解答例</summary>

`reset --hard` は履歴ごと作業を消す、取り返しのつかないコマンドなので、状況が分からないまま打つのは危険です。まず `status` と `log --oneline` で現在地を控えて、履歴を消す操作の前にチームの詳しい人に相談するよう勧めます。コミット済みの変更は消さない限り残っているので、相談を待っても状況は悪化しません。

</details>

## 確認クイズ

### Q1. 困ったときに最初にやることとして、このレッスンの型に合うものはどれですか。

- A. 検索で見つけたコマンドをすぐ試す
- B. status・log・diff で現在地を確かめる
- C. リポジトリのフォルダを丸ごとコピーして避難する

<details>
<summary>答え</summary>

**B** — 3つとも見るだけの安全なコマンドです。現在地が分からないまま手を動かすことが、いちばん傷を広げます。

</details>

### Q2. Git のエラーメッセージについて、正しい説明はどれですか。

- A. 原因と次の一手のヒントが書いてあることが多いので、まず読む
- B. 読んでも意味がないので、すぐ検索する
- C. エラーが出た時点で履歴は失われている

<details>
<summary>答え</summary>

**A** — Git のエラーの多くは「〜してから、やり直して」と対処まで提案してくれます。英語でもコマンド名だけ拾えば読めます。

</details>

### Q3. main のまま間違えてコミットしてしまいました。作業を失わずに立て直す一手はどれですか。

- A. リポジトリを削除して、最初から作り直す
- B. コミットしたファイルを手で元に戻して保存する
- C. その場で `git switch -c feature/...` を打ち、コミットごと新しい枝に移る

<details>
<summary>答え</summary>

**C** — `switch -c` は今いる場所から新しい枝を出すので、直前のコミットごと新しい枝に乗ります。コミットは消えておらず、作業も失われません。

</details>

### Q4. 「壊す前に聞く」の型として正しい行動はどれですか。

- A. reset --hard を打ってから、結果を報告する
- B. status と log の結果を控えて、履歴を消す操作の前に詳しい人に相談する
- C. 誰にも言わず、リポジトリを作り直して何もなかったことにする

<details>
<summary>答え</summary>

**B** — 履歴を消す操作だけは取り返しがつきません。コミット済みの変更は消さない限り残っているので、状況を控えて相談する時間は十分あります。

</details>

### Q5. 相談を待つ間に状況が悪化しない、と言える理由はどれですか。

- A. Git は一定時間ごとに自動でバックアップを取っているため
- B. コミット済みの変更は、履歴を消す操作をしない限り残っているため
- C. エラーが出た時点で Git がリポジトリを自動修復するため

<details>
<summary>答え</summary>

**B** — この研修の出発点だった「履歴が残っていれば戻れる」がここでも効きます。コミットさえしてあれば、落ち着いて助けを求められます。

</details>
