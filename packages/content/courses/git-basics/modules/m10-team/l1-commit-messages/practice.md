# レッスン10-1 演習 — 伝わるコミットメッセージ

対象トピック: 10-1-1 〜 10-1-4

## ハンズオン

手元の VS Code のターミナルで試します。このモジュールの演習用に、新しいフォルダを1つ作ります。

1. VS Code の「フォルダーを開く」で、新しいフォルダ `git-practice-m10` を作って開く
2. ターミナルを開き、`git init` でリポジトリにする
3. エディタで `meeting-notes.txt` を作り、「4月定例の議事メモ」と1行書いて保存する
4. 要約だけのコミットをする

   ```bash
   git add meeting-notes.txt
   git commit -m "4月定例の議事メモを作成"
   ```

5. `meeting-notes.txt` に「次回は5/10に変更」と1行追記して保存する
6. 要約と本文(なぜ)を持つコミットをする

   ```bash
   git add meeting-notes.txt
   git commit -m "次回開催日を5/10に変更" -m "会場の予約が取れなかったため"
   ```

7. `git log --oneline` で一覧を読み返し、2件とも「何をしたか」が分かるか確かめる
8. `git log` (オプションなし)でも表示し、2件目の本文が1行空けて記録されていることを確かめる

## 演習問題

### 問1(基本)

次のコミットメッセージの1行目を、伝わる要約に書き直してください。変更の内容は「会員一覧の資料に、退会済みの会員を表示しない条件を足した」です。

```text
修正しました
```

### 問2(基本)

問1の変更には「営業部から、退会済みの行が混ざって集計を誤るという連絡があった」という背景がありました。要約と本文を持つコミットメッセージの全体を書いてください。

### 問3(応用)

あなたは「1行目は日本語で長く丁寧に書く」派ですが、配属先のチームは `fix:` などの prefix + 短い要約という型を使っています。どちらの書き方でコミットすべきですか。理由も1文で書いてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

```text
会員一覧から退会済みの会員を除外
```

「何を」(会員一覧)と「どうした」(退会済みを除外)が1行目だけで分かれば正解です。「修正しました」は一覧に並んだとき、開かないと内容が分かりません。

</details>

<details>
<summary>問2の解答例</summary>

```text
会員一覧から退会済みの会員を除外

退会済みの行が集計に混ざり数値を誤るとの連絡が営業部からあったため
```

1行目に要約、1行空けて本文に「なぜそうしたか」を書きます。差分には写らない背景こそ、本文に残す価値があります。

</details>

<details>
<summary>問3の解答例</summary>

チームの型(prefix + 短い要約)で書くべきです。書き方が揃っていれば全員が履歴を同じ読み方で流し読みできるので、型が揃っていること自体に自分の好みより大きな価値があるためです。

</details>

## 確認クイズ

### Q1. コミットメッセージの1行目の書き方として最も良いものはどれですか。

- A. 「修正」のように短ければ短いほど良い
- B. 「何をしたか」が一目で分かる要約を50字目安で書く
- C. 変更の背景や理由をすべて1行目に詰め込む

<details>
<summary>答え</summary>

**B** — 1行目は一覧表示にそのまま出る見出しです。「何を」「どうした」が分かる要約にします。理由は1行空けて本文に書きます。

</details>

### Q2. 「なぜそうしたか」を書く場所として正しいものはどれですか。

- A. 1行目の要約に続けて、同じ行に書く
- B. コミットメッセージには書かず、別のメモ帳に残す
- C. 1行目のあとに1行空けて、本文として書く

<details>
<summary>答え</summary>

**C** — 要約と本文の間に空行を1行はさむのが型です。Gitのツール類は最初の空行までを見出しとして扱います。

</details>

### Q3. `fix:` や `feat:` のような prefix について、正しい説明はどれですか。

- A. 1行目の頭に付ける「変更の種類」のラベルで、チームの型があればそれに従う
- B. Gitが自動で付ける記号で、自分では書かない
- C. 付けないとコミットがエラーになる、Gitの必須の文法

<details>
<summary>答え</summary>

**A** — prefix は書き方を揃えるためのチームのルールの一例です。Gitの文法ではないので、どんな型を使うかはチームごとに決まっています。

</details>

### Q4. 自分のコミットメッセージの品質を確かめる方法として、このレッスンで学んだものはどれですか。

- A. `git log --oneline` の一覧を読み返し、意味が分かるか確かめる
- B. メッセージの文字数を数え、50字ちょうどになっているか確かめる
- C. コミットの直後に差分を見て、変更が正しいか確かめる

<details>
<summary>答え</summary>

**A** — メッセージが実際に読まれる場面は一覧表示です。読まれる場面と同じ形で読み返し、一覧だけで「何をしたか」が追えれば合格です。

</details>
