# レッスン10-1 伝わるコミットメッセージ

## このレッスンの目標

- [ ] 「1行目は要約、1行空けて本文に理由」の型でコミットメッセージを書ける
- [ ] prefix などチームの型に合わせる理由を説明できる
- [ ] `log --oneline` で自分のメッセージの品質を点検できる

## 10-1-1 1行目は要約

> **1行目は「何をしたか」が一目で分かる要約にする(50字目安)**

コミットメッセージを読むのは、未来の自分とチームメイトです。書くのは数秒ですが、読まれる回数はその何倍にもなります。そして読み手は、変更の中身をまだ知りません。

「修正」「更新」だけのメッセージが並んだ履歴は、1件ずつ開いて差分を見ないと何も分かりません。1行目は一覧表示にそのまま出る「見出し」なので、**「何を」「どうした」が一目で分かる要約**にします。長さは50字が目安です(一覧で切れずに読める長さ)。

```bash
# 伝わらない例
git commit -m "修正"

# 伝わる例
git commit -m "会員一覧の並び順を入会日順に変更"
```

「何を」(会員一覧の並び順)と「どうした」(入会日順に変更)が入るだけで、開かずに内容が追えるメッセージになります。

## 10-1-2 なぜは本文に書く

> **「なぜそうしたか」は1行空けて本文に書く**

「何をしたか」は差分を見れば分かります。しかし「なぜそうしたか」は、書き残さない限りどこにも残りません。理由の分からない変更は、後から直してよいのか、消してよいのかを誰も判断できなくなります。

そこでコミットメッセージには型があります。

```text
価格表の消費税率を10%に更新

9月請求分から新税率を適用するため
```

- 1行目 = 要約(見出し)
- 空行を1行はさむ
- 2行目以降 = 本文。「なぜそうしたか」を書く

空行はただの見た目ではありません。Gitのツール類は「最初の空行まで」を見出しとして扱うので、この区切りが型になっています。

ターミナルからは `-m` を2つ書くと、この形で記録できます。

```bash
git commit -m "価格表の消費税率を10%に更新" -m "9月請求分から新税率を適用するため"
```

すべてのコミットに長い本文が要るわけではありません。差分を見ても理由が伝わらないと感じたら本文を書く、と覚えておけば十分です。

## 10-1-3 チームの型に従う

> **prefix などチームの型があるなら、自分の好みよりそれに従う**

現場の履歴を見ると、`fix:` や `feat:` のような記号で始まるコミットメッセージをよく見かけます。これは **prefix**(接頭辞。1行目の頭に付ける「変更の種類」のラベル)で、チームでメッセージの書き方を揃えるためのルールの一例です。

```text
fix: 会員一覧の重複表示を解消
feat: 日報に検索機能を追加
docs: README のセットアップ手順を最新化
```

| prefix の例 | 意味 |
| --- | --- |
| `fix:` | 不具合の修正 |
| `feat:` | 機能の追加 |
| `docs:` | 文書だけの変更 |

大事なのは、どの型が正しいかではなく**チームで揃っていること**です。全員が同じ書き方をしていれば、履歴を同じ読み方で流し読みできます。だからチームの型があるなら、自分の好みよりそれに従います。新しい現場に入ったら、まず過去のコミットを眺めてチームの型をまねるのが早道です。

## 10-1-4 一覧で読めるかが品質

> **log --oneline で読み返して意味が分かるかが、メッセージの品質**

書いた直後は、どんなメッセージでも分かった気になります。しかし実際にメッセージが読まれる場面は、ほとんどが一覧表示です。だから品質の確認も、読まれる場面と同じ形でやります。

```bash
git log --oneline
# 3f2a1c9 feat: 日報に検索機能を追加
# a8d4e07 fix: 会員一覧の重複表示を解消
# 91b6c53 修正   ← これだけ何をしたか分からない
```

コミットしたら `git log --oneline` で読み返す習慣を付けましょう。一覧だけで「何をしたか」が追えれば合格です。伝わらないメッセージは一覧に混ざるとすぐ目立つので、読み手の視点を毎回体験できます。
