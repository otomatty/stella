# レッスン10-3 演習 — VS CodeでGitを使う

対象トピック: 10-3-1 〜 10-3-4

## ハンズオン

手元の VS Code で試します。レッスン10-1・10-2 で使った `git-practice-m10` を開いてください(無い場合は新しいフォルダで `git init` し、`meeting-notes.txt` を1つコミットしてから始めてください)。

### その1: ソース管理ビューで diff と commit

1. エディタで `meeting-notes.txt` の1行を書き換えて保存する(例: 開催時刻を変える)
2. 左端の枝分かれアイコンをクリックして、ソース管理ビューを開く
3. 「変更」に並んだ `meeting-notes.txt` をクリックし、左右並びの diff を確認する
   (左が変更前・右が変更後、変わった行だけに色が付いていること)
4. ファイル名の「+」を押してステージし、「ステージされている変更」へ移ることを確かめる
5. 入力欄に「fix: 開催時刻を修正」と書いて「コミット」ボタンを押す
6. ターミナルで確かめる(裏では同じ Git であることの確認)

   ```bash
   git status
   git log --oneline
   ```

### その2: マージエディタでコンフリクトを解決

1. ターミナルで、同じ行を別々に変える2つの状態を作る

   ```bash
   git switch -c feature/room-a
   ```

2. エディタで `meeting-notes.txt` の会場の行を「会場: 会議室A」に変えて保存し、コミットする

   ```bash
   git add meeting-notes.txt
   git commit -m "feat: 会場を会議室Aに決定"
   ```

3. main に戻り、同じ行を「会場: 会議室B」に変えて保存し、コミットする

   ```bash
   git switch main
   git add meeting-notes.txt
   git commit -m "feat: 会場を会議室Bに決定"
   ```

4. マージしてコンフリクトを起こす

   ```bash
   git merge feature/room-a
   ```

5. ソース管理ビューに出た `meeting-notes.txt` から「マージ エディターで解決」を開く
6. 上段の左右(自分の枝と相手の枝)を見比べ、残したい側の「取り込む」を選び、完了する
7. いつもどおり確定し、済んだ枝を消す

   ```bash
   git add meeting-notes.txt
   git commit -m "merge: 会場の決定を統合"
   git branch -d feature/room-a
   ```

## 演習問題

### 問1(基本)

ソース管理ビューで、変更したファイルの「+」を押す操作と「コミット」ボタンを押す操作は、それぞれどのコマンドに対応しますか。

### 問2(基本)

ターミナルの diff と比べて、ファイル名をクリックして開く左右並びの diff は何が読みやすいですか。1〜2点挙げてください。

### 問3(応用)

GUI だけで Git を覚えた同僚が「変更の同期ボタンを押したら何かが起きたが、何が起きたか分からない」と困っています。裏で動いている操作を説明し、状態を確かめる方法を1つ教えてあげてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

「+」は `git add`(ステージングエリアに載せる)、「コミット」ボタンは `git commit`(入力欄のメッセージでコミットする)に対応します。

</details>

<details>
<summary>問2の解答例</summary>

- 左(変更前)と右(変更後)が並ぶので、+ と − を頭の中で組み立てなくてよい
- 変わった行だけに色が付くので、見直しは色の行を追うだけで済む

</details>

<details>
<summary>問3の解答例</summary>

「変更の同期」は裏では `git pull` と `git push` で、リモートの新しいコミットを取り込み、手元のコミットを送っています。何が起きたか確かめるには、ターミナルで `git status` や `git log --oneline` を打てば、画面と同じリポジトリの状態がそのまま見えます。

</details>

## 確認クイズ

### Q1. VS Code でソース管理ビューを開く方法はどれですか。

- A. 左端のアクティビティバーにある、枝分かれした形のアイコンをクリックする
- B. ターミナルに `git open` と入力する
- C. ファイルを右クリックして「印刷」を選ぶ

<details>
<summary>答え</summary>

**A** — 左端の縦のアイコン列(アクティビティバー)の枝分かれマークが入口です。変更一覧・メッセージ入力欄・コミットボタンが並びます。

</details>

### Q2. ソース管理ビューで変更ファイルをクリックすると起きることはどれですか。

- A. ファイルが即座にコミットされる
- B. 変更前と変更後が左右に並んだ diff が開く
- C. ファイルの変更が取り消される

<details>
<summary>答え</summary>

**B** — クリックは表示するだけで、何も変更しません。左が変更前・右が変更後で、削除行は赤、追加行は緑で色が付きます。

</details>

### Q3. マージエディタの利点として正しいものはどれですか。

- A. コンフリクト自体が起きなくなる
- B. どちらを残すかをボタンで選べて、マーカーの消し忘れが起きない
- C. マージが自動で完了し、add や commit も不要になる

<details>
<summary>答え</summary>

**B** — マージエディタでも「どちらを残すか」を決めるのは自分です。ただしマーカーを手で触らないので、消し忘れの事故が起きません。解決後の add と commit は必要です。

</details>

### Q4. GUI の Git 操作とコマンドの関係について、正しいものはどれですか。

- A. GUI はコマンドとは別のしくみで履歴を記録している
- B. GUI で作ったコミットはターミナルの log には表示されない
- C. GUI の操作は裏では同じ Git で、意味は学んだコマンドと同じ

<details>
<summary>答え</summary>

**C** — GUI は同じ Git の別の入口です。「+」= add、「コミット」ボタン = commit のように対応し、どちらで操作しても同じ履歴に記録されます。

</details>
