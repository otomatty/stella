# レッスン8-4 pushが拒否されたら

## このレッスンの目標

- [ ] rejected が「リモートが先へ進んでいる合図」だと説明できる
- [ ] rejected されたら pull してから push し直す手順を実行できる
- [ ] 強制 push の危険性を説明し、共有ブランチで使わない判断ができる

## 8-4-1 rejectedは先行の合図

> **rejected はリモートが自分より先へ進んでいる合図(壊れていない)**

push したら真っ赤な表示で断られる。チーム開発では誰にでも、それも頻繁に起きる出来事です。

```text
! [rejected]        main -> main (fetch first)
error: failed to push some refs to
       'https://github.com/sato-dev/daily-report.git'
```

**rejected** の意味は「リモートに、あなたの知らないコミットがあります」です。自分が作業する間に、同僚のコミットがリモートに増えていただけです。

もしこのまま push を通してしまうと、同僚のコミットを知らずに上書きしかねません。それを防ぐために、Git が**わざと**止めてくれています。つまり rejected はエラーというより、安全装置が働いた合図です。壊れていないので、慌てる必要はありません。

## 8-4-2 pullしてからpush

> **先に pull で取り込んでから、push し直せばよい**

rejected されたまま push を繰り返しても、何度でも断られます。リモートに増えた分を、まず自分が受け取る必要があるからです。手順は2つだけです。

```bash
git pull
# (リモートの先行分が手元に合流する)
git push
# (今度は成功する)
```

1. pull で「リモートの先行分」と「自分のコミット」を手元で合流させる
2. 合流が済んだら、push し直す

pull の中身は merge なので、同じ箇所を互いに変えていればコンフリクトが出ることもあります。その場合も、合流のモジュールで学んだ「あるべき形に編集 → add → commit」の手順で解決してから push すれば大丈夫です。

「rejected を見たら、pull してから push」。この型をそのまま覚えてしまいましょう。

## 8-4-3 force pushは使わない

> **強制 push は他人のコミットを消し得る(共有ブランチでは使わない)**

rejected について調べると、「`--force` を付ければ通せる」という情報が見つかります。rejected を無視して、リモートの履歴を自分の履歴で上書きする操作、いわゆる **強制push** です。

```bash
git push --force   # ← 打たない
```

```text
リモート: A - B - C (同僚のC) → A - B - D (Cが消えた)
```

rejected は「同僚のコミットを消さないための安全装置」でした。強制 push はその安全装置を手で外す操作なので、リモートにしかなかった同僚のコミットは上書きで消えてしまいます。

- rejected の正しい対処は、前のトピックのとおり「pull してから push」です
- この研修では強制 push は使いません。「強制 push が必要に思える」時点で何かがおかしいので、打つ前に必ず人に相談してください

やり直しのモジュールで学んだ「履歴を消す操作は封印する」という方針の、リモート版だと考えてください。
