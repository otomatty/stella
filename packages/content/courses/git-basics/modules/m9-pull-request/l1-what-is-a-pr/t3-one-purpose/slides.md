# 9-1-3
# 1PR1目的

Git入門研修 — Module 9 / レッスン9-1

<!-- ノート: PRの流れが分かったところで、1つのPRに入れる変更の量の話をします。コミットの「1目的」と同じ考え方です。 -->

---

## なぜ必要か

- 作業しているうちに、直したい所が次々見つかる
- 全部まとめて1つの PR にすると、何が起きるか?
- レビューする側の気持ちで考えてみる

<!-- ノート: あるあるです。ついでの修正を積んでいくと、PRはどんどん太ります。見る側の視点に立たせてから結論に入ります。 -->

---

## 結論

**1つのPRには1つの目的だけ(小さいほど早く取り込まれる)**

- 小さい PR はすぐ読めて、すぐレビューが返ってくる
- 目的が1つなら、取り込む・直すの判断も1回で済む

<!-- ノート: 大きなPRはレビューが後回しにされがちで、指摘も増え、マージまでの時間が伸びます。小さく出すほうが結局速いのです。 -->

---

## よくある間違い

```text
悪い例: 「並び順修正 + 新機能 + 誤字直し」を1つのPRに
  → 誤字は良くても新機能に指摘が付き、全部が止まる

良い例: 「並び順修正」「新機能」「誤字直し」を別々のPRに
  → 問題ない分から先にマージされる
```

<!-- ノート: 混ぜたPRは一部への指摘で全体が止まるのが痛いところです。分けてあれば、済んだものから順に取り込めます。 -->

---

## まとめ

**1つのPRには1つの目的だけ(小さいほど早く取り込まれる)**
