## なぜ必要か

- PR が「依頼と相談の場」だとして、いつ開いて、いつ終わるのか
- 全体の流れを知らないと、自分がいまどの段階にいるか分からない

<!-- ノート: 個々の操作より先に地図を持ちます。流れが頭にあれば、この後の各トピックが「どの段階の話か」で整理できます。 -->

---

## 結論

**流れは、枝を push → PR を開く → レビュー → マージ**

- **レビュー** は、取り込む前に内容を確認して相談する工程
- マージで PR は完了。この4段階の繰り返しで開発が進む

<!-- ノート: レビューという言葉をここで導入します。4段階を声に出して1回通し、この順番だけ覚えれば迷わないと伝えます。 -->

---

## 最小の例

```text
1. ブランチで作業して push     (手元 → GitHub)
2. PR を開く                   (GitHub 上)
3. レビュー                    (内容の確認と相談)
4. マージ                      (main に取り込まれて完了)
```

- 1 は手元のターミナル、2〜4 は GitHub 上の操作

<!-- ノート: どこまでが手元で、どこからがGitHub上かの線引きも一緒に確認します。pushまでは今までどおりの操作です。 -->
