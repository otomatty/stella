# レッスン9-1 演習 — PRとは

対象トピック: 9-1-1 〜 9-1-4

## ハンズオン

手元の VS Code のターミナルで試します。Module 8 の演習で GitHub に置いた練習用リポジトリ(`~/git-practice-remote`)を使い、ブランチを push して PR を1つ開いてみます。

1. 練習用フォルダへ移動し、main を最新にします

   ```bash
   cd ~/git-practice-remote
   git switch main
   git pull
   ```

2. 作業用のブランチを作って移動します

   ```bash
   git switch -c update-practice-note
   ```

3. `practice.txt` に1行(例: `PRの練習: 説明には何を・なぜを書く`)を追記して保存します
4. 変更をコミットして、ブランチを push します

   ```bash
   git add practice.txt
   git commit -m "PR練習用のメモを追記"
   git push -u origin update-practice-note
   ```

5. ブラウザで GitHub のリポジトリを開くと「Compare & pull request」ボタンが出ています。押してください
6. タイトルと説明を「何を・なぜ」の形で書きます(例: 何を: 練習メモを1行追記 / なぜ: PR の練習のため)
7. 「Create pull request」を押すと、PR が開きます。`update-practice-note → main` という宛先と、コミット・変更ファイルの一覧を確認しましょう

自分1人のリポジトリでは、他の人の Approve(承認)がなくてもマージまで進められます。ただし今回はまだマージしません。この PR は次のレッスンのレビュー練習で使うので、開いたままにしておいてください。

## 演習問題

### 問1(基本)

PR の画面には `fix-member-sort → main` のような表示があります。これは何を表していますか。

### 問2(基本)

「会員一覧の並び順修正と、新しい検索機能と、READMEの誤字直し」を1つの PR で出すことの問題点を1つ挙げてください。

### 問3(応用)

PR の説明に「どう変えたか」を細かく書かなくてよいのはなぜですか。1文で説明してください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

「fix-member-sort ブランチを main に取り込んでほしい」という依頼の宛先を表しています。

PR は「どのブランチを、どこへ」取り込む依頼かを必ず持ちます。この表示で取り込み元と取り込み先が一目で分かります。

</details>

<details>
<summary>問2の解答例</summary>

一部への指摘で、問題のない変更まで取り込みが止まることです。

たとえば検索機能に修正依頼が付くと、誤字直しのような問題ない変更もマージされずに待たされます。目的ごとに PR を分けてあれば、済んだものから順に取り込めます。レビューの負担が大きくなり後回しにされやすい、という答えでも正解です。

</details>

<details>
<summary>問3の解答例</summary>

どう変えたかは差分そのものに写っていて、レビューする人は差分を見れば分かるからです。

差分に写らないのは「何を・なぜ」という目的と背景だけです。人間が書くのはそこに絞ります。

</details>

## 確認クイズ

### Q1. プルリクエスト(PR)の説明として最も適切なものはどれですか。

- A. 手元の履歴を GitHub へ自動でバックアップする機能
- B. 「このブランチを取り込んでほしい」という依頼と相談の場
- C. main のコミットを1つずつ取り消すための機能

<details>
<summary>答え</summary>

**B** — PR はブランチの取り込み依頼であり、変更内容を見ながら会話できる相談の場です。バックアップや取り消しの機能ではありません。

</details>

### Q2. PR を使った作業の流れとして正しい順番はどれですか。

- A. PR を開く → 枝を push → マージ → レビュー
- B. 枝を push → PR を開く → レビュー → マージ
- C. レビュー → 枝を push → PR を開く → マージ

<details>
<summary>答え</summary>

**B** — まずブランチを push して GitHub に置き、PR を開き、レビューを経てマージで完了します。この4段階の繰り返しで開発が進みます。

</details>

### Q3. 「1つのPRには1つの目的だけ」とするのはなぜですか。

- A. GitHub の仕様で、2つ以上の目的を含む PR は作れないから
- B. 小さい PR はすぐ読めてレビューが早く返り、早く取り込まれるから
- C. PR の数が多いほど評価が上がるから

<details>
<summary>答え</summary>

**B** — 小さく目的が1つの PR はレビューしやすく、判断も1回で済むので早くマージされます。仕様上の制限や評価の話ではありません。

</details>

### Q4. PR のタイトルと説明に書くべき内容として最も適切なものはどれですか。

- A. 何を変えたかと、なぜ変えたか
- B. 変更した行の全文
- C. 使った Git コマンドの一覧

<details>
<summary>答え</summary>

**A** — 書くのは「何を・なぜ」です。どう変えたかは差分が語るので、行の全文やコマンドの記録を書き写す必要はありません。

</details>
