# レッスン9-2 演習 — レビュー

対象トピック: 9-2-1 〜 9-2-4

## ハンズオン

手元の VS Code のターミナルと GitHub の画面で試します。レッスン9-1で開いたままにした練習用リポジトリ(`~/git-practice-remote`)の PR を使い、1人2役でレビューのやりとりを体験します。

1. GitHub で PR を開き、「Files changed」タブを表示します。追記した行が差分として見えることを確認します
2. レビューする人の役になり、差分の行にコメントを付けます。行の左に出る「+」を押し、「この行の表現をもう少し具体的にできますか?」のように書いて投稿します
3. 書いた人の役に戻り、手元で `practice.txt` の該当行を直して保存します
4. 修正コミットを同じブランチへ push します

   ```bash
   cd ~/git-practice-remote
   git add practice.txt
   git commit -m "レビュー指摘に沿って表現を修正"
   git push
   ```

5. GitHub の PR 画面を再読み込みし、コミット一覧と差分に修正が自動で反映されたことを確認します
6. 手順2で付けたコメントに「修正しました」と返事を書きます

なお、GitHub の仕様で自分の PR に自分で Approve は送れません。1人のリポジトリでは Approve がなくてもマージに進めるので、練習に支障はありません。この PR は次のレッスンでマージするので、引き続き開いたままにしておいてください。

## 演習問題

### 問1(基本)

レビューで「この条件、0件のときはどうなりますか?」という質問コメントをもらいました。これは粗探しでしょうか。レビューの位置づけに触れて答えてください。

### 問2(基本)

PR に Request changes が付きました。このあと取るべき行動を、操作の順番で説明してください。

### 問3(応用)

レビューの指摘に納得できず、直さないことにしました。このとき絶対にやってはいけない対応は何ですか。正しい対応とあわせて答えてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

粗探しではありません。レビューは品質を一緒に上げる工程で、質問も立派なレビューコメントです。

見落としていた場合に気づけるうえ、問題なければ「0件のときは空の一覧を表示します」と答えればやりとりは完了します。

</details>

<details>
<summary>問2の解答例</summary>

指摘された点を手元で修正し、同じブランチへ修正コミットを push して、コメントに返事を書き、再レビューを依頼します。

Request changes は拒絶ではなく「直してから取り込みたい」の合図です。PR を作り直す必要はなく、push すれば PR に自動で反映されます。

</details>

<details>
<summary>問3の解答例</summary>

やってはいけないのは、無言で無視することです。正しい対応は、直さない理由をコメントへの返事として書くことです。

例えば「既存の表記に合わせているため今回はこのままにします」のように書きます。返事がそろって初めてレビューのやりとりが完了します。

</details>

## 確認クイズ

### Q1. レビューの位置づけとして最も適切なものはどれですか。

- A. 書いた人の能力を採点する工程
- B. 粗探しではなく、品質を一緒に上げる共同作業の工程
- C. マージを遅らせないために省略すべき工程

<details>
<summary>答え</summary>

**B** — レビューの対象はコードや文書であって人ではなく、提案や質問も含めて品質を一緒に上げる工程です。採点でも省略対象でもありません。

</details>

### Q2. レビューの指摘に沿って修正した結果を PR に届ける方法はどれですか。

- A. PR をいったん閉じて、新しい PR を作り直す
- B. 同じブランチへ修正コミットを push する(PR に自動で反映される)
- C. 修正後のファイルをコメント欄に貼り付ける

<details>
<summary>答え</summary>

**B** — PR はブランチと結びついているので、同じブランチに push すれば差分もコミット一覧も自動で更新されます。作り直しや貼り付けは不要です。

</details>

### Q3. Request changes の意味として正しいものはどれですか。

- A. この PR は拒絶されたので、ブランチごと削除するべきだ
- B. 指摘した点を直してから取り込みたい、という意思表示
- C. 取り込んでよい、という承認の意思表示

<details>
<summary>答え</summary>

**B** — Request changes は「直してから」の合図で、修正の push を待っている状態です。拒絶ではなく、承認は Approve のほうです。

</details>

### Q4. もらったコメントへの対応として適切なものはどれですか。

- A. 直した指摘には「修正しました」、直さない指摘には理由を、全部に返事する
- B. 直した指摘は push で伝わるので、返事は不要
- C. 納得できない指摘は、返事をせずそっとしておく

<details>
<summary>答え</summary>

**A** — コメントには全部返事をします。無言で直す・無言で無視の2つを避け、直した/直さない理由が全コメントに付いた状態を目指します。

</details>
