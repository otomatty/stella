# レッスン9-2 レビュー

## このレッスンの目標

- [ ] レビューがどういう心構えで行う工程かを説明できる
- [ ] 指摘をもらったときの対応(修正 push・返事)を実行できる
- [ ] Approve と Request changes の意味の違いを説明できる

## 9-2-1 レビューは共同作業

> **レビューは粗探しではなく、品質を一緒に上げる工程**

はじめて自分の PR に指摘コメントが付くと、否定された気分になりがちです。逆に自分が見る側に回ると、何を言えばいいのか分からず固まってしまいます。最初に、レビューという工程の位置づけをはっきりさせましょう。

レビューの対象はコードや文書であって、書いた人ではありません。指摘は人への評価ではなく、変更をより良くするための材料です。そして、悪い所探しだけがレビューではありません。

```text
「この変数名だと会員数と会員一覧を取り違えそうです。
  memberList はどうでしょう?」          ← 提案
「この条件で0件のときはどうなりますか?」 ← 質問
「この書き方、読みやすいですね」          ← 良い点
```

提案・質問・良い点の共有は、どれも立派なレビューコメントです。命令ではなく提案や質問の形で書くのが基本で、これは見る側になったときの心得でもあります。

実務では、レビューを通じてチームの知識がそろっていく効果も大きいです。「この書き方のほうが安全」という知見が、コメントを通じて共有されていきます。

## 9-2-2 指摘には修正pushで応える

> **指摘には同じブランチへ修正コミットを push して応える(PRに自動で反映される)**

「ここを直してほしい」と指摘をもらったら、どう応えればよいでしょうか。PR を閉じて作り直す必要はありません。PR はブランチと結びついていて、常にそのブランチの最新状態を映しているからです。

やることは、今まで学んだ操作の組み合わせだけです。

```bash
# 指摘: 「見出しの表現が分かりにくい」→ 手元のファイルを修正して…
git add price-list.md
git commit -m "見出しの表現をレビュー指摘に沿って修正"
git push
# → 開いている PR に新しいコミットが自動で並ぶ
```

同じブランチに新しいコミットを push すれば、PR の差分とコミット一覧に自動で追加されます。すでに `push -u` 済みのブランチなので、2回目からは `git push` だけで届きます。

レビューする人は追加されたコミットだけを見て、「指摘した点が直ったか」を確認できます。だからこそ、修正コミットのメッセージには何を直したかを書いておくと親切です。

## 9-2-3 ApproveとRequest changes

> **Approve は「取り込んでよい」、Request changes は「直してから」の意思表示**

コメントのやりとりだけでは、「それで、取り込んでいいの?」という結論が曖昧なままになります。GitHub にはレビューの結論をはっきり伝えるしくみがあり、レビューを送信するときに次の3つから選びます。

```text
Approve          : 取り込んでよい(マージに進める)
Request changes  : ここを直してから(修正の push を待つ)
Comment          : 質問・感想だけ(結論はまだ出さない)
```

中心になるのは **Approve** と **Request changes** の2つです。

- **Approve** は「この内容で取り込んでよい」という承認の意思表示です
- **Request changes** は拒絶ではなく、「指摘した点を直してから取り込みたい」という合図です。もらったら修正を push して、再度レビューを依頼します

チームによっては「Approve が1つ以上ないとマージしない」という決まりを設けています。意思表示がボタンとして記録に残るので、誰が承認したかも後から追えます。

## 9-2-4 コメントには全部返事

> **もらったコメントには全部返事をする(直した/直さない理由)**

指摘どおりに直して push したら、それで終わりでしょうか。実は、無言のままだと相手の画面ではコメントが放置されたままに見えます。読まれたのかどうかすら伝わりません。

もらったコメントには、1つ残らず返事をします。内容は短くてかまいません。

```text
「修正しました」                          ← 直した場合
「ここは既存の表記に合わせているため、
  今回はこのままにします」                ← 直さない場合
「この指摘の意図を教えてください」        ← 分からない場合
```

ポイントは3つです。

- 直したら「直しました」と書く(どのコミットで直したかを添えるとさらに良い)
- 直さない選択もあってよい。ただし理由を必ず添える
- 分からなければ質問で返す。それも立派な返事

避けるべきは「無言で直す」と「無言で無視」の2つだけです。全コメントに返事がそろった状態が、レビューのやりとりの完了条件だと覚えてください。
