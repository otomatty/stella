# レッスン9-4 GitHub Flow

## このレッスンの目標

- [ ] GitHub Flow の1周の流れを自分の言葉で説明できる
- [ ] main へ直接 push しない理由を説明できる
- [ ] Issue と PR の役割分担と紐づけ方を説明できる

## 9-4-1 GitHub Flowとは

> **GitHub Flow は「main から枝を出し、PR で戻す」の繰り返し**

ブランチ・マージ・push・PR と、道具は一通りそろいました。しかし実務で必要なのは、道具の使い方だけではありません。「チームとしてどう回すか」という型です。毎回やり方を相談していたら、開発は進みません。

じつは、この研修で学んできた1周の流れそのものに名前が付いています。それが **GitHub Flow** です。

```text
main ──●──────────●──────────●──→
        \        /  \        /
         ●──●──●     ●──●──●
        (枝で作業、PRで戻す) (また枝を出す)
```

- 出発点はいつも main。最新の main からブランチを出す
- 作業してコミットを積み、push して PR を開く
- レビューを経てマージし、ブランチを片付けて、また main から次の枝を出す

新しい操作は1つもありません。ここまで手を動かしてきた1周に名前が付くだけです。この型はシンプルなので、多くのチームがこのまま、あるいは少し変形して使っています。「うちは GitHub Flow です」と言われたら、この1周のことだと分かれば会話に入れます。

## 9-4-2 mainは常に動く状態

> **main は常に動く状態に保つ(だから main へ直接 push しない)**

GitHub Flow で毎回わざわざブランチを切るのは、なぜでしょうか。ブランチを切らずに main で直接作業して push すれば、一見手っ取り早く見えます。

理由は、main が全員の作業の出発点だからです。GitHub Flow では、次の枝は必ず main から出ます。main が壊れていると、そこから枝を切った全員が壊れた状態を引き継ぎ、被害が一気に広がります。

```text
悪い例: 「1行だけだから」と main に直接 push
  → 誤りがあれば全員の出発点が壊れる。気づくのも遅れる

良い例: 1行でもブランチ + PR を経由
  → 取り込む前に人の目が入る。記録も残る
```

だからチームは、この約束を守ります。

- main に入れてよいのは、レビューを通った変更だけ
- 変更は、どんなに小さくてもブランチ + PR を経由させる

「1行の修正だから」という油断がいちばん危険です。例外を作らないことが、main を常に動く状態に保つコツです。Module 8 で学んだ「共有ブランチで強制 push しない」と並ぶ、チームの基本の約束と覚えてください。

## 9-4-3 Issueと紐づける

> **作業の理由は Issue に残し、PR から紐づける**

「なぜこの作業をするのか」は、PR を開く前から存在しています。不具合の報告、改善の要望、検討したい相談。こうした理由の置き場所がないと、口頭やチャットで流れて消えてしまい、後から「なぜ変えた?」に答えられなくなります。

GitHub には、そのための道具として **Issue** があります。Issue はリポジトリ上の課題管理の単位で、不具合・要望・相談を1件ずつ番号付きで記録します。

役割分担はこうです。

| 場所 | 残すもの |
| --- | --- |
| Issue | 作業の理由(何に困っているか・何をしたいか) |
| PR | 理由に対する変更(どのブランチをどう取り込むか) |

2つをつなぐのが、PR の説明欄での紐づけです。

```text
Issue #7: 会員一覧の並び順が探しにくい(営業チームより)

PR の説明欄: 「Closes #7」と書く
  → PR から Issue へリンクが張られる
  → PR がマージされると Issue #7 は自動で閉じる
```

`Closes #番号` と書くだけで、理由と変更が双方向にリンクされ、マージ時の Issue の後片付けまで自動になります。「#7 の件です」と番号で会話できるのも、チームでは大きな時短です。Issue に始まり、PR のマージで終わる。この1本の線を引けるようになれば、GitHub Flow の1周は完成です。
