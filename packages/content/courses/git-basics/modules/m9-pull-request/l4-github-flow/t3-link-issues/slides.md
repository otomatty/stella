# Issueと紐づける

Git入門研修 — Module 9 / レッスン9-4

## なぜ必要か

- 「なぜこの作業をするのか」は、PR を開く前から存在している
- 不具合の報告、改善の要望…理由の置き場所がないと口頭で流れて消える
- 後から「なぜ変えた?」に答えられなくなる

<!-- ノート: PRは作業を始めてからの記録です。作業の発端そのものを残す場所が別にある、というのがこの回です。 -->

---

## 結論

**作業の理由は Issue に残し、PR から紐づける**

- **Issue** は GitHub 上の課題管理の単位(不具合・要望・相談を1件ずつ)
- PR の説明で Issue 番号を挙げれば、理由と変更がつながる

<!-- ノート: Issueという言葉をここで導入します。理由はIssue、変更はPR、と置き場所を分けてリンクでつなぐのが型です。 -->

---

## 最小の例

```text
Issue #7: 会員一覧の並び順が探しにくい(営業チームより)

PR の説明欄: 「Closes #7」と書く
  → PR から Issue へリンクが張られる
  → PR がマージされると Issue #7 は自動で閉じる
```

<!-- ノート: Closes #番号、という書き方1つで、紐づけと後片付けまで自動になります。番号で会話できるのもチームでは便利です。 -->
