# レッスン6-1 ブランチとは

## このレッスンの目標

- [ ] ブランチが「動く付箋」であることを自分の言葉で説明できる
- [ ] main の役割(完成した状態の置き場)を説明できる
- [ ] 「作業は作業用ブランチで行う」理由を説明できる

## 6-1-1 ブランチは動く付箋

> **ブランチは、コミットの連なりに付けた「動く付箋」**

実務では「本番用はそのままにして、別の直しを試したい」が毎日のように起きます。フォルダごとコピーする方法は Module 0 で見たとおり破綻します。Git の答えが **ブランチ** です。

ブランチと聞くと「フォルダの複製」を想像しがちですが、違います。実体はこれまで積んできたコミットの列のままで、ブランチはその先頭に貼った**目印(付箋)**にすぎません。

```text
コミットA ← コミットB ← コミットC
                          ↑
                  ブランチ(動く付箋)
```

この付箋には大事な性質があります。**新しいコミットを積むと、付箋はひとりでに先頭へ動く**のです。上の図でコミットDを積めば、付箋はDを指すようになります。だから「動く付箋」です。

ブランチは常に「その作業の最新コミット」を指し続けてくれる目印だ、と覚えてください。

## 6-1-2 mainは完成の置き場

> **main は既定のブランチで、完成した状態を置く場所**

実は、ブランチはこの研修の最初から存在していました。`git init` した瞬間に、Git はブランチを1本だけ用意します。それが **main** です。

```text
コミットA ← コミットB ← コミットC
                          ↑
                        main
```

これまでの研修で積んだコミットは、すべてこの main に積まれていました。見慣れた履歴の正体は「main という付箋が先頭に付いたコミットの列」だったわけです。

技術的には、main は他のブランチと同じただの付箋です。しかし現場では役割の約束が載ります。

- main は**完成した状態を置く場所**にする
- チームの誰が見ても「main を開けば動くもの・完成したものがある」と信じられる状態を保つ

この約束があるから、main は「困ったときの戻り先」「共有の基準点」として機能します。

なお、環境によっては既定のブランチ名が `master` になっている場合があります。役割は同じで、名前が違うだけです。

## 6-1-3 作業はブランチで

> **作業は main に直接ではなく、作業用ブランチで行う**

main が完成の置き場なら、当然の疑問が出ます。作りかけの作業はどこでやるのか?

答えはシンプルで、**直しごとに作業用のブランチを作り、コミットはそこへ積む**です。できあがったら、後で main に取り込みます(取り込みの手順は後のモジュールで学びます)。

```text
×: main の上で直接作業
   → 作りかけのコミットが main に積まれ、完成の置き場が崩れる

○: 作業用ブランチの上で作業
   → main はいつ見ても完成の状態のまま
```

作業用ブランチの上なら、失敗しても、作業を途中で止めても、main は無傷です。1人での練習なら main に直接コミットしても動きますが、チームに入った瞬間にこの差が事故になります。「作業を始めるときは、まず作業用ブランチを作る」を今のうちに型にしておきましょう。

## 6-1-4 ブランチ作成は軽い

> **ブランチを作るのは一瞬(気軽に作って、終わったら消す)**

「直しのたびにブランチを作る」と聞くと、面倒で重い作業に思えるかもしれません。フォルダのコピーと同じ感覚でいると、作るのをためらってしまいます。

実際は逆です。ブランチは付箋にすぎないので、**作るのは一瞬**です。

- 増えるのは付箋1枚だけ。ファイルは複製されない
- 作業フォルダが2倍になったりはしない

```text
×: フォルダのコピーで別案を試す
   → 作業フォルダが複製されて重い。どれが本物か分からなくなる

○: ブランチで別案を試す
   → 増えるのは付箋1枚。ファイルは1組のまま
```

だから、ためらう理由がありません。試したいことがあれば作る。要らなくなったら消す。実験用・練習用に作っても構いません。この気軽さが、前トピックの「作業はブランチで」という運用を現実的にしています。
