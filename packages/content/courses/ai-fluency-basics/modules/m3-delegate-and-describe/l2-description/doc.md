# レッスン3-2 Description: どう伝えるか

## このレッスンの目標

- [ ] 依頼を成果物の形から書ける
- [ ] できの基準を先に渡せる
- [ ] 譲れない手順と制約だけを書き、判断に要る材料を添えられる

## 3-2-1 依頼は成果物から書く

> **依頼は、何が出てきたら完了かという成果物の形から書きます**

このレッスンから 4D の2つ目、**Description(伝える)** に入ります。前のレッスンで決めたことを、相手に渡す文にする段階です。

よくあるすれ違いから始めます。「この障害についていい感じにまとめて」と頼んだところ、箇条書きが返ってきました。欲しかったのは、そのまま提出できる1ページの文章でした。悪気はどちらにもありません。頼んだ側が、何が出てくれば完了かを決めていなかっただけです。

ここで 2 つの語を置きます。

- **依頼** — AI に渡す、頼みごとの文
- **成果物** — その依頼が終わったとき、手元に残るもの

依頼は、成果物の形から書きます。書き換えると次のようになります。

- 前: 「この障害についてまとめて」
- 後: 「障害報告を1ページで書いてください。発生時刻・影響・原因・対応の4つの見出しを持つ文章にしてください」

変えたのは「長さ」と「構成」の2つだけです。それでも返ってくるものは大きく安定します。

前のレッスンで書いたゴールと、成果物は別のものです。

| | ゴール | 成果物 |
| --- | --- | --- |
| 誰のための文か | 自分 | 相手 |
| 書く内容 | どうなっていたいか | 何が出てくれば完了か |
| 例 | 朝会で説明できる状態にする | 4見出しの1ページの報告 |

ゴールをそのまま貼り付けても、相手には届きません。**形に翻訳する一手間** が依頼を書くという作業です。

## 3-2-2 できの基準を先に渡す

> **良し悪しを判断する軸(できの基準)を先に渡すと、出力の当たりが安定します**

成果物の形が決まっても、まだ足りません。形は合っているのに中身が合わない、という場面があります。返ってきたものを見て「もっと短く」「もっと具体的に」と言い直し、3往復してようやく望みどおりになる、という進み方です。

この往復が起きるのは、良し悪しの軸が自分の頭の中にしかないからです。この軸を **できの基準** と呼びます。できの基準とは、出てきたものが良いか悪いかを決める軸のことです。

できの基準は、直しながら伝えるのではなく、依頼に先に書きます。次の3つはどんな依頼でもだいたい書けます。

- **読む相手** — 非エンジニアの営業担当
- **長さ** — 1000文字以内
- **言葉づかい** — 専門用語には初出で一言の説明を付ける

書き出すことには、往復を減らす以外の効き目もあります。

| | 後出しで直す | 先に渡す |
| --- | --- | --- |
| 往復の回数 | 増える | 減る |
| 基準の在りか | 自分の頭の中 | 依頼の文 |
| 他の人が引き継げるか | できない | できる |

頭の中にある基準は、自分にしか使えません。文にした基準は、チームの誰でも同じ依頼を出せるようになります。実務では、この差のほうが大きく効きます。

## 3-2-3 譲れない進め方だけ手順にする

> **進め方に譲れない縛りがあるときだけ、手順と制約として明示します**

次は、進め方をどこまで書くかです。ここは両側に失敗があります。やり方を1から10まで書いたら、依頼を書くほうが時間がかかりました。逆に何も書かなかったら、使ってはいけない部品を使った案が返ってきました。

線を引くための語を2つ置きます。

- **手順** — こういう順でやってほしい、という進め方の指定
- **制約** — 守ってほしい条件、やってはいけないこと

既定は「書かない」です。そのうえで、譲れないものがあるときだけ足します。

- 手順: 「先に既存のテストを読み、それから実装を書いてください」
- 制約: 「新しい外部の部品は追加しないでください」

どちらも、書く理由が現場にあります。テストを先に読ませるのは、既存の期待どおりに書いてほしいからです。部品を増やさないのは、増やすとチームの審査が要るからです。**理由が言えないものは書かなくてよい**、と考えてください。

| | 全部指定する | 何も指定しない | 譲れないものだけ |
| --- | --- | --- | --- |
| 書く手間 | 大きい | 小さい | 小さい |
| 事故 | 起きにくい | 起きる | 起きにくい |

狙うのは右の列です。手順と制約を書きすぎると、進め方の工夫が全部こちらの負担になり、任せた意味が薄くなります。

## 3-2-4 判断に要る材料を添える

> **AIは社内の事情を知らないため、判断に要る材料を依頼に添えます**

依頼の書き方を整えても、まだ埋まらない穴があります。社内の命名の決まりを知らない前提で書かれたコードが返ってくる、去年決めた社内の方針が当然のように無視される、といったことです。

これは書き方の問題ではありません。そもそも知らないことを聞いているからです。学習データに社内の事情は入っておらず、知識の切れ目より後のことも知りません。

そこで、**材料** を添えます。材料とは、判断に要る手元の情報のことです。既存のコード、規約の抜粋、エラーのログ、過去の議事録などが当てはまります。材料を依頼に添えると、その内容がコンテキストに載り、出力に反映されます。

何を添えるかは、依頼の型でだいたい決まります。

- **レビュー依頼** — 対象のコードと、チームのレビュー観点の抜粋
- **調査依頼** — エラーの本文と、直前に変えた箇所の差分
- **文章依頼** — 似た目的で過去に書いた文書の一部

毎回ゼロから考える必要はありません。よく出す依頼については、添える材料をあらかじめ決めておけます。

| | 材料なし | 材料あり |
| --- | --- | --- |
| 返ってくるもの | 一般論として正しい案 | この現場で通る案 |
| 手直し | 大きい | 小さい |

一般論として正しいことと、この現場で使えることは別です。材料を添えた分だけ、後者に寄っていきます。

## もっと知りたい人へ

- ここで扱った成果物・できの基準・手順・制約・材料は、人に仕事を頼むときの要素とほぼ同じです。後輩に依頼を出すときの文を思い出すと、書く順番が掴みやすくなります
- よく出す依頼は、自分用の雛形として1つ持っておくと便利です。毎回書き直すのは成果物と材料だけになります
