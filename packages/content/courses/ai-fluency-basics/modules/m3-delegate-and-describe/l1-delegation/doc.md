# レッスン3-1 Delegation: 何を任せるか決める

## このレッスンの目標

- [ ] 達成したいゴールを一文で書ける
- [ ] 仕事を工程に割り、工程ごとに誰がやるかを決められる
- [ ] 自分で持つべき工程と、道具の守備範囲を踏まえて配れる

## 3-1-1 任せる前にゴールを言葉にする

> **AIに渡す前に、自分が達成したいゴールを一文で言葉にします**

AI に何かを渡してみて、返ってきたものに「そうじゃない」と感じた経験は多いはずです。このとき、うまくいかない原因は渡し方だと思いがちです。ところが「では何が欲しかったのですか」と聞かれると、自分でも言葉にできないことがあります。

そこで最初にやることが、**ゴール** を一文にすることです。ゴールとは、その仕事が終わったとき、何がどうなっていてほしいかを表した一文です。

- ぼんやり: 「この障害調査、何とかしたい」
- ゴール: 「明日の朝会で、障害の原因の候補を3つ説明できる状態にする」

違いは、**誰に・いつ・何ができれば終わりか** が入っているかどうかです。この3つが入ると、一文が締まります。一文で書けないうちは、渡し方を工夫しても結果は安定しません。まだ自分の中で何を欲しいかが決まっていないからです。

ゴールの一文は、AI に見せるための文ではありません。自分の頭を決めるための文です。書いたあと、そのまま渡すかどうかは別の話になります。

### Delegation(任せる)と委任は別の語

このレッスンから 4D の1つ目、**Delegation(任せる)** に入ります。ここで、日本語がよく似ている 2 つの語を分けておきます。

| | Delegation / 任せる | 委任 |
| --- | --- | --- |
| どの枠の語か | 4D の1つ | 3モードの1つ |
| 何を指すか | 何を誰がやるか決める局面 | 進め方ごと AI に預ける関わり方 |

つまり Delegation は「配る前に決める話」、委任は「配ると決めたあとの、関わり方の強さ」です。このレッスンで扱うのは左側です。

## 3-1-2 仕事は工程に割ってから配る

> **仕事を工程に分けると、どこを任せるかを工程ごとに決められます**

ゴールが一文になったら、次は仕事の中身です。よくある失敗は、「この機能を作っておいて」と仕事をまるごと渡してしまうことです。かたまりが大きいほど返ってくるものは使いにくく、しかもどこがずれたのかも分かりません。結果として、全部自分でやるか全部渡すかの二択になります。

そこで、仕事を **工程** に割ります。工程とは、ゴールに至るまでの作業の区切りです。判断の単位を仕事まるごとではなく工程1つずつに変えると、配り方が細かく決められます。

障害調査を例にすると、次のようになります。

| 工程 | 誰がやるか |
| --- | --- |
| ログを集める | 自分 |
| 症状を整理する | 一緒にやる |
| 原因の候補を出す | 一緒にやる |
| 本番で再現を試す | 自分 |
| 報告書の下書きを作る | 任せる |

同じ「障害調査」でも、工程によって配り方が変わっています。ここを一括で決めようとすると、必ずどこかに無理が出ます。

割らずに渡すと、たとえば「障害を調べて報告書まで作って」という頼み方になります。返ってくるのは、事実と推測が混ざった文章です。どの工程でずれたのかが分からないため、最初からやり直しになります。工程に割ることは、**やり直しの範囲を小さくする作業** でもあります。

## 3-1-3 判断の土台は自分で持つ

> **判断の土台になる工程を任せ続けると、自分の理解が空洞化します**

工程ごとに配れるようになると、次は配りすぎが問題になります。

AI が出した設計をそのまま採用する日々が続いたとします。作業は回っています。ところがレビューで「なぜこの形にしたのですか」と聞かれたとき、答えられません。これが **空洞化** です。空洞化とは、仕事は回っているのに、判断の根拠を自分で持てなくなった状態を指します。

空洞化のやっかいなところは、失敗として現れないことです。できあがった量はむしろ増えます。表に出るのは、質問されたときや、想定外のことが起きたときです。

対策は、土台になる工程を残すことです。関わり方の強さを工程ごとに変えます。

| 工程 | 関わり方 |
| --- | --- |
| 要件のどれを優先するか決める | 自分で持つ |
| 設計の候補を挙げる | 拡張で一緒に出す |
| 定型の変換作業 | 委任してよい |

すべてを自分で抱える必要はありません。**判断の根拠になる工程だけ** を、委任ではなく拡張までにとどめる、という決め方です。

次の2つが出てきたら、その工程は一度自分でやり直す価値があります。

- 出てきたものに「たぶん合っている」以上の感想が持てない
- 直すよう言われても、どこをどう直せばよいか自分で決められない

## 3-1-4 任せる範囲は道具の守備範囲で決まる

> **道具ごとにできること(守備範囲)が違うため、任せる範囲は使う道具に合わせて決めます**

配る工程が決まっても、渡す先によって現実にできることは変わります。チャット画面に「うちのリポジトリのこの処理を直して」と頼んでも、その道具はリポジトリを見ていません。返ってくるのは、それらしい別物です。

この、その道具が実際に読めるもの・実行できることの範囲を **守備範囲** と呼びます。工程を配る前に、渡す先の守備範囲を確かめます。

守備範囲は、次の3つの問いで確かめられます。

- **何が読めるか** — こちらが見せたものだけか、手元のファイルまで届くか
- **どこまで読めるか** — コンテキスト上限を超えた分は出力に反映されない
- **いつまで知っているか** — 学習データより後のことは知らない

この3問は、どの道具にも同じ形で聞けます。上限の実際の値は道具ごとに違い、しかも変わっていくので、使う製品の資料で確かめてください。この講座で覚えるのは、**確かめる問いのほう** です。

噛み合わない配り方は、たとえば次のような形で現れます。

- 社内の最新の規約に従わせたいのに、何も見せずに任せる
- 長い設計書をまるごと渡し、後半だけ無視された出力を受け取る

どちらも守備範囲の外を任せた例です。工程をもっと小さく割り直すと、守備範囲に収まることがよくあります。

## もっと知りたい人へ

- 仕事を工程に割る考え方は、AI を使わない場面でも役に立ちます。チーム内で作業を分担するときや、見積もりを出すときに、同じやり方で区切ってみてください
- 道具の守備範囲は変わっていきます。半年前に「できない」と判断したことは、使う前にもう一度確かめる価値があります
