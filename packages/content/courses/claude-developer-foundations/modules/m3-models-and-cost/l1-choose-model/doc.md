# レッスン3-1 モデルを選ぶ

## このレッスンの目標

- [ ] 用途に合わせて、最初に試すモデルを選べます。
- [ ] 候補のモデルや effort の値を、評価のセットで比べる手順を説明できます。
- [ ] モデルを組み合わせる前に確かめることを説明できます。

## 3-1-1 選ぶ基準を先に決める

> **モデルは、性能・速度・費用のどれを優先するかを決めてから選びます。**

モデルを選ぶときは、先に何を優先するかを決めます。公式ドキュメントが挙げる観点は次の 4 つです。

| 観点 | 確かめること |
| --- | --- |
| 性能 | 用途に要る機能や、解ける課題の難しさ |
| 速度 | 応答までに待てる時間 |
| 費用 | 開発と本番の予算 |
| effort | 1 つのモデルの中で、性能と速度・費用をどう釣り合わせるか(3-1-3) |

最初に試すモデルの決め方は、大きく 2 つあります。

- **速度・費用から始める**: Claude Haiku 5.5 のような速くて安いモデルで作り、課題を十分に試します。足りないところがあるときだけ、上のモデルに上げます。試作、待たせられない画面、量が多く単純な処理に向きます。
- **性能から始める**: Claude Opus 5.5 のような強いモデルで作り、プロンプトを整えます。そのうえで、effort を下げるか小さいモデルに替えて効率を上げます。難しい推論、正確さが費用より大事な処理、自律して長く動くエージェントに向きます。

モデルごとの料金・コンテキストウィンドウ・出力の上限は、公式ドキュメントのモデルの比較表で確かめます。モデルは入れ替わるので、名前を覚えるより、決め方を覚えます。

## 3-1-2 自分の課題で比べる

> **候補のモデルは、自分の課題で作った評価のセットで比べます。**

評価のセットは、実際に使うプロンプトとデータに、期待する答えを添えた例の集まりです。公式ドキュメントは、モデルを上げるか替えるかを決める手順として、次の順を挙げています。

1. 自分の用途に合わせた評価のセットを作る(最も大切な手順)
2. 実際のプロンプトとデータで試す
3. 答えの正しさ・答えの質・例外的な入力の扱いを、モデルごとに比べる
4. 性能と費用の釣り合いを考える

一般の評判や、ほかの用途での結果は、自分の課題に当てはまるとは限りません。モデルを替えるたびに同じ評価のセットで比べると、良くなったか悪くなったかを数字で言えます。評価の作り方は、評価とデバッグの単元で扱います。

## 3-1-3 かける量を決める

> **effort で、1 つのモデルが応答にかけるトークンの量を調整します。**

effort は、応答にどれだけのトークンを使って取り組むかを指示する値です。リクエストの `output_config.effort` に書きます。

```js
const message = await client.messages.create({
  model,
  max_tokens: 4096,
  messages,
  output_config: { effort: "low" },
});
```

| 値 | 動き |
| --- | --- |
| `max` | 使うトークンに制限を設けず、最も深く取り組む |
| `xhigh` | 長く続く作業向けに、high より深く取り組む |
| `high` | 良い結果に要るだけトークンを使う。多くのモデルの既定 |
| `medium` | ほどほどにトークンを節約する。Claude Opus 5.5 と Claude Haiku 5.5 の既定 |
| `low` | 最も効率がよく、性能が少し下がる。単純な処理やサブエージェント向き |

使える値はモデルによって違います。既定の値を書くのは、effort を省くのと同じ動きです。

effort は本文だけでなく、ツールの呼び出しや考える過程を含む、すべての出力のトークンに効きます。下げるとツールの呼び出しも少なく短くなります。effort は動きの目安で、厳密な上限ではありません。低い値でも、十分に難しい問題では考えます。

公式ドキュメントは、モデルを替えるより effort を調整するほうがよい手段になることが多いとしています。費用は高いが質は足りているなら、まず今のモデルで effort を下げて、評価のセットで質が保てるかを確かめます。

## 3-1-4 モデルを組み合わせる

> **モデルの組み合わせは、1 つのモデルの effort を調整しても足りないときに考えます。**

モデルの組み合わせは、安いモデルと強いモデルを 1 つの処理の中で使い、トークンの多くを安い料金で処理する方法です。公式ドキュメントは、2 つの形を挙げています。

| 形 | 進め方 | 向く処理 |
| --- | --- | --- |
| アドバイザー(advisor) | 安いモデルが処理を進め、難しい判断のときだけ強いモデルに聞く | ほとんどは易しく、ところどころ難しい判断がある一続きの作業 |
| オーケストレーター(orchestrator) | 強いモデルが計画して作業を配り、安いモデルが大量の作業をする | 互いに独立したファイルや文書を、手分けして処理する作業 |

組み合わせは仕組みが複雑になり、いつも得をするとは限りません。公式ドキュメントの順番は次のとおりです。

1. 今のモデルで effort を変えて比べる(たいていの処理はここで決まる)
2. それでも足りなければ、強いモデルを低い effort で使った費用を見積もる
3. 組み合わせは、1 つのモデルのどの effort よりも良いときだけ作る

組み合わせを試すときは、同じモデルを低い effort にしたものと、1 つ下のモデルだけで動かしたものの両方と比べます。
