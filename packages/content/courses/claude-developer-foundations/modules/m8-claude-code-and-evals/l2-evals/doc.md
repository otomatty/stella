# レッスン8-2 評価とデバッグ

## このレッスンの目標

- [ ] 具体的で測れる成功の基準を書けます。
- [ ] 評価のセットと採点の方法を選び、変更の前後を比べられます。
- [ ] ツールの誤用を、症状から直せます。

## 8-2-1 成功の基準を先に決める

> **作る前に、具体的で測れる成功の基準を決めます。**

成功の基準は、何ができたらアプリが成功といえるかを決めたものです。作る前に決めておくと、変更のたびに良くなったか悪くなったかを数字で言えます。よい基準は、次の 4 つを満たします。

| 条件 | 中身 | 例 |
| --- | --- | --- |
| 具体的 | 達したいことをはっきり書く | 「よい性能」ではなく「感情の分類が正しい」 |
| 測れる | 数や、決まった尺度で表す | 正解率、応答までの時間、1〜5 の尺度 |
| 届く | 実験やいまのモデルの力に照らして、実現できる目標にする | 前の版の結果をもとに決める |
| 用途に合う | アプリの目的と利用者に合わせる | 医療のアプリなら引用の正確さを重く見る |

安全性のような捉えにくいものも数で表せます。「安全な出力」ではなく「1 万回の出力のうち、内容のフィルターで問題ありと判定されるのが 0.1% 未満」のように書きます。

## 8-2-2 同じ評価で比べる

> **プロンプトを変えたら、同じ評価のセットを自動で採点して前と比べます。**

評価のセットは、実際の入力と期待する答えの例の集まりです。作るときは、次の 3 つを守ります。

1. **用途に合わせる**: 本番の入力の分布に似せ、例外的な入力(関係のない入力・長すぎる入力・人でも判断が割れる入力など)も入れる
2. **できるだけ自動で採点する**: 選択式・文字列の一致・コードでの採点・LLM による採点にできる形にする
3. **質より量**: 人が丁寧に採点する少数より、少し粗くても自動で採点できる多くの例のほうがよい

採点の方法は、できるだけ速く・確かで・数を増やせるものを選びます。

| 方法 | 長所 | 短所 |
| --- | --- | --- |
| コードで採点(完全一致・含むかどうか) | 最も速く確かで、数を増やせる | 決まりに当てはめにくい細かな判断ができない |
| LLM による採点 | 速く柔軟で、細かな判断ができる | 先に、採点が確かかを試す必要がある |
| 人が採点 | 最も柔軟で質が高い | 遅く高い。できるだけ避ける |

LLM に採点させるときは、はっきりした基準を書き(「最初の文に会社名がなければ不正解」)、「正解」「不正解」や 1〜5 のような決まった形で答えさせ、考える過程を使わせます。

プロンプトやモデルを変えたら、同じ評価のセットで前と比べます。試す例が前と後で違うと、比べられません。合格率の上下だけでなく、前は通って後で落ちた例(悪化)も確かめます。合格率が上がっていても、大事な例が落ちていることがあります。

## 8-2-3 ツールの誤用を直す

> **ツールの誤用は、ツールの説明・スキーマ・strict から直します。**

ツールの使われ方がおかしいときは、多くの場合、ツールの定義の側に原因があります。公式ドキュメントの「Troubleshooting tool use」は、症状ごとに次の直し方を挙げています。

| 症状 | ありそうな原因 | 直し方 |
| --- | --- | --- |
| 別のツールが呼ばれる | 説明があいまい | 何をするかだけでなく、いつ使うかで説明を書き分ける |
| 一度も呼ばれない | 名前の重なり、スキーマが一般的すぎる | 名前の重なりを確かめ、`input_examples` で使い方を具体的に見せる |
| 入力の型が違う | スキーマがあいまい | `strict: true` を付けるか、`input_examples` を足す |
| スキーマにない項目を作る | strict を付けていない | `strict: true` を付ける |
| enum の外の値が来る | strict を付けていない、選択肢が多すぎる | 選択肢を減らすか、`input_examples` で正しい値を見せる |

直したら、同じ評価のセットで、誤用が減ったことを確かめます。
