# レッスン10-1 API の機能を見分ける

## このレッスンの目標

- [ ] 場面の条件から、ストリーミングとバッチのどちらを使うかを選べます。
- [ ] キャッシュとバッチを重ねるときの、効き方と注意を説明できます。
- [ ] 構造化出力と strict が、それぞれ何の形を決めるかを言えます。
- [ ] stop_reason と HTTP のエラーを、分けて扱えます。

このレッスンでは、M1〜M5 で別々に学んだ機能のうち、選択肢に並びやすい組を、場面の条件で選び分けます。どの機能も、詳しくは元の単元で扱っています。

## 10-1-1 待つ人がいるかで選ぶ

> **人が応答を待つならストリーミング、急がない大量の処理ならバッチで送ります。**

ストリーミングもバッチも、時間のかかる処理のための機能に見えます。違いは、結果を待っている人がいるかどうかです。

| | ストリーミング(2-2-1) | Message Batches API(2-3-1) |
| --- | --- | --- |
| 結果の届き方 | 本文が差分のイベントとして、届いた順に | すべて終わるか 24 時間たつと、まとめて |
| 料金 | 通常 | 通常の半額 |
| 向く場面 | チャット画面、長い回答の表示 | 大量の評価・分類・要約など、すぐには結果の要らない処理 |

バッチの多くは 1 時間以内に終わりますが、送ってすぐには返りません。画面の前で人が待っている処理をバッチにすると、待たせることになります。反対に、翌朝までに結果があればよい大量の処理をストリーミングで 1 件ずつ送ると、半額の割引を使えません。

バッチの中のリクエストには、ほとんどの機能(ツール使用・画像・system・複数ターンの会話など)を入れられますが、`stream: true` は書けません。バッチの結果は、流れてくるのではなく 1 つのファイルとして返るためです。書くと検証のエラーになります。

## 10-1-2 割引を重ねる

> **キャッシュとバッチの割引は重ねられますが、バッチの中のキャッシュは当たるとは限りません。**

プロンプトキャッシュ(3-2-1)とバッチは、安くする理由が違います。キャッシュは同じ前半を使い回すことで、バッチは急がない処理をまとめて送ることで安くします。そのため、2 つの割引は重ねて効きます。同じ手引きを付けた大量の分類を夜間に流すような処理は、両方を使える場面です。

ただし、バッチの中のリクエストは非同期に、同時に処理されるので、キャッシュは当たるとは限りません。公式のドキュメントでは、当たる割合は送り方によって 30% から 98% ほどとされています。当たりやすくするには、次のようにします。

- すべてのリクエストに、同じ `cache_control` のブロックを入れる
- できるだけ多くの部分を、リクエストの間で同じにする
- バッチの処理は 5 分を超えることがあるので、1 時間のキャッシュを考える

費用を見積もるときは、キャッシュが当たらなかった場合の費用も出しておきます。

## 10-1-3 スキーマをかける場所

> **応答の形は構造化出力で、ツールの入力の形は strict で決め、両方を同じリクエストで使えます。**

構造化出力(4-2-1)と strict(5-2-3)は、どちらも JSON スキーマで形を決める機能ですが、決める相手が違います。

| 機能 | 決めるもの | 書く場所 |
| --- | --- | --- |
| 構造化出力 | Claude が答える本文(text ブロック)の形 | リクエストの `output_config.format` |
| strict | Claude がツールを呼ぶときの入力(`tool_use` の `input`)の形 | ツールの定義の `strict: true`(形は `input_schema` に書く) |

ツールの入力が崩れるのを直したいのに `output_config.format` を足しても、ツールの入力には効きません。反対に、ツールに `strict: true` を付けても、最後の答えの本文の形は決まりません。

2 つは、同じリクエストで一緒に使えます。ツールを呼びながら、最後に決まった形の答えを返させるときに使います。

```js
const request = {
  model,
  max_tokens: 1024,
  messages,
  tools: [{ name: "lookup_order", description, strict: true, input_schema: orderInput }],
  output_config: { format: { type: "json_schema", schema: replySchema } },
};
```

構造化出力は、引用(citations)と一緒には使えず、一緒に指定すると 400 のエラーになります。

## 10-1-4 エラーではない止まり方

> **stop_reason は成功した応答が止まった理由で、HTTP のエラーとは分けて扱います。**

stop_reason(1-3-1)は、成功した応答の本文に入る値で、生成がなぜ止まったかを表します。HTTP のエラー(2-1-1)は、リクエストの処理そのものが失敗したことを表し、4xx か 5xx のステータスと、エラーの内容が返ります。

| | stop_reason | HTTP のエラー |
| --- | --- | --- |
| 届くもの | 成功した応答(Claude の本文が入る) | 4xx・5xx のステータスと、エラーの内容 |
| 例 | `end_turn`・`max_tokens`・`tool_use`・`refusal` | 400・429・529 |
| 扱い | 値ごとに処理を分ける | 一時的なもの(429・529 など)だけを送り直す |

取り違えると、次のような誤りになります。

- 拒否(`refusal`)を例外の処理で拾おうとする。拒否は HTTP 200 の応答で届くので、例外にはなりません。
- `max_tokens` で切れた応答を、429 と同じように同じ設定のまま送り直す。同じ上限では、また切れます。`max_tokens` を上げるか、続きを書かせます。
- 529 のエラーを、`stop_reason` の分岐の中で待つ。エラーのときは応答がないので、`stop_reason` は読めません。
