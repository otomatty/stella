# テスト設計と品質保証 入門研修 カリキュラム(takeaway 一覧)

設計書: [2026-08-20-test-design-basics-design.md](../../../../docs/superpowers/specs/2026-08-20-test-design-basics-design.md)

テストは「品質の情報を届ける活動」であり、テストケースは仕様から技法で導ける。
設計したケースは pytest にそのまま写せて、リグレッション資産になる — この一本道を 6 モジュールで積む。

- Web(LMS): スライド視聴・まとめ・確認クイズ(合格点 80)
- コード演習(自動採点): なし(Python はランナー対象外)
- ハンズオン: practice.md の 2 段構え(①ケース表を書く → ②手元の Python + pytest で実装する)
- 対象外: レビュープロセスの詳細、テストマネジメント論(見積り技法・構成管理)、ツール分類学、
  JSTQB 模擬試験、pytest の網羅的な機能解説、UI/E2E 自動化ツールの操作

## 進行の設計(なぜこの順か)

1. **M1 で「テストは情報を届ける活動」という軸**を立てる(最後の 5-4-3 で同じ軸に帰ってくる)
2. **M2 で「どこで・何を」の地図**(レベル・タイプ・ピラミッド)を持たせてから、
3. **M3 で「どう作るか」**に入る。技法は 同値分割 → 境界値 → デシジョンテーブル → 状態遷移 の順
   (入力 1 個 → 範囲 → 条件の組み合わせ → 時間軸、と対象が段階的に複雑になる)
4. 各技法レッスンの最後に **pytest へ写すトピック**を置き、「設計 → 実装」の往復を 4 回反復する
5. **M4 で系統的技法の限界**(カバレッジの限界・経験ベース)を知り、網を補完する
6. **M5 で個々のケースから戦略へ**視点を上げる(何を自動化するか・リスクで厚みを変える・報告)
7. **M6 の capstone** で M1〜M5 の全語彙を使って通しの成果物を作る

## 全体構成(6 モジュール / 21 レッスン / 82 トピック)

### M1. テストの基礎 — レッスン 1-1 テストは何のためにあるか

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-1-1 | テストという活動 | テストはソフトウェアの品質に関する情報を関係者に届ける活動である |
| 1-1-2 | テストとデバッグ | テストは欠陥を見つける活動で、デバッグは原因を探して直す別の活動である |
| 1-1-3 | 品質保証とテスト | 品質保証(QA)はプロセス全体を良くする活動で、テストはその一部である |
| 1-1-4 | テストは実行だけではない | テストは実行だけでなく、計画・分析・設計・実装・完了報告まで含む一連の活動である |

### M1 — レッスン 1-2 エラー・欠陥・故障

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-2-1 | エラー | 欠陥は人間の思い違い(エラー)から生まれる |
| 1-2-2 | 欠陥と故障 | コードに潜む欠陥は、実行されて初めて故障として表に出る |
| 1-2-3 | 根本原因 | 故障から根本原因までさかのぼると、同じ種類の欠陥を繰り返さずに済む |

### M1 — レッスン 1-3 テストの 7 原則 I

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-3-1 | 欠陥がないことは示せない | テストは欠陥の存在は示せるが、欠陥がないことは証明できない |
| 1-3-2 | 全数テストは不可能 | 入力の組み合わせは爆発するので、すべてを試すことはできない |
| 1-3-3 | 早期テストの原則 | テストは早く始めるほど、欠陥を安く直せる |
| 1-3-4 | 欠陥の偏在 | 欠陥は少数のモジュールに集中する |

### M1 — レッスン 1-4 テストの 7 原則 II

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-4-1 | 殺虫剤のパラドックス | 同じテストを繰り返すだけでは、新しい欠陥は見つからなくなる |
| 1-4-2 | テストはコンテキスト次第 | 正しいテストのやり方は、対象と状況によって変わる |
| 1-4-3 | 欠陥ゼロの落とし穴 | 欠陥を全部直しても、利用者の役に立たなければ失敗である |

### M2. 何をどこでテストするか — レッスン 2-1 テストレベル

| ID | トピック | takeaway |
| --- | --- | --- |
| 2-1-1 | テストレベル | テストは対象の大きさごとに 4 つのレベルに分けて行う |
| 2-1-2 | コンポーネントテスト | 関数やクラスの単位で、小さく速いテストを数多く回す |
| 2-1-3 | 統合テスト | 部品どうしのつなぎ目に潜む欠陥は統合テストで狙う |
| 2-1-4 | システムテスト | システムテストは利用者の視点で全体の振る舞いを確かめる |
| 2-1-5 | 受け入れテスト | 受け入れテストでは発注者や利用者が「使えるか」を判断する |

### M2 — レッスン 2-2 テストタイプ

| ID | トピック | takeaway |
| --- | --- | --- |
| 2-2-1 | 機能テスト | 機能テストは「仕様どおりに動くか」を確かめる |
| 2-2-2 | 非機能テスト | 非機能テストは性能や使いやすさなど「どう振る舞うか」を確かめる |
| 2-2-3 | ブラックボックステスト | ブラックボックステストは中身を見ず、入力と出力だけで確かめる |
| 2-2-4 | ホワイトボックステスト | ホワイトボックステストはコードの構造を見てテストを作る |

### M2 — レッスン 2-3 変更に伴うテスト

| ID | トピック | takeaway |
| --- | --- | --- |
| 2-3-1 | 確認テスト | 確認テストは「直した欠陥が本当に直ったか」を確かめる |
| 2-3-2 | リグレッションテスト | リグレッションテストは「変更が別の場所を壊していないか」を確かめる |
| 2-3-3 | リグレッションと自動化 | 繰り返し実行するテストほど、自動化の価値が高い |

### M2 — レッスン 2-4 テスト戦略の土台

| ID | トピック | takeaway |
| --- | --- | --- |
| 2-4-1 | シフトレフト | テスト活動を開発の早い段階へ寄せるほど、手戻りが減る |
| 2-4-2 | テストピラミッド | 下の層(コンポーネント)ほど多く、上の層ほど少なく持つのが安定した形である |
| 2-4-3 | アイスクリームコーン | 手動テストと E2E 偏重の逆ピラミッドは、遅くて壊れやすい |
| 2-4-4 | テストの四象限 | テストの役割は「ビジネス/技術 × 支援/批評」の 4 象限で整理できる |

### M3. テスト設計技法 I: ブラックボックス — レッスン 3-1 同値分割

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-1-1 | テストケースの形 | テストケースは入力・手順・期待結果の 3 点セットで書く |
| 3-1-2 | 同値パーティション | 同じ扱いを受ける入力はひとつのグループ(同値パーティション)にまとめられる |
| 3-1-3 | 代表値 | 各パーティションから代表値を 1 つ選べば、ケースを大きく減らせる |
| 3-1-4 | 無効同値パーティション | エラーになる入力のグループも、漏らさずパーティションとして数える |
| 3-1-5 | pytest の最小形 | pytest は test_ で始まる関数の assert が成り立つかでテストの合否を決める |

### M3 — レッスン 3-2 境界値分析

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-2-1 | 欠陥は境界に集まる | 「以上」「未満」の境目は、実装者が最も間違えやすい場所である |
| 3-2-2 | 2 値の境界値 | 境界の内側と外側を 1 つずつテストするのが境界値分析の基本形である |
| 3-2-3 | 3 値の境界値 | 境界そのものと両隣を試すと、境界の取り違えをより確実に捕まえられる |
| 3-2-4 | ケース表を parametrize へ | ケース表の 1 行は pytest.mark.parametrize の 1 組にそのまま写せる |

### M3 — レッスン 3-3 デシジョンテーブル

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-3-1 | 条件の組み合わせ | 条件が複数絡む仕様は、頭の中ではなく表で整理しないと漏れる |
| 3-3-2 | デシジョンテーブルの書き方 | デシジョンテーブルは条件×ルールの表で、組み合わせを列挙する |
| 3-3-3 | ルールの簡約 | 結果に影響しない条件を「−」でまとめると、ルールを減らせる |
| 3-3-4 | 表からテストコードへ | デシジョンテーブルのルール 1 列が、テスト 1 ケースになる |

### M3 — レッスン 3-4 状態遷移

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-4-1 | 状態という見方 | 同じ操作でも状態によって結果が変わる仕様は、状態遷移でとらえる |
| 3-4-2 | 状態遷移図 | 状態遷移図は状態とイベントを図にして、仕様の抜けを見つける道具である |
| 3-4-3 | 状態遷移表 | 状態遷移表にすると、図では見えない「無効な遷移」が浮かび上がる |
| 3-4-4 | 遷移カバレッジ | すべての状態を踏むか、すべての遷移を踏むかで、テストの強さを選べる |
| 3-4-5 | 遷移のテストコード | 状態遷移テストでは、遷移の 1 本が「操作の列+期待する状態」の 1 ケースになる |

### M3 — レッスン 3-5 技法の使い分け

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-5-1 | 仕様の形で技法を選ぶ | 範囲なら境界値、条件の絡みならデシジョンテーブル、状態があれば状態遷移を選ぶ |
| 3-5-2 | 技法は重ねて使う | 1 つの機能に複数の技法を重ねて、それぞれ違う種類の欠陥を狙う |
| 3-5-3 | 表が仕様の穴を暴く | ケース表を書けない場所は、仕様が決まっていない場所である |

### M4. テスト設計技法 II: コードと経験から — レッスン 4-1 カバレッジ

| ID | トピック | takeaway |
| --- | --- | --- |
| 4-1-1 | カバレッジ | カバレッジはテストがコードをどれだけ踏んだかを測る物差しである |
| 4-1-2 | ステートメントカバレッジ | ステートメントカバレッジは全部の行を少なくとも 1 回実行したかを測る |
| 4-1-3 | ブランチカバレッジ | 行を全部踏んでも、分岐の真偽両方を通したとは限らない |
| 4-1-4 | カバレッジの限界 | カバレッジ 100% でも、書かれていないコードの欠陥(仕様漏れ)は見つからない |

### M4 — レッスン 4-2 経験ベースの技法

| ID | トピック | takeaway |
| --- | --- | --- |
| 4-2-1 | エラー推測 | 「ここが壊れやすい」という経験を、明示的にテストケースへ変えるのがエラー推測である |
| 4-2-2 | チェックリストベースドテスト | 壊れやすい入力の定番(空・0・負数・重複・長すぎ)はチェックリストで漏れを防ぐ |
| 4-2-3 | 探索的テスト | 探索的テストは、テストしながら学び、次のテストを設計する進め方である |
| 4-2-4 | 経験ベースの位置づけ | 経験ベースの技法は、系統的な技法の網から漏れた欠陥を拾う補完役である |

### M4 — レッスン 4-3 受け入れ基準と ATDD

| ID | トピック | takeaway |
| --- | --- | --- |
| 4-3-1 | 受け入れ基準 | ユーザーストーリーに受け入れ基準を書くと、完成の条件がテスト可能になる |
| 4-3-2 | Given-When-Then | 受け入れ基準は前提(Given)・操作(When)・期待(Then)の 3 部で書ける |
| 4-3-3 | ATDD | ATDD は受け入れテストを先に書き、それを満たすように実装する進め方である |
| 4-3-4 | 曖昧な仕様への向き合い方 | テストケースにできない仕様は、書き直しを提案するのがテスト担当者の仕事である |

### M5. 自動テスト戦略と品質の報告 — レッスン 5-1 何を自動化するか

| ID | トピック | takeaway |
| --- | --- | --- |
| 5-1-1 | 自動化の利点 | 自動テストは繰り返しに強く、人の時間を新しいテストに振り向けられる |
| 5-1-2 | 自動化のコスト | 自動テストには作るコストと維持するコストがあり、全部の自動化は割に合わない |
| 5-1-3 | 自動化する対象の選び方 | 繰り返しが多く、合否判定が機械的なテストから自動化する |
| 5-1-4 | 人に残すテスト | 自動化は既知の確認、人の探索的テストは未知の発見と役割を分ける |

### M5 — レッスン 5-2 リスクベースの優先順位

| ID | トピック | takeaway |
| --- | --- | --- |
| 5-2-1 | プロダクトリスク | プロダクトリスクは「壊れたときの影響 × 起きやすさ」で見積もる |
| 5-2-2 | リスクで厚みを変える | リスクの高い機能に技法を厚く、低い機能には薄くかける |
| 5-2-3 | 優先順位付け | 全部はやれない前提で、重要なテストから先に実行する順番を決める |
| 5-2-4 | 開始基準と終了基準 | 「いつ始めてよいか」「いつやめてよいか」は、テストを始める前に決めておく |

### M5 — レッスン 5-3 欠陥レポート

| ID | トピック | takeaway |
| --- | --- | --- |
| 5-3-1 | 欠陥レポートの目的 | 欠陥レポートは、直す人が再現できるだけの情報を届ける文書である |
| 5-3-2 | 再現手順 | 再現手順には環境と操作を、読んだ人がそのままなぞれる粒度で書く |
| 5-3-3 | 期待と実際 | 「動きません」ではなく、期待した結果と実際の結果の差分を書く |
| 5-3-4 | 深刻度と優先度 | 深刻度は影響の大きさ、優先度は直す順番で、別のものさしである |

### M5 — レッスン 5-4 品質を報告する

| ID | トピック | takeaway |
| --- | --- | --- |
| 5-4-1 | テストメトリクス | ケースの消化数・欠陥数・カバレッジで、テストの進み具合を数値にできる |
| 5-4-2 | テストレポート | テストレポートは読み手によって載せる情報を変える |
| 5-4-3 | 意思決定の材料 | テストの報告は「リリースしてよいか」という判断に答えるためにある |

### M6. 総合演習 — レッスン 6-1 仮想案件で通しでやる

| ID | トピック | takeaway |
| --- | --- | --- |
| 6-1-1 | テスト観点出し | 仕様を読んだら、ケースを書く前に「何をテストすべきか」の観点一覧を作る |
| 6-1-2 | 技法の割り当て | 観点ごとに使う技法を選び、選んだ根拠を書き残す |
| 6-1-3 | ケース表からテストスイートへ | ケース表を parametrize に写すと、そのままリグレッション資産になる |
| 6-1-4 | 自動化提案書 | 「何をどのレベルで自動化するか」を、根拠つきの 1 枚にまとめて提案する |

M6 の確認クイズは M1〜M5 の全範囲から 5 問を出す。出題範囲がレッスンに閉じない意図的な例外
(基本情報技術者の模擬試験モジュールと同じ方式)。他の全レッスンは、そのレッスンのトピックに範囲を閉じる。
