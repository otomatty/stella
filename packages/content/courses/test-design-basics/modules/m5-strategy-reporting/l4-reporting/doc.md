# レッスン5-4 品質を報告する

## このレッスンの目標

- [ ] 基本のテストメトリクス 3 つを、前週との差つきで出せる
- [ ] 読み手に合わせてテストレポートの粒度を変えられる
- [ ] リリース判断を求められたとき、材料の形で 3 行で答えられる

## 5-4-1 テストメトリクス

> **ケースの消化数・欠陥数・カバレッジで、テストの進み具合を数値にできる**

進捗会議で「テストの状況は?」と聞かれ、「だいぶ進んでいます」と答える。翌週も「もう少しです」。3 週続くと、聞くほうも信じなくなります。感覚の言葉は比べられないので、情報になりません。

**テストメトリクス** は、テストの状況を測る数値です。基本は 3 つで足ります。

- **消化数** — 実行したケース数 / 全体
- **欠陥数** — 新規・未修正・深刻度別
- **カバレッジ** — 自動テストがコードをどれだけ踏んだか

数値にすると、先週との差が言えます。差が言えると、あと何週かかるかの予測ができます。

| 指標 | 今週 | 先週 |
| --- | --- | --- |
| ケース消化 | 96 / 120 件(80%) | 62 / 120 件(52%) |
| 新規の欠陥 | 4 件 | 11 件 |
| 未修正(深刻度 高) | 1 件 | 3 件 |
| カバレッジ | 78% | 71% |

先週の列があることが肝心です。1 週ぶんの数字だけでは、良いのか悪いのか分かりません。この表からは「消化が加速し、新しい欠陥は減り、高深刻度の残りも減っている」と読めます。3 つとも同じ向きなので、素直に良い週です。

指標を増やしたくなりますが、増やすほど集める手間が増え、やがて更新されなくなります。3 つで始めてください。

そして、数値には落とし穴があります。

- **消化率 100% = 品質が良い、ではない** — 全部実行して全部落ちても消化率は 100% になります
- **欠陥数が減った = 品質が上がった、とは限らない** — 探すのをやめても減ります
- **カバレッジは書かれていないコードを測れない** — 仕様漏れは映りません

数値は判断の材料であって、判断そのものではありません。指標を目標にすると、指標を良くするだけの行動が始まります。必ず言葉の説明を添えてください。

## 5-4-2 テストレポート

> **テストレポートは読み手によって載せる情報を変える**

全ケースの一覧を貼り付けた 20 ページの報告書を経営会議に出したところ、聞かれたのは「で、明日リリースできるの?」の 1 問だけ。20 ページのどこにも、その答えは書かれていませんでした。

情報量が多いことと、伝わることは別です。**テストレポート** は、テストの状況と結果をまとめて関係者に伝える文書ですが、同じ元データでも読み手によって見たい粒度が違います。

| 読み手 | 主に載せるもの | 分量 |
| --- | --- | --- |
| 開発者 | 未修正の欠陥レポート、再現手順、深刻度 | 一覧 |
| リーダー | 消化数の推移、残りの範囲、遅れの理由 | 1 ページ |
| 経営・企画 | リリース判断の材料、残るリスクと対処案 | 3 行 |

削るのは手抜きではありません。読み手が判断できる形に絞るのが仕事です。全部載せるのは、実は誰にも読まれない形になります。3 行で書けるかが、いちばん難しく、いちばん効きます。

粒度は変えますが、どの読み手にも必ず書くことが 3 つあります。

- 何をテストしたか(範囲)、そして**何をテストしなかったか**
- 終了基準に対して、どこまで達したか
- 残っているプロダクトリスクと、その扱い方(様子見・次回対応・回避策)

とくに 1 つ目です。「やらなかったこと」を書く報告は信用されます。書いていないと、読んだ人は全部見たと誤解します。低リスクだから薄くした、という判断はレッスン5-2 で根拠つきで決めたはずなので、そのまま書けます。

優先度は開発側が決めるものなので、レポートには「深刻度 高が 1 件、優先度の判断待ち」のように、事実として書きます。

## 5-4-3 意思決定の材料

> **テストの報告は「リリースしてよいか」という判断に答えるためにある**

会議で「テスト担当としては、リリースしてよいと思いますか」と聞かれます。「大丈夫だと思います」と答えると、翌週の障害で「大丈夫と言った」ことになります。逆に「まだ不安です」と言えば、根拠を示せないまま日程だけが延びます。答え方の型を持っていないと、どちらに転んでも損をします。

判断そのものを下すのは、事業の責任を持つ人です。テスト担当が届けるのは、**判断に必要な材料**です。材料は 3 点あります。

- 何を確かめたか
- 何が残っているか
- 残りのリスクの大きさ

3 行にすると、たとえばこうなります。

> 高リスクの 3 機能は終了基準を満たしました。未修正は深刻度「中」が 2 件で、
> どちらも回避策(管理画面から手動で修正)があります。
> 低リスクのお知らせ表示は未着手ですが、リリース後の確認で足りると判断しています。

「よい」とも「だめ」とも言っていません。それでも、聞いた人はその場で決められます。これが最も強い報告の形です。

避けたい答え方も並べておきます。

| 答え方 | なぜ困るか |
| --- | --- |
| 「大丈夫です」 | 根拠が無く、あとで責任の話になる |
| 「バグがゼロなので出せます」 | 見つかっていないだけかもしれない |
| 「まだ不安です」 | 何が足りないのか、相手が動けない |

2 つ目には、モジュール1で扱った 2 つの原則が効いています。テストは欠陥がないことを証明できません。そして欠陥ゼロの落とし穴、つまり欠陥を全部直しても利用者の役に立たなければ失敗だという話です。ゼロは目的ではありません。

第 1 回で「テストは品質に関する情報を関係者に届ける活動である」と置きました。この回で、その情報が最後に何に使われるかが決まります。届け先は関係者の意思決定です。技法もケース表も自動化も、そこに向かうための道具でした。

## もっと知りたい人へ

- 報告の 3 行は、書いてから声に出して読んでみてください。読みながら「これは何を意味するの?」と自分で聞きたくなる箇所があれば、そこがまだ材料になっていません
- 終了基準を満たしていないままリリースすることも実務ではあります。そのときは「満たしていない」と書いたうえで、残るリスクと回避策を添えます。黙って基準を書き換えないでください
