# レッスン3-5 技法の使い分け

## このレッスンの目標

- [ ] 仕様の書かれ方から使う技法を選び、その根拠を説明できる
- [ ] 1 つの機能に複数の技法を重ねて適用できる
- [ ] ケース表の空欄を仕様への質問として持ち出せる

## 3-5-1 仕様の形で技法を選ぶ

> **範囲なら境界値、条件の絡みならデシジョンテーブル、状態があれば状態遷移を選ぶ**

技法は覚えたのに、仕様書を渡されると手が止まる。とりあえず思いついた値を並べて、それらしいケース表を作ってしまう。「なぜその技法を使ったのか」を聞かれても答えられない。技法を知っていることと、選べることは別です。

**テスト設計技法** は、仕様からテストケースを導く決まった手続きです。「決まった手続き」なので、同じ仕様に同じ技法を当てれば、誰がやっても似たケース表が出ます。この再現性が、勘で作ったケース表との一番の違いです。

選ぶ手がかりは、仕様の**書かれ方の形**にあります。

| 仕様に出てくる言葉 | 選ぶ技法 |
| --- | --- |
| 「〜以上」「〜円未満」「1〜10 件」 | 同値分割 + 境界値分析 |
| 「〜かつ〜の場合」「〜なら、ただし〜」 | デシジョンテーブル |
| 「〜のあとは」「ステータスが〜のとき」 | 状態遷移 |

仕様書に線を引きながら読むと、この 3 種類のどれかに当たります。当たらない部分(「使いやすいこと」「速いこと」など)は、これらの技法では扱えません。そこはモジュール4で扱う別の技法の担当です。

選び間違えると、手は動いているのに狙う欠陥に届かない状態になります。

| 仕様の形 | 誤って選ぶと |
| --- | --- |
| 範囲に状態遷移 | 状態が 1 つしかない図ができる |
| 条件の絡みに境界値 | 組み合わせが抜ける |
| 状態にデシジョンテーブル | 経過を表せず、途中の操作が消える |

どれも表そのものは作れてしまうので、気づきにくい失敗です。ケース表を作り終えたら「この表はどの技法の産物か」「その技法はどんな欠陥を狙うものだったか」を一度自分に聞いてみてください。

## 3-5-2 技法は重ねて使う

> **1 つの機能に複数の技法を重ねて、それぞれ違う種類の欠陥を狙う**

キャンセル機能に状態遷移を使い、遷移カバレッジ 100% を達成しました。ところが、返金額の計算に手数料の境界(10,000 円)があることは、状態遷移表には出てきません。状態は全部通ったのに、返金額が 1 円ずれる欠陥が残ります。1 つの技法で覆えるのは、仕様の 1 つの側面だけです。

技法は択一ではありません。「どれを使うか」ではなく「どれとどれを重ねるか」で考えます。

| 技法 | 狙う欠陥 | ケース例 |
| --- | --- | --- |
| 状態遷移 | 発送済でもキャンセルできる | 発送済 → キャンセルでエラー |
| 境界値分析 | 手数料の境目のずれ | 購入額 9,999 / 10,000 |
| デシジョンテーブル | 会員と手数料の組み合わせ漏れ | プレミアム × 10,000 円以上 |

同じ 1 つの機能に、3 つの技法がそれぞれ別の角度から入っています。狙う場所が違うので、重ねてもケースの重複はあまり増えません。件数が 3 倍になるわけではない、という点は覚えておいてください。

重ねる順番には、扱いやすい形があります。

1. **状態遷移** — まず「どの状態でその機能を使えるか」を決める
2. **デシジョンテーブル** — 使える状態の中で、条件の組み合わせを並べる
3. **境界値分析** — 各条件の中に範囲があれば、そこに境界値を入れる

外側から内側へ、が原則です。逆から始めると、そもそもその機能を使えない状態のケースを大量に作ってしまいます。「発送済の注文で購入額 9,999 円のときの返金額」は、そもそもキャンセルできないので意味のないケースです。

## 3-5-3 表が仕様の穴を暴く

> **ケース表を書けない場所は、仕様が決まっていない場所である**

デシジョンテーブルの 3 列目に、期待結果が書けません。仕様書を読み返しても、その組み合わせのことが書かれていません。とりあえず「たぶん 0%」と書いて先へ進んでしまう。ここで手が止まったことこそが情報なので、埋めて進んではいけません。

期待結果が書けないということは、合格の条件が決まっていないということです。合格の条件が決まっていない機能は、実装のしようもありません。表の空欄は、そのまま仕様への質問になります。

| 空欄が出た場所 | 仕様への質問 |
| --- | --- |
| 表の 3 列目 | 会員かつクーポンありのとき、割引は重なるのか |
| 状態遷移表の空マス | 発送済の注文はキャンセルできるのか |
| 境界の行 | 「3,000 円以上」に 3,000 円は含むのか |

どれもコードが書かれる前に出せる質問です。実装が終わってから聞くと、直す費用は跳ね上がります。モジュール1で扱った早期テストの原則が、ここで具体的な作業として現れています。テスト設計は、テストを実行するための準備であると同時に、実装より前に仕様の穴を見つける活動でもあるのです。

推測で埋めることの害も、はっきりさせておきます。

- 「たぶん 0%」と書いた瞬間、質問が消えて、仕様が確定したように見えます
- 決めるのは仕様を持っている人(企画・発注者)で、テスト担当者ではありません
- 実装者も別の推測をしているので、両者が食い違ったとき「テストが間違っている」と言われて終わります

空欄のまま持っていくのが正しい振る舞いです。「この表の 3 列目が埋まりません。会員かつクーポンありのとき、割引は 15% でよいですか」と聞けば、10 秒で決まります。表があるので、質問の場所も具体的です。空欄は未完成ではなく、成果物だと考えてください。

## もっと知りたい人へ

- ここまでの 3 技法は、いずれも仕様からケースを導く「系統的な技法」です。仕様に書かれていないことは、技法をどれだけ厚くかけても出てきません。その穴を埋める技法はモジュール4で扱います
- 仕様の穴を質問にするときは、選択肢を添えると早く決まります。「15% ですか、それとも 10% ですか」の形にすると、相手は選ぶだけで済みます
- 複数の技法を重ねたときは、ケース表に「どの技法から出たケースか」の列を持たせておくと、仕様変更のときに影響範囲を追いやすくなります
