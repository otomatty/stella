# レッスン3-4 状態遷移

## このレッスンの目標

- [ ] 状態とイベントで仕様をとらえ、状態遷移図に書き起こせる
- [ ] 状態遷移表から無効な遷移を数え上げられる
- [ ] 状態カバレッジと遷移カバレッジを使い分けてケースを選べる

## 3-4-1 状態という見方

> **同じ操作でも状態によって結果が変わる仕様は、状態遷移でとらえる**

「キャンセルボタンを押すとキャンセルできる」という仕様でテストしました。ところが発送済みの注文でもキャンセルできてしまい、返金だけ済んで商品が届く事故が起きます。押したボタンは同じなのに、正しい結果が違っていました。

**状態** は、対象が今どうなっているかを表します(受付・支払済・発送済・キャンセル)。**イベント** は、状態を変えるきっかけの操作です(支払う・発送する・キャンセルする)。イベントによって状態が別の状態に移ることを **状態遷移** と呼びます。

| いまの状態 | イベント | 移る先 |
| --- | --- | --- |
| 受付 | 支払う | 支払済 |
| 支払済 | 発送する | 発送済 |
| 受付 | キャンセルする | キャンセル |
| 発送済 | キャンセルする | (できない) |

3 行目と 4 行目は同じイベントですが、結果が違います。違いを作っているのは「いまの状態」だけです。つまり、**いまの状態を入力の一部として数える**のがこの技法の要点です。

ここまでの技法と並べると、違いがはっきりします。

| 技法 | 何を入力と見るか |
| --- | --- |
| 同値分割・境界値分析 | 1 つの値 |
| デシジョンテーブル | 同時に成り立つ条件の組 |
| 状態遷移 | **いまの状態 + イベント** |

状態遷移だけが「そこに至るまでの経過」を持ち込みます。デシジョンテーブルの条件はすべて同時に成り立つものですが、状態は過去の操作の積み重ねで決まります。だからテストも、1 回の呼び出しではなく操作の列になります。

## 3-4-2 状態遷移図

> **状態遷移図は状態とイベントを図にして、仕様の抜けを見つける道具である**

注文の仕様書に、ステータスの説明が箇条書きで 2 ページ書かれています。読んでも「支払期限が切れたら」の説明が見当たりません。文章のまま読んでいる限り、書かれていないことには気づけません。抜けは、書いてあるものを読んでも見つからないのです。

**状態遷移図** は、状態を丸、イベントを矢印で描いた図です。目的は、きれいにまとめることではなく、抜けを目に見えるようにすることです。矢印が出ていない状態、行き先のないイベントが抜けの候補になります。

- 受付 ──支払う──▶ 支払済
- 支払済 ──発送する──▶ 発送済
- 受付 ──キャンセルする──▶ キャンセル
- 支払済 ──キャンセルする──▶ キャンセル

状態は 4 つ(受付・支払済・発送済・キャンセル)、矢印は 4 本です。この一覧を眺めると、発送済とキャンセルが左側に一度も現れないこと、つまりそこからは矢印が 1 本も出ていないことに気づきます。本当に終わりの状態でよいのか。返品はどう扱うのか。

図を描くと、こうした質問が短時間で出てきます。

- 受付のまま支払期限が切れたらどうなるのか
- 発送済のあとに返品されたら、どの状態に移るのか
- キャンセルから受付に戻せるのか

どれも仕様書に書かれていなかった項目です。図を描くと 5 分で 3 件出ます。これはテスト設計の副産物ですが、実務ではこちらのほうが価値が大きい場面もあります。テストケースを作る前に仕様の穴が埋まれば、そもそも欠陥が作り込まれないからです。早期テストの原則がここで効いてきます。

## 3-4-3 状態遷移表

> **状態遷移表にすると、図では見えない「無効な遷移」が浮かび上がる**

図には矢印が 4 本あったので、4 件のテストケースを作りました。発送済の注文をキャンセルする操作は、図に無いのでテストしませんでした。そして本番でそれができてしまいます。図は「起きること」しか描きません。起きてはいけないことは、図には現れないのです。

**状態遷移表** は、行に状態、列にイベントを並べ、**すべてのマスを埋める**表です。起きてはいけない状態とイベントの組を **無効な遷移** と呼びます。

| 状態＼イベント | 支払う | 発送する | キャンセルする |
| --- | --- | --- | --- |
| 受付 | 支払済 | − | キャンセル |
| 支払済 | − | 発送済 | キャンセル |
| 発送済 | − | − | − |
| キャンセル | − | − | − |

4 状態 × 3 イベントで 12 マスです。埋まっているのは 4 マスだけで、残り 8 マスが無効な遷移になります。マスの数は状態 × イベントで決まるので、図の矢印の数とは一致しません。この差が、図では見えなかった部分です。

| | 見えるもの | 数 |
| --- | --- | --- |
| 状態遷移図 | 起きる遷移 | 矢印 4 本 |
| 状態遷移表 | 起きる遷移 + 起きてはいけない組 | 12 マス |

表の「−」のマスは「何も起きない」ではありません。「エラーになるべき」です。ここに期待結果を書けば、そのままテストケースになります。「発送済の注文をキャンセルしようとすると、『発送済の注文はキャンセルできません』と表示される」まで書ければ、見た瞬間に合否が決まります。

無効な遷移は、実装で見落とされやすい場所です。開発者は正常な流れを作ることに集中するので、「そこには来ないはず」の分岐が空いたまま残ります。表を作るコストは小さく、見つかる欠陥は重い。割のよい技法です。

## 3-4-4 遷移カバレッジ

> **すべての状態を踏むか、すべての遷移を踏むかで、テストの強さを選べる**

「注文のステータスはひととおり見ました」と報告しました。4 つの状態を画面で確認したのは事実です。しかし、支払済からキャンセルする経路は一度も通していませんでした。「ひととおり」が何を指すのかは、人によって違います。

目盛りを 2 つ用意すると、この曖昧さが消えます。

- **状態カバレッジ** — すべての状態を 1 回は通ったか
- **遷移カバレッジ** — すべての遷移(矢印)を 1 回は通ったか

| | 満たす条件 | 注文の例 |
| --- | --- | --- |
| 状態カバレッジ | 4 状態を訪れる | 2 経路で足りる |
| 遷移カバレッジ | 4 本の矢印を通る | 3 経路必要 |

受付 → 支払済 → 発送済 と、受付 → キャンセル の 2 経路で 4 状態は埋まります。しかし、支払済 → キャンセルの矢印が残ります。この矢印を通すには 受付 → 支払済 → キャンセル という 3 本目の経路が要ります。同じ「ひととおり」でも、目盛りが違えばケース数も網の広さも変わります。

注意が 1 つあります。状態カバレッジも遷移カバレッジも、**起きる遷移しか数えません**。無効な遷移(表の「−」)は、この数字には含まれません。「発送済でキャンセルするとエラーになる」というテストは、遷移カバレッジ 100% でも未実施のままです。

カバレッジの数字だけを見ていると、無効な遷移が丸ごと抜けます。カバレッジは「何を数えているか」とセットで読む値です。この性質は、モジュール4で扱うコードのカバレッジでもまったく同じ形で出てきます。

実務では、まず遷移カバレッジ 100% を目標に経路を作り、そのうえで無効な遷移の一覧から重要なものを別途テストケースにする、という順序が扱いやすい進め方です。

## 3-4-5 遷移のテストコード

> **状態遷移テストでは、遷移の 1 本が「操作の列+期待する状態」の 1 ケースになる**

「支払済からキャンセルできる」をテストしたいのですが、いきなり支払済の注文は作れません。受付から始めて、支払ってから、キャンセルする必要があります。1 回呼ぶだけでは足りず、そこに至るまでの操作が要ります。

これがテストケースの 3 点セットにどう表れるかを見てください。**手順** の列が、そこへ至るまでの操作の並びになります。**期待結果** は、最後のイベントのあとの状態です。手順が長くなるのが状態遷移テストの特徴です。

```python
# order.py
class Order:
    TRANSITIONS = {
        ("受付", "支払う"): "支払済",
        ("受付", "キャンセルする"): "キャンセル",
        ("支払済", "発送する"): "発送済",
        ("支払済", "キャンセルする"): "キャンセル",
    }

    def __init__(self):
        self.status = "受付"

    def handle(self, event):
        key = (self.status, event)
        if key not in self.TRANSITIONS:
            raise ValueError(f"{self.status} では {event} はできません")
        self.status = self.TRANSITIONS[key]
        return self.status
```

```python
# test_order.py
import pytest

from order import Order


def test_pay_then_ship_reaches_shipped():
    order = Order()
    order.handle("支払う")
    assert order.handle("発送する") == "発送済"
```

`Order()` が受付の状態、その次の行の `handle` が前提を作る操作、最後の行が確かめたい遷移です。前提を作る操作と、確かめたい遷移を、行の位置で見分けられるように書いておくと読みやすくなります。

無効な遷移は形が変わります。

```python
def test_cannot_ship_before_payment():
    order = Order()
    with pytest.raises(ValueError):
        order.handle("発送する")
```

表の「−」のマスは、この形で書きます。何も起きないのではなく、エラーになることを確かめます。`pytest.raises` は「この中でその例外が起きること」を期待する書き方でした。無効同値パーティションのときと同じ道具です。

なお、`Order` の実装が遷移の表そのものを持っている点にも注目してください。仕様が表の形をしているなら、実装も表の形にできます。そうすると、仕様の表・実装の表・テストの表が一直線に並び、どこかが食い違えばすぐ見えるようになります。

## もっと知りたい人へ

- 状態遷移図は UML のステートマシン図として書式が決まっています。開始状態を黒丸、終了状態を二重丸で描く、といった記法を覚えておくと、設計者が書いた図をそのまま読めます
- 「1 スイッチカバレッジ」という、連続する 2 つの遷移の並びをすべて通す、より強い目盛りもあります。遷移カバレッジで足りないと分かってから検討してください
- `pytest.raises` の詳細: <https://docs.pytest.org/en/stable/how-to/assert.html>
