# レッスン3-4 演習 — 状態遷移

対象トピック: 3-4-1 〜 3-4-5

## 手元で試す

**①仕様からケース表を書く → ②表を pytest に写して実行する**。今回の「ケース表」は状態遷移表と、そこから選んだ経路の一覧です。

### ① 状態遷移表を書く

次の仕様を読んでください。

> **仕様**: 注文のステータスは 受付 / 支払済 / 発送済 / キャンセル の 4 つ。新しい注文は受付から始まる。受付の注文は「支払う」で支払済に、「キャンセルする」でキャンセルになる。支払済の注文は「発送する」で発送済に、「キャンセルする」でキャンセルになる。発送済とキャンセルの注文には、どの操作もできない。

まず状態遷移表を埋めます。起きない組には「−」を書いてください。

| 状態＼イベント | 支払う | 発送する | キャンセルする |
| --- | --- | --- | --- |
| 受付 | | | |
| 支払済 | | | |
| 発送済 | | | |
| キャンセル | | | |

埋めたら、次を確かめてください。

- マスは全部で 12 個ありますか。行 × 列で数え、空白のマスが残っていないか見ます
- 埋まったマス(起きる遷移)は 4 つですか
- 「−」のマスが 8 つありますか。これが無効な遷移です

次に、**遷移カバレッジ 100% を満たす経路の一覧**を作ります。1 経路 = 1 テストケースです。

| # | 手順(操作の列) | 期待する状態 | 通る遷移 |
| --- | --- | --- | --- |
| 1 | | | |
| 2 | | | |
| 3 | | | |

最少で何経路になるか、自分の答えと数えた遷移の数を照らし合わせてください。

### ② 表を pytest に写す

作業用のフォルダに次の 2 ファイルを置いてください。

```python
# order.py
class Order:
    TRANSITIONS = {
        ("受付", "支払う"): "支払済",
        ("受付", "キャンセルする"): "キャンセル",
        ("支払済", "発送する"): "発送済",
        ("支払済", "キャンセルする"): "キャンセル",
    }

    def __init__(self):
        self.status = "受付"

    def handle(self, event):
        key = (self.status, event)
        if key not in self.TRANSITIONS:
            raise ValueError(f"{self.status} では {event} はできません")
        self.status = self.TRANSITIONS[key]
        return self.status
```

```python
# test_order.py
import pytest

from order import Order


def run(events):
    order = Order()
    for event in events:
        order.handle(event)
    return order


@pytest.mark.parametrize("events, expected", [
    (["支払う", "発送する"], "発送済"),          # 受付→支払済→発送済
    (["キャンセルする"], "キャンセル"),           # 受付→キャンセル
    (["支払う", "キャンセルする"], "キャンセル"),  # 受付→支払済→キャンセル
])
def test_valid_transitions(events, expected):
    assert run(events).status == expected


@pytest.mark.parametrize("events, last", [
    ([], "発送する"),                  # 受付では発送できない
    (["支払う"], "支払う"),            # 支払済でもう一度は払えない
    (["支払う", "発送する"], "キャンセルする"),  # 発送済はキャンセルできない
])
def test_invalid_transitions(events, last):
    order = run(events)
    with pytest.raises(ValueError):
        order.handle(last)
```

ターミナルで実行します。

```bash
pytest -v
```

`6 passed` と表示されれば成功です。上の 3 件が遷移カバレッジ 100% の経路、下の 3 件が無効な遷移のテストです。前者だけでは無効な遷移が一度も試されないことを、テストの並びで確かめてください。

確かめられたら、次の改造をしてみましょう。

1. `order.py` の `TRANSITIONS` から `("支払済", "キャンセルする")` の行を消して実行し、**どのテストが落ちるか**を確かめる(確かめたら戻す)
2. `TRANSITIONS` に `("発送済", "キャンセルする"): "キャンセル"` を足して実行し、無効な遷移のテストが落ちることを確かめる(確かめたら戻す)。仕様に無い遷移を実装が持っている、という欠陥がこの形で見つかります
3. 残り 5 つの無効な遷移のうち 2 つを選び、`test_invalid_transitions` に組として追加する

## 演習問題

### 問1(基本)

「同じ操作なのに結果が違う」という仕様を、状態遷移でとらえるべき理由を 1 文で書いてください。

### 問2(基本)

状態が 3 つ、イベントが 4 つの仕様があります。状態遷移表のマスはいくつになりますか。また、そのうち埋まるマスが 6 つだったとき、無効な遷移はいくつですか。

### 問3(応用)

ある担当者が「状態遷移図の矢印をすべて通したので、状態遷移のテストは完了です」と報告しました。この報告に足りていない観点を指摘してください。

### 問4(応用)

注文の仕様に「支払済の注文は、発送前なら返品予約できる(状態は支払済のまま変わらない)」が追加されました。状態遷移表にどう書き加えるか答え、テストケースをどう増やすか説明してください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

結果の違いを作っているのが「いまの状態」だからです。入力と条件だけを並べる技法では、そこに至るまでの操作の経過を表せません。状態遷移は「いまの状態 + イベント」を入力として数えるので、この形の仕様を漏れなく扱えます。

</details>

<details>
<summary>問2の解答例</summary>

マスは 3 × 4 = 12 個です。埋まるマスが 6 つなら、無効な遷移は 12 − 6 = 6 つになります。

マスの数は状態 × イベントで決まり、図の矢印の数とは一致しません。この差が、図では見えなかった部分です。

</details>

<details>
<summary>問3の解答例</summary>

無効な遷移が一度も試されていません。状態遷移図に描かれるのは「起きる遷移」だけなので、矢印をすべて通しても、起きてはいけない組み合わせは 1 つも確かめていないことになります。

注文の例では、矢印 4 本に対して無効な遷移が 8 つありました。数の上では、確かめていない側のほうが多い状態です。状態遷移表を作り、「−」のマスにも期待結果を書いてテストケースにする必要があります。

なお「遷移カバレッジ 100%」という言葉自体は間違っていません。カバレッジは「何を数えているか」とセットで読む値だ、という点が要点です。

</details>

<details>
<summary>問4の解答例</summary>

イベントの列に「返品予約する」を足し、支払済の行に「支払済」と書きます(自分自身に戻る遷移)。他の状態の行は「−」です。

| 状態＼イベント | 支払う | 発送する | キャンセルする | 返品予約する |
| --- | --- | --- | --- | --- |
| 受付 | 支払済 | − | キャンセル | − |
| 支払済 | − | 発送済 | キャンセル | **支払済** |
| 発送済 | − | − | − | − |
| キャンセル | − | − | − | − |

テストケースは 2 種類増えます。1 つは遷移そのもの(支払済で返品予約して、状態が支払済のままであること)。もう 1 つは新しく生まれた無効な遷移 3 件(受付・発送済・キャンセルで返品予約するとエラーになること)です。

自分自身に戻る遷移は、状態が変わらないので「何も起きていない」ように見えます。状態だけを見る期待結果では合否を判定できないので、「返品予約が 1 件登録されている」など、別の観点の期待結果も添える必要があります。

</details>

## 確認クイズ

### Q1. 状態遷移でとらえるべき仕様はどれですか。

- A. 同じ操作でも、いまの状態によって結果が変わる仕様
- B. 入力が数値の範囲で分かれる仕様
- C. 複数の条件が同時に成り立つ仕様

<details>
<summary>答え</summary>

**A** — B は境界値分析、C はデシジョンテーブルの出番です。状態遷移だけが「そこに至るまでの経過」を持ち込みます。

</details>

### Q2. 状態遷移図を描く目的として、このレッスンで示したものはどれですか。

- A. 仕様書をきれいにまとめる
- B. 仕様の抜けを目に見えるようにする
- C. 実装の構造をそのまま写す

<details>
<summary>答え</summary>

**B** — 矢印が出ていない状態、行き先のないイベントが抜けの候補になります。図を描くと仕様への質問が短時間で出てきます。

</details>

### Q3. 状態が 4 つ、イベントが 3 つのとき、状態遷移表のマスはいくつですか。

- A. 7 個
- B. 図の矢印と同じ数
- C. 12 個

<details>
<summary>答え</summary>

**C** — 状態 × イベントで決まります。図の矢印の数(この例では 4 本)とは一致せず、その差が無効な遷移です。

</details>

### Q4. 遷移カバレッジ 100% を満たしても未実施のまま残るものはどれですか。

- A. 無効な遷移のテスト
- B. すべての状態を訪れるテスト
- C. 開始状態から始めるテスト

<details>
<summary>答え</summary>

**A** — 状態カバレッジも遷移カバレッジも、起きる遷移しか数えません。無効な遷移は別の一覧としてテストケースにします。

</details>

### Q5. 状態遷移テストのテストケースで、手順の列に書くのは何ですか。

- A. 期待する状態の名前
- B. 状態遷移表のマスの数
- C. 確かめたい遷移に至るまでの操作の並び

<details>
<summary>答え</summary>

**C** — いきなり支払済の注文は作れないので、受付から始めて支払う操作が要ります。手順が長くなるのが状態遷移テストの特徴です。

</details>
