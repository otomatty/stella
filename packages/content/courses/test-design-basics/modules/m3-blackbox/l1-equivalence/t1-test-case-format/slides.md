# 3-1-1
# テストケースの形

テスト設計入門 — Module 3 / レッスン3-1

<!-- ノート: ここから「どう作るか」に入ります。まずはテストケースを書く器の形から。 -->

---

## なぜ必要か

- 手順書に「送料が無料になることを確認」とだけ書いてある
- 読んだ人は、いくらの注文で試せばよいのか分からない
- 結果が「なんとなく正しそう」で終わり、合否が人によって割れる

<!-- ノート: つかみ。書いた本人以外が実行できないテストは、テストとして機能しません。ここで結論は言わない。 -->

---

## 結論

**テストケースは入力・手順・期待結果の 3 点セットで書く**

- **入力** — 何を与えるか(値・データ・前提の状態)
- **手順** — どう操作するか
- **期待結果** — どうなれば合格か

<!-- ノート: 結論を言い切る。3 つのうち 1 つでも欠けると、他人が実行できないか、合否を判定できません。 -->

---

## 送料計算のテストケース 1 件

| 入力 | 手順 | 期待結果 |
| --- | --- | --- |
| 購入額 3,000 円 | 商品をカートに入れ、注文確認画面を開く | 送料が 0 円と表示される |

この 3 列の表を **ケース表** と呼びます。1 行が 1 テストケースです。

<!-- ノート: 具体例の枠。書いた本人が休んでも、この 1 行があれば別の人が同じテストを実行できます。 -->

---

## 期待結果になっていない書き方

| 書き方 | なぜ困るか |
| --- | --- |
| 「正しく表示される」 | 何が正しいかが人によって違う |
| 「エラーが出ない」 | 出なければ何でも合格になる |
| 「送料が 0 円と表示される」 | ○ 見れば合否が決まる |

<!-- ノート: 失敗例の枠。期待結果は「見れば合否が決まる」粒度まで書きます。ここが曖昧なテストは実行しても情報が増えません。 -->
