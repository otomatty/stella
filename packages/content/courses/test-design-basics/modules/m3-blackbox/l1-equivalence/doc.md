# レッスン3-1 同値分割

## このレッスンの目標

- [ ] テストケースを入力・手順・期待結果の 3 点セットで書ける
- [ ] 仕様から同値パーティションを漏れなく重なりなく切り出せる
- [ ] ケース表の 1 行を pytest のテスト関数に写せる

## 3-1-1 テストケースの形

> **テストケースは入力・手順・期待結果の 3 点セットで書く**

手順書に「送料が無料になることを確認」とだけ書いてある。読んだ人は、いくらの注文で試せばよいのか分かりません。結果も「なんとなく正しそう」で終わり、合否が人によって割れます。書いた本人以外が実行できないテストは、テストとして機能しません。

テストケースは 3 つの要素で書きます。**入力**(何を与えるか)、**手順**(どう操作するか)、**期待結果**(どうなれば合格か)です。1 つでも欠けると、他人が実行できないか、合否を判定できません。

| 入力 | 手順 | 期待結果 |
| --- | --- | --- |
| 購入額 3,000 円 | 商品をカートに入れ、注文確認画面を開く | 送料が 0 円と表示される |

この 3 列の表を **ケース表** と呼びます。1 行が 1 テストケースです。このレッスンから先、テスト設計の成果物はほぼすべてこの形の表になります。

つまずきやすいのは期待結果です。次の 3 つを比べてください。

| 書き方 | なぜ困るか |
| --- | --- |
| 「正しく表示される」 | 何が正しいかが人によって違う |
| 「エラーが出ない」 | 出なければ何でも合格になる |
| 「送料が 0 円と表示される」 | ○ 見れば合否が決まる |

期待結果は「見れば合否が決まる」粒度まで書きます。ここが曖昧なテストは、実行しても情報が増えません。テストは品質に関する情報を届ける活動でしたから、情報が増えないテストは目的を果たしていないことになります。

## 3-1-2 同値パーティション

> **同じ扱いを受ける入力はひとつのグループ(同値パーティション)にまとめられる**

送料の計算を試すのに、100 円・200 円・300 円…と並べた手順書があります。全部で 40 件ありますが、どれも同じ場所を通っています。一方で 3,000 円ちょうどは 1 件も入っていません。数が多いことと、網が広いことは別です。

**同値パーティション** は、仕様の上で同じ結果になる入力の集まりです。入力の全体を、重なりのないパーティションに分ける作業を **同値分割** と呼びます。

> 仕様: 購入額 3,000 円以上なら送料無料。3,000 円未満なら送料 500 円。購入額は 1 円以上。

| パーティション | 範囲 | 結果 |
| --- | --- | --- |
| P1 | 1 〜 2,999 円 | 送料 500 円 |
| P2 | 3,000 円以上 | 送料 0 円 |
| P3 | 0 円以下 | エラー |

100 円も 200 円も 2,999 円も、すべて P1 の一員です。40 件並べても P1 を 40 回試しただけになります。

ここで大事なのは、「同じ扱いを受ける」の根拠が仕様であって、コードではないという点です。中身を見ずに入力と出力だけで考えるので、これはブラックボックスの技法です。

分け方が正しいかどうかは、2 つの条件で確かめられます。

| 分け方 | どこが問題か |
| --- | --- |
| 1〜3,000 と 3,000 以上 | 3,000 が両方に入る(重なっている) |
| 1〜2,999 と 3,001 以上 | 3,000 がどこにも入らない(抜けている) |
| 1〜2,999 と 3,000 以上 と 0 以下 | ○ 重なりも抜けもない |

重なりがあると、同じ入力に 2 つの期待結果が付いてしまいます。抜けがあると、そこはそのままテストの穴になります。

## 3-1-3 代表値

> **各パーティションから代表値を 1 つ選べば、ケースを大きく減らせる**

パーティションに分けたところまでは終わりました。では 1〜2,999 円を全部試すのか、と聞かれて答えに詰まる。減らしてよい理由を言えないと、結局全部並べてしまいます。

**代表値** は、そのパーティションを代表して試す 1 つの値です。1 つで足りる根拠は「同じパーティションの中は同じ扱いを受ける」という前提です。前提が崩れている(実は 2,000 円だけ別扱いだった、など)なら、そこは別のパーティションとして切り直します。

| # | 入力(購入額) | 期待結果 | 代表するパーティション |
| --- | --- | --- | --- |
| 1 | 1,500 円 | 送料 500 円 | P1(1〜2,999) |
| 2 | 5,000 円 | 送料 0 円 | P2(3,000 以上) |
| 3 | 0 円 | エラー | P3(0 以下) |

100 円刻みの 40 件が 3 件になりました。ケースが減ったというより、重複が消えたと考えてください。

選び方には落とし穴があります。

| 選び方 | 何が起きるか |
| --- | --- |
| P1 から 3 つ、P2 から 0 つ | 数は多いのに無料になる側を試していない |
| キリのよい 1,000 円ばかり | 特別扱いされる値に偏り、普通の値を試せない |
| 各パーティションから 1 つずつ | ○ 網が全パーティションに届く |

数を数えるのではなく、パーティションを数えます。ケース表に「代表するパーティション」の列を足しておくと、どこが 0 件かがひと目で見えます。

## 3-1-4 無効同値パーティション

> **エラーになる入力のグループも、漏らさずパーティションとして数える**

送料のテストは 3 件でカバーできた、と報告しました。ところが本番で、購入額に空文字が入った注文が 500 円で通ってしまいます。残るのは「そんな入力は来ない想定でした」という説明だけです。想定外の入力は必ず来ます。

パーティションには 2 種類あります。**有効同値パーティション** は仕様が正常に処理すると決めている入力の集まり、**無効同値パーティション** は仕様がエラーとして扱う入力の集まりです。両方あわせて初めて入力の全体になります。片方だけでは分割が終わっていません。

| 種別 | パーティション | 代表値 | 期待する振る舞い |
| --- | --- | --- | --- |
| 有効 | 1 〜 2,999 円 | 1,500 | 送料 500 円 |
| 有効 | 3,000 円以上 | 5,000 | 送料 0 円 |
| 無効 | 0 円以下 | 0 | エラー |
| 無効 | 数値でない | "abc" | エラー |

3 件だった表が 4 件になりました。増えた 1 件が、さきほど本番で漏れたものです。

無効の側を書くときの注意が 2 つあります。

1 つ目は、**1 パーティションにつき 1 件ずつ、別々のケースにする**ことです。空文字と負数を 1 件のケースにまとめると、最初のエラーで処理が止まり、残りを確かめられません。それでも「そのケースは通った」と記録されるので、通っていない検証が通ったように見えます。

2 つ目は、期待結果を「エラー」で終わらせず、**どんなエラーかまで書く**ことです。エラーの種類が違えば、利用者に見えるものも違います。「購入額は 1 円以上です、というメッセージが表示される」まで書ければ、見た瞬間に合否が決まります。

## 3-1-5 pytest の最小形

> **pytest は test_ で始まる関数の assert が成り立つかでテストの合否を決める**

ケース表はできましたが、実行するのは毎回人の手です。3 件なら回りますが、リリースのたびに回すと決めた瞬間に重くなります。表のまま置いておくと、コードが変わっても誰も気づきません。設計したケースを自動テストの形にすると、そのままリグレッションテストの資産になります。

**pytest** は Python の自動テストを実行するツールです。覚えることは決まりが 2 つだけです。

- **テスト関数** — `test_` で始まる名前の関数。pytest はこれだけを集めます(ファイル名も `test_` で始めるか `_test.py` で終わらせます)
- **assert** — 条件が真であることを主張する文。偽ならそのテストは失敗します

```python
# shipping.py
def shipping_fee(total):
    if total < 1:
        raise ValueError("購入額は 1 円以上です")
    return 0 if total >= 3000 else 500
```

```python
# test_shipping.py
from shipping import shipping_fee


def test_under_3000_costs_500():
    assert shipping_fee(1500) == 500
```

ターミナルで `pytest` と打つと `1 passed` と表示されます。`shipping_fee(1500)` が入力、`== 500` が期待結果です。ケース表の 1 行がそのまま 1 関数になりました。手順の列は、この場合「関数を呼ぶ」だけなので消えています。画面操作を伴うテストでは手順が数行になります。

集めてもらえない書き方に注意してください。

| 書き方 | 何が起きるか |
| --- | --- |
| 関数名を `check_...` にする | 集められず `no tests ran` になる |
| ファイル名を `shipping_tests.py` にする | 同じく集められない |
| `print` で結果を出す | 人が読まないと合否が分からない |

`no tests ran` は「テストが失敗した」ではなく「1 つも集まっていない」という意味です。赤い `assert` の行が出ないので見落としやすい表示です。テストが 0 件で緑になっている状態は、テストがない状態と同じだと考えてください。
