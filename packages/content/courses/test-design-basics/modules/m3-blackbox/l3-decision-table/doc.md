# レッスン3-3 デシジョンテーブル

## このレッスンの目標

- [ ] 複数の条件が絡む仕様をデシジョンテーブルに書き起こせる
- [ ] 結果に効いていない条件を「−」で簡約できる
- [ ] ルール 1 列をテスト 1 ケースとしてコードに写せる

## 3-3-1 条件の組み合わせ

> **条件が複数絡む仕様は、頭の中ではなく表で整理しないと漏れる**

「プレミアム会員は 10% 引き。クーポンがあれば 5% 引き」という仕様がありました。テスト担当者は「会員」と「クーポン」を 1 件ずつ試し、どちらも期待どおりでした。ところが本番で、両方を持つ利用者だけ割引が 5% になっています。1 つずつ試すと、重なった場合が抜けます。

**条件** は、結果を左右する真偽の判断です(会員か / クーポンがあるか)。**組み合わせ** は、条件それぞれの真偽をすべて並べたものです。条件が n 個あれば組み合わせは 2 の n 乗になります。2 個で 4 通り、3 個で 8 通り、5 個で 32 通り。3 個を超えたあたりから、頭の中では追えなくなります。

| 試した内容 | 会員 | クーポン | 結果 |
| --- | --- | --- | --- |
| ケース1 | ○ | × | 10% ○ |
| ケース2 | × | ○ | 5% ○ |
| **未実施** | **○** | **○** | **?** |

2 条件なら 4 通りありますが、2 件しか試していません。抜けた 1 つに欠陥が出ました。「会員のテストもクーポンのテストもやりました」という報告は、組み合わせの観点では 4 分の 2 です。

ここで、モジュール1でやった「全数テストは不可能」との線引きを確認しておきます。

- 同値分割で扱ったのは「1 つの入力を値の範囲で切る」話です。購入額のすべての値は試せません
- ここで扱うのは「複数の条件が同時に成り立つ」話です。条件の数は仕様で決まっているので有限です

購入額の全数テストは不可能ですが、条件の組み合わせは数が小さければ全部書けます。だから表にする価値があります。

## 3-3-2 デシジョンテーブルの書き方

> **デシジョンテーブルは条件×ルールの表で、組み合わせを列挙する**

組み合わせを書き出そうとして、箇条書きで並べ始めました。「会員でクーポンあり」「会員でクーポンなし」…と書くうちに重複が出ます。そして、全部書けたのかどうかが、見ても分かりません。並べる形が決まっていないと、数え上げが終わったかを確認できないのです。

**デシジョンテーブル** は、上半分に条件、下半分にアクションを置く表です。**ルール** は表の 1 列、つまり条件の真偽の組み合わせ 1 通りを指します。**アクション** はそのルールのときの結果です。

| 条件 | R1 | R2 | R3 | R4 |
| --- | --- | --- | --- | --- |
| プレミアム会員か | N | N | Y | Y |
| クーポンがあるか | N | Y | N | Y |
| **割引率** | **0%** | **5%** | **10%** | **15%** |

条件が 2 つなので 2 の 2 乗で 4 列です。列の数が数え上げの完了を教えてくれます。5 列あったら重複、3 列なら漏れです。

書くときの決まりは 3 つです。

1. 条件は **Y / N で答えられる形**に言い換えてから並べる。「会員区分は?」のような 3 択は、Y/N の条件 2 つに割るか、Y/N ではなく値そのものを並べる列にします。まずは Y/N で慣れてください
2. 列は Y/N を機械的に並べる。左から N,N / N,Y / Y,N / Y,Y のように、二進数を数える要領で書きます。考えながら並べると必ず漏れます
3. **ルール 1 列 = テストケース 1 件**。列がそのままケース表の行になります

この表を作る過程で、仕様に書かれていない組み合わせが見つかることがよくあります。「両方持っている人はどうなるのか」が仕様に無い、というのがまさにそれです。表の空欄は、仕様の空欄です。

## 3-3-3 ルールの簡約

> **結果に影響しない条件を「−」でまとめると、ルールを減らせる**

割引の仕様に「クーポンが期限内か」という条件が増えました。条件 3 つで列は 8 本になります。よく見ると、クーポンを持っていない列では期限の Y/N が結果に効いていません。条件 5 つなら 32 本。全部をテストケースにするのは現実的ではありません。

**簡約** は、結果が同じで、効いていない条件がある列どうしをまとめる作業です。「−」は「Y でも N でも結果は変わらない」という意味で書きます。

| 条件 | R1 | R2 | R3 | R4 | R5 | R6 |
| --- | --- | --- | --- | --- | --- | --- |
| プレミアム会員か | N | N | N | Y | Y | Y |
| クーポンがあるか | N | Y | Y | N | Y | Y |
| クーポンが期限内か | − | N | Y | − | N | Y |
| **割引率** | **0%** | **0%** | **5%** | **10%** | **10%** | **15%** |

R1 と R4 が「−」を持つ列です。もとの 8 列のうち 2 組ずつがまとまり、8 列が 6 列になりました。減らしているのは列であって、条件ではありません。条件の行は 3 つのままです。

簡約には、やってよい形とやってはいけない形があります。

| まとめ方 | 良し悪し |
| --- | --- |
| 効いていないと確かめた条件を「−」に | ○ 正しい簡約 |
| 結果が同じ列を、条件を見ずにまとめる | × 別の欠陥を見逃す |
| 列が多いので、面倒な列を消す | × ただの手抜き |

2 行目が特に危ない判断です。R2(一般・クーポンあり・期限切れ)と R5(プレミアム・クーポンあり・期限切れ)は結果が違うので迷いませんが、たまたま結果が同じ列どうしを条件を見ずにまとめると、その組み合わせでだけ起きる欠陥を見逃します。「割引率が同じだから 1 件でいい」は簡約ではありません。条件の意味を見て、その条件が効いていないことを確かめたときだけ「−」にします。

## 3-3-4 表からテストコードへ

> **デシジョンテーブルのルール 1 列が、テスト 1 ケースになる**

6 列の表を作り、テストコードも 6 件書きました。半年後、仕様が変わって列が 8 本に戻ります。表は更新されましたが、コードのどれが表のどの列に当たるのか分かりません。設計とコードの対応が切れると、表は飾りになります。

写し方は境界値の表と同じです。違うのは、対応が縦向きだという点だけです。

- 条件の行 → 引数
- ルールの列 → parametrize の 1 組
- アクションの行 → 期待結果

```python
# discount.py
def discount_rate(is_premium, has_coupon, coupon_valid):
    rate = 10 if is_premium else 0
    if has_coupon and coupon_valid:
        rate += 5
    return rate
```

```python
# test_discount.py
import pytest

from discount import discount_rate


@pytest.mark.parametrize("premium, coupon, valid, rate", [
    (False, True, True, 5),    # R3: 一般 + 有効クーポン
    (True, True, True, 15),    # R6: プレミアム + 有効クーポン
])
def test_discount_rate(premium, coupon, valid, rate):
    assert discount_rate(premium, coupon, valid) == rate
```

コメントの `# R3` が表との対応です。この 4 文字があるだけで、表を直したときにコードのどこを直せばよいかが分かります。逆に、コードにあって表に無い組が見つかれば、それは表の更新漏れです。

簡約した「−」の列だけは、写すときに判断が要ります。「−」は Y でも N でもよいので、**どちらか一方を選んで書く**しかありません。選んだ値は表には無い情報なので、コメントに残します。

```python
    (False, False, True, 0),   # R1: クーポンなし(期限は「−」→ True を採用)
```

迷ったら、実務で起きやすいほうを選びます。ここでの判断を記録しておくと、あとで「なぜ True なのか」と聞かれたときに答えられます。テスト設計の成果物は、値そのものより「なぜその値か」のほうが寿命が長い、と考えておいてください。

## もっと知りたい人へ

- 条件が多くて列が爆発するときは、まず条件どうしが本当に独立かを疑ってください。「クーポンがある」と「クーポンが期限内」のように片方が片方に依存していると、実際に起こりうる組み合わせは 2 の n 乗より少なくなります
- 3 択以上の条件(会員区分が一般 / プレミアム / 法人 など)は、Y/N の代わりに値そのものを列に並べる書き方もあります。表の意味は同じです
- `pytest.mark.parametrize` の `ids` 引数を使うと、実行結果に `R3` のような名前を表示できます: <https://docs.pytest.org/en/stable/how-to/parametrize.html>
