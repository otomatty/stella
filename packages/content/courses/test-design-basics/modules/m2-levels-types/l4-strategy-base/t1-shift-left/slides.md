# シフトレフト

テスト設計入門研修 — Module 2 / レッスン2-4

<!-- ノート: 戦略の土台の 1 本目。原則で学んだ「早く」を、具体的な動き方に落とします。 -->

---

## なぜ必要か

- テスト担当が仕様を読むのは、実装が終わってから
- 読んで初めて「この条件、どちらとも取れます」と気づき、作り直しになる

<!-- ノート: つかみ。早期テストの原則は知っていても、実際の予定表では最後に置かれている。ここで結論は言わない。 -->

---

## 結論

**テスト活動を開発の早い段階へ寄せるほど、手戻りが減る**

- **シフトレフト** — テストプロセスの前半の活動を、開発の左側(早い時期)へ動かす進め方

<!-- ノート: 結論を言い切る。動かすのは実行ではなく、分析とテスト設計。仕様がある時点で始められる。 -->

---

## 何を左へ動かすか

| 段階 | 寄せられる活動 |
| --- | --- |
| 要件を決めるとき | 仕様をテストできる文か点検する |
| 設計するとき | テスト設計を始め、条件の抜けを洗う |
| 実装するとき | コンポーネントテストを同時に書く |
| 結合してから | 実行する(ここは動かせない) |

<!-- ノート: 具体例の枠。「テストを早くする」ではなく「テストの考える部分を早くする」。仕様の欠陥はコードになる前なら書き直しだけで済む。 -->
