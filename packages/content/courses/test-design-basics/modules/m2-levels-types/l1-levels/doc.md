# レッスン2-1 テストレベル

## このレッスンの目標

- [ ] テストレベルが「対象の大きさ」による区分であることを説明できる
- [ ] コンポーネント・統合・システム・受け入れの 4 レベルの目的を区別できる
- [ ] 目の前のテストがどのレベルの話かを判断できる

## 2-1-1 テストレベル

> **テストは対象の大きさごとに 4 つのレベルに分けて行う**

「会員登録の機能をテストしておいて」と頼まれたとき、どこから手をつけるでしょうか。画面から登録してみるのか、パスワードの判定をする関数に値を渡してみるのか。どちらもテストですが、確かめられることは同じではありません。

逆の失敗もあります。開発者がそれぞれ自分の担当ぶんを動かして確認したのに、つなげたら動かない。これは、誰もつなぎ目を見ていなかったということです。

そこで、何を 1 つのかたまりとして扱うかでテストを段階に分けます。これを **テストレベル** と呼びます。この講座では 4 つのレベルを扱います。

| レベル | 対象 | 会員登録での例 |
| --- | --- | --- |
| コンポーネント | 関数 1 つ | パスワードの文字数を判定する関数 |
| 統合 | 部品のつなぎ目 | フォーム → 会員登録 API |
| システム | 全体 | 登録して、初回注文まで通す |
| 受け入れ | 利用者の目的 | 業務として使い始めてよいか |

レベルが違えば、目的も、見つかる欠陥の種類も、担当する人も変わります。テストの話が噛み合わないときは、たいてい話し手と聞き手のレベルがずれています。以降の 4 トピックで、1 つずつ見ていきます。

## 2-1-2 コンポーネントテスト

> **関数やクラスの単位で、小さく速いテストを数多く回す**

画面から操作して確かめると、1 パターンあたり 3 分かかります。割引の計算が合わないとき、画面・API・データベースのどこが原因かも分かりません。

**コンポーネントテスト** は、単体で切り離せるモジュール 1 つを対象にするテストレベルです。料金計算 API の中にある割引額の計算関数だけを取り出して、値を渡し、戻り値を見ます。

| 入力(購入額, 会員区分) | 期待する割引額 |
| --- | --- |
| 1,000 / 一般 | 0 円 |
| 1,000 / 会員 | 100 円 |
| 0 / 会員 | 0 円 |

この形には 2 つの利点があります。1 つは速いことです。画面もデータベースも通らないので、1 件が一瞬で終わります。速いということは、数を打てるということです。もう 1 つは、失敗したときに疑う場所が狭いことです。落ちたのはこの関数なので、原因の切り分けが要りません。

表の 1 行が、そのままテストの 1 件に対応している点も覚えておいてください。この「表の行がテスト 1 件になる」形は、技法を扱うモジュールでずっと使い続けます。

## 2-1-3 統合テスト

> **部品どうしのつなぎ目に潜む欠陥は統合テストで狙う**

会員登録フォームも会員登録 API も、単体では正しく動いていました。それでも、つないだら生年月日が 1 日ずれて保存されていた。こういうことが起こります。

**統合テスト** は、2 つ以上の部品をつないだ状態を対象にするテストレベルです。コンポーネントテストが部品の中身を見るのに対して、統合テストは部品の間を見ます。

つなぎ目の欠陥は、多くが「約束の解釈違い」から生まれます。

| 型 | 会員登録での例 |
| --- | --- |
| 形式の食い違い | 日付を送る側は文字列、受ける側は時刻 |
| 単位の食い違い | 金額を送る側は円、受ける側は銭 |
| 想定外の値 | 任意項目が空のまま届く |
| 順序の前提ずれ | 保存前にメールが送信される |

どの例も、送る側だけを見ても、受ける側だけを見ても正しく見えます。両者の思っていた約束が違うので、つないだ瞬間に初めて表に出ます。だからこのレベルのテストは省けません。

## 2-1-4 システムテスト

> **システムテストは利用者の視点で全体の振る舞いを確かめる**

部品も、つなぎ目も、ひととおり確認は済んでいる。それでも「この画面から先に進めない」という報告が上がってくることがあります。部分の合格を積み上げても、通しの流れが成立するとは限らないからです。

**システムテスト** は、構築したシステム全体を、本番に近い環境で対象にするテストレベルです。ここで見る単位は「部品」ではなく「利用者がやりたいこと」に変わります。

| 手順 | 利用者がやること |
| --- | --- |
| 1 | 会員登録フォームから登録する |
| 2 | 届いたメールのリンクで有効化する |
| 3 | 商品を選び、料金と送料を確認する |
| 4 | 注文を確定し、確認メールを受け取る |

1 本のシナリオが複数の部品をまたぐので、ここで見つかる欠陥は「流れが途切れる」という形で現れます。有効化のリンクの期限が短すぎる、送料の表示と請求額が違う、といった具合です。品質の全体像が見えるのは、このレベルからです。

## 2-1-5 受け入れテスト

> **受け入れテストでは発注者や利用者が「使えるか」を判断する**

仕様書のとおりに動いているのに、「これでは業務が回らない」と言われることがあります。リリース直前に運用担当者から追加の要望が出てくるのも、同じ根を持つ話です。

**受け入れテスト** は、発注者や利用者が主体となり、受け取ってよいかを決めるテストレベルです。ほかの 3 レベルが「作ったものが正しいか」を見るのに対して、このレベルだけは「求めたものが届いたか」を見ます。

| | システムテスト | 受け入れテスト |
| --- | --- | --- |
| 主体 | 作る側 | 発注者・利用者 |
| 問い | 仕様どおりに動くか | 業務で使えるか |
| 結論 | 欠陥の一覧 | 受け取る / 受け取らない |

同じ画面で同じ操作をしても、判断の基準が違います。ここで出る指摘は、多くが欠陥ではなく「求めていたものとの差」です。品質の最終的な物差しは利用者の側にあるので、この差は仕様の書き方や、そもそもの要望の聞き方に返っていきます。

なお「受け入れてよいか」を判断するには、判断の条件が先に決まっている必要があります。その条件の書き方は、あとのモジュールで正面から扱います。

## もっと知りたい人へ

- レベルの数え方や名前は、現場や契約によって違います。「単体テスト」「結合テスト」「総合テスト」という呼び方もよく使われます。新しい現場に入ったら、その言葉が 4 レベルのどれを指しているかを確認してください
- 小さなチームでは、統合テストとシステムテストの境目があいまいなこともあります。大事なのは名前ではなく、「つなぎ目」と「通しの流れ」の両方を誰かが見ているかどうかです
