対象トピック: 6-1-1 〜 6-1-4

このレッスンの演習が、この講座の総合演習です。新しい技法は出てきません。モジュール1からモジュール5までの道具を総動員して、**成果物 4 点**を作り切ります。

| # | 成果物 | 使う道具 |
| --- | --- | --- |
| ① | テスト観点一覧 | 仕様の読み方・チェックリスト・プロダクトリスク |
| ② | 技法割当表 | 同値分割 / 境界値分析 / デシジョンテーブル / 状態遷移 / 探索的テスト |
| ③ | pytest のテストスイート | `parametrize` / `assert` / `pytest.raises` |
| ④ | 自動化提案書(1 枚) | テストレベル・テストピラミッド・保守コスト |

## 手元で試す

### 案件の仕様書(全文)

この仕様書が、成果物 4 点すべての入力です。ここに書かれていないことは「仕様が決まっていない」と扱ってください。

> **案件**: オンラインストアのリニューアル。会員登録フォームと料金計算 API が対象。
>
> **1. 会員登録フォーム**
>
> - 入力はメールアドレス・パスワード・生年月日の 3 つ。
> - メールアドレスは `@` を 1 つ以上含む 1 文字以上 254 文字以下。範囲外・`@` 無しはエラー。
> - パスワードは 8 文字以上 32 文字以下。範囲外はエラー。
> - 生年月日から算出した年齢が 18 歳以上のときだけ登録できる。誕生日当日は 18 歳とみなす。
> - 登録に成功した会員の会員区分は「一般」で始まる。
>
> **2. 料金計算 API**
>
> - 入力は購入額・会員区分(一般 / プレミアム)・クーポン(有効なクーポンを持つか)。
> - 購入額は 1 円以上の整数。0 円以下、または整数でないときはエラー。
> - 割引率は、プレミアム会員なら 10%。有効なクーポンがあればさらに 5% を足す。
> - 割引額 = 購入額 × 割引率(1 円未満は切り捨て)。割引後の金額 = 購入額 − 割引額。
> - 送料は 500 円。ただし **割引後の金額** が 3,000 円以上なら 0 円。
> - 請求額 = 割引後の金額 + 送料。
>
> **3. 注文ステータス**
>
> - 注文のステータスは 受付 / 支払済 / 発送済 / キャンセル の 4 つ。新しい注文は受付から始まる。
> - 受付の注文は「支払う」で支払済に、「キャンセルする」でキャンセルになる。
> - 支払済の注文は「発送する」で発送済に、「キャンセルする」でキャンセルになる。
> - 発送済とキャンセルの注文には、どの操作もできない。
>
> **4. 非機能とプロジェクトの制約**
>
> - 料金計算 API の応答は 1 秒以内。
> - リリースは 3 週間後。テスト期間は 5 営業日、担当は 2 名。
> - 会員登録フォームは前回リリースから変更なし。**クーポンの機能は今回の新規実装**。
> - 注文ステータスは去年 2 件の障害を出している。

### 実装を手元に置く

作業用のフォルダを 1 つ作り、次のファイルを置いてください。成果物③ でテストを書く相手です。

```python
# store.py
def register(email, password, birth_date, today):
    if "@" not in email or not 1 <= len(email) <= 254:
        raise ValueError("メールアドレスが不正です")
    if not 8 <= len(password) <= 32:
        raise ValueError("パスワードは 8 文字以上 32 文字以下です")
    age = today.year - birth_date.year
    if (today.month, today.day) < (birth_date.month, birth_date.day):
        age -= 1
    if age < 18:
        raise ValueError("18 歳以上のみ登録できます")
    return {"email": email, "rank": "一般"}


def billing(total, rank, has_valid_coupon):
    if not isinstance(total, int) or total < 1:
        raise ValueError("購入額は 1 円以上の整数です")
    rate = 10 if rank == "プレミアム" else 0
    if has_valid_coupon:
        rate += 5
    discounted = total - total * rate // 100
    shipping = 0 if discounted >= 3000 else 500
    return {"discounted": discounted, "shipping": shipping, "amount": discounted + shipping}


class Order:
    TRANSITIONS = {
        ("受付", "支払う"): "支払済",
        ("受付", "キャンセルする"): "キャンセル",
        ("支払済", "発送する"): "発送済",
        ("支払済", "キャンセルする"): "キャンセル",
    }

    def __init__(self):
        self.status = "受付"

    def handle(self, event):
        key = (self.status, event)
        if key not in self.TRANSITIONS:
            raise ValueError(f"{self.status} では {event} はできません")
        self.status = self.TRANSITIONS[key]
        return self.status
```

置けたら、同じフォルダで 1 行だけ確認しておきます。

```bash
python -c "from store import billing; print(billing(3000, '一般', True))"
```

`{'discounted': 2850, 'shipping': 500, 'amount': 3350}` と出れば準備完了です。**購入額 3,000 円なのに送料が無料になっていない**ことに気づいたかもしれません。これは欠陥ではなく仕様です(判定は割引後の金額)。この「気づき」が、成果物① に書く 1 行になります。

## 演習問題

### 問1(基本)— 成果物① テスト観点一覧

仕様書から、テスト観点を 12 行以上書き出してください。値は書きません。

| # | 対象 | 観点 |
| --- | --- | --- |
| 1 | 会員登録フォーム | |
| 2 | | |
| … | | |

書けたら、次の 4 つで見直してください。

- 「会員登録」のような、粗すぎて技法が決まらない行はありませんか
- 「パスワードが 7 文字ならエラー」のような、値まで書いた行はありませんか(それはケースです)
- 非機能の観点(応答時間)が 1 行以上ありますか
- 仕様書に書かれていない箇所への疑問が、1 行以上ありますか

### 問2(基本)— 成果物② 技法割当表

問1 の一覧に 3 列足して、技法割当表にしてください。リスクは 高 / 中 / 低 の 3 段階です。

| # | 観点 | リスク | 技法 | 根拠 |
| --- | --- | --- | --- | --- |
| 1 | | | | |

- リスクの根拠には、仕様書の「4. 非機能とプロジェクトの制約」を使ってください
- 「高」を付けた行には、原則として技法を 2 つ以上重ねてください。式が単純である、1 つの技法で必要な範囲を押さえ切れる、といった理由があれば 1 つでも構いません。その場合は、なぜ 1 つで足りるかを根拠の列に添えてください
- 根拠の列が空の行を残さないでください

### 問3(応用)— 成果物③ pytest のテストスイート

問2 で選んだ技法どおりにケース表を作り、`test_store.py` に写して実行してください。

守るのは 3 つです。

1. **観点 1 つ = テスト関数 1 つ**。関数の上に `# 観点N: ...` のコメントを置く
2. **ケース表の 1 行 = `parametrize` の 1 組**。組のコメントに技法上の位置づけ(境界の内側 / R4 など)を書く
3. **注文ステータスは、有効な遷移 4 本と無効な遷移 8 マスの両方**を入れる

エラーになる入力は `pytest.raises` で確かめます。

```python
with pytest.raises(ValueError):
    billing(0, "一般", False)
```

実行して全件が緑になったら、次の 3 つの改造で「落ちること」も確かめてください(確かめたら戻します)。

1. `store.py` の送料の判定を `discounted > 3000` に書き換える → 送料の境界のケースだけが落ちるか
2. `rate += 5` を `rate = 5` に書き換える → デシジョンテーブルのどのルールが落ちるか
3. `TRANSITIONS` に `("発送済", "キャンセルする"): "キャンセル"` を足す → 無効な遷移のケースが落ちるか

3 つとも「落ちるべきものだけが落ちる」なら、スイートが観点をきちんと押さえている証拠です。落ちなかった改造があれば、その観点のケースが足りていません。

### 問4(応用)— 成果物④ 自動化提案書(1 枚)

問3 のスイートをもとに、自動化提案書を 1 枚にまとめてください。次の 5 つの見出しをすべて埋めます。

| 見出し | 書くこと |
| --- | --- |
| 目的 | 何のために自動化するか。時間の数字で書く |
| 自動化する対象 | 対象 / テストレベル / 根拠 / 工数 の表 |
| **自動化しないこと** | 対象と、やらない根拠 |
| 効果 | 投資(人日)と回収(時間 / 月) |
| 前提とリスク | この提案が崩れる条件 |

- 「自動化率」を目標に置かないでください
- 「順次拡大」という言葉を使わないでください
- 対象の行は、同じ確認ができるなら低いテストレベルを選んでください

- **9(切り捨て)** — 「1 円未満は切り捨て」は 1 行しかない文ですが、割引後の金額と請求額の両方に効きます
- **10(割引後で判定)** — 仕様の中でいちばん間違えやすい箇所です。「3,000 円以上で送料無料」を購入額で判定する実装が自然に見えてしまいます

16 の行は、仕様書のどの文からも出てきません。チェックリストベースドテストの定番を、2 周目で足したものです。仕様書を 1 周しただけでは、この行は出ません。

| # | 観点 | リスク | 技法 | 根拠 |
| --- | --- | --- | --- | --- |
| 1 | メールアドレスの形式 | 低 | 同値分割 | 変更なし。有効 / 無効の 2 グループで足りる |
| 2 | メールアドレスの長さ | 低 | 境界値分析(2 値) | 1〜254 という範囲の仕様 |
| 3 | パスワードの長さ | 中 | 境界値分析(3 値) | 8〜32 という範囲。上限・下限の 2 か所 |
| 4 | 登録できる年齢の下限 | 中 | 境界値分析(2 値) | 18 歳という境界が 1 か所 |
| 5 | 誕生日当日の扱い | 中 | 境界値分析(2 値) | 「当日は 18 歳」の解釈違いが起きやすい |
| 7 | 購入額の有効・無効 | 中 | 同値分割(無効パーティション) | 0・負数・非整数の 3 グループ |
| 8 | 割引率の決まり方 | 高 | デシジョンテーブル + 探索 15 分 | 会員区分 × クーポンの 2 条件。クーポンは新規実装 |
| 9 | 1 円未満の切り捨て | 中 | 境界値分析(3 値) | 端数が出る購入額の周辺で確かめる |
| 10 | 送料無料の判定 | 高 | 境界値分析(3 値) + 探索 30 分 | 割引後で判定するため、会員区分ごとに境界が動く |
| 11 | 請求額の合計 | 高 | 同値分割(代表値 1 件) | 過大請求は影響が大。ただし式は足し算 1 つなので、技法 1 つ・1 件で足りる |
| 12 | 応答時間 | 中 | 非機能テスト(1 秒の基準で測る) | 1 秒以内という数値の基準がある |
| 13 | 有効な遷移 | 高 | 状態遷移(遷移カバレッジ 100%) | 去年 2 件の障害。発送事故は影響が大。状態遷移表 1 枚で 12 マスを押さえ切れるので技法は 1 つ |
| 14 | 無効な遷移 | 高 | 状態遷移(状態遷移表の「−」8 マス) | 図の矢印だけでは 1 つも試されない。観点13 と同じ表から出るので技法は 1 つ |
| 16 | 空・0・負数・長すぎ | 中 | チェックリストベースドテスト | 仕様書に文が無く、系統的技法では出ない |

**解説**

リスクの根拠は、仕様書の「4. 制約」から引いています。

- **クーポンは新規実装** → 観点8 と 10 の起きやすさが上がる
- **注文ステータスは去年 2 件の障害** → 欠陥は少数のモジュールに集中するので、観点13・14 の起きやすさが高い
- **会員登録フォームは変更なし** → 観点1・2 は低リスク。ケースは薄くてよい

観点10 の技法に注目してください。境界値分析を選んだ根拠が「範囲の仕様だから」だけでなく、「**割引後**で判定するため境界が動く」まで書いてあります。ここまで書いてあると、ケースを作るときに「会員区分ごとに境界を計算し直す」ことを忘れません。根拠の列は、あとの自分への申し送りでもあります。

「高」の 5 行のうち、技法を 2 つ重ねたのは観点8 と 10 だけです。残りの 3 行が 1 つで済む理由は、それぞれ違います。

- **観点11** — リスクは高いが、式が足し算 1 つで単純だから。**リスクの高さは自動的にケース数の多さにはなりません**。厚みは「リスク × 仕様の複雑さ」で決めます
- **観点13・14** — 状態遷移という 1 つの技法で、有効な遷移 4 本と無効な遷移 8 マスの両方を押さえ切れるから。技法は 1 つでも、そこから出るケースは 12 件です

**技法の数と厚みは別物**です。「高だから 2 つ重ねる」を機械的に適用すると、意味のない技法が 1 つ増えるだけになります。1 つで足りると判断したなら、その理由を根拠の列に残してください。

観点6・15 は解答例では表から落としています。他の観点のケースを実行すれば必ず通る道なので、専用のケースを立てませんでした。この「立てない」判断も、表に残すか、消す理由を 1 行書いておくのが親切です。

# test_store.py
from datetime import date

import pytest

from store import Order, billing, register

TODAY = date(2026, 4, 1)


# 観点3: パスワードの長さ(境界値分析 / 3 値)
@pytest.mark.parametrize("password, ok", [
    ("a" * 7, False),   # 8 文字の境界の外側
    ("a" * 8, True),    # 8 文字の境界
    ("a" * 9, True),    # 8 文字の境界の内側
    ("a" * 32, True),   # 32 文字の境界
    ("a" * 33, False),  # 32 文字の境界の外側
])
def test_password_length(password, ok):
    args = ("user@example.com", password, date(2000, 1, 1), TODAY)
    if ok:
        assert register(*args)["rank"] == "一般"
    else:
        with pytest.raises(ValueError):
            register(*args)


# 観点4・5: 登録できる年齢の下限(境界値分析 / 2 値)
@pytest.mark.parametrize("birth_date, ok", [
    (date(2008, 4, 2), False),  # 18 歳の境界の外側(誕生日の前日)
    (date(2008, 4, 1), True),   # 18 歳の境界(誕生日当日)
])
def test_registration_age(birth_date, ok):
    args = ("user@example.com", "password1", birth_date, TODAY)
    if ok:
        assert register(*args)["email"] == "user@example.com"
    else:
        with pytest.raises(ValueError):
            register(*args)


# 観点1・2: メールアドレス(同値分割 / 無効同値パーティション)
@pytest.mark.parametrize("email", ["userexample.com", "", "a" * 250 + "@b.com"])
def test_invalid_email_is_rejected(email):

        register(email, "password1", date(2000, 1, 1), TODAY)


# 観点8: 割引率の決まり方(デシジョンテーブル / ルール 1 列 = 1 ケース)
@pytest.mark.parametrize("rank, coupon, discounted", [
    ("一般", False, 3000),        # R1: 割引なし
    ("一般", True, 2850),         # R2: クーポン 5%
    ("プレミアム", False, 2700),   # R3: 会員 10%
    ("プレミアム", True, 2550),    # R4: 会員 10% + クーポン 5%
])
def test_discount_rules(rank, coupon, discounted):
    assert billing(3000, rank, coupon)["discounted"] == discounted


# 観点10: 送料無料の判定(境界値分析 / 判定は「割引後」の金額)
@pytest.mark.parametrize("total, rank, coupon, shipping", [
    (2999, "一般", False, 500),        # 境界の外側
    (3000, "一般", False, 0),          # 境界
    (3000, "一般", True, 500),         # 割引後 2,850 円: 割引で境界を割る
    (3528, "プレミアム", True, 500),    # 割引後 2,999 円: 境界の外側
    (3529, "プレミアム", True, 0),      # 割引後 3,000 円: 境界
])
def test_shipping_boundary(total, rank, coupon, shipping):
    assert billing(total, rank, coupon)["shipping"] == shipping


# 観点11: 請求額 = 割引後 + 送料
def test_amount_is_discounted_plus_shipping():
    result = billing(3000, "プレミアム", True)
    assert result["amount"] == result["discounted"] + result["shipping"]


# 観点7・16: 購入額の無効同値パーティション
@pytest.mark.parametrize("total", [0, -1, "3000"])
def test_invalid_total_is_rejected(total):
    with pytest.raises(ValueError):
        billing(total, "一般", False)


def run(events):
    order = Order()
    for event in events:
        order.handle(event)
    return order

読むところは 4 か所です。

**1. 送料の境界が 2 つある** — `(3000, "一般", False, 0)` と `(3529, "プレミアム", True, 0)` です。判定が割引後の金額なので、割引率が変わると境界の入力値が動きます。プレミアム + クーポンは 15% 引きなので、割引後 3,000 円になるのは購入額 3,529 円のときです(3,529 − 529 = 3,000)。技法割当表の根拠に「境界が動く」と書いておいたから、この 2 行が出てきます。

**2. 一番怖い行は `(3000, "一般", True, 500)`** — 購入額 3,000 円でクーポンを使うと、割引後が 2,850 円になって送料が発生します。「送料無料にするためにクーポンを使ったら、かえって高くなった」という利用者の体験です。仕様どおりなのでテストは緑ですが、**この行は仕様への疑問として提案書に載せる価値があります**。テストの仕事は欠陥を見つけることだけではありません。

**4. 関数の上のコメントが観点番号** — `# 観点10:` があるので、技法割当表の 10 行目とコードが結び付きます。仕様が変わって表の 10 行目を直したとき、コードのどこを直せばよいか、検索 1 回で分かります。

### Q4. テスト担当者が「ブランチカバレッジ 100% を達成したので、欠陥はもうありません」と報告しました。この報告の問題点はどれですか。
