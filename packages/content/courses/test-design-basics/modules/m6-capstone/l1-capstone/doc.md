# レッスン6-1 仮想案件で通しでやる

## このレッスンの目標

- [ ] 仕様書から、粒度のそろったテスト観点の一覧を作れる
- [ ] 観点ごとに技法とリスクを割り当て、根拠を書き残せる
- [ ] ケース表を pytest のテストスイートに写し、自動化提案書 1 枚にまとめられる

このレッスンは総合演習です。新しい技法は出てきません。モジュール1からモジュール5までで身に付けた語彙と道具を、1 つの案件に総動員して、成果物 4 点を作り切ることが目標です。

題材はモジュール2から使ってきたオンラインストアです。仕様書の全文と課題は [practice.md](practice.md) にあります。

## 6-1-1 テスト観点出し

> **仕様を読んだら、ケースを書く前に「何をテストすべきか」の観点一覧を作る**

仕様書を渡され、いきなりケース表を書き始めたとします。送料の境界値は 12 件そろいました。しかし、パスワードの長さを 1 件も見ていません。レビューで「なぜ料金計算だけこんなに厚いのですか」と聞かれ、答えられない。よくある詰まり方です。

原因は、書きやすいところから書いたことにあります。ケース表は縦に長くなるので、書いている本人からは全体の形が見えません。見えないものは、偏っていても気づけません。

**テスト観点** は、「どこの、何を確かめるか」を 1 行で表した、ケースより粗い単位です。

- 観点は**値を持ちません**。「パスワードの長さ」までで、「7 文字ならエラー」はまだ書きません
- 観点は 1 行から技法が 1 つ決まる粒度にします
- 機能・非機能を問わず、同じ一覧に並べます

一覧が先にあると、抜けが「行が無いこと」として目に見えます。ケース表が 100 行になっても、観点一覧は 20 行程度に収まるので、俯瞰できるのです。

案件の仕様は、この 1 枚で通します。

| 対象 | 仕様 |
| --- | --- |
| 会員登録フォーム | メール(`@` を含む 1〜254 文字)/ パスワード(8〜32 文字)/ 生年月日(18 歳以上) |
| 料金計算 API | 購入額(1 円以上の整数)・会員区分(一般 / プレミアム)・クーポン(あり / なし) |
| 割引と送料 | プレミアムは 10%、有効クーポンで +5%。**割引後**が 3,000 円以上なら送料 0 円、未満は 500 円 |
| 注文ステータス | 受付 / 支払済 / 発送済 / キャンセル の 4 状態 |
| 制約 | 応答 1 秒以内 / テスト期間 5 営業日・2 名 / クーポンは今回の新規実装 |

粒度がそろっているかは、次の 4 つで見分けます。

| 書き方 | 良し悪し |
| --- | --- |
| パスワードの長さ | ○ 場所と性質がある |
| 会員登録 | × 粗すぎて技法が決まらない |
| パスワードが 7 文字ならエラー | × それはもうテストケース |
| 料金計算 API の応答時間 | ○ 非機能の観点も同じ列に並べる |

粗すぎる行は割り、細かすぎる行はまとめます。判断に迷ったら「この 1 行から技法が 1 つ決まるか」を試してください。決まらなければ粗すぎ、技法を通り越して値まで書けていれば細かすぎです。

観点を出す材料は、仕様書の文だけではありません。プロダクトリスクの高い場所、過去に欠陥が出た場所、チェックリストの定番(空・0・負数・重複・長すぎ)も観点の出どころになります。仕様書を 1 周したあと、この 3 つで 2 周目を回すと、たいてい 3〜5 行増えます。

## 6-1-2 技法の割り当て

> **観点ごとに使う技法を選び、選んだ根拠を書き残す**

観点一覧が 12 行そろい、上から順にケースを書き始めたとします。得意な境界値分析ばかり当ててしまい、条件の組み合わせを見るケースが 1 件もない。そして半年後に仕様が変わったとき、どの行を作り直せばよいか分かりません。

技法の選択が頭の中にしかないと、他人も未来の自分も引き継げません。だから表に書きます。

選ぶ手がかりは 2 つです。

- **仕様の形** — 範囲なら境界値分析、条件の絡みならデシジョンテーブル、状態があれば状態遷移
- **リスクレベル** — 高い行には技法を重ね、低い行は代表値 1 件で止める

観点一覧に 3 列足すだけで、技法割当表になります。

| 観点 | リスク | 技法 | 根拠 |
| --- | --- | --- | --- |
| パスワードの長さ | 中 | 境界値分析(3 値) | 8〜32 という範囲の仕様だから |
| 割引率の決まり方 | 高 | デシジョンテーブル | 会員区分 × クーポンの 2 条件が絡むから |
| 送料無料の判定 | 高 | 境界値分析 + 探索 30 分 | 割引後で判定するため境界が動く。今回の新規実装 |
| 注文ステータスの遷移 | 高 | 状態遷移 | 同じ操作でも状態で結果が変わるから |
| お知らせの表示順 | 低 | 同値分割(代表値 1 件) | 壊れても影響が小さいから |

根拠の列が埋まらない行は、まだ仕様を読み切れていない行です。「なんとなく境界値」と書きそうになったら、仕様書に戻ってください。範囲を表す文がどこにも無ければ、その観点に境界値分析は当たりません。

根拠を書くのは 1 行 10 秒ですが、寿命はケースの値よりずっと長く残ります。

| | 根拠なし | 根拠あり |
| --- | --- | --- |
| 仕様変更のとき | 全行を読み直す | 変わった仕様の行だけ直す |
| レビューで聞かれたら | 記憶を頼りに答える | 表を指して答える |
| 引き継ぎ | 口頭説明が要る | 表を渡せば済む |

1 つの観点に技法を 2 つ重ねてよいことも、あらためて確認しておきます。「送料無料の判定」に境界値分析と探索を両方当てているのは、リスクが高いからです。厚みの配分そのものが設計であり、薄くする判断も、根拠を書けば立派な設計です。

## 6-1-3 ケース表からテストスイートへ

> **ケース表を parametrize に写すと、そのままリグレッション資産になる**

技法ごとにケース表を 4 枚作り、表計算ソフトに保存しました。リリースのたびに 34 件を手で流し、毎回 2 時間かかります。3 か月後には、表と実装のどちらが正しいのか誰も分からなくなります。

表のままでは、置いた瞬間から古くなっていきます。**テストスイート** は、まとめて実行されるテストのひとかたまりです。表をここへ写すと、変更のたびに全件が自動で流れるようになります。

写すときの対応は、最初に決めて最後まで崩さないでください。

| 設計 | コード |
| --- | --- |
| 観点 1 つ | テスト関数 1 つ |
| ケース表の 1 行 | `parametrize` の 1 組 |
| 技法上の位置づけ | 組のコメント |

```python
# 観点4: 割引率の決まり方(デシジョンテーブル)
@pytest.mark.parametrize("rank, coupon, discounted", [
    ("一般", False, 3000),        # R1: 割引なし
    ("プレミアム", True, 2550),    # R4: 会員 10% + クーポン 5%
])
def test_discount_rules(rank, coupon, discounted):
    assert billing(3000, rank, coupon)["discounted"] == discounted
```

関数名の上のコメントが観点、組のコメントが技法上の位置づけです。この 2 種類のコメントがあれば、表計算ソフトの表を捨てても、設計にたどり着けます。「なぜこの値なのか」がコードに残っている状態です。

写す価値は、実行の速さだけではありません。

| | 表計算ソフトの表 | テストスイート |
| --- | --- | --- |
| 実行 | 人が 2 時間 | 機械が数秒 |
| 変更のたび | 流さない回が出る | 毎回全件 |
| 仕様変更に気づく | 気づかない | 落ちて教えてくれる |
| 観点との対応 | 表の題名 | 関数名とコメント |

3 行目が本題です。仕様が変わったのに表を直し忘れると、表は静かに嘘になります。スイートなら、その嘘は次の実行で赤くなって表に出ます。リグレッションテストが自動で毎回流れる状態は、設計の鮮度が保たれる状態でもあるのです。

なお、全部を写す必要はありません。「見た目が崩れていないか」のように合否を人が目で決める観点は、写しても壊れやすいだけです。何を写して何を写さないかを決めるのが、次のトピックです。

## 6-1-4 自動化提案書

> **「何をどのレベルで自動化するか」を、根拠つきの 1 枚にまとめて提案する**

スイートが動くようになり、「自動化を広げましょう」と提案しました。「工数は」「どこまでやるのか」と聞かれ、その場で答えられません。提案は保留になり、手で流す 2 時間は来月も続きます。

良い設計をしても、判断する人に届かなければ何も変わりません。**自動化提案書** は、対象・テストレベル・根拠・やらないことを 1 枚に収めた文書です。読み手は「やる / やらない」を決めたい人なので、1 枚に収めます。

提案の本体は 5 行程度で足ります。

| 対象 | レベル | 根拠 | 工数 |
| --- | --- | --- | --- |
| 割引率・送料の計算 | コンポーネント | 高リスク・毎回流す・値で比較できる | 2 日 |
| 注文ステータスの遷移 | コンポーネント | 高リスク・無効遷移 8 件が手では漏れる | 1 日 |
| 登録 → 注文 → 請求の 1 本道 | 統合 | つなぎ目の欠陥は単体では出ない | 2 日 |
| 画面の見た目・表示位置 | **やらない** | 合否を人が目で決める。E2E は保守コストが高い | — |
| 未知の欠陥探し | **やらない** | 探索的テストで人が担う。45 分 / リリース | — |

上の 3 行がテストピラミッドの下側に寄っていることを確かめてください。E2E に寄せると保守コストが跳ね上がるので、同じ確認ができるなら低いレベルを選びます。

そして、**「やらないこと」を書くのが要点**です。範囲が閉じていない提案は決裁できません。「順次拡大していきます」と書かれた提案は、読み手から見ると終わりの見えない約束です。やらないと決めた行に根拠が添えてあれば、それは手抜きではなく設計だと伝わります。

通らない提案と通る提案の差は、だいたいこの 4 点に出ます。

| | 通らない | 通る |
| --- | --- | --- |
| 目標 | 「自動化率 80%」 | 「手で流す 2 時間を 10 分に」 |
| 範囲 | 「順次拡大」 | 「この 3 つ。他はやらない」 |
| 根拠 | 「品質が上がるので」 | リスクレベルと実行頻度 |
| 効果 | 書いていない | 5 日投資 → 月 16 時間回収 |

左の列はどれも、読み手が判断できない書き方です。「自動化率」を目標に置くと、保守コストの高いテストまで書いてしまいます。数えるなら本数ではなく、手で流す時間がどれだけ減るかを数えてください。

最後に、この講座の最初の 1 文に戻ります。テストはソフトウェアの品質に関する情報を関係者に届ける活動でした。観点一覧・技法割当表・テストスイート・自動化提案書という 4 点の成果物は、その「届ける」の具体的な形です。ケースを書く技術と、それを届ける文書は、どちらが欠けても仕事になりません。

## もっと知りたい人へ

- `pytest.mark.parametrize` の `ids` を使うと、実行結果に `R4` のような名前を表示できます。観点との対応をさらに強く残せます — [pytest 公式ドキュメント](https://docs.pytest.org/en/stable/how-to/parametrize.html)
- 観点一覧は、案件が変わっても 6〜7 割は使い回せます。作った一覧を個人のチェックリストとして育てると、2 案件目からの立ち上がりが速くなります
- 自動化提案書は、3 か月後に振り返ると学びが多い文書です。見積もった工数と実際、回収できた時間を突き合わせると、次の提案の精度が上がります
