# レッスン4-2 経験ベースの技法

## このレッスンの目標

- [ ] エラー推測を頭の中ではなくケース表の行として書ける
- [ ] チェックリストの定番 5 観点を、担当する機能に当てはめられる
- [ ] 探索的テストをチャーターの形で計画できる

## 4-2-1 エラー推測

> **「ここが壊れやすい」という経験を、明示的にテストケースへ変えるのがエラー推測である**

同値分割・境界値分析・デシジョンテーブル・状態遷移を全部当てて、30 件のケース表を作りました。ベテランが表を眺めて一言、「登録済みのメールでもう一度登録したら?」。表のどこにも、その行はありません。仕様書にも書かれていないからです。

**エラー推測** は、過去の欠陥や勘所から、壊れそうな入力を狙ってケースにする技法です。仕様や構造ではなく人の経験を出発点にする技法をまとめて **経験ベースの技法** と呼び、エラー推測はその代表です。

要点は「明示的に」の一語です。ベテランが触りながら勘で見つけるのは、再現も引き継ぎもできません。ケース表の行にして初めて、技法として扱えます。

| 過去の経験 | 推測した入力 | 期待結果 |
| --- | --- | --- |
| 二重登録の考慮漏れが多い | 登録済みのメールで再登録 | エラー |
| 全角・半角の変換漏れ | 全角の `＠` を含むメール | エラー |
| 前後の空白の扱いが決まっていない | 先頭に空白のあるメール | 空白を除いて登録 |

3 行とも仕様書には書かれていません。書かれていないから実装も漏れます。そして、書かれていない以上、仕様から作る技法では絶対に出てきません。

系統的な技法との関係を整理しておきます。

| | 系統的な技法 | エラー推測 |
| --- | --- | --- |
| 出発点 | 仕様・コード | 過去の欠陥・勘 |
| 再現性 | 誰がやっても同じ表 | 人によって変わる |
| 網羅の説明 | できる | できない |
| 強み | 漏れがない | 表の外を突ける |

優劣ではなく役割の違いです。エラー推測は網羅を説明できないので、これ単独では使いません。この位置づけは 4-2-4 でもう一度まとめます。

## 4-2-2 チェックリストベースドテスト

> **壊れやすい入力の定番(空・0・負数・重複・長すぎ)はチェックリストで漏れを防ぐ**

エラー推測には弱点があります。人によって出てくる量が違うことです。経験の浅い人は「何を疑えばいいか」がそもそも出てきません。そしてベテランの勘は、その人が抜けた瞬間に消えます。属人的なままでは、チームの品質が人の入れ替わりで上下します。

**チェックリスト** は、過去の欠陥から作った、毎回あてる観点の一覧です。経験を個人の勘から、チームの資産に変える道具だと考えてください。使い方は簡単で、ケース表を書き終えたあとに上から順に当てて、漏れている行を足します。

まず覚えるのは次の 5 つです。入力を扱うあらゆる機能に当たります。

| 観点 | 会員登録フォーム | 送料計算 |
| --- | --- | --- |
| 空 | メールを空で送信 | 購入額が未入力 |
| 0 | (該当なし) | 購入額 0 円 |
| 負数 | (該当なし) | 購入額 -1 円 |
| 重複 | 登録済みメールで再登録 | 同じ商品を 2 回入れる |
| 長すぎ | 300 文字のメール | 購入額 10 億円 |

「該当なし」の欄を空欄にせず書いているところに注目してください。空欄だと、見落としたのか、当てて外したのかが区別できません。当てた記録を残すのが、チェックリストの半分の価値です。

リストは固定の正解表ではありません。育てるものです。

- 出た欠陥は毎回リストに足す。足さないリストは育たない
- 定番 5 つはあくまで出発点。扱うドメイン固有の観点(日付をまたぐ、通貨が混ざる、など)を継ぎ足す
- 同じリストだけを当て続けると殺虫剤のパラドックスに当たる。定期的に見直す

## 4-2-3 探索的テスト

> **探索的テストは、テストしながら学び、次のテストを設計する進め方である**

ケース表どおりに 30 件を実行し、全部通りました。実行中に「戻るボタンで前の画面に戻ったらどうなる?」と思ったのですが、表に無いので飛ばしました。リリース後、まさにそこで注文が二重に入りました。

手を動かしている人の頭には、表に無い問いが浮かびます。それを捨てるのはもったいない。**探索的テスト** は、設計・実行・学習を同時に、短い周期で回すやり方です。1 件試して分かったことが、次の 1 件を決めます。

ただし、行き当たりばったりとは違います。事前に決めるのは、ケースの中身ではなく **目的と時間** です。これを 1〜3 行にまとめたものを **テストチャーター** と呼びます。

| 項目 | 例 |
| --- | --- |
| 対象 | 会員登録フォーム |
| 目的 | 異常な入力でエラー画面や二重登録が起きないか |
| 時間 | 45 分 |
| 記録 | 試した操作と気づきをメモに残す |

この 4 行があると、報告のときに「何を、どこまでやったか」が説明できます。逆に、目的も時間も決めずに触っているだけなら、それは探索的テストではありません。

台本どおりの実行と比べます。

| | ケース表どおりの実行 | 探索的テスト |
| --- | --- | --- |
| 事前に決める | ケースの中身 | 目的と時間 |
| 得意なこと | 既知の確認・自動テスト化 | 未知の発見 |
| 再実行 | 同じことができる | 同じにはならない |
| 残るもの | ケース表 | メモとチャーター |

再実行できないのが探索的テストの性質です。だから、見つけた欠陥はケース表に足して資産にします。探索は発見器、ケース表は保管庫、と役割を分けてください。

## 4-2-4 経験ベースの位置づけ

> **経験ベースの技法は、系統的な技法の網から漏れた欠陥を拾う補完役である**

現場では「ケース表を作る人」と「触って見つける人」が別々に語られがちです。どちらが偉いかの話になり、順番の基準が置かれません。経験ベースだけで進めたチームは、報告の場で「何をテストしたか」を答えられませんでした。

順番は決まっています。

- 先に系統的な技法で網を張る(説明できる網羅ができる)
- そのうえで経験ベースを重ねる(網の外を突く)
- 逆にすると、何を試したかを説明できなくなる

補完役という言葉は「おまけ」という意味ではありません。網の外は必ずあるので、必須の一手です。送料計算に 3 段で当てると、次のようになります。

| 順番 | 手立て | 出てくるもの |
| --- | --- | --- |
| 1 | 同値分割・境界値分析 | 仕様の範囲を埋めるケース表(4 件) |
| 2 | チェックリスト | 空・0・負数・重複・長すぎの追加行(3 件) |
| 3 | 探索的テスト(45 分) | 表の外にある想定外 |

1 と 2 は表に残ります。3 で見つけたものも、表に足して初めて資産になります。

片方だけに頼るとどうなるかを、並べておきます。

| | 系統的な技法だけ | 経験ベースだけ |
| --- | --- | --- |
| 弱点 | 仕様に無い欠陥が残る | 網羅を説明できない |
| 品質のばらつき | 小さい | 人が変わると変わる |
| 資産 | リグレッションテストに残る | 再実行できない |

前のレッスンのカバレッジも同じ構図でした。測る道具(カバレッジ)と作る技法、系統と経験。どれも一方だけでは足りません。テストは重ねて使うものだ、というのがモジュール3から一貫した話です。

## もっと知りたい人へ

- チェックリストは、自分の担当するドメインの言葉で書き直すほど効きます。「空・0・負数・重複・長すぎ」を出発点に、自分の 10 行を作ってみてください
- 探索的テストの時間の区切り方(セッション)や記録の残し方には、いくつも流儀があります。まずは 45 分・メモ 1 枚から始めるので十分です
- 探索的テストと自動テストの役割分担は、モジュール5の「人に残すテスト」でもう一度扱います
