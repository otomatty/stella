# 4-3-3
# ATDD

テスト設計入門研修 — Module 4 / レッスン4-3

<!-- ノート: シフトレフトを、いちばん左まで押し切った形です。 -->

## なぜ必要か

- 受け入れ基準は書いたが、読み返すのは実装が終わってから
- 実装者は基準を見ずに作り、あとから食い違いが出る
- 「そこは対象外だと思っていた」が、リリース直前に判明する

<!-- ノート: つかみ。基準を書いただけでは、読まれるタイミングが遅いままです。 -->

---

## 結論

**ATDD は受け入れテストを先に書き、それを満たすように実装する進め方である**

- **ATDD** — 受け入れテストを実装より前に書く進め方
- 最初は必ず落ちる。その落ちるテストが「完成の定義」になる
- 食い違いが着手前に出るので、直すのは文章 1 行で済む

<!-- ノート: 結論を言い切る。テストを先に書くと、仕様の曖昧さがその場で見つかります。書けなければ、決まっていないということです。 -->

---

## 受け入れ基準をそのままテストに

```python
# test_acceptance.py — 実装より先に書く
import pytest
from shipping import shipping_fee

@pytest.mark.parametrize("total, expected", [
    (3000, 0),     # 受け入れ基準 1
    (2999, 500),   # 受け入れ基準 2
])
def test_shipping_fee(total, expected):
    assert shipping_fee(total) == expected
```

<!-- ノート: コードの枠。この時点で `shipping.py` はまだありません。実行すると import で落ちます。それが出発点です。 -->

## 先に書く場合と、あとで書く場合

| | 先に書く(ATDD) | あとで書く |
| --- | --- | --- |
| 食い違いの発覚 | 着手前 | 実装後 |
| 完成の判定 | テストの合否 | 人の合意 |
| 直す対象 | 受け入れ基準の文 | コード・テスト・画面 |
