# レッスン4-3 受け入れ基準と ATDD

## このレッスンの目標

- [ ] ユーザーストーリーに、合否が判定できる受け入れ基準を書ける
- [ ] 受け入れ基準を Given-When-Then の 3 部で書ける
- [ ] テストケースにできない仕様を見つけ、書き直し案を持って聞ける

## 4-3-1 受け入れ基準

> **ユーザーストーリーに受け入れ基準を書くと、完成の条件がテスト可能になる**

「会員登録できること」というチケットを受け取りました。どこまでできたら完成なのか、何度読んでも決まりません。実装が終わってから「メール確認が要るはずだ」と揉めます。この揉め事は、実装が悪いのでも読み方が悪いのでもありません。完成の条件が書かれていないだけです。

**ユーザーストーリー** は、「〈誰〉として〈何〉をしたい、なぜなら〈理由〉」という形で書く要求の単位です。**受け入れ基準** は、そのストーリーが完成したと言える条件の一覧です。ストーリーは「なぜ」を伝え、受け入れ基準は「どこまで」を決めます。役割が違うので、両方が要ります。

受け入れ基準は、モジュール2で扱った受け入れテストの入口でもあります。発注者や利用者が「使えるか」を判断する材料になるので、**合否が判定できる文だけ**を書きます。

> 買い物客として、3,000 円以上買ったら送料を無料にしてほしい。
> まとめ買いのほうが得だと分かるからだ。

1. 購入額が 3,000 円以上のとき、送料は 0 円と表示される
2. 購入額が 3,000 円未満のとき、送料は 500 円と表示される
3. 購入額が 0 円以下のときは注文できない

3 行とも「見て合否が言える」形になっています。ここまで書けていれば、そのままケース表に写せます。

逆に、基準になっていない書き方を並べます。

| 書き方 | なぜ困るか |
| --- | --- |
| 送料が正しく計算される | 何が正しいかが決まらない |
| 使いやすい画面にする | 合否を判定できない |
| 3,000 円くらいで無料 | 境界が決まらない |

3 つとも、読むぶんには意味が通ります。困るのはテストケースにしようとした瞬間です。期待結果の欄に何を書けばよいか分からない、という形で気づきます。**テストケースに書き下せるかどうかが、受け入れ基準の合格判定**だと考えてください。

## 4-3-2 Given-When-Then

> **受け入れ基準は前提(Given)・操作(When)・期待(Then)の 3 部で書ける**

受け入れ基準を「3,000 円以上なら送料無料」と 1 行で書きました。実装者から質問が来ます。「カート画面ですか、注文確認画面ですか。送料はどこに出しますか」。期待だけがあって、前提と操作が書かれていませんでした。1 行で書くと、必ずどれかが抜けます。抜けたぶんは読む人が想像で埋めるので、想像が食い違うと揉めます。

**Given-When-Then** は、受け入れ基準を 3 部に分けて書く型です。Given がそのときの状態、When が利用者の操作、Then が観測できる結果です。

| 部 | 内容 |
| --- | --- |
| Given | カートに 3,000 円ぶんの商品が入っている |
| When | 注文確認画面を開く |
| Then | 送料が「0 円」と表示される |

型の価値は、書きやすさではなく **埋まらない欄が見えること** にあります。3 つの欄が埋まらなければ、まだ決まっていないところがあるということです。抜けを検出する道具として使ってください。

境界のもう一方は、1 本の基準に詰め込まず、Given の数字を 2,999 円に変えてもう 1 本書きます。「3,000 円のとき 0 円、2,999 円のとき 500 円」と 1 本に押し込むと、どちらが落ちたのか分からなくなります。境界値分析と同じ数え方です。

そして、ここがこのレッスンの本題です。

| Given-When-Then | テストケース |
| --- | --- |
| Given | 入力・事前の状態 |
| When | 手順 |
| Then | 期待結果 |

モジュール3の最初に「テストケースは入力・手順・期待結果の 3 点セットで書く」と学びました。Given-When-Then はそれと同じ構造です。つまり **受け入れ基準を GWT で書くと、そのままケース表の 1 行になります**。書き直しの手間がゼロになるうえ、書き写す過程での取りこぼしも起きません。

## 4-3-3 ATDD

> **ATDD は受け入れテストを先に書き、それを満たすように実装する進め方である**

受け入れ基準は書きました。しかし読み返すのは実装が終わってからです。実装者は基準を見ずに作り、あとから食い違いが出ます。「そこは対象外だと思っていた」がリリース直前に判明する、という進み方です。基準を書いただけでは、読まれるタイミングが遅いままなのです。

**ATDD** は、受け入れテストを実装より前に書く進め方です。書いた時点では実装が無いので、テストは必ず落ちます。その落ちるテストが「完成の定義」になります。

```python
# test_acceptance.py — 実装より先に書く
import pytest

from shipping import shipping_fee


@pytest.mark.parametrize("total, expected", [
    (3000, 0),     # 受け入れ基準 1
    (2999, 500),   # 受け入れ基準 2
])
def test_shipping_fee(total, expected):
    assert shipping_fee(total) == expected
```

この時点で `shipping.py` はまだありません。実行すると `ModuleNotFoundError` で落ちます。それが出発点です。`shipping.py` を書き、`2 passed` になったら、受け入れ基準 1 と 2 は満たされたことになります。

先に書く場合と、あとで書く場合を比べます。

| | 先に書く(ATDD) | あとで書く |
| --- | --- | --- |
| 食い違いの発覚 | 着手前 | 実装後 |
| 完成の判定 | テストの合否 | 人の合意 |
| 直す対象 | 受け入れ基準の文 | コード・テスト・画面 |

モジュール1の早期テストの原則と、モジュール2のシフトレフトが、この 1 表に集約されています。欠陥は早く見つけるほど安く直せる、という話を、いちばん左まで押し切った形が ATDD です。

もうひとつ副産物があります。**テストを先に書こうとすると、仕様の曖昧さがその場で見つかります**。書けなければ、決まっていないということです。次のトピックはその話です。

## 4-3-4 曖昧な仕様への向き合い方

> **テストケースにできない仕様は、書き直しを提案するのがテスト担当者の仕事である**

「レスポンスは速いこと」という受け入れ基準が回ってきました。Given-When-Then に書き直そうとしたのですが、Then が書けません。「速い」の合否を判定する方法が決まっていないからです。書けないまま実装が進み、リリース後に「遅い」と言われます。

書けないことに気づいた人は、この時点でもういます。声を上げるかどうかだけの差です。**書けない = 合否を判定できない = 完成が定義されていない**、という連鎖を覚えてください。

このとき「曖昧です」と差し戻すのは得策ではありません。書いた人にも、どこがどう曖昧なのかは見えていないからです。**案を持って聞く**ほうが早く終わります。

| 元の基準 | 聞くこと | 書き直した基準 |
| --- | --- | --- |
| レスポンスは速いこと | どの操作が、何秒以内? | 注文確定は 95% が 1 秒以内に応答する |
| 送料が正しく計算される | 境界はいくら? 以上? 超過? | 3,000 円以上のとき送料 0 円 |
| 不正な入力を弾く | 不正とは? | 購入額が 0 以下または整数でないときエラー |

右の列を先に書いて持っていくと、会話が「これで合っていますか」の 1 往復で済みます。仕様を書く人を責める話ではありません。曖昧さは、書いた時点では見えないのが普通です。テストケースにしようとして初めて見える、という順序になります。

そして、聞くのは早いほど安く済みます。

| 気づいた時期 | 直すもの |
| --- | --- |
| 受け入れ基準を書くとき | 文章 1 行 |
| 実装中 | コードとテスト |
| リリース後 | コード・テスト・画面・お詫び |

これはモジュール3の「ケース表を書けない場所は、仕様が決まっていない場所である」を、受け入れ基準の側から見た同じ話です。仕様の穴を早期に暴くことは、テスト担当者が届けられる情報のなかで、もっとも価値の高いもののひとつです。
