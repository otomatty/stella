# レッスン4-3 演習 — 受け入れ基準と ATDD

対象トピック: 4-3-1 〜 4-3-4

## 手元で試す

いつもの 2 段構えを、**順番を逆にして**やります。**①受け入れ基準を Given-When-Then で書く → ②実装より先にテストを書いて、落ちるところから始める**。

### ① 受け入れ基準を Given-When-Then で書く

次のユーザーストーリーを読んでください。

> 買い物客として、3,000 円以上買ったら送料を無料にしてほしい。
> まとめ買いのほうが得だと分かるからだ。

受け入れ基準を 3 本、Given-When-Then で書いてください。1 本に条件を詰め込まず、Given を変えて本数を増やします。

| # | Given | When | Then |
| --- | --- | --- | --- |
| 1 | カートに 3,000 円ぶんの商品が入っている | 注文確認画面を開く | 送料が「0 円」と表示される |
| 2 | | | |
| 3 | | | |

埋めたら、次を確かめてください。

- 3 本のうち 2 本が、3,000 円の境界の内側と外側になっていますか
- Then の欄に「正しく表示される」と書いた行はありませんか。何が正しいのかを書いてください
- 空欄の Given がありませんか。空欄は「まだ決まっていない」の印です

### ② 実装より先にテストを書く

作業用の空のフォルダを作り、**まずテストファイルだけ**を置いてください。実装ファイルはまだ作りません。

```python
# test_acceptance.py — 実装より先に書く
import pytest

from shipping import shipping_fee


@pytest.mark.parametrize("total, expected", [
    (3000, 0),     # 受け入れ基準 1: 境界の内側
    (2999, 500),   # 受け入れ基準 2: 境界の外側
])
def test_shipping_fee(total, expected):
    assert shipping_fee(total) == expected


def test_zero_is_rejected():
    # 受け入れ基準 3: 0 円以下は注文できない
    with pytest.raises(ValueError):
        shipping_fee(0)
```

この状態で実行します。

```bash
pytest -v
```

`ModuleNotFoundError: No module named 'shipping'` で **collection error** になります。これが ATDD の出発点です。落ちているテストが、これから作るものの定義です。

次に、同じフォルダに実装を書きます。

```python
# shipping.py
def shipping_fee(total):
    if total < 1:
        raise ValueError("購入額は 1 円以上です")
    return 0 if total >= 3000 else 500
```

もう一度 `pytest -v` を実行してください。`3 passed` と表示されます。受け入れ基準 3 本が満たされた、という意味です。

確かめられたら、次の改造をしてみましょう。

1. `shipping.py` の `total >= 3000` を `total > 3000` に書き換えて実行し、`test_shipping_fee[3000-0]` が落ちることを確かめる(確かめたら戻す)
2. 「離島は追加で 800 円かかる」という受け入れ基準が **あとから追加された** とします。まずテストを 1 本足して落ちることを確かめ、それから実装する、という順で直してください
3. 2 で足したテストの Given(何が離島だと分かるのか)を書けますか。書けなければ、それは仕様が決まっていない印です。何を聞くべきかをメモしてください

## 演習問題

### 問1(基本)

次のユーザーストーリーに、受け入れ基準を 3 つ書いてください。合否が判定できる文にしてください。

> 新規の利用者として、メールアドレスとパスワードで会員登録したい。次回から入力の手間を省きたいからだ。

### 問2(基本)

「カート画面が使いやすいこと」という受け入れ基準を Given-When-Then に書き直そうとしました。どの欄が書けませんか。書けない理由も答えてください。

### 問3(応用)

次の受け入れ基準は 1 本に条件が詰め込まれています。Given-When-Then で複数本に分けてください。

> 購入額が 3,000 円以上なら送料無料、未満なら 500 円、0 円以下ならエラーになること。

### 問4(応用)

あなたのチームが ATDD で進めることになりました。「受け入れ基準を書く」「実装する」「テストが通ることを確認する」「受け入れテストを書く」「テストが落ちることを確認する」の 5 つを正しい順に並べ、**2 番目と 3 番目のあいだで得られるもの**を説明してください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

1. 未登録のメールアドレスと 8 文字以上のパスワードを入力して登録すると、登録完了画面が表示される
2. 既に登録されているメールアドレスで登録すると、「このメールアドレスは登録済みです」と表示され、登録されない
3. パスワードが 7 文字以下のときは登録できず、文字数の条件が表示される

「登録できること」ではなく、**入力と結果の対** で書くのが要点です。8 文字という数字は仕様から引きます。仕様に書かれていなければ、それを聞くのがこのレッスンの後半の話です。

</details>

<details>
<summary>問2の解答例</summary>

**Then が書けません**。「使いやすい」を観測する方法が決まっていないからです。何を見れば合格と言えるのかが無いので、期待結果の欄が埋まりません。

When も曖昧です(どの操作を指すのかが決まっていない)。ただし決定的なのは Then です。判定できない基準は、完成の定義になりません。

書き直すなら、たとえば「Given カートに商品が 1 件入っている / When 数量を 2 に変更する / Then 合計金額が画面の再読み込みなしに更新される」のように、観測できる事実へ落とします。

</details>

<details>
<summary>問3の解答例</summary>

| # | Given | When | Then |
| --- | --- | --- | --- |
| 1 | カートに 3,000 円ぶんの商品が入っている | 注文確認画面を開く | 送料が「0 円」と表示される |
| 2 | カートに 2,999 円ぶんの商品が入っている | 注文確認画面を開く | 送料が「500 円」と表示される |
| 3 | カートの合計が 0 円である | 注文確認画面を開く | 注文できない旨が表示される |

3 本に分ける理由は 2 つあります。1 つは、どれが満たされていないのかが分かること。1 本にまとめると、落ちたときにどの条件かを切り分けられません。もう 1 つは、Given の数字を境界値に選べることです。2,999 円という値は、境界値分析で選んだ外側そのものです。

</details>

<details>
<summary>問4の解答例</summary>

正しい順序は次のとおりです。

1. 受け入れ基準を書く
2. 受け入れテストを書く
3. テストが落ちることを確認する
4. 実装する
5. テストが通ることを確認する

2 番目と 3 番目のあいだ、つまり **受け入れテストを書こうとする過程** で得られるものが、仕様の曖昧さの発見です。Then に何を書けばよいか分からない基準、Given の数字が決まらない基準が、その場で浮かび上がります。この時点なら直すのは文章 1 行で済みます。

3 番目の「落ちることを確認する」を飛ばさないでください。落ちないなら、テストが対象を呼んでいないか、既に実装されている(=作る必要がない)かのどちらかです。

</details>

## 確認クイズ

### Q1. 受け入れ基準とは何ですか。

- A. 実装者が参照する技術的な設計書
- B. そのユーザーストーリーが完成したと言える条件の一覧
- C. 見つかった欠陥をまとめた報告書

<details>
<summary>答え</summary>

**B** — ユーザーストーリーが「なぜ」を伝えるのに対し、受け入れ基準は「どこまでできたら完成か」を決めます。合否が判定できる文だけを書きます。

</details>

### Q2. 次のうち、受け入れ基準として成立しているのはどれですか。

- A. 送料が正しく計算される
- B. 使いやすいカート画面にする
- C. 購入額が 3,000 円未満のとき、送料は 500 円と表示される

<details>
<summary>答え</summary>

**C** — A は「正しい」の中身が決まらず、B は合否を判定できません。テストケースの期待結果の欄に書き下せるかどうかが、受け入れ基準の合格判定です。

</details>

### Q3. Given-When-Then の Given に書くのはどれですか。

- A. そのときの前提となる状態
- B. 利用者が行う操作
- C. 観測できる結果

<details>
<summary>答え</summary>

**A** — Given が状態、When が操作、Then が結果です。テストケースの「入力・手順・期待結果」とそのまま対応します。

</details>

### Q4. ATDD で受け入れテストを先に書き、すぐに実行するとどうなりますか。

- A. 通る。テスト自体が正しいことの確認になる
- B. 実装が無いので実行そのものができず、何も起きない
- C. 実装がまだ無いので落ちる。その落ちるテストが完成の定義になる

<details>
<summary>答え</summary>

**C** — 落ちることの確認は飛ばせません。落ちないなら、テストが対象を呼んでいないか、既に実装済みかのどちらかです。

</details>

### Q5. 「レスポンスは速いこと」という受け入れ基準を受け取りました。テスト担当者として適切な行動はどれですか。

- A. 判断できないので、実装が終わってから実測して評価する
- B. 「注文確定は 95% が 1 秒以内に応答する」のような案を作り、これで合っているか確認する
- C. 曖昧なので、受け入れ基準の一覧から削除する

<details>
<summary>答え</summary>

**B** — 「曖昧です」と差し戻すより、案を持って聞くほうが 1 往復で済みます。この時点なら直すのは文章 1 行です。実装後に気づくと、コードとテストと画面を直すことになります。

</details>
