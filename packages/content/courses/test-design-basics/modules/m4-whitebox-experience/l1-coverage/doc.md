# レッスン4-1 カバレッジ

## このレッスンの目標

- [ ] カバレッジが何を分母にした割合なのかを説明できる
- [ ] 同じテストでステートメントとブランチの数値が食い違う理由を説明できる
- [ ] カバレッジ 100% でも残る欠陥を挙げられる

## 4-1-1 カバレッジ

> **カバレッジはテストがコードをどれだけ踏んだかを測る物差しである**

仕様からケース表を 12 件作り、pytest で全部通しました。上長に「これで十分ですか」と聞かれ、答えられません。「仕様は全部見ました」とは言えるのですが、コードのどこに触れたかを示す材料がないからです。

**カバレッジ** は、テストの実行中に通った箇所の割合です。コードの構造を見て測るので、ホワイトボックスの道具になります。まったく新しい考え方ではありません。モジュール3の状態遷移で、「すべての遷移を 1 回は通ったか」を数えて **遷移カバレッジ** と呼びました。分母を状態遷移表からコードに置き換えたものが、このレッスンのカバレッジです。

分母に何を置くかで、カバレッジは何種類にも分かれます。

| 種類 | 分母 | 100% の意味 |
| --- | --- | --- |
| ステートメントカバレッジ | コードの文 | 全部の文を 1 回は実行した |
| ブランチカバレッジ | 分岐の枝 | すべての分岐の両側を通った |
| 遷移カバレッジ(モジュール3) | 状態遷移表の遷移 | すべての遷移を 1 回は通った |

そのため、「カバレッジ 80% です」という報告だけでは何も分かりません。**何を分母にした 80% なのか**を必ず添えます。分母が違えば、同じテストでも数値は変わります。

先に釘を刺しておきます。カバレッジは次の 3 つを答えません。

- 「踏んだ」は実行したというだけで、**結果を確かめたか**は測らない
- 分母は書かれたコードだけなので、書き忘れた仕様は数に入らない
- 数値は目標ではなく、**踏んでいない場所を指す地図**として読むもの

3 つ目が特に大事です。詳しくは 4-1-4 で扱います。

## 4-1-2 ステートメントカバレッジ

> **ステートメントカバレッジは全部の行を少なくとも 1 回実行したかを測る**

送料計算のテストを 1 件だけ書いて、通りました。コードのどこを踏み残しているのかは、目で追うしかありません。4 行の関数ならまだしも、200 行では追いきれません。

**ステートメントカバレッジ** は、実行した文 ÷ 全部の文です。分母は関数の本体にある実行される文で、`def` の行や空行は数えません。100% の意味は「すべての文が最低 1 回は動いた」、それだけです。

```python
def shipping_fee(total):
    fee = 500          # 文1
    if total >= 3000:  # 文2
        fee = 0        # 文3
    return fee         # 文4
```

2,999 円で 1 件だけテストすると、`if` が偽になるので文3 を踏みません。3/4 で 75% です。ここに 3,000 円のケースを足すと文3 も動き、4/4 で 100% になります。

注目してほしいのは、この 2 件が **境界値分析で選んだ内側と外側そのもの** だという点です。仕様から技法で作った表が、結果としてコードを埋めています。カバレッジを上げるためにケースを作るのではなく、技法で作ったケースの成果をカバレッジで確認する、という順序で使ってください。

| | ステートメントカバレッジ |
| --- | --- |
| 分かる | `fee = 0` が一度も動いていない = 穴の位置 |
| 分からない | その文の結果が正しいかどうか |
| 落とし穴 | `assert` を書かずに関数を呼ぶだけでも 100% になる |

落とし穴の行に注意してください。カバレッジは「実行したか」しか見ません。期待結果を確かめているのは `assert` です。`assert` を 1 つも書かずに関数を呼ぶだけのテストでも、カバレッジは 100% になります。

## 4-1-3 ブランチカバレッジ

> **行を全部踏んでも、分岐の真偽両方を通したとは限らない**

3,000 円のケース 1 件だけで、ステートメントカバレッジが 100% になりました。「全部の行を踏んだので十分です」と報告できそうです。しかし、送料が **有料になる経路** は一度も動いていません。3,000 円を入れると `fee = 500` も `fee = 0` も両方通ってしまうからです。上書きされるので、文としては両方が実行済みに数えられます。

**分岐** は、`if` のように条件の真偽で処理が 2 手に分かれる場所です。**ブランチカバレッジ** は、通った枝 ÷ 全部の枝で測ります。1 つの `if` には枝が 2 本あります。`else` が書かれていなくても、条件が偽のときに素通りする経路が枝として存在します。

同じ関数を 3 通りのテストで測ると、こうなります。

| テストの組 | 実行した文 | ステートメント | 通った枝 | ブランチ |
| --- | --- | --- | --- | --- |
| 2,999 のみ | 3/4 | 75% | 偽のみ | 50% |
| 3,000 のみ | 4/4 | **100%** | 真のみ | **50%** |
| 2,999 と 3,000 | 4/4 | 100% | 真と偽 | 100% |

2 行目が要点です。ステートメント 100% とブランチ 50% が同居します。**ブランチが 100% ならステートメントも必ず 100% ですが、逆は成り立ちません**。ブランチカバレッジのほうが強い(条件が厳しい)基準です。

50% のまま何を見逃すのかを、具体的に見ます。`fee = 500` を `fee = 5000` と書き間違えたとしましょう。

- 3,000 円のケースは `fee = 0` で上書きするので、**通ってしまう**
- ステートメントカバレッジは 100% のまま、数値は何も知らせない
- 2,999 円を 1 件足せば、その場で落ちる

ここでも、境界値分析で内側と外側を 1 つずつ取っていれば、この 2 件は最初から表にあります。技法がブランチカバレッジを連れてくる、という関係です。

## 4-1-4 カバレッジの限界

> **カバレッジ 100% でも、書かれていないコードの欠陥(仕様漏れ)は見つからない**

ブランチカバレッジ 100% を達成し、胸を張って報告しました。ところが本番で「離島なのに追加送料が加算されない」と問い合わせが来ます。コードを見ると、離島の分岐が **そもそも書かれていませんでした**。

カバレッジの分母は「書かれたコード」です。実装し忘れた仕様は分母に入らないので、100% でも残り続けます。書かれていないものは踏みようがありません。カバレッジはコードの写像であって、仕様の写像ではないのです。

| 欠陥の種類 | 例 | 見つける手立て |
| --- | --- | --- |
| 仕様漏れ | 離島の追加送料が実装されていない | 同値分割・デシジョンテーブル |
| 期待結果の誤り | 0 円のはずが 500 円で `assert` している | 仕様のレビュー |
| 非機能の問題 | 応答に 3 秒かかる | 非機能テスト |

3 つとも、コードを 100% 踏んだうえで残ります。カバレッジを上げても近づきません。

では数値をどう使うか。次の 3 点で覚えてください。

- **低い数値は情報**です。踏んでいない場所が特定でき、次に書くケースが決まります
- **高い数値は証明ではありません**。100% を目標に掲げると、`assert` の無いテストが増えます。数値だけを追うと、テストの目的(品質の情報を届けること)から離れていきます
- 仕様から作る技法(網を張る)とカバレッジ(穴を探す)は両輪です

現場で「カバレッジ 80% を維持」といった基準を置くこと自体は普通です。問題になるのは、数値を **達成すべき目標** にしたときです。診断結果として読み、低いところの理由を説明できる状態を保つ、という使い方が実用的です。

## もっと知りたい人へ

- カバレッジの種類はほかにもあります。条件が `and` / `or` で複数つながっているとき、その一つひとつの真偽まで見る基準もあります。まずはステートメントとブランチの 2 つを押さえてください
- カバレッジは道具で測るものです。Python では計測ツールが「どの行を踏まなかったか」を一覧で出してくれます。数値そのものより、この一覧のほうが実務では役に立ちます
- 数値を報告に載せる話は、モジュール5のテストメトリクスでもう一度扱います
