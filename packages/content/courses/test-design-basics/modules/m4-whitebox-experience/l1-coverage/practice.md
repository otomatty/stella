## 手元で試す

これまでと同じ 2 段構えです。**①カバレッジを手で数える → ②pytest で「見逃す」ことを実際に確かめる**。

### ① カバレッジを手で数える

次の関数を見てください。実行される文は 4 つです。

```python
def shipping_fee(total):
    fee = 500          # 文1
    if total >= 3000:  # 文2
        fee = 0        # 文3
    return fee         # 文4
```

テストの入力ごとに、踏む文と枝を表に埋めてください。

| テストの組 | 踏む文 | ステートメント | 通る枝 | ブランチ |
| --- | --- | --- | --- | --- |
| 3,000 円のみ | | | | |
| 2,999 円のみ | | | | |
| 2,999 円と 3,000 円 | | | | |

埋めたら、次を確かめてください。

- ステートメントが 100% なのにブランチが 50% になる行がありますか
- ブランチが 100% でステートメントが 100% 未満の行は作れますか(作れないはずです。理由を 1 行で書いてください)

### ② pytest で「見逃す」ことを確かめる

作業用のフォルダに次の 2 ファイルを置いてください。

```python
# shipping.py
def shipping_fee(total):
    fee = 500
    if total >= 3000:
        fee = 0
    return fee
```

```python
# test_shipping.py
from shipping import shipping_fee


def test_free_over_3000():
    assert shipping_fee(3000) == 0
```

ターミナルで実行します。

```bash
pytest -v
```

`1 passed` と表示されます。この 1 件でステートメントカバレッジは 100%(文1〜文4 をすべて踏む)、ブランチカバレッジは 50%(`if` の真だけ)です。

ここから、**カバレッジ 100% が見逃すもの**を体験します。

1. `shipping.py` の `fee = 500` を `fee = 5000` に書き換えて `pytest` を実行する。**まだ `1 passed` のまま**です。文1 は実行されているのに、間違いが見つかりません
2. `test_shipping.py` に次のテストを足して、もう一度実行する

```python
def test_paid_under_3000():
    assert shipping_fee(2999) == 500
```

3. `1 failed, 1 passed` になり、`assert 5000 == 500` と表示されます。`fee = 5000` を `fee = 500` に戻すと `2 passed` になります

たった 1 件足しただけで、ブランチカバレッジが 50% → 100% になり、同時に欠陥が捕まりました。この 1 件は 3,000 円の境界の外側、つまり境界値分析で最初から表にある値です。

余力があれば、次も試してください。

- `test_shipping.py` の `assert` の行を消して `shipping_fee(3000)` と呼ぶだけにする。テストは通ります。**カバレッジは変わらないのに、何も確かめていない**状態です
- `shipping.py` に「離島なら 800 円を足す」処理を入れ忘れたとして、いま書いた 2 件のテストが何%になるか考える。100% のままです

## 演習問題

### 問1(基本)

「カバレッジ 85% です」という報告を受けました。この数値だけでは判断できません。何を聞き返しますか。2 つ挙げてください。

### 問2(基本)

次の関数を `is_member=True, total=5000` の 1 件だけでテストしました。ステートメントカバレッジとブランチカバレッジをそれぞれ答えてください。

```python
def discount(total, is_member):
    rate = 0
    if is_member:
        rate = 10
    return total * rate // 100
```

### 問3(応用)

問2 の関数について、ブランチカバレッジ 100% になるテストケースの組を答えてください。あわせて、その組でも見つからない欠陥の例を 1 つ挙げてください。

### 問4(応用)

チームで「カバレッジ 90% を達成すること」という目標が設定されました。この目標のまずい点を 2 つ挙げ、代わりにどう使うことを提案しますか。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

- **何を分母にした 85% か**(ステートメントか、ブランチか)。分母が違えば同じテストでも数値は変わります
- **踏んでいない 15% はどこか**。数値そのものより、どの分岐が未実行かの一覧のほうが次の行動につながります

余裕があれば「そのテストに `assert` は入っているか」も聞きたいところです。カバレッジは実行したかしか測りません。

</details>

<details>
<summary>問2の解答例</summary>

文は `rate = 0` / `if is_member:` / `rate = 10` / `return ...` の 4 つです。`is_member=True` なら 4 つとも実行されるので、**ステートメントカバレッジは 100%** です。

一方 `if` の枝は真しか通っていないので、**ブランチカバレッジは 50%** です。非会員のとき割引が 0 になるかは、一度も確かめていません。

</details>

<details>
<summary>問3の解答例</summary>

`is_member=True` と `is_member=False` の 2 件で、ブランチカバレッジは 100% になります。

| # | 入力 | 期待結果 |
| --- | --- | --- |
| 1 | total=5000, is_member=True | 500 |
| 2 | total=5000, is_member=False | 0 |

それでも見つからない欠陥の例としては、たとえば「本来は会員ランクごとに割引率を変える仕様なのに、一律 10% でしか実装されていない」があります。書かれていない分岐は分母に入らないので、100% のまま残ります。ほかに「`//` による切り捨ての扱いが仕様と違う」なども、`total` を 1 種類しか試していないので通り抜けます。

</details>

<details>
<summary>問4の解答例</summary>

まずい点:

- **`assert` の無いテストでも数値が上がる**ため、目標を満たすだけなら中身の薄いテストを量産できてしまいます
- **仕様漏れには効かない**ので、90% を達成しても「実装されていない機能」は残ります。数値が安心の根拠にされると、かえって危険です

提案としては、目標値ではなく **診断** として使うことです。「未実行の行の一覧を毎回見て、なぜ踏んでいないかを説明できる状態にする」「説明できない未実行があればケースを足す」という運用にすると、数値を追わずに穴だけを潰せます。

</details>

## 確認クイズ

### Q1. カバレッジは何を測る物差しですか。

- A. 仕様書のうちレビューが終わった割合
- B. テストの実行中に通ったコードの割合
- C. 見つかった欠陥の数

<details>
<summary>答え</summary>

**B** — コードの構造を見て測るので、ホワイトボックスの道具です。分母をコードの文にするか、分岐の枝にするかで種類が分かれます。

</details>

### Q2. `fee = 500` / `if total >= 3000:` / `fee = 0` / `return fee` の 4 文からなる関数を、3,000 円のケース 1 件だけでテストしました。カバレッジはどうなりますか。

- A. ステートメントもブランチも 100%
- B. ステートメントもブランチも 50%
- C. ステートメントは 100%、ブランチは 50%

<details>
<summary>答え</summary>

**C** — 3,000 円だと `fee = 500` も `fee = 0` も実行される(上書きされる)ので文は 4/4 です。しかし `if` は真しか通っていないので、枝は 1/2 です。

</details>

### Q3. `else` が書かれていない `if` 文の枝は、何本として数えますか。

- A. 1 本。真のときの経路だけ
- B. 2 本。真のときの経路と、偽で素通りする経路
- C. 条件式に出てくる変数の数と同じ

<details>
<summary>答え</summary>

**B** — `else` が書かれていなくても、条件が偽のときに `if` の中を飛ばして進む経路は存在します。そこを通っていなければブランチカバレッジは 50% です。

</details>

### Q4. `assert` を 1 つも書かず、対象の関数を呼ぶだけのテストを実行しました。ステートメントカバレッジはどうなりますか。

- A. 呼んだ範囲の文は実行済みに数えられ、100% になることもある
- B. `assert` が無いので必ず 0% になる
- C. テストとして成立しないので計測できない

<details>
<summary>答え</summary>

**A** — カバレッジは「実行したか」しか見ません。期待結果を確かめているのは `assert` です。100% を目標にすると、この種の中身の無いテストが増えます。

</details>

### Q5. ブランチカバレッジ 100% を達成しました。それでも残る可能性が高い欠陥はどれですか。

- A. 分岐の偽側だけで起きる計算間違い
- B. 一度も実行されていない行に潜む欠陥
- C. 仕様にあるのに実装されていない機能の欠落

<details>
<summary>答え</summary>

**C** — カバレッジの分母は「書かれたコード」です。実装し忘れた仕様は分母に入らないので、100% でも残り続けます。ここは同値分割やデシジョンテーブルなど、仕様から作る技法が受け持ちます。

</details>
