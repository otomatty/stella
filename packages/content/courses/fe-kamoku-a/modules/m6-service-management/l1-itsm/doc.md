# レッスン6-1 サービスマネジメントと監査

## このレッスンの目標

- [ ] ITサービスマネジメントとSLAの意味を説明できる
- [ ] インシデント管理と問題管理の違いを、復旧と原因除去の観点で説明できる
- [ ] フルバックアップと差分バックアップの違いと、システム監査の独立性を説明できる

## 6-1-1 ITサービスは運用が本番

> **ITサービスマネジメントは、サービスを安定して提供し続けるための管理活動**

システムは完成した日がゴールではありません。翌日から毎日、社員や顧客が使い続けます。止まれば業務も止まるので、動かし続ける仕組みが必要です。そのための日々の管理活動をまとめた呼び名が **ITサービスマネジメント** です。

たとえば社内の勤怠システムなら、毎朝の正常確認、問い合わせ対応、障害に備えた復旧手順の整備などが該当します。派手さはありませんが、この積み重ねが「安定して提供し続ける」ことを支えます。

品質の約束には **SLA** を使います。SLAは、サービスの品質を数値で約束する合意です。たとえば「稼働率(サービスが動いている時間の割合)99.9%以上」のように、提供者と利用者が事前に数値で合意しておきます。「なんとなく頑張る」ではなく数値で約束する、という点が選択肢の判定基準になります。

## 6-1-2 インシデント管理は復旧優先

> **インシデント管理は、原因究明より先にサービスの復旧を優先する**

サービスの正常な提供を妨げる出来事を **インシデント** と呼びます。業務時間中にシステムが止まれば、利用者はその瞬間から仕事ができません。そこで **インシデント管理** では、原因をじっくり調べるより先に、まずサービスを使える状態に戻します。

サーバーが停止したら、まず再起動して復旧させ、利用者に知らせます。再起動は応急処置にすぎませんが、インシデント管理としては正解です。詳しい調査は落ち着いてから行います。

復旧の後、根本原因を取り除いて再発を防ぐのが **問題管理** です。2つの管理は次のように役割が分かれています。

| | インシデント管理 | 問題管理 |
| --- | --- | --- |
| 目的 | サービスの復旧 | 根本原因の除去 |
| やること | 応急処置・回復 | 原因の調査・再発防止 |
| 急ぎ度 | 最優先で急ぐ | 落ち着いて取り組む |

「応急処置で戻すのがインシデント管理、二度と起きないようにするのが問題管理」——この区別は選択肢の問題で繰り返し問われます。

## 6-1-3 バックアップは運用の基本

> **バックアップは、障害に備えてデータの複製を別の場所に残す運用**

ディスクの故障で業務データが消えてから慌てても、データは戻りません。そこで、障害というインシデントが起きる前に、データの複製を別の場所に残しておきます。これが **バックアップ** です。「別の場所に」が大事で、同じディスクに置いた複製は障害のときに一緒に消えてしまいます。

バックアップは一度きりではなく、決めた周期で繰り返す運用です。ただし、毎日全データを取ると時間も容量もかかります。そこで2つの方式を組み合わせるのが定番です。

- **フルバックアップ** — 全データの複製を取る方式
- **差分バックアップ** — 最後のフルバックアップ以降に変更された分だけを取る方式

| | フルバックアップ | 差分バックアップ |
| --- | --- | --- |
| 対象 | 全データ | フル以降の変更分 |
| 取得時間 | 長い | 短い |
| 復元手順 | フル1本で戻る | フル+最新の差分1本 |

たとえば日曜にフル、月〜土曜に差分を取る運用なら、金曜に障害が起きても復元できます。復元の手順は「日曜のフル」に「木曜の差分1本」を重ねるだけです。差分は「フル以降の変更分をまとめて含む」ので、途中の差分を全部たどる必要はありません。この復元手順の違いが出題の狙い所です。

## 6-1-4 システム監査は第三者の目

> **システム監査は、独立した立場の監査人がITの管理状況を点検する活動**

「うちの運用は大丈夫」と現場は言いますが、自分の仕事の欠点は自分では気づきにくいものです。そこで、ITの管理状況を点検する活動として **システム監査** があります。点検する人が **監査人** です。

監査の基本の流れは次のとおりです。

1. 監査人が管理の状況(たとえばバックアップの実施記録)を点検する
2. 不備があれば **指摘** する
3. 直すよう **改善勧告** を出す

実際に直すのは監査人ではなく、運用の現場です。監査人が自分で直し始めると、当事者になってしまいます。

最も重要な条件は、監査人が開発や運用の当事者から独立していることです。当事者から離れていることを **独立性** と呼びます。運用担当者が自分の運用を点検すると、都合の悪い点は意識せずとも甘くなりがちです。「運用部門の部長が自部門を監査する」は独立性を欠くのでNG——この判定が選択肢の問題で繰り返し問われます。

## もっと知りたい人へ

- ITサービスマネジメントの実践をまとめた枠組みとして、ITILという名前が知られています。まずは「安定提供のための管理活動」という定義を固めるのが先です
- バックアップには、直前のバックアップ以降の変更分だけを取る増分方式もあります。フルと差分の対比が固まってから広げると混乱しません
- システム監査の進め方は、計画・実施・報告という段階で整理されます。監査人の独立性という土台を先に押さえてください
