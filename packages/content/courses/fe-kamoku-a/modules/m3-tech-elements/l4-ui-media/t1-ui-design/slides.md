# 3-4-1
# UIは使う人に合わせて設計する

基本情報 科目A対策 — Module 3 / レッスン3-4

<!-- ノート: ここからヒューマンインタフェースのレッスンです。技術の話から少し離れて、「人とシステムの接点」をどう設計するかを扱います。 -->

---

## なぜ必要か

- 機能はまったく同じなのに、「使いやすいアプリ」と「使いにくいアプリ」がある
- 使いにくい画面は、入力ミスや問い合わせを増やし、業務の時間を奪う
- この差はどこから生まれるのか

<!-- ノート: つかみ。社内システムで「どこを押せばいいか分からない」経験を思い出させると効果的。機能の差ではなく接点の差だ、と問いを立てる。 -->

---

## 結論

**ユーザーインタフェースは、使う人が迷わず操作できることを基準に設計する**

- 画面・ボタン・入力欄など、人とシステムの接点が **ユーザーインタフェース**(UI)
- 目的の操作を迷わず正確にできる度合いを **ユーザビリティ** と呼ぶ

<!-- ノート: 結論を言い切る。UIの良し悪しを測るものさしがユーザビリティ、という関係で覚える。試験では「ユーザインタフェース」「ヒューマンインタフェース」と表記される。 -->

---

## 最小の例

同じエラーでも、伝え方で使いやすさが変わる。

| 場面 | 迷わせるUI | 迷わせないUI |
| --- | --- | --- |
| エラー表示 | 「エラー E-4021」 | 「パスワードは8文字以上にしてください」 |
| 日付の入力 | 自由入力(形式が不明) | カレンダーから選択 |

- どちらも機能は同じ。使う人が次に何をすべきか分かるかどうかが違う

<!-- ノート: 最小の例。上の行は「原因も対処も分からない」、下の行は「そもそも間違えようがない」。良いUIは注意書きを増やすのではなく、迷う場面自体を減らす。 -->

---

## 迷わせない設計の型

- **選ばせる** — 自由に入力させず、選択肢から選ばせて誤りを防ぐ
- **確認させる** — 削除など取り返しのつかない操作の前に確認を挟む
- **戻れるようにする** — 操作を取り消せる手段を用意する

<!-- ノート: 強化枠。3つとも「人は必ず間違える」前提の設計。試験では入力チェックや画面設計の適切な方法を選ぶ形で問われる。 -->
