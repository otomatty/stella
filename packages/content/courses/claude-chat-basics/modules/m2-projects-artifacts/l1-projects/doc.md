# レッスン2-1 Projectに文脈を置く

## このレッスンの目標

- [ ] Projectが何のための入れ物かを説明できる
- [ ] ある材料をナレッジに置くか、会話に貼るかを判断できる
- [ ] 置く前に機密情報かどうかを確かめられる

## 2-1-1 Projectは文脈の入れ物

> **Projectは、同じ前提を使う会話をまとめて置いておく入れ物です**

ここまでで、2つのことを学びました。1つは、Claudeはこの会話に渡していない社内の事情や今回の対象を知らないということです。もう1つは、話題が変わったら新しい会話を始めるということです。

この2つを合わせると、ある不便が起きます。会話を分けるたびに、同じ材料を渡し直すことになるのです。

```text
月曜  新しい会話 → チーム体制と用語集を貼る → 本題
火曜  別の話題なので新しい会話 → また同じものを貼る → 本題
水曜  貼るのを忘れる → 一般論が返ってくる
```

貼る手間そのものより、水曜の行が問題です。人は必ず貼り忘れます。そして貼り忘れた回だけ、返答の質が落ちます。

そこで、会話の外側に置き場を作ります。それが **Project** です。Projectは、同じ前提を使う会話をまとめておく単位です。ここでいう **前提** とは、どの会話でも同じように使う、変わらない材料や決まりのことを指します。

```text
Projectを使わない
  会話A: 前提を貼る → 本題
  会話B: 前提を貼る → 本題

Projectを使う
  Project(前提はここに1回だけ)
    ├ 会話A: 本題だけ
    └ 会話B: 本題だけ
```

会話はまるごとコンテキストとして読まれます。Projectの中で会話を始めると、そこに置いた前提もあわせて読まれます。だから本題だけを書けば済みます。

| | Projectを使わない | Projectを使う |
| --- | --- | --- |
| 前提を渡す回数 | 会話の数だけ | 1回置くだけ |
| 貼り忘れ | 起きる | 起きない |
| 会話の中身 | 前置き + 本題 | 本題だけ |

ひとつ補足します。Projectは会話を消すものではありません。会話は今までどおり作りますし、話題が変われば新しい会話にします。変わるのは、前提をどこに書くかだけです。

## 2-1-2 置くのは変わらない材料だけ

> **Projectには、会話が変わっても変わらない材料をナレッジとして置きます**

置き場ができると、次に起きるのは入れすぎです。手元の資料をまとめて置きたくなります。今日の議事録も、今回の見積りも、そのとき届いたログも。

しばらくは問題ありません。困るのは数週間後です。とっくに変わった数字や、終わったはずの案件の事情を前提にした返答が返ってきます。しかも、なぜそうなったのかがすぐには分かりません。置いたことを忘れているからです。

Projectに置いた材料のことを **ナレッジ** と呼びます。画面での呼び名は変わることがありますが、役割は「置いた前提」で変わりません。

置くかどうかは、重要さでは決めません。**変わるかどうか** で決めます。

| | ナレッジに置く | 会話に貼る |
| --- | --- | --- |
| 使う期間 | 何か月も同じ | その日だけ |
| 例 | 用語集、書き方の決まり、体制図 | 今日のログ、今回の議事録 |
| 変わったら | 置き直す | 貼り直さない |

迷ったら、次の一問で決めます。

> **来月の会話でも、これを渡しますか**

「はい」ならナレッジに置きます。「いいえ」なら、その会話に貼るだけで十分です。一度きりの材料は、一度きりの場所に置くのが正しい姿です。

なお、置いたものは古くなります。体制が変わった、決まりが変わった、というときはナレッジも置き直してください。置きっぱなしのナレッジは、貼り忘れと同じくらい静かに返答をずらします。

## 2-1-3 毎回書く指示は固定できる

> **毎回書いていた進め方の指示は、Projectに固定すると書かずに済みます**

Projectに置けるのは材料だけではありません。進め方の指示も置けます。

前のモジュールで、依頼には手順や制約を書くと学びました。実際に書いてみると、毎回ほとんど同じ行を書いていることに気づきます。

```text
毎回書いていた前置き
  「です・ます調で。結論から書いて。表は使わないで。」
  + 本題
```

前置きのほうが本題より長い、という状態です。しかも書き忘れた回だけ体裁が崩れ、直させる往復が増えます。

この、毎回同じ手順や制約をProjectの側に置いておくことを **指示の固定** と呼びます。画面での呼び名は変わることがありますが、役割は「書かずに効く指示」で変わりません。

```text
固定したあと
  Project側: です・ます調 / 結論から / 表は使わない
  依頼: 本題だけ
```

ナレッジが材料の置き場だとすれば、こちらは進め方の置き場です。効果は2つあります。書く量が減ること、そして書き忘れによるばらつきが消えることです。

ただし、何でも固定すると窮屈になります。境目は材料のときと同じ考え方です。

| | Projectに固定する | その依頼に書く |
| --- | --- | --- |
| 対象 | どの依頼でも同じ進め方 | 今回だけの手順や制約 |
| 例 | 文体、結論を先に書く、長さの目安 | 今週の締切、今回の提出先、今回だけの様式 |

固定した指示が邪魔になったと感じたら、それは今回だけの事情まで縛っているサインです。固定するのは「次の依頼でも同じことを書く」ものだけにしてください。

## 2-1-4 置く前に機密情報かを確かめる

> **ナレッジに材料を置く前に、それが社外に出せない機密情報でないかを確かめます**

ここまでは「置くと便利」という話でした。最後に、置く前の確認を足します。

**機密情報** とは、社外に出せない情報のことです。講座1で扱った語です。顧客名、個人情報、鍵やパスワード、未公開の仕様、契約の中身などが当てはまります。

まず押さえておきたいのは、この確認が **会話に材料を貼るときにも同じように要る** ことです。講座1で扱ったとおりです。貼った材料が送信と同時に消えるわけではありません。会話は残るので、貼ったものもその会話を消すまで残っています。

そのうえで、なぜこのレッスンで改めて扱うかというと、ためる場所ができたからです。ナレッジは、残る長さではなく、読まれる範囲と見直す機会が違います。

| | 会話に貼る | ナレッジに置く |
| --- | --- | --- |
| 残る期間 | その会話を消すまで | 置き場を消すまで |
| 読まれる範囲 | その会話だけ | Project内のすべての会話 |
| 気づく機会 | 貼るたびに毎回 | 置いた1回だけ |

効くのは下の2行です。貼る材料は貼るたびに自分の目を通りますが、置いた材料は以後だれも読み直さないまま、すべての会話で読まれ続けます。だから、貼るときと同じ確認を、置く前の1回にはより丁寧にかけます。

判断には、講座1と同じ一問を使います。

> **この内容を、社外の人に画面で見せられるか**

見せられるなら、そのまま置けます。ためらいが出たときは、何がためらいの原因かを探してください。多くの場合、原因は文書全体ではなく、ごく一部の固有名詞です。そこを伏せて書き直せば置けることがほとんどです。

伏せると意味が消えてしまうもの、たとえば未公開の仕様そのものが中身であるような材料は、置かないと決めます。**置かないという判断も正解です。**

これは4Dの「責任を持つ」を、置き場の上でそのまま実行していることになります。加えて、チームや客先に取り決めがあるときは、そちらが優先です。判断に迷ったら、置く前にリーダーへ一度確認してください。

## もっと知りたい人へ

- Projectを作るときは、いきなり資料をまとめて置かず、2〜3本会話をしてから「毎回書いていること」を見つけて置くほうがうまくいきます。実際に書いた前置きが、そのまま置くべき前提の候補になります
- ナレッジには見直しのきっかけがありません。四半期に一度など、置いたものを読み返す時期をチームで決めておくと、古い前提が残り続けるのを防げます
- 画面の並びや呼び名は変わります。置き場そのものの操作で迷ったときは、使っている製品のドキュメントで最新のものを確認してください
