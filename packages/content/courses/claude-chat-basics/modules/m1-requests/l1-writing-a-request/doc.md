# レッスン1-1 伝わる依頼を書く

## このレッスンの目標

- [ ] 依頼を書くことが4Dの「伝える」にあたると説明できる
- [ ] 丸投げの依頼を、成果物とできの基準を入れた依頼に書き直せる
- [ ] 手順と制約を書き足すかどうかを判断できる

## 1-1-1 依頼を書くことは伝えること

> **よい依頼を書くとは、4Dの「伝える」を入力欄の上でそのまま実行することです**

考え方は分かっているのに、入力欄の前に座ると手が止まる。とりあえず書いて送ってみると、返ってくるものが毎回変わる。このレッスンは、その段差を埋めるところから始めます。

まず、この講座で使う語を置きます。

- **4D** — 生成AIと働くときの4つの局面の呼び名です(講座1で扱った語です)
- **依頼** — Claudeに渡す、頼みごとの文です

4つの局面は、次のように並びます。

| 英語名 | 日本語 | 何を決めるか |
| --- | --- | --- |
| Delegation | 任せる | 何を自分でやり、何をClaudeに渡すか |
| **Description** | **伝える** | 渡すものを、どう言葉にするか |
| Discernment | 見極める | 返ってきた内容を、どう確かめるか |
| Diligence | 責任を持つ | 出したものに、どう責任を持つか |

このレッスンが扱うのは2行目だけです。残りの3つは名前だけ覚えておいてください。中身はこのあとのモジュールで使います。

大事なのは、**画面の上で新しい作法を覚えるわけではない** ということです。「伝える」でやることは、チャットでも変わりません。渡すものを言葉にする、それだけです。違うのは、その言葉を入力欄に打ち込む、という点だけです。

入力欄の上で「伝える」を実行すると、たとえばこうなります。

```text
障害の原因の候補を3つ、可能性の高い順に挙げてください。
それぞれに、根拠になったログの行を添えてください。
読む相手は非エンジニアの営業担当です。
```

3行とも、頭の中にあった条件を言葉にしただけです。特別な言い回しは使っていません。どの行が何にあたるかは、このあとのトピックで1つずつ扱います。

つまりこのレッスンは、新しい知識を足す回ではありません。習った枠を、そのまま画面に持ち込む回です。以降のトピックでは、その1つ目の局面である「伝える」を、依頼という具体的な文に落としていきます。

## 1-1-2 丸投げの依頼は的を外す

> **何が出てきたら完了かを書かない丸投げの依頼は、返答が毎回的を外します**

実際に書いてみると、たいてい最初につまずくのはここです。

「このログ見といて」と投げたら、ログの要約が返ってきました。欲しかったのは原因の候補でした。返ってきた内容は間違っていません。ただ、使えません。

このように、何をどこまでやれば終わりかを書かずに渡す依頼を、この講座では **丸投げ** と呼びます。実務でよく見るのは、たとえば次のような一言です。

```text
「このログ見といて」
「議事録、いい感じにまとめて」
「このコード、なんとかして」
```

どれも目的すら書かれていません。同じ職場の同僚になら、これで通じることもあります。その人が案件の事情を知っているからです。Claudeは、こちらが渡していない事情を知りません。

的を外す理由は、性能ではなく **的が置かれていない** ことにあります。同じ一言から、次のどれが返ってきても不思議はありません。

| 投げた依頼 | 返りうる返答 |
| --- | --- |
| 「このログ見といて」 | ログの要約 |
| 「このログ見といて」 | エラー行の抜き出し |
| 「このログ見といて」 | 原因の候補と対処案 |

3つとも、依頼に対しては正しい返答です。どれが当たりかは運になります。運で決まる依頼を毎日出していると、書き直しの往復がそのまま作業時間になります。

なお、返答がずれたときに言い直して寄せていくのは、前のレッスンでやったとおり正しい進め方です。ここで問題にしているのは、**毎回同じずれ方をしている** 状態です。同じ往復を繰り返しているなら、直すべきは返答ではなく最初の依頼です。

## 1-1-3 入力欄でも成果物から書く

> **入力欄の依頼も、何が出てきたら完了かという成果物の形から書き出します**

丸投げを反省すると、多くの人はまず「情報を足す」方向に動きます。案件の事情を長々と書き足してみる。ところが、文は長くなったのに返ってくる形はやはり毎回変わります。

足りないのは量ではありません。**書き出す場所** です。

- **成果物** — その依頼が終わったとき、手元に残るものです(講座1で扱った語です)

成果物の形から書き出す、という順番は講座1で扱ったとおりです。入力欄の上でも変わりません。実際に書き直すと、こうなります。

```text
前: このログ見といて

後: 障害の原因の候補を3つ、可能性の高い順に並べてください。
    それぞれに、そう考えた根拠のログの行を添えてください。
```

変えたのは、数(3つ)・並び順(可能性の高い順)・添えるもの(根拠の行)の3つだけです。案件の事情はまだ1文字も足していません。それでも返ってくるものは大きく安定します。

| | 丸投げの依頼 | 成果物から書いた依頼 |
| --- | --- | --- |
| 完了の形 | 書いていない | 書いてある |
| 返答の幅 | 広い | 狭い |
| 書き直し | 毎回起きる | 減る |

返答の幅が狭くなることは、窮屈になることではありません。当たりに近づくことです。

コツは、送る前に自分へ一言聞くことです。「これが返ってきたら、この会話は終わりにできるか」。答えられないなら、まだ成果物の形が決まっていません。

もう1つ、成果物の形が決まると **何を渡せばよいかも決まります**。原因の候補が欲しいのなら、当のログを会話に渡す必要があります。判断に要る材料を添えるという話は前のレッスンで扱いました。成果物を先に決めると、添える材料の見当も付きます。

## 1-1-4 できの基準も先に書く

> **良し悪しを分ける軸(できの基準)は、往復で直す前に依頼へ書きます**

成果物の形が決まっても、まだ終わりではありません。形は指定どおりなのに、中身が重くて読ませられない。「もっと短く」「もっとやさしく」と3往復して、ようやく通る。そんな進み方になることがあります。

この往復が起きるのは、良し悪しの軸が自分の頭の中にしかないからです。

- **できの基準** — 出てきたものが良いか悪いかを決める軸です(講座1で扱った語です)

軸は先に渡す、というのも講座1で扱ったとおりです。画面の上では、往復で言っていた内容を最初の一言に前倒しする形になります。1-1-3 で書き直した依頼に足すと、こうなります。

```text
前: 障害の原因の候補を3つ、可能性の高い順に並べてください。

後: 障害の原因の候補を3つ、可能性の高い順に並べてください。
    読む相手は非エンジニアの営業担当です。
    候補1つにつき3行以内、専門用語には一言の説明を付けてください。
```

足した2行は、往復のたびに口で言っていた内容そのものです。頭の中では最初から決まっていて、書いていなかっただけです。軸は 読む相手 / 長さ / 言葉づかい の3つでだいたい足ります。

| | 往復して直す | 依頼の中で先に書く |
| --- | --- | --- |
| 軸の在りか | 自分の頭の中 | 依頼の文 |
| 往復の回数 | 増える | 減る |
| 同僚が同じ依頼を出せるか | 出せない | 出せる |

効き目は往復の回数だけではありません。頭の中にある基準は、自分にしか使えません。文にした基準は、チームの誰でも同じ依頼を出せるようになります。実務では、この差のほうが大きく効きます。

## 1-1-5 譲れない縛りだけ書き足す

> **手順や制約は、進め方に譲れない縛りがあるときだけ依頼に書き足します**

ここまでで、成果物とできの基準がそろいました。残るのは進め方です。ここは両側に失敗があります。

やり方を1から10まで書いたら、依頼を書くほうが時間がかかった。逆に何も書かなかったら、使ってはいけない部品を使った案が返ってきた。どちらも実際によく起きます。

線を引くために、語を2つ置きます。

- **手順** — こういう順でやってほしい、という進め方の指定です(講座1で扱った語です)
- **制約** — 守ってほしい条件、やってはいけないことです(講座1で扱った語です)

既定は「書かない」、という線引きも講座1と同じです。そのうえで、譲れないものがあるときだけ入力欄で足します。

```text
前: この関数のテストを書いてください。正常系と異常系を3件ずつ。

後: この関数のテストを書いてください。正常系と異常系を3件ずつ。
    先に既存のテストを読み、それから実装を書いてください。
    新しい外部の部品は追加しないでください。
```

足した2行が、手順と制約です。どちらも、書く理由が現場にあります。テストを先に読ませるのは、既存の期待どおりに書いてほしいからです。部品を増やさないのは、増やすとチームの審査が要るからです。**理由が言えないものは書かなくてよい**、と考えてください。

| | 全部指定する | 何も指定しない | 譲れないものだけ |
| --- | --- | --- | --- |
| 書く手間 | 大きい | 小さい | 小さい |
| 事故 | 起きにくい | 起きる | 起きにくい |

狙うのは右の列です。手順と制約を書きすぎると、進め方の工夫が全部こちらの負担になります。それでは任せた意味が薄くなります。

判断に迷ったら、こう考えてください。**やり方が変わっても成果物が変わらないなら、書かなくてよい**。やり方が変わると成果物が使えなくなるなら、それは譲れない縛りです。

これでレッスン1-1はそろいました。依頼に書くのは、成果物・できの基準・(あれば)手順と制約の3種類です。順番もこのとおりです。

## もっと知りたい人へ

- ここで扱った成果物・できの基準・手順・制約は、人に仕事を頼むときの要素とほぼ同じです。後輩に依頼を出すときの文を思い出すと、書く順番がつかみやすくなります
- 同じ依頼を何度も出していることに気づいたら、その文をメモに残しておいてください。毎回書き直すのは成果物の部分だけになります
- うまくいかなかった依頼は消さずに残し、どこが足りなかったかを一言書き添えてください。丸投げだったのか、できの基準がなかったのかが見えると、次の依頼が速くなります
