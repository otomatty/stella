# レッスン4-1 要件から設計する

## このレッスンの目標

- [ ] 業務の説明からエンティティの候補を挙げられる
- [ ] 主キーに何を選ぶべきかを判断できる
- [ ] 自分の設計を4つの観点で見直せる

## 4-1-1 要件から名詞を拾う

> **設計は、業務の説明に出てくる名詞をエンティティの候補として拾うところから始める**

正規化もリレーションも分かったのに、白紙から始めようとすると手が止まります。取っかかりが要ります。

**要件** は、その仕組みが何をするかを書いた説明です。まず、そこに出てくる名詞に印を付けます。

```text
「社員が書籍を借りる。貸出日と返却日を記録する」

  社員   書籍   貸出

→ 候補: employees / books / loans
```

注目してほしいのは「貸出」です。もとは「借りる」という動詞ですが、**貸出日と返却日を記録する必要がある** ため、記録の単位としてエンティティになります。

動詞が名詞になってエンティティになる、というのは頻出のパターンです。「注文する」→ 注文、「参加する」→ 参加、「支払う」→ 支払い。**記録が要る出来事は、それ自体がエンティティ** だと考えてください。

拾った名詞はあくまで候補です。次の段階で、主キーが決められるか、他と関係を持つかを確かめて絞ります。

## 4-1-2 主キーは変わらない値にする

> **主キーには、業務の都合で変わらない値を選ぶ**

メールアドレスを主キーにしたら変更のたびに参照元が壊れた、社員番号の体系が変わって過去のデータと合わなくなった。どちらも実際に起きる失敗です。

**代理キー** は、業務の意味を持たない、連番などの識別用の値です。

```text
主キーに向かない       主キーに向く
 メールアドレス          id (連番)
 社員番号                id (連番)
 商品コード
```

業務上の意味を持つ値は、**業務が変われば変わります**。主キーは他のテーブルから参照される値なので、変わると参照元をすべて直すことになります。

「変わらないと思っていたものが変わる」のが業務です。だから **迷ったら代理キー** が実務の既定です。

ただし、メールアドレスが重複してよいわけではありません。主キーにはせず、**重複を許さない列(一意制約)として別に持ちます**。役割を分けるということです。

- 主キー — 行を特定し、他から参照される。変わらない
- 一意な列 — 業務上重複してはいけない。変わりうる

## 4-1-3 関係は「1件に対して何件か」で決める

> **関係の種類は、双方向に「1件に対して相手は何件か」を問えば決まる**

1対多なのか多対多なのかを感覚で決めると、後からテーブルを作り直すことになります。判断は機械的にできます。

**多重度** は、片方1件に対して相手が何件対応するかです。**両方向に問う** のがコツです。

```text
「社員は何冊借りられるか」        → 複数
「1冊の書籍は何人に貸し出されるか」 → (期間を変えて)複数

→ 多対多 → 中間テーブル(loans)を作る

片方が「1件だけ」なら 1対多 → 多い側に外部キー
```

片方向だけ見ると判断を誤ります。「社員は複数の書籍を借りる」だけを見て1対多だと決めると、書籍側に社員IDを持たせることになり、2人目に貸し出せなくなります。

もう1つのコツは **時間軸を意識する** ことです。「同時に借りられるのは1人」でも、期間を変えれば何人にも貸し出されます。記録として残すなら、多対多です。

## 4-1-4 設計は変更の起きる場所で見直す

> **設計の良し悪しは、変更が起きたときに直す場所が何か所かで確かめる**

設計には正解が1つに決まりません。だからこそ、良し悪しを確かめる具体的な問いが要ります。

**レビュー観点** として、次の4つを当ててください。

```text
1. 会社名が変わったら、何行を直すか        → 1行であるべき
2. 1マスに複数の値が入っていないか          → 第1正規形
3. その列は何によって決まるか               → 第2・第3正規形
4. 消したい行が参照されていたらどうするか   → 参照整合性
```

1つ目が、この講座を通しての核心です。**変更が起きたときに直す場所が1か所なら、その設計は壊れにくい**。逆に、同じ情報を何行も直す必要があるなら、分け方を見直す合図です。

4つすべてに答えられれば、その設計は「説明できる状態」になっています。設計は正解が1つに決まらないからこそ、**なぜそう分けたかを説明できること** が品質の基準になります。

この講座で学んだことは、次のように使ってください。新しい機能の設計を任されたら、名詞を拾い、主キーを決め、多重度を問い、この4つの観点で見直す。手順として繰り返せることが、入門を終えた状態です。
