# レッスン2-1 リレーション

## このレッスンの目標

- [ ] 外部キーで参照関係を宣言できる
- [ ] 1対多と多対多を、テーブルの形で表せる
- [ ] 参照先を消すときの選択肢を説明できる

## 2-1-1 外部キーで参照先を宣言する

> **外部キーは、その列が別のテーブルの主キーを指していることをデータベースに教える**

正規化でテーブルを分けると、新しい問題が生まれます。`customer_id` という列がどのテーブルを指しているのか、定義を見ただけでは分かりません。そして、存在しないIDを書いた行もそのまま入ってしまいます。

- **外部キー** — 別のテーブルの主キーを指す列
- **参照** — その行が別のテーブルの行を指していること

```sql
CREATE TABLE orders (
  id          INTEGER PRIMARY KEY,
  customer_id INTEGER REFERENCES customers(id)
);
```

`REFERENCES customers(id)` と宣言すると、2つのことが起きます。

- **データベースが守ってくれる** — 存在しない `customer_id` の行は入れられなくなる
- **意図が定義に残る** — この列が何を指すのかが、コメントではなく定義そのものに書かれる

1つ注意があります。**SQLite では、外部キーの検査が既定でオフ**です。`REFERENCES` と書いてあっても、接続ごとに `PRAGMA foreign_keys = ON` を実行しないと、存在しない `customer_id` の行がそのまま入ってしまいます(PostgreSQL や MySQL では宣言だけで検査されます)。SQLite で試すときは、次の1行を先に実行してください。

```sql
PRAGMA foreign_keys = ON;
```

SQL入門で学んだ `JOIN ... ON` は「取り出すときのつなぎ方」でした。外部キーは「定義としてのつながり」です。両方あって初めて、設計の意図が守られます。

## 2-1-2 1対多は多い側にIDを持つ

> **1対多の関係は、多い側のテーブルに相手のIDを持たせて表す**

顧客と注文をつなぐとき、どちらのテーブルにIDを置くか迷います。

**1対多** は、1件に対して相手が複数ある関係です(顧客1人に注文が複数)。

```text
customers            orders
| id | name |        | id | customer_id | total |
|----|------|        |----|-------------|-------|
| 1  | 佐藤 |        | 10 | 1           | 320   |
                     | 11 | 1           | 200   |
```

答えは **多い側(注文)に相手のIDを置く** です。理由は単純で、逆にすると1マス1値が守れなくなるからです。顧客テーブルに `order_ids` という列を作って `10, 11` と並べれば、レッスン1-1で見た第1正規形の違反そのものになります。

この形は設計で最も頻出します。「1対多なら、多い側に外部キー」と覚えてください。

## 2-1-3 多対多は間にテーブルを置く

> **多対多の関係は、両方のIDを持つ中間テーブルを作って表す**

1つの注文に複数の商品があり、1つの商品も複数の注文に現れます。この場合、どちらにIDを置いても1マスに複数の値を入れることになってしまいます。

- **多対多** — 双方向に複数が対応する関係
- **中間テーブル** — 両方のIDを持ち、関係そのものを表すテーブル

```text
orders          order_items(中間)      products
| id |          | order_id | product_id | 数量 |   | id | name |
|----|          |----------|------------|------|   |----|------|
| 1  |          | 1        | 10         | 2    |   | 10 | ノート|
| 2  |          | 1        | 11         | 1    |   | 11 | ペン  |
                | 2        | 10         | 1    |
```

発想の転換は、**関係そのものを行として持つ** ことです。「注文1に商品10が2個」という関係が、中間テーブルの1行になります。

中間テーブルは、関係に固有の情報も持てます。`数量` は注文にも商品にも属さず、「この注文でこの商品を」という関係にだけ意味がある値です。

レッスン1-1で第2正規形を説明したときの `order_items` が、まさにこの中間テーブルでした。多対多を分解すると、自然に1対多が2つになります。

## 2-1-4 参照先を消すときの扱いを決める

> **参照されている行を消せるかどうかは、設計時に決めておく**

退会した顧客を消したら、その人の注文の参照先が消えてしまった。過去の売上を集計しようとしたら、顧客名が引けなくなった。これは設計時に決めておくべきことを決めていなかった結果です。

**参照整合性** は、参照先が必ず存在している状態を保つことです。選択肢は3つあります。

```text
1. 消させない    … 注文が残っている顧客は削除できない(既定)
2. 一緒に消す    … 顧客を消すと注文も消える(履歴が失われる)
3. 消さない設計  … 「退会済み」の印を付けて行は残す
```

1つ目は、外部キーを宣言すると既定で得られる動きです。参照している行があるうちは、参照先を消せません。安全ですが、「消したいのに消せない」という運用上の問題は残ります。

2つ目は、指定すれば一緒に消せます(カスケード削除)。ただし履歴まで消えるので、注文や決済のような記録には向きません。

3つ目が、実務でよく選ばれる方法です。SQL入門6-1-3で触れた「削除済みの印を付ける」設計です。行が残るので、過去の集計もそのまま引けます。

**履歴を扱うテーブルでは、消さない設計を選ぶ**。これは覚えておく価値のある判断です。
