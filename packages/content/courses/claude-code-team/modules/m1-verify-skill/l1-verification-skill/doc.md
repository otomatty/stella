# レッスン1-1 検証を手順書にする

## このレッスンの目標

- [ ] 毎回くり返す検証の手順をSkillに落とせる
- [ ] 長い基準を参照ファイルに分けて指し示せる
- [ ] 決まった操作をスクリプトに切り出し、本文に手順と判断を残せる

## 1-1-1 繰り返す検証はSkillにする

> **毎回くり返す検証の手順は、Skillという手順書にして呼び出します**

M0で検証の型(テスト → lint → 自分の目)が決まりました。この型は、変更を受け取るたびに使います。つまり、検証は **繰り返し** の代表です。

毎回「テストとlintを実行して、差分の要約を出して」と書くのは手間ですし、急いでいる日ほど一部が抜けます。前の講座で学んだとおり、繰り返す指示は仕組みにするのが答えです。検証の **手順**(進める1つ1つのステップ)を、**Skill**(特定のタスクのやり方をまとめた **手順書**)にします。

```text
毎回書く   「テストとlintを実行して、
            差分の要約を出して」

Skillにする 「受け取り検証をやって」
            → 決めた手順書に沿って毎回検証できる
```

呼び出す一言だけで、決めた手順書に沿って検証を進められるようになります。Skillも読ませて従わせる手順書なので、実行そのものが機械的に保証されるわけではありませんが、手順書に照らして進むぶん、ぶれと抜けが減り、抜けたときに気づけます。厳密に毎回同じ操作にしたい部分の逃がし先(スクリプト)は1-1-4で、破られては困る決まりの置き先(hook)は次のモジュールで扱います。

| 毎回指示を書く | 検証Skillを呼ぶ |
| --- | --- |
| 書き方が日によってぶれる | 手順書がぶれを抑える |
| 急ぐと項目が抜ける | 抜けた項目に気づける |
| 自分しか再現できない | チームで手順書を共有しやすくなる |

検証は「毎回やる」「抜けると事故になる」「手順が決まっている」の三拍子がそろった、Skill化の一番おいしい題材です。

## 1-1-2 検証SkillはSKILL.mdに書く

> **検証Skillの正体は、名前とdescriptionと手順を書いたSKILL.mdというファイルです**

書き方は前の講座で通ったとおりです。Skillの本体は **SKILL.md** というMarkdownの **ファイル** で、**名前** と、いつ使うかが分かる **description**(説明文)と、本文の手順を書きます。検証Skillだからといって特別な仕掛けはありません。

```text
name:        verify-changes
description: 生成した変更を受け取る前の検証。
             テスト・lint・差分の確認に使う

本文:        1. テストを実行し、結果を貼る
             2. lintを実行し、結果を貼る
             3. 差分の要約と気になる点を挙げる
```

上の例は、書く要素を並べた構造だけの模式図です。実際のSKILL.mdの書式(frontmatterの区切りなど)は、前の講座で扱ったとおり製品のドキュメントに従ってください。本文の手順は、M0で決めた型そのままです。検証Skillらしい一工夫は、証拠の残し方にあります。

| 書き方 | 効果 |
| --- | --- |
| 「結果をそのまま貼る」と書く | 通ったはず、で済まされない |
| 「落ちたらそこで止める」と書く | 壊れたまま先へ進まない |

「実行しました」という報告だけでは、それ自体が仮説です。結果の出力そのものを貼らせると、検証の証拠が会話に残ります。

## 1-1-3 長い基準は参照ファイルへ

> **観点の一覧のような長い基準は参照ファイルに分けて、SKILL.mdから指し示します**

検証Skillは育ちます。「頼んでいないファイルの変更がないか」「消してはいけない処理が消えていないか」と、差分を読むときの観点を足していくと、SKILL.mdはどんどん長くなり、手順が資料に埋もれて読みにくくなります。

そこで、良し悪しを判定するものさしである **基準**、確認項目を並べた **チェックリスト** のような長い資料は、**参照ファイル**(SKILL.mdから指し示す別ファイル)に分けます。参照ファイルは要るときだけ読まれるので、長くなっても普段のコストは増えません。

```text
SKILL.md      3. 差分をチェックリストに沿って確認する
              (観点は checklist.md を参照)

checklist.md  - 頼んでいないファイルの変更がないか
              - 消してはいけない処理が消えていないか
              - ...観点が20行続く...
```

| 全部SKILL.mdに書く | 参照ファイルに分ける |
| --- | --- |
| 手順が資料に埋もれる | 手順は数行のまま |
| 観点を足すたび手順書が太る | 足すのはチェックリスト側だけ |

観点に気づくたびチェックリストに1行足す、という育て方ができるようになります。手順は短く、資料は別ファイルで厚く、が分け方です。

## 1-1-4 決まった操作はスクリプトへ

> **決まりきった操作はスクリプトに切り出し、SKILL.mdには手順と判断を残します**

参照ファイルに続く、もう1つの切り出し先が **スクリプト** です。

「テストを実行して、lintも実行して、結果をこの形式で集計して」という決まりきった **操作**(コマンドの実行や集計のような決まった作業)を文章で毎回説明するのは長く、実行のたびに少しずつ違うやり方になりえます。ぶれてほしくない操作は、スクリプト(決まった操作をひとまとめにした実行ファイル)にして、そのまま実行させるのが確実です。

一方で、結果を見てどうするかを選ぶ **判断** は、スクリプトにできません。そこは文章のままSKILL.mdの本文に残します。

```text
SKILL.md   1. verify.sh を実行する
           2. 失敗があれば、直してから 1 に戻る
           3. 全部通ったら、差分の要約を報告する

verify.sh  テストの実行と lint をまとめて実行し、
           結果を1つの表にして出す
```

これで検証Skillの置き場が3つに分かれました。

| 置き場 | 置くもの |
| --- | --- |
| SKILL.md 本文 | 手順と判断 |
| 参照ファイル | 読む資料(チェックリスト・基準) |
| スクリプト | 叩く操作(実行・集計) |

**読む資料は参照ファイル、叩く操作はスクリプト、選ぶ判断は本文。** この3分担が検証Skillの完成形です。

ここまでの仕組みは、どれも「呼べば効く」ものでした。次のモジュールでは、呼ばなくても自動で実行される仕組み、hooksを扱います。
