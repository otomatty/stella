# レッスン4-1 リポジトリで配る

## このレッスンの目標

- [ ] チームに効かせたい仕組みをリポジトリにコミットして配れる
- [ ] リポジトリに載せるものと個人用の設定を分けられる
- [ ] GitHubの@claudeが何かを説明できる

## 4-1-1 仕組みはリポジトリで配る

> **CLAUDE.md・Skill・hookといったチームに効かせたい仕組みは、リポジトリにコミットして配ります**

ここまでで、検証Skill・hooks・MCPの設定という仕組みがそろいました。しかし、良い仕組みも自分の手元にあるだけでは **チーム** は変わりません。口頭やチャットで「まねしてね」と伝える配り方は、人によって入り方が違い、あとから入る新人には届きません。

配り方の答えは、すでに持っています。仕組みの正体は、CLAUDE.mdもSkillもhookの設定も、どれもファイルです。ファイルなら、コードと同じように **リポジトリ** に **コミット** して **配る** ことができます。

```text
リポジトリにコミットするもの

  CLAUDE.md      毎回効く約束
  Skillの置き場   検証Skillと参照ファイル・スクリプト
  hookの設定      整形・危険なコマンドの停止
```

| 配り方 | 結果 |
| --- | --- |
| 口頭・チャットで共有 | 人によって入り方が違う。新人に届かない |
| リポジトリにコミット | 取り込んだ全員が同じ仕組みで働く |

リポジトリに入れれば、次に取り込んだ全員へ同じ仕組みの土台が届きます(個人の設定で上書きされる部分は残ります)。配布の仕組みを新しく作る必要はありません。

MCPの設定を共有するときだけ、2つ注意します。第一に、M3で触れたとおり設定の置き場には自分専用と共有用の2系統があるので、チームに効かせたいものは共有用の置き場に書きます(自分専用に書いた設定は、コミットしてもチームには届きません)。第二に、APIキーなどの認証情報は設定に直接書いてコミットせず、環境変数などで各自の手元に置きます。リポジトリに載せるのは仕組みであって、鍵ではありません。

## 4-1-2 個人用の設定は混ぜない

> **自分の好みの設定は個人用の置き場に置き、リポジトリには入れません**

配る話には裏面があります。リポジトリに入れたものはチーム全員に効いてしまう、ということです。

正解が1つでない、自分のやりやすさのための設定を **好み** と呼びます。「説明は箇条書きでほしい」という口調の指定や、自分だけが試している実験中のhookなどです。これをリポジトリに入れると、他人の環境に自分の癖を押しつけることになります。好みは **個人用** の **置き場**(リポジトリの外にある、自分だけに効く設定の置き場)に置きます。

見分けの問いは、前の講座と同じです。「他の人が違うやり方をしていたら困るか?」。困るなら共有、困らないなら好みです。

```text
リポジトリ   検証Skill、整形のhook、
             チームで使うMCPサーバーの設定

個人用       「説明は箇条書きで」という口調の好み、
             自分だけが試している実験中のhook
```

| 間違い | 症状 |
| --- | --- |
| 好みをリポジトリに | 全員の動きが自分の癖に引きずられる |
| 全員に要る仕組みを個人用に | 自分だけ守られて、チームは揃わない |

間違いは両方向にあります。実験は個人用で始めて、チームに効かせたくなったらリポジトリへ。この流れも前の講座のとおりです。

## 4-1-3 仕組みの変更もレビューを通す

> **リポジトリに載せる仕組みの変更は、コードと同じようにレビューを通します**

リポジトリに入れる側の品質は、どう守るのでしょうか。

CLAUDE.mdの1行やhookの設定の変更は、「ただの設定だから」と素通りされがちです。しかしその1行は、チーム全員とエージェントの動きを変えます。影響範囲で見れば、仕組みのファイルは **コード** と同等か、それより広いことさえあります。

だから答えは1つです。仕組みの変更も、コードと同じように **レビュー**(取り込む前に人が変更を確認すること)を通します。新しい手続きを作るのではなく、すでにあるレビューの流れに仕組みのファイルも乗せるだけです。

```text
検証Skillの手順を1つ削る変更

  レビューなし  気づいたら全員の検証が緩くなっていた

  レビューあり  「この確認を消して大丈夫?」が
                取り込む前に議論される
```

特に検証やhookの変更は、緩める方向の事故が怖いところです。レビューの観点は、前のモジュールまでの判断基準そのままです。

| 変更 | 確認すること |
| --- | --- |
| CLAUDE.md | 毎回効かせてよい約束か。長くなりすぎないか |
| Skill / hook | 検証や決まりが緩んでいないか |
| MCPの設定 | 出どころと触れる範囲は確認済みか |

素通りで入った仕組みは、素通りで壊れます。仕組みはチーム全員に効くコード、と覚えてください。

## 4-1-4 GitHubにも@claudeを呼べる

> **GitHubには、Issueやプルリクエストから@claudeに作業を頼める仕組みがあります**

最後に、手元のVS Codeの外にある仕組みを1つ紹介します。

チームの仕事は **GitHub** の上でも回っています。課題を管理する **Issue**、変更をレビューして取り込む **プルリクエスト**。この共有の場にも、Claudeの手を借りる仕組みがあります。**@claude** です。GitHubのコメントで@claudeに呼びかけると、Claudeがその場で作業します。

```text
Issueのコメント

  「@claude このバグを修正して」

→ Claudeが修正のプルリクエストを作る
→ 人がレビューして取り込む
```

Issueから修正を頼む、プルリクエストのレビューを頼む、といった使い方ができ、結果は変更やコメントとしてGitHub上に返ってきます。大切なのは、ここでも最後は人がレビューして取り込むことです。この講座で学んだ検証の構えは、GitHubの上でもそのまま生きます。

| 内容 | この講座 |
| --- | --- |
| @claudeが何か・何を頼めるか | 説明できるようにする |
| リポジトリへの導入・権限の設定 | 対象外(管理者の作業) |

導入はリポジトリ管理者の作業で、権限や秘密情報の設定を伴うため、この講座では扱いません。「あることを知っていて、説明できる」が到達点です。使いたくなったら、リポジトリの管理者に相談してください。

## もっと知りたい人へ

- 個人用の置き場の実際のパスは、製品のドキュメント(Claude Code の settings / memory の項)で確認してください。リポジトリ用と個人用の2系統がある、という構図はどの時期でも変わりません
- @claudeの導入方法(GitHub Actions への組み込み)は管理者向けの公式ドキュメントにあります。この講座の範囲外です
