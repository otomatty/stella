# レッスン2-1 自動で実行される決まり

## このレッスンの目標

- [ ] 指示とhookの効き方の違いを説明できる
- [ ] 「実行の前・あと」のイベントに合った処理を結びつけられる
- [ ] hookの型(command / prompt / agent)と置き分けができる

## 2-1-1 hookは自動で実行される

> **hookは指示と違って、設定され有効なら決めたタイミングで自動実行される仕組みです**

前の講座の最後に、4つ目の入れ物としてhookの名前だけを予告しました。ここからがその本編です。

CLAUDE.mdに太字で書いても、**指示** は読んで従うものである以上、読み落としがゼロにはなりません。「ほぼ守られる」で足りるものはそれで十分ですが、プロジェクトには「たまに破られる」では困る決まりがあります。

**hook** は、決めたタイミングで決めた処理を自動で実行する仕掛けです。読んで従うのではなく、イベントに結びつけて動くので、読み落としという抜け道がありません。

```text
指示   「コミット前に必ず整形してね」
       → ほぼ守られる。でも、たまに抜ける

hook   コミット前に整形が自動で実行される
       → 読み落としという抜け道がない
```

Skillとの違いも効き方にあります。Skillは呼ばれたときに効く手順書、hookは呼ばなくても決めたタイミングで効く仕掛けです。

| 入れ物 | 効き方 |
| --- | --- |
| 指示(CLAUDE.mdなど) | 読んで従う。破られうる |
| Skill | 呼ばれたとき効く |
| hook | 設定され有効なら、決めたタイミングで自動実行される |

「自動」は「設定され、有効化され、マッチャに一致し、処理が成功したとき」という意味です。hookも設定の1つなので、外されていれば動きません。hook自体の処理が失敗したり、タイムアウトしたりすることもあります(実行前のcommand hookがタイムアウトすると、通常の権限フローに進むことがあります)。プロジェクトのhookは、ワークスペースを信頼する前には動きません。それでも「読み落とし」という抜け道がない点が、指示との決定的な違いです。hookは最後の防波堤ではなく、指示や権限・CIと重ねる1枚の壁です。「守ってもらう」から「守られる状態を作る」への切り替えが、このモジュールの主題です。

## 2-1-2 hookはイベントに結びつける

> **hookは、ツールの実行の前後といったイベントに結びつけて動かします**

「決めたタイミング」の正体が **イベント** です。イベントは動作のきっかけになる出来事のことで、hookはイベントに結びつけて設定します。

エージェントは **ツール**(ファイルを触ったりコマンドを実行したりする道具)を使って作業を進めます。このツールの実行の「前」と「あと」が、hookを差し込む代表的なイベントです。

```text
イベント            結びつける処理の例

ツールの実行の前  →  これから実行される内容を検査する
ツールの実行のあと →  変更されたファイルを後始末する
```

前と後では、向く処理が変わります。

| イベント | 向く処理 |
| --- | --- |
| 実行の前 | 検査して、まずいものを通さない |
| 実行のあと | 整える・記録するなどの後始末 |

hookの設定は「どのイベントに、どの処理を結びつけるか」という組で考えます。イベントの正式な名前や設定ファイルの綴りは製品のドキュメントで確認するものとして、この講座では「前に検査、あとに後始末」という2方向を覚えれば十分です。

次の2つのトピックで、それぞれの代表例を1つずつ見ます。

## 2-1-3 整形はhookで抜けなくする

> **編集のあとにフォーマッタを実行するhookにすると、整形が抜けなくなります**

「実行のあと」に結びつける代表例が整形です。

**フォーマッタ**(コードの見た目を決まった形に揃える道具)は、どのプロジェクトにもたいていあります。「**整形** してからコミットして」という指示はよく守られますが、たまに抜けます。そして整形の乱れは、レビューで人が指摘するには惜しい仕事です。

そこで、エージェントがファイルを書き換える **編集** というイベントのあとに、フォーマッタの実行を結びつけます。

```text
hookの設定(意味だけ)

  イベント:  ファイルの編集のあと
  処理:      そのファイルにフォーマッタを実行する

→ 編集のたびに、フォーマッタが自動で実行される
```

| やり方 | 結果 |
| --- | --- |
| 指示「整形を忘れないで」 | 忘れた日は乱れが混ざる |
| 編集のあとのhook | 実行し忘れという概念がなくなる |

1つだけ正確に覚えてください。hookが保証するのは「フォーマッタが実行されること」までです(設定され有効なとき)。書きかけの構文エラーなどで、実行されたフォーマッタ自体が失敗することはあります。失敗の結果は放置せず、直してから先へ進みます。それでも抜けを許したくないチームは、CI側の整形チェックをもう1枚重ねて締めます。

M0で「機械に任せられる検査は機械に回す」と決めました。整形のhookはその実践です。設定の正確な綴りは製品のドキュメントで確認してください。持ち帰るのは「編集のあとに整形」という組だけです。

## 2-1-4 危険なコマンドは実行前に止める

> **実行前のhookで危険なコマンドを見分けて、実行そのものを止められます**

「実行の前」に結びつける代表例は、安全装置です。

**コマンド** の中には、取り消せない削除や上書きのように、実行したら戻せないものがあります。こうした **危険なコマンド** に対して「危ないことはしないで」という指示だけで備えるのは、確実とは言えません。講座4では「取り消せない操作は自動承認から外す」という人の側の備えを学びました。hookを使うと、これに機械の壁を1枚足せます。

コマンドの実行の前というイベントで内容を検査し、危険な形に合致したら **止める**(実行させずに終わらせる)hookです。

```text
hookの設定(意味だけ)

  イベント:  コマンドの実行の前
  処理:      内容を検査し、危険な削除の形なら止める

→ 該当するコマンドは、そもそも実行されない
```

あとから謝るより、前で止める。実行前イベントだからできることです。

| 層 | 役割 |
| --- | --- |
| 指示「危険な操作は避けて」 | ふだんの行動を方向づける |
| 実行前のhook | 設定・有効・マッチャ一致・判定成功のときに止める |

hookがあるから指示が要らなくなる、という関係ではありません。指示で方向づけ、hookが壁を1枚足す二段構えです。hookは最後の防波堤ではありません。無効化・タイムアウト・設定漏れがあり得るので、講座4で学んだ「取り消せない操作は自動承認から外す」という人の承認、権限の設定、サンドボックス、CIと重ねて備えます。どのコマンドを危険とみなすかは、プロジェクトごとに決めます。

## 2-1-5 hookの型と置き分け

> **白黒の決まりはcommand hookに、文脈の判断はprompt/agent hookか指示・Skillに置き分けます**

hookは自動実行されるので強力です。強力なので、何でもhookにしたくなりますが、ここに線引きが要ります。

hookには型があります。**command hook** はシェルコマンドなどで、条件に合うかどうかを決定的に判定します。整形されているか、危険な削除の形か。こうした白黒のつく **決まり** はcommand hookに向きます。

一方、文脈によって答えが変わる判断には、**prompt hook** や **agent hook** という型もあります。LLMに判定を任せるので、判定が揺れたり費用がかかったりします。使う場合は製品のドキュメントで性質を確認してから選びます。

「この設計でよいか」「この命名は分かりやすいか」のような問いは、対話で進めたいなら指示とSkillの側に残すのが向きです。

```text
command hook向き       整形されているか
                      危険な削除の形か

prompt/agent hookも可  この変更は意図どおりか
(ただし揺れ・費用あり)

指示・Skillに残す      この設計でよいか
                      この命名は分かりやすいか
```

見分けの問いは「条件を文字で書き切れるか」です。書き切れるならcommand hookにできます。書き切れないものは、型を選ぶか、人とエージェントの判断の領分(指示・Skill)に残します。厳密に毎回同じ操作にしたい部分はスクリプト、破られては困る決まりの強制はhookとCIで重ねます。

| 内容 | 置き先 |
| --- | --- |
| 白黒がつく検査・後始末 | command hook |
| 文脈の判断(揺れを許容できる) | prompt/agent hook |
| 文脈の判断(対話で進めたい) | 指示 / Skill |

これで、前の講座の「4つの入れ物」の地図のうち、hookの行が実装まで埋まりました。次のモジュールでは、外の道具を繋ぐ仕組み、MCPを扱います。

## もっと知りたい人へ

- hookのイベントの一覧・設定ファイルの書き方・型(command / prompt / agent)の詳細は、製品のドキュメント(Claude Code の hooks の項)で確認してください
- 実行前hookのタイムアウト時の挙動(通常の権限フローへ進むこと)や、プロジェクトhookとワークスペース信頼の関係も、同じドキュメントで確認できます
- チームのリポジトリに整形のhookを入れる話は、M4(チームへの展開)で扱います
