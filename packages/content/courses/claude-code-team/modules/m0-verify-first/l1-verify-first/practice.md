# レッスン0-1 演習 — 生成は仮説

対象トピック: 0-1-1 〜 0-1-4

## 手元で試す

VS Code で自分のリポジトリ(または練習用リポジトリ)を開いて進めます。Claude Code が使えない場合は、1と4を紙の上でやるだけでも検証の練習として成立します。

1. 自分のプロジェクトの「テスト・lint・自分の目」に当たるものを書き出す(テストを実行するコマンド、lintのコマンド、差分をどこで読むか)
2. Claude Code に小さな修正を1つ任せ、受け取る前に 1 で書き出した順(機械の検査 → 差分を読む)で検証する
3. 検証で気づいたこと(テストで落ちた、頼んでいない変更が混ざっていた、など)をメモする。何もなければ「何もなかった」と分かったことが収穫です
4. 最近任せた(または任せたい)依頼を1つ選び、「自分が結果を検証できる範囲か」を判定する。検証できないなら、割る・テストを足すなどの変え方を1行で書く

## 演習問題

### 問1(基本)

「生成は仮説」とはどういう意味かを、「検証」という語を使って1〜2文で説明してください。

### 問2(基本)

検証の3点セット(テスト・lint・自分の目)それぞれの守備範囲を、1つずつ1行で書いてください。

### 問3(応用)

「差分を目で読んでから、最後にテストを実行している」という進め方の問題点を、機械の検査という語を使って2文以内で指摘してください。

### 問4(応用)

「テストのないモジュール全体の作り直しを、一度にClaude Codeへ任せたい」という同僚に、任せる範囲の決め方を踏まえた助言を2〜3文で書いてください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

生成された変更は、正しいかもしれないがまだ確かめていない答えだという意味です。検証で証拠を得てはじめて、受け取ってよい変更になります。

</details>

<details>
<summary>問2の解答例</summary>

テストは動きが正しいかを実行して確かめます。lintはコードの形の問題を機械的に見つけます。自分の目は、変更が意図どおりかを差分を読んで確かめます。

</details>

<details>
<summary>問3の解答例</summary>

時間のかかる目の検証を先にすると、あとの機械の検査で落ちたときに読み直しになります。機械の検査を先に通せば、目は通り抜けた差分の「意図どおりか」だけに集中できます。

</details>

<details>
<summary>問4の解答例</summary>

任せてよい範囲は、自分が結果を検証できる範囲で決めます。テストのない全体の作り直しは検証できないので、一度には任せません。目の届く単位に割るか、先にテストを書かせてから進めるのがよいです。

</details>

## 確認クイズ

### Q1. Claude Codeが「修正しました。テストも通るはずです」と報告しました。受け取る前の扱いとして適切なのはどれですか。

- A. 報告を信じてそのまま受け取る
- B. 仮説として扱い、検証してから受け取る
- C. 生成をやり直させる

<details>
<summary>答え</summary>

**B** — 生成は仮説です。「通るはず」を、検証で「通った」に変えてから受け取ります。

</details>

### Q2. テストが全部通ったのに、頼んでいないファイルまで書き換わっていました。これに気づける検証はどれですか。

- A. テストをもう一度実行する
- B. lintを実行する
- C. 差分を自分の目で読む

<details>
<summary>答え</summary>

**C** — 意図どおりかを確かめられるのは自分の目だけです。テストとlintは動きと形しか見ません。

</details>

### Q3. 検証の順番として適切なのはどれですか。

- A. 差分を読んでから、テストとlintを実行する
- B. テストとlintを実行してから、差分を読む
- C. 差分を読めば、テストとlintは省略できる

<details>
<summary>答え</summary>

**B** — 機械の検査を先に通し、落ちたら読む前に差し戻します。目は最後に「意図どおりか」へ集中させます。

</details>

### Q4. 任せる範囲の決め方として適切なのはどれですか。

- A. 難しい仕事は任せず、簡単な仕事だけ任せる
- B. 生成が速いので、できるだけ大きくまとめて任せる
- C. 自分が結果を検証できる範囲に合わせて任せる

<details>
<summary>答え</summary>

**C** — 基準は難易度ではなく検証可能性です。検証できない依頼は、割る・テストを足すなどで検証できる形に変えてから任せます。

</details>
