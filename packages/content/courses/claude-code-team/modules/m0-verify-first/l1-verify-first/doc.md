# レッスン0-1 生成は仮説

## このレッスンの目標

- [ ] 生成した変更を仮説として扱い、検証してから受け取れる
- [ ] テスト・lint・自分の目の3つを、機械を先にする順番で使える
- [ ] 任せる範囲を「検証できるか」で決められる

## 0-1-1 生成は仮説にすぎない

> **Claude Codeが生成した変更は仮説なので、受け取る前に検証します**

シリーズの到達点となるこの講座は、「作らせ方」ではなく「確かめ方」から始まります。

Claude Codeの生成した変更は、いつも正しそうに見えます。説明は筋が通っていて、コードもきれいです。しかし「正しそうに見える」と「正しい」は別のことです。前の講座で「書かせたものほど自分で読む」という構えを通りました。この講座はそれを1語に言い直します。生成は **仮説**(正しいかもしれないが、まだ確かめていない答え)です。

仮説は **検証**(仮説が正しいことを、証拠で確かめる作業)を通ってはじめて、受け取ってよい変更になります。

```text
Claude Code 「修正しました。テストも通るはずです」

自分        「はず、はまだ仮説。
             確かめてから受け取る」
```

エージェント自身も途中で確認をしますが、最後に受け取る責任は人の側にあります。「通るはず」を「通った」に変えるのが検証です。

| 生成だけ | 生成 + 検証 |
| --- | --- |
| 速いが、壊れていても気づけない | 一手間かかるが、壊れたら気づける |
| 直した「つもり」で先へ進む | 直った「事実」で先へ進む |

検証は生成のブレーキではありません。壊れたらすぐ気づける状態を作ることで、安心して速く進むための装置です。

## 0-1-2 確かめ方は3つある

> **生成した変更は、テスト・lint・自分の目の3つで検証します**

検証しようと決めても、「ちゃんと確認して」だけでは何をすれば済みかが分かりません。確かめ方が人によってばらつくと、そこに抜けが生まれます。この講座では、検証の道具を3つに決めます。

- **テスト** — プログラムを実行して、動きが正しいかを確かめる仕掛け
- **lint** — コードの形の問題(乱れた書き方・危うい書き方)を機械的に見つける検査
- **自分の目** — 変更を自分で読んで、意図どおりかを確かめること

```text
テスト     動きは正しいか   → テストを実行する
lint       形は整っているか → lintを実行する
自分の目   意図どおりか     → 変更を読む
```

3つは守備範囲が違うので、どれか1つでは代わりになりません。

| 抜けた検証 | 見逃すもの |
| --- | --- |
| テストなし | 動きの壊れ |
| lintなし | 形の乱れ・危うい書き方 |
| 自分の目なし | 意図と違う変更・余計な変更 |

テストが全部通っていても、頼んでいないファイルまで書き換わっていることはあります。それに気づけるのは自分の目だけです。3点セットで1つの検証、と覚えてください。

## 0-1-3 機械の検査を先に通す

> **テストとlintという機械の検査を先に実行し、残った差分を自分の目で読みます**

3つの道具には、使う順番があります。

自分の目で読むのは、3つの中でいちばん時間がかかり、いちばん疲れる作業です。機械で見つかる問題まで目で探していると、集中力が切れて肝心の見落としが出ます。

そこで、テストとlintのようにコマンド一発で答えが出る検証を **機械の検査** と呼び、先に実行します。機械の検査で落ちた変更は、読む前に差し戻します。自分の目に届くのは、機械を通り抜けた **差分**(変更の前後を比べた、増えた行と減った行の一覧)だけです。

```text
1. テストを実行  → 落ちたら差し戻す
2. lintを実行    → 落ちたら差し戻す
3. 差分を読む    → 意図どおりなら受け取る
```

順番の理屈は「安いものから先に」です。機械の検査は人手よりずっと安く何度でも繰り返せますが、目は有限です。

| 順番 | 起きること |
| --- | --- |
| 目 → 機械 | 読んだあとにテストで落ちて、読み直しになる |
| 機械 → 目 | 目は「意図どおりか」だけに集中できる |

機械に任せられる検査を機械に回すほど、自分の目の価値が上がります。この「機械にやらせる」という分担の考え方は、このあとのhooksのモジュールにそのままつながります。

## 0-1-4 検証できる範囲だけ任せる

> **任せてよい範囲は、自分が結果を検証できる範囲に合わせて決めます**

検証の構えを持つと、任せ方の判断も変わります。

生成が速いと、つい大きな変更まで一度に任せたくなります。しかし任せた **結果**(仕事の出来上がり)が仮説のまま積み上がると、どこかで崩れたときに、どこから壊れていたのか分からなくなります。

そこで、一度に任せる変更の大きさ、つまり **範囲** の上限を決める基準を1つにします。「自分が結果を検証できるか」です。難しいから任せない、のではありません。確かめられないから任せない、のです。

```text
テストのある部分の修正   → 検証できる  → 任せられる
テストのない大改修を一括 → 検証できない → 割ってから任せる
```

検証できない依頼は、あきらめるのではなく、検証できる形に変えます。大きな改修は目の届く単位に割る。テストのない場所は、先にテストを書かせてから本体を直させる。どちらも「検証できる範囲」に収める工夫です。

| 状況 | 任せる範囲 |
| --- | --- |
| テストが充実している | 広く任せて、機械の検査で受け取る |
| テストが薄い | 小さく割って、目の届く単位で受け取る |

検証の仕組みが育つほど、安心して任せられる範囲は広がります。だから次のモジュールからは、検証そのものを仕組みにしていきます。

## もっと知りたい人へ

- 自分のプロジェクトで「テスト・lint・自分の目」に当たるコマンドと手順が何かを、この機会に書き出してみてください。次のレッスンでそのままSkillの材料になります
- プロジェクトによっては、型検査・ビルド・セキュリティ検査なども機械の検査に加わります。この講座は代表の3つに絞っていますが、「機械を先に、目は最後に」という順番はどの組み合わせでも同じです
- テストの書き方そのものは、テスト設計の講座(テスト設計と品質保証 入門)で扱っています
