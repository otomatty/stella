# レッスン4-1 オブジェクトの型

## このレッスンの目標

- [ ] `type` でオブジェクトの形に名前を付けられる
- [ ] 省略可能なプロパティを定義できる
- [ ] オブジェクトの配列と `readonly` を使える

## 4-1-1 typeでオブジェクトの形に名前を付ける

> **typeを使うと、オブジェクトの形に名前を付けて何度も使い回せる**

サーバー側で扱うデータは、ほとんどがオブジェクトです。同じ形を関数のたびに書き下していると、項目が1つ増えたときに直す場所を探すことになります。

- **型エイリアス** — 型に名前を付ける仕組み(`type 名前 = ...`)
- **プロパティ** — オブジェクトが持つ、名前と値の組

```ts
type User = {
  id: number;
  name: string;
};

function findUser(id: number): User {
  return { id, name: "佐藤" };
}
```

名前を付ける効果は2つあります。1つは、項目が増えたときに直すのが定義の1か所だけで済むこと。もう1つは、**チームの会話で使える言葉になる** ことです。「User を返す関数」と言えば、どんな形のデータかが伝わります。

## 4-1-2 無いかもしれない項目は?を付ける

> **プロパティ名の後ろに?を付けると、その項目は無くてもよくなる**

電話番号を登録していない利用者もいます。全項目を必須にすると、実際のデータが型に合わなくなります。

**省略可能なプロパティ** は、名前の後ろに `?` を付けて定義します。

```ts
type User = {
  id: number;
  name: string;
  phone?: string;      // 無くてもよい
};

const a: User = { id: 1, name: "佐藤" };              // OK
const b: User = { id: 2, name: "田中", phone: "03" };  // OK
```

考え方は、省略可能な引数(レッスン3-1)とまったく同じです。省略できるということは、そのプロパティの型が `string | undefined` になるということで、**使うときは値が無い場合の確認が必要になります**。

現実のデータには欠けがある、という事実を型として持っておくと、確認漏れによる障害を防げます。

## 4-1-3 オブジェクトの配列でまとまりを表す

> **User[] と書くと、同じ形のオブジェクトが並んだデータを型で表せる**

データベースから取り出した複数件を、そのまま扱いたい場面があります。SQL入門で学んだ `SELECT` の結果は、まさにこの形です。

**レコード** は1件分のデータのことで、表の1行に当たります。

```ts
type User = { id: number; name: string };

const one: User = { id: 1, name: "佐藤" };

const many: User[] = [
  { id: 1, name: "佐藤" },
  { id: 2, name: "田中" },
];
```

配列の型の作り方は、レッスン2-1で学んだ規則(中身の型 + `[]`)がそのまま当てはまります。`string[]` が文字列の配列なら、`User[]` は User の配列です。

中身の形が保証されるので、取り出した後の処理が単純になります。「この件には name が無いかもしれない」と身構える必要がありません。

## 4-1-4 readonlyで書き換えを禁じる

> **readonlyを付けたプロパティは、作った後に書き換えられなくなる**

受け取ったデータをどこかの処理が勝手に書き換えていた、という不具合は、規模が大きくなるほど追いにくくなります。

**readonly** は、そのプロパティを読み取り専用にする印です。

```ts
type Order = {
  readonly id: number;
  status: string;
};

const order: Order = { id: 1, status: "受付" };
order.status = "発送";   // OK
order.id = 2;            // エラー: 読み取り専用
```

この例では、注文の識別子(`id`)は作った後に変わってはいけないもの、状態(`status`)は変わってよいもの、という設計を型で表しています。

**変えてよいものと、変えてはいけないものを型で区別できる** ことに価値があります。コメントで「id は変更しないこと」と書いても読まれないことがありますが、型で書けば検査が守ってくれます。

これでこの講座で扱う型はすべてです。基本の型・関数の型・オブジェクトの型の3つがあれば、サーバー側の小さなプログラムは型付きで書けます。より高度な型(ジェネリクスなど)は、必要になったときに学べば十分です。
