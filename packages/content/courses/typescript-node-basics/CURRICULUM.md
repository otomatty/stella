## 設計の方針

- **型を全部教えない。** 0-1-3 で扱う範囲(基本の型・関数の型・オブジェクトの型)を宣言し、ジェネリクス・クラス・デコレーター・高度な型演算は明示的に対象外にしています。到達点は「型を付けたプログラムを Node.js で動かし、型エラーを自分で読んで直せる」ことです
- **書く場所と書かない場所を教える。** 変数は推論に任せ(2-1-2)、関数の引数と戻り値は必ず書く(3-1-1 / 3-1-2)。理由は「関数の入口と出口は他人と接する境界だから」で一貫させています
- **型の限界を隠さない。** M5 で「型検査は実行前、データが来るのは実行時」というずれを正面から扱い、`as` の危うさ・`unknown`・`catch` の `unknown` を経て、**境界で 1 度だけ確認する** 設計に着地します。これは後続の REST API 入門のリクエスト検証にそのまま続きます
- **Node.js 入門との接続を本文に書く。** `devDependencies`(1-1-1)、`npm scripts` と `&&`(1-1-4 / 1-1-5)、`process.env` の `undefined`(2-1-3)、`try-catch`(5-1-3)は、前講座で学んだ内容の再利用として説明します

## 対象外

次の内容はこの講座では扱いません(0-1-3 で受講者にも明示しています)。

- **ジェネリクス** — 型を引数にとる書き方。使う場面が出てきたときに学べば十分です
- **クラス・継承・デコレーター** — サーバー側の小さなプログラムには要りません
- **高度な型演算(`keyof` / 条件型 / マップ型 / ユーティリティ型)** — フロントエンドの TypeScript 入門(M5・M6)の範囲です
- **`interface`** — `type` に統一します。使い分けの議論は入門の段階では負担が勝ちます
- **バリデーションライブラリ(zod など)** — 5-1-2 で「実務ではライブラリに任せることもある」と触れるだけに留めます。導入は `rest-api-basics` の範囲です
- **フレームワーク / データベース接続 / テスト** — それぞれ `rest-api-basics`・`python-testing-ci-basics` の範囲です
