# 3-1-3
# CI が遅いと開発が止まる

Pythonテスト自動化とCI入門 — Module 3 / レッスン3-1

<!-- ノート: テストピラミッドが CI の話とつながる回です。 -->

---

## なぜ必要か

- PR を出してから結果が出るまで40分待つ
- 待つのが嫌で、変更をまとめて大きな PR にしてしまう

<!-- ノート: つかみ。遅い CI は、レビュー単位まで悪化させる。ここで結論は言わない。 -->

---

## 結論

**CIの実行時間が長いと開発が止まるため、速い単体テストを中心に据える**

- 直して → 確かめて → また直す、の周期が **フィードバックループ**
- 1周が長いほど、1回の変更が大きく雑になる

<!-- ノート: 結論を言い切る。速さは快適さの話ではなく、変更の品質の話。 -->

---

## 遅さは上から来る

| 種類 | 1件あたり | 本数の目安 |
| --- | --- | --- |
| 単体 | ミリ秒 | 多い |
| 結合 | 秒 | 中くらい |
| E2E | 分 | 少ない |

- テストピラミッドの形が崩れると、CI が一気に遅くなる

<!-- ノート: 対比枠。E2Eを10本足すと分単位で伸びる。単体は1000本でも数秒。 -->

---

## 速く保つ工夫

- 単体テストで守れるものは単体テストで守る
- 遅いテストは、本数ではなく **必要性** で選ぶ
- どのテストが遅いかを測ってから減らす

<!-- ノート: 勘で減らさない。pytest --durations で上位を見てから決める。 -->
