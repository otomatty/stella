# レッスン3-1 演習 — CI で品質を守る

対象トピック: 3-1-1 〜 3-1-4

## 手元で試す

CI は LMS の中では回せません。代わりに、CI が実行しているのと同じことを手元でやってみます。

まず、テストが遅い順に並ぶことを確かめます。

```bash
pytest --durations=5 --durations-min=0
```

いちばん遅いテストが上に出ます。`--durations-min=0` を付けているのは、既定では 0.005 秒より速いテストが `(N durations < 0.005s hidden.)` と隠されるためです。ここまでで書いたテストはどれも速いので、付けないと1件も並びません。実際のプロジェクトで遅いテストを探すときは `pytest --durations=10` だけで十分です。

次に、テストが通った行の割合を出してみましょう。まだテストを書いていない関数を `order.py` に足しておきます。

```python
# order.py に追記
def calc_shipping(total):
    """合計が5000円以上なら送料0円、未満なら500円。"""
    if total >= 5000:
        return 0
    return 500
```

```bash
pip install pytest-cov
pytest --cov=order --cov-report=term-missing
```

`order.py` の何%の行が実行されたかと、実行されなかった行番号が `Missing` の列に表示されます。いま足した `calc_shipping` の行がそこに並んでいるはずです。確かめられたら、次もやってみましょう。

1. `calc_shipping(10000)` を呼ぶだけで `assert` を書かないテストを1本足して再実行し、カバレッジの数字が上がるのに `calc_shipping` を壊しても赤くならないことを確かめる(確かめたら消す)
2. 1 のあとも `Missing` に残る行を探す。`total >= 5000` が偽になる経路を1度も通っていないので、分岐の片方だけが未実行で残る
3. 自分が関わっているリポジトリの `.github/workflows/` を開き、`on` と `steps` に何が書かれているか読む
4. その CI が1回あたり何分かかっているか、実行履歴から確認する

## 演習問題

### 問1(基本)

次のワークフローは、何を合図に、何をしますか。

```yaml
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install pytest
      - run: pytest
```

### 問2(基本)

「自分の環境では通るのに、CI では落ちる」という状況で、CI 側の結果を信じるべき理由を1〜2文で説明してください。

### 問3(応用)

CI が赤い PR を「急ぎなので」とマージしたとします。その後、チームに何が起きるかを順を追って説明してください。

### 問4(応用)

「カバレッジ80%を達成したので、もうバグは出ないはずだ」という主張に反論してください。

## 解答例と解説

<details>
<summary>問1の解答例</summary>

プッシュされたときと、プルリクエストが出されたときを合図に、Ubuntu の環境でリポジトリのコードを取得し、pytest をインストールして実行します。読むべきなのは `on`(合図)と `steps`(やること)の2か所です。1つ目の `actions/checkout` を忘れると、コードが1つも無い場所で pytest が走ります。pytest は `no tests ran` と表示して終了コード5を返すので CI は赤くなりますが、失敗したテストは1つも表示されません。

</details>

<details>
<summary>問2の解答例</summary>

CI は全員共通の環境で実行しているため、手元だけの設定やインストール済みパッケージに依存しません。手元で通るのは、たまたま自分の環境に条件がそろっているだけの可能性があります。

</details>

<details>
<summary>問3の解答例</summary>

main が壊れ、そこから新しく枝を作った人や main を取り込んだ人から順に赤くなっていきます。すると各自「自分のせいか分からない赤」を見ることになり、赤を無視し始めます。最終的に CI の結果を誰も見なくなり、仕組みとして意味を失います。

</details>

<details>
<summary>問4の解答例</summary>

カバレッジは行が実行されたかどうかしか示さず、正しいと検証したかは示しません。`assert` を書かずに関数を呼ぶだけでも数字は上がります。また、実行された行の中でも、境界値や異常系の入力を試していなければ不具合は残ります。

</details>

## 確認クイズ

### Q1. CI の説明として正しいものはどれですか。

- A. プッシュや PR を合図に、共通の環境でテストを自動実行する仕組み
- B. 本番環境へ自動でデプロイする仕組み
- C. コードの書き方を統一するための設定ファイル

<details>
<summary>答え</summary>

**A** — 自動デプロイ(CD)はこの講座の対象外です。CI は「毎回自動でテストを回す」仕組みです。

</details>

### Q2. CI が赤い PR に対して、してはいけない対応はどれですか。

- A. 急ぎなのでそのままマージする
- B. 落ちたテスト名を添えて相談する
- C. 自分の変更が原因なら直して push し直す

<details>
<summary>答え</summary>

**A** — 赤のままマージすると main が壊れ、main を取り込んだ枝から順に赤くなります。

</details>

### Q3. CI の実行時間が長いと、なぜ問題になりますか。

- A. フィードバックループが伸びて、1回の変更が大きく雑になるから
- B. リポジトリの容量を消費するから
- C. テストの本数が自動的に減るから

<details>
<summary>答え</summary>

**A** — 待ち時間が長いほど PR が大きくなり、レビューの質まで下がります。

</details>

### Q4. CI を速く保つ考え方として正しいものはどれですか。

- A. 単体テストで守れるものは単体テストで守る
- B. E2Eテストを増やして単体テストを減らす
- C. 遅いテストを勘で削る

<details>
<summary>答え</summary>

**A** — ピラミッドの土台を厚くします。減らすときは `--durations` で測ってから決めます。

</details>

### Q5. カバレッジについて正しいものはどれですか。

- A. テストで通った行の割合であり、正しさを検証した証明ではない
- B. 数字が高いほどバグが少ないことの証明になる
- C. assert が無いテストではカバレッジは上がらない

<details>
<summary>答え</summary>

**A** — 通過と検証は別ものです。低い場所を見つける地図として使ってください。

</details>
