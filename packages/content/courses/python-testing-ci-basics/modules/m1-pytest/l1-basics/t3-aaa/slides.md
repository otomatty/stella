## なぜ必要か

- 半年前に書いたテストが、何を確かめているのか読み取れない
- 失敗したとき、どこを直せばいいのか探すところから始まる

<!-- ノート: つかみ。テストは失敗した日に読まれる。書いた日ではなく。ここで結論は言わない。 -->

---

## 結論

**テストは準備・実行・検証(AAA)の3段で構造化すると読みやすくなる**

- **準備・実行・検証** の頭文字(Arrange / Act / Assert)を取って **AAA**
- 3段の順番を崩さないだけで、読む速さが変わる

<!-- ノート: 結論を言い切る。新しい機能ではなく、書き方の型。 -->

---

## 最小のコード

```python
def test_calc_total():
    prices = [100, 200]        # 準備
    total = calc_total(prices) # 実行
    assert total == 300        # 検証
```

- 1行ずつ役割が違う
- 検証は最後にまとめる

<!-- ノート: コメントは説明用。慣れたら空行で区切るだけでよい。 -->

---

## 混ざると読めなくなる

```python
def test_calc_total():
    assert calc_total([100, 200]) == 300
    prices = [100, 200, 400]
    assert calc_total(prices) == 700
```

- 準備と検証が交互に出てきて、話の切れ目が見えない

<!-- ノート: 失敗例枠。これでも動くが、失敗したときに読み解く時間が増える。 -->
