# レッスン1-1 pytest の基本

## このレッスンの目標

- [ ] pytest に見つけてもらえる形でテストを書ける
- [ ] assert で合否を判定させ、失敗時の出力を読める
- [ ] 1テスト1振る舞いを、AAA の3段で書ける

## 1-1-1 pytest はテスト関数を自動で見つける

> **pytestは `test_` で始まる関数を自動で見つけて実行する**

テストを書いたことがない現場では、動作確認用のコードを各自が好きな場所に書いています。実行するたびにコメントを外し、確認が終わったらまたコメントに戻す、という運用です。どれが最新なのかも分かりません。

**pytest** は、Python のテストを実行する道具です。pytest には、テストを登録する作業がありません。**名前が登録そのもの** です。

```python
# test_order.py
def test_calc_total():
    assert calc_total([100, 200]) == 300
```

決まりは2つです。

1. ファイル名を `test_` で始める(**テストファイル**)
2. 関数名を `test_` で始める(**テスト関数**)

この2つを守ったものだけが集められ、ターミナルで `pytest` と打つだけで実行されます。

ファイル名については、既定では `_test.py` で終わる形(`order_test.py` など)も集められます。どちらでも動きますが、**チームで片方にそろえる** ほうが探しやすくなります。この講座は `test_` で始める形に統一します。

名前の決まりから外れると、こうなります。

```python
# orders.py — ファイル名が名前の決まりから外れている
def check_total():  # 関数名も test_ で始まらない
    assert calc_total([100, 200]) == 300
# => 収集されず、テストは 0 個
```

このとき出るのは `collected 0 items` と `no tests ran` です。**テストが失敗したのではなく、1つも集まっていない** 状態です。失敗した `assert` の赤い行は出ないので、出力をざっと眺めただけでは見落とします。実行したテストの数が想定と合っているか、必ず確認してください(pytest は0件のとき終了コード5を返すので、CI では赤くなります)。

## 1-1-2 assert が偽ならテストは失敗する

> **`assert 式` が偽になるとテストは失敗し、期待値と実際の値が表示される**

確認用に `print` を並べる書き方は、出力を人が見比べる必要があります。判定する人がいるので、自動化になっていません。

判定をプログラムに任せるのが `assert` です。

```python
def test_calc_total():
    assert calc_total([100, 200]) == 300
```

`==` の右側、つまり「こうなってほしい値」が **期待値** です。式が真なら何も起きずに合格し、偽なら **テストの失敗** になります。**通った `assert` については何も表示されないのが正しい姿** です(テスト全体の集計は `1 passed` のように表示されます)。

失敗すると、pytest は式を分解して両方の値を並べてくれます。

```text
E       assert 250 == 300
E        +  where 250 = calc_total([100, 200])
```

左が実際に返ってきた値、右が期待値です。`print` を仕込んで回る作業が要らなくなるのが、この機能のいちばんの価値です。出力の詳しい読み方は M2 で扱います。

## 1-1-3 テストは準備・実行・検証の3段で書く

> **テストは準備・実行・検証(AAA)の3段で構造化すると読みやすくなる**

テストは、書いた日ではなく **失敗した日に読まれます**。半年後の自分か、別のメンバーが読みます。そのとき「何を確かめているのか」がすぐ分からないテストは、直す前に読み解く時間がかかります。

そこで、テストの中身を3段に固定します。**準備・実行・検証** の3段で、頭文字(Arrange / Act / Assert)を取って **AAA** と呼びます。

```python
def test_calc_total():
    prices = [100, 200]        # 準備
    total = calc_total(prices) # 実行
    assert total == 300        # 検証
```

新しい機能ではなく、書き方の型です。コメントは説明のために付けていますが、慣れたら空行で区切るだけで十分です。

段が混ざると、話の切れ目が見えなくなります。

```python
def test_calc_total():
    assert calc_total([100, 200]) == 300
    prices = [100, 200, 400]
    assert calc_total(prices) == 700
```

これでも動きますが、準備と検証が交互に現れるため、読むのに時間がかかります。

## 1-1-4 1つのテストは1つの振る舞いだけ検証する

> **1つのテストは1つの振る舞いだけを検証する**

**振る舞い** とは、「こういう入力なら、こうなる」という決まりごと1つのことです。テストは、この振る舞い1つにつき1本書きます。

```python
def test_returns_sum_of_prices():
    assert calc_total([100, 200]) == 300


def test_returns_zero_for_empty_list():
    assert calc_total([]) == 0
```

名前が違うということは、確かめている振る舞いが違うということです。名前は「どうなるか」を書いてください。`test_1` や `test_ok` では、失敗しても何も分かりません。

1本に詰め込むと、次の問題が起きます。

```python
def test_calc_total():
    assert calc_total([100, 200]) == 300
    assert calc_total([]) == 0          # 上が失敗すると実行されない
    assert calc_total([-1]) == 0        # ここも実行されない
```

`assert` は最初に失敗した時点でテストを終わらせます。つまり **後ろの検証は実行されていません**。直したつもりで再実行すると、また別の赤が出る、という往復が起きます。

分けておけば、失敗したテストの名前を見るだけで、どの振る舞いが壊れたのか分かります。

## もっと知りたい人へ

- pytest はクラスにまとめたテスト(`class Test...`)も集めます。この講座では関数だけを使います
- Python 標準ライブラリにも `unittest` というテストの仕組みがあります。書き方は違いますが、考え方はこの講座の内容がそのまま通用します
