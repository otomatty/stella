# 0-1-2
# テストは壊したことに最も早く気づく仕組み

Pythonテスト自動化とCI入門 — Module 0 / レッスン0-1

<!-- ノート: テストを「品質を上げる道具」ではなく「気づく仕組み」として位置づけます。 -->

---

## なぜ必要か

- 直した場所ではなく、関係ないはずの機能が壊れていた
- 気づいたのはリリース後で、原因を探すのに半日かかった

<!-- ノート: つかみ。動いていたものが動かなくなる事故を **デグレ** と呼ぶ、とだけ触れる。ここで結論は言わない。 -->

---

## 結論

**テストは壊したことに最も早く気づく仕組みであり、品質はマージ前に担保する**

- 変更をまとめて取り込む依頼が **プルリクエスト**(PR)
- 取り込む操作が **マージ**。ここを通す前に気づくのが目的

<!-- ノート: 結論を言い切る。テストは品質を作るのではなく、壊れたことを教える。作るのは書く人。 -->

---

## 気づくのが遅いほど高くつく

| 気づく場所 | 直すコスト |
| --- | --- |
| 手元でテスト実行 | 数分 |
| PR のレビュー中 | 数十分 |
| リリース後 | 数日 + 謝罪 |

<!-- ノート: 対比枠。数字は目安だが、桁が変わることを実感させる。手元で回すのが最も安い。 -->
