# レッスン5-1 テストしやすいコードの書き方

## このレッスンの目標

- [ ] 隠れた依存を見つけられる
- [ ] 依存を引数で渡す形に書き換えられる
- [ ] ロジックと I/O を分けて、純粋関数を切り出せる

## 5-1-1 テストしにくさの正体は隠れた依存

> **テストしにくさの正体は、現在時刻・乱数・グローバル変数・外部I/Oといった「隠れた依存」である**

テストを書こうとしたら、そもそも書けない関数に出会うことがあります。これは腕の問題ではなく、**コードの形の問題** です。

引数に現れない依存先を **隠れた依存** と呼びます。呼び出す側から見えないので「隠れた」と言います。関数の外に置いた共有の値が **グローバル変数**、ファイル・通信・画面などのやり取りが **入出力**(I/O)です。

```python
import datetime


def is_campaign_period():
    today = datetime.date.today()   # 隠れた依存
    return today.month == 12
```

この関数は引数を1つも取りませんが、結果は実行した日によって変わります。テストを書いても、12月にしか緑になりません。月が変わったら昨日まで緑だったテストが赤くなる、という事故はここから起きます。

見つけ方は簡単です。**引数が同じでも結果が変わるなら、隠れた依存があります。**

| 合図 | 例 |
| --- | --- |
| 現在時刻・乱数 | `date.today()` / `random` |
| 外の値 | グローバル変数 / 環境変数 |
| 入出力 | ファイル読み書き / 通信 |

## 5-1-2 依存は引数で渡すと差し替えられる

> **依存を引数で渡す(注入する)と、テストのときだけ差し替えられるようになる**

隠れた依存を見つけたあと、やってはいけない対処が2つあります。1つはシステムの日付を変えてテストすること、もう1つはテスト専用の分岐をコードに入れることです。どちらも、テストのために本番の動きを歪めています。

正しい直し方は、**依存先を外から渡す形にする** ことです。これを **依存性の注入** と呼びます。名前は大げさですが、やることは引数を1つ増やすだけです。

```python
import datetime


def is_campaign_period(today):
    return today.month == 12


def test_december_is_campaign():
    assert is_campaign_period(datetime.date(2026, 12, 1)) is True
```

関数の中から `datetime.date.today()` が消えました。**誰が「今日」を知るかを、外へ押し出しただけ** です。テストは好きな日付を渡せるようになり、12月でなくても実行できます。

既存のコードに後から入れるときは、既定値を使う形が便利です。

```python
import datetime


def is_campaign_period(today=None):
    today = today or datetime.date.today()
    return today.month == 12
```

本番のコードは引数なしのまま呼べるので、呼び出し側を全部直す必要がありません。テストのときだけ日付を渡します。

同じやり方が、DB や外部 API にも使えます。依存先を引数で受け取る形にしておけば、テストでは代役(テストダブル)を渡せます。M4 で書いた `to_yen(amount, rate_api)` が、まさにこの形でした。

## 5-1-3 純粋関数が最もテストしやすい

> **入力と出力だけで結果が決まる純粋関数は、最もテストしやすい部品である**

同じ入力なら必ず同じ出力を返す関数を **純粋関数** と呼びます。隠れた依存も、外の状態を変える働きもない関数です。外の状態を変えてしまう働きを **副作用** と言います。

```python
def calc_discount(total, rate):
    return int(total * (1 - rate))


def test_calc_discount():
    assert calc_discount(1000, 0.2) == 800
```

準備も後片付けも要りません。fixture が1本も要らないのが純粋関数のテストです。何度実行しても、どの順で実行しても、同じ結果になります。**最も安く、最も壊れないテスト** が書けます。

一方、副作用がある形はこうなります。

```python
def calc_discount(order):
    order["total"] = int(order["total"] * 0.8)   # 引数を書き換える
```

呼んだあと、渡した側の値まで変わっています。どこで値が変わったのかを追うのが難しくなり、テストでも「呼ぶ前の状態」を毎回作り直す必要が出ます。**戻り値で返せば済む場面で書き換えない** でください。

## 5-1-4 ロジックと I/O を分ける

> **ロジックと入出力(I/O)を分離すると、単体テストで守れる範囲が広がる**

純粋関数がよいと分かっても、実務では保存も通信も必要です。そこで、**混ぜない** という形にします。判断や計算の部分と、読み書きの部分を別の関数に分ける — これが **ロジックとI/Oの分離** です。

よくあるのは、1つの関数に全部入っている形です。

```python
def process(path):
    prices = read_csv(path)              # 入出力
    total = sum(prices) - 100            # 計算
    save_to_db(total)                    # 入出力
```

計算だけを確かめたいのに、ファイルと DB の準備が必要になります。テストが重くなるだけでなく、壊れやすくもなります。

分けるとこうなります。

```python
def calc_total(prices):        # 純粋関数
    return sum(prices) - 100


def process(path):             # I/O を担当
    save_to_db(calc_total(read_csv(path)))
```

計算部分が純粋関数になったので、単体テストで何通りでも確かめられます。残った `process` は読み書きをつなぐだけの薄い関数になり、確かめる中身がほとんど残りません。つなぎ目は結合テスト1本で足ります。

M4 の「単体で守れるものを結合に持ち込まない」は、**そもそも単体で守れる形にしておく** ことで実現できます。テストの書き方の話と、コードの書き方の話は、ここでつながります。

## もっと知りたい人へ

- I/O を外側に集め、中心を純粋関数で固める設計は、いくつかの呼び名で語られます(関数核・命令殻など)。名前より、**どこに副作用があるか説明できる** ことが大事です
- 既存コードに依存性の注入を入れるときは、既定値付きの引数から始めると、呼び出し側を壊さずに少しずつ移行できます
