# Python テスト自動化と CI 入門 カリキュラム

Python で関数やスクリプトは書けるが、テストコードを書いたことがなく、PR で CI が落ちた経験もないメンバー向けの入門講座です。
1 トピック = 覚えることが 1 つ(takeaway 1 文)の粒度で、テストを書く理由 → pytest の書き方 → 失敗の読み方 → CI →
結合テスト → テストしやすい設計 → テスト以外の自動チェック、の順に通します。

- Web(LMS): スライド視聴・まとめ・確認クイズ(合格点 80)
- 手を動かす部分: `practice.md` の「手元で試す」。手元の Python と pytest で実行して確かめる
- コード演習(VS Code 拡張の採点)は **この講座にはありません**。採点基盤(`@falcon/code-runner`)のランナーは
  JavaScript / TypeScript / SQL の 3 つで、Python は対象外です(`@falcon/shared` の `Language` 型)
- 前提講座: **ITのきほん(`it-basics`)**。スキルツリーの入口講座で、コンピュータ・ファイル・Web の基本のことばをそろえてから受講します(`course.json` の `prerequisites` に対応)
- 対象外: デプロイ自動化(CD)、IaC、Docker の詳細、GitHub Actions の高度な構文(matrix・再利用ワークフロー等)、
  AWS 固有のテスト手法(Lambda / Glue、moto / LocalStack)、負荷試験・E2E ツールの実装、lint / 型チェッカーの詳細な設定方法

## 到達目標

1. 関数に対する単体テストを pytest で **書ける**
2. 失敗したテストの出力を読んで原因を **特定できる**
3. 検証したい振る舞いに応じて単体・結合・E2E のどれで守るかを **選べる**
4. PR 時に CI が落ちた理由を **説明できる**
5. 隠れた依存を引数で渡す形に直し、テストしやすいコードに **書き換えられる**

## 全体構成(7 モジュール / 8 レッスン / 28 トピック)

### M0. なぜテストを書くのか — レッスン0-1 テストを書く理由

| ID | トピック | takeaway |
| --- | --- | --- |
| 0-1-1 | 自動テストは一度書けば毎回実行できる | 手動確認は変更のたびに同じコストがかかるが、自動テストは一度書けば毎回実行できる |
| 0-1-2 | テストは壊したことに最も早く気づく仕組み | テストは壊したことに最も早く気づく仕組みであり、品質はマージ前に担保する |
| 0-1-3 | テストピラミッドで割り振りを決める | テストピラミッドでは、速く安い単体テストを土台に、結合・E2E を上に少なく積む |

### M1. pytest でテストを書く — レッスン1-1 pytest の基本

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-1-1 | pytest はテスト関数を自動で見つける | pytestは `test_` で始まる関数を自動で見つけて実行する |
| 1-1-2 | assert が偽ならテストは失敗する | `assert 式` が偽になるとテストは失敗し、期待値と実際の値が表示される |
| 1-1-3 | テストは準備・実行・検証の3段で書く | テストは準備・実行・検証(AAA)の3段で構造化すると読みやすくなる |
| 1-1-4 | 1つのテストは1つの振る舞いだけ検証する | 1つのテストは1つの振る舞いだけを検証する |

### M1. pytest でテストを書く — レッスン1-2 テストケースを充実させる

| ID | トピック | takeaway |
| --- | --- | --- |
| 1-2-1 | 境界値と異常系も同じくらい重要 | 境界値と異常系は正常系と同じくらい重要なテスト対象である |
| 1-2-2 | parametrize で入力データを並べる | parametrizeを使うと、同じ検証を複数の入力データで繰り返せる |
| 1-2-3 | fixture で準備と後片付けを共通化する | fixtureを使うと、テストごとの準備・後片付けを共通化できる |

### M2. 失敗を読んで直す — レッスン2-1 テストの失敗を読んで直す

| ID | トピック | takeaway |
| --- | --- | --- |
| 2-1-1 | 失敗出力は決まった順に読む | 失敗出力は「どのテストが・どの行で・何を期待して・何が返ったか」の順に読む |
| 2-1-2 | 失敗にはバグとテストの誤りがある | テストの失敗には「コードのバグ」と「テスト自体の誤り」の2種類がある |
| 2-1-3 | 再現テストを書いてから直す | 再現手順をテストとして書いてから直すと、同じバグの再発を防げる |

### M3. CI で品質を守る — レッスン3-1 CI で品質を守る

| ID | トピック | takeaway |
| --- | --- | --- |
| 3-1-1 | CI はテストを共通の環境で自動実行する | CIはプッシュやPRを合図に、テストを全員共通の環境で自動実行する仕組みである |
| 3-1-2 | 赤のままマージしない | CIが赤のままマージしないルールが、mainブランチの品質を守る |
| 3-1-3 | CI が遅いと開発が止まる | CIの実行時間が長いと開発が止まるため、速い単体テストを中心に据える |
| 3-1-4 | カバレッジは証明ではなく道具 | カバレッジは品質の証明ではなく、テストされていない場所を見つける道具である |

### M4. つなぎ目を守る — レッスン4-1 結合テストで「つなぎ目」を守る

| ID | トピック | takeaway |
| --- | --- | --- |
| 4-1-1 | 結合テストはつなぎ目の不具合を捕まえる | 結合テストは、部品単体ではなくDBや外部APIとの「つなぎ目」で起きる不具合を検出する |
| 4-1-2 | テストダブルは依存先の代役 | テストダブル(モック等)は、本物の依存先の代わりに振る舞いを差し替える部品である |
| 4-1-3 | 本物かダブルかは不具合の場所で選ぶ | 依存先を本物にするかテストダブルにするかは、検証したい不具合がどこで起きるかで選ぶ |
| 4-1-4 | 単体で守れるものを結合に持ち込まない | 結合テストは遅く壊れやすいため、単体テストで守れるものを結合テストに持ち込まない |

### M5. テストしやすいコード — レッスン5-1 テストしやすいコードの書き方

| ID | トピック | takeaway |
| --- | --- | --- |
| 5-1-1 | テストしにくさの正体は隠れた依存 | テストしにくさの正体は、現在時刻・乱数・グローバル変数・外部I/Oといった「隠れた依存」である |
| 5-1-2 | 依存は引数で渡すと差し替えられる | 依存を引数で渡す(注入する)と、テストのときだけ差し替えられるようになる |
| 5-1-3 | 純粋関数が最もテストしやすい | 入力と出力だけで結果が決まる純粋関数は、最もテストしやすい部品である |
| 5-1-4 | ロジックと I/O を分ける | ロジックと入出力(I/O)を分離すると、単体テストで守れる範囲が広がる |

### M6. テスト以外の自動チェック — レッスン6-1 テスト以外の自動チェック

| ID | トピック | takeaway |
| --- | --- | --- |
| 6-1-1 | lint は実行前に危ない書き方を指摘する | lintは、バグになりやすい書き方をテスト実行前に機械が指摘する仕組みである |
| 6-1-2 | 整形の自動化でレビューが本質に集中する | フォーマッタで整形を自動化すると、レビューが本質的な指摘に集中できる |
| 6-1-3 | 型チェッカーは実行せずに食い違いを見つける | 型ヒントと型チェッカーは、実行しなくても引数や戻り値の食い違いを検出できる |

## この講座の進め方

- 各レッスンは **スライド → まとめ → 確認クイズ** の順で並びます
- `practice.md` の「手元で試す」は、手元の Python と pytest だけで完結します。自動採点はありません
- スマートフォンからでも、スライドとまとめと確認クイズだけで最後まで進められます

## 設計メモ(要件定義からの申し送り)

- **前提講座**: この講座は Python の文法を教えません。関数・引数・戻り値・リスト・辞書・例外の読み書きができる状態を前提にします。
  リポジトリに Python の入門講座が無いため、前提講座 slug の指定は **保留** です。Python 入門講座を追加したら、ここに slug を書いてください
- **語彙台帳は講座をまたぎません**。「テスト」「PR」「CI」などの前提語は、この講座の M0 / M3 で導入し直しています
- **コード演習は配線していません**。理由は上記のとおり採点基盤が Python 非対応のためです。
  Python ランナーが追加されたら、L1-1 / L1-2 に `course.json` の `exercises` を足すのが最初の候補です
- **GitHub Actions の YAML は最小限**にとどめ、L6 のツール名(ruff / mypy 等)も例として触れる程度に抑えています。改訂コストを下げるためです
- **改訂担当者は未記入**です。要件定義シートの問 7 が埋まるまで、この講座は暫定版として扱ってください
