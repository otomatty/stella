# レッスン5-1 テストとデバッグ

## このレッスンの目標

- [ ] テストがリリースの関門になっていることを説明できる
- [ ] テストデータをテストの中で作れる
- [ ] アサーションとデバッグログで、失敗の原因を追える

## 5-1-1 テストがないと本番に出せない

> **Apex は、テストでコードの 75% 以上を通していないと本番組織へ出せない**

他の基盤ではテストは方針ですが、Salesforce では仕組みとして強制されます。テストを工数に入れ忘れると、リリース直前に必ず遅れます。

- **テストクラス** — Apex を動かして結果を確かめるための Apex
- **コードカバー率** — テストで実行された行の割合

```apex
@isTest
private class OrderServiceTest {
  @isTest
  static void countsOrders() {
    // ここで対象のコードを動かす
  }
}
```

`@isTest` はクラスとメソッドの 2 か所に付きます。テストクラス自身はカバー率の分母に入りません。

| 状態 | リリース |
| --- | --- |
| 組織全体 74% | 止まる |
| 組織全体 75% 以上 | 進める |
| 素通しのトリガが 1 つでもある | 止まる |

**全体の数字だけでは足りません。** 通常のクラスはカバー率 0% でも組織全体の平均が 75% を超えていれば通りますが、**デプロイするトリガはどれも最低 1 行は通しておく**必要があります。この講座はトリガを書くので、ここは必ず引っかかります。デプロイ時に実行するテストを指定する方式では、対象の Apex ごとに 75% を求められることもあります。

0-1-3 で「コードには保守の約束が付く」と言ったことの具体形です。数字を満たすだけの空テストを書きたくなりますが、それは 5-1-3 で潰します。

## 5-1-2 テストデータは自分で作る

> **テストは組織のデータを見ないので、必要なレコードはテストの中で作る**

Sandbox では通ったテストが、本番組織へのリリース時に落ちる。手元にあったレコードが向こうには無い、というのが原因です。組織ごとにデータが違う以上、既存データに頼るテストは移した瞬間に壊れます。

**テストデータ** は、テストの中で作るそのテスト専用のレコードです。Apex テストは既定で組織のデータから遮断されているため、どの組織で走らせても同じ結果になります。

```apex
@isTest
static void countsOrders() {
  Account acc = new Account(Name = 'テスト商事');
  insert acc;
  // ここで対象のコードを動かす
}
```

テストの中で `insert` してもロールバックされるので、本番組織に `テスト商事` は残りません。安心して作ってください。

作る件数にも意味があります。

| 作るデータ | 確かめられること |
| --- | --- |
| 1 件 | 動くこと |
| 200 件 | 一括処理になっていること |

4-2-2 の事故は、200 件のテストでしか見つかりません。リストで 200 件作るテストを 1 本入れる習慣をつけてください。

## 5-1-3 アサーションで結果を確かめる

> **実行できたことではなく、期待した値になったことをアサーションで確かめる**

カバー率は 90% あるのにバグがそのまま本番に出た、というのは実際に起きます。テストは全部通っていたのに、です。

**アサーション** は「こうなっているはず」を書いて、違えばテストを失敗させる命令です。アサーションが 1 つも無いテストは、行を通すだけの装置になります。カバー率は稼げますが、何も守りません。

```apex
Order__c saved = [SELECT Status__c FROM Order__c WHERE Id = :order.Id];
Assert.areEqual('受付', saved.Status__c, 'Status が初期化されていない');
```

期待値・実際の値・失敗時のメッセージを渡します。保存後の値を SOQL で取り直してから確かめる点が大事です。変数のままでは、保存されたかどうかを確かめたことになりません。

| テストの中身 | 守れるもの |
| --- | --- |
| 動かすだけ | カバー率 |
| アサーションあり | ふるまい |

カバー率は関門を通るための数字、アサーションは仕様を守るための仕掛けです。目的が違います。1 つのテストにつき、確かめたいことを 1 つ書いてください。

## 5-1-4 デバッグログで実行の跡を読む

> **サーバー上で何が起きたかは、デバッグログを取って読む**

4-1-1 のとおり Apex はサーバー上で動くので、途中で止めて覗くことができません。代わりに **デバッグログ**(実行中の出来事を記録したもの)を読みます。

設定でログを取る対象のユーザと期間を決めると、その人の操作ぶんが残ります。取りっぱなしにはできず、期限が来ると自動で止まります。

自分で印を残すこともできます。

```apex
System.debug('取得件数: ' + rows.size());
```

知りたい値を通り道に置いておく、`printf` デバッグと同じ発想です。テストの中でも同じように使えます。

ログには読む場所があります。

| 見出し | わかること |
| --- | --- |
| `SOQL_EXECUTE_BEGIN` | どのクエリが何回走ったか |
| `LIMIT_USAGE` | 上限をどこまで使ったか |
| `FATAL_ERROR` | どこで止まったか |

4-2-3 の書き方の良し悪しは、ここで数字として見えます。特に `LIMIT_USAGE` は、ループの中の SOQL を見つける最短経路です。
