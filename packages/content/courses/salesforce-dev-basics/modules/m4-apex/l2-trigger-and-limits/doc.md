# レッスン4-2 トリガとガバナ制限

## このレッスンの目標

- [ ] before と after を使い分けてトリガを書ける
- [ ] 200 件の束で呼ばれる前提のコードを書ける
- [ ] ループの中の SOQL / DML を見つけて直せる

## 4-2-1 トリガは保存に割り込む

> **トリガは、レコードの保存の前後に自動で割り込む Apex である**

「商談を保存したら、必ず担当者を埋めておきたい」という要件には、画面から入る経路と取り込みから入る経路の両方があります。どの入口にも効かせるには、保存そのものに割り込む必要があります。

- **トリガ** — 保存のタイミングで自動的に呼ばれるコード
- **before** — 保存される直前。値を書き換えられる
- **after** — 保存された直後。ID が確定している

```apex
trigger OpportunityTrigger on Opportunity (before insert) {
  for (Opportunity opp : Trigger.new) {
    if (opp.OwnerId == null) { opp.OwnerId = UserInfo.getUserId(); }
  }
}
```

**Trigger.new** は、これから保存されるレコードのリストです。`before insert` なので、値を書き換えるだけで保存されます。ここで `update` を呼ぶ必要はありません。

| やりたいこと | 使う側 |
| --- | --- |
| 自分の項目を埋める | before |
| 子レコードを作る | after |

before で自分の項目を直すときに DML を呼ぶと、同じトリガが再び走ります。before は「保存される前の値を触っているだけ」という感覚を持ってください。

2-1-4 で予告したとおり、**トリガは API バージョンに関わらず常にシステムモードで動きます**。保存に割り込む処理は、実行しているユーザに見えないレコードにも触れるということです。トリガから別の Apex を呼び出す場合、その先はその Apex 自身のバージョンと宣言に従うので、切り分けて考えてください。

## 4-2-2 トリガは束で呼ばれる

> **トリガは 1 件ずつではなく、最大 200 件の束で呼ばれる**

画面から 1 件保存するぶんには、何を書いても動いてしまいます。データ取り込みを流した途端に同じコードが落ちる、というのが典型的な事故です。

**バッチサイズ** は、1 回のトリガ実行にまとめて渡される件数です。1,000 件を取り込むと、200 件ずつ 5 回に分けて呼ばれます。`Trigger.new` に 200 件入ってくることを前提に書きます。

```apex
trigger OrderTrigger on Order__c (before insert) {
  Order__c order = Trigger.new[0];   // 危ない
  order.Status__c = '受付';
}
```

これは動きますし、画面から 1 件保存するテストは通ってしまいます。しかし残りの 199 件は無言で処理されません。

```apex
for (Order__c order : Trigger.new) {
  order.Status__c = '受付';
}
```

常にリストとして回し、件数を仮定しません。この形を既定にしてしまえば、件数を気にしなくてよくなります。

## 4-2-3 ループの中に SOQL と DML を置かない

> **SOQL と DML はループの外に出し、ループの中では変数だけを触る**

200 件の束の中で 1 件ずつ親を取りに行くと、SOQL が 200 回になります。上限は 100 回なので、途中で止まります。4-2-2 の束と 0-1-2 の上限が、ここで正面からぶつかります。

- **ループ** — リストの要素を 1 つずつ処理するくり返し
- **マップ** — 鍵と値の組で持っておく入れ物

危ない書き方はこうなります。

```apex
for (Order__c order : Trigger.new) {
  Account acc = [SELECT Name FROM Account WHERE Id = :order.AccountId__c];
  order.AccountName__c = acc.Name;
}
```

ループの回数だけ SOQL が走ります。開発組織の数件では動いてしまうのが厄介なところです。

まとめて取ってから回す形に直します。

```apex
Map<Id, Account> accounts = new Map<Id, Account>(
  [SELECT Name FROM Account WHERE Id IN :accountIds]);
for (Order__c order : Trigger.new) {
  order.AccountName__c = accounts.get(order.AccountId__c).Name;
}
```

`IN` 句にリストを渡してまとめて取り、マップで引きます。SOQL は 1 回、ループの中は変数の操作だけです。この「先に集める → 回す」が一括処理の型です。

## 4-2-4 制限を超えたときに起きること

> **ガバナ制限を超えると例外が起き、そのトランザクションは丸ごと巻き戻る**

![1つのトランザクションの中で2件保存したあと上限を超えると、保存した2件も巻き戻ることを示した図](t4-governor-limits/assets/rollback.svg)

取り込みが失敗したとき、一部だけ入っているのか全部戻ったのかで復旧の手順が変わります。

- **例外** — 処理を続けられないときに投げられる異常の知らせ
- **ロールバック** — その処理でのデータの変更を、すべて無かったことにすること

中途半端な状態が残らないのは救いでもありますが、「一部だけ入る」ことを期待した設計はできません。

```apex
try {
  // ここで SOQL の回数が上限を超えると
} catch (Exception e) {
  // ここには入ってこない
}
```

普通の例外と違い、ガバナ制限の例外は `try` で受け止められません。回避策を書く場所は無く、書き方を直すしかありません。

| 対処 | 効くか |
| --- | --- |
| 例外を捕まえる | 効かない |
| 上限を引き上げる | できない |
| ループの外に出す | これだけ |

マルチテナントの基盤である以上、上限は交渉の対象になりません。だから作法が要ります。
