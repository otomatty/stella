# レッスン4-1 別の文脈に渡す

## このレッスンの目標

- [ ] サブエージェントが何を返す相手かを説明できる
- [ ] メインの文脈を汚さない仕組みを説明できる
- [ ] 渡してよい仕事かどうかを判断できる

## 4-1-1 サブエージェントは別の相手

> **サブエージェントは、任せた仕事を別の会話として進めて、結果だけを返す相手です**

CLAUDE.mdとSkillは「指示の紙」の話でした。3つ目の入れ物は毛色が変わって、相手が増える話です。

大きめの仕事では、調べものと本題が1つの会話に混ざっていきます。「この調べもの、誰かに頼んで結果だけ教えてほしい」。人のチームなら自然にやっている切り出しです。

**サブエージェント** は、その切り出しの相手です。**任せる**(仕事を切り出して渡し、進め方は相手に委ねること。講座4で扱った語です)と、任せた仕事を別の会話として進め、**結果**(まとめの報告)だけを返します。

```text
自分            「この修正の前に、既存の使われ方を調べて」

メインの会話      調べものをサブエージェントへ切り出す
サブエージェント   別の会話でファイルを読み回る
メインの会話      「使われ方は3か所。一覧はこれ」という結果を受け取る
```

Claude Codeの中に、別の会話で働くもう1人がいるイメージです。切り出しの判断はメインのClaudeがしますが、依頼の中で「先に調べて」と促すこともできます。

| | メインの会話でやる | サブエージェントに任せる |
| --- | --- | --- |
| 進む場所 | いまの会話の中 | 別の会話 |
| 戻ってくるもの | 途中経過も全部 | 結果だけ |

「結果だけ」が何を守ってくれるのか。それが次のトピックです。

## 4-1-2 メインの文脈を汚さない

> **調べた中身はサブエージェント側に残り、メインの会話には結果だけが戻ります**

講座4で、会話が長くなるほどコンテキストの余裕が減ることを学びました。実は、コンテキストを一番食う作業が調べものです。30ファイルを読めば、その中身が全部いまの会話に積もります。本題に戻るころには、残りが心細くなっています。

サブエージェントは、この費用の払い先を変えます。**メインの会話**(自分が本題を進めている、もとの会話)ではなく、切り出された別の会話が読む費用を払うのです。

```text
サブエージェント側   30ファイルを読んだ中身で埋まる
                  → この会話は結果を返したら役目を終える

メインの会話       受け取るのは結果の数行だけ
                  → コンテキストはほぼ減っていない
```

読んだ中身はサブエージェント側の文脈に残り、メインには報告の数行だけが届きます。大量に読む費用を、使い捨ての会話に払わせる構図です。

| | メインで調べる | サブエージェントで調べる |
| --- | --- | --- |
| 調べた中身 | メインに全部積もる | 向こう側に残る |
| メインのコンテキスト | 大きく減る | ほぼ減らない |
| 本題への影響 | 余裕がなくなる | 保たれる |

「メインの文脈を汚さない」とは、この表の右列のことです。サブエージェントを使う理由を1つだけ挙げるなら、これです。

## 4-1-3 向くのは調査と検証

> **サブエージェントに向くのは、読む量が多くて結果を短く言える調査や検証の仕事です**

「別の会話に切り出せる」と知っても、何を切り出すべきかは別の問題です。なんでも渡すと、かえって結果待ちと説明のやり直しが増えます。

向いているのは2種類です。**調査**(現状を調べて報告する仕事。「どこで使われているか」「どう動いているか」)と、**検証**(決めた観点で確かめて合否を報告する仕事。「規約に沿っているか」)です。

```text
調査  「この関数の使われ方を全部調べて、一覧にして」
      読む: 大量 / 返す: 一覧の数行

検証  「この差分が命名規約に沿っているか確かめて」
      読む: 差分+規約 / 返す: 合否と指摘の数行
```

共通点は「入りは大きく、出は小さい」。読むのは30ファイル、報告は5行、という形です。メインでやればコンテキストを大きく食い、しかも結果は短く言える。だから、報告だけ受け取る形が一番得をします。

| 問い | 向いている答え |
| --- | --- |
| 読む量は多いか | 多い |
| 結果は短く言えるか | 数行で言える |
| 進め方を途中で相談したいか | しなくてよい |

3問目が「いいえ」と言い切れない仕事もあります。それを次のトピックで扱います。

## 4-1-4 向かないのは対話が要る仕事

> **途中で相談しながら進めたい仕事は、サブエージェントに渡さずメインの会話で進めます**

切り出しの便利さを知ると、本題の設計や修正まで渡したくなります。しかし渡してみると、途中で口を挟めないことが急に不便になります。

**相談**(進め方の選択肢を見て、その場で決めるやり取り)が要る仕事は、サブエージェントに向きません。別の会話で進むということは、途中が見えず、口も挟みにくいということだからです。利点の裏返しが、そのまま欠点になります。

```text
向かない  「この機能の設計を決めて実装まで進めて」
         → 分かれ道で相談したいのに、途中では口をはさめない

向く     「実装の前に、似た機能の作りを調べて一覧にして」
         → 分かれ道がなく、報告を待つだけでよい
```

講座4で「ずれたら途中で止めて直す」という舵取りを学びました。その舵取りをしたい仕事は、自分の目の届くメインの会話に置くべきです。

同じ本題でも、相談が要る部分と要らない部分に割れます。割ってから、要らない側だけを渡すのがうまい使い方です。

| 問い | 渡してよい答え |
| --- | --- |
| 結果は短く言えるか | 言える |
| 途中の分かれ道はあるか | ない |
| 失敗してもやり直せるか | 調べ直せばよいだけ |

## 4-1-5 役割はファイルで定義できる

> **よく任せる役割は、frontmatterにnameとdescriptionを書き、本文に指示を置いたファイルとして定義できます**

サブエージェントを使い込むと、また既視感のある症状が出てきます。「規約の検証役」を頼むたびに、観点と報告の形を毎回説明しているのです。毎回説明するなら、それはもう繰り返しの指示に戻っています。

答えはこの講座でもう2回使った型と同じです。ファイルに書いて置きます。

よく任せる **役割**(決まった観点で働く係。「検証役」「調査役」のような肩書き)は、Markdownファイルとして定義しておけます。Skillと同じく、先頭の **frontmatter**(`---` で挟んだYAML)に `name` と `description` を書き、その下の **本文** に係への指示を書きます。`指示:` のようなキーは使いません。

```markdown
---
name: naming-checker
description: 差分の命名を規約と照らして確かめたいときに使う
---

規約の一覧と照らし、違反と直し方だけを短く報告する。
```

置き場所の例:

```text
プロジェクト用  .claude/agents/naming-checker.md
個人用         ~/.claude/agents/naming-checker.md
```

置き場所と形式は変わりうるので、実際に作るときは製品のドキュメントでも確認してください。

一度書けば、「検証役に見てもらって」で通じるようになり、説明の抜けによるぶれも消えます。

| | 毎回説明する | ファイルで定義する |
| --- | --- | --- |
| 手間 | 呼ぶたびに観点を書く | 一度書けば呼ぶだけ |
| ぶれ | 説明の抜けで変わる | 揃う |
| 共有 | できない | リポジトリでチームに配れる |

リポジトリに入れてチームに配れるのも、Skillと同じです。これで4つの入れ物のうち3つが、ファイルとして手元に揃いました。

## もっと知りたい人へ

- 直近の仕事から「読む量が多くて、結果は短く言えた調べもの」を1つ思い出してください。それがサブエージェントに渡す最初の候補です
- 定義ファイルの正確な形式・置き場所・指定できる項目は製品側で変わっていきます。実際に使うときは、製品のドキュメントで確認してください
