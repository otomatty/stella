# レッスン3-1 SKILL.mdを書く

## このレッスンの目標

- [ ] SKILL.mdの構成(frontmatter+本文)を説明できる
- [ ] いつ使うかが照らせるdescriptionを書ける
- [ ] 参照ファイルへの分け方と、共有の置き場所を選べる

## 3-1-1 Skillの正体はSKILL.md

> **Skillの正体は、決まったフォルダに置いたSKILL.mdというMarkdownのファイルです**

「Skillを作る」と聞くと、何か特別な開発が要りそうに聞こえます。実際は違います。

Skillの正体は、**Markdown**(見出しや箇条書きを書ける、ただのテキストの書き方)で書かれた **SKILL.md** という名前のファイルです。Skill 1つにつき **フォルダ**(ファイルをまとめる入れ物)を1つ作り、その中にSKILL.mdを1枚置きます。

```text
リポジトリの中
└── .claude/skills/         ← Skill置き場(執筆時点の例)
    └── review-pr/          ← Skill 1つ = フォルダ1つ
        └── SKILL.md        ← 中身はここに書く
```

この形だけ覚えれば十分です。Skill置き場は執筆時点では `.claude/skills/` ですが、パスは変わりうるので、実際に作るときは製品のドキュメントでも確認してください。

| | CLAUDE.md | SKILL.md |
| --- | --- | --- |
| 実体 | Markdownのファイル | Markdownのファイル |
| 枚数 | 直下から始める(複数可) | Skillごとに1枚 |
| 置き方 | リポジトリ直下 | Skillごとのフォルダの中 |

実体がただのテキストなので、コードと同じようにレビューも履歴管理もできます。プログラムを書く必要はありません。

## 3-1-2 frontmatterが入り口

> **SKILL.mdの先頭にはfrontmatterとして、名前と、いつ使うかが分かるdescriptionを書きます**

Module 2 で、Skillが選ばれるかどうかはdescriptionで決まると学びました。そのdescriptionの書き場所が、SKILL.mdの先頭にある **frontmatter** です。Markdownの先頭に `---` で挟んで書く、決まった形の情報のことです。

書くのは2つ。**名前**(そのSkillを指す短い呼び名)と、descriptionです。

```text
---
name: review-pr
description: プルリクエストのレビューを頼まれたときに使う。
  観点の順番と指摘の書き方をまとめた手順書。
---
```

決まった枠に入っているから、Claudeは全Skillの背表紙を一覧できます。descriptionは「いつ使うか」と「何の手順書か」の2点が入っていれば合格です。

| description | 判定 |
| --- | --- |
| 「レビューを頼まれたときに使う。観点の順番の手順書」 | いつ使うかが照らせる |
| 「レビューについて」 | いつ使うかが分からない |
| 「チームの便利メモ」 | 何のタスクかも分からない |

書き方のコツは、「〜を頼まれたときに使う。」で書き始めることです。これだけで、依頼と照らせる文になります。

## 3-1-3 本文は手順を順番に書く

> **SKILL.mdの本文には、人に引き継ぐつもりで手順を1つずつ順番に書きます**

frontmatterの下に続く、手順書の中身が **本文** です。

手順が頭の中にあるうちは書ける気がするのに、いざ書くと「いい感じにやって」になりがちです。曖昧な手順書は、読んだ相手の解釈次第で結果がぶれます。

基準は1つだけ持てば足ります。**新しく入った同僚が、これだけ読んで同じ作業をできるか。** 読み手はClaudeですが、書く基準は人への引き継ぎと同じです。人が読んで曖昧な手順は、Claudeが読んでも曖昧です。

```text
## レビューの手順

1. 変更の目的を、プルリクエストの説明から1文で把握する
2. 差分を読み、動きが変わる箇所を先に確認する
3. 細かい書き方の指摘は、動きの確認が終わってから
4. 指摘には、理由と直し方の例を必ず添える
```

番号付きで、1行に1つの手順。対象と動作をはっきり書いた短い文にします。使うのはMarkdownの見出しと箇条書きだけです。

| 書き方 | 判定 |
| --- | --- |
| 「差分を読み、動きが変わる箇所を先に確認する」 | 順番と対象が明確 |
| 「差分をいい感じに確認する」 | 解釈が読み手任せ |
| 「レビューは丁寧にやる」 | 手順になっていない |

「いい感じ」「丁寧に」という言葉が出てきたら、具体的な動作に割る合図です。

## 3-1-4 長い資料は参照ファイルへ

> **長い資料は参照ファイルに分けてSKILL.mdから指し示すと、要るぶんだけ読まれます**

手順書は育ちます。観点表、命名規則の一覧、用語集。足していくと、SKILL.mdは何百行にもなります。しかし、毎回のタスクで使うのはそのうちの一部だけです。

CLAUDE.mdで見た「詰め込みすぎ」は、SKILL.mdの中でも起きるのです。

逃がし先が **参照ファイル** です。SKILL.mdと同じフォルダに置く、補助資料の別ファイルのことです。SKILL.md側には「どんなときにどれを見るか」の1行だけを書きます。

```text
review-pr/
├── SKILL.md            手順(短い)
│     「命名の判断に迷ったら naming.md を見る」
├── naming.md           命名規則の一覧(長い)
└── checklist.md        観点の詳細一覧(長い)
```

手順書の本冊と、付録の分冊の関係です。分冊の読み込みは、その付録が要るときだけ起きます。

| | 1枚に全部書く | 参照ファイルに分ける |
| --- | --- | --- |
| Skillを使うときの読み込み | 全部 | 手順+要る分冊だけ |
| 資料の育てやすさ | 育つほど重くなる | 分冊だけ育てられる |

「要るときだけ読む」というSkillの利点を、Skillの中でも入れ子で効かせる考え方です。

## 3-1-5 リポジトリに入れて共有する

> **リポジトリに入れたSkillはチームの共有になり、個人用のSkillは自分だけに効きます**

書けた手順書を、どこに置くか。CLAUDE.mdのときと同じ論点が、Skillにもあります。

置き場所は2種類あります。リポジトリの `.claude/skills/<名前>/SKILL.md` に置くと、クローンしたチーム全員に同じ手順書が届きます。CLAUDE.mdと同じ、コードと同じ配り方です。プルリクエストで直せて、履歴も残ります。

もう1つが **個人用** です。`~/.claude/skills/<名前>/SKILL.md` に置くと、どのプロジェクトでも自分の会話にだけ効きます(正確なパスは製品のドキュメントで確認してください)。

```text
チームに配る   リポジトリの中のSkill置き場に入れる
             → クローンした全員に同じ手順書が届く

自分だけ      リポジトリの外の自分の領域に置く
             → どのプロジェクトでも自分にだけ効く
```

どちらが正しいという話ではなく、効かせたい相手で選びます。

| Skill | 置き場所 |
| --- | --- |
| チームのレビュー手順 | リポジトリ(共有) |
| チームのリリース前チェック | リポジトリ(共有) |
| 自分の実験中の手順書 | 個人用 → 育ったら共有へ |

実験は個人用で始めて、効くと分かったらリポジトリに入れて配る。この流れが安全です。チームと個人の線引きの判断は、Module 5 でもう一度扱います。
