# レッスン2-1 Skillという入れ物

## このレッスンの目標

- [ ] Skillがいつ効く入れ物かを説明できる
- [ ] descriptionの役割を説明できる
- [ ] CLAUDE.mdとSkillを効くタイミングで置き分けられる

## 2-1-1 Skillはタスクのときだけの手順書

> **Skillは、特定のタスクのやり方をまとめた手順書で、そのタスクのときだけ効きます**

Module 1 の最後で、CLAUDE.mdから追い出したものがありました。特定の作業のときだけ要る手順です。その行き先が **Skill** です。

Skillは、特定の **タスク**(依頼して進めるひとまとまりの仕事。講座4で扱った語です)のやり方をまとめた **手順書** です。CLAUDE.mdが「毎回の約束の紙」なら、Skillは「作業ごとの手順書」。棚に並べておき、合うタスクのときだけ取り出されます。

例はどれも、どの言語のプロジェクトでも成り立つものにします。

```text
レビュー手順          プルリクエストを見るときの観点の順番
コミットメッセージの型  1行目の形式と、本文に書くこと
リリース前チェック     出す前に確かめる項目の一覧
```

共通するのは「毎回ではないが、そのタスクでは毎回同じやり方をしてほしい」という性質です。

| | CLAUDE.md | Skill |
| --- | --- | --- |
| 中身 | 毎回の約束 | タスクのやり方 |
| 効くとき | 毎回 | 合うタスクのときだけ |
| 数 | まず直下に1枚(階層で足せる) | タスクの種類ごとに増やせる |

「タスクの種類ごとに増やせる」は大きな性質です。手順書が10冊に増えても、取り出されるのは合う1冊だけ。なぜそれで平気なのかは、このレッスンの後半で分かります。

## 2-1-2 descriptionが呼び出しの鍵

> **ClaudeはdescriptionというSkillの説明文と依頼を照らして、使うSkillを自分で選びます**

手順書を棚に置いたとして、誰が取り出すのでしょうか。「このSkillを使って」と毎回自分で指定するなら、消したはずの繰り返しが戻ってきてしまいます。

取り出すのはClaudeです。各Skillは **description** という説明文を持ちます。そのSkillが何のためのもので、いつ使うかを書いた、棚の背表紙にあたる文です。Claudeは **依頼**(タスクを頼むときに書く文。講座4で扱った語です)とdescriptionを照らして、いまのタスクに合うSkillを自分で選びます。

```text
依頼          「このプルリクエストをレビューして」

descriptionの例 「プルリクエストのレビューを頼まれたときに使う。
               観点の順番と指摘の書き方をまとめた手順書」

→ 照らして合う → このSkillが選ばれて使われる
```

だからdescriptionには「いつ使うか」が書かれている必要があります。中身がどれだけ良くても、背表紙が曖昧だと棚から出てきません。

| descriptionの書き方 | 結果 |
| --- | --- |
| 「レビューを頼まれたときに使う」 | レビューの依頼で選ばれる |
| 「便利な手順いろいろ」 | いつ使うか照らせず、選ばれない |

descriptionの実際の書き方は Module 3 で扱います。

## 2-1-3 要るときだけ読み込まれる

> **Skillの中身が読み込まれるのは使うときだけで、増やしてもふだんの費用は短いdescriptionのぶんだけです**

ここで、Module 1 を思い出した人は疑問を持つはずです。CLAUDE.mdでは、書くほどに毎回のコンテキストが削られました。手順書をタスクの種類ごとに増やしたら、同じ問題が起きないのでしょうか。

中身については、起きません。ここがSkillとCLAUDE.mdの根本的な違いです。

**読み込み**(ファイルの中身が **コンテキスト**〈Claudeが一度の会話で読める量。講座4で扱った語です〉に入ること)のタイミングが違います。ふだんの会話に入っているのは、各Skillの短いdescriptionだけです。中身の読み込みは、そのSkillが選ばれて使われるときだけ起きます。

```text
ふだんの会話       Skill 10個ぶんのdescription(各1〜2行)だけ

レビューの依頼が来た  レビュー手順のSkillだけ中身が読み込まれる
                   残り9個は背表紙のまま
```

10個に増えても、毎回の費用は背表紙10行ぶんです。中身の長さは、使うときにしか払いません。descriptionのぶんの費用はゼロではないので、使わなくなったSkillを棚から下ろす手入れは要ります。

| | CLAUDE.md | Skill |
| --- | --- | --- |
| 毎回入るもの | 全文 | descriptionだけ |
| 中身の読み込み | 毎回 | 使うときだけ |
| 増やしたときの費用 | 全会話に効く | ほぼ増えない |

これで、置き分けの理屈がつながりました。毎回効くものは全文入りのCLAUDE.mdへ。タスクの手順は、要るときだけ開くSkillへ。

## 2-1-4 CLAUDE.mdとの違いは効くタイミング

> **毎回効かせたい約束はCLAUDE.mdに、タスクのときだけ効かせたい手順書はSkillに置き分けます**

CLAUDE.mdもSkillも「指示を先に置く」点は同じなので、初めは区別がつきにくいものです。しかし区別を間違えると、Module 1 で見た「埋もれるCLAUDE.md」に逆戻りします。

そこで、この2つの **使い分け**(同じ指示を、効くタイミングで置き先に振り分けること)を1枚の判断に固めます。問いはいつも1つです。「これは毎回か、タスクのときだけか」。

```text
「コメントは日本語で」            毎回         → CLAUDE.md
「テストは bun run test で」     毎回         → CLAUDE.md
「レビューはこの観点の順で」       レビューのとき → Skill
「リリース前はこの項目を確認」     リリースのとき → Skill
```

4つとも大事な指示です。大事かどうかでは分けられません。いつ効いてほしいかだけが線になります。

置き間違えると、それぞれにはっきりした症状が出ます。

| 間違い | 症状 |
| --- | --- |
| 手順書をCLAUDE.mdに | 毎回のコンテキストが減り、約束が埋もれる |
| 毎回の約束をSkillに | そのタスク以外で効かず、ぶれが戻る |

症状から逆に、置き間違いに気づくこともできます。「約束が守られない」ならCLAUDE.mdが長すぎないか。「タスクによって挙動がぶれる」なら、毎回効かせたいものがSkillに入っていないか。

## もっと知りたい人へ

- 自分のチームの「手順書」にあたるもの(レビュー観点、リリース手順、命名規則の適用手順)を思い出して、Skill候補の一覧を作ってみてください。Module 3 でそのまま1つを書きます
- Skillの選ばれ方・読み込みの正確な仕様は製品側で変わっていきます。実際に使うときは、製品のドキュメントで確認してください
