# レッスン5-1 どの入れ物に置くか

## このレッスンの目標

- [ ] 効くタイミングで4つの入れ物を選べる
- [ ] 詰め込みの症状に気づいて、手順書をSkillへ移せる
- [ ] チームに載せる範囲と個人用の範囲を分けられる

## 5-1-1 迷ったら効くタイミングで決める

> **置き場所に迷ったら、その指示がいつ効いてほしいかという効くタイミングで決めます**

4つの入れ物が出そろいました。仕上げに、判断を1本に束ねます。

入れ物を4つ知った今こそ、「どれに置くか」で手が止まりやすくなります。機能の印象や内容の重要さで選ぶと、後から置き間違いの症状に悩まされます。

**置き場所**(その指示を仕組みとして置く先)を決める最初の1問は、いつも同じです。「これはいつ効いてほしい?」

```text
いつ効いてほしい?
  毎回効く             → CLAUDE.md
  タスクのとき          → Skill
  別の文脈で(調べる間)   → サブエージェント
  必ず実行(例外なく)     → hook
```

Module 0 の4句(毎回効く / タスクのとき / 別の文脈で / 必ず実行)が、そのまま答えの並びです。

この4行が、この講座の持ち帰りです。1問目で4つのうち1つに落ちます。

迷いが残るのは、たいてい「毎回かタスクのときか」の境目です。そのときは「それ以外の作業のときにも要るか」と問い直します。

| 迷う指示 | 問い直し | 答え |
| --- | --- | --- |
| 「テストのコマンド」 | どの作業でも使う? | 使う → CLAUDE.md |
| 「レビュー観点」 | レビュー以外でも要る? | 要らない → Skill |

## 5-1-2 詰め込みが一番の失敗

> **一番多い失敗は、CLAUDE.mdへの手順書の詰め込みで、どの約束も効きにくくなります**

使い分けを学んでも、現場のCLAUDE.mdは自然と太っていきます。「1か所に全部あるほうが分かりやすい」という善意が原因なので、気づきにくいのです。

効くタイミングの違うものを1つの入れ物に全部書くことを、**詰め込み** と呼びます。代表例が、CLAUDE.mdへの手順書の詰め込みです。手順書が全部CLAUDE.mdにあると、Skillの出番がなくなり、毎回の約束は埋もれ、どの指示も効きにくくなります。

症状は分かりやすいものです。

```text
症状  CLAUDE.mdが100行を超えている
      「書いてあるのに守られない」が増えた
      リリース手順・調査手順・レビュー観点が同居している

処方  手順書をSkillへ移す → 毎回の約束だけが残る
```

処方は消すことではなく、**移すこと** です。手順書はSkillでこそ効きます。

| | 詰め込んだCLAUDE.md | 移した後 |
| --- | --- | --- |
| CLAUDE.md | 100行 | 毎回の約束 10行 |
| 手順書 | 埋もれている | Skillとして要るときだけ効く |
| 毎回のコンテキスト | 100行ぶん消費 | 10行+背表紙だけ |

移すだけで、両方の入れ物が本来の効き方に戻ります。この棚卸しを定期的にやるのが、チームの手入れです。

## 5-1-3 チームに載せる範囲を分ける

> **チームの全員に効かせたい仕組みはリポジトリに載せ、自分の好みは個人用に置きます**

いつ効くかで入れ物を選んだら、もう1本の軸で置き場所を選びます。誰に効かせるか、です。

よくある間違いは2方向あります。自分の **好み**(正解が1つでない、自分のやりやすさのための設定)をチームのリポジトリに入れてしまう。逆に、全員に要る約束が誰かの手元にだけあって、配られていない。

問いはこうです。「これは全員で揃えるべきか、自分の勝手でよいか」。見分けの目安は「他の人が違うやり方をしていたら困るか」です。困るなら揃える、困らないなら好みです。

```text
チーム(リポジトリ)   テストのコマンド、レビュー手順のSkill
                    命名規約、検証役の定義

個人用              説明は箇条書きでという口調の好み
                    自分の実験中のSkill
```

| 間違い | 症状 |
| --- | --- |
| 好みをリポジトリに | 他人の環境に自分の癖を押しつける |
| 全員に要る約束を手元に | 自分だけ守られて、チームは揃わない |

リポジトリに入れるものはレビューを通す、という運用にしておくと、この間違いは自然に濾されます。Module 3 の「実験は個人用で始めて、育ったら共有へ」も、この線引きの実践です。

## 5-1-4 必ず守らせたいことはhookへ

> **破られると困る決まりは、指示ではなく必ず実行されるhookにする道があります**

最後に、指示という道具の限界の話をします。

CLAUDE.mdに太字で書いても、指示は読んで従うものである以上、読み落としがゼロにはなりません。「ほぼ守られる」で足りるものは、それで十分です。しかしプロジェクトには、「たまに破られる」では困る **決まり**(例外なく守られてほしいルール)がいくつかあります。「コミット前に必ず整形する」「機密のファイルには触れない」のようなものです。

そこで4つ目の入れ物、hookの出番です。指示は読んで従うもの、hookは決めた操作を機械的に実行するもの。実行される仕掛けなので、読み落としという抜け道がありません。

```text
指示で書く   「コミット前に整形コマンドを実行してね」
            → ほぼ守られる。でも、たまに抜ける

hookにする   コミット前に整形コマンドが自動で実行される
            → 抜けようがない
```

| 内容 | 置き先 |
| --- | --- |
| 文体・観点など、ずれても直せるもの | CLAUDE.md / Skill |
| 整形・検査など、抜けた1回が困るもの | hook |

hookの作り方は次の講座で扱います。この講座で持ち帰るのは判断だけです。これで4つの入れ物の地図がすべて埋まりました。

繰り返しに気づいたら、仕組みにする。迷ったら、いつ効いてほしいかで決める。誰に効かせるかで置き場所を分ける。この3つが、この講座の締めくくりです。

## もっと知りたい人へ

- チームのCLAUDE.mdがあるなら、「毎回の約束」と「手順書」に線を引いてみてください。手順書側が多ければ、Skillへの引っ越しを提案する良い機会です
- hooksの書き方・イベントの種類・設定の形式は次の講座の範囲です。急ぐ場合は製品のドキュメントで確認してください
