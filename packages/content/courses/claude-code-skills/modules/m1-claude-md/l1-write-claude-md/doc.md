# レッスン1-1 CLAUDE.mdを書く

## このレッスンの目標

- [ ] CLAUDE.mdがいつ読み込まれるかを説明できる
- [ ] CLAUDE.mdに書くもの・書かないものを選べる
- [ ] 短く保つ理由をコンテキストの語で説明できる

## 1-1-1 CLAUDE.mdは毎回読み込まれる

> **作業フォルダとその上位のCLAUDE.mdは会話の始まりに読み込まれ、プロジェクトの約束を書くファイルです**

「毎回効く」入れ物の正体から始めます。

**CLAUDE.md** は、名前のとおりのただのテキストの **ファイル**(中身が保存されている入れ物)です。特別な登録の操作は要りません。**作業フォルダ**(Claude Codeを起動したときのカレントディレクトリ)と、その **上位**(親フォルダ側)の階層にあるCLAUDE.mdは、Claude Codeとの **会話**(ひと続きのやり取り。講座4で扱った語です)の始まりに、毎回自動で読み込まれます。

書く内容は、**プロジェクト**(1つの開発対象のまとまり)で毎回守ってほしい **約束** です。作業フォルダより下の階層(子フォルダ側)に置いたCLAUDE.mdは、会話の始まりには読まれません。その配下のファイルをClaudeが触るときに読み込まれます。個人用の `~/.claude/CLAUDE.md` もありますが、まずはリポジトリ直下から始めれば十分です。

```text
CLAUDE.md の中身の例

# このプロジェクトの約束
- テストは bun run test で走らせる
- コメントとコミットメッセージは日本語で書く
```

飾りのない箇条書きで十分です。これだけで、どの会話でもClaudeは最初からこの約束を知っている状態になります。

| | 依頼に毎回書く | CLAUDE.mdに書く |
| --- | --- | --- |
| 効くのは | 書いた会話だけ | すべての会話 |
| 読み込み | 自分が書いたとき | 会話の始まりに自動 |
| 忘れると | その回だけ抜ける | 忘れる余地がない |

0-1-1で見た「仕組みに置く」の、これが1つ目の実体です。

## 1-1-2 リポジトリに置いて共有する

> **プロジェクトのCLAUDE.mdはリポジトリの直下に置き、チームの共有の約束にします**

次は置き場所です。自分の手元だけで効く形にしてしまうと、隣の人のClaude Codeは別の動きをします。「あの約束はどこに書いてあるのか」が人によって違うと、直すときにも揃いません。

プロジェクトの約束は、プロジェクトの **リポジトリ**(ファイル一式の置き場。講座4で扱った語です)に置きます。場所は直下、READMEの隣です。

```text
リポジトリ直下
├── CLAUDE.md      ← ここに置く
├── README.md
└── src/
```

リポジトリに入れれば、クローンした **チーム**(同じプロジェクトを触る人たち)の全員のClaude Codeが、同じ約束を読みます。これが **共有**(全員が同じものを使う状態)です。コードと同じ配り方なので、約束の変更もコードと同じくレビューを通して進められます。

| | 自分の手元だけ | リポジトリの直下 |
| --- | --- | --- |
| 効く相手 | 自分だけ | クローンした全員 |
| 直すとき | 全員がばらばらに直す | 1ファイルを直して配れる |
| 約束のずれ | 人ごとに起きる | 起きにくい |

自分だけの好みをどこに置くかは、Module 5 で扱います。

## 1-1-3 書くのは毎回効く約束だけ

> **CLAUDE.mdに書くのは、どの作業のときにも毎回効いてほしい約束だけです**

白紙のCLAUDE.mdを前にすると、思いついたことを何でも書きたくなります。基準がないと、後で見返しても消せません。

採用の基準は、M0の背骨がそのまま使えます。効くタイミングです。**作業**(修正・調査・レビューなど、依頼して進めるひとまとまりの仕事)を思い浮かべて、「これはどの作業でも効いてほしいか?」と1問だけ問います。

```text
どの作業でも効く       テストは bun run test で走らせる
                     コメントは日本語で書く
                     3つのアプリの役割(1行ずつ)

特定の作業のときだけ    リリース前の確認は…(手順が10行)
                     障害調査のときは、まずログを…
```

下の2つが悪い指示なのではありません。毎回は効かない指示なので、この入れ物ではない、というだけです。

何から書けばよいか迷ったら、この3種類から始めれば十分です。

| 種類 | 例 |
| --- | --- |
| よく使うコマンド | テスト・ビルドの走らせ方 |
| 書き方の約束 | コメントの言語、命名の方針 |
| プロジェクトの地図 | フォルダの役割を1行ずつ |

どれも、どの作業でも最初に知っていてほしいことです。

## 1-1-4 短く保つ

> **CLAUDE.mdは毎回コンテキストに入るので、読んで守れる長さに短く保ちます**

効いてほしい約束を足し続けると、CLAUDE.mdは自然に長くなります。そして長くなったころ、「書いてあるのに守られない」約束が増えてきます。

理由は、起動時に読み込まれるという性質の裏返しです。作業フォルダとその上位のCLAUDE.mdは毎回 **コンテキスト**(Claudeが一度の会話で読める量のこと。上限があります。講座4で扱った語です)に入ります。つまり、長さはタダではありません。

```text
10行のCLAUDE.md    どの約束もよく効く
                  コンテキストの残りも十分

100行のCLAUDE.md   大事な約束が他の行に埋もれる
                  どの会話でも100行ぶんを毎回消費する
```

行数そのものが基準ではありませんが、量には費用があります。埋もれた約束は、書いていないのと同じになります。

だから、CLAUDE.mdは一度書いたら終わりのファイルではなく、コードと同じように手入れするファイルです。

| 習慣 | やること |
| --- | --- |
| 足すとき | 既にある約束を1つ消せないか探す |
| 見返すとき | 守られていない約束を消すか言い換える |
| 迷うとき | 「これがないと毎回困るか?」と問う |

消すことは失敗ではなく、手入れです。

## 1-1-5 手順書を書かない

> **特定の作業のときだけ要る手順は、CLAUDE.mdに書かずタスク向けの入れ物に置きます**

CLAUDE.mdを壊す一番の原因を、先に禁じ手として覚えておきます。**手順**(作業を進める順番を書いたもの。「まずAして、次にB」の形)の書き込みです。

「リリース前の確認手順」をCLAUDE.mdに全部書きたくなります。書けば書くほど安心な気がします。しかし、手順が効くのはその作業のときだけです。毎回は効かないものを、毎回読む場所に置くと、こうなります。

```text
CLAUDE.mdに手順を足していくと

リリース手順 12行  ← リリースのとき以外は無駄に読む
障害調査手順 15行  ← 調査のとき以外は無駄に読む
毎回の約束    5行  ← 32行の中に埋もれる
```

手順そのものには価値があります。置き場所のせいで、毎回のコンテキストを削り、肝心の毎回の約束を埋もれさせてしまうのです。

| 書くもの | 置き場所 |
| --- | --- |
| どの作業でも効く約束 | CLAUDE.md |
| 特定の作業の手順 | タスク向けの入れ物(Skill) |

M0の地図のとおり、タスクのときだけ効く入れ物が別にあります。手順の行き先であるSkillを、次のモジュールで正面から扱います。

## もっと知りたい人へ

- 自分のプロジェクトにCLAUDE.mdが既にあるなら、声に出して読める長さかを確かめてみてください。長ければ、Module 5 の「削る」演習の材料になります
- CLAUDE.mdは複数置けます。作業フォルダとその上位に置いたものは会話の始まりに読み込まれ、下位の階層に置いたものはその配下を触るときに読み込まれます。モノレポではパッケージごとに下位へ足していく使い方もあります。個人用の `~/.claude/CLAUDE.md` も持てます。迷ったら、まずはリポジトリ直下から始めてください
